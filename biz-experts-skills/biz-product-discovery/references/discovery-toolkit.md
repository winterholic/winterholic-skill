# 발견 툴킷 — 인터뷰 스크립트·가정 매핑·실험 설계

> biz-product-discovery 심화 참조. Teresa Torres *Continuous Discovery Habits* 계보. 프레임은 2026-07 웹 검증. 실무 바로 투입용.

## 목차
1. 기회 솔루션 트리(OST) 실전 작성
2. 인터뷰 스크립트 (오프닝→스토리 유도→마무리, 그대로 읽는 문장)
3. 인터뷰 스니펫 → 기회 추출 (합성 절차)
4. 가정 매핑 — 4유형 × 위험도 매트릭스
5. 실험 설계 카탈로그 (가정 유형별 최소비용 실험)
6. 리스크 우선순위 매트릭스 (무엇부터 검증)
7. 발견 흔한 실수
8. 출처

## 1. 기회 솔루션 트리(OST) 실전 작성 (Torres, 2016)

```
[Outcome 원하는 결과]  — 사업/제품 지표 1개 (예: D7 리텐션 25%→35%)
   │
   ├─ [기회 A] 사용자 니즈/페인 (인터뷰 증거에서)
   │     "신규 사용자가 첫 주에 '핵심 가치'를 못 느껴서 안 돌아온다"
   │        ├─ 솔루션 A1 · 솔루션 A2 · 솔루션 A3   (한 기회에 3개+ 발산)
   │        │      └─ 실험(가장 위험한 가정 검증)
   │        └─ …
   ├─ [기회 B] …
   └─ [기회 C] …
```

### 작성 규칙 (실무)
- **위→아래 단방향**: 솔루션을 기회 없이 매달지 않는다(그러면 feature factory).
- **기회는 니즈 언어로**: "알림 기능이 없다"(솔루션 부재)가 아니라 "언제 다시 봐야 할지 몰라 놓친다"(니즈).
- **기회는 인터뷰 인용에 앵커**: 각 기회 노드에 실제 사용자 발화 1개를 붙인다. 없으면 그건 가설이지 기회 아님.
- **기회끼리 MECE 지향**: 형제 기회는 겹치지 않게(중복이면 상위로 묶기).
- **한 번에 한 기회만 공략**: 트리에서 영향×시장크기×전략적합으로 1개 선택 → 그 아래만 솔루션 발산.

> OST는 2016년 Torres가 제시(원문 발행 정확 월/일은 개정판 리다이렉트로 미확정, "2016년"까지 확정). 지금은 outcome 지향 팀의 표준 발견 산출물. https://www.producttalk.org/opportunity-solution-trees/

## 2. 인터뷰 스크립트 (과거 스토리 기반 — 그대로 읽는 문장)

목표: 의견·미래 예측이 아니라 **가장 최근의 구체적 실제 행동**을 캔다.

### 오프닝 (라포·프레이밍, 2분)
> "오늘은 제품 얘기보다 [관련 상황]에서 어떻게 하시는지가 궁금해요. 정답은 없고, 최근에 실제로 있었던 일을 그냥 이야기해 주시면 됩니다. 편하게요."

### 스토리 유도 (핵심 — 12~15분)
> "가장 최근에 [관련 상황]하셨던 때가 언제였어요? 그날 처음부터 끝까지, 무슨 일이 있었는지 순서대로 말씀해 주실 수 있을까요?"

추적 질문(스토리가 멈출 때마다):
- "그 다음엔 어떻게 하셨어요?" (행동 체인 추적)
- "그때 무엇을 하려고 하셨던 거예요?" (의도)
- "무엇이 막았나요? / 어떻게 해결하셨어요?" (마찰·우회)
- "그 순간 어떤 기분이었어요?" (감정 = 페인 신호)
- "그거 하기 전에 마지막으로 뭘 하셨어요?" (트리거 역추적)

### 마무리 (2분)
> "제가 놓친 게 있을까요? 이 얘기 중에 더 하고 싶은 게 있으세요?"

### 절대 금지 문장 (유도·가상)
- ❌ "이 기능 있으면 좋겠죠?" (유도)
- ❌ "X 쓰실 건가요?" (미래 예측 — 사람은 미래 행동을 과대 보고)
- ❌ "Y 불편하지 않으세요?" (원하는 답 심기)
- ❌ "저희가 Z를 만들 건데 어떠세요?" (가설 노출 → 예의상 긍정)

> 근거: Torres/Young — 신뢰할 단서는 "무엇을 원하는가"가 아니라 "실제로 무엇을 했는가". https://www.lennysnewsletter.com/p/teresa-torres-on-how-to-interview

## 3. 인터뷰 스니펫 → 기회 추출 (합성 절차)

인터뷰 직후(기억 신선할 때) 24시간 내 합성. 녹취만 쌓지 말 것.

### 인터뷰 스냅샷 양식 (그대로 채움)
```
대상: ______ (세그먼트/맥락)   일시: ______
표면 요청: 그가 말한 것 ("X 버튼 있으면…")
그 밑 니즈(job): 실제로 이루려던 것
결정적 순간: 막힌/우회한 지점 (인용문 그대로)
놀란 점(insight): 예상과 달랐던 것
→ 기회 트리 매핑: [기회 노드] 신규 or 기존 강화
```

### 기회로 승격하는 기준
- **반복성**: 여러 사용자에서 같은 페인이 나오면 기회, n=1은 가설.
- **니즈로 표현**: 솔루션이 아니라 "무엇에 막히나"로.
- **행동 근거**: 실제 스토리에서 관찰됨(진술만이 아니라).

## 4. 가정 매핑 — 4유형 × 위험도 (Torres)

각 솔루션 뒤엔 "참이어야 성공하는 가정"이 숨어 있다. 유형별로 훑어 빠짐없이 꺼낸다.

| 유형 | 질문 | 예시 가정 |
|---|---|---|
| **Desirability 욕구** | 사람들이 원할까? | "사용자가 개인화 다이제스트를 열어볼 것이다" |
| **Usability 사용성** | 쓸 줄 알까? | "설정 없이도 첫 화면에서 기능을 찾을 것이다" |
| **Feasibility 실현성** | 만들 수 있나?(+법/보안/컴플라이언스) | "실시간 추천을 200ms 안에 낼 수 있다" |
| **Viability 사업성** | 사업에 맞나? | "이 기능이 이탈을 막아 LTV를 올린다" |

### 실전 순서
1. 선택한 솔루션마다 **스토리맵**을 그려 desirability·usability·feasibility 가정을 뽑고,
2. **OST의 선(line)을 따라 걸으며** viability 가정을 뽑는다(Torres의 "walk the lines").
3. 각 가정을 아래 매트릭스에 배치.

## 5. 실험 설계 카탈로그 (가정 유형별 최소비용 실험)

**원칙: 코드가 가장 비싼 검증 수단.** 가장 위험한 가정을 가장 싼 실험으로 먼저.

| 가정 유형 | 싼 실험 | 성공 신호(사전 정의) |
|---|---|---|
| Desirability | Fake door / 랜딩페이지 / 스모크 테스트 | 클릭률·이메일 등록률 X% 이상 |
| Desirability | "이걸 만들기 전에 열어볼까?" — 알림 문구 A/B | 오픈율 |
| Usability | 종이·클릭 프로토타입 5인 사용성 테스트 | 5명 중 4명이 무도움 완수 |
| Feasibility | 기술 스파이크(타임박스 2일) | 200ms 내 응답 재현 |
| Feasibility | Wizard of Oz(뒤에서 사람이 수동 처리) | 수동으로도 가치 전달되나 |
| Viability | 콘시어지(소수에게 수동 서비스) | 유료 전환·유지 관찰 |
| Viability | 가격 민감도 설문/프리오더 | 실제 결제 의향(카드 등록) |

### 실험 설계 양식
```
가정: ______ (유형: D/U/F/V)
위험도: 틀리면 얼마나 비싼가 (상/중/하)
불확실도: 지금 얼마나 모르나 (상/중/하)
실험: ______ (가장 싼 방법)
성공 신호: ______ (숫자로, 실험 전에 못박기)
기간/비용: ______
```

> 성공 신호를 **실험 전에** 숫자로 못박는다 — 사후에 정하면 확증편향으로 아무 결과나 "성공" 해석.

## 6. 리스크 우선순위 매트릭스 (무엇부터 검증)

```
        불확실도 高
          │  ②먼저 검증    │  ①즉시 검증(최우선)
위험도 低 ├───────────────┼──────────────── 위험도 高
          │  ④무시/후순위  │  ③검증 or 완충설계
        불확실도 低
```
- **① 위험 高 × 불확실 高**: 틀리면 비싸고 지금 모른다 → 가장 먼저, 가장 싸게 실험.
- **② 위험 低 × 불확실 高**: 배움은 있으나 급하지 않음.
- **③ 위험 高 × 불확실 低**: 안다면 완충 설계로 관리.
- **④ 위험 低 × 불확실 低**: 그냥 진행.

"가장 위험한 가정(riskiest assumption)"이란 ①사분면 = 틀렸을 때 프로젝트를 죽이는데 아직 증거가 없는 것.

## 7. 발견 흔한 실수
1. **솔루션을 기회로 위장** — "알림 기능 없음"은 기회가 아니라 솔루션 부재. 니즈로 다시 쓴다.
2. **미래 질문** — "쓰실 건가요?"는 무의미(과대 보고). 과거 스토리만.
3. **인터뷰 후 합성 스킵** — 녹취만 쌓이고 결정에 안 쓰임. 24h 내 스냅샷.
4. **성공 신호 사후 정의** — 실험 후 결과에 맞춰 해석. 사전에 숫자로.
5. **가장 위험한 가정 대신 쉬운 가정 검증** — 검증하기 편한 것부터 하면 정작 죽는 가정을 놓침. 위험도×불확실도 매트릭스로 강제.
6. **한 번의 큰 리서치로 끝** — 발견은 매주 소량 지속(듀얼트랙, evidence 4 참조).
