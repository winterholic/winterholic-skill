# 마이크로카피 패턴 라이브러리 (상태별 ❌/✅)

> biz-ux-writer 실무 레퍼런스. 상태별로 공식·안티패턴·복사용 예시를 모았다.
> 출처는 각 절 하단. 1차·공식 스타일가이드 우선. 검증일 2026-07-01.
> 한국어 예시는 원칙을 한국어 UI에 적용한 것(원문 인용이 아님). 원칙 자체의 출처만 표기.

---

## 0. 공통 원칙 (모든 문구에 선적용)

권위 스타일가이드가 반복해서 요구하는 5가지 — 개별 패턴보다 먼저 통과시켜야 한다.

1. **명확함 > 영리함.** "clear than entertaining" — 재미보다 명확이 항상 우선(Mailchimp).
2. **능동태 + 평이한 언어.** 격식체·긴 단어 금지. "구매하다→사다", "지원하다→돕다"(GOV.UK plain English).
3. **사용자 시점 2인칭 "당신/여러분".** 앱이 사용자에게 직접 말하듯(Material). 단 한국어 UI는 2인칭 대명사를 자주 생략(높임 어미로 대체).
4. **긍정형으로.** 실패를 알릴 때도 "다시 시도" 같은 회복 경로 중심(Material: "Try again" > "The action failed").
5. **소리내어 읽기.** "Read it out loud. Does it sound like something a human would say? Ship it."(Shopify Polaris).

- Mailchimp Content Style Guide — Voice and Tone: https://styleguide.mailchimp.com/voice-and-tone/
- GOV.UK — Words to avoid / plain English: https://www.gov.uk/guidance/style-guide/a-to-z
- Material Design — Writing: https://m1.material.io/style/writing.html
- Shopify Polaris — Actionable language: https://polaris.shopify.com/content/actionable-language

## 1. 에러 메시지

**공식: [무슨 일이 났는지] + [왜(가능하면)] + [어떻게 고칠지] + (안심).**
- 비난 금지("잘못 입력하셨습니다" ❌). 원인은 시스템/상황에 둔다.
- 에러 코드·전문용어는 전면에 두지 않는다(접힘 상세로).
- "field(필드)" 같은 반복 단어 넣지 않기(GOV.UK).
- 톤 전환: 평소 캐주얼 → 에러에선 "supportive and detailed"(지지적·자세히)(Material).

| 상황 | ❌ | ✅ |
|---|---|---|
| 이메일 형식 | "잘못된 입력입니다" | "이메일 형식이 올바르지 않아요. 예: name@example.com" |
| 필수 미입력 | "이 필드는 필수입니다" | "이메일을 입력해주세요" |
| 서버 오류 | "Error 500 / Null pointer" | "일시적인 문제가 생겼어요. 잠시 후 다시 시도해주세요. (문제가 계속되면 고객센터로 문의)" |
| 결제 거절 | "결제 오류 (code 402)" | "카드 승인이 거절됐어요. 한도를 확인하거나 다른 카드로 다시 시도해보세요. (요금은 청구되지 않았어요.)" |
| 비밀번호 규칙 | "비밀번호가 유효하지 않습니다" | "비밀번호는 8자 이상, 숫자를 하나 이상 포함해주세요" |
| 네트워크 끊김 | "네트워크 에러" | "인터넷 연결이 끊겼어요. 연결을 확인하고 다시 시도해주세요" |

**막히면(원인을 사용자에게 못 밝힐 때)**: "일시적인 문제예요, 잠시 후 다시" + 재시도 CTA. 코드는 접힘 상세.

> 출처: NN/g Error Message Guidelines(Neusesser & Sunwall, 2023) https://www.nngroup.com/articles/error-message-guidelines/ · Material(긍정형·톤전환) https://m1.material.io/style/writing.html · GOV.UK(field 금지·plain English) https://www.gov.uk/guidance/style-guide/a-to-z · Readability Guidelines(무슨 일·왜·해결) https://readabilityguidelines.co.uk/clear-language/error-messages/

## 2. 빈 상태(Empty State)

빈 상태는 신규 사용자가 거의 항상 보는 첫 화면 — 온보딩 기회다. **[여기 무엇이 올지] + [첫 행동 CTA].**

두 종류를 구분한다:
- **최초 사용(아직 만든 게 없음)**: 격려 + 첫 행동 유도.
- **결과 0(필터·검색 결과 없음)**: 조건이 문제임을 알리고 초기화 경로 제공.

| 종류 | ❌ | ✅ |
|---|---|---|
| 최초·프로젝트 | 흰 화면 / "데이터 없음" | "아직 프로젝트가 없어요. 새 프로젝트로 시작해보세요 [새 프로젝트]" |
| 검색 결과 0 | "결과 없음" | "'{검색어}'에 대한 결과가 없어요. 다른 키워드로 검색해보세요" |
| 필터 결과 0 | (빈 표) | "조건에 맞는 항목이 없어요 [필터 초기화]" |
| 받은 알림 0 | "알림 없음" | "새 알림이 여기 표시돼요. 지금은 확인할 게 없어요" |

## 3. 성공·확인(토스트/스낵바)

**[무슨 일이 됐는지] + (되돌리기 있으면 노출).** 경쾌·간결(1줄).
- 파괴적 작업 직후엔 되돌리기(Undo)를 함께 — 확인 다이얼로그를 대체할 수 있어 마찰이 준다.

| 상황 | ❌ | ✅ |
|---|---|---|
| 저장 | "작업이 성공적으로 완료되었습니다" | "저장됐어요" |
| 삭제 | "삭제 완료" | "항목을 삭제했어요 [실행 취소]" |
| 전송 | "전송에 성공하였습니다" | "메시지를 보냈어요" |
| 복사 | (무반응) | "링크를 복사했어요" |

**막히면(후속 행동이 있을 때)**: 다음 단계 CTA를 붙여 흐름 유지("초대를 보냈어요 [멤버 더 초대]").

## 4. 버튼·액션 라벨

**결과를 말하는 동사 + 목적어.** 모호한 "확인/제출/예" 금지.
- 문장은 동사로 시작 — "지시"처럼 읽히게(Polaris: "Start sentences with verbs").
- "you can…" 같은 완충어 제거, 직접 명령형(Polaris: "add apps" not "you can add apps").
- 라벨은 매우 짧게, 1~3단어(Material). 영문은 sentence case(첫 단어·고유명사만 대문자), ALL CAPS 금지(Material).

| 맥락 | ❌ | ✅ |
|---|---|---|
| 폼 제출 | "제출" / "확인" | "가입하기" / "결제하기" / "저장하기" |
| 무료 체험 | "예" / "확인" | "무료로 시작하기" |
| 파일 추가 | "추가할 수 있어요" | "파일 추가" |
| 다이얼로그 | "확인 / 취소" | (질문에 답하는 동사 — 아래 5절) |

**막히면(공간 부족)**: 동사 우선 한 단어("저장"). 아이콘 단독 버튼은 `aria-label` 필수(3절 접근성).

> 출처: Podmajersky *Strategic Writing for UX*(결과 동사) · Shopify Polaris https://polaris.shopify.com/content/actionable-language · Material(sentence case·1~3단어) https://m1.material.io/style/writing.html

## 5. 확인 다이얼로그(삭제·되돌릴 수 없는 작업)

**질문에 답이 명확한 두 라벨.** "확인/취소" 금지 — 어느 쪽이 무엇인지 헷갈려 오작동을 부른다.
- 제목은 도입 상투어 생략, 바로 질문("저장할까요?" — Material: "Save changes?" not "Would you like to save?").
- 결과(되돌릴 수 없음)를 본문에 명시.

```
❌  제목: "확인"
    본문: "정말 하시겠습니까?"
    버튼: [확인] [취소]

✅  제목: "이 프로젝트를 삭제할까요?"
    본문: "삭제하면 관련 파일이 모두 사라지고 복구할 수 없어요."
    버튼: [삭제하기] [그대로 두기]
```

**막히면(고위험·대량 삭제)**: 위험 쪽 버튼을 시각적으로 덜 강조 + 텍스트 입력 확인(프로젝트 이름 재입력)을 고려.
파괴 후 되돌리기(Undo) 토스트로 확인 다이얼로그 자체를 줄일 수 있으면 그쪽이 마찰이 적다.

## 6. 폼 — 라벨 · 헬프텍스트 · 플레이스홀더

- **라벨은 항상 노출**(플레이스홀더로 라벨을 대체하지 않는다 — 입력 시작하면 사라져 접근성·기억 부담).
- **헬프텍스트**: 규칙·형식을 미리(에러 전에) 안내. "8자 이상, 숫자 포함".
- **플레이스홀더**: 예시(`예: 010-1234-5678`)에만. 지시("여기에 입력") 금지.
- 선택 항목은 라벨에 "(선택)" 표기 — 필수를 별표(*)로만 표기하면 색맹·스크린리더에서 놓친다.

| 요소 | ❌ | ✅ |
|---|---|---|
| 라벨 | (플레이스홀더만) "이름" | 라벨 "이름" + 필드 |
| 헬프텍스트 | (없음, 에러로만 규칙 전달) | "숫자 포함 8자 이상" |
| 플레이스홀더 | "이름을 입력하세요" | "예: 홍길동" |
| 선택 필드 | "회사" (필수처럼 보임) | "회사 (선택)" |

---

## 7. 삭제·파괴 확인 카피 어조

- 사실·결과 중심, 감정 유발 금지.
- "복구할 수 없어요" 같은 결과를 분명히 — 그러나 겁주기(FUD)가 아니라 정보로.
- 되돌릴 수 있으면 그 사실을 알려 안심시킨다("30일 후 완전 삭제, 그 전엔 복구 가능").

---

## 8. 로딩·대기

- 안심 + (가능하면) 이유·소요. "불러오는 중… 잠시만요".
- 오래 걸리면 진행률/단계 표시. 무한 스피너만 두지 않는다.
- 긴 작업 완료 후엔 성공 토스트로 확실히 닫아준다.

## 실전 카피 리뷰 체크리스트 (소리내어 읽으며)

- [ ] **결과 동사인가** — 버튼이 "무엇을 하는지" 말하나("확인" ❌)
- [ ] **사용자 언어인가** — 내부용어·전문용어 0("엔티티/레코드/큐" ❌)
- [ ] **비난 없나** — 에러가 사용자 탓처럼 들리지 않나
- [ ] **원인+해결 있나** — 에러에 다음 행동이 있나
- [ ] **능동태·평문인가** — 격식체·긴 단어 없나(GOV.UK)
- [ ] **긍정형인가** — 실패보다 회복 경로 중심(Material)
- [ ] **다크패턴 없나** — 거절 버튼 흐리기·죄책감 유발 없나(→ voice-tone.md 4절)
- [ ] **텍스트만으로 의미 통하나** — "여기 클릭/더 보기" 없나(→ voice-tone.md 3절 접근성)
- [ ] **선택지 라벨이 동등한가** — 확인 다이얼로그 양쪽이 명확한 동사인가
- [ ] **현지화 대비** — 길이 늘어도 깨지지 않나, 문자열 결합 없나(→ voice-tone.md 5절)
- [ ] **사람이 말하듯인가** — 소리내어 읽어 자연스러운가(Polaris)
