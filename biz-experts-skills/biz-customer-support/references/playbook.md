# biz-customer-support — 실무 플레이북

> 일류 지원 운영자의 실전 절차. 근거는 `evidence.md`. 수치는 출발점(조직별 튜닝, 확인 필요).

---

## 1. 티켓 분류·트리아지 (Triage)

문의가 들어오면 두 축을 **분리**해서 판단한다(ITIL 4: severity와 priority는 다른 개념).

- **Impact(영향 범위)**: 몇 명? 매출·법·평판 영향? 전체 장애 vs 개인.
- **Urgency(긴급도)**: 지금 막혔나 vs 대기 가능한가.
- **Priority = Impact × Urgency** — 이 매트릭스로 P1~P4 산출.

트리아지 체크:
1. 카테고리 태깅(제품 영역·문의 유형) — VOC 집계의 기반이므로 **초기 태깅 품질이 전부**.
2. 우선순위 산정(아래 SLA 표).
3. 중복·기존 티켓 병합(같은 장애의 폭주는 하나의 상위 인시던트로 링크).
4. 셀프서비스로 해결 가능한지 먼저 판단(단순 정보성 → KB 링크 + 매크로).

---

## 2. SLA / SLO 설계

**참고 우선순위 매트릭스**(ITIL/업계 관행, 조직별 튜닝 — 확인 필요):

| 등급 | 정의(예시) | 첫응답(ack) | 해결 목표 | 에스컬레이션 |
|---|---|---|---|---|
| **P1** 크리티컬 | 전면 장애·데이터 손실·다수 영향 | ≤15분 | 1~2시간(무중단 대응) | 분류 즉시 시니어+매니지먼트 자동 |
| **P2** 높음 | 핵심 기능 저하·단일 중요 시스템 다운 | ≤1시간 | 4~8시간 | 목표 초과 임박 시 |
| **P3** 보통 | 부분 불편·우회 존재 | ≤4시간 | 24~48시간 | 필요 시 |
| **P4** 낮음 | 문의·개선 요청 | ≤1영업일 | 백로그 | — |

설계 원칙:
- **채널별로 FRT 목표가 달라야 함**(챗 초 단위 vs 이메일 시간 단위). 단일 SLA 강제는 함정.
- **응답 SLA ≠ 해결 SLA** 분리. 빠른 첫응답이 미해결을 가리지 않게 해결 SLA·재문의율을 병행.
- **에스컬레이션 트리거는 사고 전에 정의** — 발생 후 협상 금지. P1은 분류 시점 자동 승급.
- SLA "달성률"만 보지 말 것: 목표 직전에 형식적 응답만 찔러넣는 게이밍(SLA gaming)을 재문의율·CES로 감시.

## 3. 디플렉션 & 셀프서비스 전략

목표: **쉬운 문의를 사람 손에서 떼어내 사람이 어렵고 감정적인 케이스에 집중**하게.

계층:
1. **인앱 컨텍스트 도움말**(문제 발생 지점에서 바로) — 최고의 디플렉션은 문의가 뜨기 전.
2. **KB/헬프센터**(검색 최적화, 최신성 유지) — 오래된 KB는 오히려 재문의 유발.
3. **챗봇/AI 응답** — 정보성·FAQ에 한정. 행동·감정 케이스는 사람으로 핸드오프.
4. **커뮤니티/포럼**(피어 답변).

디플렉션 카운트 규칙(중요):
- ✅ **진짜 해결 + 후속 문의 없음**일 때만 디플렉션으로 인정.
- ❌ KB 페이지뷰, 답 못 찾고 이탈, 봇에서 좌절 후 재문의 → 디플렉션 아님(부풀림).
- 검증 지표: 셀프서비스 세션 후 **72시간 내 티켓 생성률**(낮아야 진짜 디플렉션).

## 4. 응대: 공감 → 해결 (Effortless)

CEB 연구의 실전 번역 — **고노력의 4대 신호를 응대에서 제거**:
1. **채널 전환 금지**: 고객을 다른 채널로 떠넘기지 말고 현 채널에서 끝낸다.
2. **정보 반복 금지**: 이전 문의·계정 맥락을 상담원이 미리 확보(재질문 최소화).
3. **이관(transfer) 최소화**: 첫 상담원이 소유권(ownership)을 갖고 해결하거나 백엔드로 조용히 연결.
4. **Next Issue Avoidance**: 이번 문제 + "곧 물어볼 다음 문제"까지 선제 안내(예: 배송 지연 응대 시 반품 기한도 함께).

응대 순서: **① 공감·상황 인정 → ② 소유권 선언("제가 확인해 드릴게요") → ③ 실제 해결 → ④ 차기이슈 선제 안내 → ⑤ 마무리 확인.**

## 5. 매크로 / 캔드 리스폰스 작성 원칙

- **적합 대상**: 정보성·반복 문의(환불 정책, 배송 조회 방법 등). ❌ 행동·감정·복잡 케이스에 통짜 매크로 금지.
- **개인화 필드**: 이름·주문번호·계정 맥락 머지 필드 필수 — "form letter"처럼 읽히면 실패.
- **구조**: 개인화 인사 → 이슈 재진술·인정 → 공감 한 줄 → 해결/다음 단계 → 소유권·후속.
- **effort 감소가 목적**: 매크로 때문에 고객이 더 헤매면(재문의) 실패. 매크로별 CSAT/재문의율 태깅해 나쁜 매크로 폐기.
- 최신성 오너 지정: 제품 변경 시 관련 매크로·KB 동시 갱신(오너 없으면 부패).

## 6. 지표 대시보드 (관계와 함정)

| 지표 | 뜻 | 함정 |
|---|---|---|
| **FRT** 첫응답시간 | 최초 사람 응답까지 | 자동응답을 FRT로 세면 무의미. 채널별로 목표 분리 |
| **AHT** 평균처리시간 | 상담원이 티켓에 쓴 시간 | **낮을수록 좋다는 착각** — 대충 닫으면 재문의로 총비용↑ |
| **TTR** 해결시간 | 완전 해결까지 | 대기(고객 응답 대기) 시간 제외해야 공정 |
| **FCR** 최초해결률 | 첫 접촉에 해결(~70~80% 양호) | 재문의 정의 애매하면 조작 가능. 72시간/7일 창으로 고정 |
| **CSAT** | 응대 만족(top-box %) | 만족 스냅샷일 뿐 **충성도 예측 약함** |
| **CES** | 노력 척도(v2.0 7점 동의) | **충성도/재구매 예측력 최상** — 서비스 상호작용의 북극성 후보 |

**황금률**: 속도 지표(FRT·AHT) 단독 최적화는 CEB가 명시한 함정. 반드시 **해결 지표(FCR·재문의율·CES)와 짝**으로 본다.

## 7. Tier 구조 & 에스컬레이션

- **Tier 0**: 셀프서비스(KB·봇). **Tier 1**: 일반 상담(정보성·표준). **Tier 2**: 기술·복잡. **Tier 3**: 엔지니어링·전문(버그·인시던트).
- **일선 재량(empowerment)**: Tier 1에 소액 환불·재발송 등 **재량 한도** 부여 → 뺑뺑이(안티패턴 5) 제거. 권한 없는 일선은 고객 노력을 폭증시킨다.
- **에스컬레이션은 조용히**: 고객에게 "다른 팀으로 넘길게요"보다 뒤에서 연결하고 소유권은 유지(채널 전환·이관 = 고노력 신호).
- **인시던트 대응(P1)**: 상위 인시던트로 통합 → 상태 페이지·정기 업데이트 → 사후 포스트모템.

## 8. VOC (Voice of Customer) 루프

지원은 고객 목소리의 최전선. **수집 → 태깅 → 분석 → 액션 → 루프 클로징**의 폐루프로 운영.

1. **수집**: 모든 티켓·이탈 사유·저CES 코멘트.
2. **태깅**: 공유 택소노미(제품 영역·테마·근본원인)로 일관 분류 — 태깅 표준 없으면 집계 불가.
3. **분석**: 상위 문의 원인 트렌드 → 제품·문서·UX 신호.
4. **액션**: 반복 원인을 제품 개선·KB·인앱 도움으로 환류(문의 자체 제거 — 안티패턴 3).
5. **루프 클로징**: 바꾼 것을 고객·조직에 되알림("반영했습니다"). 조용한 개선은 절반의 VOC.

정기 리듬: 주간 상위 문의 리포트 → 제품·CS에 공유, 월간 근본원인 리뷰.

---

## 9. 흔한 실수 (체크리스트)

- [ ] 속도 지표(FRT/AHT)만 KPI로 잡음 → 재문의 폭증 (해결 지표 병행하라)
- [ ] 매크로를 감정·복잡 케이스에 통짜로 붙임 → 분노 증폭
- [ ] 반복 문의를 매번 개별 응대만 → VOC 환류 없이 부하 무한 증가
- [ ] 디플렉션을 KB 페이지뷰로 셈 → 실제 이탈을 성과로 착각
- [ ] 채널 전환·이관·정보 반복 요구 → CEB 고노력 4대 신호 그대로 밟음
- [ ] 일선 재량 0 → 모든 걸 위로 떠넘겨 고객 뺑뺑이
- [ ] 단일 SLA를 전 채널 강제 → 채널 기대 무시
- [ ] KB·매크로 오너 없음 → 제품 변경 후 방치·부패
