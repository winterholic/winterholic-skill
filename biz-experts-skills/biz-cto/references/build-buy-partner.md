# build vs buy vs partner — 3자 의사결정

> "직접 만들까 사올까"는 2지선다가 아니다. **build / buy / partner** 3자로 본다.

## 1. 1차 필터: 해자 판정
가장 먼저 던지는 질문 하나: **"이게 우리의 경쟁 해자(competitive moat)인가?"**
- **예** → build 후보. 여기가 차별화의 원천이면 통제권을 가져야 한다.
- **아니오** → buy/partner 디폴트. 공통 기능(인증·결제·이메일·로그·모니터링·검색 인프라)에 엔지니어를 쓰면 그만큼 제품이 늦어진다.

> Werner Vogels(AWS CTO)의 유명한 원칙과 상통: "차별화되지 않는 무거운 짐(undifferentiated heavy lifting)"은 위임하라. (개념 참조, 정확 인용 확인 필요)

## 2. 3자 판정 매트릭스
| 축 | build | buy | partner |
|---|---|---|---|
| 전략적 중요도 | 최고(해자) | 낮음(공통) | 높지만 역량 없음 |
| 사내 역량 | 있음 | 불필요 | 없음/부족 |
| 시장 진입 속도 | 느려도 됨 | 즉시 필요 | 즉시+리스크 분담 |
| 통제권 필요 | 완전 통제 | 위탁 가능 | 공동 |
| 대표 형태 | 직접 개발 | SaaS·OSS·라이선스 | 공동개발·화이트라벨·리셀러·JV |

## 3. TCO(총소유비용) — build의 숨은 비용
build 결정의 진짜 비용은 초기 개발이 아니라 **영구 유지보수**다. build TCO 항목:
- 초기 개발 인건비 (눈에 보이는 유일한 비용, 흔히 과소평가)
- **영구 유지보수·버그픽스·보안 패치** (매년 초기 개발비의 15~25% 통념, 확인 필요)
- 온콜·운영 부담 (엔지니어 시간 + 번아웃)
- 기회비용 = 이 팀이 제품 차별화에 못 쓴 시간
- 문서·온보딩·버스팩터(만든 사람 퇴사 리스크)

buy TCO: 구독료 + 통합·마이그레이션 + 벤더 락인 리스크 + 커스터마이즈 한계.

**판정**: build 3년 TCO vs buy 3년 TCO를 나란히 놓되, build 쪽에 "제품 지연 기회비용"을 반드시 계상. 대개 build가 처음 생각보다 훨씬 비싸다.

## 4. 되돌리기 비용(reversibility) — Bezos Type 1/2
- **Type 1(일방통행문)**: 되돌리기 어려움 → 신중히, buy/partner라도 락인·데이터 이동 비용 큰 계약 조심.
- **Type 2(양방향문)**: 되돌리기 쉬움 → 빠르게 결정하고 실험. 대부분의 buy 결정은 여기.
→ 되돌리기 비용이 낮으면 "일단 buy로 검증 후 필요시 build"가 안전. (Amazon 주주서한 개념 참조)

## 5. 사례 판정
- **검색**: 검색이 제품 자체(예: 검색 엔진 스타트업)면 build. 부가 기능이면 매니지드(Elasticsearch/Algolia) buy.
- **인증/결제**: 거의 항상 buy(Auth0/Clerk, Stripe) — 여기서 차별화하는 회사는 드물고 규제·보안 부담이 큼.
- **핵심 AI 모델**: 우리 데이터·도메인이 해자면 파인튜닝/자체(build), 범용이면 API buy, 공동 데이터셋이 필요하면 partner.
- **인프라(K8s·관측)**: 초기엔 매니지드 buy로 시간 확보, 규모·비용이 임계 넘으면 부분 build 재검토.

## 6. 안티패턴
- **NIH(Not Invented Here)**: "우리가 더 잘 만든다"며 공통 기능을 build → 제품 지연.
- **역NIH**: 해자까지 전부 buy → 차별화 상실, 벤더에 종속.
- **partner 무시**: build/buy만 보고 제휴 옵션을 안 봄 → 속도·리스크 분담 기회 놓침.
