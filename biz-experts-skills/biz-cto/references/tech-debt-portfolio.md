# 기술 부채 포트폴리오 — 분류·정량화·상환

> 부채는 "갚을 빚"이 아니라 **관리할 투자 포트폴리오**. 목표는 부채 제로가 아니라 이자 최적화.

## 1. 분류: Fowler 4분면 (원전)
Martin Fowler는 부채를 **의도성 × 신중함** 2축으로 나눈다:

|          | 신중(Prudent)                        | 무모(Reckless)                    |
|----------|--------------------------------------|-----------------------------------|
| **의도적** | "지금은 출시가 우선, 나중에 갚는다" (전략적) | "설계할 시간 없어" (변명)          |
| **우발적** | "돌아보니 더 나은 방법이 있었네" (학습)   | "레이어드 아키텍처가 뭔데?" (무지) |

- **신중·의도적**만이 정당한 부채 — 반드시 상환 계획과 함께 진다.
- **무모·우발적**(무지)은 부채가 아니라 역량 문제 → 교육·리뷰로 해결.
> 근거: Fowler "TechnicalDebtQuadrant" (2009) https://martinfowler.com/bliki/TechnicalDebtQuadrant.html

## 2. 정량화: 이자율 모델
부채 항목마다 **이자율 = 변경 빈도 × 변경 시 고통**으로 점수화:
- **변경 빈도**: git 로그로 실측(최근 6개월 커밋/수정 횟수). "핫스팟" 파일 찾기.
- **변경 시 고통**: 그 파일 건드릴 때 걸리는 시간·버그 유발률·PR 리뷰 난이도(팀 체감 1~5).
- **이자율 높음 = 자주 만지는데 만질 때마다 아픈 곳** → 최우선 상환.
- **이자율 0 = 안 만지는 안정 코드** → 부채가 있어도 방치 허용(재작성 낭비).

핫스팟 실측 팁: `git log --format=format: --name-only | sort | uniq -c | sort -rg | head` 로 변경 빈도 상위 파일 추출 → 그 목록만 고통 점수 매김. (Adam Tornhill *Your Code as a Crime Scene*의 행동적 코드 분석 접근 — 확인 필요, 개념 참조)

### SQALE / 정적 도구 (보조)
SonarQube 등은 부채를 "수정 예상 시간"으로 환산(SQALE 방법론: remediation cost ÷ development cost = 기술부채 비율). 절대 신뢰 대상은 아니고 **핫스팟 우선순위의 참고 지표**로만. 도구 점수가 높아도 안 만지는 코드면 후순위.

## 3. 상환 전략
| 전략 | 언제 | 리스크 |
|---|---|---|
| **보이스카웃 룰** (건드린 김에 조금씩 개선) | 이자율 중간, 자주 만지는 코드 | 낮음 — 기본값 |
| **선별 리팩터링** (고이자 모듈 집중) | 이자율 최상위 소수 | 중간 — 범위 통제 필요 |
| **스트랭글러 무화과** (신구 병행, 점진 교체) | 큰 레거시를 못 멈추고 바꿔야 할 때 | 중간 — Fowler 패턴, 안전 |
| **전면 재작성** | 거의 하지 마라 | **높음** — Netscape가 시장을 잃음 |

- **전면 재작성 금지 원칙**: Joel Spolsky "Things You Should Never Do" — Netscape는 코드를 버리고 처음부터 재작성하다 IE에 시장을 내줬다. 재작성 중엔 신기능이 0이라 경쟁사가 추월. https://www.joelonsoftware.com/2000/04/06/things-you-should-never-do-part-i/
- 큰 교체가 불가피하면 **스트랭글러 무화과 패턴**(Fowler): 옛 시스템을 감싸며 기능을 하나씩 새 시스템으로 옮기고 옛것을 서서히 고사시킴. https://martinfowler.com/bliki/StranglerFigApplication.html

## 4. CTO의 부채 대화법 (사업 언어로 번역)
경영진/이사회에 부채를 설명할 땐 "코드가 지저분함"이 아니라:
- "이 부채 때문에 신기능 출시가 평균 X일 느립니다" (속도 세)
- "이 모듈 장애율이 전체의 Y%입니다" (안정성)
- "여기 상환에 Z주 투자하면 이후 기능당 리드타임 W% 단축" (ROI)
→ **부채 상환도 사업 지표로 정당화**(SKILL 핵심 신조).

## 5. 실전 배분 휴리스틱
- 스프린트 용량의 **10~20%를 부채·역량 투자에 상시 배정**(통념, 확인 필요) — "리팩터링 분기" 몰아치기보다 지속적 소액 상환이 안전.
- 단 PMF 전 초기 스타트업은 의도적으로 부채를 지고 속도를 사는 게 맞을 때가 많음 — 단계 판단이 CTO의 일.
