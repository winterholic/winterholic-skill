## 1. 범위를 먼저 못 박는다

작업 시작 전 한 줄로 고정한다: **어느 화면 / 어느 뷰포트 / 어느 파일까지.**

- 공용 자산(전역 CSS·셸 레이아웃·디자인 토큰·공용 컴포넌트)을 건드리면 **안 바꾸기로 한 뷰포트도 작업 후 반드시 다시 잰다.** "안 건드렸으니 괜찮겠지"는 근거가 아니다.
- CSS 모듈에서 값을 넣을 자리를 고를 때 **파일 안 규칙 순서를 먼저 확인한다.** 미디어쿼리가 파일 끝에 몰려 있다고 가정하지 않는다 — 같은 특정도면 뒤에 오는 전역 규칙이 미디어쿼리를 덮는다.
- **쿼리 경계에 어떤 컨텍스트가 걸리는지 계산한다.** `max-width: 860px` 는 인쇄(A4 794px)에도 걸린다. 화면 전용이면 `screen and (max-width: ...)` 로 묶는다.
- **한쪽 상한을 내리면 반대쪽이 역전된다.** 데스크톱 폰트 상한을 낮췄더니 `520px 이하` 규칙이 상대적으로 더 커져 모바일에서 6줄이 됐다.
- 모바일 지적에 데스크톱을 같이 손대지 않는다. 두 뷰는 따로 있고, 한쪽이 이미 만족 상태일 수 있다.
- **되돌리기는 눈이 아니라 diff 로 검증한다.** 렌더가 원본처럼 보여도 값은 다를 수 있다.
- **JS 뷰 분기 임계값과 CSS 브레이크포인트가 어긋나 있는지 본다.** `useMobileView` 가 `max-width: 375px` 라 390~430인 흔한 폰이 모바일 흐름에 안 걸리고 데스크톱 하이브리드로 깨진 적이 있다. 실제 기기 폭 분포와 대조한다.

## 2. 요구의 크기를 줄이지 않는다

요청을 받으면 먼저 등급을 판정하고 **그 등급대로** 한다.

| 등급 | 신호 | 하는 일 |
|---|---|---|
| 국소 조정 | "이 여백만", "이 색만", "정렬만" | 그 값만. 범위 확대 금지 |
| 부분 재구성 | "이 영역 배치를 다시" | 그 영역의 구조를 다시 짠다 |
| 전면 재설계 | "아예 새로운 양식으로", "새로 짜라" | 판을 다시 짠다. 기존 구조 유지 금지 |

- 재설계 요구가 왔는데 **숫자 하나로 끝나는 조정**을 내놓았다면 비용이 싼 쪽으로 도망친 것이다.
- **"상자를 만들라"는 "컴포넌트를 설계하라"는 뜻일 때가 많다.** 컨테이너만 두르고 내부 구성을 그대로 두면 오히려 나빠진다 — 여백이 상자 안에 갇혀 더 도드라진다.
- 요구에 **성역**이 있으면 그것을 침범하는 해법은 후보에서 뺀다(→ 규율 7).

> 근거: 2026-09-01 0900. 요구는 "카드 크기는 무조건 고정, 좁은 상자를 아예 새 양식으로"였는데 상자를 두고 카드를 줄였다. 평가는 *"카드가 너무 작고 설명란은 여전히 비대하다"*. 회고에 남은 말 — **"쉬운 쪽으로 갔던 것이다."**

## 3. 공간 예산을 먼저 잰다

"한 화면에 담아라"류 요구는 설계가 아니라 **산수로 시작한다.**

1. 고정 요소(성역 크기·헤더·셸 패딩·안내 문구)를 먼저 더한다.
2. 뷰포트 높이에서 빼서 **남는 px 를 확정한다.**
3. 그 숫자를 적어두고 **그 안에 들어가도록** 나머지를 설계한다.
4. 최악 조건(가장 긴 라벨·버튼 2개·설명 2문단)을 DOM 에 심어 다시 잰다.

**측정 전제가 틀리면 측정은 무의미하다.** 기기 해상도가 아니라 **실제 웹 뷰포트**로 잰다 — 사파리 하단 바·안드로이드 내비가 100px 안팎을 먹는다.

| 기기 | 기기 해상도 | 실제 웹 뷰포트(세로 예산용) |
|---|---|---|
| iPhone SE | 375x667 | **375x553** |
| 갤럭시 보급형 | 360x740 | **360x620** |
| iPhone 14 | 390x844 | **390x664** |
| Pixel | 393x852 | **393x680** |
| 갤럭시 S23 | 412x915 | **412x740** |

## 4. 원인을 하나로 확정하지 않는다

여백·정렬·"답답함" 증상은 원인이 겹쳐서 난다. 첫 번째로 찾은 원인이 가장 큰 몫이라는 보장이 없다.

- 후보를 **최소 2~3개** 세운다. 흔한 조합: ①숨은 `min-height`(누르는 면적용) ②`line-height` 미지정으로 인한 상속 ③부모 `gap` 과 자식 `gap` 이 같아 그룹 경계가 사라짐 ④음수·상쇄 margin ⑤규칙이 여러 블록에 흩어져 있음.
- 각 후보의 **기여 px 를 따로 잰다.** 하나 고치고 "됐다"로 닫지 않는다.
- 고친 뒤 **묶음 안 간격 < 묶음 사이 간격** 이 성립하는지 확인한다(게슈탈트 근접성).
- **감각적 지적을 받으면 값이 아니라 구조를 먼저 의심한다.** "패딩이 이상하다"는 직감은 맞았지만 실체는 값 하나가 아니라 규칙이 네 블록에 흩어진 것이었다.

## 5. 검증은 눈이 아니라 계측으로 닫는다

- 흑백 테스트·스크린샷은 **위계 점검 수단**이지 완료 근거가 아니다.
- 완료를 말하기 전 실측한다: `getBoundingClientRect` 로 높이·간격, `scrollHeight - clientHeight` 로 넘침, `getComputedStyle` 로 실제 적용값, 잘림은 `scrollWidth > clientWidth`.
- **바꾼 뷰포트와 안 바꾼 뷰포트를 같은 회차에 잰다**(규율 1과 짝).
- **경계값을 채택하지 않는다.** 분기점을 측정으로 찾고 한 단계 물러난다 — 34pt 가 2줄·3줄 분기점이면 폰트 폴백 차이를 감안해 33pt 를 쓴다.
- **엔진·실기기 한계를 적는다.** 헤드리스 크로미움은 오버레이 스크롤바를 못 보여주고, WebKit(아이폰)은 따로 확인해야 한다. 못 본 것은 못 봤다고 남긴다.
- **보고한 숫자가 사용자 화면과 다르면 그때부터 신뢰가 깎인다.** "고쳤다"를 실측 없이 말하지 않는다.
- **손으로 재기 전에 도구가 있다.** 렌더되는 URL 이 있으면 `ui-refine-loop` 의 T0 한 줄이 더 빠르고,
  **못 본 영역의 비율까지 함께 신고**한다 — `node ~/.claude/skills/ui-refine-loop/scripts/quick.mjs --url <url>`.
  DevTools 콘솔뿐이면 `biz-ui-designer/scripts/ui_probe.js` 를 붙여넣는다.

## 6. 보이는 것과 발견되는 것은 다르다

시각 정리는 자주 콘텐츠를 접거나 줄이거나 스크롤 뒤로 민다. 그 순간 **발견가능성이 조용히 사라진다.**

- 스크롤·접힘·탭·스와이프 뒤의 콘텐츠는 **신호(시그니파이어)가 없으면 없는 것이다.**
- 스크롤바를 감추기로 했다면 "더 있다"를 알릴 다른 신호를 같이 설계한다. 화면 안의 작은 상자는 셸 본문과 달리 막대가 유일한 단서일 수 있다.
- **가로 스크롤은 "더 있다"가 시각적으로 읽힐 때만 쓴다.** 칩처럼 잘려도 티가 안 나는 요소는 줄바꿈이 맞다.
- 같은 기능인데 어떤 화면에서만 발견된다면, **차이는 보통 문구 유무**다. 잘 되는 화면의 문구를 그대로 옮긴다.
- 이 축은 시각 판단만으로 닫히지 않는다 — `biz-ux-designer` 안티패턴 2(숨은 기능)·3(상태 안 보임) 렌즈로 한 번 본다.

## 7. 승인 경계 — 스타일은 자율, 구조는 승인

**가장 많은 반려가 여기서 났다.** 기술적 근거가 타당한 것과 승인 없이 실행해도 되는 것은 별개다.

| 자율(그냥 한다) | 승인 사항(먼저 묻는다) |
|---|---|
| 색·타이포·괘선·여백·간격 조정 | 요소 신설·삭제 |
| 대비·위계 교정 | 레이아웃 구조 변경(분할 방향·열 수·순서) |
| 지적받은 자리의 수정 | 지적 안 받은 영역으로의 확대 |

- **오너가 만족을 표명한 영역은 성역이다.** "2·4·6·8p 는 훌륭해", "UI 는 이미 예쁘니 글자만", "카드 크기 통일은 유지, 정렬만" — 진단이 맞아도 갈아엎지 않는다.
- **"개선해봐"는 구성 변경 승인이 아니다.** 진단서에 원인을 적어둔 것과, 그 해법이 구조 변경이라는 걸 사용자가 이해한 것은 다르다.
- 부작용 범위를 **먼저 짚고 물으면 대개 바로 승인된다.** 묻는 것 자체를 번거로워하지 않는다.
- **안 고친 것도 보고한다.** "완성도를 올리려는 것이지 갈아엎으려는 게 아니다" — 멀쩡한 곳을 왜 뒀는지가 보고의 일부다.
- **인상이 크게 바뀌는 변경은 시안 하나를 먼저 보여주고 승인받는다.** 팔레트 교체·조판 언어 변경을 전 페이지에 일괄 적용했다가 통째로 반려된 적이 있다. 디자인은 되돌리기 비싼 변경이다.
- 반려 표현이 *"당황스럽네"* 면 결과가 나쁘다는 게 아니라 **예상 못 한 변경이 있었다**는 신호다. 되돌릴 때 칭찬받은 스타일까지 같이 되돌리지 않는다.

## 8. 진단 순서 — 배치 → 상자 → 크기

넘침·잘림·이상한 여백을 보면 **크기(폰트·패딩)부터 깎지 않는다.** 순서가 있다.

1. **배치가 의도대로 적용됐나** — grid·flex 설정, `grid-column` 강제, 자동 배치가 예상과 다른가. 같은 클래스에 규칙을 덧붙일 때 앞 규칙의 grid·flex 설정을 반드시 확인한다.
2. **상자가 병목인가** — `max-width` 캡, 컨테이너 종횡비. 이미지 잘림은 `object-position` 미세조정이 아니라 **패널 종횡비**가 원인인 경우가 많다.
3. **그 다음에 크기.**

**"패딩이 이상하다"는 신고의 절반은 패딩이 아니다** — 크기 계산이 한 축만 볼 때 생기는 잔여 공간이 패딩처럼 보인다.

> 근거: 2026-07-30 0110 — 7p 를 세 번 다시 맞췄다(-222px → -37 → -2 → +75px). 원인을 모른 채 폰트·패딩부터 깎았는데 진짜 원인은 `grid-column: 2` 강제가 print 까지 따라와 3단이 2단으로 눌린 것이었다. 배치를 고치니 350px 가 남았다. / 2026-07-29 0200 — 표지를 못 키우던 이유가 폰트가 아니라 `max-width: 920px` 캡이었다. / 2026-09-01 — 카드 상세·홈 두 화면이 같은 원인이었다.

## 9. 기존 코드의 결을 따른다

- **새 화면을 만들 때 레이아웃을 새로 짜지 않는다.** 같은 종류의 화면이면 기존 CSS 모듈을 재사용한다 — **"라우트를 나눈다 ≠ 생김새를 바꾼다."**
- 프로젝트에 이미 있는 어법(그리드 패턴·빈 상태 처리·컨테이너 스타일)을 먼저 찾고 그 안에서 푼다. 새 어법을 도입하면 "디자인 시스템과 이질감"으로 지적된다.
- 코드에 남은 **과거 판단 주석은 전제부터 확인한다.** 전제가 바뀌었으면 결론도 뒤집힌다.
- 일반론이 프로젝트 선호와 충돌하면 **프로젝트가 이긴다.** 예: "여백이 디자인이다"는 일반론이지만, 이 오너는 **이유 없이 남는 여백을 미완성으로 읽는다**("굳이 오른쪽을 비워놓을 이유가 없다" — 한 프로젝트에서 세 번 지적). 빈 공간을 보면 채우라는 뜻이 아니라 **요소를 옮겨 담으라**는 뜻일 수 있다.

> 근거: 2026-08-23 — 한 재설계에서 **네 번 연속 지적**받았다(승격 잔재 → 필터 잔재 → 배치 오독 → 스타일 이질). 공통 원인은 *"기존 코드의 결을 확인하지 않고 내 판단으로 새로 만든 것"*.

## 10. 한 곳 지적은 전수 점검 요청이다

- 지적받은 자리만 고치는 건 부족하다. **같은 패턴이 다른 화면·다른 요소에도 있는지 실측 스크립트로 뽑는다.** 눈대중은 31px 차이를 "정렬됐다"고 판정한다.
- 한 번 배제된 프레이밍·표현·스타일은 **다른 요소에도 전파해 점검한다.** 같은 지적을 두 번 하게 만들면 어조가 세진다("답답", "왜 저렇게 잡아놨냐니까").
- **화면이 갈리는 곳은 양쪽 다 챙긴다** — 로그인·비로그인, 모바일·데스크톱, 목록·상세. 한쪽만 손보면 반드시 지적이 온다.
- 사용자가 "이런 거 또 있나 다 찾아봐"라고 말하기 전에 먼저 한다.

> 근거: 2026-08-08 — *"이런거 혹시 또 있나 찾아보고 다 꼼꼼히 찾아서"*. / 2026-07-29 0430 — 한 번 배제한 프레이밍이 제목에 다시 나타나 *"이거도 …초점 맞추지마라니까... 답답"*.

## 11. 계측이 거짓말하는 세 가지 방식

규율 5는 "재라"까지 말한다. 그런데 **잰 값 자체가 틀린 사고가 반복해서 났다.** 완료를 말하기 전 셋을 순서대로 의심한다.

**① 측정 대상이 지금 코드가 아니다**
- 사용자 서버가 켜진 채로 빌드를 돌려 실행 중 서버의 CSS 가 500 이 됐다(같은 사고 **2회**).
- 새 서버가 포트 점유로 즉시 죽었는데 **`curl` 이 살아 있는 옛 프로세스에 200 을 받아** "재기동 완료"로 오보했다. **`curl` 200 은 재기동 근거가 아니다 — 기동 로그의 `Ready` 를 본다.**
- 죽은 서버를 때려 "최소 폰트 13/16px, overflowX 5655" 같은 말이 안 되는 값이 나온 적도 있다. **값이 상식 밖이면 코드보다 환경을 먼저 의심한다.**

**② 도구가 틀린 값을 준다**
- `backgroundColor` 만 읽어 gradient 배경 위 텍스트의 대비를 계산 → **오탐 135건**.
- 셀렉터 판별자가 엉뚱한 것에 걸려 개수를 잘못 셌다. **"0건"을 주장하려면 판별자부터 검증한다**(일부러 걸리는 입력을 넣어 검사가 실패할 수 있는지 먼저 본다 — negative control).
- 빌드 산출물 캐시 잔재로 `tsc` 가 없는 라우트를 참조해 오류를 냈다. 소스 문제로 오인하면 멀쩡한 작업을 되돌린다.

**③ 축이 틀렸다**
- **요소 박스 vs 글리프** — `min-height` 안에서 글자가 중앙 정렬되면 박스는 줄어도 글자 위치는 그대로다. 사용자가 보는 것은 글리프다.
- **기기 해상도 vs 웹 뷰포트** — 규율 3 참조.
- **전체를 잰 줄 알았지만 일부만** — 문서가 아니라 내부 상자가 스크롤하면 문서 기준 측정·`fullPage` 캡처가 화면 대부분을 놓친다.

> 도구: `biz-ui-designer/scripts/ui_probe.js` 의 `identity`(대상) · `contrast.unmeasured`(도구) · `glyphVsBoxGaps`·`scrollTruth`(축) · `truncated`·`blindSpots`(못 본 것)가 이 셋을 각각 겨눈다. 결과에서 그 필드가 비어 있지 않으면 **"문제 없음"이 아니라 "확인 못함"이다.**

## 12. 완료의 기준은 로컬이 아니라 사용자가 보는 화면

- **커밋·푸시는 완료가 아니다.** 로컬 렌더만 근거로 완료를 보고했다가 *"장난하냐"* 를 들었다. 실제로는 2차 코드가 배포 전이었다.
- **push = 배포여도 CDN 캐시가 빠지기 전엔 라이브가 옛 화면이다.** 응답 헤더의 캐시 상태·age 와 **HTML 안 마커 문자열**을 같이 본다. 정적 생성 페이지는 `?cb=` 같은 쿼리로 캐시를 못 뚫는다(쿼리가 새 캐시 엔트리를 만들지 않는다).
- **로컬이 운영을 보고 있을 수 있다.** 프록시 기본 타깃이 운영이거나, 빌드가 프로덕션 API 로 프리렌더하면 "코드가 안 먹는 것처럼" 보인다. 여기서 30분을 날린 적이 있다.
- **사용자가 보는 매체를 먼저 확인한다.** 인쇄만 고치고 화면 규칙을 그대로 뒀다가 *"아직도 개큰데?"* 가 돌아왔다.
- 확인 못 한 층은 그렇게 적는다 — "로컬에서는 통과, 라이브 미확인".
