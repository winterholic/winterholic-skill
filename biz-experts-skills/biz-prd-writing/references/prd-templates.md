## 1. PRD 섹션 템플릿 (표준 — 복사용)

```markdown
# [기능명] PRD
작성자: __ | 상태: Draft/Review/Approved | 최종수정: __

## 1. 문제 / 배경
- 누구의: (세그먼트)
- 무슨 문제: (페인, 관찰된 증거)
- 왜 지금: (타이밍 근거)
- 안 풀면 비용: (이탈/손실)

## 2. 목표(성공 지표)
- Outcome 지표: ____ | 현재값: ____ → 목표: ____
- 측정 방법: ____ | 확인 시점: D+__

## 3. 비목표 (Non-goals) ★ 범위 방어선
- 이번에 명시적으로 안 하는 것: ____

## 4. 사용자 & 시나리오
- 주 사용자: __ | 핵심 시나리오(스토리): __

## 5. 해법 개요 (상세 UI는 디자인/화면설계서로 위임)
- 접근 방식: __ (와이어·플로우는 링크)

## 6. 유저스토리 + 수용기준
- (아래 §3·§4 양식)

## 7. 의존성 / 리스크 / 열린 질문 ★ 숨기지 말 것
- 의존성: __ | 리스크: __ | 열린 질문(미결정): __

## 8. 출시 · 측정 계획
- 롤아웃: (베타/단계적/전면) | 측정 대시보드: __
```

> **적정 해상도가 핵심**: "무엇을·왜"까지가 PRD. 픽셀·문구·엣지 전부를 PRD에 박으면 안 읽히고(=정렬 실패) 발견 학습을 막는다. 상세는 위임.

## 2. Amazon PR/FAQ 템플릿 (Working Backwards)

### 보도자료(PR) — 7블록, 1페이지, 고객 관점 (Amazon 표준)
```
1. Heading(제목): 타깃 고객이 이해할 제품명 한 줄
2. Subheading(부제): 누구를 위한, 어떤 혜택인지 한 줄
3. Summary(요약): 핵심 가치·혜택 요약 (경영진용 3~4문장)
4. Problem(문제): 고객 관점에서 이 제품이 푸는 문제 (1인칭 고객 시점)
5. Solution(해법): 제품이 그 문제를 어떻게 쉽게 푸는지
6. Quotes(인용): ① 회사 대변인 인용 ② 가상 고객이 얻은 혜택 인용
7. Getting Started(시작): 얼마나 쉽게 시작하는지 + 링크
```

### FAQ — 두 종류
- **고객 FAQ**: 고객이 물을 법한 질문(가격·프라이버시·호환성…).
- **내부 FAQ**: 왜 우리가·시장 크기·리스크·기술 난제·의존성·수익 모델. **어려운 질문일수록 여기 적는다**(숨기면 회의에서 터짐).

### 프로세스 규율 (검증된 사실)
- 첫 초안은 **며칠이 아니라 몇 시간** 안에 — 빠른 옵션 탐색이 목적.
- 이후 **10번 이상 고쳐 쓰고 시니어와 5회 이상** 다듬는 일이 드물지 않음.
- **"이 한 페이지를 설득력 있게 못 쓰면 만들 가치가 없다"** — PR/FAQ가 통과 못 하면 제품이 통과 못 한 것.
- 회의는 6페이지 산문 문서를 **침묵 독서**로 시작(불릿 PPT 금지) — 산문이 논리 구멍을 드러냄.

> PR/FAQ는 발견(→ biz-product-discovery)을 대체하지 않는다 — 가상 고객 인용은 검증된 니즈에 근거해야 한다.

## 3. 유저스토리 — Connextra 포맷 + INVEST

### Connextra 포맷 (런던 XP팀 ~2001, Cohn이 대중화 — Cohn 발명 아님)
```
As a [역할], I want [목표], so that [가치/이유].
(예: 카드 결제 사용자로서, 결제 실패 시 자동 재시도되기를 원한다, 왜냐하면 다시 입력하는 번거로움 없이 구매를 끝내고 싶기 때문이다.)
```
"so that"(왜)가 빠지면 유저스토리가 아니라 태스크. 가치를 반드시 명시.

### INVEST 체크 (Bill Wake, 2003) — 좋은 스토리 6조건
- [ ] **I**ndependent 독립적 — 다른 스토리에 얽매이지 않음
- [ ] **N**egotiable 협상가능 — 계약이 아니라 대화의 시작
- [ ] **V**aluable 가치있음 — 사용자/고객에게 가치
- [ ] **E**stimable 추정가능 — 규모를 가늠할 수 있음
- [ ] **S**mall 작음 — 한 스프린트 내 완료 크기
- [ ] **T**estable 검증가능 — 완료를 판정할 수 있음(→ 수용기준 필요)

## 4. Given-When-Then 수용기준 (BDD/Gherkin)

### 계보
Given-When-Then은 **Chris Matts & Dan North(~2004) 공동**, North가 2006년 글로 공개, Cucumber가 표준화. (North 단독 귀속은 오류.)

### 구조
```
Given [초기 상황·전제조건]
When  [사용자/시스템의 행위]
Then  [관찰 가능한 결과]
(And / But 로 추가 조건·결과 연결 가능)
```

### 작성 원칙
- **입력 상황·동작·결과가 모두 구체적·관찰가능**이어야 QA가 통과 판정 가능.
- 시나리오 하나에 하나의 행위(When 1개). 여러 조건은 시나리오 분리.
- 구현이 아니라 **행동**을 기술(어떻게가 아니라 무엇이 관찰되나).

### 안티패턴 vs 검증가능 예시집
| ❌ 빈약 | ✅ 검증가능 |
|---|---|
| Given 결제 실패, When 재시도, Then 성공 | Given 카드 결제가 타임아웃으로 실패했을 때, When 시스템이 30초 후 1회 자동 재시도하면, Then 동일 카드로 재승인되고 사용자에게 중복 청구되지 않는다 |
| "로그인이 잘 돼야 함" | Given 등록된 이메일·올바른 비밀번호로, When 로그인 버튼을 누르면, Then 3초 내 대시보드로 이동한다 |
| "에러 처리 잘함" | Given 잔액 부족으로 결제가 거절됐을 때, When 재시도하면, Then 재시도하지 않고 "다른 결제수단" 안내를 표시한다 (거절은 재시도 대상 아님) |

### 엣지·부정 시나리오도 명시
- 실패/거절/타임아웃/중복요청/권한없음 등 **부정 경로**를 별도 GWT로. 정상 경로만 적으면 재작업.

## 5. Shape Up pitch 템플릿 (Basecamp, 무료 공개)

```
## [기능] Pitch
### Problem  문제 (구체적 상황 1개, 추상 금지)
### Appetite 쓸 의향 시간: Small Batch(1~2주) / Big Batch(6주)  ← 범위를 시간으로 고정
### Solution 해법 스케치 (fat marker — 대략만, 픽셀 금지)
### Rabbit holes 위험한 구멍 (미리 짚어 제거)
### No-gos  명시적으로 안 하는 것
```

- **appetite로 범위를 고정**: "얼마나 좋게?"가 아니라 "얼마 쓸 가치?"로. 시간이 상수, 범위가 변수.
- **circuit breaker (교정된 사실)**: 6주 사이클 안에 못 끝내면 기본은 **연장이 아니라 취소(cancel)**. 다시 pitch해서 새 사이클에 베팅. (흔히 "연장"으로 오해.)

## 6. 완성 PRD 예시 (결제 실패 재시도 — 전 섹션 채움)

```markdown
# 결제 실패 자동 재시도 PRD
작성자: PM Kim | 상태: Review | 최종수정: 2026-07-01

## 1. 문제 / 배경
- 누구: 카드 정기결제 사용자 (월 ~8,000명 결제 시도)
- 문제: 일시적 네트워크/발급사 타임아웃으로 결제가 실패하면, 사용자가
  재입력 없이 이탈. 최근 30일 결제 실패의 약 40%가 재시도 시 성공(로그).
- 왜 지금: 갱신 실패로 인한 비자발적 이탈(involuntary churn)이 이탈의 상위 원인.
- 안 풀면 비용: 실패 건의 상당수가 회복 가능한데 매출로 안 잡힘.

## 2. 목표(성공 지표)
- Outcome: 결제 성공률 92% → 95%  | 측정: 결제 대시보드 성공/시도 비율
- 확인 시점: 전면 출시 후 D+14

## 3. 비목표 (Non-goals)
- 신규 결제수단 추가(계좌이체 등) — 이번 범위 아님
- 해외 발급 카드 특수 처리 — 다음 사이클
- 사용자가 직접 누르는 수동 재시도 버튼 — 자동에 집중

## 4. 사용자 & 시나리오
- 주 사용자: 정기결제 갱신 대상자
- 시나리오: 갱신일에 타임아웃 실패 → 시스템이 조용히 재시도 → 성공 시 무통보,
  최종 실패 시에만 대체수단 안내.

## 5. 해법 개요 (상세 플로우는 디자인 링크)
- 회복 가능 오류(타임아웃/일시 오류)에 한해 지수 백오프로 최대 N회 재시도.
- 회복 불가 오류(잔액부족/거절/유효기간만료)는 재시도하지 않고 즉시 안내.

## 6. 유저스토리 + 수용기준
US1) 카드 결제 사용자로서, 일시 오류 시 자동 재시도되기를 원한다,
     왜냐하면 재입력 없이 갱신을 끝내고 싶기 때문이다.
- GWT-1 Given 결제가 타임아웃으로 실패했을 때, When 30초 후 1회 자동 재시도하면,
        Then 동일 카드로 재승인되고 중복 청구되지 않는다.
- GWT-2 Given 잔액부족으로 거절됐을 때, When 처리하면,
        Then 재시도하지 않고 "다른 결제수단" 안내를 표시한다.
- GWT-3 Given 재시도가 최대 횟수까지 모두 실패했을 때, When 종료되면,
        Then 사용자에게 실패 알림 1건만 발송한다(중복 알림 금지).

## 7. 의존성 / 리스크 / 열린 질문
- 의존성: PG사 멱등키(idempotency key) 지원 필요(중복청구 방지)
- 리스크: 재시도가 발급사에 과도 요청 → 계정 플래그 가능성
- 열린 질문: 재시도 횟수·간격 정책 미정(2회/30s·5m? 결제팀 확인 필요)

## 8. 출시 · 측정 계획
- 롤아웃: 5% → 50% → 100% 단계적, 각 단계 D+3 성공률·중복청구 0 확인
- 대시보드: 결제 성공률, 재시도 성공 기여분, 중복청구 건수(=0 목표)
```

## 7. PRD 리뷰 체크리스트
- [ ] 솔루션 전에 문제·대상·왜 지금이 먼저 나오나?(안티패턴 1)
- [ ] 성공 지표 + 목표치 + 측정법 + 확인시점이 있나?(안티패턴 2)
- [ ] 비목표(안 할 것)가 명시됐나?(범위 크리프 방어)
- [ ] 상세 UI를 PRD에 안 박고 위임했나?(안티패턴 3, 적정 해상도)
- [ ] 열린 질문·리스크·가정이 드러났나?(안티패턴 4)
- [ ] 불릿 더미가 아니라 서사가 있나?(안티패턴 5)
- [ ] 수용기준이 GWT로 검증가능한가? 부정/엣지 경로도?(안티패턴 6)
- [ ] 유저스토리에 "so that"(가치)이 있고 INVEST를 만족하나?
