# 니엘슨 10 휴리스틱 실전 플레이북 — 위반 예 / 진단 / 수정

> biz-ux-designer 심화 참조. 각 휴리스틱마다 **정의(NN/g 원문) → 흔한 위반(❌) → 진단 질문 → 수정(✅) → 인접 원칙**을 실무 수준으로. 출처 2026-07-01 재검증(NN/g ten-usability-heuristics, error-prevention). 원저 Nielsen-Molich 1994(초기 개발 1990). 이 파일은 SKILL.md의 안티패턴 카탈로그를 "휴리스틱별"로 재조직한 심화판 — SKILL 본체와 중복이 아니라 상호 참조용.

---

## 실전 사용법

휴리스틱 평가(heuristic evaluation)는 3~5명의 평가자가 **독립적으로** 인터페이스를 훑고 각자 위반을 기록한 뒤 취합하는 방법이다(Nielsen). 1명은 평균 위반의 약 35%만 발견 — 그래서 여러 명이 필요. 각 위반에는 **심각도(severity)**를 매긴다:

| 등급 | 의미 | 대응 |
|---|---|---|
| 0 | 사용성 문제 아님 | 무시 |
| 1 | 겉치레(cosmetic) | 시간 남으면 |
| 2 | 경미 | 낮은 우선순위 |
| 3 | 심각 | 높은 우선순위, 출시 전 수정 |
| 4 | 재앙(catastrophe) | 출시 전 필수 수정 |

심각도는 **빈도 × 영향 × 지속성(persistence, 반복 극복 가능한가)**의 합성. "예뻐 보이지만 아무도 못 찾는 버튼"은 빈도 높고 지속적이라 3~4가 되곤 한다. (근거: NN/g "Severity Ratings for Usability Problems" — 확인 필요, 등급 체계는 Nielsen 표준.)

## #1 시스템 상태 가시성 (Visibility of System Status)

**정의(NN/g):** "디자인은 적절한 피드백으로, 합리적인 시간 안에, 무슨 일이 일어나는지 사용자에게 항상 알려야 한다."

**❌ 위반**
- 저장 버튼을 눌렀는데 아무 변화 없음 → 사용자가 저장됐는지 몰라 또 누름(중복 제출)
- 긴 업로드에 진행률 없이 스피너만 무한 회전
- 다단계 폼에서 "지금 몇 단계인지" 표시 없음

**진단 질문**
- 모든 사용자 액션에 100ms 안에 눈에 보이는 반응이 있는가?
- 1초 넘는 작업에 진행 표시가 있는가? 10초 넘으면 남은 시간·완료 예고가 있는가?
- 시스템이 지금 어떤 모드/상태인지(로그인됨, 편집 중, 오프라인) 항상 보이는가?

**✅ 수정**
- 즉시 피드백: 버튼 눌림 상태 → 로딩 스피너 → 성공 토스트/실패 메시지의 3상태를 항상 설계
- 응답시간 3한계 준수: <0.1s 즉각감 / <1s 흐름유지 / <10s 주의한계(NN/g). 1s 넘으면 로딩, 10s 넘으면 진행률 %와 취소 버튼
- 낙관적 UI(optimistic update)는 실패 시 롤백·재시도 경로를 반드시 병행

**인접:** #6(인식) — 상태를 "보이게" 하는 것이 곧 회상 부담을 줄인다.

## #2 시스템-현실 일치 (Match Between System and Real World)

**정의(NN/g):** "사용자의 언어로 말하라. 내부 전문용어 대신 사용자에게 친숙한 단어·개념을 써라."

**❌ 위반**
- "인증 토큰이 만료되었습니다(HTTP 401)" 를 일반 사용자에게 노출
- 실제 순서와 다른 정보 배치(예: 결제 화면에서 배송지보다 카드번호를 먼저)
- 개발자 관점 라벨: "엔티티 삭제", "레코드 없음"

**진단 질문**
- 이 라벨을 대상 사용자가 소리 내 읽고 뜻을 즉시 아는가?
- 화면의 정보 순서가 사용자의 실제 사고·업무 순서와 같은가(natural mapping)?
- 은유(휴지통, 폴더, 장바구니)가 사용자 세계의 개념과 맞는가?

**✅ 수정**
- 도메인 용어를 사용자 용어로 번역("잔여 한도" > "가용 크레딧")
- 실세계 순서·관습 따르기(달력은 월요일/일요일 시작을 지역 관습에 맞춤)
- 마이크로카피 세부는 biz-ux-writer로 넘기되, **순서·구조** 결정은 UX

**인접:** #4(일관성·표준) — "야콥의 법칙: 사용자는 다른 사이트에서 대부분의 시간을 보낸다."

## #3 사용자 통제·자유 (User Control and Freedom)

**정의(NN/g):** "사용자는 실수로 액션을 한다. 긴 과정을 거치지 않고 원치 않는 상태를 벗어날 '비상구'가 명확히 필요하다."

**❌ 위반**
- 실행 취소(undo)/다시 실행(redo) 없음 — 실수하면 수동 복구뿐
- 모달에 닫기 없이 "동의" 강제, 또는 뒤로가기가 폼 데이터를 전부 날림
- 결제·가입 마법사 중간 이탈 시 처음부터 다시

**진단 질문**
- 모든 파괴적·비가역 액션에 undo 또는 확인이 있는가?
- 어떤 화면에서든 "취소/뒤로/닫기"로 안전하게 빠져나갈 수 있는가?
- 자동저장으로 중간 이탈이 데이터 손실로 이어지지 않는가?

**✅ 수정**
- **undo > 확인 다이얼로그**를 우선(Gmail식 "실행 취소" 토스트 5초). 확인 다이얼로그는 남발 시 무시(banner blindness)되므로 정말 위험한 것에만
- 비상구: 모든 모달에 명시적 닫기, 마법사에 단계 저장, 폼 자동저장
- 소프트 삭제(30일 복구)로 "되돌릴 수 없음"을 "되돌릴 수 있음"으로 전환

**인접:** #5(에러 예방) — 통제·자유는 "이미 난 실수"의 회복, 에러 예방은 "실수 자체"를 막음. 둘 다 필요.

## #4 일관성·표준 (Consistency and Standards)

**정의(NN/g):** "서로 다른 단어·상황·액션이 같은 것을 뜻하는지 사용자가 고민하지 않게 하라. 플랫폼·업계 관습을 따르라."

**❌ 위반**
- 같은 기능을 화면마다 다른 라벨("삭제"/"제거"/"휴지통")
- 저장 아이콘이 화면마다 위치·모양이 다름
- 플랫폼 관습 무시(iOS에서 안드로이드식 back, 웹에서 밑줄 없는 링크색만으로 링크 표시)

**진단 질문**
- 같은 개념에 같은 단어·아이콘·색·위치를 쓰는가(내부 일관성)?
- 플랫폼/업계 표준을 따르는가 — 장바구니는 카트 아이콘, 링크는 파랑+밑줄(외부 일관성)?
- 관습을 깼다면, 깨서 얻는 가치가 학습비용보다 큰가?

**✅ 수정**
- 용어집(terminology glossary)·컴포넌트 라이브러리로 내부 일관성 강제(→ biz-design-system)
- 야콥의 법칙 존중: "관습을 깨려면 그럴 만한 강력한 이유가 있어야 한다"(Nielsen)
- 관습 파괴가 불가피하면 시그니파이어로 새 규칙을 크게 알림

**인접:** #2(현실 일치) — 둘 다 "사용자가 이미 가진 기대"에 맞추는 것.

## #5 에러 예방 (Error Prevention) — 이 스킬의 심장

**정의(NN/g):** "좋은 에러 메시지도 중요하지만, 최선의 디자인은 애초에 문제가 일어나지 않게 세심히 예방한다."

**슬립(slip) vs 실수(mistake) — NN/g 구분(핵심):**
- **슬립(slip):** 사용자가 A를 하려 했는데 무의식적으로 유사한 B를 함 — 오토파일럿·주의 분산 때 발생. **인터페이스로 막을 수 있다.**
- **실수(mistake):** 의도 자체가 틀림(잘못된 멘탈모델) — 도움말·안내·더 나은 개념모델로 대응.

**NN/g가 슬립을 유발한다고 지목한 4대 설계 결함:**
1. **미스큐(miscue):** 관습을 위반하는 디자인
2. **구분 안 되는 선택지(poorly differentiated options):** 유사한 이름·시각 스타일의 서로 다른 선택지 ← **하와이 경보의 핵심**
3. **문제적 배치(problematic presentation):** 안전장치 없는 레이아웃(위험 버튼이 일상 버튼 바로 옆)
4. **확인 누락(missing confirmations):** 중대 액션에 검증 부재

**❌ 위반**
- 신용카드 입력에 형식 검증 없이 제출 후에야 "형식 오류"
- "저장"과 "삭제"가 나란히 같은 색·크기, 확인 없이 즉시 실행
- 유사 라벨 항목이 한 드롭다운에("Test Missile Alert" / "Missile Alert")

**진단 질문(슬립 4결함으로)**
- 관습을 어긴 곳이 있는가?(miscue)
- 위험 선택지와 일상 선택지가 시각·라벨로 충분히 구분되는가?(differentiation)
- 위험 버튼이 일상 버튼과 물리적으로 떨어져 있는가?(presentation)
- 비가역 액션에 확인/재인증/undo가 있는가?(confirmation)

**✅ 수정 — 예방 위계(강한 것부터)**
1. **제약(constraint)으로 실수를 불가능하게** — 예: 결제 완료 전엔 삭제 버튼 비활성화, 형식 벗어난 입력 자체를 차단(포카요케)
2. **좋은 기본값·인라인 검증** — 실시간으로 잘못을 지적, 제출 전에 고치게
3. **위험 액션 분리·시각 차별화** — 위치·색·크기로 일상 액션과 구분
4. **확인/재인증** — 비가역·고비용에만(남발 금지)
5. **undo** — 위 전부 실패 시 회복 경로

**인접:** #3(회복)과 짝. #9(에러 회복)는 "이미 난 에러", #5는 "안 나게". NN/g: "사람이 실수하기 어렵게, 남은 실수는 회복하기 쉽게."

## #6 회상보다 인식 (Recognition Rather than Recall)

**정의(NN/g):** "요소·액션·옵션을 보이게 해 사용자의 기억 부담을 최소화하라."

**❌ 위반**
- 이전 화면의 코드·값을 외워서 다음 화면에 입력하게 함
- 명령어를 외워야만 쓸 수 있는 CLI식 UI(일반 사용자용에서)
- 아이콘만 있고 라벨/툴팁 없어 뜻을 기억해야 함

**진단 질문**
- 사용자가 A화면 정보를 B화면에서 쓸 때 "다시 보여주는가", 아니면 "외우게 하는가"?
- 작업기억 한계(7±2, 실제로는 3~4 청크 — 확인 필요, Miller 1956/Cowan 2001)를 넘겨 정보를 붙들게 하는가?
- 선택지를 노출(자동완성·최근 항목·추천)해 타이핑을 줄일 수 있는가?

**✅ 수정**
- 필요한 정보를 그 자리에 다시 표시(주문 확인 화면에 배송지·상품 재노출)
- 자동완성, 최근 사용, 즐겨찾기, 드롭다운 노출로 "고르기"로 전환
- 아이콘에 라벨/툴팁 병기

**인접:** #1(가시성) — 상태·정보를 보이게 하는 것이 회상 부담 제거.

## #7 유연성·효율 (Flexibility and Efficiency of Use)

**정의(NN/g):** "초보자에겐 숨겨진 단축키가 전문가의 상호작용을 가속해, 초보·숙련 모두를 만족시킨다."

**❌ 위반**
- 매일 쓰는 파워유저에게도 초보용 마법사만 강제
- 반대로: 단축키·제스처가 유일한 진입점이라 초보는 기능을 못 찾음(시그니파이어 부재와 결합된 위반)

**진단 질문**
- 초보는 발견 가능한 경로로, 숙련자는 단축키/일괄처리로 각자 최적 경로가 있는가?
- 가속기(키보드 단축키, 매크로, 템플릿, 최근 항목)가 있는가?
- 개인화(자주 쓰는 액션 상단 고정)가 가능한가?

**✅ 수정**
- **점진적 노출(progressive disclosure):** 기본은 단순, 고급 옵션은 접어두기
- 숨은 단축키는 "선택적 가속기"여야지 "유일한 경로"면 안 됨 — 항상 발견 가능한 대체 경로 병행(안티패턴: 숨은 제스처만)
- 스마트 기본값 + 커스터마이즈

**인접:** #8(최소주의) — 고급 기능을 숨겨 기본 화면을 단순하게.

## #8 심미·최소주의 (Aesthetic and Minimalist Design)

**정의(NN/g):** "인터페이스는 무관하거나 거의 안 쓰이는 정보를 담아선 안 된다."

**❌ 위반**
- 한 화면에 모든 기능·정보를 다 노출(신호 대 잡음비 저하)
- 장식용 요소가 핵심 액션의 시각 위계를 흐림
- 안 쓰는 옵션·배너·팝업이 핵심 콘텐츠와 주의를 경쟁

**진단 질문**
- 화면의 모든 요소가 사용자의 현재 목표에 기여하는가?
- 핵심 액션(primary CTA)이 시각적으로 가장 두드러지는가?
- 정보 밀도가 대상 사용자·맥락에 맞는가(전문가 대시보드는 밀도 높아도 됨)?

**✅ 수정**
- 콘텐츠 우선순위화 → 부차적 요소는 점진적 노출로 숨김
- "최소주의 = 미니멀 미학"이 아니라 **"관련성"** — 필요한 건 다 있되 무관한 건 없게
- 시각 위계는 biz-ui-designer와 협업하되, "무엇을 보일지"는 UX 판단

**인접:** #7(효율) — 덜 중요한 걸 숨기면 핵심 경로가 빨라짐.

## #9 에러 인식·진단·회복 (Recognize, Diagnose, Recover from Errors)

**정의(NN/g):** "에러 메시지는 평이한 언어로(에러 코드 금지), 문제를 정확히 지목하고, 해결책을 건설적으로 제안해야 한다."

**❌ 위반**
- "오류가 발생했습니다"(무엇이? 어떻게 고치나?)
- "Error 0x8007000E"만 노출
- 에러가 폼 상단에만 뜨고 어느 필드가 문제인지 안 짚음

**진단 질문**
- 에러 메시지가 (1) 무엇이 잘못됐는지 (2) 왜 (3) 어떻게 고치는지 세 가지를 다 말하는가?
- 에러가 문제 발생 지점 가까이 표시되는가(인라인)?
- 사용자를 탓하지 않는 어조인가("잘못 입력했습니다" ❌ → "이메일 형식을 확인해 주세요" ✅)?

**✅ 수정**
- 문제 지목 + 원인 + 해결책 + (가능하면) 원클릭 수정
- 인라인 에러 + 해당 필드 하이라이트 + 포커스 이동
- 어조·문구는 biz-ux-writer, 위치·구조·복구 경로는 UX

**인접:** #5(예방)의 안전망. 예방이 최선, 회복이 차선.

## #10 도움말·문서 (Help and Documentation)

**정의(NN/g):** "설명이 필요 없는 게 최선이다. 다만 필요하면 과업 완수를 돕는 문서를 제공하라."

**❌ 위반**
- 설명서를 봐야만 쓸 수 있는 UI(노먼의 "설명서 필요한 문")
- 검색 안 되는 방대한 매뉴얼, 맥락과 동떨어진 도움말

**진단 질문**
- 핵심 과업이 문서 없이 수행 가능한가(그게 이상)?
- 도움말이 필요한 지점에, 검색 가능하고, 과업 중심으로 제공되는가?
- 온보딩/툴팁/빈 상태 안내가 "사용하면서 배우게" 돕는가?

**✅ 수정**
- 1차 목표: 자기설명적 UI(시그니파이어·좋은 라벨로 문서 불필요하게)
- 필요한 도움말은 **맥락 내(in-context)**: 툴팁, 인라인 힌트, 빈 상태의 첫걸음 안내
- 문서는 과업 지향·검색 가능·단계별

**인접:** #2(현실 일치)·#6(인식) — 잘 지키면 문서 의존이 줄어든다.
