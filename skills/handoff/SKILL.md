현재 대화를 압축해 인계 문서를 만든다. 출력 위치와 작성 절차는 아래 규칙을 **그대로** 따른다.

> **빠른 경로 (Quick start)**: 시간이 급하면 — ① 0단계로 일반/task 판정(보통 일반) → ② 1단계 5질문이 모두 "아니오"면 **최소 모드**(`## 현재 상태`·`## 다음 할 일`·`## suggested skills` 3개만, 20줄 이내)로 즉시 작성. 실패해도 안전(일반=새 파일이라 이전 핸드오프 보존, task=누적, 삭제는 명시 요청 시에만).

## 0단계 — 두 종류 중 무엇인지 먼저 정한다 (가장 먼저, 건너뛰지 말 것)

handoff에는 **일반 handoff**와 **task-handoff** 두 종류가 있다. 작성 전에 반드시 어느 쪽인지 결정한다.

| 종류 | 무엇인가 | 출력 위치 | 동작 | 삭제 |
|------|----------|-----------|------|------|
| **일반 handoff** (기본) | 단일 세션 종료 시점의 단기 인계. 다음 세션이 이어받고 끝나면 폐기. | `~/.claude\handoffs\YYYY-MM-DD-HHmm-<topic-kebab>.md` | 매번 **새 파일** (날짜·시각별 누적, 이전 파일 보존) | 자유 (오래된 건 `handoff-history\`로 보관 또는 삭제) |
| **task-handoff** | 분량 많고 여러 세션에 걸치는 **하나의 큰 작업**. clear된 세션이 막힘 없이 이어가도록 맥락을 최대한 자립적으로 담는다. | `~/.claude\handoffs\tasks\<task>.md` | **Living Brief**(항상 최신 유지) + **세션 로그**(최신 블록 맨 위 누적, 완료분 ✅ 보존) 2부 구성 | **사용자가 명시적으로 "이 작업 끝났어, 지워" 라고 할 때만** |

### 폴더 구조 (3곳, 역할이 다르다)

```
~/.claude\handoffs\
├── YYYY-MM-DD-HHmm-<topic>.md   ← ① 활성: 지금 이어받아야 할 일반 handoff
├── handoff-history\             ← ② 보관: 끝났지만 남겨두고 싶은 것
└── tasks\<task>.md              ← ③ task-handoff (여러 세션 누적)
```

- **① 루트 = 활성 구역.** 새 일반 handoff는 항상 여기에 쓴다. 여기 있는 파일은 "아직 안 끝난 일"이라는 뜻이므로, 쌓여 있으면 그 자체가 신호다.
- **② `handoff-history\` = 보관소.** 작업이 끝났거나 다음 세션이 이어받고 종료된 handoff 중 **기록으로 남기고 싶은 것**을 여기로 옮긴다. 읽기 전용 취급 — 이어쓰지 않는다.
- **③ `tasks\`** — 위 표 참조.

**보관 판정 (일반 handoff를 새로 쓸 때마다 확인)**: 루트에 이전 handoff 파일이 있으면, 그게 **이번에 이어받아 끝낸 작업의 것**인지 본다.
- 끝난 것이면 → `handoff-history\`로 옮긴다(삭제 아님). 루트에는 활성 handoff만 남긴다.
- 아직 안 끝났으면 → 그대로 둔다. 여러 개가 동시에 활성일 수 있다.
- **사용자가 "이건 남겨둬"·"보관해줘"라고 하면** 무조건 `handoff-history\`로. 삭제는 사용자가 명시적으로 "지워"라고 할 때만 한다.

```powershell
Move-Item "~/.claude\handoffs\<파일명>.md" "~/.claude\handoffs\handoff-history\"
```

### 어느 쪽인지 판정

**task-handoff로 작성**하는 신호 (하나라도 해당되면 task-handoff):
- 사용자가 `task-handoff` / `태스크 핸드오프` / `작업 핸드오프` / `이 작업 계속 이어서` / `맥락 다 담아서` 등을 언급
- argument에 `--task <name>` 포함
- `~/.claude\handoffs\tasks\`에 이미 이 작업의 파일이 있어 **이어쓰는** 상황 (이 경우 무조건 task-handoff, 새 일반 handoff로 만들지 말 것)
- 작업이 여러 세션에 걸칠 만큼 크고, 사용자가 전체 맥락 보존을 원함이 분명할 때

그 외 일반적인 세션 마무리·다음 세션 인계는 모두 **일반 handoff**(기본).

**애매하면 1회만 질의**: "이건 한 번 넘기고 끝나는 일반 handoff인가요, 아니면 이 작업을 계속 이어서 누적하는 task-handoff인가요?" 답이 없으면 일반 handoff로 처리.

### 판정 전 확인 명령 (그대로 실행)
작성을 시작하기 전에 기존 task-handoff와 루트의 활성 handoff를 함께 확인한다 — task 파일이 있으면 이어쓰고(중복 신규 생성 방지), 루트 파일은 보관 판정 대상이다:
```powershell
Get-ChildItem "~/.claude\handoffs\tasks\" -File -ErrorAction SilentlyContinue | Sort-Object LastWriteTime -Descending | Select-Object -First 10 Name, LastWriteTime
Get-ChildItem "~/.claude\handoffs\" -File -ErrorAction SilentlyContinue | Sort-Object LastWriteTime -Descending | Select-Object -First 10 Name, LastWriteTime   # 활성 handoff (보관 판정 대상)
```
`handoff-history\`는 **여기서 뒤지지 않는다** — 보관소는 이어쓰기 대상이 아니다. 사용자가 과거 작업을 찾을 때만 읽는다.

### task-handoff 이름(`<task>`) 정하기
- argument `--task <name>`이 있으면 그 이름 사용. kebab-case로 정규화(공백·특수문자→`-`, 소문자).
- 없으면 작업 내용으로 짧은 kebab-case 이름을 제안하고 확인받는다 (예: `api-pagination`, `oauth-rotation`).
- `tasks/`에 유사한 기존 파일이 있으면 새로 만들지 말고 그 파일에 이어쓸지 먼저 확인한다. 직전 누적 상태는 다음으로 빠르게 확인:
```bash
Get-Content "~/.claude\handoffs\tasks\<task>.md" -TotalCount 5   # 제목·현재 상태·블록 인덱스 확인
```

## 용어 (먼저 알기)

- **in-flight**: 시작했지만 끝나지 않은 작업. handoff의 핵심 대상.
- **WIP 파일**: 수정했지만 테스트·커밋 안 된 파일. 줄 번호까지 명시 권장.
- **블로커**: 외부 응답·승인·서비스 의존으로 진행 못 하는 항목. 우회 작업 동반 필요.
- **모드(최소·중간·복잡)**: 1단계 평가 결과로 결정되는 인계 문서의 깊이·길이 등급. (**일반 handoff 전용** — task-handoff는 모드 없이 "task-handoff 전용 규칙"의 2부 구조를 따른다)
- **다음 세션 초점**: 사용자가 argument로 지정한, 다음 세션이 우선 집중할 작업명.

비유 — 일반 handoff는 **식당 교대 인수인계 쪽지**다. 끓는 냄비(WIP), 기다리는 주문(블로커), 먼저 볼 테이블(초점)을 적고, 교대가 끝나면 버린다. task-handoff는 **그 가게의 운영 일지**다. 큰 공사(예: 주방 설비 교체)가 여러 날 이어지면, 매일 끝에 "오늘 한 것/막힌 것/내일 할 것"을 일지 맨 위에 덧붙이고 지난 기록은 ✅로 남겨, 누가 와도 공사 전체 맥락을 처음부터 따라올 수 있게 한다. 공사가 끝나야 일지를 덮는다.

### task-handoff 흐름 walkthrough (한눈에)

처음 쓰는 사람이 "Living Brief 갱신 + 세션 로그 누적"을 그림으로 잡도록 3세션 흐름을 예시한다(상세 형식은 아래 "task-handoff 전용 규칙"):

1. **1세션 (생성)**: `tasks/oauth-rotation.md` 신규 → 제목·상태줄·세션 인덱스 → **Living Brief 6섹션 채움**(미션·완료기준·환경착수·지형도·결정·함정) → `⬆ 06-23 …(최신)` 세션 로그 블록 1개.
2. **2세션 (이어쓰기)**: 기존 파일 읽기만 함 → **Living Brief §1~4 최신화**(현재 사실로 덮어씀)·**§5~6에 새 결정·발견 추가**(누적) → 06-23 블록 `(최신)` 제거·완료항목 ✅ → 제목 아래·06-23 블록 **위**에 `⬆ 06-24 …(최신)` 삽입 → 상태줄·인덱스 갱신.
3. **3세션 (마무리)**: 같은 방식. 세션 로그 8블록/40KB 초과 시 낡은 로그 블록 아카이브 분리를 **제안**(Living Brief는 항상 본체 유지).
4. **작업 종료**: 사용자가 "이 작업 끝났어, 지워"라고 **명시**하면 → work-history 최종 요약 확인 후 파일 삭제.

핵심 두 축: **Living Brief는 항상 "지금"을 반영(갱신), 세션 로그는 최신이 맨 위로 쌓이고 이전은 절대 안 지움(✅ 표시)**. clear된 세션은 Living Brief만 읽어도 onboard되고, 최신 로그로 "지금 할 일"을 안다.

## 입력·의존성

- 외부 도구: 없음. 텍스트 작성과 파일 I/O만 사용.
- 입력: 현재 대화 + (있다면) PR 본문·커밋 메시지·plan/ADR 파일·이전 handoff 파일. 같은 내용은 다시 적지 않고 경로/URL로 참조.
- **입력 부재·손상 시**: 이전 handoff/PR을 못 찾거나 읽지 못하면, 현재 대화만으로 작성하고 문서 끝에 "이전 컨텍스트 미참조 — <사유>" 한 줄을 명시한다(중복·맥락 누락 위험을 다음 세션에 알림). 첫 핸드오프(참조할 이전 기록 없음)는 정상 상황이며 별도 표기 불필요.
- 출력: 마크다운 파일 1개 (0단계에서 정한 위치).

## 다른 문서와의 경계 (먼저 확인)

호출되기 전에 사용자 요청이 정말 handoff인지 확인한다.

- **work-history (`~/.claude/artifacts/work-history\YYYY-MM-DD.md`)**: 완료된 작업의 회고·기록. 과거형. → 작업이 끝났다면 work-history.
- **/init (`CLAUDE.md`)**: 프로젝트 영구 문서. 코드베이스 전체 안내. → 프로젝트 안내라면 /init.
- **handoff (이 스킬)**: 진행 중(in-flight) 작업을 다음 세션이 이어받게 하는 인계.

세 가지가 동시에 해당될 수도 있다(예: 작업 일부 완료 + 일부 진행 중). 그 경우 handoff는 in-flight 부분만 다루고, 완료 부분은 work-history 경로를 참조로만 적는다.

## 1단계 — 작성 전 상황 평가 (일반 handoff 전용, 건너뛰지 말 것)

> **task-handoff는 1~4단계를 건너뛰고 "task-handoff 전용 규칙"으로 직행한다.** 아래 5질문·최소모드·길이 가이드는 모두 일반 handoff용이다. (단 5질문은 task-handoff 세션 로그에 무엇을 담을지 점검용 체크리스트로 참고는 가능 — 의무는 아님.)

문서를 쓰기 전에 아래 5개 질문에 "예/아니오"로 답한다. 각 답이 어떤 섹션을 포함할지 결정한다.

| # | 질문 | "예"일 때 포함할 섹션 |
|---|------|---------------------|
| 1 | 시도했다가 되돌린 코드, 또는 사용자가 "그건 아니야"라고 한 접근이 1개 이상 있는가? | `## 시도했지만 실패한 접근` |
| 2 | 사용자에게 물어봤는데 답을 못 받았거나, 외부 의존(다른 사람·서비스·승인) 때문에 멈춘 항목이 있는가? | `## 미해결 / 블로커` |
| 3 | 2개 이상의 파일에 미완성 변경(수정 중·테스트 안 됨)이 남아 있는가? | `## WIP 파일 상태` |
| 4 | 도구 호출이나 코드 탐색으로 알아낸, 코드만 봐서는 모를 사실(API 응답 형태, 숨은 동작, 도메인 규칙 등)이 있는가? | `## 발견한 컨텍스트` |
| 5 | 사용자가 argument로 다음 세션 목적을 지정했는가? | `## 다음 세션 초점` (문서/블록 맨 앞에 배치) |

평가 결과 모두 "아니오"라면 → **최소 인계 모드**로 작성 (아래 "항상 포함" 섹션만, 총 20줄 이내).

## 2단계 — 항상 포함하는 섹션 (3개)

순서를 지킬 것.

1. `## 현재 상태` — 1~2문장. "무엇을 어디까지 했고, 지금 무엇을 하던 중인지." 모호한 표현(거의 다, 조만간, 대충) 금지, 구체 단계로 표현.
2. `## 다음 할 일` — 우선순위 순서로 1~5개 항목. 각 항목은 한 줄, 동작 동사로 시작 ("X 함수에 Y 케이스 테스트 추가").
3. `## suggested skills` — 다음 세션에서 호출하면 좋은 스킬명 목록. 이유 한 줄씩.

## 3단계 — 조건부 섹션 작성 규칙

1단계에서 "예"가 나온 섹션만 작성. 각 섹션의 작성 방식은 아래 표를 따른다.

| 섹션 | 작성 방식 |
|------|----------|
| `## 다음 세션 초점` | argument 원문을 인용한 뒤, 그 목적에 직결되는 컨텍스트만 2~5줄로 정리 |
| `## 시도했지만 실패한 접근` | 각 항목: "시도한 것 → 왜 실패/거부됐는지". 다음 세션이 같은 실수를 반복하지 않도록 **이유**를 반드시 포함 |
| `## 미해결 / 블로커` | 각 항목: "무엇이 막혔는지 → 누구/무엇의 응답이 필요한지 → 그동안 진행 가능한 우회 작업이 있다면 명시" |
| `## WIP 파일 상태` | `파일경로:줄번호 — 현재 상태 (예: "타입 정의는 했고 구현 미작성")` 형식 |
| `## 발견한 컨텍스트` | 비자명한 사실만. "X는 Y를 반환한다(코드만 봐서는 Z처럼 보이지만 실제는 다름)" 형식. 자명한 내용은 적지 말 것 |

## 4단계 — 길이 가이드 (목표 범위)

| 상황 | 권장 길이 | 판정 기준 |
|------|----------|----------|
| 단순 | 20줄 이내 | 1단계 평가에서 "예"가 0개, 단일 파일·명확한 흐름 |
| 중간 | 30~80줄 | "예"가 1~2개 |
| 복잡 | 80줄 이상 가능 | "예"가 3개 이상. 단 각 섹션은 핵심만, 장황한 서술 금지 |

길이를 채우기 위해 내용을 부풀리지 말 것. 쓸 게 없으면 짧은 게 정답.

> ⚠️ **이 길이 가이드는 일반 handoff 전용이다.** task-handoff는 정반대 원칙(자립성·완전성 우선)을 따르며 이 표의 적용을 받지 않는다 — 아래 "task-handoff 전용 규칙" 참조. task-handoff가 짧게 나왔다면 그건 거의 항상 맥락이 빠졌다는 신호다.

## 작성 규칙 (모호함 방지)

- **중복 금지 (일반 handoff 한정)**: 이미 PR 본문·커밋 메시지·ADR·plan 파일에 있는 내용은 옮기지 말고 `경로:줄번호` 또는 URL로 참조만 한다. **단 task-handoff는 예외** — 이어받는 세션이 그 링크에 접근 못 할 수 있으므로 핵심 맥락은 본문에 직접 담는다(참조는 보조). "task-handoff 전용 규칙"의 자립성 원칙을 따른다.
- **민감 정보 제거**: API 키, 비밀번호, 토큰, PII는 `[REDACTED]` 로 치환. 저장 직전 아래 둘 중 하나로 스캔한다(누락·오타 방지). 치환 시 보고에 "민감 정보 N건 [REDACTED] 처리" 한 줄 추가.
  - **빠른 스캔(읽기 전용)** — 의심 토큰 위치만 확인:
    ```bash
    grep -nE 'sk-|ghp_|AKIA|xox[bp]-|Bearer |password=|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+|\b\d{6}-\d{7}\b' <작성중인 파일 또는 임시본> || echo "민감정보 미탐지"
    ```
  - **자동 치환(번들 스크립트)** — stdin→[REDACTED] 치환 + 건수 출력:
    ```bash
    python3 ~/.claude\skills\handoff\scripts\redact.py < draft.md > clean.md   # 끝에 "민감 정보 N건 처리" 출력
    ```
- **모호어 금지**: "거의", "대충", "조만간", "곧", "약간" 같은 표현은 구체 수치·단계로 바꾼다.
- **코드 인용**: 5줄 이하만 인라인. 그 이상은 `파일경로:시작줄-끝줄` 로 참조.
- **시제**: 완료된 작업은 과거형, 진행 중은 "현재 ~하는 중", 다음 할 일은 명령형.

## task-handoff 전용 규칙 (최대 맥락·제로 블로커)

> **목적**: clear된 세션(기억 0)이 **이 파일 하나만 읽고 막힘 없이 작업을 이어가는 것.** 이 한 문장이 아래 모든 규칙의 근거다.
>
> 그래서 task-handoff는 일반 handoff와 작성 철학이 **반대**다:
> - **자립성 우선** — 핵심 맥락은 본문에 직접 담는다. PR·커밋·work-history는 *보조 참조*일 뿐 본문을 대체하지 못한다. 이어받는 세션이 그 링크에 접근 못 할 수 있으니 "가서 보라"로 때우지 말 것.
> - **완전성 우선, 분량은 결과물** — 일반 handoff의 "짧을수록 좋다 / 중복 금지 / 1단계 5질문" 미니멀 규칙은 task-handoff에 **적용하지 않는다.** 큰 작업의 맥락이 짧게 나왔다면 거의 항상 빠진 게 있다는 신호다.
> - **고신호 유지** — 자명한 내용·잡담·채우기용 부풀림은 금지. "코드만 봐선 모를 것"은 전부 담되, 아는 척 추측으로 채우지 말 것(모르면 "미확인"으로 표기).

### 🔒 #1 불변식 — 기존 내용은 절대 파괴하지 않는다 (다른 모든 규칙보다 우선)

task-handoff의 존재 이유는 **맥락의 변천이 보이는 것**이다: "초반엔 이런 맥락이었는데 → 중간에 이런 이유로 이렇게 바뀌어 → 지금은 이렇다". 기존 내용을 지우고 새로 쓰면 이 변천이 통째로 증발해 task-handoff가 목적을 잃는다 — **그냥 덮어쓸 거면 일반 handoff와 다를 게 없다.**

- **이어쓸 때 파일을 통째로 다시 쓰지 않는다.** 반드시 ① 기존 파일을 **Read**(통독) → ② 기존 내용을 **그대로 둔 채** 새 블록 삽입·해당 줄만 부분 수정. → **`Write` 툴로 전체 교체 금지, `Edit` 툴로만 변경한다.**
- 이전 세션 로그 블록·§5 결정 기록·§6 함정은 **한 글자도 지우지 않는다**(완료 항목은 ✅로 표시만 바꾸고 내용은 유지).
- "요약해서 압축"·"낡았으니 정리"도 **금지**. 파일이 길어지면 오직 [비대화 관리]의 아카이브(사용자 승인)로만 줄인다.
- ⚠️ **관찰된 실패(반복 금지)**: 이어쓰기인데 기존 핸드오프를 **지우고 새 내용으로 덮어쓴** 사례가 있었다. 이는 명백한 위반이다. 아래 "이어쓰기 절차"와 "저장 후 보존 검증"을 반드시 따른다.

### 파일 구조 — 2부 구성 (Living Brief + 세션 로그)

task-handoff 파일은 **항상 최신으로 유지되는 Living Brief** + **세션마다 쌓이는 로그** 두 부분이다. 이어받는 세션은 Living Brief로 완전히 onboard된 뒤, 최신 세션 로그로 "지금 막 무엇을 하던 중"을 본다.

```markdown
# <작업명> — task-handoff
> 현재 상태: <한 줄> · 브랜치: <name> · 최종 갱신: YYYY-MM-DD
<!-- 세션 인덱스(최신순): 06-26 / 06-25 / 06-24 -->

## 📌 Living Brief — 이어받는 세션이 **가장 먼저** 읽는 부분. 매 세션 최신 사실로 갱신.
### 1. 미션 (무엇을·왜)
### 2. 완료 기준 (Definition of Done)
### 3. 환경·착수 (어디서·어떻게 돌리나)
### 4. 핵심 지형도 (건드리는 파일·역할)
### 5. 결정 기록 (결정→왜→버린 대안)      ← 누적, 지우지 않음
### 6. 함정·발견 (코드만 봐선 모를 것)     ← 누적, 지우지 않음

## 🗓 세션 로그 — 최신이 맨 위, 이전 블록은 ✅로 보존(삭제 금지)
> ## ⬆ YYYY-MM-DD — <요약> (최신)
> ...
```

### Living Brief 각 섹션 작성 기준 (빠지면 이어받는 세션이 거기서 막힌다)

| 섹션 | 반드시 담을 것 | 누락 시 블로커 |
|------|---------------|---------------|
| **1. 미션** | 목표 1~3문장 + **왜** 하는가(비즈니스/기술 맥락, 티켓 번호) | 엉뚱한 방향으로 진행 |
| **2. 완료 기준** | "무엇이 충족되면 끝"인지 체크리스트. 범위 밖(안 하는 것)도 1줄 | 언제 멈출지 몰라 과/소 작업 |
| **3. 환경·착수** | repo 경로·브랜치·현재 HEAD / 빌드·실행·테스트 **명령(copy-paste)** / 필요한 접근·서버·DB·자격증명(값은 `[REDACTED]`, **위치·획득법만**) | 돌리지도 못해 시작부터 막힘 |
| **4. 핵심 지형도** | 관련/건드리는 파일 목록 + 각 역할 + 진입점 `경로:줄` | 코드 어디 있는지 찾느라 헤맴 |
| **5. 결정 기록** | 내린 결정 + **왜** + 검토하고 버린 대안 + 버린 이유 | 이미 내린 결정을 되돌리거나 재논의 |
| **6. 함정·발견** | 코드만 봐선 모를 사실, 이미 부딪힌 막다른 길, 숨은 동작·환경 특이점 | 같은 함정에 다시 빠져 시간 낭비 |

- **§1~4는 "현재 스냅샷"** — 항상 지금의 사실을 반영한다. 단 **"덮어쓰기"는 §1~4의 해당 줄 한정**이지 파일·블록 전체가 아니다(위 #1 불변식).
  - 단순 정정(오타·경로·HEAD 해시 갱신)은 그냥 그 줄만 고친다.
  - **실질적 변경(목표·완료기준·접근 방향·지형도가 바뀜)이면, 줄을 고치는 동시에 §5 결정 기록에 "무엇이 → 무엇으로 → 왜" 한 줄을 남긴다.** 그래야 "초반 맥락 → 변경 이유 → 현재"의 변천이 보인다. 옛 사실을 §1~4에서 지워도 그 변천은 §5에 영구 보존된다.
- **§5~6은 누적**(영구 지식 — 지우지 않고 새 항목만 추가). 변천·결정의 역사가 여기 쌓인다.

### 세션 로그 블록 형식 (누적, 최신이 맨 위)

```markdown
> ## ⬆ YYYY-MM-DD — <이번 세션 한 줄 요약> (최신)
> **현재 상태**: 직전 대비 무엇이 바뀌었나 (구체 단계로)
> **이번에 한 일**: 커밋 해시·`파일:줄` 수준으로 구체적
> **다음 할 일**: 실행 가능 수준 — "어느 파일 어느 함수에 무엇을 어떻게". 1번 항목은 **즉시 착수 가능**하게.
> **막힌 점/되돌린 것**: 있으면 (이유 포함)
> 상세 회고 → ~/.claude/artifacts/work-history\YYYY-MM-DD.md
```
- 날짜는 KST(`Asia/Seoul`). 블록 전체를 `>` 인용으로 감싸 "한 세션 단위"임을 드러낸다.
- 이번 세션의 **새 결정·발견은 세션 로그에 적는 동시에 Living Brief §5·§6에도 반영**한다(다음 세션이 로그 전체를 뒤지지 않게).

### 새 파일 / 이어쓰기 절차

- **새 파일**: `tasks/` 없으면 생성 → 제목·상태줄·세션 인덱스 → **Living Brief 6섹션을 빠짐없이 채움** → 첫 세션 로그 블록. (신규 파일이므로 `Write` 가능)
- **이어쓰기** (기존 파일이 있으면 무조건 이 경로 — 새 파일로 만들지 말 것):
  1. 기존 파일을 **Read로 통독**한다(건너뛰지 말 것 — 안 읽고 쓰면 덮어쓰게 된다).
  2. **`Edit` 툴로만** 변경한다(`Write` 전체 교체 금지). 변경 항목:
     - **제목 아래·기존 블록 위**에 새 세션 로그 블록 삽입(최신이 맨 위).
     - 직전 블록의 `(최신)` 표시 제거, 완료된 "다음 할 일"은 ✅로.
     - Living Brief §1~4 해당 줄 최신화(실질 변경이면 §5에 변천 한 줄), §5~6에 새 항목 **추가**.
     - 상태줄·세션 인덱스 갱신.
  3. 기존 세션 로그 블록·§5·§6 기존 항목은 **그대로 보존**(삭제·압축·재작성 금지).
- **🔍 저장 후 보존 검증 (필수)**: 저장 직후 파일을 다시 확인해 **이전 세션 로그 블록이 전부 그대로 남아 있고**(개수 = 이전 + 1), §5·§6의 기존 항목이 보존됐는지 확인한다. 하나라도 사라졌으면 덮어쓴 것 → 즉시 복구(가능하면 직전 상태로 되돌리고 Edit로 재시도). 보고에 "이전 N블록 보존 확인" 한 줄 포함.

### ✅ 제로 블로커 자가 점검 (저장 전 필수)

저장 직전, **기억 0인 LLM이 이 파일만 읽는다**고 가정하고 아래 5문에 모두 "예"인지 확인한다. 하나라도 "아니오 / 가서 봐야 안다"면 그 내용을 본문에 끌어와 보강한 뒤 저장한다.

1. 이 작업이 **무엇이고 왜** 하는지 아는가? (§1·§2)
2. 코드를 **빌드·실행·테스트**할 수 있는가? (§3 명령)
3. 관련 코드가 **어디** 있는지 아는가? (§4 지형도)
4. **지금 정확히 무엇을**, 어느 파일부터 손대야 하는지 아는가? (최신 세션 로그의 "다음 할 일")
5. 왜 이렇게 만들어졌는지 알아 **되돌리거나 재논의하지 않는가**? (§5)

### 비대화 관리

- 세션 로그 블록이 **8개를 초과하거나 파일이 ~40KB를 넘으면**, 오래된 로그 블록(✅ 완료분)을 `tasks/<task>.archive.md`로 분리할 것을 사용자에게 제안한다. **Living Brief는 절대 아카이브하지 않는다**(항상 본체에 유지 — onboarding 핵심). 본체에는 Living Brief 전체 + 최근 블록 + "이전 N개 블록은 archive 참조" 한 줄.
- 아카이브는 **사용자 승인 후에만**. 승인 없이 본체에서 옮기지 않는다(맥락 유실 방지).

### 삭제 정책 (엄수)

- task-handoff 파일은 **사용자가 명시적으로 "이 작업 끝났어 / 지워줘 / 정리해" 라고 지목할 때만** 삭제한다.
- handoff 작성 중 자동으로 지우거나 덮어쓰지 **않는다**. 새 일반 handoff 요청이 와도 task 파일은 건드리지 않는다.
- 삭제 요청 시: 지우기 전에 **완료된 작업이면 work-history에 최종 요약이 남아 있는지 확인**하고, 없으면 work-history 기록을 먼저 제안한 뒤 삭제한다.
