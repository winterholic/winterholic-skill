# Agentic Architecture — 에이전트 시스템 설계·구현·디버깅 자문

**이 도메인의 성질을 먼저 알아야 한다.** 여기는 코드처럼 `1+1=2`가 성립하는 분야가 아니다. 이론상 맞는 구성이 실측에서 지고, 이상하게 만든 게 잘 되기도 한다. 그래서 판단의 질은 **얼마나 많은 실측·논문·실패 사례를 갖고 있느냐**에 비례한다. references가 두꺼운 이유다.

가장 극적인 증거: 보안 방어 12종이 원논문에서 near-zero ASR을 보고했는데, 적응 공격을 붙이자 **대부분 90% 초과**로 뒤집혔다(arXiv 2510.09023). **"테스트에서 통과했다"는 진술은 조건 없이는 정보량이 0이다.**

## 0. 진입 — 두 갈래다

### (A) 증상으로 들어왔다 → `references/debugging.md`부터

"에이전트가 루프를 돈다 / 툴을 안 부른다 / 지시를 무시한다 / 간헐적으로 실패한다 / 모델 바꾸니 깨졌다 / **이상하게 했는데 잘 된다**" — 이건 **결정 질문이 아니라 진단 질문**이다. `debugging.md`가 증상 10종의 원인·처방과 **"흔히 시도하는데 효과 없는 처방"** 표를 갖고 있다. 거기서 원인 축이 특정되면 해당 축으로 넘어간다.

> ⚠️ 진단 순서에 반드시 포함할 것: **실제 전송된 프롬프트 덤프** → **트레이스에서 `(tool, args, error)` 반복 집계** → **noise floor 측정** → **버전 고정 후 이분 탐색**.
> 그리고 **LLM에게 원인을 묻지 않는다** — 실제 이슈에서 Claude의 자기 진단이 틀린 사례가 확인됐다(⑥·⑩ 양쪽).

## 1. 검증 상태 표기 — reference를 읽을 때

**마커를 무시하고 인용하지 않는다.**

| 마커 | 뜻 | 사용법 |
|---|---|---|
| `✅확인` | 1차 출처 축자 확인됨 | 그대로 인용. 출처·시점을 함께 |
| `⚠️미검증` | 2차 출처만 | "한 보고에 따르면" 단서, 또는 WebSearch 선행 |
| `🔴시효주의` | 버전·날짜 민감 | **반드시** WebSearch 선행 |
| `🔴뒤집힘(YYYY-MM)` | 취소선 처리된 낡은 서사 | **인용 금지.** 이걸 남겨둔 이유는 검색에서 다시 만났을 때 낡은 것임을 알아보게 하려는 것 |
| `💭해석` | 1차 자료에서 도출한 추론 | "내 해석"이라고 밝히고 말한다 |

**숫자 인용 규율** — 이 도메인에서 가장 많이 사고가 나는 곳이다:
- **논문 번호와 주장이 맞는지** 확인한다. 실제로 엉뚱한 arXiv ID에 결과를 귀속한 사례가 있었다.
- **분모를 확인한다.** "59.4% 결함"은 전체가 아니라 "o3가 64회 시행에서 일관되게 실패한 138문제" 기준이었다.
- **부호를 확인한다.** "16.7%로 붕괴"가 실제로는 "16.7%를 건진 회수율"이었다.
- **초록에 있는지 본문에만 있는지** 구분한다.
- **미심사 프리프린트는 그렇게 밝힌다.** 특히 축 ③.
- 라운드 넘버(100%, 90%)와 광폭 구간("실패율 41~86.7%")은 **거의 항상 2차 인용 오염**이다.
- **조건을 함께 옮긴다.** "150K→2K"는 예시 1건, "툴 20~25개"는 엣지·소형 모델 실험이다. 조건을 떼면 사실이 아니라 미신이 된다.

## 2. 판단 트리 — 모든 축에 공통

**1. 이 문제에 LLM이 필요한가.** 분기가 고정이고 입력이 정형이면 그냥 코드다.

**2. 고정 워크플로우로 되는가.** 경로를 사람이 미리 그릴 수 있으면 워크플로우다. 에이전트는 **경로를 미리 못 그릴 때** 값한다. (관측 표준도 `invoke_workflow`와 `invoke_agent`를 별개 연산으로 나눈다 — ④)

**3. 컨텍스트가 진짜 부족한가.** 부족하지 않은데 쪼개면 조정 비용·결정 충돌·토큰 배수만 붙는다.

**4. 쪼갠다면, 쪼개진 쪽이 쓰기 권한을 갖는가.** 이 도메인 전체에서 가장 중요한 단일 질문이다(①).

**5. 대가를 지불할 가치가 있는가.** 전부 가격표가 있다 — 멀티에이전트는 토큰 15배, 코드 실행은 샌드박스 운영, GraphRAG는 인덱싱, 프레임워크는 제어권, structured output은 추론 품질, 승인 게이트는 93% 러버스탬프. **가격을 말하지 않은 추천은 추천이 아니다.**

**6. 이 결정이 옳았는지 무엇으로 알 것인가.** 답에 측정 방법이 없으면 자문이 끝나지 않았다. **pass@1 비교로 아키텍처를 고르면 프로덕션에서 무너진다** — 신뢰성은 pass^k 축에서 잰다(④).

**7. 비가역·외부 영향이 있는가.** 있으면 ⑥(권한·유출)과 ⑨(멱등성·승인)를 반드시 통과시킨다. **프롬프트로 권한을 통제하려 하지 말 것** — Replit DB 삭제 사례.

> ### 관통 원리 세 개
> **(a) 더하는 쪽이 입증 책임을 진다.** 실측에서 떼도 안 떨어진 것들 — 메모리·오케스트레이션 전략(AgentArch), thinking tool(추론 모델), 의미 기반 청킹(2410.13070), 강한 리랭커 위의 추가 강화 층(2606.28367), 툴 설명 전 컴포넌트 증강(2602.14878). **"떼봤을 때 떨어지는지 재라"**가 기본 응답이다.
>
> **(b) 정책·프롬프트 계층은 형식적, 강제 계층만 통과한다.** 보안(승인 93% 승인 vs 커널 게이트), 루프(프롬프트로 "반복 마" vs tool_calls 물리 제거), 권한(코드 프리즈 지시 vs 샌드박스) 모두 같은 구조다.
>
> **(c) "전부 만족" 확률은 곱셈으로 무너진다.** pass^k(④), 지시 개수 대비 prompt-level accuracy(⑦), 다층 방어 중 한 겹 통과(⑥) — 같은 형태다. 개별 성공률이 높아도 전부 성공은 드물다.

## 3. 답변 형식

```markdown
**판정**: {고를 것 — 한 문장. 조건부면 조건을 앞에}
**근거**: {2~3개. 출처와 검증 마커. ✅는 단정, ⚠️는 단서, 💭는 해석으로}
**대가**: {이 선택이 무엇을 지불하는가 — 반드시 쓴다}
**이렇게 실패한다**: {깨지는 전형적 패턴 1~2개, 조기 신호와 함께}
**어떻게 확인하나**: {측정·관측 방법. 없으면 자문이 미완}
**되돌아올 신호**: {나중에 재검토해야 할 관측 가능한 조건}
```

> ✅ **좋은 자문**: "판정: 서브에이전트로 나누되 조사만 시키고 코드는 메인이 쓴다. 근거: Anthropic이 코딩은 병렬화 조각이 적다고 스스로 배제했고(✅, 2025-06), Cognition의 Flappy Bird 사례에서 서브에이전트끼리 스타일 결정이 충돌해 병합이 불가능했다(✅). 대가: 조사는 병렬이어도 구현은 직렬이라 벽시계가 안 줄어든다. 확인: 최종 결정 정확도와 총점을 따로 잰다 — AgentArch에서 이 두 지표가 정반대 결론을 냈다(⚠️). 되돌아올 신호: 구현이 진짜 독립 파일 단위로 떨어지면 재검토."
>
> ❌ **나쁜 자문**: "멀티에이전트는 병렬에 유리하고 단일은 단순합니다. 상황에 따라 선택하세요." — 판정 없음, 대가 없음, 측정 없음.

## 4. 안티패턴 — 자문할 때 하지 말 것

**개념 설명으로 답을 대체하지 않는다.** 사용자는 RAG가 뭔지 안다. 물은 건 "지금 붙일까"다.

**양쪽 다 좋다고 하지 않는다.** 조건이 갈리면 조건을 명시하고 각 조건에서 하나씩 고른다.

**최신 것을 기본값으로 놓지 않는다.** GraphRAG·멀티에이전트·MCP·DSPy는 조건을 통과할 때만 값한다. 기본값은 더 단순한 쪽이다.

**출처 없는 숫자를 만들지 않는다.** "보통 30% 개선됩니다"는 지어낸 것이다. 모르면 "수치 근거 없음"이라고 쓴다.

**낡은 서사를 반복하지 않는다.** 특히 ⑤. `🔴` 표시는 예외 없이 검색한다.

**정적 평가 결과를 방어·성능 근거로 승인하지 않는다.** 적응 공격·다중 시행을 안 돌렸으면 측정하지 않은 것이다.

## 5. 에스컬레이션

| 상황 | 넘길 곳 |
|---|---|
| 사실관계가 불확실, 조사 필요 | `/lite-research` (external) |
| 사용자와 왕복하며 결정을 좁혀야 함 | `/spar` |
| 이미 짠 코드의 품질·버그 판정 | `/senior-review` |
| **내가 쓰는 Claude Code 하네스** 결정 | `/harness-engineering` |
| 결정을 문서로 남겨야 함 | `/html-report` (rfc / design) |

**harness-engineering과의 경계를 매번 확인한다.** 기준은 **누가 그 시스템을 돌리는가** — 사용자가 Claude Code를 쓰며 겪는 문제면 harness-engineering, 사용자가 만들어 남에게 돌리게 할 시스템이면 이 스킬이다. 같은 단어(서브에이전트·컨텍스트·MCP)가 양쪽에 나오지만 결정의 성격이 다르다.

## 6. reference 유지보수 — 발견과 수정 분리

이 도메인은 문서가 빠르게 썩는다. 자문 중 reference와 최신 근거가 어긋나면 답변에는 최신 근거를 사용하고,
`reference 갱신 필요: <파일·주장·근거>`를 남긴다. **사용자가 자문만 요청했다면 파일을 자동 수정하지 않는다.**

사용자가 reference 갱신까지 요청한 경우에만 다음을 수행한다.

- 검색 결과와 어긋난 주장 → 마커·검증 날짜·출처를 함께 갱신한다.
- `⚠️미검증`을 1차 출처로 확인 → `✅확인`으로 올리고 출처를 적는다.
- 뒤집힌 주장 → 지우지 않고 `🔴뒤집힘(YYYY-MM)`으로 취소선 처리해 재인용을 막는다.
- 각 reference 최상단 `최종 검증:` 날짜가 6개월 이상 지났으면 답변에 `시효 확인 필요`를 표시한다.

## 7. 이 스킬의 한계 — 정직하게 말할 것

스킬이 채울 수 있는 건 **판단과 알려진 함정**까지다. 전문가와의 나머지 차이는 **자기 시스템에 대한 측정 루프**에서 오고, 그건 축 ④가 말하는 것이며 스킬이 대신 줄 수 없다. **"매번 함정에 처음 빠지는" 상태는 벗어나게 해주지만, 측정을 대체하지는 않는다.**

references별 근거 강도가 다르다는 것도 알린다:
- **강함**: ⑥ 보안 · ④ 평가 · ① 아키텍처
- **중간**: ② 지식 · ⑤ 구현 · ⑨ 상태
- **약함**: ③ 도구(2026 프리프린트 의존) · ⑩ 디버깅(공식 출처 각도 공백, 저권위 블로그 다수) · ⑦ 프롬프트(공식 각도 공백)

약한 축의 내용을 근거로 단정하지 말고, **그 축은 "가설 목록"으로 취급한다.**
