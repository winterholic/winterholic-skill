## 핵심 판단 — 기본값은 직접 구현이다

`💭해석` 에이전트 루프의 본체는 **"모델 호출 → 툴 실행 → 결과 append → 반복"**이고 프레임워크 없이 수십 줄이다. 프레임워크가 값하는 건 그 위에 얹히는 것 — 영속성, 체크포인팅, 재개, 스트리밍, 관측 — 이 **실제로 필요할 때**다.

고르기 전에 물을 것: **"내가 필요한 게 루프인가, 루프 주변의 인프라인가?"** 루프뿐이면 직접 짠다.

`✅확인` **deepagents가 공식 트랙에 별도 존재한다** — `create_agent` 위에 상위 에이전트 레이어를 얹는 방향이 공식 로드맵이다. "1.0 내고 정리 끝"이 아니다.

`✅확인` v1 구조(공식 마이그레이션 문서):
- `langchain` 네임스페이스는 **에이전트용 필수 빌딩블록**(agents, messages, tools, chat models, embeddings)으로 축소
- **`langchain-classic` 이동 대상**: 레거시 체인(LLMChain·ConversationChain), retrievers, indexing API, hub, embeddings 모듈, langchain-community 재수출
- `create_react_agent` → **`create_agent`**로 대체. `langgraph.prebuilt`는 구 거처이고 **LangGraph가 에이전트 인프라(그래프·체크포인팅) 층**을 담당
- `create_agent`는 LangGraph 위에 지어져 **durable execution·스트리밍·체크포인팅이 그래프 코드 없이 따라온다**

`🔴뒤집힘(2026-08)` ~~"구 API EOL은 2026-12"~~ — **공식 마이그레이션 문서·changelog 어디에도 삭제/EOL 날짜가 없다.** 상태는 "deprecated + langchain-classic 이동, **미삭제**"다. 널리 유통되는 2026-12는 1차 출처가 전무하므로 **완화하지 말고 폐기한다.** 정확한 표현은 **"공식 EOL 날짜 미발표(2026-08 확인)"**.

`🔴뒤집힘(2026-08)` ~~"신규 에이전트는 LangGraph로. 멘탈모델이 달라 사실상 재작성"~~ — 2024~2025 초 서사이고 무효다. 목적지는 `create_agent`이고 LangGraph는 **커스텀 그래프·상태 제어가 필요할 때 내려가는 하위 계층**이다.
*(두 항목을 지우지 않고 남긴 이유 — 둘 다 아직 검색 상위에 대량으로 깔려 있어서, 다시 만났을 때 낡은 것임을 알아야 한다.)*

**자문에 쓰는 방식**: "LangChain 쓸까 LangGraph 쓸까"라는 질문에는 **질문 자체가 낡았다**고 알려준다. 지금 갈림길은 `create_agent`(대부분) vs 그래프 직접 조립(제어가 필요할 때) vs 프레임워크 없이(루프만 필요할 때)다.

## 멀티에이전트 프레임워크 — 실패는 줄지 않고 이사한다

`✅확인` MAST([arXiv 2503.13657](https://arxiv.org/html/2503.13657v3))는 프레임워크별 트레이스를 실제로 갖고 있다: 7개 시스템 **1,642 트레이스** (ChatDev 230, MetaGPT 330, **AG2/MathChat 427**, Magentic-One 195, HyperAgent 30, AppWorld 30, OpenManus 30).

`✅확인` **동일 조건(GPT-4o, ProgramDev-v2)에서 MetaGPT는 ChatDev보다 FC1·FC2 실패가 60~68% 적지만 FC3(검증) 실패는 1.56배 많다.** → **프레임워크를 바꾸면 실패 유형이 이동한다.**

`✅확인` 집계 분포 **FC1 43.9% / FC2 32.15% / FC3 23.95%**. **"MAS 실패에 one-size-fits-all 해법은 없다"**가 저자 결론이고, 시스템별 지문이 있다(AppWorld=조기 종료, OpenManus=단계 반복, HyperAgent=단계 반복+부정확한 검증).

`✅확인` 개입 실험(ChatDev): 역할 명세 개선 +9.4%p, 상위 목표 검증 추가 +15.6%p. **그럼에도 절대 완료율은 낮아 "구조적 재설계 필요"로 닫는다.**

`💭해석` **자문 결론**: 프레임워크 교체는 물론이고 프롬프트·오케스트레이션 튜닝도 조정 문제를 못 푼다. "CrewAI로 바꾸면 나아질까?"라는 질문에는 **아니오, 실패 유형만 바뀐다**고 답한다.

`⚠️미검증` 프레임워크 간 허위정보 전파 캐스케이드가 포화에 가깝고 CrewAI에서 허브 노드 주입이 전체 실패 100%를 유발한 반면 리프 노드는 15.9%였다는 보고 — **원논문 미확인, 수치 인용 금지.** 방향(중앙 집중 토폴로지가 단일 오염점에 취약)만 참고.

## Claude Agent SDK

`✅확인` 공식 문서(https://code.claude.com/docs/en/agent-sdk/overview):
- **Python·TypeScript만** 제공. 다른 언어는 CLI를 서브프로세스로(`-p --output-format json`)
- capability: built-in tools(파일 read/write/edit, 명령 실행, 웹 검색) · hooks · subagents · MCP · permissions · sessions(재개·fork) · **skills/commands/memory(`.claude/` 및 `~/.claude/`에서 Claude Code와 동일하게 자동 로드)** · plugins

`✅확인` **공식 3단 선택 기준** — 이게 "프레임워크 vs 직접 구현" 이분법을 깬다:

| 원하는 것 | 고를 것 |
|---|---|
| 툴 루프를 직접 구현하지 않기 (내 프로세스에서 루프 실행) | **Agent SDK** |
| API를 직접 호출하고 루프를 직접 구현 | **Client SDK** |
| 장기·비동기 에이전트를 샌드박스·세션 인프라 없이 | **Managed Agents** (별개 제품, 호스팅 REST API — **Anthropic이 에이전트와 샌드박스를 직접 운영**) |
| 터미널에서 대화식 개발·일회성 작업 | **Claude Code CLI** |

`💭해석` 즉 축은 두 개다 — **루프를 누가 소유하나 / 인프라를 누가 소유하나.** 이 프레임이 이 축 자문에서 가장 유용한 도구다.
그리고 **Managed Agents가 축 ③의 코드 실행 판정과 직접 연결된다** — 코드 실행을 쓰지 말아야 할 조건이 "샌드박싱·리소스 제한·모니터링을 감당 못 할 때"였는데, Managed Agents는 정확히 그 인프라를 남에게 넘기는 선택지다. "코드 실행을 하고 싶지만 샌드박스를 운영할 수 없다"면 여기가 답이다.

`✅확인` 라이선스·브랜딩(원문 확인, 2026-08-26): Anthropic **Commercial Terms of Service** 적용(자기 고객·엔드유저에게 제공할 때도 포함). **사전 승인 없이는 제3자 개발자가 자기 제품에 claude.ai 로그인이나 claude.ai 레이트리밋을 제공할 수 없고 API 키 인증을 써야 한다.**
브랜딩 — 허용: "Claude Agent"(드롭다운 권장), "Claude"(이미 "Agents"로 라벨된 메뉴 안에서), "{내제품명} Powered by Claude". **불허: "Claude Code" / "Claude Code Agent"**, Claude Code를 모방하는 ASCII 아트·시각 요소.
`💭해석` 상용 제품을 만들 계획이면 이게 설계 제약이다 — 인증 방식이 강제되므로 "사용자가 자기 claude.ai 계정으로 로그인해서 쓰는 제품"은 사전 승인 없이는 불가능하다.

`⚠️미검증` TS SDK 변경: 서브에이전트 **중첩 스폰 깊이 상한 5→1**(`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`로 완화), **동시 실행 20 상한**(`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). 원문 CHANGELOG 미열람이라 **정확한 숫자·버전 인용 금지.**
`💭해석` 방향이 사실이면 흥미롭다 — **프레임워크가 팬아웃 설계를 강제로 좁힌 사례**이고 축 ①의 조정 비용 논점과 정확히 맞는다.

`✅확인` 공식 문서가 **에이전트 하네스 설계 자료를 직접 링크**한다 — *"A harness for every task: dynamic workflows in Claude Code"*(claude.com/blog). Claude Code 팀이 서브에이전트를 대규모로 오케스트레이션하는 방식이라 축 ① 자문에 참고 가치가 있다. *(내용 미확인 — 다음 라운드 확인 대상.)*

## 프레임워크를 떠날 신호

`💭해석` 이탈은 "느려서"가 아니라 **제어권 상실** 때문이다. 조건부 라우팅, 커스텀 재시도, 툴 호출 중 부분 출력 스트리밍 같은 **비자명한 요구**가 생기면 상속 여러 겹을 뒤져 주입 지점을 찾게 되고, 결국 프레임워크를 감싸는 어댑터를 쓰게 된다.
**→ 어댑터를 쓰기 시작한 시점이 raw SDK로 내려갈 신호다.**

추가 신호:
- 프레임워크가 **컨텍스트 조립을 불투명하게 감싼다.** 컨텍스트 프루닝이 비용·정확도의 핵심 레버인데(축 ②) 무엇이 프롬프트에 들어가는지 못 보면 그 레버를 못 잡는다.
- 디버깅할 때 **최종 프롬프트를 눈으로 못 본다.** (축 ④의 트레이싱 필수 항목)
- 버전 업그레이드가 내 코드를 깨는 빈도가 기능 추가 빈도보다 높다.

⚠️ **중요한 경고 — "LangChain exit" 서사의 증거 상태**
`🔴뒤집힘(2026-08)` ~~"실명 1차 이탈 후기는 존재하지 않는다"~~ — **존재한다.** 대표적으로 Octomind(Fabian Both, 2024)의 *Why we no longer use LangChain for building our AI agents*.
다만 `⚠️미검증` **이번 조사에서 검색 상위는 전부 저자 불명 SEO 블로그**였고, 그 블로그들은 *"팀들은 걷어낸 프레임워크에 대해 자축 글을 안 쓰니 이 이주는 보이지 않는다"*는 **반증불가 논법으로 근거 부재를 변명**한다. 즉 2026년의 "프레임워크 이탈" 담론 대부분은 **1차 증거 없이 유통되는 밈**이다. 사용자가 이걸 근거로 결정하려 하면 이 상태를 알려준다.

`⚠️미검증` **직접 구현의 숨은 비용**(재시도·영속성·관측을 자작하며 무엇을 잃었나) 실측 후기를 **하나도 못 찾았다.** 프레임워크 유지 조건을 정당화하는 핵심 반례인데 표본이 없다 — **"직접 짜라"고 권할 때 이 비대칭을 밝힌다.**

## DSPy — 값하는 조건과 실제 이탈 이유

`⚠️미검증`(2차 수렴 + 실명 후기) 값하는 조건 3개:
1. **잘 정의된 태스크** + **라벨된(또는 라벨 가능한) 평가 세트**
2. 체계적으로 도달해야 할 **성능 목표**
3. 호출량이 커서 최적화·소형 모델 전환이 **비용으로 회수**될 것

`✅확인` **이탈 후기가 실재한다** — HN "If DSPy is so great, why isn't anyone using it?" ([item 47490365](https://news.ycombinator.com/item?id=47490365)), 실사용자 핸들 인용:
- eval에 수십 달러 썼지만 **매번 개선이 전혀 없었다**
- Pydantic만 쓰는 것보다 효과가 없고 **컨텍스트 제어가 부족**해 제거
- 프로덕션에 썼다가 **bloat만 남아 되돌렸다**
- **최적화된 프롬프트를 추출할 수 없다**는 걸 알고 물러섰다

`✅확인` **공통 병목은 옵티마이저 성능이 아니라 자동 메트릭·평가셋 부재다** — *"DSPy는 좋은 자동 메트릭이 있기 전까지는 이점을 드러내지 않는다"*, *"사람들이 풀려는 문제 상당수는 평가 경로가 자명하지 않다."*
→ **위 3조건 판정을 그대로 지지한다.** 메트릭 없이 DSPy를 권하지 않는다. 그리고 그 메트릭 설계는 축 ④의 문제다.

`⚠️미검증` 구조적 마찰 2건: (a) **Python 전용**이라 폴리글랏 조직에서 막히고, 한 팀은 옵티마이저를 돌리려 **프로덕션에 안 쓸 별도 Python 레포**를 유지해야 했다. (b) 최적화 산출물이 불투명한 blob으로 취급돼 프롬프트를 꺼내 볼 수 없다.

`⚠️미검증` 긍정 측: Dropbox가 DSPy로 모델 교체 테스트를 돌려 **측정 근거로 모델 선택**을 결정한 사례, 프로덕션 명단(Shopify·Databricks·JetBlue·Moody's·Replit·AWS 등), *"옵티마이저를 돌리기 전에 DSPy 시그니처로 옮기기만 해도 결과가 좋아졌다"*는 후기.
`💭해석` 마지막 항목이 시사적이다 — 이득의 일부는 옵티마이저가 아니라 **구조화 강제**에서 온다. 그렇다면 Pydantic 등으로도 얻을 수 있고, 실제로 그렇게 판단해 이탈한 사용자가 위에 있다.

`🔴시효주의` GEPA가 MIPROv2 대비 +13%, AIME 2025 +12%를 35배 적은 rollout으로 달성한다는 수치 — **2차 출처 경유, arXiv 원문 미확인. 인용 금지.**

## 선택 표

| 상황 | 고를 것 |
|---|---|
| 에이전트 루프만 필요, 인프라는 이미 있음 | **직접 구현** |
| 표준 루프 + 영속성·스트리밍·체크포인팅을 공짜로 | `create_agent` (LangChain v1) |
| 제어 흐름이 비표준(분기·인간 개입·재개 지점 지정) | **LangGraph 그래프 직접 조립** |
| Claude 전용, 툴 루프를 안 짜고 싶다 | **Claude Agent SDK** |
| 장기·비동기 + 샌드박스 인프라를 안 만들고 싶다 | **Managed Agents** |
| 측정 가능한 메트릭 + 라벨 세트 + 대량 호출 | **DSPy** (3조건 전부 충족 시) |
| 멀티에이전트 프레임워크(CrewAI 등) | 축 ①을 먼저 통과시킨다. **대개 통과 못 하고, 통과해도 실패는 이사만 한다** |
| AutoGen | **신규 채택 금지** — 상류가 maintenance mode |

## 실패 패턴

- **프레임워크를 먼저 고르고 문제를 거기 맞춘다** — 가장 흔하다. 신호: "이걸 어떻게 체인으로 표현하지?"
- **낡은 튜토리얼로 deprecated API를 새로 짓는다** — 이 도메인 특유의 함정. 튜토리얼 날짜를 먼저 본다.
- **멀티에이전트 프레임워크로 축 ①을 우회한다** — 조정 문제는 구조 문제이고 라이브러리가 안 풀어준다(MAST).
- **관측을 나중에 붙인다** — 비결정적 시스템은 트레이스 없이 재현조차 못 한다. 선택 기준에 처음부터 넣는다(축 ④).
- **SEO 비교글로 프레임워크를 고른다** — 이 축에서 검색 결과 오염이 가장 심하다. 공식 릴리스 노트를 본다.

- LangChain 구 API의 **실제 삭제 계획** — 각 심볼의 `@deprecated(removal=...)` 인자를 소스에서 확인해야 한다.

- Managed Agents의 **세부 기능 범위·GA 여부·가격** 미확인. 확보한 것은 "별개 제품, 호스팅 REST, Anthropic이 에이전트+샌드박스 운영"까지다. platform.claude.com/docs/en/managed-agents/overview 를 직접 볼 것.

- Claude/OpenAI/Google SDK의 **현장 실패 후기·GitHub 이슈** 전혀 조사 못 함.
- 프레임워크 오버헤드의 **레이턴시·토큰 정량 실측** 없음.
