# ③ 도구 연결 — function calling / 툴 설계 / MCP / 코드 실행

최종 검증: 2026-08-26 (심층 lite-research, claim 44개 중 **confirmed 19 · unverifiable 24 · refuted 1**)

> ⚠️ **이 축은 검증률이 가장 낮다.** 근거의 상당수가 2026년 **미심사 프리프린트**이고 초록만 확인된 경우가 많다. 정밀 수치를 자문에 쓸 때는 반드시 "프리프린트, 본문 미확인" 단서를 붙인다. 방향은 신뢰하되 숫자는 단정하지 말 것.

## 핵심 판단 — 토큰을 태우는 건 툴 호출이 아니라 두 가지다

`✅확인` Anthropic이 명시한 두 주범 — [code-execution-with-MCP](https://www.anthropic.com/engineering/code-execution-with-mcp), 2025-11-04:
1. *"Tool definitions overload the context window"* — 툴 정의 **선탑재**
2. *"Intermediate tool results consume additional tokens"* — 중간 결과가 모델을 **반복 통과**

**진단을 먼저 가른다.** 사용자가 "토큰이 많이 나온다"고 하면:

| 증상 | 주범 | 대응 |
|---|---|---|
| 첫 메시지 전부터 컨텍스트가 이미 크다 | 툴 정의 선탑재 | 적응형 쇼트리스트, 툴 통합·감축 |
| 대화가 진행될수록 급격히 커진다 | 중간 결과 통과 | 코드 실행으로 데이터를 모델 밖에서 흐르게 |
| 툴은 적은데 응답 하나가 거대하다 | 툴 응답 설계 | 페이지네이션·필터·truncation |

## 툴 개수 — "임계 N개"라는 답은 거부됐다

`✅확인`(존재·설계) *How Many Tools Should an LLM Agent See? A Chance-Corrected Answer* — [arXiv 2605.24660](https://arxiv.org/abs/2605.24660) (Repantis·Gawde·Singh·Blackwell II, v1 2026-05-23 / v2 2026-06-07).

이 논문은 **"임계 N개"라는 상수 답을 명시적으로 거부**하고, 같은 깊이에서 랜덤 선택이 낼 성과를 뺀 chance-corrected 지표 **Bits-over-Random(BoR)**로 **쇼트리스트 깊이 자체**를 평가 대상으로 삼는다. 벤치마크 3종, 레지스트리 20~3,251개(BFCL 370, ToolBench 3,251).

`✅확인`(원문 대조 2026-08-26) 결과:
- BFCL(370 툴)에서 학습된 깊이 정책은 **평균 7개만 노출해 90.3%** — 고정 50개(90.8%)와 사실상 동등. **노출을 7배 줄이고 0.5pp만 잃는다.**
- **프런티어 실측**: Claude Sonnet 4.6에서 적응형 **93.1% vs 고정 5개 87.1%**, 중난도 쿼리 **76.8% vs 60.9%**.
- **트레이드오프**: ToolBench(3,251 툴)에서는 고정 5개가 **aggregate 64.7%**로 BoR(61.9%)보다 높다. **그런데** 정답이 6~20위인 하드 쿼리에서는 고정 5개가 **아무것도 못 찾고(0%)**, BoR이 그중 **16.7%를 건져낸다.**

`🔴뒤집힘(2026-08)` ~~"BoR은 6~20위 랭크 쿼리에서 16.7%로 붕괴 — 리트리버가 약하면 적응 깊이가 역효과"~~ — **부호가 반대였다.** 16.7%는 붕괴 수치가 아니라 **BoR만 잡아내는 회수율**이고, 거기서 도출한 "리트리버 약하면 적응이 역효과"라는 결론은 근거가 없다.

`💭해석` 정확한 트레이드오프는 이것이다 — **적응 깊이는 평균을 조금 깎고 꼬리를 건진다.** aggregate 지표만 보면 고정 소수가 이기는데, 그 지표가 "정답이 리트리버 상위에 없는 쿼리"를 전부 0점으로 묻어버리기 때문이다. 즉 **어느 쪽이 나은지는 꼬리 쿼리가 중요한 서비스인지에 달렸다.** 롱테일이 있는 제품이면 적응, 정형화된 요청만 받으면 고정.

⚠️ 다만 저자가 **RL 에이전트는 "제안 시스템이 아니라 지표의 프로브일 뿐"**이라고 명시했다. 즉 이 논문의 기여는 특정 구현이 아니라 **"임계 N개라는 질문 자체가 틀렸다"는 지표론**이다.
`🔴뒤집힘(2026-08)` ~~"단일 모델 실험이라 과대 인용 금지"~~ — 초록에 그런 서술이 없다. 실제로는 **벤치마크 3종 · 복수 scorer · 레지스트리 20~3,251툴**이다.

`🔴시효주의` 기존 "20~25개설"의 근거인 [arXiv 2411.15399](https://arxiv.org/abs/2411.15399) *Less is More*(2024-11-23, 46→19개 축소)는 **엣지 디바이스·소형 모델** 실험이다. 프런티어 외삽 금지. "20~25"라는 숫자 자체도 논문 축자가 아니라 검색 요약의 특성화다.

`💭해석` **자문 규칙**: "툴 몇 개까지 괜찮나"라는 질문에는 숫자로 답하지 않는다. 답은 **"리트리버 품질이 먼저다"** — 적응형 노출은 리트리버가 좋을 때만 이득이고, 나쁘면 고정 소수가 낫다.

## 툴 설명 문구 — 효과가 실재하지만 비단조다

`✅확인`(존재) *MCP Tool Descriptions Are Smelly!* — [arXiv 2602.14878](https://arxiv.org/html/2602.14878v1) (Hasan·Li·Rajbahadur·Adams·Hassan, 2026-02-16). MCP 서버 103개(공식 23·커뮤니티 80)의 툴 **856개** 감사.

`✅확인`(초록 축자) **97.1%가 스멜 1개 이상**, **56%가 목적 불명확.**
`⚠️미검증`(본문) 스멜 6종 개별 유병률(한계 미기재 89.8% · 가이드라인 부재 89.3% · 파라미터 불투명 84.3% · 과소명세 79.1% · 예시 문제 77.9%)과 **공식 vs 커뮤니티 서버 통계 검정(p>0.17)은 초록에 없다.** 본문 미열람 — 개별 수치 인용 시 단서 필수.

`✅확인`(초록 축자) 전 컴포넌트 증강 효과 — MCP-Universe(231 태스크, 6 도메인):
- 성공률 중위 **+5.85 percentage points**
- **부분 목표 달성 +15.12%** ← "평가자 점수"가 아니다
- 실행 스텝 중위 **+67.46%**, **16.67% 케이스 퇴행**

`✅확인` **논지가 확정됐다 — "컴팩트가 낫다"다.** 초록 마지막 문장: *여러 컴포넌트를 조합한 **컴팩트 변형이 행동 신뢰성을 보존하면서 불필요한 토큰 오버헤드를 줄인다.*** 즉 **전 컴포넌트 증강은 비용과 퇴행을 부른다.**
`🔴시효주의` "Examples 제거는 유의한 저하 없음"은 **초록에 없다.** 본문 확인 전까지 개별 필드 우열을 단정하지 말 것.

`💭해석` 그래서 실용 결론은 "설명을 채워라"가 아니라 **"필요한 것만 채우고 스텝 수를 함께 재라"**다. 성공률 +5.85pp를 스텝 +67% 주고 사는 건 대부분의 서비스에서 손해다 — 스텝은 레이턴시·비용·실패 기회를 모두 늘린다. **성공률만 보면 이 거래가 이득처럼 보인다는 게 함정이다.**

`⚠️미검증` 툴 이름 자체가 공격 표면이라는 연구 — **ToolTweak**(arXiv 2510.02554), 적대적 툴 이름·설명 최적화로 선택 편향을 유도. 수치는 미확인. `💭해석` 방어 측면에서 **툴 설명은 신뢰 경계**다 — 서드파티 MCP 서버의 설명 문구는 프롬프트 인젝션 표면이다(2025년 tool poisoning 연구로 이미 확립된 일반 명제).

## 툴 선택 실패의 분류

`⚠️미검증` *ToolChoiceConfusion: Causal Minimal Tool Filtering* — [arXiv 2606.06284](https://arxiv.org/abs/2606.06284) (Babu·Iyer, 2026-06-04). 실패를 셋으로 분해:
1. **wrong-tool call** — 잘못된 툴
2. **premature action** — 관련은 있으나 **현 단계에서 불필요한** 호출
3. 토큰 비용

핵심 진단: **의미 유사도 리트리벌은 premature action을 못 잡는다** (의미상 관련 있으니 걸러지지 않는다). 처방 CMTF는 precondition-effect 계약으로 **다음 스텝의 최소 프런티어만 노출**하며, 노출 100→스텝당 1개, 토큰 약 −90%를 보고한다.

⚠️ 두 수집자가 같은 논문을 official/high와 "원문 미확인"으로 정반대 분류했다. **정밀 수치는 인용 보류.**

`💭해석` 그래도 **premature action이라는 구분 자체가 실용적으로 값하다** — "툴 선택을 자꾸 틀린다"는 호소가 실제로는 "지금 부르면 안 되는 걸 부른다"인 경우가 많고, 그 처방은 이름·설명 개선이 아니라 **상태에 따라 노출을 좁히는 것**이다.

## 코드 실행 vs 툴 호출 — 정면 비교가 나왔다

`✅확인`(존재) *The Bitter Lesson of Tool Calling* — [arXiv 2608.06370](https://arxiv.org/html/2608.06370) (Patel·Sen·Lumer·Subbiah, PwC, 2026-08-06). BFCL v4 309-엔트리 서브셋, 2024-11~2026-07 출시 모델 14종에서 **programmatic tool calling(PTC)** vs 네이티브 JSON 대조.

`✅확인`(본문 대조 2026-08-26) 규모: **BFCL v4의 309-엔트리 대표 서브셋**, 2024-11~2026-07 릴리스 모델(Anthropic 5종 + OpenAI 9종). **14개 중 11개에서 PTC 동등 이상**, 대표 개선치 GPT-5.6 계열 **+10.6%**. 성능이 모델 계열보다 **출시 세대**를 따라간다.

`✅확인` 절제별 결과:
| 절제 | 결과 |
|---|---|
| **순차 체이닝** (n=52, 길이 2~20) | **길이 ≥12에서 PTC가 절대 +18.8%p 우위.** PTC는 단일 추론 턴, JSON은 링크당 턴 |
| **열거 팬아웃** (n=32, 7~48 호출) | **PTC는 N=100까지 100% 정확**, Claude Sonnet 5의 JSON은 **N=72에서 75%로 하락** |
| **context rot** (n=31, 128 스키마 홍수) | PTC 평균 **+5.5%**, JSON **−2.3%**, 파일시스템 탐색 비교군 **−32%** |
| **지연** | 13/14 모델이 베이스라인의 **0.32~0.96배**. **GPT-5만 예외로 2.8배** |

`✅확인` **PTC가 지는 조건 — 그리고 초록과 본문이 상충한다:**
본문 축자: *"Programmatic tool calling underperforms JSON tool calling by an absolute 14.1% on average in the **parallel and parallel_multiple categories**."*
그런데 **초록은 병렬 팬아웃을 "13/14 동등 이상"으로 요약한다.** 같은 논문 안에서 방향이 어긋난다.

`🔴뒤집힘(2026-08)` ~~"−14.1%는 '열거가 아닌 병렬' 태스크 값"~~ — **BFCL의 `parallel`/`parallel_multiple` 카테고리 평균**이다. 그리고 ~~"원인은 리터럴 `\n` subprocess 문법 오류, 해당 모델 −19.7~−26.9%"~~ 는 본문에서 확인되지 않았다.
`🔴뒤집힘(2026-08)` ~~"순차 체이닝 Sonnet 5 80.8→96.2%, Opus 4.8 80.8→94.2%"~~ / ~~"토큰 교차점 N≈26"~~ / ~~"JSON은 N≈70~72에서 호출을 아예 누락"~~ — 본문 확인 결과 정확한 표현은 위 표다. 특히 Sonnet 5 JSON은 **N=72에서 누락이 아니라 75%로 하락**이다.

`💭해석` **자문할 때 이렇게 쓴다** — 코드 실행은 **긴 순차 체인(≥12)과 대량 열거에서 확실히 이기고, BFCL의 병렬 카테고리에서는 진다.** 초록만 읽고 "병렬에 유리"로 인용하면 본문과 어긋나므로, **"긴 체인이면 코드 실행, 독립 병렬이면 측정해보라"**가 안전한 판정이다.
그리고 **`GPT-5`의 2.8배 지연은 단일 예외**이지 PTC의 일반 특성이 아니다 — 확장 추론 모델을 쓸 때만 확인한다.

`✅확인` Anthropic 절감 사례: *"This reduces the token usage from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%."* — **특정 예시 워크플로 1건의 수치이지 평균이 아니다.**

`✅확인` **쓰지 말아야 할 조건이 공식적으로 명시돼 있다**: *"Running agent-generated code requires a secure execution environment with appropriate sandboxing, resource limits, and monitoring. These infrastructure requirements add operational overhead and security considerations that direct tool calls avoid."*
→ **샌드박싱·리소스 제한·모니터링을 감당할 조직이 아니면 직접 툴 호출이 낫다.** 반드시 함께 말한다.

## Progressive disclosure — 어디서 하나 (미해결 논쟁)

`✅확인` Anthropic 처방: 툴을 **파일시스템 구조로 노출**해 정의를 온디맨드로 읽게 하거나, 상세도 파라미터가 있는 `search_tools`를 둔다(*"name only, name and description, or the full definition with schemas"*).

`⚠️미검증` **반대 진영**: 서버가 '툴을 찾아주는 툴'을 노출하는 형태는 한 겹을 더할 뿐이고 **호스트(에이전트) 측에서 해야 한다**는 지적. 권위는 비대칭(개인 의견)이지만 처방이 정반대라 병기 가치가 있다.
⚠️ 단, 이 논쟁을 **보안 근거로 판정하려 하지 말 것** — 툴 설명 인젝션은 정적 설명에도 성립하므로 어느 진영의 근거도 되지 않는다.

⚠️ 위 PTC 실험에서 **파일시스템 발견 방식이 −32%**로 나온 것은 이 논쟁에 불리한 데이터점이다(`⚠️미검증`, 참조 조건).

## 툴 설계 — 개수보다 형태

`⚠️미검증` Anthropic *Writing tools for agents*(2025-09-11 추정, 축자 미확인):
- **"툴이 많다고 결과가 좋아지지 않는다."** API 엔드포인트를 1:1로 래핑하지 말고 고임팩트 워크플로를 겨냥한 소수의 툴을.
- 통합 예: `list_users`+`list_events`+`create_event` → **`schedule_event`** / `read_logs` → **`search_logs`** / `get_customer_by_id`+`list_transactions`+`list_notes` → **`get_customer_context`**
- **네임스페이싱**(`asana_search` 식)이 경계 구분에 도움되며 **접두 vs 접미 선택조차 평가 성능에 non-trivial한 영향** — 모델별 실측 필요.
- **툴 응답 크기 자체가 설계 대상.** 페이지네이션·범위 선택·필터·기본 truncation.

`🔴시효주의` "Claude Code는 툴 응답을 기본 25,000 토큰으로 제한" — **버전에 따라 바뀌는 구현 상수.** 시점 표기 없이 인용 금지.

`💭해석` 가장 실용적인 휴리스틱: **"이 툴은 사람이 한 번에 하고 싶어 하는 일 하나에 대응하는가?"** API 스펙이 아니라 사용자 의도 단위로 자르면 개수와 선택 정확도가 동시에 해결된다.

## MCP를 쓰면 안 되는 경우

`💭해석`:
- **툴이 소수이고 고정된 단일 앱 내부 호출** — 프로세스 경계·스키마 협상 비용만 추가된다. 함수를 부른다.
- **대용량 중간 결과가 컨텍스트를 통과해야 하는 파이프라인** — 코드 실행으로 데이터를 모델 밖에서 흐르게 해야 한다. MCP로 감싸도 문제는 남는다.
- **재사용·조합 가능성이 없는 일회성 통합** — MCP의 값어치는 여러 호스트가 같은 서버를 재사용할 때 나온다.

⚠️ "대응책은 툴을 줄이는 게 아니라 코드로 감싸는 것"이라는 대비는 **과장**이다. Anthropic은 툴 수 줄이기도 함께 권고하며 둘은 배타적이지 않다.

`⚠️미검증` 프로덕션 신호로 자주 인용되는 것들 — MCP 서버 다수 연결 시 첫 메시지 전 수만 토큰 소진, 특정 호스트의 툴 개수 상한 도입, 병렬 툴 호출 회귀 버그 등. **전부 GitHub 이슈·개인 블로그 자기보고이고 원문 미열람이다.** 사례로 언급할 수 있으나 수치 인용 금지.

## 실패 패턴

- **툴 선택을 자꾸 틀린다** → 개수보다 **경계 모호성**과 **premature action**을 먼저 본다. 처방은 이름 개선이 아니라 상태별 노출 축소일 수 있다.
- **첫 턴부터 컨텍스트가 크다** → 붙여둔 MCP 서버 수를 센다. 안 쓰는 서버를 떼는 게 가장 싸다.
- **툴은 성공했는데 답이 틀리다** → 응답이 조용히 잘렸거나 형식이 모호한 경우. 응답 스키마를 본다.
- **에이전트가 같은 툴을 반복 호출** → 응답에 "다음에 뭘 해야 하는지"가 없다. 에러 메시지를 **모델이 읽고 복구할 수 있게** 쓴다. (`💭해석` — 이 처방의 정량 실측은 확보 못 했다. 축 ①의 "재시도보다 재계획" 항목 참조)
- **병렬 호출을 켰더니 순서 의존이 깨졌다** → 열거형(독립 팬아웃)과 순서 의존형을 구분하지 않은 것. 위 PTC 실험도 이 두 경우가 정반대 결과를 낸다.
