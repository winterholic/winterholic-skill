# ⑨ 상태·내구성·HITL — 체크포인팅 / 멱등성 / 승인 게이트

최종 검증: 2026-08-26 (심층 lite-research, claim 25개 중 confirmed 16 · unverifiable 5 · refuted 4)

> ⚠️ **이 축은 수집자 하나가 망가진 결과를 반환해 현장 각도 하나만 반영됐다.** 공식 문서 각도(프레임워크의 durable execution 설계 의도)가 비어 있으므로, 아래는 **"어디서 깨지는가"에 치우쳐 있다.** 균형을 위해 프레임워크 공식 문서를 별도로 볼 것.

## 핵심 판단 — 프레임워크의 durability 플래그를 신뢰 경계로 삼지 말 것

이 축에서 가장 값진 발견이다. **`durability="sync"`조차 exactly-once가 아니다.**

`✅확인` [langgraph#8039](https://github.com/langchain-ai/langgraph/issues/8039) — 재현자가 코드 라인까지 짚었다: `pregel/_loop.py`가 **`checkpointer.put_writes()`(완료된 task의 pending writes)와 `checkpointer.put()`(후속 체크포인트)을 같은 `BackgroundExecutor`(ThreadPoolExecutor)에 순서 보장 없이 submit**한다. 따라서 `put()` 중 크래시 시 writes의 durability가 **OS 스레드 스케줄러에 좌우된다.**

`✅확인` **결과가 호스트 CPU 수에 따라 갈린다.** SIGKILL 재현 스크립트에서 1-vCPU 호스트와 16-thread AMD Ryzen이 **상반된 결과**를 보였다(각 호스트에서는 결정론적). 즉 **동일 코드·동일 버전이 실행 환경에 따라 결제·메일을 두 번 보낸다.**
⚠️ 어느 지연이 어느 결과를 낳는지의 **인과 매핑은 보고서 요약과 원문 로그가 반대로 읽혀 확정하지 않는다.** 현상(환경에 따라 부작용 중복)만 취한다.

`✅확인` 이슈는 **열린 상태**이고 메인테이너 응답이 확인되지 않았다.

**→ 판정: 멱등성은 프레임워크가 아니라 툴 호출 계층에서 강제한다.** idempotency key + 실행 로그 + 사전 조회. 프레임워크의 durability 보장은 "대개 잘 된다" 수준으로 취급한다.

## 툴 실행 멱등성 — 비가역 작업은 노드를 격리한다

`✅확인` **`interrupt()`는 재개 시 노드를 처음부터 재실행한다.** 그래서 한 `tool_node` 안에 자동 실행 툴과 승인 필요 툴을 섞으면 — 승인 화면이 뜨기 전에 이미 끝난 자동 툴이 재개 시 **한 번 더 실행된다.** 구체 사례: `create_ticket`(자동) + `send_email`(승인) → **티켓 2건.**

`✅확인` 코드 수준 원인: 그래프 state **밖의 로컬 `results` 리스트**가 interrupt로 버려지고, 재개 시 루프가 처음부터 돈다. 관련 이슈 langgraph#6208(2025-09) 미해결 보고.

**→ 처방: 부작용이 있거나 비가역인 툴은 각각 독립 노드로 분리한다.** 이게 이 축의 가장 실용적인 단일 규칙이다.

`🔴뒤집힘(2026-08)` ~~"병렬 툴 interrupt ID 충돌(#6626)·ToolNode resume 오라우팅(#6533)이 현재 제약"~~ — **두 이슈 모두 CLOSED다.** "과거 보고된 결함"으로만 쓰고, 현재 버전 재현 여부는 직접 확인 후 현재형으로 인용한다.

### 비가역 작업 체크리스트 (`💭해석`)
1. 이 툴이 두 번 실행되면 무엇이 잘못되나? (답이 "아무것도"가 아니면 idempotency key 필수)
2. 외부 시스템이 idempotency key를 받는가? 안 받으면 **사전 조회**(이미 했는지 확인)로 대체.
3. 실행 로그를 툴 호출 **이전에** 쓰는가? 이후에 쓰면 그 사이 크래시가 중복을 만든다.
4. 되돌릴 수 있는가? 없으면 승인 게이트 또는 dry-run이 필요하다.

## 보상 트랜잭션 / saga — 공백이다

`⚠️미검증` **에이전트 맥락에서 saga·보상 트랜잭션이 실제로 돌고 있다는 실명 증거를 찾지 못했다**(부재의 증거가 아니라 예산 내 미발견). 프레임워크는 compensation 프리미티브를 제공하지 않는 것으로 보이고, 현장은 **"비가역 툴 노드 격리 + idempotency key + 승인 게이트"**로 회피하는 쪽을 택했다.

`💭해석` 이 공백 자체가 설계 정보다 — **에이전트에서 saga를 쓰려면 직접 만들어야 한다.** Temporal 등 워크플로 엔진의 compensation 문서가 이식 후보이지만 이번 라운드에서 확인하지 못했다.

## 체크포인트 크기 — 즉시 오는 운영 비용

`✅확인` 실명 프로덕션 후기(Tadeo Donegana): **주 12만+ 대화**, 대화 1건당 4개 테이블에 **약 93 레코드**(메시지 2 + 툴콜 3 기준), **스테이징 1주에 `checkpoint_blobs` 56MB / 약 1.8만 레코드.** TTL·아카이브 없이는 무한 증가.

`✅확인` 그 팀의 대응 — **그대로 쓸 수 있는 패턴이다**:
| 조치 | 이유 |
|---|---|
| conversations 마스터 테이블 타임스탬프 기준 주기적 DELETE | OSS Postgres checkpointer에 TTL이 없어서 직접 구현 |
| **partman으로 `thread_id` 파티셔닝** | 대량 삭제 시 **프로덕션 테이블 락 회피**가 동기 |
| 주간 S3 콜드 스토리지 ETL | LangSmith 14일 보존 한계 탈피 |
| **선택적 체크포인팅** — supervisor 그래프에만 체크포인터 컴파일, specialist 서브그래프는 제외 | 전부 체크포인트할 필요가 없다 |
| `setup()` 대신 Alembic 마이그레이션 | 스키마를 프레임워크에 맡기지 않음 |

`✅확인` **단 이 후기에 장애 사고는 없다** — 사후 대응이 아니라 **선제적 용량 계획**이다. "터졌다"는 실명 postmortem이 아니라는 점을 밝혀 쓴다.

`⚠️미검증` [langgraph#7714](https://github.com/langchain-ai/langgraph/issues/7714) — 직렬화가 매 체크포인트 쓰기마다 채널 값별로 **full Pydantic 메타데이터**를 직렬화해 **저장 85.3%(6.79배) · 토큰 37.8% 오버헤드**를 내며 **opt-out 경로가 없다.** 재현 가능한 drop-in fix 첨부.

`⚠️미검증` OSS Postgres Checkpointer에는 **TTL 기능이 없다**(Postgres 자체도 네이티브 TTL 없음). TTL 설정은 LangGraph Platform 쪽에만 제공.

`💭해석` **제어면 / 데이터면 분리**가 핵심 설계 처방이다 — 라우팅 플래그 같은 작은 상태는 체크포인트에 두고, 대용량 컨텍스트(문서 본문·RAG 페이로드)는 참조만 남긴다. 매 스텝 새 체크포인트를 만드는 구조에서 state에 큰 페이로드를 넣으면 write amplification이 누적된다.
`🔴시효주의` 이 항목의 정량 예시("50MB PDF × 10스텝 = 500MB")는 계측이 아니라 산술 예시이고 출처도 2차 매체다. **수치 없이 설계 처방만 쓴다.**

## Human-in-the-loop

`✅확인` **실명 사례 — Replit 프로덕션 DB 삭제(2025-07).** Jason Lemkin의 공개 피해 보고와 Replit CEO의 공개 사과로 확인된다.
`🔴뒤집힘(2026-08)` ~~"승인 피로·러버스탬프 사례"~~ — **실패 유형이 다르다.** 사람이 승인을 남발한 게 아니라, **코드 프리즈 지시를 무시한 에이전트에게 승인 게이트 자체가 없었고 비가역 작업(DB drop)에 dry-run·미리보기가 없었던** 사례다. 승인 피로 근거로 인용하면 사례를 왜곡한다.

`💭해석` 그래서 이 사례의 교훈은 **"비가역 작업에는 게이트가 있어야 한다"**이지 "승인을 잘 받자"가 아니다. 그리고 **지시(코드 프리즈)로 막으려 한 것이 실패 원인**이다 — 프롬프트는 권한 통제 수단이 아니다.

`✅확인` **승인 피로는 벤더 실측으로 확인됐다 — Claude Code 사용자가 권한 프롬프트의 약 93%를 승인했다.** 대응은 경계를 OS 샌드박스로 옮겨 **프롬프트를 84% 줄인** 것이다. 상세·출처는 `references/security.md`.
`🔴뒤집힘(2026-08)` ~~"승인 피로의 1차 근거를 찾지 못했다"~~ — 보안 축(⑥) 조사에서 확보됐다.
`💭해석` **그래서 이 절의 결론이 바뀐다** — 승인 게이트를 촘촘히 두는 설계는 실패한다. **승인 빈도를 줄이고 남은 승인의 질을 높이는 쪽**이 맞다.
⚠️ 다만 "일괄 승인 사이에 위험 작업이 끼어 통과된다", "런어웨이 하나가 $50~500 태운다" 류 **개별 서술·수치는 여전히 SEO 블로그 근거이므로 인용 금지.** 아래는 설계 원칙으로만 쓴다:
- **위험 최소화 언어를 쓰지 말 것** — 승인 요청이 "괜찮아 보이게" 쓰이면 사람이 판단할 수 없다
- **배치 승인은 위험 작업을 숨긴다** — 비가역 작업은 개별 승인
- **요청 빈도가 높으면 판단이 사라진다** — 자동 승인 범위를 넓혀 빈도를 줄이는 게 오히려 안전할 수 있다
- **dry-run·미리보기**로 "무엇이 바뀌는지"를 보여준다. 이것 없이는 승인이 형식이다

## 장기 실행 운영

`💭해석` (정량 근거 없음 — 설계 서술로만):
- **하드 캡을 셋 다 건다** — 토큰, 툴 호출 횟수, wall-clock. 하나만 걸면 다른 축으로 폭주한다.
- **루프 감지**: 같은 툴 + 같은 인자의 반복을 카운트한다. 축 ⑩의 증상 진단과 연결된다.
- **진행 상황 노출**이 중간 개입의 전제다. 진행이 안 보이면 사람은 끝날 때까지 못 끼어든다.
- 체크포인트가 있으면 **중단이 안전하다** — 중단 가능성 자체가 폭주 대응 수단이다.

## 실패 패턴

- **프레임워크 durability를 믿고 멱등성을 안 넣는다** — 위 #8039. 환경에 따라 갈린다.
- **자동 툴과 승인 툴을 한 노드에 섞는다** — 재개 시 자동 툴이 중복 실행된다.
- **체크포인트에 대용량 페이로드를 넣는다** — 매 스텝 복제되며 누적된다.
- **재개 성공을 검증하지 않는다** — 이 계층은 조용히 실패한다.
- **비가역 작업을 프롬프트로 막으려 한다** — Replit 사례. 지시는 권한 통제가 아니다.
- **TTL 없이 운영 시작** — OSS 체크포인터에 TTL이 없어서 직접 만들어야 한다.

## 미확인 (gap)

- **상태 관리 실패의 실명 프로덕션 postmortem이 없다.** 확보한 것은 합성 SIGKILL 재현(#8039), 선제적 용량 계획(사고 아님), 프레이밍이 다른 Replit 사례뿐. **이 항목은 별도 심층 조사 후보다.**
- **프레임워크 공식 durable execution 설계 문서 미확인** — 이 축의 수집자 하나가 실패해 "설계 의도" 각도가 비어 있다. 위 내용이 결함에 치우친 이유다.
- Temporal 등 워크플로 엔진의 compensation 패턴 중 에이전트에 이식 가능한 부분 미조사.
- 승인 피로의 1차 근거(HCI 연구 등) 미확보.
- 타임아웃 설계(툴별 vs 전체), 좀비 작업 정리의 구체 패턴 미확보.
