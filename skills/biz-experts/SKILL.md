# biz-experts 디스패처

> 용어: **디스패처** = 전화 교환원(작업을 받아 맞는 부서로 연결만, 직접 작업 ❌) · **라우터** = 작업을 분해해 전문가 조합을 정하는 CPO/CMO · **폴백** = 전문가 스킬이 미제작일 때 거장 원칙 + 공식 자료로 진행하는 대체 경로.

비개발 직군 작업(제품·디자인·마케팅·사업·운영·세일즈·피플)을 받으면:

1. **프로젝트 규칙 우선 확인** — 현재 작업이 프로젝트 폴더 안이고 그 프로젝트에 CLAUDE.md·프로젝트 스킬이 있으면 **그쪽이 우선**. 이 스킬군은 프로젝트 규칙이 침묵하는 영역만 채운다.
2. 직무가 정확히 특정되고 README의 단일 항목과 일치하면 실제 `SKILL.md` 존재를 확인한 뒤 직행한다. 이름을 추측하지 않는다. 그 외에는 `biz-chief-strategist/SKILL.md`를 읽는다.
3. 모호한 증상은 직무보다 **증거가 먼저**다. inspect 가능한 화면·문서·데이터·work-history를 보고 관찰 가능한 가설 2~4개와 반증 조건, 바뀌면 안 되는 면을 만든 뒤 라우팅한다. 사용자의 표현은 결론도 잡음도 아니라 조사 시작점이다.
4. 호출 전 route capsule을 만든다: `목표·증상 / 직접 관측 / 가설·반증 / 범위·비범위 / 불변식 / 성공 기준·확인 방법`. 주도 전문가 1명부터 시작하고 게이트에서만 다음 전문가를 순차 추가한다.
5. 카탈로그에 없거나 파일이 없으면 인접 전문가를 꾸며내지 않고 `거장 원칙 + 최신 공식 자료`로 해당 축만 폴백한다. 빠진 전문성·대체 근거·재확인 항목을 한 줄로 알린다.
6. 되돌리기 어려운 결정은 산출물에 `가설·성공지표·확인 시점·뒤집을 조건`을 반드시 남긴다. 공용 ledger는 일반 작업 중 자동 수정하지 않고, 사용자가 기록을 요청했을 때만 프로젝트 로컬 또는 명시 경로에 쓴다.

## 라우팅 ❌/✅ 예시

- ✅ "온보딩 화면 기획해줘" → 이 디스패처 (서비스 기획·UX)
- ✅ "이 화면 패딩이 이상하고 답답해" → ui-refine-loop로 위치·관찰 고정 → 구조 문제면 biz-ui/ux/design-system → 구현은 dev
- ✅ "이 기능 PRD 써줘" → biz-prd-writing 직행 (직무 특정)
- ❌ "온보딩 화면 React로 구현해줘" → dev-experts (코드 작성이 본체)
- ❌ "삼성전자 살까?" → stock-experts (투자 판단)
- ❌ "연말정산 어떻게" → life-experts (개인 세무)
- ✅ "마케팅 카피 + 랜딩 구조 같이" → 라우터 경유 (copywriter + ux-writer/product-marketing 조합)

## 사용자가 라우팅을 거부하면

- **"스킬 찾지 말고 그냥 해줘"** → 디스패처 생략하고 직접 진행. 단 윤리 게이트 영역(과장광고·다크패턴·차별·허위표시)이면 리스크 한 줄은 남긴다.
- **"그 전문가 말고"** → 이유를 1회만 묻고 지정대로 진행.
- **권고 자체 거부** → 거부된 권고와 리스크를 1줄 기록하고 진행(partial — 전체 보류 금지).

## 라우팅 출력

인라인으로 `주도 전문가와 이유 / route capsule / 다음 전문가를 부를 조건 / 성공지표·확인 시점 / 확인 필요`만 남긴다. 내부 카탈로그 설명은 사용자 응답에 노출하지 않는다.

## 주의

- 스킬에 적힌 벤치마크·전환율·플랫폼 수수료·정책은 작성 시점 기준이다 — 낡았으면 **공식 문서·플랫폼 정책이 이긴다**.
- 이 스킬군은 일반론 전문가다. 프로젝트 고유 브랜드 가이드·도메인 규칙과 충돌하면 프로젝트가 이기고, 알려진 안티패턴일 때만 한 줄 지적한다.
- 코드가 필요한 지점(랜딩 구현·이벤트 트래킹 코드·대시보드 구현)은 dev-experts로 넘긴다 — biz는 **무엇을·왜**까지, **어떻게 코딩**은 dev.
- 신규 화면·흐름·정책 설계는 biz가 주도한다. 이미 렌더된 화면의 모호한 시각 불만은 `ui-refine-loop → 필요한 biz 렌즈 → dev 구현 → ui-refine-loop 회귀 확인` 순서다.
