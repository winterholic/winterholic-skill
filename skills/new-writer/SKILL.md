# new-writer — 실제로 쓰는 글을 다듬는다

겨누는 것은 "잘 쓴 글"이 아니라 **읽는 사람이 걸리지 않는 글**이다. 사용자는 개발자이고 한국어로 쓰지만 머릿속 개념은 영어인 경우가 많다. 그래서 실패는 어휘가 어려워서가 아니라 **문장 구조가 영어인 채로 한국어 옷만 입어서** 난다.

## 번들 — 필요할 때만 연다

| 이걸 할 때 | 읽는다 |
|---|---|
| 번역체·AI 티를 걷어낼 때 (거의 항상) | `references/korean-tells.md` |
| 밀도가 과한지 판단이 안 설 때 | `references/voice-profile.md` — 실측 배율 |
| 사내 메신저 글 | `references/casual.md` |
| 커밋·PR·주석·기술문서·이슈 | `references/dev.md` |
| 고객사 메일·상태 보고 | `references/business.md` |
| 말투 프로파일이 낡았을 때 | `scripts/measure-voice.py --self-test` 로 필터 검증 후 `--compare` |

## 세 갈래 — 먼저 어느 쪽인지 정한다

| 갈래 | 어디에 | 지배 규칙 |
|---|---|---|
| **캐주얼** | 사내 메신저, 스레드, 짧은 공지 | 짧게. 완결문 강박을 버린다. 존대 수위를 상대에 맞춘다 |
| **개발자 일상** | 커밋·PR·주석·기술문서·이슈 | 사실과 이유. 용어는 음차 유지. 독자는 미래의 나 |
| **비즈니스** | 고객사 메일·상태 보고·장애 통보 | 결론 먼저. **약속과 추정을 구분한다.** 사과보다 다음 행동 |

**갈래가 애매하면 독자로 가른다.** 같은 팀이면 캐주얼, 코드베이스에 남으면 개발자, 회사 밖으로 나가면 비즈니스다. 섞인 글은 **바깥쪽 독자를 기준**으로 잡고 안쪽 규칙을 보조로 쓴다.

---

## ⛔ SKIP — 이럴 때는 발동하지 않는다

자동으로 걸리는 스킬은 SKIP 이 없으면 사용자를 짜증나게 한다. 아래가 같은 메시지에 있으면 **글을 손대지 않는다.**

- **원문이 영어**이거나 번역 요청
- **법적·계약 문구**, 사양서의 정의 조항 — 정확도가 가독성보다 앞선다. 지적만 한다
- **남의 말 인용**, 로그·에러 메시지 원문
- 사용자가 `"그대로 둬"`·`"손대지 마"`·`"내용만 봐줘"` 라고 함
- **코드 자체**에 대한 리뷰 요청 — `code-review` 로 간다
- 글이 아니라 **구조·정보**를 묻는 질문 ("이 문서에 뭐가 빠졌어?")

발동은 했는데 중간에 위 조건이 드러나면 **거기서 멈추고 남은 부분은 지적만 한다.** 이미 고친 것은 되돌리지 말고 밝힌다.

## 언제나 먼저 — 빠른 점검 7

갈래와 무관하게 이걸 먼저 훑는다. 실측상 위 세 개만 잡아도 대부분 해결된다. 근거와 예시는 `references/korean-tells.md`.

1. **em 대시(—)** 가 있는가 → 문장을 끊는다 (**사용자는 432발화 중 0회.** 나는 100문단당 38.7회)
2. **괄호**가 한 문장에 둘 이상인가 → 하나를 문장으로 뺀다 (**6.7배**)
3. **쉼표**가 한 문장에 셋 이상인가 → 문장을 나눈다 (**3.4배**)
4. 문장의 **주어가 뒤에** 있는가 → 앞으로 당긴다
5. `~에 대해`·`~을 통해`·`되어지`·`가지고 있`·불필요한 `들` 을 찾는다
6. 같은 명사가 인접해서 두 번 나오는가
7. 단위 명사가 대상에 맞는가 (`3벌` → `3건`)

**고치는 방법은 쉬운 단어로 바꾸는 게 아니라 문장을 끊는 것이다.** 어휘를 낮추면 오히려 어색해진다.

⚠️ **반대로 가는 네 가지가 있다.** 말줄임(`...`)·물음표·`ㅋㅋ`·세미콜론은 **사용자가 나보다 16~31배 많이 쓴다.** 교정에서 이걸 지우면 tell 을 없애는 게 아니라 목소리를 지우는 것이다.

## 절차

### 1. 모드를 먼저 가른다 — 누구 목소리로 쓸 것인가

이게 갈래보다 먼저다. **같은 말투 프로파일을 모드마다 반대로 쓴다.**

| 모드 | 언제 | 누구 목소리 | 프로파일 사용법 |
|---|---|---|---|
| **교정** | "고쳐줘"·"다듬어줘" + 사용자 글이 있음 | 사용자 것을 지킨다 | **기준선.** 사람이 안 쓰는 밀도만 걷어낸다 |
| **대필** | "슬랙에 뭐라고 쓰지"·"메일 초안"·"이렇게 답장해줘" — **사용자가 그대로 붙여넣을 글** | **사용자 목소리로 쓴다** | **목표.** 사용자처럼 읽혀야 한다 |
| **작성** | "문서 써줘"·"README 정리" — 내가 저자로 남는 글 | 중립 문체 | 구두점 밀도만 낮춘다 |
| **판단** | "이거 어때?" | — | **고치지 말고** 걸리는 지점만 짚는다 |

**대필과 작성을 헷갈리지 마라.** 가르는 질문은 하나다. *이 글을 보낼 때 발신자 이름이 사용자인가?* 그렇다면 대필이다.

대필에서 맞출 지문 6가지는 `references/voice-profile.md` 의 「대필 모드에서 재현할 것」에 있다. **캐주얼 갈래에만 적용한다** — 비즈니스 메일에서 `ㅋㅋ` 를 쓰면 사고다. 그리고 **존댓말 수위는 받는 사람에 맞춘다.** 사용자가 나한테 반말로 친다고 팀장에게 갈 초안을 반말로 쓰지 않는다.

### 2. 교정의 기본값은 최소 수정

사용자가 쓴 글은 사용자의 것이다. 뜻이 통하면 두고 **걸리는 곳만** 고친다. 문체를 통째로 갈아엎지 않는다. 전면 재작성은 사용자가 그걸 요청했을 때만 한다.

고친 곳마다 **왜 고쳤는지 한 줄**을 붙인다. 이유 없이 바뀐 문장은 사용자가 되돌릴 수 없다.

**`korean-tells.md` 맨 아래 「고치지 말아야 할 때」 표를 먼저 본다.** 사용자의 말투(`~잖아`·`~거든`·`...`·`ㅋㅋ`·오타)는 tell 이 아니라 목소리다.

### 3. 갈래별 규칙을 적용한다

해당 `references/` 파일을 연다. 캐주얼 갈래에서는 **구두점 축만** 보고 문법 축은 거의 적용하지 않는다. 메신저에서 `~에 대해` 하나 고치자고 문장을 다시 쓰는 것은 과잉이다.

## 판정 기준

| 상황 | 선택 | 이유 |
|---|---|---|
| 원문이 어색하지만 뜻은 통함 | 두거나 한 곳만 손댄다 | 최소 수정. 사용자 글은 사용자 것이다 |
| 용어를 순화할지 음차할지 | 독자가 개발자면 음차 | 억지 순화가 오히려 번역체로 읽힌다 |
| 독자가 비개발자 | 용어를 풀지 말고 **용어 자체를 뺀다** | 풀어쓰기는 양쪽 다 불편하다 |
| 문장이 길어 읽기 힘듦 | 쉬운 말로 바꾸지 말고 **끊는다** | 어휘가 아니라 밀도가 문제다 |
| 사과문을 쓸지 | 사과 한 줄 + **다음 행동** | 사과만 있으면 상대가 할 일을 모른다 |
| 추정을 단정으로 쓸지 | 추정이면 추정으로 | 비즈니스 글에서 이게 나중에 책임이 된다 |
| 고칠지 지적만 할지 | **판정이 안 서면 지적만** | 고쳐 놓고 되돌리는 비용이 더 크다 |

## 산출물

- **파일이 아니라 응답**이다. 고친 글을 그대로 준다.
- 순서는 **고친 글 먼저, 이유는 뒤에.** 이유를 앞에 늘어놓지 않는다.
- 검증·검토 과정의 흔적("~를 검토한 결과", "3개 항목을 점검했습니다")은 **남기지 않는다.** 결과만 준다.
- 파일 저장은 사용자가 요청할 때만. 경로는 `CLAUDE.md` § Output Paths 를 따른다. 같은 이름이 있으면 덮어쓰지 않고 묻는다.

### 출력 형식

```markdown
<고친 글 전문>

---
**바뀐 곳**
- 2행: "~에 대해 검토를 진행했습니다" → "~를 검토했습니다" (전치사 직역 + 명사화)
- 5행: 문장을 둘로 끊음 (한 문장에 사실 3개)
```

## 예시

### 비즈니스

**나쁨:**
```
해당 이슈에 대해서 현재 총 3벌의 케이스가 확인되어지고 있으며,
고객사 측에서 요청주신 사항들에 대한 대응 방안을 통해 처리가 진행될 예정입니다.
```

**좋음:**
```
지금까지 확인된 케이스는 3건입니다.
요청하신 사항은 아래 방안으로 처리하겠습니다.
```

단위 명사 오용(벌→건) · 이중 피동 · 전치사 직역 두 곳 · 복수 `들` · 한 문장에 사실 두 개.

### 개발자

**나쁨:** `성능 개선 작업을 통해 응답 속도가 향상되었습니다.`
**좋음:** `쿼리를 고쳐 응답이 1.4초에서 0.2초가 됐습니다.`

숫자가 있으면 숫자를 쓴다. `향상되었습니다` 는 아무 정보가 없다.

### 캐주얼

**나쁨:** `해당 건은 배포가 완료되었습니다.`
**좋음:** `그거 배포 완료했어요`

### 실제 반려 사례 — 가장 값어치 있는 한 쌍

평가는 *"가독성이 쓰레기"*, *"국어적으로 잘못된 문장 같다"* 였다.

```
❌ O(N)을 줄여서 풀리는 문제가 아니라, 계산이 놓인 자리를 옮겨야 하는 문제였습니다
✅ 느린 원인은 코드가 아니라, 요청 하나가 짊어진 데이터 양이었습니다
```

부정 대조 자체는 죄가 아니다. 채택문에도 있다. 문제는 **부정 대조 + 당위(`~해야 하는`) + 명사화(`~하는 문제였습니다`)가 겹칠 때**다. `korean-tells.md` §17.

## 실패·거부 시

| 상황 | 다음 수단 |
|---|---|
| 원문이 영어이거나 번역 요청 | 이 스킬은 발동하지 않는다. 그대로 처리하고 이유를 한 줄 밝힌다 |
| 갈래가 안 갈림 | 독자로 가른다. 그래도 안 되면 한 줄 묻는다 |
| 사용자가 "그냥 다 고쳐줘" | 최소 수정 기본값을 풀고 전면 교정한다. 대신 **원문을 함께 남긴다** |
| 고객사 메일인데 약속의 수위를 모름 | 초안을 주되 **약속 문장은 비워 두고** 사용자가 채우게 한다. 대신 정하지 않는다 |
| 고칠 게 없음 | **"고칠 곳 없음"이 유효한 결과다.** 억지로 찾아 고치지 않는다 |
| 법적·계약 문구 | 손대지 않고 지적만 한다. 정확도가 가독성보다 앞선다 |

## 판단이 안 설 때

- **누가**: 사용자에게 묻는다
- **언제**: ①갈래가 안 갈릴 때(그전에 독자 기준을 먼저 적용한다) ②고객사에 나가는 글에서 약속의 수위가 애매할 때 ③같은 문장을 두 번 고쳤는데 또 지적이 나올 때 — 세 번째 수정을 시도하지 말고 묻는다
- **어떻게**: 한 줄 질문 + 후보 2개. 선택지를 늘어놓고 설명하지 않는다
- **기대값**: 한 줄 답. 무응답이면 **덜 고친 쪽**으로 진행하고 그 사실을 밝힌다

## Gotchas

### 1. 말투를 재려면 붙여넣기를 먼저 걷어내야 한다 (2026-09-03)

`voice-profile.md` 1차 측정에서 em 대시가 사용자 쪽에 100발화당 138회로 나왔다. 사용자가 **내 출력과 파일 내용을 붙여넣은 것**이 사용자 발화로 잡혀서다. 걸러내니 893건 중 432건만 남았다. **나머지 절반은 사람이 친 것이 아니었다.**

그래서 필터를 산문으로 적어 두지 않고 **스크립트로 박았다.** 손으로 다시 짜면 또 틀린다.

```bash
python ~/.claude\skills\new-writer\scripts\measure-voice.py --self-test
```

필터를 고칠 일이 생기면 `--self-test` 를 **먼저** 돌린다. 사람 문장 3종 통과 + 붙여넣기 7종 차단을 확인하고 나서 결과를 믿는다.

### 2. 문장 길이는 아직 비교하지 못했다

사람 33자 / 클로드 31자로 비슷하게 나왔으나, 사람의 글은 줄바꿈이 거의 없고 내 글은 불릿으로 쪼개져 있어 **같은 단위로 잰 것이 아니다.** 이 수치로 "문장 길이는 문제가 아니다"라고 결론 내리면 안 된다. **확인 못함: 구조가 달라 비교 불가.**
