# 한국어 tell — 번역체와 AI 티

읽는 사람이 "AI 가 썼네" 또는 "번역기 돌렸네"라고 느끼는 지점은 어휘가 아니다. **구두점 밀도, 영어 문법이 남은 구조, 그리고 리듬**이다. 그래서 쉬운 단어로 바꾸는 처방은 거의 항상 빗나간다.

숫자가 붙은 항목은 `voice-profile.md` 의 실측값이다. 감으로 재지 않는다.

**순서가 중요하다.** 1~3 은 한 번에 가장 많이 걸리는 자리라 먼저 훑는다. 나머지는 걸릴 때만 본다.

**한 번 나온 표현과 반복되는 버릇을 구분한다.** 사람도 상투구·접속사·대구를 한 번은 쓴다. 같은 문형이 한 글에 여러 번 나오거나 같은 위치에서 되풀이될 때 AI 티로 판정한다. 대시처럼 사용자 기준에서 아예 쓰지 않는 항목을 제외하면, 단어 하나를 발견했다는 이유만으로 문서 전체에서 일괄 삭제하지 않는다.

---

## 축 1 — 구두점 밀도 (실측 1~3위)

### 1. em 대시 (—) — 사람 대비 **26배**

가장 큰 지문이다. 다른 어떤 tell 보다 격차가 크다.

```
나쁨: 원인은 캐시가 아니라 — 요청 하나가 데이터를 너무 많이 들고 온다 — 쿼리 설계였습니다.
좋음: 원인은 캐시가 아니라 쿼리 설계였습니다. 요청 하나가 데이터를 너무 많이 들고 옵니다.
```

**고치는 법**: 대시를 다른 문장부호로 바꾸지 말고 **문장을 끊는다.** 쉼표나 콜론으로 갈아 끼우면 밀도는 그대로다.

**두는 경우**: 없다. 한국어 산문에서 em 대시는 거의 항상 뺄 수 있다.

### 2. 괄호 곁말 — 사람 대비 **5.5배**

본문에서 밀려난 말을 괄호에 넣는 습관.

```
나쁨: 이 값은 캐시(TTL 300초, 배포마다 초기화됨)에서 읽습니다.
좋음: 이 값은 캐시에서 읽습니다. TTL 은 300초이고 배포하면 초기화됩니다.
```

**두는 경우**: ①약어 풀이 `LTV(Loan-To-Value)` ②단위·수치 보조 `3건(전체의 2%)` ③원어 병기 `커버(cover)`. 셋 다 **한 문장에 하나까지**.

### 3. 쉼표로 절 잇기 — 사람 대비 **3.5배**

```
나쁨: 배포는 끝났고, 로그도 정상이지만, 지표가 아직 안 올라와서, 내일 다시 봐야 합니다.
좋음: 배포는 끝났고 로그도 정상입니다. 다만 지표가 아직 안 올라왔습니다. 내일 다시 보겠습니다.
```

**두는 경우**: 나열(`A, B, C`)과 짧은 대조. 한 문장에 쉼표가 셋이면 이미 문장이 둘 이상이다.

### 4. 물결 범위 (`A~B`)

`3~5건` 은 괜찮다. `~정도`, `~쯤` 처럼 어미 자리에 쓰는 물결이 tell 이다.

## 축 2 — 어휘·레지스터

### 5. 기술 용어 과잉 순화 → **음차를 유지한다**

실패는 반대 방향으로 난다. 영어 개념을 억지로 순우리말로 바꾸는 것이 오히려 번역체로 읽힌다.

```
나쁨: 덮개 범위를 늘리고 방아쇠 조건을 좁혔습니다.
좋음: 커버리지를 늘리고 트리거 조건을 좁혔습니다.
```

**두는 경우**: 독자가 비개발자면 용어를 풀지 말고 **용어 자체를 뺀다.** 풀어쓰기는 어정쩡해서 양쪽 다 불편하다.

### 6. 한 문서 안 레지스터 흔들림

같은 것을 어떤 문단에서는 `커버`, 다른 문단에서는 `덮다` 로 쓰는 일. 사람은 이렇게 안 쓴다. **문서 하나에 표기 하나.**

### 7. 영어와 한국어 혼재

사용자가 이미 승인했던 영어 제목까지 폐기하고 전부 한글화한 전례가 있다. *"영어로 제대로 적을 자신 없으면 그냥 한국어로 하셈."*

**두는 경우**: 코드 식별자, 제품명, 업계에서 영어로 굳은 것(`PR`, `CI`, `FDE`).

### 8. 불필요한 부정 대조 남발

`X가 아니라 Y다` 구문. 진짜로 놀라운 대조에만 남긴다. 대조가 자명하면 긍정문으로 쓴다.

### 9. 같은 단어 반복

사용자는 한 문장에 `요청` 이 두 번 나온 것을 어색함으로 즉시 잡아냈다. 문법이 아니라 리듬 문제다. **한 문장·인접 문장에 같은 명사가 두 번 나오면 하나를 지시어로 바꾸거나 문장을 합친다.**

## 축 3 — 번역체 문법

### 10. 단위 명사 오용

옷을 세는 것도 아닌데 `3벌`. 세는 대상에 맞는 의존명사를 쓴다.

| 대상 | 단위 | 예 |
|---|---|---|
| 사례·이슈·문의·오류 | **건** | 오류 3건 |
| 종류·유형·방식 | **종 / 가지** | 방식 2가지 |
| 커밋·PR·이슈 티켓 | **개 / 건** | 커밋 4개, PR 2건 |
| 서버·인스턴스·컨테이너 | **대 / 개** | 인스턴스 3대 |
| 문서·보고서 | **부 / 건** | 보고서 1부 |
| 배포·릴리스 | **회 / 차** | 배포 2회 |
| 옷 | 벌 | (여기 말고는 쓰지 않는다) |

**막히면 `개` 를 쓴다.** 틀린 단위보다 무난한 `개` 가 낫다.

### 11. 명사화 과잉

```
검토를 진행하다   → 검토하다
배포를 수행하다   → 배포하다
확인이 필요합니다 → 확인하겠습니다 / 확인해 주세요
개선 작업을 하다  → 개선하다
장애가 발생하다   → 장애가 났다
```

**두는 경우**: 그 명사가 고유명사처럼 굳은 절차일 때(`코드 리뷰를 진행합니다`).

### 12. 이중 피동

```
확인되어지고 있습니다 → 확인하고 있습니다 / 확인됩니다
보여집니다            → 보입니다
쓰여집니다            → 쓰입니다
```

피동은 한 번만. 그리고 **행위자를 아는데 피동으로 숨기지 않는다.** `배포되었습니다` 보다 `배포했습니다` 가 낫다. 단 고객사 메일에서 책임 주체를 흐릴 이유가 있으면 그건 판단의 영역이다.

### 13. 영어 전치사 직역

```
~에 대해 검토했습니다   → ~를 검토했습니다
~을 통해 처리합니다     → ~로 처리합니다
~에 있어서 중요합니다   → ~에서 중요합니다
~로 인해 실패했습니다   → ~때문에 실패했습니다
~와 관련하여            → ~는 (대개 통째로 뺄 수 있다)
```

**대부분 조사 하나로 줄어든다.** 줄여 보고 뜻이 안 상하면 줄인다.

### 14. `have` 직역

```
3개의 인자를 가집니다   → 인자가 3개입니다
권한을 가지고 있습니다  → 권한이 있습니다
```

### 15. 복수 `들` 남용

한국어는 수를 문맥으로 처리한다.

```
요청주신 사항들에 대한  → 요청하신 사항은
파일들을 확인했습니다   → 파일을 확인했습니다
```

**두는 경우**: 복수임이 뜻에 결정적이고 문맥으로 안 드러날 때.

### 16. 무생물 주어의 능동

`이 문서는 X를 설명한다` 는 기술 문서에서 굳었으니 둔다. 그러나 `보고서가 말하기를`, `데이터가 보여주듯이` 는 번역체다.

## 축 4 — 문장 설계 (반려 사례에서 나온 축)

### 17. 주어 → 서술로 끝낸다

실제 반려 사례다. 평가는 *"가독성이 쓰레기"*, *"국어적으로 잘못된 문장 같다"* 였다.

```
❌ O(N)을 줄여서 풀리는 문제가 아니라, 계산이 놓인 자리를 옮겨야 하는 문제였습니다
✅ 느린 원인은 코드가 아니라, 요청 하나가 짊어진 데이터 양이었습니다
```

부정 대조 자체가 죄는 아니다. 채택문에도 남아 있다. 문제는 **부정 대조 + 당위(`~해야 하는`) + 명사화(`~하는 문제였습니다`)가 겹칠 때** 한 번에 안 읽힌다는 것이다.

**점검**: 문장을 소리 내 읽어 **주어가 어디 있는지** 본다. 뒤쪽에 있으면 앞으로 당긴다.

### 18. 당위 구문 남발

`~해야 한다`, `~할 필요가 있다` 를 사실 서술로 바꿀 수 있는지 본다. 지침 문서가 아니면 대개 바꿀 수 있다.

### 19. 추상 명사 제목

제목은 **메소드명처럼** 짓는다. 읽고 내용이 추측되면 좋은 제목이다.

```
❌ Accuracy / Growth / Emotion Summary / 데이터 처리
✅ 안 읽어도 되는 필드 걷어내기 / 배포한 뒤 다시 재기
```

### 20. 오글거리는 문구·스핀

실패를 포장하지 않는다. 과장 형용사(`혁신적인`, `강력한`)를 뺀다. 있는 그대로 쓴다.

## 축 5 — 결론을 꾸미는 문형

본문은 멀쩡한데 결론과 맺음말에서 갑자기 AI 티가 나는 경우가 많다. 쓸 정보가 떨어지자 형식으로 빈칸을 채우기 때문이다.

### 21. 결산 접속어가 반복된다

`결론적으로`·`따라서`·`이를 통해`·`요약하면`·`정리하자면`이 세 번 이상 나오면 한두 개만 남긴다. 접속어 없이 시작해도 결론이라는 사실은 문맥에서 드러난다.

### 22. 문장을 일부러 갈라 강조한다

`필요한 것은 X다`·`핵심은 X라는 점이다`·`문제는 X에 있다`는 주어와 서술어를 바로 잇는다.

```
나쁨: 중요한 것은 장애를 빨리 알리는 것입니다.
좋음: 장애는 빨리 알려야 합니다.
```

`~하는 이유다`처럼 앞의 결과를 뒤에서 결산하는 도치도 순서대로 읽히는 평서문으로 돌린다. 한 글에서 같은 형태가 두 번을 넘으면 버릇으로 본다.

### 23. 범위를 부풀려 결말을 만든다

`단순한 X를 넘어 Y로`·`X가 아니라 새로운 Y다`·`이제 ~할 때다`·`더 이상 ~이 아니다`는 실제 변화가 있을 때만 쓴다. 변화가 없다면 무엇을 할지 바로 적는다.

### 24. 내용 없는 문패와 맺음말

`과제도 남아 있다`·`한계도 분명하다`처럼 다음 내용을 예고만 하는 문장은 실제 과제부터 쓴다. 아래처럼 행동·시점·사실이 없는 문장은 고치지 않고 지운다.

- 최선을 다하겠습니다
- 빠른 시일 내에 처리하겠습니다
- 적극적으로 검토하겠습니다
- 많은 관심 부탁드립니다
- 내부적으로 여러 방안을 검토했습니다
- 문의 사항이 있으면 언제든 말씀해 주세요

맺음말에 적을 내용이 없으면 인사만 남긴다. 허전하다는 이유로 문장을 만들지 않는다.

### 25. 열거를 예고하고 시작한다

`크게 세 가지로 나눌 수 있다`·`다음과 같은 방법이 있다`를 지우고 첫 항목부터 쓴다. 개수가 의사결정에 중요할 때만 숫자를 남긴다.

## 축 6 — 모델이 편애하는 낱말과 수사

문법은 맞지만 모델이 비유로 자주 쓰는 낱말이 있다. 평범한 말로 바꿔도 뜻이 그대로면 비유가 필요 없던 문장이다.

### 26. 평범한 동작을 비유로 말한다

| 모델이 자주 고르는 말 | 먼저 시험할 말 |
|---|---|
| 자리·대목 | 경우·때·위치 |
| 가른다·갈린다 | 정한다·다르다·나뉜다 |
| 한 벌·덩어리 | 하나·묶음·구성 단위 |
| 그린다 | 만든다·보여 준다 |
| 기능이 죽는다 | 실패한다·멈춘다 |
| 규칙이 이긴다 | 규칙을 우선한다·따른다 |
| 심는다·태운다·굽는다 | 넣는다·싣는다·만든다 |
| 값어치 | 가치·쓸모 |
| 주범·용의자 | 원인·후보 |
| 잰다·깎인다 | 판단한다·나빠진다 |
| 지문 | 특징·자국 |
| 몰려 있다 | 자주 나온다·여러 번 나온다 |

코드·업계에서 굳은 표현은 그대로 둔다. 예를 들어 프로세스가 실제로 종료된 상황의 `죽었다`와 기능 설명에서 멋으로 쓴 `죽는다`는 다르다.

### 27. 유일성을 표어로 못 박는다

`핵심은 하나다`·`방법은 하나뿐이다`·`정본은 하나다`가 반복되면 그냥 결론을 쓴다. `정확히 이것이다`·`바로 그 실패다`도 강조어를 빼고 사실 관계만 남긴다.

### 28. 격언처럼 문단을 맺는다

앞 내용을 짧은 단정문으로 다시 요약해 명언처럼 떼어 놓지 않는다. 앞 문장에 합치거나 실제 행동으로 바꾼다.

### 29. 자기가 만든 문장을 인용한다

출처 없는 요약을 큰따옴표와 굵은 글씨로 감싸 권위를 만들지 않는다. 따옴표는 실제 발화·문헌·UI 문구처럼 원문이 있을 때만 쓴다.

## 축 7 — 리듬·서식·양식의 자국

한 문장씩 보면 멀쩡해도 문단과 문서 여러 개를 나란히 놓으면 AI가 채운 틀이 드러난다.

### 30. 문두 접속사와 메타 진입이 몰린다

`또한`·`따라서`·`즉`·`나아가`·`아울러`, 그리고 `이는`·`이 점에서`가 한 문단에 셋 이상이면 절반쯤 덜어낸다. 전부 지우지 말고 바로 본론으로 시작할 수 있는 문장만 줄인다.

### 31. 종결어미와 문장 길이가 일정하다

같은 종결어미가 네 문장 이어지면 일부를 합치거나 형태를 바꾼다. 문장 길이도 모두 비슷하면 짧은 문장 하나와 설명이 필요한 긴 문장을 섞는다. 리듬을 만든다고 새 내용을 보태지는 않는다.

### 32. 이름표를 붙여 빈칸을 채운다

`비유:`·`교훈:`·`왜:`·`핵심 신조:`처럼 문장의 역할을 먼저 선언하지 않는다. 이름표를 떼고도 내용이 남으면 본문에 합친다. 떼었더니 아무것도 남지 않으면 그 문장은 필요 없던 것이다.

### 33. 부호로 완결문을 압축한다

가운뎃점·화살표·원문자로 주어와 서술어가 있는 문장 여러 개를 한 줄에 잇지 않는다. 낱말 나열이면 가운뎃점을 쓸 수 있지만, 주장 여러 개면 문장이나 목록으로 나눈다.

### 34. 강조가 문서 전체에 깔린다

한 문단에 굵은 글씨는 한 곳 정도면 충분하다. 문장 전체를 굵게 하거나 한 문장 안에서 여러 구절을 따로 강조하면 어디가 중요한지 사라진다. 진짜 인용이 아닌 따옴표 강조도 같은 기준으로 줄인다.

### 35. 문서가 자기 존재를 설명한다

`이 문서가 필요한 이유`·`이 스킬이 존재하는 이유`처럼 제목이 이미 말한 것을 다시 소개하지 않는다. 자기 항목 번호를 근거처럼 인용하거나 질문형 소제목을 만든 뒤 바로 자문자답하는 구조도 실제 주제로 바꾼다.

### 36. 주제가 달라도 같은 틀이 반복된다

문서 세 개의 같은 위치에 경계표·비유·교훈·면책·점검표가 같은 순서로 나오면 내용보다 양식이 먼저인 글이다. 그 문서에만 필요한 말이 무엇인지 남기고, 공통 형식은 진짜 서식이 필요할 때만 별도 템플릿으로 뺀다.

## 교정 뒤 역검사 — tell을 다른 tell로 옮기지 않는다

다듬은 부분만 다시 훑는다.

| 없앤 것 | 새로 만들기 쉬운 것 | 확인 |
|---|---|---|
| 대시 | 쉼표·콜론으로 갈아 끼운 긴 문장 | 문장을 실제로 끊었는가 |
| 결산 접속어 | `~하는 이유다` 도치 | 순서대로 읽히는가 |
| 부정 대조 | `단순한 X를 넘어 Y` | 평서문으로 끝냈는가 |
| 완곡 표현 | 근거 없는 단정 | 추정 강도를 지켰는가 |
| 상투구 | 새 비유·격언 | 원문에 없던 장식을 넣지 않았는가 |

원문과 결과를 맞대어 수치·고유명사·직접 인용이 그대로인지, 새 주장이나 새 비유가 들어가지 않았는지, 격식이 달라지지 않았는지 확인한다.

## ⛔ 고치지 말아야 할 때 — 이 절이 이 스킬을 과잉 교정 도구로 만들지 않는다

tell 이 보인다고 전부 고치면 사용자 글이 내 글이 된다. 아래는 **그대로 둔다.**

| 상황 | 판단 |
|---|---|
| **사용자의 원래 말투** | 둔다. `~잖아`·`~거든`·`...`·`ㅋㅋ`·오타는 tell 이 아니라 목소리다 |
| **캐주얼 갈래** | 완결문 강박을 강요하지 않는다. `그거 배포 완료` 가 정답일 때가 있다 |
| **업계 관용어로 굳은 것** | `PR 을 올리다`, `이슈를 파다`, `롤백하다` 는 그대로 |
| **뜻은 통하는데 어색한 정도** | 최소 수정 원칙. 한 곳만 손대거나 그냥 둔다 |
| **원문이 인용문일 때** | 남의 말은 고치지 않는다 |
| **법적·계약 문구** | 정확도가 가독성보다 앞선다. 손대지 말고 지적만 한다 |
| **고치면 뜻이 좁아질 때** | 둔다. 모호함이 의도일 수 있다 |

**판정이 안 서면 고치지 않고 지적만 한다.** 고쳐 놓고 되돌리는 비용이 지적하고 넘어가는 비용보다 크다.

## 빠른 점검 순서

글을 받으면 이 순서로 훑는다. 위에서 세 개를 먼저 잡고, 긴 글이나 `AI 티 나` 요청이면 8~12까지 모두 본다.

1. **em 대시**가 있는가 → 문장을 끊는다
2. **괄호**가 한 문장에 둘 이상인가 → 하나를 문장으로 뺀다
3. **쉼표**가 한 문장에 셋 이상인가 → 문장을 나눈다
4. 문장의 **주어가 뒤에** 있는가 → 앞으로
5. `~에 대해`·`~을 통해`·`되어지`·`가지고 있`·`들` 을 찾는다
6. 같은 명사가 인접해서 두 번 나오는가
7. 단위 명사가 대상에 맞는가
8. 결산 접속어·분열문·내용 없는 맺음말이 반복되는가
9. 비유 낱말·유일성 표어·자기 인용이 있는가
10. 같은 종결어미와 문장 길이가 이어지는가
11. 이름표·기호 압축·과한 굵게·반복 양식이 있는가
12. 고친 자리에서 다른 tell이 생기지 않았는가
