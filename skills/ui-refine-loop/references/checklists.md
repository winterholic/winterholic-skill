# 축별 체크리스트 · 요소 번호 규약 · 비평가 프롬프트

이 문서가 스킬의 실질이다. 나머지는 이걸 태우는 배관이다.

## 작성 원칙

**"판단해라"가 아니라 "이 패턴이 있는지 봐라"로 쓴다.**
- ❌ *"시각 위계가 적절한가"* → 취향 담론. 논문이 실패한 프롬프트가 이 종류다.
- ✅ *"제목과 본문의 크기 차이가 눈으로 구분되지 않는다"* → 보면 알고, 틀렸으면 틀렸다고 말할 수 있다.

**디자인마다 다른 것은 "무엇이 옳은 값인가"이고, "무엇이 어긋난 상태인가"는 안 달라진다.**
카드 3개 패딩이 12/16/12 면 어떤 디자인 언어를 쓰든 어긋난 것이다.

**측정 가능 여부 표기** — 중재자는 측정치로만 판정하므로 이 표기가 곧 자동수정 가능 여부다.

- **◆** 1b 가 무조건 측정 가능 → 자동수정 후보
- **◆?** **조건부** — 특정 DOM 구조가 있을 때만 측정 가능(각 항목에 조건 명시). 조건 불충족 시 ○ 로 강등
- **○** 측정 불가 → 중재자는 예외 목록에만 대조 → 대부분 보류함행

⚠️ **`◆` 는 "측정 가능"이지 "구현됨"이 아니다.** 실제로 `scripts/collect.js` 가 재는 것은
아래 24종뿐이고, 그 외 `◆` 항목은 **현재 비평가 몫(○ 취급)** 이다.
표기와 구현이 어긋나면 중재자가 있지도 않은 측정치를 찾다가 전부 보류함으로 보낸다.

**구현된 판정 24종** (테스트베드에서 심어둔 결함 17/17 검출 · 정상 화면 오탐 0 실측):

| 종류 | 대응 항목 |
|---|---|
| `overflow` `overlap` `alignment` `hierarchy` `scale` `cls` | 3-9 · (겹침) · 3-1/3-7/3-15 · 1-3/1-17 · (스케일 이탈) · 5-9 |
| `repeat-padding` `double-indent` `gap-asym` `pad-asym` `control-ratio` | 1-1 · 1-14 · 1-12 · 1-6 · 1-4 |
| `weight-variety` `affordance` `focus-missing` | 2-4 · 2-10 · 2-12 |
| `cell-padding` `row-height` `table-header` `decimals` `num-align` `tabular-nums` `empty-cell` | 6-7 · 6-10 · 6-6 · 3-12 · 3-5 · 3-13 · 6-9 |
| `input-width` `placeholder-label` `required-mark` | 6-1 · 6-5 · 6-2 |

판정 종류를 늘리면 **`collect.js` · `capture.mjs` 집계 · `score.mjs` 의 `ORDER` 세 곳을 함께**
고친다. 한 곳만 고치면 새 지표가 점수에 안 들어가 조용히 무시된다.

⚠️ **체크리스트에 절대 임계 숫자를 쓰지 않는다.** "2px 이하", "3개 이상" 같은 값은 근거가 없으면
지어낸 것이다. 세는 것(개수·종류 수)만 숫자로 두고, **재는 것은 "눈으로 구분되지 않는다"로 쓴다.**
실측은 1b 가 한다.

## ★ 요소 번호 오버레이 규약 (이게 없으면 스킬이 아무것도 못 고친다)

**문제**: 3층 중재자는 "1b 가 같은 지점을 측정했는가"로 판정하는데, 비평가는 자연어로 위치를 쓰고
1b 는 DOM 셀렉터를 낸다. 둘을 잇는 수단이 없으면 **모든 finding 이 보류함으로 떨어지고 4층에 입력이
없다.** 반대로 비평가에게 셀렉터를 주면 절대 규칙 1(저작 맥락 비노출)에 걸린다.

**해소**: 번호는 코드도 저작 의도도 아니다. 규칙 1 을 어기지 않으면서 역참조 핸들이 된다.

1. 캡처 시 하네스가 **후보 요소**에 순번을 매기고 좌상단에 작은 배지를 굽는다.
   후보 = 뷰포트 안에 보이고, 크기 ≥ 8×8, 자체 텍스트나 배경·테두리를 가진 요소.
2. **두 벌을 찍는다** — 배지가 있는 이미지(비평가용) / 배지가 없는 원본(픽셀 diff·회귀 판정용).
   배지를 섞으면 자기 잡음 캘리브레이션이 오염된다.
3. 하네스는 `번호 → 셀렉터 + rect + computed style` 매핑 테이블을 보관한다.
   ⚠️ **번호는 DOM 순회 순서로 매긴다 — 측정 대상 여부·뷰포트와 무관하게.** 측정 대상만 세면
   폭마다 번호가 밀려 **같은 `#28` 이 1440 에서는 종목코드 셀, 360 에서는 등락률 셀**이 된다
   (실측 224 vs 77개). 비평가는 여러 폭을 함께 보고 번호를 한 줄에 섞어 쓰므로, 그대로 두면
   3층이 **조용히 엉뚱한 요소에 매칭**한다. 한계: 반응형으로 **DOM 자체가 바뀌면** 여전히 어긋난다.
4. 비평가는 `target` 에 **번호**를 쓴다(`#12`, `#12,#14`). 자연어는 보조 설명일 뿐이다.
5. 3층은 번호로 1b 측정치를 즉시 조회한다. 4층은 번호 → 셀렉터 → CDP nodeId →
   `CSS.getMatchedStylesForNode` 로 토큰/로컬을 판정한다.

⚠️ **셀렉터에 `>>` 나 `>>iframe` 이 들어 있으면 그 아래는 다른 문서다** — 각각 shadow root 안,
같은 출처 iframe 문서 안이라는 뜻이다. 그 셀렉터는 `document.querySelector` 로 못 찾으므로,
4층은 **컴포넌트 정의 파일 / 임베드된 별도 HTML** 을 고쳐야 한다. 부모 페이지를 뒤지면 없다.
(`>>iframe` 아래 요소의 좌표는 부모 좌표계로 이미 환산돼 있어 배지 위치는 화면과 일치한다.)

⚠️ research §8 이 "과투자"라며 버린 것은 **좌표 정밀도(IoU)** 다. 여기서 필요한 것은 정밀도가 아니라
**역참조 가능한 핸들**이고, 그건 훨씬 싸다. 버린 결정과 모순되지 않는다.

## 축 4. 색·대비

강조·링크·비활성은 축 2 로 갔다. 이 축은 **색 자체와 대비**만 본다.

| | 관찰할 패턴 | 측정 |
|---|---|---|
| 4-1 | 같은 의미를 다른 색으로, 다른 의미를 같은 색으로 쓴다 (`semanticColors` 선언분 제외) | ○ |
| 4-3 | 회색 단계 중 **서로 구분되지 않는 쌍이 있다** (개수가 아니라 구분 가능성) | ◆? (ΔE 임계를 `.ui-refine.json` 에 선언했을 때) |
| 4-4 | 상태(성공·경고·오류)가 **색으로만** 구분된다 | ◆? (`role="alert"`·`aria-live` 가 있을 때) |
| 4-5 | **다크모드에서 대비가 뒤집히거나 색이 그대로다** | ◆ |
| 4-6 | 배경 이미지·그라디언트 위 텍스트가 묻힌다 | ○ (배경 판정 불가 → `incomplete`) |
| 4-9 | 포커스 링이 배경과 대비가 낮거나 인접 요소·컨테이너 경계에 잘린다 | ◆ |
| 4-10 | 다크모드에서 표면색은 바뀌었는데 **테두리·구분선만 라이트 값이 남아 있다** | ◆ |

⚠️ 4-6 은 **자동 대비 검사 오탐 1위 경로**다. 배경 판정이 불가하면 색을 덮어쓰지 않고
`incomplete` 로 돌린다.

⚠️ 4-1 은 금융에서 특히 위험하다. 등락 색상은 의도된 관례이므로 `semanticColors` 에 선언돼
있으면 중재자가 폐기한다.

## 축 5. 정보 밀도

사용자가 말한 **"UX가 투머치"** 축이다. 취향으로 흐르기 가장 쉬우므로 항목을 특히 좁게 썼다.

| | 관찰할 패턴 | 측정 |
|---|---|---|
| 5-2 | 같은 정보가 한 화면에 두 번 이상 나온다 (**표 셀·반복 리스트 제외**) | ◆ |

| 5-4 | 목록에서 항목당 표시 필드가 많아 **항목 간 비교가 안 된다** | ○ |
| 5-5 | 스크롤 없이 보이는 영역에 액션이 하나도 없다 (조회 전용 화면은 예외) | ◆? (라우트 예외 대조 후) |
| 5-6 | 긴 문단 위에 굵기·크기가 다른 요약 한 줄이 없다 (공시·약관 화면 제외) | ◆? (라우트 예외 대조 후) |

| 5-8 | **빈 상태인데 왜 비었는지·뭘 해야 하는지 안내가 없다** | ◆? (state 라벨이 `empty` 인 이미지에 한정) |

```
각 이미지 앞에 라벨이 붙어 있다.
  [S1] viewport=1440 state=default
  [S2] viewport=360  state=default
같은 화면의 다른 폭·다른 상태다.
**모든 지적에는 그것을 실제로 본 이미지 ID를 적는다.**

이미지에는 요소마다 작은 번호 배지가 찍혀 있다. 지적할 때 그 번호로 대상을 가리킨다.
번호는 내가 나중에 해당 요소를 찾기 위한 것이다.

## 먼저 — 판정할 수 없는 이미지 걸러내기
아래에 해당하는 이미지는 판정 대상에서 빼고 맨 아래 UNUSABLE 줄에 ID와 사유만 적는다.
- 전체가 비었거나 단색이다
- 콘텐츠 자리가 회색 블록(스켈레톤)이다 / 스피너만 있다
- 폰트가 로드되지 않은 채 렌더된 티가 난다
- 잘렸거나 깨져서 화면 구조를 알 수 없다
모든 이미지가 해당하면 NO_FINDINGS 만 출력하고 끝낸다.

## 절대 지적하지 않을 것 — 캡처 환경의 산물
앱 UI 가 아니라 스크린샷을 찍는 과정에서 생긴 것이다. 결함이 아니다.
- 요소 번호 배지 그 자체
- 스크롤바 · 포커스 링 · 텍스트 캐럿
- 개발 오버레이(HMR 배지, devtools, 에러 오버레이, 프레임워크 인디케이터)
- 사라지는 중인 토스트 · 모달 잔상 · 애니메이션 중간 프레임
- 이미지 가장자리의 1~2px 잘림

## 네가 볼 축: {축 이름}
아래 패턴이 이 화면에 있는지 하나씩 확인한다.

{해당 축의 체크리스트 항목 전문}

### 세 가지 규칙
- **개수 하한은 없다. 0건은 정상적인 결과다.** 걸리는 게 없으면 NO_FINDINGS 를 출력하고
  끝낸다. 그게 맞는 답이면 그게 이 작업의 성공이다. 없는 문제를 지어내면 이 작업 전체가
  무의미해진다.
- **이 축만 본다.** 다른 축(색·정렬·밀도 등)의 문제가 눈에 띄어도 쓰지 마라.
  그 축은 다른 사람이 따로 본다. 여기 쓰면 같은 문제가 두 번 세어진다.
- 체크리스트에 없더라도 **이 축에서** 어긋난 것이 보이면 쓸 수 있다. 단 item 에 offlist 를
  적고, **화면 안의 두 대상을 짝지어** 무엇과 무엇이 어긋났는지 써라.
  "전반적으로", "느낌이", "좀 더 ~했으면" 으로 시작하는 것은 지적이 아니다.

### 숫자를 다루는 법
- **셀 수 있는 것**(요소 개수·색 종류·굵기 종류) → 세어서 쓴다.
- **재야 하는 것**(px·pt·비율) → **재지 마라.** "눈으로 구분되지 않는다" /
  "명확히 다르다" 로만 판정한다. 추정 수치를 쓰면 그 지적은 통째로 버려진다.
  실측은 다른 도구가 한다.

## 출력 형식
아래 블록만 반복 출력한다. 서론·총평·요약·우선순위 목록을 붙이지 마라.

---FINDING---
seen_in: [S1, S2]
target: #12, #14
target_desc: 요약 카드 3개 중 가운데
item: 1-1
observed: #12 와 #14 는 숫자 위아래 여백이 같고, #13 만 눈에 띄게 좁다.
why_wrong: 같은 종류의 반복 요소인데 내부 패딩이 서로 다르다.
severity: 2
severity_why: 셋이 나란히 붙어 있어 어긋남이 바로 보인다. 읽기나 조작은 막지 않으므로 3은 아니다.
intent_flag: none
---END---

지적이 하나도 없으면 블록 없이 이 한 줄만 출력한다.
NO_FINDINGS

판정 불가 이미지가 있었으면 마지막 줄에 적는다.
UNUSABLE: S2 (스켈레톤 로딩 상태)

### 각 필드
**seen_in** — 그 문제를 실제로 본 이미지 ID 전부. 같은 대상의 같은 문제가 여러 폭·상태에서
  보이면 **블록은 하나만** 쓰고 여기에 나열한다. 특정 상태에서만 보이면 그 ID 하나만 —
  어느 상태에서 보였는지가 그 지적의 핵심이다.

**target** — 이미지에 찍힌 **요소 번호**. 여러 개면 쉼표로. 번호를 못 찾겠으면
  `unnumbered` 라고 쓰고 target_desc 를 최대한 자세히 쓴다.

**target_desc** — 사람이 읽을 위치 설명 한 줄. 화면에 적힌 텍스트가 있으면 그대로 인용한다.

**observed** — 실제로 본 것만. **비교 대상을 함께 쓴다**("A는 넓고 B는 좁다").
  원인·해석·수정 방향을 넣지 마라. 추정 수치를 쓰지 마라.

**why_wrong** — 어느 패턴에 걸리는지 한 문장. **번호만 적는 것은 근거가 아니다.**
  이 화면에서 무엇과 무엇이 어긋났는지 말해야 한다.

**severity (0~4)** — 0 문제 아님 / 1 화장품 / 2 사소 / 3 중대 / 4 재앙. 두 축을 곱한다.
  - **범위**: 한 군데만 → 낮음 / 반복 요소 전체·모든 폭 → 높음
  - **방해**: 읽기·조작을 안 막음 → 1~2 / 읽기 어렵게 함 → 3 / 못 읽거나 못 누름 → 4
  사용자가 이 화면을 얼마나 자주 보는지 너는 알 수 없다. 추측해서 올리지 마라.
  **0 은 실제로 쓰라고 있는 값이다.** 써놓고 다시 보니 문제가 아닌 것 같으면 0 을 매겨라.
  0 은 감점이 아니고, 억지로 1 로 올리는 것이 훨씬 나쁘다.

**severity_why** — 왜 3이 아니고 2인지. **여기에도 개선 제안을 쓰지 마라.**
  "~가 있으면 괜찮아진다" 는 제안이다. 지금 상태가 어느 정도로 어긋났는지만 쓴다.

**intent_flag** — `none` 또는 `possible-intent`
  체크리스트에 걸리지만 의도된 설계일 수 있다고 보이면(도메인 관례, 의도적 강조 등)
  **빼지 말고 그대로 올린 뒤** `possible-intent` 를 붙이고 다음 줄에 `intent_why:` 로
  근거를 화면 안에서 한 문장 댄다.
  **판정은 다른 사람이 한다. 스스로 검열해서 빼는 것이 지어내는 것보다 나쁘다.**

## 하지 말 것
- 코드·CSS·클래스명·추정 수치를 쓰지 마라. 너는 화면만 봤다.
- **개선 제안 금지.** "~하면 좋겠다 / 넓히면 / 키우면 / 통일하면 / 맞추면" 은 어느 필드에도
  쓰지 마라. **무엇이 어긋나 있는지만** 쓴다.
- 잘 된 점·총평·요약·우선순위 목록을 쓰지 마라.
- 같은 대상의 같은 문제를 스크린샷마다 반복하지 마라. seen_in 에 나열하면 끝난다.
```

### 문장별 근거

| 문장 | 근거 |
|---|---|
| "처음 보는 사람이다 / 누가 만들었는지 모른다" | self-bias 가 6개 모델 전부에 있고 자기정제가 증폭시킨다. **"처음 켠 사용자"가 아니라 "처음 보는 사람"** — 전자는 과업 서사·취향 담론을 부른다 |
| **"0건은 정상적인 결과다" + `NO_FINDINGS` 형태 명시** | 시뮬레이션에서 깨끗한 화면에 2건을 지어냈고, **최대 원인이 "빈 출력 형태 미정의"** 였다. 형식 공백을 만나면 형식을 채우는 쪽으로 간다 |
| "0 은 실제로 쓰라고 있는 값이다" | 근거를 먼저 쓰게 하고 severity 를 나중에 매기면 **0 이 원리적으로 안 나온다**(문제라고 논증한 직후 "문제 아님"은 자기모순) |
| "이 축만 본다" | 지문에 `axis` 가 들어가므로 **축 간 중복은 dedup 을 통과한다** |
| 셀 수 있는 것 / 재야 하는 것 분리 | "추측한 값 금지" 와 체크리스트 수치 항목의 정면 모순을 해소 |
| `seen_in` + 이미지 ID 라벨 | 봉투의 `viewport`·`state` 를 채울 유일한 경로. 상태 한정 항목(1-9·4-5)이 무력화되는 것을 막는다 |
| `target` = 요소 번호 | **3층 매칭 병목의 유일한 해소책.** 자연어만으로는 1b 측정치와 대조 불가 |
| `intent_flag`(제거가 아니라 플래그) | UICrit 실패 모드 — LLM 검증 단계가 유효 지적을 되레 죽인다. 자기검열을 막고 신호만 전달 |
| 판정 불가 이미지 사전 필터 | 무효 렌더 게이트를 비평가도 알아야 한다. 스켈레톤을 결함으로 보고하는 것을 막는다 |
| `severity_why` 옆 제안 재금지 | 시뮬레이션에서 **제안이 새어나온 유일한 자리**가 여기였다 |
| "번호만 적는 것은 근거가 아니다" | 근거 강제가 체크리스트 번호 스탬프로 퇴화하는 것을 막는다 |

⚠️ **[확인 필요]** 이 프롬프트는 이전 판의 약 2.5배 길이다. research §1.7 이 확인한 레버는
근거·severity·severity 이유·위치 넷뿐이고 나머지는 오탐 억제·파싱 목적이라 **커버리지를
떨어뜨릴 가능성**이 있다. 특히 "이 축만 본다"와 캡처 아티팩트 목록이 유효 지적을 일부 억제할 수
있다. 도입 후 한 화면을 이전 판과 A/B 로 돌려 유효 지적 수 변화를 확인한다.

## finding 봉투

지적 **내용**은 자유 텍스트다. 디자인마다 다르므로 분류 체계를 만들지 않는다.

| 필드 | 값 |
|---|---|
| `screen` | 라우트 (`/orders`) |
| `seen_in` | 이미지 ID 배열 — viewport·state 는 이미지 라벨에서 역산 |
| `axis` | `spacing` · `hierarchy` · `alignment` · `color` · `density` · `form-table` · `overlay-responsive` · `cross-screen` |
| `target` | 요소 번호 배열 (또는 `unnumbered`) |
| `item` | 체크리스트 항목 번호 또는 `offlist` |
| `severity` | 0~4 |
| `intent_flag` | `none` · `possible-intent` |

**지문 = `screen + target + item`**
⚠️ `axis` 를 지문에서 뺐다. 축이 다르면 지문이 달라져 **축 간 중복이 dedup 을 통과**하기 때문이다.
`item` 을 넣은 이유는 같은 요소에 대한 서로 다른 종류의 지적을 구분하기 위해서다.

### severity 0 처리

비평가가 스스로 0 을 매기면 폐기하고 로그만 남긴다.
⚠️ **[확인 필요]** 이 규칙은 "LLM 이 자기 오탐에 스스로 0 을 매긴다"를 전제하는데 그 근거는 없다
(research 의 severity 0 는 사람 master set 이 매긴 값이다). 위 프롬프트에 "0 은 쓰라고 있는 값"을
명시해 유도했으나, **실제로 0 이 나오는지 첫 실행에서 확인하고 안 나오면 이 경로를 폐기한다.**
