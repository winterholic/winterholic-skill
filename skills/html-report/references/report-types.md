# Report Types — 11개 타입별 추천 구조

각 타입은 **고정 골격(필수 섹션)** + **선택 섹션**으로 구성된다. 보고서를 시작할 때는 타입을 먼저 결정하고, 그 타입의 골격을 베이스로 콘텐츠를 채운다.

타입이 모호할 때 사용자에게 한두 가지 질문으로 확정한 뒤 진행한다.

---

## 타입 판단 플로우

```
[새 보고서 요청]
    │
    ├─ "어떻게 할지 구상" / "받은 업무 정리"   → 1. Task Plan
    ├─ "큰그림" / "전체 분석" / 방대한 작업 사전 → 2. Analysis
    ├─ "옵션 비교" / "라이브러리 선택" / "조사"   → 3. Tech Investigation
    ├─ "설계" / "RFC" / "아키텍처 제안"        → 4. System Design
    ├─ "회고" / "리뷰" / "후기"               → 5. Retrospective
    ├─ "장애" / "인시던트" / "postmortem"      → 6. Incident Postmortem
    ├─ "설명해줘" / "해설" / "X가 뭔지 정리"    → 7. Explainer
    ├─ "방법론" / "산출 방식" / "산식·알고리즘 명세" → 8. Methodology
    ├─ "가이드" / "how-to" / "절차 문서" / "runbook" → 9. Guide
    ├─ "점검" / "감사" / "잔재 확인" / "audit"   → 10. Audit
    └─ "백테스트 결과" / "벤치마크" / "실험 결과" / "측정 결과" → 11. Results
```

판단이 안 서면: "이 보고서를 한 줄로 요약하면 어떤 문장입니까?" 질문해서 동사로 분류.
- "~하기로 결정했다" → Tech Investigation 또는 System Design
- "~할 계획이다" → Task Plan
- "~를 분석했다" → Analysis
- "~를 했고, 무엇을 배웠다" → Retrospective
- "~장애가 발생했고 ~로 복구했다" → Incident Postmortem
- "~가 어떻게 동작하는지 이해시킨다" → Explainer
- "~를 이렇게 계산/산출한다" → Methodology
- "~를 따라 하면 ~가 된다" → Guide
- "~를 기준에 대고 검사했더니 ~가 나왔다" → Audit
- "~를 돌렸더니/측정했더니 ~가 나왔다" → Results

**계열 구분** — ① 결정·보고(plan·analysis·invest·design·retro·incident): "무엇을 할지/골랐는지/겪었는지"가 본문, 옵션 비교·리스크 필수. ② 지식(explain·method·guide): "독자를 이해시키거나 따라 하게"가 본문, 옵션 비교 원칙 미적용. ③ 증거(audit·results): "검사/실험했더니 무엇이 나왔다"가 본문, 판정 기준·조건을 결과보다 먼저 고정하는 게 핵심 원칙.

**섞인 요청 처리**: 하나의 요청에 여러 계열이 섞이면 주 골격 하나를 정하고 나머지는 별도 문서로 분리하거나 링크한다. 예 — "RS 지수 산출 방식을 정하고 문서화해줘": 산식이 이미 정해졌으면 Methodology, 아직 고르는 중이면 Tech Investigation → 확정 후 Methodology 로 정본화. "백테스트 돌리고 결과 정리해줘": 산식 정의는 method 문서 링크, 결과는 Results 가 주 골격.

## 1. Task Plan (작업 계획서)

> **언제**: 업무를 받았을 때 "어떻게 할지" 구상한 결과를 동료/대표에게 공유하거나 본인이 정리할 때.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (한 줄 결론·접근 방향) | `.tldr` |
| 2 | 컨텍스트 (왜 이 업무가 들어왔나) | `<p>` + `.callout.note` |
| 3 | 목표·비목표 (Scope) | `.proscons` (할 것/안 할 것) 또는 `.callout.info` |
| 4 | 접근 옵션 비교 | `.grid.cols-3 > .card` 또는 `<table>` |
| 5 | 선택안과 근거 | `.callout.info` + `.proscons` |
| 6 | 실행 단계 | `<ol class="steps">` |
| 7 | 마일스톤 | `.timeline` |
| 8 | 리스크·미해결 질문 | `.risk-grid` 또는 `<details class="qa">` |
| 9 | 체크리스트 | `.checklist` |

### 선택 섹션
- 의존성·전제 (`.callout.warn`)
- 검증 기준 (`.checklist`)

### kicker 텍스트
`Task Plan` 또는 `Work Plan`

### 핵심 원칙
- "내가 어떻게 할 건지"를 **읽는 사람이 5분 안에 동의/반대할 수 있게** 정리한다.
- 옵션이 1개뿐이라면 보고서 가치가 낮음. 최소 옵션 2~3개를 비교하고 선택 근거를 명시.
- 단계는 **검증 가능한 단위**로 나눔 (Step 5개 이하 권장).

## 2. Analysis / Big-Picture (분석 보고서)

> **언제**: 인프라 전환·시스템 리아키텍처처럼 **착수 전에 전체 그림**을 그려야 할 때. infra-transfer-plan 같은 케이스.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR | `.tldr` |
| 2 | 컨텍스트·목표 | `<p>` + `.callout.info` |
| 3 | AS-IS (현재 구조와 문제) | `.compare > .as-is` 또는 단독 `.card.outline` + 문제 리스트 |
| 4 | TO-BE (목표 구조) | `.compare > .to-be` |
| 5 | 핵심 변화 KPI | `.grid.cols-3 > .stat` |
| 6 | 아키텍처 다이어그램 | `.mermaid-wrap` |
| 7 | 기술 스택 선택 | `<table>` (옵션 비교) + `.callout.info` (왜 채택했는가) |
| 8 | 전환 전략 (단계) | `<ol class="steps">` 또는 `.timeline` |
| 9 | 리스크 매트릭스 | `.risk-grid` |
| 10 | 후속 작업·미해결 | `.callout.warn` + `<details class="qa">` |

### 선택 섹션
- 보안 특성 (`.callout.success`)
- 운영 부하 변화 (`.stat`)
- 비용 추정 (`<table>`)

### kicker 텍스트
`Analysis Report` 또는 `Big Picture`

### 핵심 원칙
- AS-IS → TO-BE 의 **격차(Gap)** 가 명확해야 함. 단순히 "현재는 이렇고 미래는 저렇다"가 아니라, **무엇이 바뀌어 무엇이 해결되는지** 1:1 매핑.
- 다이어그램은 1개만 메인. 여러 개면 청중이 헷갈림.
- 리스크 매트릭스는 모든 분석 보고서의 필수. "장밋빛 계획" 방지.

## 3. Tech Investigation (기술 검토·옵션 비교)

> **언제**: 라이브러리·아키텍처·툴 선정. "X 와 Y 중 뭘 쓸까?" 류.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (결론 + 한 줄 근거) | `.tldr` |
| 2 | 문제 정의 | `<p>` + `.callout.note` |
| 3 | 평가 기준 (가중치) | `<table>` 기준 + 가중치 |
| 4 | 후보 옵션 소개 | `.grid.cols-3 > .card` (각 옵션 1카드) |
| 5 | 옵션별 상세 비교 | `<table>` 또는 `.proscons` 반복 |
| 6 | 결정 매트릭스 | `<table class="decision">` + `.winner` |
| 7 | 채택안의 트레이드오프 | `.callout.warn` |
| 8 | 도입 단계 (선택안만) | `<ol class="steps">` |

### 선택 섹션
- 벤치마크 결과 (`<table>` + `.stat`)
- 마이그레이션 비용 (`.stat`)
- 미선택안의 향후 재검토 조건 (`<details class="qa">`)

### kicker 텍스트
`Tech Investigation` 또는 `RFC: Library Selection`

### 핵심 원칙
- **평가 기준을 먼저 정한 뒤** 옵션을 보여야 결론에 설득력. 옵션 보고 기준 짜맞추는 거 금물.
- 결정 매트릭스의 가중치는 명시 (×3, ×2 등). 점수 산식 투명하게.
- "비기는 경우" 가 나오면 의도적으로 tie-breaker 기준을 추가.

## 4. System Design / RFC (설계 문서)

> **언제**: 새 기능·시스템 설계. "OO 기능을 이렇게 만들겠다" 제안.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR | `.tldr` |
| 2 | 동기·문제 | `<p>` + `.callout.info` |
| 3 | 목표·비목표 | `.proscons` (Goals / Non-Goals) |
| 4 | 요구사항 (기능·비기능) | `<table>` 또는 `<ul>` 분리 |
| 5 | 아키텍처 (Mermaid) | `.mermaid-wrap` |
| 6 | 데이터 모델 | `<pre>` (스키마) 또는 mermaid `erDiagram` |
| 7 | API 스펙 | `<table>` (endpoint × method) |
| 8 | 대안 검토 (Considered Alternatives) | `.proscons` 또는 `<details class="qa">` 반복 |
| 9 | 보안·프라이버시 | `.callout.warn` + `<ul>` |
| 10 | 단계별 롤아웃 | `<ol class="steps">` 또는 `.timeline` |
| 11 | 미해결 질문 (Open Questions) | `<details class="qa">` |

### 선택 섹션
- 메트릭·관측 (`.checklist`)
- 호환성·마이그레이션 (`.compare`)

### kicker 텍스트
`System Design` 또는 `RFC-{번호}`

### 핵심 원칙
- RFC 는 **결론보다 사고 과정**이 중요. "왜 A 대신 B 인가" 가 본문.
- 데이터 모델·API 스펙은 의도적으로 자세히. 구현자가 다른 사람이어도 짤 수 있게.
- Open Questions 는 *반드시* 1개 이상. "다 해결됐다"는 거짓말이거나 검토가 얕다는 신호.

---

## 5. Retrospective / Review (회고·점검)

> **언제**: 작업 완료 후·스프린트 회고. 기간 단위 활동 점검.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (한 줄 결론) | `.tldr` |
| 2 | 기간·범위 | `.report-meta` 또는 `.callout.note` |
| 3 | 한 일 (Done) | `.timeline` 또는 `<ul>` |
| 4 | 메트릭 결과 | `.grid.cols-3 > .stat` (배포 횟수, 인시던트, 코드량 등) |
| 5 | 잘된 점 (Keep) | `.callout.success` |
| 6 | 문제·아쉬운 점 (Problem) | `.callout.warn` 또는 `.proscons` |
| 7 | 시도해볼 것 (Try) | `<ol class="steps">` |
| 8 | 액션 아이템 | `<table>` (항목·담당·기한) |

### 선택 섹션
- 학습·인사이트 (`<details class="qa">`)
- 다음 사이클 목표 (`.checklist`)

### kicker 텍스트
`Retrospective` 또는 `Sprint Review` 또는 `Project Postmortem`

### 핵심 원칙
- KPT (Keep/Problem/Try) 구조 권장. 잘된 것·문제·시도 셋 다 균형 있게.
- 액션 아이템에 **담당자·기한**이 없으면 회고가 아니라 일기. 표로 명시.
- 메트릭은 객관 데이터로. "체감상 빨라졌다" 같은 정성 평가는 callout 별도로 분리.

## 6. Incident Postmortem (장애 회고)

> **언제**: 운영 장애 발생 후. 비난 없이(blameless) 원인·재발 방지를 정리.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | 요약 (TL;DR) | `.tldr` (1~2문장: 무엇이·언제·얼마나·어떻게) |
| 2 | 심각도·영향 | `.grid.cols-3 > .stat` (다운타임, 영향 사용자, 데이터 손실) + `.badge` |
| 3 | 타임라인 | `.timeline` (시각 단위, 24h 표기) |
| 4 | 근본 원인 (Root Cause) | `.callout.danger` |
| 5 | 기여 요인 (Contributing Factors) | `<ul>` 또는 `.grid.cols-2 > .card` |
| 6 | 무엇이 잘 작동했나 | `.callout.success` |
| 7 | 무엇이 못 작동했나 | `.callout.warn` |
| 8 | 액션 아이템 | `<table>` (단기·중기·장기 분류, 담당·기한) |
| 9 | 재발 방지 | `.checklist` |

### 선택 섹션
- 5 Whys 분석 (`<details class="qa">` 5개 중첩)
- 관련 로그·메트릭 (`<pre>` 또는 mermaid `timeline`)

### kicker 텍스트
`Incident Postmortem` 또는 `INC-{번호}`

### 핵심 원칙
- **Blameless**: 사람 이름·역할 비판 금지. 시스템·프로세스 관점으로 기술.
- 타임라인은 **분 단위 정확도**. "약 30분 후" 같은 모호한 표현 금지.
- 액션 아이템 없는 postmortem 은 가치 없음. 최소 3개 이상, 담당·기한 명시.
- "왜 못 막았나" 보다 "다음에 어떻게 빨리 알아챌까" 에 비중.

## 7. Explainer (개념·기술 해설)

> **언제**: 개념·기술·시스템이 "무엇이고 왜 그런지"를 독자 눈높이로 풀어 설명할 때. tech overview, "X explained", 도메인 개념 해설. 결정·계획이 아니라 **독자의 멘탈 모델 형성**이 목적.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (이 문서가 답하는 질문 + 한 줄 답) | `.tldr` |
| 2 | 왜 존재하나 (푸는 문제 + 비유) | `<p>` + `.callout.note` |
| 3 | 큰 그림 (멘탈 모델) | `.mermaid-wrap` + `.grid.cols-3 > .card` (구성요소) |
| 4 | 어떻게 동작하나 | `<ol class="steps">` + `.example` (구체 예시) |
| 5 | 흔한 오해 | `.compare` (오해 → 실제) |
| 6 | 한계 (어디까지 통하나) | `.callout.warn` |
| 7 | 요약 치트시트 | `<table>` (질문 × 한 줄 답) |
| 8 | 용어집 | `dl.glossary` |

### 선택 섹션
- 곁가지 배경지식 (`details.primer`) — 인접 개념 한정
- 실전 적용 예 (`.example` 추가)

### kicker 텍스트
`Explainer` 또는 `Tech Overview`

### 핵심 원칙
- **순서가 생명**: 문제(왜) → 큰 그림 → 메커니즘 → 오해 교정 → 한계. 메커니즘부터 시작하면 실패.
- 추상 설명마다 비유 또는 구체 예시를 짝짓는다. 비유는 **어디까지 성립하는지 경계도 함께** 명시 (비유 과신이 새 오해를 만든다).
- 보조 레이어 규칙이 다른 타입과 반대: **핵심 개념은 본문에 직접** 풀고, primer 는 곁가지 인접 개념에만. 본문이 곧 풀이인 문서에서 핵심을 접어두면 문서가 빈다.
- 옵션 비교·리스크 매트릭스 원칙 적용 안 됨 (결정 문서가 아님). 대신 "흔한 오해"와 "한계" 섹션이 그 역할 — 이 둘이 없으면 홍보 자료가 된다.

---

## 8. Methodology (방법론·산식 명세)

> **언제**: 지표 산출 방식, 점수 산식, 가중치 체계, 알고리즘 등 "어떻게 계산/동작하는지"의 **정본(reference)** 을 남길 때. 한 번 읽고 버리는 보고서가 아니라 두고두고 찾아보는 문서.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (무엇을 정의하는 문서인가) | `.tldr` |
| 2 | 전체 구조 (입력→단계→출력) | `.mermaid-wrap` (`flowchart LR`) |
| 3 | 기호·용어 고정 | `<table>` (기호·뜻·예) |
| 4~ | 핵심 정의 (단계당 1섹션 반복) | 말로 정의 → `.formula` + `dl.formula-where` → `.example` (숫자 예시) → `.callout.warn` (경계 조건) |
| n+1 | 변형 비교 (있을 때만) | `<table class="decision">` + `.winner` |
| n+2 | 파라미터 (있을 때만) | `<table>` (기본값·범위·민감도) |
| n+3 | 결정 필요 사항 | `<details class="qa">` (없으면 "없음" 명시) |
| n+4 | 참고 자료 · 용어집 | `<ul>` + `dl.glossary` |

### kicker 텍스트
`Methodology`

### 핵심 원칙
- 계산 단계마다 **[말 정의 → 수식 → 숫자 예시] 3종 세트를 반복**한다. 수식만 있으면 비전문가는 못 따라오고, 말만 있으면 구현자가 못 만든다. 숫자 예시는 독자가 손으로 따라 계산해 같은 답이 나오는 수준으로.
- 수식은 KaTeX 등 외부 렌더러 없이 `.formula` mono 선형 표기 + `<sub>/<sup>`. 기호는 3번 섹션에서 고정하고 거기 없는 기호를 본문에 쓰지 않는다.
- **경계 조건 필수**: 0으로 나누기·결측·신규 진입 등 수식이 깨지는 입력과 그때의 처리 규칙. 이게 없는 산식 문서는 구현 단계에서 반드시 되돌아온다.
- 변형이 여러 개면 각 변형을 같은 구조(수식+예시+장단점)로 병렬 기술한 뒤 비교표로 모은다. 변형 섹션이 곧 이 타입의 "옵션 비교".

---

## 9. Guide (절차 실행 가이드)

> **언제**: 설치·설정·마이그레이션 절차, 운영 runbook, 온보딩, 도구 사용법. 독자가 **따라 하면서** 읽는 문서.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (끝내면 얻는 상태 + N단계·M분) | `.tldr` |
| 2 | 전제 조건 | `.checklist` + `<table>` (플레이스홀더 값) |
| 3 | 진행 단계 | `<ol class="steps">` — 단계마다 `<pre><code>` 명령 + "예상 결과" 한 줄 |
| 4 | 완료 검증 | `.checklist` (명령 + 기대 출력) |
| 5 | 트러블슈팅 | `<table>` (증상·원인·대처) |
| 6 | 되돌리기 | `<pre><code>` (복구 불가 단계는 명시) |

### 선택 섹션
- FAQ (`<details class="qa">`)
- 소요 시간·난이도 메타 (`.report-meta`)

### kicker 텍스트
`Guide` 또는 `Runbook`

### 핵심 원칙
- **위→아래 한 방향 진행**. "앞에서 한 X를 다시 열고" 같은 역참조 금지 — 필요하면 단계 순서를 재배치한다.
- 모든 실행 단계는 **[명령/행동 → 예상 결과] 쌍**. 예상 결과가 없으면 독자는 자기가 성공했는지 모른다.
- 명령은 복사-붙여넣기 가능하게. 치환 값은 `{PLACEHOLDER}` 대문자로 쓰고 전제 조건 섹션에서 미리 정하게 한다.
- 위험한 단계(삭제·덮어쓰기·재시작)는 그 단계 안에 `.callout.warn` 인라인. 문서 끝에 몰아두면 이미 늦다.

## 10. Audit (감사·점검 보고서)

> **언제**: 마이그레이션 잔재 점검, 설정·권한 감사, 문서/코드 정합성 점검, 보안 셀프 점검 등 **"현재 상태를 기준에 대고 검사한 결과"** 를 남길 때.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (종합 판정: 통과/경고/실패 건수) | `.tldr` |
| 2 | 점검 범위·기준 + **점검하지 않은 것** | `<table>` + `.callout.note` |
| 3 | 점검 방법 (재현 가능한 명령) | `<pre><code>` |
| 4 | 종합 결과 | `.grid.cols-3 > .stat` (통과·경고·실패) + `<table>` (발견 목록 + 심각도 badge) |
| 5 | 발견사항 상세 (건별 반복) | `<h3>` + 증거 `<pre>` + 권고 `.callout.info` |
| 6 | 권고 조치 목록 | `<table>` (우선순위 P0/P1·담당·기한) |
| 7 | 다음 점검 | `<p>` |

### kicker 텍스트
`Audit Report`

### 핵심 원칙
- **판정 기준을 발견사항보다 먼저 고정** — 기준 없이 나열된 발견은 감사가 아니라 인상비평.
- 발견 건마다 **증거**(파일 경로·명령 출력·설정값)를 붙인다. 증거 없는 지적은 의견이다.
- **"점검하지 않은 것" 명시 필수** — 검사 안 한 영역과 이상 없는 영역의 구분이 감사 보고서의 신뢰도.
- 발견 0건이어도 보고서 가치가 있다: "이 기준으로 검사했고 깨끗하다"가 결론이 된다.

---

## 11. Results (실험·측정 결과 보고서)

> **언제**: 백테스트 결과, 벤치마크 측정, A/B 비교 실험, 성능 프로파일링 등 **"돌렸더니 무엇이 나왔다"** 를 보고할 때. 데이터가 주인공.

### 필수 섹션
| # | 섹션 | 추천 컴포넌트 |
|---|------|--------------|
| 1 | TL;DR (핵심 결과 + 단서 조항) | `.tldr` |
| 2 | 실험 조건 (데이터·기간·파라미터·코드 버전) | `<table>` + 방법론 문서 링크 `.callout.note` |
| 3 | 평가 지표 정의 | `<table>` (지표·뜻·좋은 방향) |
| 4 | 종합 결과 | `.stat` KPI + `<table class="decision">` + 메인 차트 (`.mermaid-wrap.zoomable > img`) |
| 5~ | 상세 결과 (비교 축별 반복) | `<table>` + 말로 된 해석 |
| n+1 | 해석·한계 | `.callout.warn` (과최적화·표본 편향·미반영 비용) |
| n+2 | 결론·다음 단계 | `<p>` + `.checklist` |

### kicker 텍스트
`Results Report`

### 핵심 원칙
- **조건을 결과보다 먼저** — 어떤 데이터·기간·파라미터·코드 버전으로 돌렸는지 없는 숫자는 재현도 비교도 불가능.
- 방법론 자체는 여기 정의하지 않는다 — **method 문서로 분리하고 링크**. 결과 문서에 산식이 섞이면 둘 다 못 쓰게 된다.
- **해석·한계 섹션 필수**: 과최적화·표본 편향·측정 노이즈·미반영 비용을 스스로 지적하지 않는 결과 보고서는 체리피킹으로 읽힌다.
- 차트는 base64 data URI 임베드 + `.zoomable` 클릭 확대. 표는 차트의 보조가 아니라 정본 (차트만 있고 숫자 표가 없으면 인용 불가).
