# Skills Estimate

## 왜 이 스킬이 필요한가

스킬은 한 번 만들면 사용자가 향후 수십·수백 번 호출한다. 부실한 스킬은 (1) 잘못된 트리거로 엉뚱한 상황에 발동되거나, (2) 막혔을 때 판단 근거를 못 줘 사람이 매번 같은 결정을 내려야 하거나, (3) 출력 형식이 모호해 결과물이 들쭉날쭉해진다. 이런 결함은 사용 빈도만큼 누적된다.

이 스킬은 **이미 만들어진 스킬의 결함을 정량적으로 짚어내고 보강 위치를 구체적으로 제시**한다. "나쁘다/좋다" 같은 추상적 평가가 아니라 14개 항목 채점, 약점 Top 3 + 글자 수 단위 보강안, 3가지 시나리오 충족도까지 산출한다.

---

## 절대 규칙

- **읽기 전용**: 평가 대상 SKILL.md를 절대 수정하지 않는다. 보고서만 출력한다.
- **평가 단위**: SKILL.md 한 파일 + 같은 디렉토리의 번들 리소스(scripts/, references/ 등).
- **출력 위치**: 기본은 사용자에게 직접 출력. 사용자가 "파일로 저장"을 요청하면 `~/.claude\skill-reviews\{skill-name}.md` 에 저장 (디렉터리 없으면 생성). 일괄 평가의 종합 보고서는 `{군이름}-skills-estimate-{YYYY-MM-DD}.md`.
- **재평가는 덮어쓰지 않고 append 한다.** 같은 파일이 이미 있으면 맨 아래에 `## 재평가 {YYYY-MM-DD}` 섹션을 붙이고 **이전 점수 → 이번 점수**를 나란히 적는다. 1차·2차 채점을 반복하는 것이 이 스킬의 정상 사용 패턴이라(실제로 stock-experts 는 3회 돌았다), 덮어쓰면 개선 추적이 통째로 사라진다.
- **점수 인플레이션 금지**: 후하게 주지 말 것. 5점은 "rubric을 넘어선 추가 가치가 있을 때"만.
- **모든 점수에 줄 번호 근거** 필수 인용. "감으로 4점" 금지.
- **Self-bias 가드 (자기 평가 시)**: 평가 대상이 `skills-estimate` 자신일 경우 자체 rubric은 자기 시스템의 맹점(분류 누락·점수 부정합·평가 차원 자체의 결함)을 평가할 항목이 없어 self-bias가 구조적으로 발생한다. 자기 평가는 보조 지표로만 쓰고, 최소 1회는 별도 평가자(다른 모델 인스턴스 또는 사람)에게 외부 평가를 위임한다. 자기 평가 결과를 보고서에 적을 때는 헤더에 "⚠️ 자체 평가 — self-bias 가능성 있음" 명시 + 약점 부록에 "자체 rubric으로는 짚지 못한 결함이 있을 수 있다" 한 줄 첨부.

## Quick Start — 5분 안에 한 개 채점하기

급할 때는 이 다섯 줄만 따른다. 전체 절차는 아래 「실행 흐름」이다.

```bash
# 1. 기계로 잡히는 것부터 (A2·F1 이 결정론적으로 정해진다)
python ~/.claude\skills\skill-creator\scripts\check-skill.py <스킬폴더>

# 2. 대상과 anchor 를 연다
wc -l <스킬폴더>\SKILL.md
ls ~/.claude\imported-sub-skills\pr-review\SKILL.md
```

3. 유형을 하나 고른다 (Tool/Design/Context/Checklist/Reference/Hybrid) — 2단계 결정 트리
4. `references/rubric-cheatsheet.md` 를 열고 14항목을 0~5로 매긴다. **줄 번호 근거 필수**
5. 산수는 스크립트에 맡긴다

```bash
python ~/.claude\skills\skills-estimate\scripts\score.py --name <스킬명> --type <유형> --scores A1=4,A2=5,...,F1=2
```

전체 보고서까지 필요 없고 등급만 알면 되는 경우 여기서 끝내도 된다. **다만 "약점 Top 3" 없이 등급만 넘기지는 않는다** — 등급은 판단을 못 주고, 사용자가 원하는 건 어디를 고칠지다.

## 용어

이 문서가 반복해서 쓰는 말 넷.

- **anchor**: 채점 기준선으로 삼는 **다른 스킬의 실제 문단**. 점수 기술만으로 3점인지 4점인지 안 갈릴 때, 그 문단과 평가 대상을 줄 단위로 대 본다(1.5단계).
- **원점수 / 가중점수**: 원점수는 14항목 단순 합(/70)으로 **항목별 진단용**이다. 가중점수는 유형별 카테고리 가중치를 곱한 값(/100)으로 **등급 부여의 공식 기준**이다. 둘의 백분율이 다른 게 정상이다.
- **self-bias**: 평가 도구가 자기를 잴 때, 자기 rubric 에 없는 차원의 결함이 구조적으로 안 보이는 현상. 「절대 규칙」의 가드가 이걸 막는다.
- **게이트**: 일괄 평가 전에 미리 정하는 목표 점수(예: "전 스킬 B+ 이상"). 이걸 안 정하면 등급만 나오고 아무것도 안 고쳐진다(`references/batch-evaluation.md`).

## 실행 흐름

> **대상이 20개를 넘으면** 여기서 멈추고 `references/batch-evaluation.md` 를 먼저 읽는다. 한 개씩 채점하는 절차로 수십 종을 돌리면 중간에 기준이 흔들려 앞뒤 점수가 서로 비교 불가해진다. 그 문서는 anchor 방식·배치 분할·±2%p 상대 보정·게이트 설정을 다룬다.

### 1단계: 평가 대상 파악

```bash
# 평가할 스킬 경로 확인
ls ~/.claude\skills\<skill-name>\
cat ~/.claude\skills\<skill-name>\SKILL.md  # 또는 SKILLS.md
wc -l ~/.claude\skills\<skill-name>\SKILL.md
```

**기계로 잡히는 것을 사람이 눈으로 채점하지 않는다.** 먼저 검사기를 돌린다.

```bash
python ~/.claude\skills\skill-creator\scripts\check-skill.py <스킬폴더>
```

이 출력이 **A2(frontmatter)·F1(번들)의 1차 근거**가 된다. FAIL 이 있으면 그 항목은 상한이 정해진다.

| 검사기 결과 | 채점에 미치는 영향 |
|---|---|
| `no-frontmatter` | **A2 = 0점** (Context 유형이면 정상) |
| `name-dir-mismatch` | A2 **최대 3점**. 두 등록 경로가 다른 이름을 쓰는 실제 결함이다 |
| `desc-too-long` (1024자 초과) | A2 **최대 2점**. 공식 hard limit 위반이라 등록이 깨진다 |
| `desc-missing` | **A1 = 0점, A2 = 0점** |
| `dead-bundle-ref` | **F1 최대 1점** + 본문 흐름을 깨면 D1 에 함께 반영 |
| `desc-no-when-not` (WARN) | A1 **최대 3점** (SKIP 조건 부재) |
| `body-large` (WARN) | F1 판단 재료. 쪼갤 곳을 약점 보강안에 적는다 |

검사기가 통과했다고 A2·F1 이 자동 5점은 아니다. **FAIL 은 상한을 정하고, 통과는 상한을 풀 뿐이다.**

- 사용자가 스킬명/경로를 명시하지 않으면 어느 스킬을 평가할지 묻는다.
- frontmatter 유무, 본문 길이, 디렉토리 구조(번들 리소스 존재 여부) 먼저 파악.
- 같은 스킬의 이전 평가 보고서가 `~/.claude\skill-reviews\`에 있으면 함께 읽어 비교 평가 가능.

### 1.5단계: 모범 스킬 anchor 확인

Rubric 채점 시 아래 파일이 채점 anchor로 쓰인다. 채점 전에 **실재 여부를 확인한다.**

| 항목 | anchor | 실제 경로 |
|------|--------|----------|
| A1, B2, B3, C3, D1, E1 | `pr-review` | `imported-sub-skills\pr-review\SKILL.md` (1,044줄) |
| B1, C2 | `xlsx` | `sub-skills\xlsx\SKILL.md` (291줄) |
| E2 | `web-browse` | `skills\web-browse\SKILL.md` (194줄) |

```bash
# anchor 실재 확인 — 셋 다 있어야 경계 판정이 ±1점으로 유지된다
ls ~/.claude\imported-sub-skills\pr-review\SKILL.md
ls ~/.claude\sub-skills\xlsx\SKILL.md
ls ~/.claude\skills\web-browse\SKILL.md
```

**anchor 가 없을 경우**: 해당 항목은 점수 기술에만 의존해 채점하되, 경계 판정(±1점 허용)을 **±2점으로 완화**한다. 보고서 헤더에 `⚠️ anchor 미확인 — 경계 판정 신뢰도 저하` 명시.

> ⚠️ **2026-09-03 경로 교정.** 이 표는 오래 `skills\pr-review` · `skills\xlsx` · `skills\git-workflow` 를 가리켰는데 **셋 다 그 경로에 없었다.** pr-review 는 `imported-sub-skills\` 로, xlsx 는 `sub-skills\` 로 갔고 **`git-workflow` 는 이 하네스에 아예 존재하지 않는다.** 그래서 모든 평가가 매번 "anchor 미확인"으로 떨어져 경계 판정이 ±2점으로 완화되고 있었다. E2 anchor 는 실재하고 즉시 실행 가능한 명령이 풍부한 `web-browse` 로 교체했다.
>
> ⚠️ **그때의 줄 번호 검증은 표본 4개에 그쳤고 결론이 틀렸다.** 당시 "틀린 것은 경로뿐"이라 적었는데, 2026-09-03 별도 평가자가 인용 9개를 전수 실측하니 **5개가 어긋나 있었다** — B2·B3·C3·D1·E1 이 다른 내용을 가리켰고, B1 은 범위가 75줄로 과잉이었다. 게다가 "확인했다"고 적은 4건 중 `:381~390=심각도 판정` 이 그 자리에서 틀렸다(실제 :605). 아래 Rubric 의 모범 인용은 그때 전수 교정한 것이다.
>
> **경로가 실재한다고 줄 번호까지 맞는 건 아니다.** anchor 가 옮겨지거나 길이가 바뀌면 **(1) 이 표 · (2) 아래 Rubric 의 모범 인용 · (3) `references/rubric-cheatsheet.md` 의 모범 인용, 셋을 같이 고친다.** 한쪽만 고치면 반쪽이다 — 2026-09-03 1차 교정이 실제로 (3)을 빼먹어 치트시트에 죽은 `git-workflow` anchor 가 반년 더 남아 있었다.

### 2단계: 스킬 유형 분류

평가 가중치는 유형마다 다르다. SKILL.md 본문을 빠르게 훑어 다음 4개 중 하나로 분류한다.

| 유형 | 특징 | 예시 | 식별 신호 |
|------|------|------|----------|
| **도구·통합 (Tool)** | 외부 도구·CLI·API를 호출해 파일·시스템 조작 | pr-review, xlsx, web-browse, webapp-testing | 본문에 `gh`, `git`, bash 명령어, Python 코드블록 다수 |
| **설계·원칙 (Design)** | 아키텍처·디자인 패턴·best practice 지침 | frontend-design, mcp-builder, skill-creator | 추상적 원칙·철학·"~해야 한다" 위주, 구체적 명령어 적음 |
| **컨텍스트 문서 (Context)** | 특정 프로젝트/작업의 배경 지식 (트리거 없음) | (예: 인프라 전환 계획 문서) | frontmatter 없거나 비어있음, AS-IS/TO-BE·기술 스택 위주 |
| **체크리스트 (Checklist)** | 단계별 확인 항목 나열, 짧고 정형화 | self-review | 100~200줄 내외, 체크박스·번호 리스트 위주 |
| **표준·참조 (Reference)** | 도메인 규약·컨벤션·코드 스타일 등 정형 명문화 | xlsx의 Color Coding 섹션 같은 reference 문서 | 표·규약·"X는 Y로 한다" 식 정의 위주, 절차보다 명세 |
| **하이브리드 (Hybrid)** | 두 유형 이상이 비슷한 비중으로 섞임 | 일부 pr-review처럼 도구+디자인+체크리스트 혼합 | 단일 유형 60% 이상에 도달 못함 |

#### 분류 결정 트리 (애매할 때)

본문을 훑어 다음 순서로 판정:

1. frontmatter의 description이 비어있거나 트리거 키워드 없음 → **Context**
2. 본문에 실행 가능한 명령어/코드(bash·gh·python 등)가 **30% 이상** 차지 → **Tool**
3. 본문이 표·규약·"X는 Y로 한다" 명세 위주 → **Reference**
4. 본문이 "~해야 한다" 원칙·철학 위주이고 명령어 적음 → **Design**
5. 100~200줄 내외 + 체크박스·번호 리스트 60% 이상 → **Checklist**
6. 위 어느 것도 60%를 명확히 넘지 않음 → **Hybrid** (각 유형 매칭 비율로 가중치 평균 산출)

#### 유형별 카테고리 가중치

아래는 **공표된 A~E 값**(합 100%)이다. **최종 가중치는 이 값 × 0.95 에 F=5% 를 더한 것**이고, `scripts/score.py` 가 그 계산을 한다 — 여기 표를 손으로 다시 계산하지 않는다. Hybrid 는 아래 공표 값으로 먼저 매칭 비율 가중평균을 낸 뒤, 그 결과에 같은 × 0.95 + F=5% 를 적용한다.

| 카테고리 | Tool | Design | Context | Checklist | Reference | Hybrid |
|---------|------|--------|---------|-----------|-----------|--------|
| A. 트리거·경계 | 25% | 20% | **0%** | 20% | 15% | 매칭 비율 평균 |
| B. 자기완결성·판단기준 | 25% | 20% | 30% | 15% | 20% | 매칭 비율 평균 |
| C. 출력·구조 | 25% | 15% | 20% | 25% | 30% | 매칭 비율 평균 |
| D. 에지케이스 | 15% | 15% | 20% | 20% | 15% | 매칭 비율 평균 |
| E. 친절함·실용성 | 10% | 30% | 30% | 20% | 20% | 매칭 비율 평균 |
| F. 메타데이터·번들 | 5% | 5% | 5% | 5% | 5% | 5% |

예: Tool 유형의 최종 가중치는 A 25×0.95=23.75%, B 23.75%, C 23.75%, D 14.25%, E 9.5%, F 5% (합 100%). 소수점이 나오는 것은 정상이다 — 정수로 맞추려고 값을 임의로 조정하지 않는다.

**Context 유형은 A 카테고리(트리거)를 평가에서 제외**한다 — 컨텍스트 문서는 의도적으로 트리거 없이 수동 호출되도록 설계되기 때문. 대신 B·E의 비중이 높다.

**Reference 유형**은 도메인 규약 명문화가 핵심이라 C(출력·구조)가 최상위 비중(30%×0.95=28.5%). E(친절함)는 도메인 종사자 대상이라 중간 수준.

**Hybrid 유형**은 각 매칭 유형의 비율로 A~E 공표 값을 가중평균한 **뒤에** × 0.95 + F=5% 를 적용한다. 예: Tool 50% + Design 50%로 분류되면 공표 값 기준 A=(25+20)/2=22.5% 식(→ 최종 A=22.5×0.95=21.375%). 분류가 한 유형 60%에 도달하지 못한다는 게 분류 자체의 신호이므로 평가자는 "분류 결과를 보고서 헤더에 명시"하고 사용자가 분류 이의 제기 가능하게 한다.

**과거 채점 호환**: 2026-09-03 이전 보고서는 F 제외·A~E 합 100% 방식이다. 검산은 `scripts/score.py --legacy-f-excluded` (기본은 신규 방식). 배경은 Gotchas §4.

### 3단계: 14개 항목 채점

각 항목을 0~5점 척도로 채점하고, **반드시 SKILL.md의 줄 번호 근거**를 인용한다. 채점 기준은 아래 "평가 Rubric" 섹션에 상세 명시.

채점 중에는 `references/rubric-cheatsheet.md` 를 열어 둔다 — 14항목 0~5점 분기를 한 표로 압축한 것이라 항목마다 본문을 오르내리지 않아도 된다. 판정이 애매하면 그때 아래 Rubric 전문(모범·반례·채점 예시 포함)으로 돌아간다.

### 4단계: 가중치 적용 + 최종 점수

산수는 손으로 하지 말고 `scripts/score.py` 에 맡긴다. 항목 누락·범위 밖 점수를 조용히 통과시키지 않고 exit 2 로 거부한다.

```bash
python ~/.claude\skills\skills-estimate\scripts\score.py --name <스킬명> --type tool   --scores A1=4,A2=5,A3=3,B1=2,B2=4,B3=3,C1=4,C2=2,C3=3,D1=3,D2=2,E1=3,E2=5,F1=2

# hybrid 는 매칭 비율을 준다
python ~/.claude\skills\skills-estimate\scripts\score.py --type hybrid --mix tool=50,design=50 --scores ...
# Context 유형은 A 항목을 na 로 뺀다
python ~/.claude\skills\skills-estimate\scripts\score.py --type context --scores A1=na,A2=na,A3=na,B1=3,...
```

계산기 자체가 의심스러우면 `python ~/.claude\skills\skills-estimate\scripts\score.py --self-test` 를 돌린다. 신규 방식·`--legacy-f-excluded` 재현·가중치 합 불변식·잘못된 입력 거부를 모두 확인한다. 과거 보고서 검산 전용 `--legacy-f-excluded` 는 새 채점엔 쓰지 않는다.

```
원점수 = 14개 항목 합 (만점 70점, 참고용)
유형별 가중점수 = Σ (카테고리 점수 × 카테고리 가중치) (만점 100점, F 포함 — 2026-09-03~)

최종 등급은 "유형별 가중점수의 백분율"을 사용한다 — 원점수(/70)는 항목별 진단용이고, 등급 부여의 공식 기준은 가중점수(/100)다.

- A+: 90% 이상
- A:  85~89%
- B+: 80~84%
- B:  70~79%
- C:  60~69%
- D:  60% 미만
```

> **주의**: 원점수 백분율과 가중점수 백분율이 다르게 나오는 게 정상이다 (가중치가 카테고리별로 다르므로). 평가 보고서에는 둘 다 표기하되, 등급 라벨(A+~D)은 가중점수 기준으로 단일하게 부여한다.

### 5단계: 약점 Top 3 + 보강 제안

가장 점수 낮은 카테고리/항목 3개를 뽑고, 각각에 대해:
- **현황**: 어느 부분이 부족한가 (줄 번호 근거)
- **사례**: 그래서 어떤 문제가 발생할 수 있는가
- **개선 방안**: 어디에 무엇을 추가하면 N점 → M점 도달 가능한가 (글자 수·줄 수 단위로 구체적)

### 6단계: 시나리오별 충족도

3가지 시나리오로 시뮬레이션:

1. **새 입사자가 처음 쓸 때** — description만 보고 판단 가능? 본문만으로 끝까지 따라갈 수 있나? 막힐 때 대응 명시?
2. **긴급 상황에서 빨리 써야 할 때** — Quick start가 있나? 5~10분 내 핵심만 실행 가능? 실패해도 안전?
3. **다른 스킬과 경계 모호 상황** — 유사 스킬과의 분기 명확? 호출 순서 안내?

각 시나리오마다 ✅ 충족 / 🟡 부분 / ❌ 미흡 + 근거.

### 7단계: 보고서 작성·출력

아래 "출력 보고서 형식"을 따라 한 편의 보고서로 정리. 사용자에게 직접 출력하거나, 요청 시 파일 저장.

## 점수 경계 판정 보조 규칙

채점 중 N점인지 N+1점인지 헷갈릴 때 다음 절차로 판정한다 — 평가자 재량 편차를 줄이는 핵심 장치.

- **모범/반례 직접 비교**: 해당 항목의 모범 사례(예: pr-review:3, xlsx:71~76)와 평가 대상을 **줄 단위로 직접 비교**. 모범에 더 가까우면 N+1, 모범보다 명백히 부족하면 N.
- **5점은 "rubric을 넘어선" 추가 가치가 있을 때만**: rubric의 5점 기준에 정확히 부합하면 4점이 정답. 5점은 번들 자동화·도메인 특화·다국어 지원·템플릿 라이브러리 등 rubric에 없는 별도 가치가 있을 때.
- **0점은 "관련 항목 자체가 부재"일 때만**: 미흡하더라도 어떤 형태로든 다뤘으면 1점부터.
- **확인 불가 시 사용자 질의**: "이 항목을 N점으로 판정한 근거가 X인데, Y 시나리오에서 부족할 수 있어 보입니다 — N과 N+1 중 어느 쪽이 적절합니까?" 형태로 (어느 항목 / 현재 채점안 / 근거 줄 인용 / 기대 답변) 4요소 명시해 질의.
- **평가자 일관성 검증**: 같은 평가자가 동일 스킬을 N분 간격으로 두 번 평가했을 때 항목별 점수가 ±1점 이내여야 한다. 더 흔들리면 anchor 텍스트만 보지 말고 모범/반례 직접 비교를 한 번 더 수행.

## 평가 Rubric (핵심 자산)

### 카테고리 A. 트리거·경계 명확성 (3항목, 15점)

#### A1. description이 What(하는 일) + When(트리거 키워드) + When NOT(SKIP 조건)을 모두 포함하는가?
- **0점**: description 필드 자체가 없음
- **1점**: What만 명시 ("코드 리뷰를 한다")
- **2점**: What + 트리거 키워드 1~2개
- **3점**: What + 키워드 3~5개 + 유사 스킬 1개 구분
- **4점**: 위 + SKIP 조건 1~2개 명시
- **5점**: 위 + SKIP 조건 3개 이상, 다른 스킬 호출 권장 상황까지

**모범**: pr-review:3 — 트리거 5개 + 자매 스킬 3개 + SKIP 조건
**반례**: frontend-design:3 — When NOT 부재

**채점 예시 (A1)**:
- **2점** — What + 키워드 2개, 유사 스킬 없음:
  > `description: "코드 리뷰를 한다. 'review', '리뷰 해줘' 언급 시 트리거."`
- **3점** — What + 키워드 4개 + 유사 스킬 1개:
  > `description: "PR을 리뷰한다. '리뷰', '코드 점검', '검토', 'PR review' 언급 시 트리거. /self-review(본인 코드)와 다름."`
- **4점** — 위 + SKIP 조건 명시:
  > `description: "... /self-review(본인 코드), /find-skills(탐색)과 다르며, 타인의 PR 리뷰 시 사용. 본인 코드 점검은 /self-review를 쓸 것."`

#### A2. frontmatter에 name/description이 필수로 있고 깔끔한가?
- **0점**: frontmatter 없음 (Context 유형은 0점이어도 정상)
- **2점**: name 또는 description 중 하나만
- **3점**: 둘 다 있으나 description이 모호 (<50자)
- **4점**: 명확하나 license 같은 부가 필드 미흡
- **5점**: name + description + (해당 시) license, 구조 깔끔

#### A3. 다른 스킬·도구와의 경계를 명시했는가?
- **0점**: 다른 스킬 언급 없음
- **1점**: "다른 스킬은 ○○를 한다" 부정 언급만
- **2점**: 유사 스킬 1개 명시 + 차이 1~2줄
- **3점**: 유사 스킬 2~3개 + 각각 차이 명확
- **4점**: 위 + 경계 모호한 상황의 추천 스킬
- **5점**: 위 + 호출 순서(A→B) 또는 후속 스킬 안내

### 카테고리 B. 자기완결성·판단기준 (3항목, 15점)

#### B1. 외부 의존성을 명시하고 그 이유를 설명했는가?
- **0점**: 의존성 미명시
- **1점**: 의존성만 나열
- **2점**: 의존성 + 선택지 제시
- **3점**: 의존성 + 왜 필요한가 설명
- **4점**: 위 + 없을 때 대응 절차
- **5점**: 위 + 설치/설정 스크립트 번들

**모범**: xlsx:71~76 — LibreOffice 필수 + recalc.py 번들 (`## Important Requirements` 문단)

#### B2. 모호한 상황에서의 의사결정 기준을 명시했는가? (판정 테이블/플로우)
- **0점**: 판정 기준 없음
- **1점**: "문제 있으면 물어봐" 수준
- **2점**: 2~3가지 분기
- **3점**: 의사결정 테이블/플로우 5~10개 규칙
- **4점**: 위 + 각 분기별 대체 방법(A 안 되면 B)
- **5점**: 위 + 재수집·재시도 절차까지

**모범**: pr-review:605~615 — `#### 심각도 판정 트리 (헷갈릴 때)` 의 질문→심각도 표

#### B3. 판단 불가 상황에서 누가/언제/어떻게/기대값을 명시했는가?
- **0점**: 막히면 그냥 멈춤
- **1점**: "사용자에게 물어봐"만
- **2점**: 4요소 중 1~2개만
- **3점**: 4요소 모두 명시 (누가/언제/어떻게/기대결과)
- **4점**: 위 + 확인 결과 해석 가이드
- **5점**: 위 + 확인 불가 시 대체 경로

**모범**: pr-review:628~636 — `[확인 필요]` 4요소(누가/언제/어떻게/기대 결과) + 채워진 예시 1개

### 카테고리 C. 출력·구조 명확성 (3항목, 15점)

#### C1. 출력 결과물의 형식·구조·예시를 명시했는가?
- **0점**: 출력 형식 언급 없음
- **1점**: "마크다운/코드" 수준
- **2점**: "마크다운 + 헤더 순서" 정도
- **3점**: 구체적 구조 + 예시 코드블록 1~2개
- **4점**: 위 + 각 섹션의 역할·길이 기준
- **5점**: 위 + 파일명·폴더 구조·메타데이터까지

#### C2. 각 단계·섹션마다 예시를 제시했는가? (특히 좋음/나쁨 대비)
- **0점**: 예시 없음
- **1점**: 개념 설명만
- **2점**: 전체 구조 예시 1개
- **3점**: 위 + 각 섹션마다 예시 1~2개
- **4점**: 위 + 좋은 예/나쁜 예 대비
- **5점**: 위 + 실제 프로젝트 사례·스크린샷

**모범**: xlsx:104~128 — ❌ WRONG / ✅ CORRECT 대비

**채점 예시 (C2)**:
- **2점** — 전체 구조 예시 1개(플레이스홀더):
  > `## 리뷰 결과\n| 파일 | 심각도 | 내용 |\n|------|--------|------|`
  > 구조는 있으나 값이 비어있어 "이 정도 깊이면 충분한가" 판단 불가
- **4점** — 구조 예시 + 좋은 예/나쁜 예 대비:
  > `❌ 나쁜 예: "코드가 이상함"` vs `✅ 좋은 예: "줄 42의 user.role 비교가 === 대신 == 라 null == undefined가 true로 평가됨"`
  > anchor가 있어 처음 쓰는 평가자도 기준 파악 가능

#### C3. 파일명·위치·append/overwrite 규칙을 명시했는가?
- **0점**: 파일명/위치 언급 없음
- **1점**: "output.xlsx 같은 파일" 수준
- **2점**: 파일명 패턴
- **3점**: 파일명 + 경로 패턴
- **4점**: 위 + 경로 존재 체크 절차
- **5점**: 위 + append/overwrite 규칙

**모범**: pr-review:22~27 — 저장 위치 + 파일명 패턴 + 템플릿 + append 규칙

### 카테고리 D. 에지케이스·안전성 (2항목, 10점)

#### D1. 실패 모드·엣지 케이스를 분기했는가?
- **0점**: 없음
- **1점**: "X 없으면 물어봐" 수준
- **2점**: "X면 Y, 아니면 Z" 2가지
- **3점**: 3가지+ 분기 + 각 처리 명시
- **4점**: 위 + 첫 대응 실패 시 대체
- **5점**: 위 + 사용자 거부·불가능 상황 처리

**모범**: pr-review:213~223 — `##### 작성자 거부 답글 처리 분기` 의 3행 판정표

#### D2. 사용자 거부·불가능 상황의 fallback을 명시했는가?
- **0점**: 없음
- **1점**: "스킵해"만
- **2점**: 거부 시 로깅 절차
- **3점**: 거부 이유 분류 + 각각 처리
- **4점**: 위 + 에스컬레이션 경로(상위 중재 등)
- **5점**: 위 + partial success 모드 (관찰만 계속 등)

### 카테고리 E. 친절함·실용성 (2항목, 10점)

#### E1. 도메인 용어를 풀이하고 비유·예시로 설명했는가?
- **0점**: 전문 용어만
- **1점**: 용어 정의 한두 줄
- **2점**: 비유/예시 1~2개
- **3점**: 용어 풀이 + 비유 + 구체 예시
- **4점**: 위 + 초보자용 walkthrough
- **5점**: 위 + 도메인 특화 설명 (재무/PM/주니어 등)

**모범**: pr-review:932~964 — `### 풀어쓰기 패턴 (3종)`(용어 풀이 / 일상 비유 / 숫자로 현황). "빵집 비유"는 :949

#### E2. 명령어·코드를 copy-paste 가능한 형태로 제시했는가?
- **0점**: 코드 없음
- **1점**: 의사코드 수준
- **2점**: 명령어 1~2개 (수정 필요)
- **3점**: 실행 가능 코드블록 3~5개
- **4점**: 위 + 주요 단계마다 10~30줄 코드
- **5점**: 위 + 여러 언어/도구 옵션 + 에러 시 대체

**모범**: web-browse:28~46 — 실행 명령 + 미설치 시 설치 절차 + 옵션 예시가 전부 즉시 붙여넣기 가능

### 카테고리 F. 메타데이터·번들 (1항목, 5점)

#### F1. 디렉토리 구조가 명확하고 필요시 번들 리소스가 있는가?
- **0점**: SKILL.md 외 아무것도 없는데 필요한 상황 (스크립트가 있어야 할 도구 스킬인데 없음)
- **1점**: SKILL.md 만, 단순 스킬이라 OK
- **2점**: SKILL.md + 1개 번들 (scripts/ 또는 references/)
- **3점**: SKILL.md + 2개 이상 번들 + 구조 명확
- **4점**: 위 + 디렉토리 구조 README나 설명
- **5점**: 위 + 번들 스크립트 테스트·문서화

> **주의**: 단순 체크리스트 스킬이나 짧은 컨텍스트 문서는 번들이 없어도 1~2점이 정상. 도구 스킬인데 반복 명령이 많은데 번들 스크립트가 없으면 0~1점.

## 주의사항

- **점수 인플레이션 금지**: 친한 사람 점수 매기듯 후하게 주지 말 것. 5점은 rubric을 **넘어선** 추가 가치가 있을 때만. 4점이 "충분히 잘함" 기준.
- **유형 분류가 잘못되면 가중치가 틀어진다**: 애매하면 위 "분류 결정 트리"를 따른다. 결정 못 하면 Hybrid로 분류하고 매칭 비율을 보고서 헤더에 명시.
- **약점 Top 3는 가중 점수 기준**: 원점수가 낮아도 가중치 낮은 카테고리면 우선순위 낮아질 수 있음. 가중 손실이 큰 항목부터.
- **시나리오 충족도는 합리적 추정**: "이 사용자가 그렇게 쓸 것이다" 가정이지만, 스킬 구조에서 명확한 근거가 있어야 함.
- **컨텍스트 유형(frontmatter 없음)** 평가 시 A 카테고리 0% 가중치, B/E 비중 30%/30%. 채점 자체에서 A는 평가하지 않고 "—" 표기.
- **이전 평가 보고서가 있으면 비교**: `~/.claude\skill-reviews\{skill-name}.md`가 있으면 같이 읽고 점수 변화·개선 추적 섹션 추가.
- **본인이 평가하는 스킬을 절대 수정하지 말 것**: 보강은 사용자 의사 확인 후 별도 작업.

## Gotchas

실제로 터진 것만 적는다. 새 함정이 나오면 그 라운드에 덧붙인다.

### 1. anchor 경로가 조용히 죽어 있었다 (2026-09-03 발견)

1.5단계의 anchor 표가 `skills\pr-review`·`skills\xlsx`·`skills\git-workflow` 를 가리켰는데 **셋 다 그 경로에 없었다.** 앞의 둘은 폴더가 옮겨졌고, `git-workflow` 는 이 하네스에 존재한 적이 없다.

증상이 조용했던 이유는 스킬이 **"anchor 없으면 ±2점으로 완화"** 라는 우아한 폴백을 갖고 있었기 때문이다. 그래서 매 평가가 정상처럼 굴러가면서 실제로는 경계 판정 정밀도를 잃고 있었다.

**교훈**: 폴백이 매끄러우면 결함이 안 보인다. anchor·참조 경로는 **주기적으로 실재를 확인**한다.

**후속(2026-09-03 재평가)**: 1차 교정은 "줄 번호 인용은 맞았고 틀린 건 경로뿐"이라 결론냈는데 **그게 틀렸다.** 인용 9개를 전수 실측하니 5개가 어긋나 있었다. 검증 표본은 4개뿐인데 결론만 9개 전체로 일반화한 것이다. **경로 실재 확인과 줄 번호 실측은 별개 작업이고, 표본으로 확인했으면 표본이라고 적는다.** 그리고 SKILL.md 만 고치고 치트시트를 안 봐서 교정이 반쪽으로 남았다.

### 2. 자기 자신은 이 rubric 으로 평가할 수 없다

자체 rubric 에 자기 시스템의 맹점(분류 누락·점수 부정합·평가 차원 자체의 결함)을 볼 항목이 없다. 「절대 규칙」의 self-bias 가드를 따르고, 자기 평가는 보조 지표로만 쓴다.

### 3. 등급만 넘기면 아무것도 안 고쳐진다

"이 스킬은 C 입니다"로 끝난 평가는 실제 개선으로 이어지지 않았다. 등급은 판단을 못 준다. **약점 Top 3 + 줄 번호 단위 보강안**이 실제 산출물이다.

### 4. F 카테고리 가중치 비대칭 — 2026-09-03 해소됨

**원래 문제(실증됨)**: 「유형별 카테고리 가중치」 표에 F 가 없고 A~E 합이 유형마다 정확히 100%였다. 그래서 F 는 원점수(/70)에는 들어가는데 가중점수(/100)에는 0의 영향을 줬다. 2026-09-03 별도 평가자가 F1 을 4→5 로 올렸는데 가중점수가 74.5→74.5 로 **전혀 안 움직인 것**이 이 결함을 실증했다(부록 A-5, 「6. 개선 적용 내역」 참조).

**해법**: F 에 5% 를 배정하고 A~E 를 공표된 값 × 0.95 로 축소했다(A~E 의 상대 비율은 보존). 이제 F1 이 5→0 으로 떨어지면 가중점수가 정확히 5.0 떨어진다 — `scripts/score.py --self-test` 가 이걸 직접 검증한다. 과거 ~200개 보고서(F 제외 방식으로 채점됨)를 검산할 때만 `--legacy-f-excluded` 를 쓴다.

### 5. Windows 콘솔은 cp949

번들 스크립트가 한글을 출력하면 `UnicodeEncodeError` 로 죽는다. `sys.stdout.reconfigure(encoding="utf-8")` 를 첫머리에 넣는다. 파이썬 문자열에 Windows 절대경로를 넣을 때는 `\U` 이스케이프를 조심한다 — raw 문자열을 쓴다.
