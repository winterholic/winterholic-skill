# systematic-debugging 매칭 회귀 시나리오

새 트리거·SKIP 키워드 추가 시 이 표를 검증 anchor로 사용한다. 입력 메시지·맥락 → 기대 결과 매핑.

## 1) True Positive — 정상 발동 (6개)

| # | 입력·맥락 | 기대 동작 | 검증 항목 |
|---|----------|----------|----------|
| 1.1 | "또 401" (직전 턴 401 보고 후) | 발동 → Phase 1 콜스택 추적 | 같은 에러 2회+ |
| 1.2 | "여전히 안 됨" | 발동 → Phase 1 시작 | "여전히" 키워드 |
| 1.3 | "두 번째 시도인데도 똑같아" | 발동 → 4단계 진입 | 명시적 카운트 |
| 1.4 | "왜 그런지 자세히 봐줘" | 발동 (첫 시도여도) | "왜 그런지" 명시 |
| 1.5 | "같은 에러 반복돼" | 발동 | 같은 에러 신호 |
| 1.6 | "이거 root cause 좀 찾아줘" | 발동 (첫 시도여도) | "root cause" 명시 |

## 2) False Positive — 발동하면 안 됨 (2개)

| # | 입력·맥락 | 기대 동작 | 보호 규칙 |
|---|----------|----------|----------|
| 2.1 | 첫 시도 "왜 안 돼 이거" (이전 컨텍스트 없음) | 비활성 → caveman 카테고리(3)가 짧은 답 처리 | 첫 시도 양보 |
| 2.2 | "import 이름 오타 같은데" (1턴 fix 가능) | 비활성 → 즉시 fix | 명백한 typo SKIP |

## 3) Conflict — 다른 스킬과 동시 활성 시 우선순위 (2개)

| # | 맥락 | 기대 동작 | 우선순위 |
|---|------|----------|---------|
| 3.1 | 1차 디버깅 "왜 안 돼" (caveman 카테고리 3 발동) → 2차 "또 안 돼" | 1차: caveman full(짧은 답). 2차: systematic-debugging 인계 (caveman은 강도만 유지) | 1차 caveman / 2차 본 스킬 |
| 3.2 | Phase 4 fix 후 "고쳤어" 주장 | systematic-debugging 종료 + verification-before-completion 발동(회귀 evidence 필수) | 본 스킬 → verification 체이닝 |

## 4) 갱신 시 점검

- 새 트리거 추가 시 1) True Positive 표에 행 1개 이상 추가
- 새 SKIP 추가 시 2) False Positive 표에 행 1개 이상 추가
- caveman과의 경계 룰 변경 시 3.1 행 재검증 필수
