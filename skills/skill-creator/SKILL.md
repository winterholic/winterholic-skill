# Claude Code 최적 스킬 파일 생성기

이 스킬은 Claude Code가 사용자의 요구사항을 분석하여 **구조적으로 완성도 높고, 트리거가 정확하며, 실용적인 SKILL.md 파일**을 만들어내도록 가이드한다.

## 핵심 원칙

스킬 파일은 단순한 프롬프트가 아니다. Claude가 특정 상황에서 **자동으로 불러와 따라야 하는 작업 매뉴얼**이다. 좋은 스킬은 세 가지를 동시에 달성한다:

1. **정확한 트리거링** — 필요할 때 불려오고, 불필요할 때는 무시됨
2. **명확한 실행 지침** — Claude가 읽고 바로 행동할 수 있는 구체적 단계
3. **적정 크기** — 컨텍스트 윈도우를 낭비하지 않으면서 필요한 정보를 모두 담음

---

## 워크플로우

### Phase 1: 요구사항 수집

사용자의 의도를 정확히 파악한다. 아래 질문들을 대화 맥락에서 추출하되, 빠진 부분만 물어본다.

1. **스킬이 해결할 문제** — 이 스킬이 Claude에게 무엇을 하게 만드는가?
2. **트리거 조건** — 어떤 사용자 발화/상황에서 이 스킬이 활성화되어야 하는가?
3. **출력 형태** — 파일? 코드? 텍스트 응답? 어떤 포맷인가?
4. **경계 조건** — 이 스킬이 하지 말아야 할 것은? (유사하지만 다른 스킬과의 구분)
5. **의존성** — 필요한 도구, 라이브러리, 외부 리소스가 있는가?

대화 히스토리에서 이미 답이 나온 항목은 다시 묻지 않는다. 사용자가 "이 워크플로우를 스킬로 만들어줘"라고 한 경우, 앞선 대화에서 도구 사용 패턴, 단계별 순서, 사용자의 수정 사항을 추출한다.

### Phase 2: 스킬 설계

수집한 요구사항을 바탕으로 스킬의 구조를 설계한다.

#### 디렉토리 구조 결정

```
skill-name/
├── SKILL.md          (필수 — 핵심 지침)
├── scripts/          (선택 — 반복 작업용 실행 스크립트)
├── references/       (선택 — 필요시 로드하는 참조 문서)
└── assets/           (선택 — 템플릿, 아이콘, 폰트 등)
```

단순한 스킬은 SKILL.md 하나로 충분하다. 번들 리소스는 아래 경우에만 추가한다:

- **scripts/**: 테스트 케이스마다 동일한 헬퍼 스크립트를 Claude가 직접 작성하게 될 때 → 미리 번들
- **references/**: SKILL.md가 500줄을 넘기게 될 때 → 도메인별로 분리
- **assets/**: 출력에 반복적으로 사용되는 템플릿이나 리소스가 있을 때

#### 3단계 로딩 모델

스킬은 세 단계로 점진적으로 로딩된다. 각 단계의 토큰 예산을 의식하며 설계한다.

| 단계 | 로딩 시점 | 권장 크기 |
|------|-----------|-----------|
| 메타데이터 (name + description) | 항상 컨텍스트에 존재 | ~100단어 |
| SKILL.md 본문 | 스킬 트리거 시 | 500줄 이하 |
| 번들 리소스 | SKILL.md에서 참조 시 | 제한 없음 (필요한 것만 로드) |

### Phase 3: SKILL.md 작성

#### 프론트매터 (YAML)

```yaml
---
name: skill-name
description: "스킬이 하는 일과 트리거 조건을 포함하는 설명. 아래 '트리거 설명 작성법' 참조."
---
```

#### 트리거 설명(description) 작성법

description은 스킬의 생명줄이다. Claude는 이 텍스트만 보고 스킬을 불러올지 결정한다.

**반드시 포함할 내용:**
- 스킬이 하는 일 (What)
- 스킬을 사용해야 하는 구체적 상황 (When) — 사용자가 쓸 법한 키워드와 표현을 나열
- 스킬을 사용하지 말아야 하는 상황 (When NOT) — 유사 스킬과의 경계

**작성 전략:**
- Claude는 스킬을 안 쓰는 쪽으로 편향되어 있으므로, 설명을 약간 "적극적"으로 쓴다
- 예: "대시보드를 만들 때 사용" → "대시보드, 데이터 시각화, 지표 표시, 차트 생성 등 시각적 데이터 표현이 필요한 모든 경우에 이 스킬을 사용하라"
- 부정 조건(Do NOT)도 반드시 명시하여 오발동을 방지

**나쁜 예:**
```
description: "데이터를 포맷팅합니다"
```

**좋은 예:**
```
description: "CSV, JSON, Excel 데이터를 정리·변환·포맷팅할 때 사용. 사용자가 '데이터 정리', 'clean up', '포맷 변환', '열 추가', '필터링' 등을 언급하면 트리거. 단순 읽기나 시각화는 해당하지 않음."
```

#### 본문 작성 원칙

1. **명령형으로 쓴다** — "~하세요" 대신 "~한다", "~하라"
2. **이유를 설명한다** — "ALWAYS"나 "NEVER"를 남발하기보다, 왜 그렇게 해야 하는지 설명하면 Claude가 더 잘 따른다
3. **예시를 포함한다** — 입력/출력 예시는 백 마디 설명보다 효과적

```markdown
## 커밋 메시지 포맷
**예시 1:**
입력: JWT 토큰을 사용한 사용자 인증 추가
출력: feat(auth): JWT 기반 인증 구현
```

4. **출력 포맷을 템플릿으로 제시한다** — Claude가 따라야 할 구조가 있다면 명시

```markdown
## 보고서 구조
아래 템플릿을 따른다:
# [제목]
## 요약
## 주요 발견
## 권고 사항
```

5. **Quick Reference 테이블을 활용한다** — 상황별 분기가 많을 때 표로 정리

```markdown
| 상황 | 접근법 |
|------|--------|
| 새 문서 생성 | docx-js 사용 |
| 기존 문서 편집 | XML 언팩 → 수정 → 리팩 |
| 텍스트 추출 | extract-text 사용 |
```

6. **500줄 한도를 지킨다** — 넘어갈 것 같으면 references/ 폴더로 분리하고 SKILL.md에서 "상세 내용은 `references/advanced.md`를 참조하라"라고 안내

#### 번들 스크립트 판단 기준

테스트 실행에서 Claude가 매번 비슷한 헬퍼 스크립트를 직접 작성한다면, 그 스크립트를 `scripts/`에 번들한다. 판단 기준:

- 3회 이상 유사 패턴 반복 → 번들 대상
- 결정론적이고 반복적인 작업 → 스크립트로
- 판단이 필요한 창의적 작업 → SKILL.md 지침으로

### Phase 4: 검증 및 테스트

스킬 초안 완성 후, 2~3개의 현실적인 테스트 프롬프트를 작성한다.

**좋은 테스트 프롬프트의 특징:**
- 실제 사용자가 입력할 법한 자연스러운 표현
- 적당한 구체성 (파일명, 컬럼명, 상황 설명 포함)
- 엣지 케이스 포함 (애매한 표현, 약어, 오타 등)

**나쁜 예:** `"PDF를 만들어줘"`
**좋은 예:** `"아 보스가 보낸 Q4 매출 데이터 xlsx 있는데 profit margin 컬럼 추가해야 돼. revenue는 C열이고 cost는 D열인 것 같아"`

테스트 프롬프트를 사용자에게 보여주고 확인받은 뒤, 직접 스킬을 적용하여 실행한다. 결과를 사용자에게 공유하고 피드백을 받는다.

### Phase 5: 반복 개선

피드백을 바탕으로 스킬을 개선한다.

**개선 시 핵심 마인드셋:**
- 특정 테스트 케이스에만 맞추는 과적합(overfitting)을 피한다
- 답답한 이슈가 있으면 다른 접근법(메타포, 패턴 변경)을 시도한다
- 불필요한 지침을 제거하여 스킬을 가볍게 유지한다
- 트랜스크립트를 읽고 Claude가 시간을 낭비하는 부분을 파악한다

### Phase 6: 패키징 및 전달

완성된 스킬을 사용자에게 전달한다.

```bash
# 스킬 패키징 (skill-creator의 package_skill.py 사용 가능 시)
python -m scripts.package_skill <path/to/skill-folder>
```

패키징 도구가 없는 환경에서는 스킬 디렉토리를 그대로 전달한다.

## 스킬 품질 체크리스트

스킬을 최종 전달하기 전에 아래 항목을 확인한다:

- [ ] name과 description이 프론트매터에 있는가?
- [ ] description이 What + When + When NOT을 모두 포함하는가?
- [ ] description이 충분히 "적극적"인가? (undertrigger 방지)
- [ ] 본문이 500줄 이하인가? (초과 시 references/로 분리했는가?)
- [ ] 명령형 문체를 사용했는가?
- [ ] 핵심 지침에 이유(why)를 설명했는가?
- [ ] 입출력 예시가 포함되어 있는가?
- [ ] Quick Reference 테이블이 필요한 곳에 있는가?
- [ ] 반복 스크립트를 scripts/에 번들했는가?
- [ ] 테스트 프롬프트로 검증했는가?

## 기존 스킬 개선 시

사용자가 이미 존재하는 스킬의 개선을 요청하면:

1. 원본 스킬의 name을 유지한다 (이름 변경 금지)
2. 읽기 전용 경로의 스킬은 작업 디렉토리에 복사한 뒤 편집한다
3. 변경 전/후를 사용자에게 보여주고 확인받는다
4. description 최적화가 필요하면 트리거 eval 쿼리를 작성하여 테스트한다

---

## 안티패턴 — 이것만은 피하라

### 1. 과도한 제약 (Over-constraining)

**나쁨:**
```markdown
ALWAYS use exactly 3 headers. NEVER use more than 2 bullet points per section.
MUST include a summary. ALWAYS end with "Thank you".
```

대문자 강제어를 남발하면 Claude가 경직되어 상황에 맞는 유연한 판단을 못 한다.

**좋음:**
```markdown
보고서는 명확한 구조를 갖추되, 내용의 복잡도에 따라 섹션 수를 조절한다.
간단한 주제는 2~3개 섹션이면 충분하고, 복잡한 분석은 더 필요할 수 있다.
핵심은 독자가 5초 안에 구조를 파악할 수 있는 것이다.
```

### 2. 모호한 트리거 설명

**나쁨:**
```yaml
description: "코드 관련 작업을 할 때 사용"
```

"코드 관련 작업"은 거의 모든 개발 요청에 해당하므로, 너무 넓거나 오히려 아무 것도 트리거하지 않는다.

**좋음:**
```yaml
description: "Python FastAPI 프로젝트의 REST API 엔드포인트를 생성·수정·테스트할 때 사용. 사용자가 'API 만들어줘', 'endpoint 추가', 'FastAPI 라우터', 'REST API' 등을 언급하면 트리거. Django나 Flask 프로젝트에는 해당하지 않음."
```

### 3. 컨텍스트 낭비

SKILL.md에 모든 프레임워크의 전체 API 문서를 인라인으로 포함하면 안 된다. 핵심 패턴만 SKILL.md에 두고, 프레임워크별 상세 문서는 references/에 분리한다.

```markdown
## React 컴포넌트 생성
기본 패턴은 함수형 컴포넌트 + Hooks를 사용한다.
상세한 Hook 사용법과 패턴은 `references/react-patterns.md`를 참조하라.
```

### 4. 예시 없는 지침

**나쁨:**
```markdown
적절한 형식으로 커밋 메시지를 작성하라.
```

**좋음:**
```markdown
Conventional Commits 형식을 따른다.

**예시:**
- `feat(auth): OAuth2 로그인 구현`
- `fix(cart): 수량 0 이하 입력 시 에러 처리`
- `docs(readme): 설치 가이드 업데이트`
```

## 고급 작성 패턴

### 조건부 분기 패턴

사용자의 입력 유형에 따라 다른 워크플로우를 적용해야 할 때:

```markdown
## 작업 흐름

입력 파일의 유형에 따라 접근법을 선택한다:

| 입력 | 접근법 | 이유 |
|------|--------|------|
| .csv / .tsv | pandas로 직접 처리 | 가볍고 빠름 |
| .xlsx (단순) | openpyxl로 처리 | 서식 보존 필요 |
| .xlsx (복잡, 매크로 포함) | scripts/handle_xlsm.py 사용 | 매크로 안전 처리 |

판단이 어려우면 파일을 열어 첫 10행을 확인한 뒤 결정한다.
```

### 에러 핸들링 패턴

실패 가능성이 있는 작업에 대한 가이드:

```markdown
## 에러 처리

PDF 변환이 실패하면 아래 순서로 대응한다:
1. 파일이 암호화되어 있는지 확인 → `qpdf --check`
2. 파일이 손상되었는지 확인 → `file` 명령으로 타입 검증
3. 위 두 가지가 아니라면 대체 도구(pdftotext → pymupdf 순)로 시도
4. 모든 방법이 실패하면 사용자에게 파일 상태를 보고하고 대안을 제안
```

### 점진적 복잡도 패턴

간단한 요청과 복잡한 요청을 모두 처리해야 할 때:

```markdown
## 처리 전략

**간단한 요청** (단일 파일, 명확한 작업):
바로 실행한다. 확인 불필요.

**중간 복잡도** (여러 파일, 변환 포함):
작업 계획을 한 줄로 요약하고 실행한다.

**높은 복잡도** (다단계, 판단 필요):
작업 계획을 사용자에게 보여주고 확인 후 실행한다.

복잡도 판단 기준: 되돌리기 어려운 작업이 포함되면 한 단계 올린다.
```

### 도메인별 분리 패턴

하나의 스킬이 여러 도메인/프레임워크를 지원할 때:

```
my-skill/
├── SKILL.md              (공통 워크플로우 + 도메인 선택 로직)
└── references/
    ├── react.md           (React 전용 패턴)
    ├── vue.md             (Vue 전용 패턴)
    └── svelte.md          (Svelte 전용 패턴)
```

프레임워크 감지 후 해당 참조 문서만 로드한다:

## 언어 처리

사용자의 언어에 맞춰 스킬을 작성한다. 한국어 사용자에게는 한국어로, 영어 사용자에게는 영어로 스킬을 작성하되, 코드 블록 내의 키워드와 변수명은 영어를 유지한다. description은 사용자가 사용할 언어로 작성하되, 해당 스킬의 대상 사용자층이 다국어인 경우 영어와 한국어를 병기할 수 있다.
