# 스킬 생성·고도화

스킬은 프롬프트가 아니다. Claude 가 **특정 순간에 스스로 열어 따르는 작업 매뉴얼**이다. 그래서 좋은 스킬은 세 가지를 동시에 만족한다.

1. **정확한 트리거링** — 필요할 때 열리고, 아닐 때 침묵한다
2. **명확한 실행 지침** — 읽고 바로 행동할 수 있다
3. **적정 크기** — 상시 비용은 최소, 깊이는 번들에

이 셋 중 **트리거링이 압도적으로 중요하다.** 안 열리는 스킬은 존재하지 않는 것과 같다. 그리고 스킬은 하나의 파일이 아니라 **폴더**다 (Anthropic: *"A skill is a folder, not just a markdown file."*).

## 번들 안내 — 필요할 때만 연다

| 이걸 할 때 | 읽는다 |
|---|---|
| description 을 쓰거나 고칠 때, 트리거가 안 걸릴 때 | `references/description-authoring.md` |
| 초안을 넘기기 전 품질 게이트를 통과시킬 때 | `references/quality-gate.md` |
| 분기·에러·도메인 분리 같은 구조를 짤 때, 안티패턴 확인 | `references/patterns.md` |
| 이 하네스 특유의 함정을 피할 때 (등록·경로·공개 금지) | `references/gotchas.md` |
| 뼈대가 필요할 때 | `assets/SKILL.template.md` 를 복사 |
| 한 벌을 처음부터 끝까지 따라가 보고 싶을 때 | `references/walkthrough.md` |
| 넘기기 직전 기계 검사 | `scripts/check-skill.py` — 명령은 §4 ① |

## Quick Start — 급할 때 이 네 줄

전체 절차는 §1~§6 이다. 시간이 없으면 이 순서만 지킨다. 생략한 단계는 나중에 채우고, **생략했다는 사실을 사용자에게 밝힌다.**

```bash
# 1. 뼈대를 뜬다 (빈 절을 지우지 말고 채운다 — 빈 절이 곧 체크리스트다)
mkdir -p "~/.claude\skills\<이름>"
cp "~/.claude\skills\skill-creator\assets\SKILL.template.md" "~/.claude\skills\<이름>\SKILL.md"

# 2. frontmatter 를 먼저 쓴다 (name = 디렉터리명, description 작성법은 §3)

# 3. 기계 검사 — FAIL 이 하나라도 있으면 넘기지 않는다
python "~/.claude\skills\skill-creator\scripts\check-skill.py" "~/.claude\skills\<이름>"

# 4. skill-list.md 에 행 추가 + 상단 개수 수정 (§6). 이걸 빼면 아무도 안 읽는다
```

의존성은 `python` 하나다. 없으면 §4 의 「거부·불가 시」 표를 따른다.

## 0. 먼저 — 이게 스킬이 맞나

만들기 전에 한 번 묻는다. **"이 규칙이 깨질 수 있는 순간에 이 문서가 컨텍스트에 있는가?"**

| 발동 조건 | 가야 할 곳 |
|---|---|
| 알아볼 수 있는 순간에 발동 | **스킬** (여기) |
| 어떤 턴에서든 발동해야 함 | `CLAUDE.md` |
| 결정론적으로 강제돼야 함 | 훅 |
| 사용자·프로젝트에 대한 사실 | `memory/` |

판단이 서지 않으면 `harness-engineering` 에 넘긴다. 스킬이 아닌 것을 스킬로 만들면 안 읽힌다.

---

## 1. 요구사항 수집

대화 맥락에서 뽑고, **빠진 것만** 묻는다. 이미 답이 나온 항목을 다시 묻지 않는다.

1. **해결할 문제** — 이 스킬이 Claude 에게 무엇을 하게 만드는가
2. **트리거 발화** — 사용자가 **실제로 칠 법한 표현**. 개념어가 아니라 발화다
3. **경계** — 인접한 어떤 스킬과 헷갈릴 수 있는가. 그 스킬 이름을 받아둔다
4. **산출물** — 파일인가 응답인가. 파일이면 위치·이름·덮어쓰기 규칙
5. **의존성** — 필요한 도구·라이브러리. 없으면 없다고 적는다
6. **공개 여부** — 공개 미러로 나가도 되는가 (`references/gotchas.md` §7)

"이 워크플로우를 스킬로 만들어줘"면 앞선 대화에서 도구 사용 패턴·단계 순서·사용자가 고친 지점을 추출한다. **사용자가 고친 지점이 가장 값어치 있다** — 그게 곧 판정 기준이다.

---

## 2. 설계 — 어디에 두고 무엇을 번들할지

### 둘 곳

| 위치 | 상시 비용 | 조건 |
|---|---|---|
| `skills/` | 스킬당 ~100토큰 | 자동으로 트리거돼야 하는 것 |
| `sub-skills/` 등 | 0 | 이름을 알고 부를 때만 쓰는 것 |

`skills/` 직속만 description 이 로드된다. 나머지는 자동 트리거되지 않는다. 상세는 `references/gotchas.md` §3.

### 3단 로딩을 의식하고 쪼갠다

| 단계 | 로드 시점 | 예산 |
|---|---|---|
| frontmatter (name + description) | 매 세션 | **1024자 hard limit**, ~100토큰 |
| SKILL.md 본문 | 트리거 시 | 5k 토큰 이하 |
| 번들 (`references/`·`scripts/`·`assets/`) | 명시적으로 읽을 때만 | 사실상 무제한 |

**본문이 커지면 줄이지 말고 옮긴다.** 한도는 줄 수가 아니라 분량이다. 넘으면 `references/` 로 쪼갠다 — 이 스킬 자신이 그 예다.

번들 판단 기준은 `references/patterns.md` 의 「번들 스크립트 판단 기준」.

---

### 산출물 규칙

- **위치**: 자동 트리거가 필요하면 `~/.claude\skills\<이름>\`, 아니면 `sub-skills\<이름>\`. 프로젝트 전용이면 그 레포의 `.claude\skills\`
- **폴더명**: 소문자 kebab-case. 동사보다 명사구를 쓴다 (`create-skill` 이 아니라 `skill-creator`)
- **필수 파일**: `SKILL.md` 하나. 나머지는 필요할 때만
- **같은 이름이 있으면**: 덮어쓰지 않는다. 고도화면 제자리에서 고치고, 다른 스킬이면 이름을 바꿔 받는다
- **경로 표기**: CLAUDE.md 의 § Output Paths 표를 따른다. **스킬 안에서 새 절대경로를 발명하지 않는다**

## 3. 작성

`assets/SKILL.template.md` 를 복사해서 채운다. 빈 절을 지우지 말고 채운다 — 빈 절이 곧 체크리스트다.

```bash
cp "~/.claude\skills\skill-creator\assets\SKILL.template.md" "<스킬폴더>\SKILL.md"
```

### frontmatter

`name` 은 **디렉터리명과 정확히 같게.** 다르면 두 등록 경로가 서로 다른 이름을 쓴다. 이 하네스에서 실제로 터졌다 (`references/gotchas.md` §1).

`description` 은 스킬의 생명줄이다. What + When(실제 발화) + When-NOT(경계) 4요소를 1024자 안에. 전문은 `references/description-authoring.md`.

### 본문

- **명령형으로 쓴다.** "~하세요"가 아니라 "~한다"
- **이유를 붙인다.** `ALWAYS`·`NEVER` 를 남발하는 것보다 왜 그런지 한 줄이 더 잘 지켜진다. 강제어는 되돌릴 수 없는 것에만
- **예시는 대비 쌍으로.** 좋은 예만 있으면 경계가 안 보인다
- **분기가 둘 이상이면 표로.** 산문으로 늘어놓으면 안 읽힌다

## 4. 게이트 — 넘기기 전 반드시 통과

두 겹이다. 기계가 먼저, 그다음 사람 판단.

### ① 기계 검사

```bash
# 한 개
python "~/.claude\skills\skill-creator\scripts\check-skill.py" "<스킬폴더>"

# 여러 개를 한 번에
python "~/.claude\skills\skill-creator\scripts\check-skill.py" --all "~/.claude\skills"
```

`name` 불일치 · description 1024자 초과 · 앞머리 없음 · 죽은 번들 참조를 FAIL 로 잡는다. **FAIL 이 하나라도 있으면 넘기지 않는다.**

검사기 자체를 의심할 때는 `--self-test` 를 **먼저** 돌린다. 검사기가 실패할 수 있는지부터 확인하고 나서 통과를 믿는다.

```bash
python "~/.claude\skills\skill-creator\scripts\check-skill.py" --self-test
```

정상 입력 통과 + 고의 결함을 이름으로 지목 + 대상 부재를 FAIL 처리, 셋을 확인한다.

### ② 채점에서 반복해 깎이던 다섯 자리

**B3**(판단 불가 4요소) · **C2**(좋음/나쁨 대비 예시) · **C3**(파일명·위치·덮어쓰기) · **D2**(거부·불가 fallback) · **E1**(용어 풀이). 초안이 B 를 못 넘는 이유는 거의 항상 이 다섯이다.

근거와 채우는 법은 `references/quality-gate.md`. **채점 뒤에 고치지 말고 여기서 막는다.**

정식 점수가 필요하면 그다음이 `skills-estimate` 다(14항목 채점 + 약점 Top 3). 산수는 그쪽 번들 스크립트에 맡긴다.

```bash
python "~/.claude\skills\skills-estimate\scripts\score.py" --name <스킬명> --type design --scores A1=4,A2=4,...,F1=4
```

스킬을 **여러 개 만들었으면** 그쪽 `references/batch-evaluation.md` 의 일괄 절차를 쓴다 — 하나씩 채점하면 중간에 기준이 흔들린다.

### ③ Gotchas 절을 비워두더라도 만든다

절이 없으면 다음 세션이 실패 경험을 적을 자리가 없어 그냥 휘발된다.

### ④ 거부·불가 시

게이트를 못 돌리거나 사용자가 거절하는 일이 실제로 생긴다. **"사용자에게 알린다"는 fallback 이 아니다 — 다음 수단을 지목한다.** 어느 경우든 건너뛴 사실은 산출물 안에 남긴다. 말로만 하면 다음 세션이 통과한 줄 안다.

| 상황 | 다음 수단 |
|---|---|
| `python` 이 없어 `check-skill.py` 를 못 돌린다 | `references/quality-gate.md` 의 표를 사람이 눈으로 훑는다. 스킬 안 Gotchas 에 "기계 검사 미실행" 한 줄을 남긴다 |
| 검사기 `--self-test` 가 FAIL | **대상보다 검사기를 먼저 의심한다.** 검사기를 고치기 전에는 그 출력으로 판정하지 않는다 |
| 사용자가 "게이트 건너뛰고 그냥 만들어줘" | 만든다. 대신 §4 ② 다섯 자리(B3·C2·C3·D2·E1) 중 못 채운 것을 스킬 안 Gotchas 에 항목으로 남긴다 |
| 사용자가 fresh 세션 트리거 검증을 거절 | 검증을 생략하고 그 사실을 스킬 안에 적는다. 자동 발동에 목숨이 걸린 스킬이면(§5) 한 번 더 권한다 |
| 사용자가 §6 등록을 나중에 하겠다 | 스킬 폴더는 만들되 "도달 경로 없음 — `skill-list.md` 미등록"을 한 줄로 보고한다. 등록 전까지는 완성으로 말하지 않는다 |
| 인접 스킬과 트리거가 겹치는데 그쪽을 못 고친다(다른 세션이 편집 중 등) | 이쪽 description 에만 경계를 적고, **한쪽만 고쳤다는 사실**을 보고한다. 양쪽이 서로를 지목해야 완성이다 |

## 5. 검증 — 저자가 자기 스킬을 테스트하면 안 된다

**저자의 저주.** 스킬을 쓴 이 세션은 의도를 이미 갖고 있어서, description 이 부실해도 알아서 트리거하고 본문의 모호함을 메워 읽는다. 이 세션의 "잘 되는데요"는 증거가 아니다.

Anthropic 공식 권장은 인스턴스 분리다.

1. **테스트 발화 2~3개를 만든다.** 실제 사용자가 칠 법한 자연스러운 문장으로. 애매한 표현·약어·오타를 하나 섞는다.
   - 나쁨: `"PDF 만들어줘"`
   - 좋음: `"아 보스가 보낸 Q4 매출 xlsx 있는데 profit margin 컬럼 추가해야 돼. revenue가 C열이고 cost는 D열인 것 같아"`
2. **사용자에게 발화를 보여주고 확인받는다.**
3. **fresh 세션에서 그 발화를 넣어 관찰한다.** 사용자가 `/clear` 후 붙여넣거나, 새 세션을 열어 확인한다. 이 세션에서 스스로 흉내 내면 안 된다.
4. **안 걸리면 본문이 아니라 description 을 고친다.** 트리거 실패의 원인은 거의 항상 name/description 이다.
5. 걸렸는데 엉뚱하게 행동하면 그때 본문을 고친다.

fresh 세션 검증이 과한 경우가 있다. 트리거가 자명하고 본문이 짧으면 생략하고 **생략했다는 사실을 밝힌다.** 반대로 자동 발동에 목숨이 걸린 스킬(handoff·verification 류)은 반드시 한다.

---

## 6. 등록 — 여기까지 해야 끝이다

폴더만 만들고 끝내면 아무도 안 읽는다. **도달 경로를 같이 만든다.**

- [ ] `skill-list.md` 에 행 추가. **상단 개수도 같이 고친다**
- [ ] 자동 트리거가 아닌 위치에 뒀다면, CLAUDE.md 나 디스패처 스킬에서 그 스킬로 가는 한 줄을 만든다
- [ ] 트리거 키워드가 겹치는 기존 스킬이 있으면 **양쪽 description 에 서로를 지목**한다. 한쪽만 고치면 반쪽이다
- [ ] 공개 금지 스킬이면 그 사실을 스킬 안과 `skill-list.md` 양쪽에 적는다

---

## 기존 스킬을 고도화할 때

1. **먼저 현재 상태를 잰다.** `check-skill.py` 를 돌리고, 필요하면 `skills-estimate` 로 채점한다. 재기 전에 고치면 무엇이 나아졌는지 말할 수 없다.
2. **`name` 을 바꾸지 않는다.** 이름이 바뀌면 사용자의 호출 습관과 다른 문서의 참조가 전부 깨진다.
3. **규칙 문장을 다시 쓰지 않는다.** 압축·번역은 재작성이고, 재작성은 없던 주장을 만들고 경고를 지운다. 옮길 때는 원문 그대로 옮기고, 번역했다면 원문을 부록으로 남겨 어느 쪽이 정본인지 밝힌다.
4. **본문이 커졌으면 지우지 말고 `references/` 로 옮긴다.**
5. 변경 전후를 사용자에게 보여주고 확인받는다.

---

## 판단이 안 설 때

- **누가**: 사용자에게 묻는다
- **언제**: ①스킬이 맞는 형태인지 자체가 불확실할 때 (그전에 §0 표를 먼저 적용한다) ②트리거 발화를 대화에서 못 뽑았을 때 ③같은 지적을 두 번 고쳤는데 또 나올 때 — 세 번째 문장 수정을 시도하지 말고 묻는다
- **어떻게**: 한 줄 질문 + 후보. 선택지를 늘어놓고 설명하지 않는다
- **기대값**: 한 줄 답. 무응답이면 가장 보수적인 선택으로 진행하고 그 사실을 밝힌다
