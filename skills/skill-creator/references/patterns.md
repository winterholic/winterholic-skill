# 작성 패턴 · 안티패턴

본문에서 옮겨온 것이다. 문장은 원래 것을 그대로 둔다. 트리거될 때만 열리므로 분량 부담이 없다.

---

## 안티패턴 — 이것만은 피하라

### 1. 과도한 제약 (Over-constraining)

**나쁨:**
```markdown
ALWAYS use exactly 3 headers. NEVER use more than 2 bullet points per section.
MUST include a summary. ALWAYS end with "Thank you".
```

대문자 강제어를 남발하면 Claude가 경직되어 상황에 맞는 유연한 판단을 못 한다. Anthropic 이 anti-railroading 으로 지목한 것이 이것이다.

**좋음:**
```markdown
보고서는 명확한 구조를 갖추되, 내용의 복잡도에 따라 섹션 수를 조절한다.
간단한 주제는 2~3개 섹션이면 충분하고, 복잡한 분석은 더 필요할 수 있다.
핵심은 독자가 5초 안에 구조를 파악할 수 있는 것이다.
```

### 2. 모호한 트리거 설명

**나쁨:**
```yaml
description: "코드 관련 작업을 할 때 사용"
```

"코드 관련 작업"은 거의 모든 개발 요청에 해당하므로, 너무 넓거나 오히려 아무 것도 트리거하지 않는다.

**좋음:**
```yaml
description: "Python FastAPI 프로젝트의 REST API 엔드포인트를 생성·수정·테스트할 때 사용. 사용자가 'API 만들어줘', 'endpoint 추가', 'FastAPI 라우터', 'REST API' 등을 언급하면 트리거. Django나 Flask 프로젝트에는 해당하지 않음."
```

### 3. 컨텍스트 낭비

SKILL.md에 모든 프레임워크의 전체 API 문서를 인라인으로 포함하면 안 된다. 핵심 패턴만 SKILL.md에 두고, 프레임워크별 상세 문서는 references/에 분리한다.

### 4. 예시 없는 지침

**나쁨:**
```markdown
적절한 형식으로 커밋 메시지를 작성하라.
```

**좋음:**
```markdown
Conventional Commits 형식을 따른다.

**예시:**
- `feat(auth): OAuth2 로그인 구현`
- `fix(cart): 수량 0 이하 입력 시 에러 처리`
- `docs(readme): 설치 가이드 업데이트`
```

### 5. 죽은 번들 참조

본문에서 `references/advanced.md` 를 읽으라고 지시해 놓고 그 파일을 만들지 않는 것. 스킬을 쪼개다 만 상태에서 자주 난다. `scripts/check-skill.py` 가 `dead-bundle-ref` 로 잡는다.

계획만 적어둘 때는 **읽으라고 지시하지 말고** "앞으로 추가할 것"으로 표시한다.

## 고급 작성 패턴

### 조건부 분기 패턴

사용자의 입력 유형에 따라 다른 워크플로우를 적용해야 할 때:

```markdown
## 작업 흐름

입력 파일의 유형에 따라 접근법을 선택한다:

| 입력 | 접근법 | 이유 |
|------|--------|------|
| .csv / .tsv | pandas로 직접 처리 | 가볍고 빠름 |
| .xlsx (단순) | openpyxl로 처리 | 서식 보존 필요 |
| .xlsx (복잡, 매크로 포함) | 전용 스크립트 사용 | 매크로 안전 처리 |

판단이 어려우면 파일을 열어 첫 10행을 확인한 뒤 결정한다.
```

### 에러 핸들링 패턴

실패 가능성이 있는 작업에 대한 가이드:

```markdown
## 에러 처리

PDF 변환이 실패하면 아래 순서로 대응한다:
1. 파일이 암호화되어 있는지 확인 → `qpdf --check`
2. 파일이 손상되었는지 확인 → `file` 명령으로 타입 검증
3. 위 두 가지가 아니라면 대체 도구(pdftotext → pymupdf 순)로 시도
4. 모든 방법이 실패하면 사용자에게 파일 상태를 보고하고 대안을 제안
```

### 점진적 복잡도 패턴

간단한 요청과 복잡한 요청을 모두 처리해야 할 때:

```markdown
## 처리 전략

**간단한 요청** (단일 파일, 명확한 작업):
바로 실행한다. 확인 불필요.

**중간 복잡도** (여러 파일, 변환 포함):
작업 계획을 한 줄로 요약하고 실행한다.

**높은 복잡도** (다단계, 판단 필요):
작업 계획을 사용자에게 보여주고 확인 후 실행한다.

복잡도 판단 기준: 되돌리기 어려운 작업이 포함되면 한 단계 올린다.
```

### 도메인별 분리 패턴

하나의 스킬이 여러 도메인/프레임워크를 지원할 때, 공통 워크플로우와 도메인 선택 로직만 SKILL.md 에 두고 도메인별 상세는 `references/` 로 쪼갠다.

```markdown
프레임워크 감지 후 해당 참조 문서만 로드한다:
- package.json에 react 의존성 → react 참조 문서
- package.json에 vue 의존성 → vue 참조 문서
- 판단 불가 시 사용자에게 확인
```

### 번들 스크립트 판단 기준

Claude 가 매번 비슷한 헬퍼 스크립트를 직접 작성한다면, 그 스크립트를 `scripts/` 에 번들한다.

- 3회 이상 유사 패턴 반복 → 번들 대상
- 결정론적이고 반복적인 작업 → 스크립트로
- 판단이 필요한 창의적 작업 → SKILL.md 지침으로

번들 스크립트는 **결과만 컨텍스트에 들어온다**. 코드 자체는 안 들어오므로 길이 부담이 없다. 이게 progressive disclosure 3단계의 값어치다.

## 언어 처리

사용자의 언어에 맞춰 스킬을 작성한다. 한국어 사용자에게는 한국어로, 영어 사용자에게는 영어로 스킬을 작성하되, 코드 블록 내의 키워드와 변수명은 영어를 유지한다.

**규칙 문장을 다른 언어로 옮기는 것은 재작성이다.** 판정 기준이 미묘하게 바뀔 수 있으므로, 원문이 있는 규칙을 번역해 실을 때는 원문을 부록으로 함께 두고 어느 쪽이 정본인지 밝힌다.

한국어로 쓸 때는 `skills/new-writer/SKILL.md` 의 사투리 규칙을 따른다. em 대시를 줄이고 문장을 끊는다. 기술 용어는 음차를 유지한다.
