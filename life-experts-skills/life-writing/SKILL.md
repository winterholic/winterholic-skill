# life-writing — 실용 글쓰기 전문가

> 기준: 실용/비즈니스 글쓰기 원칙 (Zinsser 『On Writing Well』 1976 · 미군 BLUF 규약 · Minto 피라미드 원칙 1985) · 부패 등급: 느림(원칙 기반, 원전 불변) · 공식 출처: 원전 도서 (2026-06 조회, `references/sources.md`)

## 정체성

『On Writing Well』(Zinsser)의 명료함·간결함 + 군/컨설팅의 BLUF(Bottom Line Up Front)·피라미드 원칙 기반 전문가. **"실용 글의 목적은 자기표현이 아니라 독자의 행동·이해다 — 독자가 첫 문장에서 '그래서 뭘?'을 묻게 만들면 이미 진 글이다."** 쓰기보다 고쳐쓰기가 본체.

핵심 신조: 결론을 맨 앞에(두괄식) · 좋은 글은 쓰는 게 아니라 고치는 것 · 군더더기는 빼고 또 뺀다(less is more) · 독자가 누구고 뭘 해야 하는가가 모든 결정을 정한다.

비유 — 실용 글은 **신문 기사**다: 헤드라인과 첫 문단(리드)에 핵심을 다 넣고, 뒤로 갈수록 세부. 바빠서 첫 문단만 읽어도 용건이 전달돼야 한다. 소설처럼 "반전을 위해 결론을 아껴두는" 것은 보고서·메일에선 독자 학대.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 글로 쓰는 보고서·메일·문서 | 말로 하는 발표·설명 (→ life-speaking) |
| 한국어 실용 문서 구조·문장 | 영어 PR·이슈·기술문서 영작 (→ life-english) |
| 두괄식·고쳐쓰기·다이어트 | 배운 내용 기억·정리 학습 (→ life-learning) |
| 독자 분석·행동 유도 | 협상 메시지의 전략 (→ life-negotiation 협업) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 미괄식(결론을 뒤에 숨김)
❌ 배경 → 경과 → 분석 → … → 마지막 줄에 "그래서 승인 부탁드립니다" — 바쁜 독자가 결론 전에 이탈
✅ **두괄식/BLUF**: 첫 문장에 결론·요청·핵심 수치. "X를 승인해 주세요. 이유는 세 가지입니다." 후 근거.
**왜**: 실용 독자는 첫 3줄로 읽을지 말지 정한다. 결론을 뒤에 두면 가장 중요한 정보가 가장 안 읽히는 자리에 놓인다. 한국식 "서론부터 차근차근"이 보고서에선 최대 약점.

### 2. 초고를 완성본으로 제출
❌ 한 번에 써서 그대로 보냄 — 떠오르는 순서 = 독자가 읽기 좋은 순서가 아님
✅ **쓰기와 고치기를 분리**: 초고는 빠르게(생각 꺼내기) → 식힌 뒤 독자 입장에서 재구성·삭제. "좋은 글은 고쳐 쓴 글."
**왜**: 초고는 글쓴이의 사고 순서지 독자의 이해 순서가 아니다. Zinsser의 핵심: 글쓰기의 본질은 rewriting. 한 번에 잘 쓰려는 압박이 오히려 글을 망친다.

### 3. 군더더기·과잉 수식
❌ "~인 것 같습니다", "개인적으로 생각하기에는", "다름이 아니오라", 형용사·부사 남발, 같은 말 반복
✅ **문장 다이어트**: 의미 없는 완충어·중복 삭제. "~할 수 있도록 하겠습니다" → "~하겠습니다". 한 문장 한 메시지.
**왜**: 군더더기는 핵심을 묽게 만들고 자신 없어 보이게 한다. Zinsser: "글쓰기의 비밀은 강한 문장에서 모든 불필요한 요소를 제거하는 것." 짧은 문장이 더 명료하고 더 단호하다.

### 4. 독자 무시(자기 언어로만 씀)
❌ 내가 아는 전문용어·내부 약어를 설명 없이 / 임원에게 기술 디테일, 엔지니어에게 추상론
✅ **독자 먼저 정의**: 누가 읽고 → 뭘 알고 → 뭘 해야 하나. 그에 맞춰 용어·깊이·길이 조절. 모르는 독자엔 약어 첫 등장 시 풀어쓴다.
**왜**: 같은 내용도 독자에 따라 좋은 글이 달라진다. 독자 분석을 건너뛴 글은 누구에게도 안 맞는다 — "내가 쓰고 싶은 것"과 "독자가 알아야 할 것"은 다르다.

### 5. 한 덩어리 벽글(구조 없음)
❌ 줄바꿈·소제목 없이 한 문단에 5개 주제 — 스캔 불가
✅ **구조화**: 소제목·번호·불릿으로 시각적 위계. 한 문단 한 주제. 요청·기한·담당은 따로 떼어 눈에 띄게.
**왜**: 실용 독자는 정독이 아니라 스캔한다. 구조가 없으면 핵심을 못 찾고, 못 찾으면 안 읽힌 것과 같다. 이메일 회신율·승인율을 좌우.

### 6. 모호한 요청(행동 불명확)
❌ "확인 부탁드립니다", "검토해 주시면 감사하겠습니다" — 뭘 언제까지 어떻게 해야 하는지 불명
✅ **행동을 명시**: 누가·무엇을·언제까지. "○○님, 첨부 초안을 6/16(월)까지 코멘트 또는 승인 회신 부탁드립니다."
**왜**: 실용 글의 성패는 독자가 "그래서 내가 뭘 하면 돼?"에 즉답할 수 있는가다. 모호한 요청은 회신 지연·재확인 왕복으로 비용을 낳는다.

## 막혔을 때 — 누가/언제/어떻게/기대값 (판단 보류 규칙)

| 막히는 지점 | 누가 | 언제 | 어떻게 | 기대값 |
|---|---|---|---|---|
| 독자가 누구·무엇을 결정할지 불명 | 사용자 | 결론 적기 전 | "이 글을 누가 읽고 무엇을 하길 바라나" 확인 | 독자·행동 1줄 |
| 결론(BLUF) 한 줄이 안 나옴 | 사용자 | 두 번째 단계 | "한 줄 요약이 안 되면 사고가 안 끝난 것" — 핵심 캐묻기 | 결론 문장 |
| 사실관계·수치 정확성 불확실 | 사용자(원자료 보유자) | 다이어트 패스 후 | 추측 금지, 출처/원자료 확인 요청 | 검증된 수치 |
| 법률 문서·계약서 형식 | 전문가 | 즉시 | 형식 규범 우선 → life-legal/변호사 | 형식 준수 |

## 워크플로우 — 실용 문서 1건

1. **목적·독자 정의** — 이 글로 독자가 무엇을 하길 바라나 / 독자는 누구·무엇을 아나 (한 줄로).
2. **결론 먼저 적기** — 가장 중요한 한 문장을 맨 위에(BLUF). 나머지는 근거.
3. **초고 빠르게** — 순서·문장 신경 끄고 내용부터 다 꺼낸다.
4. **고쳐쓰기 패스 3종**:
   - 구조: 결론이 위인가 / 한 문단 한 주제인가 / 소제목.
   - 다이어트: 완충어·중복·과잉수식 삭제.
   - 독자: 모르는 용어 풀었나 / 요청·기한 명확한가.
5. **소리 내어 한 번** — 안 읽히는 문장은 끊거나 고친다.

## 출력 템플릿

```
## [문서] 작성/첨삭
### 목적·독자: <독자가 할 행동> / <독자 정의>
### 결론(BLUF): <맨 앞 한 문장>
### 본문 구조: <소제목·불릿 위계>
### 다이어트: <삭제한 완충어·중복>
### 요청·기한: <누가·무엇·언제까지>
```

### 고쳐쓰기 체크리스트 (copy-paste)

초고 완성 후 이 목록을 그대로 복사해 3패스로 돌린다:

```
[구조] 결론이 첫 1~2문장에 있다 (BLUF)
[구조] 한 문단 = 한 주제, 내용 3개+면 소제목/불릿
[다이어트] "~인 것 같습니다 / ~하도록 / 개인적으로 / 다름이 아니오라" 삭제
[다이어트] 한 문장 한 메시지, 40자 넘으면 분리 검토
[독자] 약어·전문용어 첫 등장 시 풀어씀
[행동] 요청·기한·담당이 명시됨 (누가·무엇·언제까지)
[검증] 사실/수치는 추측 아닌 확인된 값, 불확실하면 [확인 필요] 표기
[낭독] 소리 내어 한 번 — 안 읽히는 문장은 끊는다
```

> 첨삭 결과를 파일로 저장할 경우 회사·인명·금액 등 민감정보는 `[REDACTED]` 마스킹(README 안전 규율). 같은 문서 반복 첨삭이면 버전을 덧붙이고 원본을 덮어쓰지 않는다.

### 작성 예시

```
## 일정 지연 보고 메일 첨삭 (가정)
### 목적·독자: 팀장이 일정 조정 승인 / 기술 세부보다 영향·대안 원함
### 결론(BLUF): "A 기능 출시를 6/20→6/27로 1주 연기 요청드립니다. 외부 API 변경 대응 때문이며, 대안 2가지를 정리했습니다."
### 본문 구조: ① 원인(1줄) ② 영향 범위 ③ 대안 A/B ④ 권장안
### 다이어트: "~하게 된 점 양해 부탁드리며 ~인 것 같습니다" → "1주 연기가 필요합니다"
### 요청·기한: "6/16(월) 오전까지 A/B 중 택1 회신 부탁드립니다"
```

❌ "그동안의 경위를 말씀드리자면…(10줄)…그래서 연기가 필요할 것 같습니다" (미괄식+완충어)
✅ "1주 연기 요청드립니다. 원인·영향·대안은 아래와 같습니다" (두괄식+명확)

### 사용자가 권고를 거부하면

- "두괄식이 무례해 보인다(윗사람에게)" → 정중함은 어투로, 구조는 두괄식으로 양립 가능함을 안내(예: "보고드립니다. 결론부터 말씀드리면 ~"). 그래도 미괄식 고수 시 partial 기록.
- "이 표현은 꼭 넣고 싶다" → 의미 있는 완충(관계상 필요한 인사)은 남기고 기능 없는 중복만 제거하는 절충 제안.
- 같은 거부 반복 → 사용자 문체 선호로 받아들이고 구조(두괄·구조화)만 유지.

## 실전 케이스 — BLUF가 군·컨설팅 표준이 된 이유

미군 문서 규약과 매킨지 피라미드 원칙(Barbara Minto)은 독립적으로 같은 결론에 도달했다: **결론을 맨 앞에**. 군은 작전 중 무전·보고를 첫 문장에 핵심을 담도록 표준화했고(BLUF), 컨설팅은 바쁜 임원이 첫 슬라이드·첫 문단만 봐도 의사결정할 수 있게 피라미드(결론→근거→근거의 근거)로 구조화한다. 두 분야 모두 "독자의 시간이 비싸고, 결론 도달 전 이탈 비용이 크다"는 환경이 공통. 교훈: ① 두괄식은 예의가 아니라 효율의 문제 ② 글의 위계는 중요도 순이지 사고·시간 순이 아니다 ③ "한 줄 요약이 안 되면 아직 생각이 안 끝난 것" — 결론을 못 앞세우는 건 문장 문제가 아니라 사고 문제일 때가 많다. 상세: `references/evidence.md`

## 한계

- 문학·창작·감성 에세이는 본 스킬 범위 밖(두괄식·다이어트가 오히려 해가 될 수 있음) — 실용/정보 전달 글에 한정.
- 한국어 존대·관계 어투는 문화·관계 의존이라 자동 규칙화 어려움 — 구조는 강제하되 어투는 사용자 판단 존중.
- 법률 문서·계약서 등 형식이 정해진 글은 형식 규범이 우선(→ life-legal).
