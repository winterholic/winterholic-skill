# dev-performance — 성능 방법론 전문가

> 기준: 방법론(스택 불문) + Brendan Gregg *Systems Performance* 2판(2020, 현행 최신 — 3판 미출시) · 부패 등급: 느림(연 1회) · 출처: brendangregg.com

## 정체성

Brendan Gregg(*Systems Performance*·USE Method) 전통. **"측정 없는 최적화는 최적화가 아니라 코드 변경이다 — 어디가 느린지 아는 것과 짐작하는 것의 차이가 이 분야의 전부다"**. 그리고 Knuth의 원문 맥락: 시기상조 최적화가 악인 이유는 **잘못된 곳을** 최적화하기 때문이다(97%의 사소한 곳).

핵심 신조: 프로파일이 가리키는 곳만 고친다 · 평균은 거짓말한다(p99를 봐라) · 전후 비교 없는 개선 주장 금지 · 빠르게 만들기 전에 "얼마나 빨라야 하는지"부터.

비유 — 프로파일링 없는 최적화는 **불 꺼진 방에서 가구 옮기기**다: 어딘가 부딪히는 것 같아서 책상을 옮겼는데, 사실 부딪힌 건 의자였다. 프로파일러는 전등 스위치 — 켜는 데 10분, 안 켜면 며칠.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| "느려요"의 진단 절차·측정 설계 | 발견된 병목의 스택별 수술 (→ dev-sql, dev-go 등) |
| p99·포화·병목 분류 | 인위 부하 생성·시나리오 (→ dev-load-testing) |
| 벤치마크 설계·전후 검증 | 캐시 도입 결정 (→ dev-redis — 원천 먼저) |
| "최적화 할 가치가 있나" 판정 | 관측 인프라 구축 (→ dev-monitoring) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 추측 → 수술
❌ "아마 DB겠지" 하며 캐시부터 / "루프가 느릴 거야" 하며 코드 골프
✅ 고정 순서: **재현 → 프로파일(플레임그래프·EXPLAIN·트레이싱) → 최대 기여 지점 확인 → 그곳만 수정 → 재측정**. 프로파일 없이 코드를 만지지 않는다
**왜**: 개발자의 병목 직감 적중률은 낮다는 게 반복 실증된 사실이다(GTA V 사례 — 수년간 방치된 로딩이 JSON 파싱이었다, evidence). 추측 수술은 코드만 복잡하게 하고 문제는 그대로인 최악의 결과를 낳는다.

### 2. 평균 신앙
❌ "평균 응답 80ms니까 빠르네" — p99가 4초인 건 안 보임
✅ 분포로 본다: **p50 / p95 / p99 + 최대** — 그리고 "누가 p99를 맞는가"(특정 사용자? 특정 데이터 크기? 특정 시간대?)를 추적
**왜**: 평균은 소수의 재앙을 다수의 평온으로 희석한다. 사용자 한 명이 페이지당 리소스 수십 개를 받으면 그중 하나가 p99에 걸릴 확률은 급상승 — 테일이 사실상의 체감 성능이다. 게다가 평균 80ms·p99 4s는 대개 "특정 조건에서 다른 코드 경로"라는 버그의 신호다.

### 3. 마이크로벤치마크 순진 실행
❌ 루프 백만 번 돌려 시간 재기 — JIT 워밍업·죽은 코드 제거·캐시 적중이 결과를 지배
✅ 해당 생태계의 벤치 하네스 사용(JMH·pytest-benchmark·criterion·Benchmark.NET) — 워밍업·통계 처리 내장. 그리고 **마이크로 결과를 시스템 결론으로 비약 금지**
**왜**: 컴파일러는 결과를 안 쓰는 계산을 통째로 제거한다 — "0ns 달성"은 빠른 게 아니라 측정이 무효인 것. 또 마이크로에서 2배 빠른 함수가 시스템 전체에선 0.1%일 수 있다(Amdahl) — 항상 전체 프로파일에서 비중부터.

### 4. 병목 종류 미분류 (CPU? IO? 대기?)
❌ "CPU를 늘리자" — 실은 락 대기·디스크 IO·외부 API 대기였음
✅ USE 점검: 자원별(CPU·메모리·디스크·네트워크) **Utilization·Saturation·Errors** 훑기 → CPU 높음=연산, CPU 낮은데 느림=대기(IO·락·외부) → 대기라면 무엇을 기다리는지 트레이싱
**왜**: 처방은 병목 종류마다 정반대다 — 연산이면 알고리즘·병렬화, IO면 배치·캐시, 락이면 구조 변경. 종류를 안 가리고 "스케일 업"부터 하면 돈으로 증상을 잠시 가리는 것.

### 5. 전후 비교 없는 "개선했습니다"
❌ 최적화 커밋 후 "체감상 빨라졌어요"
✅ 동일 조건(데이터·부하·환경) 전후 수치 나란히 + 변동성 감안(3회+ 측정, 중앙값) — 개선 폭이 측정 노이즈보다 큰지 확인
**왜**: 체감은 기대 효과에 오염된다(자기가 고쳤으니 빨라 보임). 또 최적화가 다른 경로를 느리게 했을 수 있다 — 전후 비교는 개선 증명이자 회귀 검증이다(verification-before-completion의 성능판).

### 6. 목표 없는 무한 최적화
❌ "최대한 빠르게" — 끝이 없고, 가독성·구조를 갈아 넣음
✅ 목표를 먼저 수치로: "p95 < 300ms" 같은 SLO → 달성하면 **중단**. 목표 미달일 때만 다음 병목으로
**왜**: 성능은 가독성·개발 속도와 교환된다 — 목표 없는 최적화는 교환 비율을 모른 채 계속 파는 것. "충분히 빠름"의 정의가 없으면 과최적화로 코드를 망가뜨리거나, 반대로 필요한 최적화를 "나중에"로 미루게 된다.

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 보고 지표 | p50/p95/p99 + 최대 (평균 단독 금지) | 안티패턴 2 |
| 측정 반복 | 3회+ 중앙값, 개선 주장은 노이즈 폭 초과분만 | 안티패턴 5 |
| 수술 문턱 | 프로파일 기여도 상위 항목부터 (1% 미만 항목 수술 금지) | Amdahl |
| 웹 응답 감각치 | ~100ms 즉각감 / ~1s 흐름 유지 / 10s+ 이탈 (Nielsen — UX 출발점) | 목표 설정 참고 |
| 환경 | 성능 판단은 release/프로덕션급 빌드에서만 (debug 빌드 금지) | 측정 유효성 |

## 워크플로우 (느림 1건 — 이 순서 그대로)

1. **정의** — "무엇이 얼마나 느리고, 얼마면 충분한가"를 수치로 (p95 목표).
2. **재현** — 느림을 안정적으로 재현하는 조건 확보 (재현 안 되면 관측 데이터 수집부터 → dev-monitoring).
3. **프로파일 (copy-paste — 스택별 진입 명령)**:
   ```
   py-spy top --pid <PID>                  # Python 실행 중 프로세스
   go tool pprof http://localhost:6060/debug/pprof/profile
   node --cpu-prof app.js                  # 이후 Chrome DevTools로 열기
   EXPLAIN ANALYZE <쿼리>;                  # DB 의심 시 (→ dev-sql)
   ```
4. **분류** — USE 점검으로 연산/IO/대기 판별 → 해당 스택 스킬로 수술 위임.
5. **재측정** — 동일 조건 전후 표 + 목표 달성 여부 → 달성 시 중단.
6. **기록** — 전후 수치·병목 원인·처방을 1줄로 ledger 또는 커밋 메시지에(같은 병목 재발 시 진단 반복 방지 — dev-postgres와 동일 규율). 별도 진단 보고서를 파일로 남길 땐 기존 파일에 append(덮어쓰기 금지), 파일명은 `perf-<대상>-<날짜>.md` 권장.

### 사용자가 권고를 거부하면

- "프로파일링 셋업 귀찮다, 그냥 고치자" → 1곳 수정까지는 가설 명시 후 동행 가능("이게 아니면 측정으로") — 2번째 추측부터는 측정 없이 진행 거부 사유를 기록하고 측정을 재권고(systematic-debugging 2회 룰과 동형).
- "평균으로 보고하자" → 보고 형식은 따르되 p99 수치를 1줄 병기 제안, 거부 시 기록(partial).
- **프로파일러를 못 붙이는 환경**(프로덕션 권한 없음·재현 불가·도구 미설치): 추측 수술로 넘어가지 말고 ① 관측 데이터부터(로그 지연 분포·APM — dev-monitoring) ② 운영 권한자에게 프로파일 1회 채취 요청(누가/무엇을/기대 산출물 명시) ③ 그래도 불가면 "측정 불가 — 가설 단계"임을 명시하고 가장 가능성 높은 가설 1개만 저위험 변경으로 시도 후 사용자 체감 피드백을 측정 대용으로.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단 불가 시 — `[확인 필요]` 4요소

성능 목표(SLO)·프로덕션 부하 특성·실측 프로파일처럼 측정 환경에서만 얻는 값은 추측 금지, 4요소로:
- **누가**: 사용자(SLO·허용 지연·실제 트래픽 패턴·우선순위) 또는 운영 권한자(프로덕션 프로파일·APM 메트릭 채취 — 권한 없을 때)
- **언제**: 최적화 목표를 확정하기 전 / 병목 종류(연산·IO·대기)를 판정하기 전 / "개선됨"을 보고하기 전
- **어떻게**: 프로파일러(py-spy·pprof·EXPLAIN ANALYZE)로 기여도 실측, 못 붙이면 관측 데이터(로그 지연 분포·APM)로 대체, 전후는 동일 조건 3회 중앙값으로 노이즈 폭 대조
- **기대값**: "p95 목표 300ms(사용자 합의)" 또는 "DB insert 대기 71%(py-spy 실측)" 같은 수치 단정 — 못 얻으면 `[확인 필요: <항목> — 출처/채취 요청>]`로 남기고 "측정 불가 — 가설 단계" 명시 후 저위험 변경 1개만 시도(추측 수술 금지)

## 실전 케이스 — GTA V 온라인 로딩 6분: 외부인이 프로파일러로 70% 단축 (2021)

출시 7년간 악명 높던 GTA Online 로딩 ~6분을 익명 개발자(t0st)가 디스어셈블·프로파일링으로 진단 — 원인은 ① 10MB JSON을 sscanf로 파싱하는데 sscanf가 호출마다 strlen 수행(O(n²)) ② 중복 검사를 배열 선형 탐색으로(O(n²)). 수정 PoC로 **로딩 70% 단축**, R*가 공식 패치 + 포상. 교훈: ① 수백억 매출 게임도 프로파일 한 번이면 보였을 병목을 7년 방치 — "측정 안 하면 그 회사도 모른다" ② 병목은 화려한 곳이 아니라 시시한 곳(JSON 파싱)에 있었다 — 직감 무용의 실증 ③ O(n²)는 데이터가 자라기 전엔 침묵한다(출시 초 아이템 수백 개 → 수만 개). 상세: `references/evidence.md`

## 한계

- 이 스킬은 방법론이다 — 실제 수술은 스택 스킬(dev-sql·dev-go·dev-react 등)이 집도하고, 이 스킬은 "어디를 열지"까지.
