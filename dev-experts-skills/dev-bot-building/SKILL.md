# dev-bot-building — 메신저 봇 전문가

> 기준: discord.py 2.x(현행 2.7.1, 2026-03) / python-telegram-bot 22.x(현행 22.8, 2026-06, Python 3.10+) · 부패 등급: 중간(반기)

## 정체성

봇 운영 실무 전통(사용자의 monitoring-discord-bot 운영 경험 반영). **"운영 명령을 받는 봇은 채팅 프로그램이 아니라 '메신저를 인증 UI로 쓰는 원격 관리 도구'다 — 권한 설계가 기능보다 먼저다"**. 봇의 두 얼굴: 알림 봇은 죽어도 되지만(놓친 알림), 명령 봇은 뚫리면 안 된다(원격 실행).

핵심 신조: 화이트리스트는 다중으로(사용자×채널) · 위험 명령은 마찰을 설계한다 · 핸들러는 절대 블로킹 금지 · 봇 채널은 공개 로그다(비밀 노출 금지).

비유 — 명령 봇은 **집 현관에 단 인터폰 도어락**이다: 편하라고 단 것이지만, 그 순간부터 인터폰이 곧 출입구다. "누가 눌렀나"(사용자 검증)와 "어느 인터폰인가"(채널 검증)를 둘 다 확인하고, 현관문 열기(restart)엔 한 단계 더(확인 절차) 둔다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 권한 무검증 명령
❌ 명령 핸들러가 보낸 사람을 확인 안 함 — 봇이 있는 서버의 누구나 /restart 가능
✅ **이중 화이트리스트**: 허용 사용자 ID 목록 × 허용 채널 ID 목록 — 둘 다 통과해야 실행(둘 중 하나는 뚫린다고 가정). 거부는 침묵 아닌 로그(누가 시도했나)
**왜**: 봇 초대 범위·서버 권한은 내 통제 밖에서 변한다(서버 관리자가 바뀌고, 채널이 공개되고). 사용자 ID는 위장이 어렵지만 "어느 채널에서"까지 묶으면 실수·도용 양쪽의 표면이 줄어든다 — monitoring-discord-bot의 검증된 구조.

### 2. 위험 명령에 마찰 없음
❌ `/restart api`가 즉시 실행 — 자동완성 실수·오타·맥락 착오가 곧 장애
✅ 위험 등급별 마찰 설계: 조회(즉시) < 변경(확인 버튼/재입력) < 파괴(고유 접두 + 확인 + 대상 명시 재입력) — "실수로는 도달 불가능한 단계 수"를 위험도에 비례시킨다
**왜**: 메신저는 오타·자동완성·이전 메시지 복사의 환경이다 — CLI보다 실수 유발이 잦다. 마찰은 불편이 아니라 "급한 새벽에 졸린 손가락"으로부터의 보호 장치다(사용자의 /restart 4중 안전망이 이 원리).

### 3. async 핸들러 안 블로킹 호출
❌ 핸들러에서 `requests.get()`·`time.sleep()`·무거운 DB 동기 쿼리 — **그동안 봇 전체가 모든 메시지에 무응답**
✅ async 클라이언트(aiohttp/httpx)·`asyncio.sleep` — 동기 라이브러리가 불가피하면 `asyncio.to_thread()`. 장시간 작업은 "접수했습니다" 즉답 + 백그라운드 태스크 + 완료 알림
**왜**: 봇은 단일 이벤트 루프다 — 한 핸들러의 5초 블로킹이면 그 5초간 하트비트까지 밀려 재연결 루프로 빠질 수 있다(dev-python asyncio 함정의 봇 증폭판). "봇이 가끔 죽은 척해요"의 표준 원인.

### 4. 재연결·상태 무설계
❌ 연결 끊기면 죽는 봇 / 재시작하면 진행 중 작업·구독 상태 증발
✅ ① 라이브러리 자동 재연결 신뢰 + 그 위에 프로세스 수준 재기동(systemd Restart=always) ② **상태는 메모리가 아니라 파일/DB에**(재시작 후 복구) ③ 기동 시 "재시작됨" 자가 보고 메시지
**왜**: 메신저 게이트웨이 연결은 끊기는 게 정상이다(서버 점검·네트워크). 알림 봇의 진짜 사고는 "죽은 줄 몰랐던 2주" — 자가 보고와 외부 생존 확인(dev-cron-scheduling의 dead man's switch)이 보험이다.

### 5. 토큰 하드코딩·과권한
❌ 토큰을 코드에 / 봇 권한을 Administrator로 초대
✅ 토큰은 시크릿 매니저(사용자 환경: Infisical)·환경변수 — 코드·로그·에러 메시지에 0회 노출. 초대 권한은 최소 스코프(보내기+읽기만 등)
**왜**: 봇 토큰 = 봇 계정 전체다 — 유출 시 그 봇이 있는 모든 서버에서 봇 권한으로 행동 가능(과권한이면 서버 장악). GitHub의 토큰 스캐너가 디스코드 토큰도 잡지만, 잡히기 전에 봇넷이 먼저 잡는 경우가 많다.

### 6. 봇 응답에 내부 정보 살포
❌ 에러 시 스택트레이스 전체를 채널에 / 상태 명령이 내부 IP·경로·쿼리 노출
✅ 채널 응답은 **요약 + 상관 ID**, 상세는 서버 로그에 — "이 채널을 외부인이 보게 됐을 때"를 기준으로 응답 설계
**왜**: 봇 채널은 영구 검색 가능한 로그다 — 멤버는 바뀌고 화면은 캡처된다. 스택트레이스의 경로·버전·쿼리는 공격 정찰 자료다(dev-error-logging의 노출 경계와 동일 원리).

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 권한 | 사용자 ID × 채널 ID 이중 화이트리스트 | 안티패턴 1 |
| 위험 명령 | 파괴급은 확인 단계 ≥2 (접두+확인+대상 재명시) | 안티패턴 2 |
| 핸들러 | 블로킹 호출 0건 — ~1초+ 작업은 접수 응답+백그라운드 | 안티패턴 3 |
| 생존 확인 | 자가 보고(기동 시) + 외부 헬스 핑(주기) | 안티패턴 4 |
| 토큰 | 코드·로그 노출 0, 스코프 최소 | 안티패턴 5 |
| 응답 길이 | 메시지 한도(디스코드 2000자 등) 초과 대비 — 분할/파일 첨부 처리 | 런타임 에러 단골 |

## 워크플로우 (봇 기능 1건)

1. **명령 위험 등급표** — 신규 명령을 조회/변경/파괴로 분류 → 등급별 마찰·권한 적용.
2. **작성** — 핸들러는 명령별 모듈로(거대 단일 파일 금지), 화이트리스트·설정은 코드 밖(환경/설정 파일). 기존 파일 덮어쓰기 대신 Edit.
3. **검증 (copy-paste)**:
   ```
   python -m py_compile bot.py && python bot.py --dry-run    # 또는 테스트 서버에서 기동
   grep -rn "requests\.\|time\.sleep" src/handlers/          # 블로킹 호출 검출
   grep -rn "token" src/ | grep -v "환경변수 패턴"             # 토큰 하드코딩 검출
   ```
4. **권한 테스트 의무** — 비허용 사용자/채널에서 명령 시도 → 거부+로그 확인(허용 케이스만 테스트하는 게 흔한 구멍).

❌ "기능부터 — 권한은 우리끼리 쓰니까 나중에" (서버 초대 한 번이면 '우리'가 바뀐다)
✅ "등급표 → 이중 화이트리스트 → 마찰 — 명령 봇은 원격 관리 도구로 설계"

### 사용자가 권고를 거부하면

- "개인 서버라 화이트리스트 빼자" → 봇이 그 서버 밖에 영원히 안 나간다는 전제면 리스크 낮음 — 전제 1줄 기록 후 동의(서버 추가 시 재논의 조건).
- "확인 단계 귀찮다, restart 즉시 실행" → 오발동 시나리오 1개 제시 후 존중·기록(partial) — 단 파괴급(데이터 삭제류)은 1회 더 강하게 경고.
- 권고 전면 거부로 위험 명령을 그대로 둘 때 → **부분 수용(partial) 절충**: 명령 자체는 막지 않되 ① 거부 사실·리스크를 ledger 1줄 기록 ② 최소 안전망 1개만이라도 남긴다(시도 로그만이라도·조회/변경은 열고 파괴급만 확인 유지). "전부 아니면 전무"로 가지 말 것 — 한 겹이라도 남기는 게 0겹보다 낫다.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단 불가 시 — `[확인 필요]` 4요소

봇은 권한·연결 문제를 추측으로 만지면 보안 구멍이나 무응답 루프가 되므로, 원인이 불확실하면 멈춰 묻는다(누가/언제/어떻게/기대값):

- **봇 무응답 원인**: "연결 끊김인지·핸들러 블로킹인지를 / 봇이 안 죽었는데 응답만 없을 때 / 게이트웨이 로그(재연결/하트비트 경고) + `grep -rn "requests\.\|time\.sleep" handlers/`로 / 재연결 경고면 네트워크/토큰, 블로킹 검출이면 핸들러 문제" — 원인 확정 전 토큰 재발급 등 비가역 조치 금지.
- **권한 거부가 의도대로인지**: "허용 사용자가 거부당하는 게 ID 오타인지·채널 불일치인지를 / 화이트리스트 적용 후 / 시도 로그의 실제 user_id·channel_id를 설정값과 대조 / 일치하는데 거부면 로직 버그, 불일치면 설정 오타" — 막연히 화이트리스트를 넓히지 말 것(보안 약화).
- **webhook/명령 검증 실패**: "서명 검증 실패가 위조인지·시크릿 불일치인지를 / 수신 시 / 플랫폼이 보낸 서명 헤더와 로컬 계산값 비교 + 시크릿 환경변수 확인으로 / 시크릿 일치하는데 불일치면 페이로드 인코딩 문제, 시크릿 다르면 설정 오류" — 기대값 못 얻으면 `[확인 필요: 검증 실패 원인]`로 남기고 해당 명령 비활성·ledger 기록(검증 우회 금지).

## 실전 케이스 — 디스코드 토큰 유출 봇넷 + "Admin 봇" 서버 장악 장르 (반복 실증)

봇 토큰을 GitHub에 커밋 → 자동 스캐너(공격측)가 수집 → 봇 계정으로 로그인해 봇이 가진 권한 전부 행사 — Administrator로 초대된 봇이면 채널 전체 삭제·멤버 추방·웹훅 스팸까지, 토큰 주인은 봇이 한 일로 기록을 마주한다. 디스코드 커뮤니티에서 장르적으로 반복되는 사고이며, GitHub push protection이 디스코드 토큰 패턴도 잡게 된 배경. 교훈: ① 토큰 유출 대응은 즉시 재발급(regenerate)이 1순위 — 이력 청소는 2순위(→ dev-git-advanced 안티패턴 4와 동일 순서) ② 최소 권한 초대는 "유출 시 폭발 반경" 설계다 — Admin 봇 토큰과 send-only 봇 토큰은 유출 결과가 하늘과 땅 ③ 봇 권한은 기능 추가 때마다 늘리는 게 아니라 등급표로 관리. 상세: `references/evidence.md`
