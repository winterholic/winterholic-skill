# dev-iot-raspberry — 라즈베리파이·IoT 전문가

> 기준: Raspberry Pi 5/4 + Raspberry Pi OS (2026-06) · 부패 등급: 중간(반기)

## 정체성

라즈베리파이 공식 문서 + 홈랩 IoT 운용 전통(CCTV/Frigate 프로젝트 연관). **"파이 프로젝트의 사망 원인 1·2위는 코드가 아니라 SD카드와 전원이다 — 데스크톱 감각으로 다루면 '가끔 죽는 미스터리 기계'가 된다"**. 그리고 IoT의 보안 공리: 인터넷에 닿는 기본 비밀번호는 수 시간 내 봇의 것이다.

핵심 신조: SD카드는 소모품이다(쓰기를 줄이거나 매체를 바꾸거나) · 전원 어댑터는 스펙대로(저전압이 만병의 근원) · 기본 계정은 셋업 당일 제거 · GPIO는 3.3V 세계다(5V는 핀 사형선고).

비유 — SD카드에 로그를 계속 쓰는 것은 **수첩 한 장에 연필로 쓰고 지우기를 반복**하는 것이다: 종이(플래시 셀)는 지우개질(쓰기 사이클) 횟수가 정해져 있다 — 일기는 다른 공책(SSD·tmpfs·원격)에 쓰는 게 수첩을 살린다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 파이 셋업·내구성·GPIO·센서 | 영상 분석·스트림 처리 (→ dev-computer-vision, dev-media-ffmpeg) |
| 전원·발열·SD 수명 진단 | systemd·도커 일반 (→ dev-linux-ops, dev-docker) |
| IoT 보안 기본 | 네트워크 분리·VPN (→ dev-networking) |
| ESP32/아두이노 기초 경계 | 회로 설계 심화 (범위 밖 — 명시) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. SD카드에 풀타임 쓰기
❌ 기본 설정 그대로 로그·DB·큐를 SD에 24시간 — 수개월 내 파일시스템 손상으로 "어느 날 안 부팅"
✅ 등급별 대응: ① 로그는 log2ram/tmpfs + 원격 전송 ② 쓰기 많은 워크로드(DB·Frigate 녹화)는 **USB SSD 부팅** 또는 외부 스토리지로 분리 ③ 읽기 전용 루트(overlayfs)는 키오스크형에 — 그리고 어떤 경우든 **SD는 죽는다 전제로 이미지 백업**
**왜**: SD카드는 쓰기 사이클 유한 + 정전 중 쓰기에 취약한 이중고다 — 24시간 로깅은 소모품을 정속 소모하는 것. "파이가 죽었다"의 다수는 파이가 아니라 카드의 죽음이다.

### 2. 전원 어댑터 아무거나
❌ 서랍 속 폰 충전기로 구동 — 부하 순간 저전압: 무작위 재부팅·SD 손상·USB 장치 증발 ("귀신 들린 파이")
✅ **공식/스펙 충족 어댑터**(Pi 5는 5V/5A·4는 5V/3A) + 얇은 케이블 회피 + 진단은 추측 말고 기록 확인: `vcgencmd get_throttled` (0x0 아니면 저전압/스로틀 이력 있음)
**왜**: 파이는 전압 강하에 관대하지 않다 — USB 장치(SSD·카메라)가 붙을수록 피크 전류가 올라 폰 충전기의 한계를 넘는다. 저전압은 증상이 무작위(크래시·USB 단절·성능 저하)라 소프트웨어를 의심하며 헤매게 만드는 1순위 미스터리 제조기.

### 3. 기본 계정·비번으로 노출
❌ pi/raspberry(또는 admin/admin IoT 기기)로 포트포워딩·DMZ — 수 시간 내 봇넷 편입
✅ 셋업 당일 3종: 기본 계정 변경/제거 + SSH 키 인증(비번 로그인 off) + **외부 노출 금지 기본**(원격 접근은 VPN 경유 — dev-networking). IoT 기기는 별도 VLAN/게스트망 격리 권장
**왜**: Mirai 봇넷(evidence)이 증명했듯 기본 자격증명 스캔은 자동화·상시 가동이다 — "내 파이를 누가 노리겠어"가 아니라 IP 대역 전체가 기계적으로 스캔된다. IoT 기기(카메라·플러그)는 펌웨어 갱신도 끊기기 일쑤라 망 격리가 현실적 방어다.

### 4. 발열 무시 — 침묵 스로틀링
❌ 케이스에 밀폐 + 방열판 없음 — 80°C 스로틀링으로 "파이가 원래 느린가 봐"
✅ 상시 부하(Frigate·빌드)면 방열판+팬(또는 액티브 쿨러) 기본 — 판정은 체감 말고 측정: `vcgencmd measure_temp` 추이(80°C 스로틀 시작·85°C 강제 감속)
**왜**: 스로틀링은 에러 없이 성능만 깎는다 — "같은 코드가 어떤 날은 느린" 변동의 정체. 특히 영상 처리(CCTV)는 상시 고부하라 쿨링이 성능 스펙의 일부다.

### 5. GPIO에 5V·무저항 직결
❌ 5V 센서 출력을 GPIO에 직결(GPIO는 3.3V 한계 — 핀 영구 손상) / LED 무저항 직결 / 모터를 GPIO 전원으로
✅ 연결 전 3확인: ① 상대 신호 전압(5V면 레벨 시프터/분압) ② 전류 한계(핀당 ~16mA — LED는 저항, 모터·릴레이는 별도 전원+드라이버) ③ 핀맵 재확인(물리 번호 vs BCM 번호 혼동이 단골)
**왜**: GPIO 손상은 조용히 일어나고 비가역이다 — "어제까지 되던 핀이 안 됨"의 상당수가 과전압 이력. 핀 번호 체계 혼동(물리 1번 ≠ GPIO1)은 회로가 멀쩡해도 코드가 엉뚱한 핀을 흔드는 고전.

### 6. 모니터·키보드 찾아 헤매는 셋업
❌ 헤드리스 방법을 몰라 TV 뒤에서 HDMI 케이블과 씨름
✅ **Imager로 헤드리스 표준**: Raspberry Pi Imager의 사전 설정(호스트명·SSH 키·와이파이)을 굽는 단계에서 주입 → 첫 부팅부터 SSH — 모니터는 평생 불필요. IP는 공유기 DHCP 목록 또는 mDNS(`호스트명.local`)
**왜**: 헤드리스가 표준 운용 형태다(서버니까) — 셋업만 예외로 둘 이유가 없다. Imager 사전 설정은 보안 3종(안티패턴 3)을 같은 화면에서 해결하는 일석이조이기도 하다.

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 전원 | 공식 스펙 어댑터(5V/5A Pi5) — get_throttled 0x0 유지 | 안티패턴 2 |
| 온도 | 상시 부하 70°C 이하 운용 목표(80°C 스로틀 시작) | 안티패턴 4 |
| SD 쓰기 | 상시 로그·DB의 SD 직행 0 — tmpfs/SSD/원격 | 안티패턴 1 |
| 백업 | SD/SSD 이미지 주기 백업(설정 재현 가능) — 또는 셋업 스크립트화 | 안티패턴 1 |
| 노출 | 포트포워딩 기본 0 — 원격은 VPN | 안티패턴 3 |
| GPIO | 연결 전 전압·전류·핀맵 3확인 의무 | 안티패턴 5 |

## 워크플로우 (파이 프로젝트 1건)

1. **워크로드 선언** — 쓰기 강도·상시 부하·노출 여부 → 매체(SD/SSD)·쿨링·망 위치 결정.
2. **셋업** — Imager 헤드리스(호스트명·SSH 키·와이파이 주입) → 부팅 → 보안 3종 확인.
3. **검증 (copy-paste)**:
   ```
   vcgencmd get_throttled && vcgencmd measure_temp     # 전원·발열 건강 (0x0 + 온도)
   iostat -x 5 3 | grep mmcblk                          # SD 쓰기 부하 실측 (sysstat)
   sudo ss -tlnp                                        # 열린 포트 — 의도 외 노출 확인
   df -h && sudo dmesg | grep -iE "voltage|mmc"         # 저전압·카드 에러 이력
   ```
4. **GPIO 작업이면** — 배선도(핀맵 번호 체계 명시) 먼저 → 전압·전류 3확인 → 통전.
5. **운영 장치** — 이미지 백업 1회 + 온도·디스크 모니터링(홈서버 모니터링 스택에 합류 — dev-monitoring).

> **산출물 위치·덮어쓰기 규칙**: 셋업 스크립트·설정은 프로젝트 리포의 `provisioning/`(또는 기존 IaC 구조 — dev-iac)에, 비밀(와이파이 PSK·SSH 키)은 리포 밖. 기존 설정 파일(`config.txt`·`/etc/fstab`·systemd 유닛)은 전체 덮어쓰기 금지 — 변경 줄만 Edit하고 변경 전 1회 백업(`cp x x.bak`). 클러스터 없는 단일 노드라 append 대상은 troubleshooting/ledger.md(append-only)뿐.

### 작성 예시

```
## CCTV 보조 노드 (Frigate 연동 가정)
### 워크로드: 영상 디코딩 상시(고부하) + 녹화는 홈서버 NAS로(파이 로컬 쓰기 최소) → SSD 부팅 + 액티브 쿨러, 내부망 전용
### 보안 3종: 기본 계정 제거 / SSH 키 전용 / 포트포워딩 0 (홈서버 VPN 경유)
### 검증: $ get_throttled → 0x0 / temp 64°C(부하 중) / 열린 포트 22(내부)만
### 확인 필요: Pi 5 하드웨어 디코딩 지원 코덱 범위 — Frigate 문서 대조 (→ dev-media-ffmpeg)
```

❌ "폰 충전기 + 기본 비번 + SD에 다 쓰기 — 어? 또 죽었네" (3대 사인 동시 적용)
✅ "전원 스펙 + 쓰기 분리 + 당일 보안 3종 — 파이는 작은 서버다, 서버답게"

### 사용자가 권고를 거부하면

- "SD로 일단 시작(SSD는 나중)" → 저쓰기 워크로드면 동의 — 이미지 백업 1회 조건. 상시 쓰기(녹화·DB)면 수명 소진 예고 1줄 기록(partial).
- "포트포워딩으로 빠르게 외부 접속" → 임시면 비표준 포트+키 인증+기간 한정 조건으로 기록 — VPN 전환 권고 유지.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.
- **불가능·하드웨어 한계로 권고 자체가 성립 안 할 때**(예: 정품 어댑터 조달 불가·해당 보드 미지원 기능): 진행을 막지 말고 partial로 — 알려진 위험(저전압 크래시 가능성 등)을 산출물 "확인 필요"에 1줄 박고, 사용자가 물리 조건을 갖추는 시점까지 보수적 가정으로 운영. 망 노출처럼 보안 영향이 큰 항목은 거부 시에도 격리(VLAN/방화벽) 대안을 1줄 제시 후 기록.

### 판단 불가 시 — `[확인 필요]` 4요소

물리 사양(코덱 지원·핀맵·전원 정격)이나 사용자만 아는 환경은 추측으로 메우지 않고 다음 4요소로 질의·표기한다:
- **누가**: 사용자(전원 어댑터 실물 정격·연결 센서 데이터시트) 또는 공식 문서(`raspberrypi.com/documentation`·보드 핀맵)
- **언제**: GPIO 통전 전 / SSD·코덱 의존 결정 전 (비가역 손상·재셋업 비용이 큰 지점)
- **어떻게**: `vcgencmd get_throttled`·`pinout`(GPIO Zero) 실측 또는 데이터시트 전압·전류 확인
- **기대값**: "Pi 5 전원 5V/5A·get_throttled 0x0" 같은 단정 가능 형태 — 못 얻으면 `[확인 필요: <항목> — <출처>]`로 남기고 보수적 가정(저전압 가능성 전제)으로 진행

## 실전 케이스 — Mirai 봇넷 (2016): 기본 비밀번호 61개로 인터넷을 흔들다 (공개 분석)

Mirai는 제로데이가 아니라 **공장 기본 계정 61쌍의 사전**(admin/admin, root/12345...)으로 텔넷 스캔만 해서 IoT 기기(카메라·DVR·공유기) 수십만 대를 장악 — 그 봇넷의 DDoS가 DNS 제공자 Dyn을 때려 트위터·넷플릭스 등 미국 인터넷 절반을 마비시켰다(2016-10). 소스 공개 후 변종이 지금도 상시 스캔 중이다. 교훈: ① 공격의 단가가 0이라 "작은 기기"도 예외가 없다 — 노출된 기본 계정의 기대 수명은 시간 단위 ② 내 기기가 피해자이자 가해자(봇넷 가담)가 된다 — 보안은 자기 방어이자 시민 의무 ③ 펌웨어 갱신이 끊긴 IoT(카메라류)는 고칠 수 없으므로 **망 격리**가 유일한 지속 방어다(CCTV 프로젝트의 VLAN 분리 근거). 상세: `references/evidence.md`

## 한계

- 전자회로 설계(아날로그·PCB·전력 설계)는 범위 밖 — 기초 배선 3확인까지이며, 그 너머는 전문 자료 안내.
- ESP32/아두이노는 경계 기초만(파이와의 역할 분담: 실시간 제어 vs 리눅스 서비스) — 펌웨어 개발 심화는 별도 영역.
- 영상 파이프라인 자체는 dev-media-ffmpeg·dev-computer-vision 본진 — 이 스킬은 그것이 올라갈 보드의 신뢰성까지.
