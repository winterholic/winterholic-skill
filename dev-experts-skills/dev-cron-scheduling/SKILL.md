# dev-cron-scheduling — 스케줄링 전문가

> 기준: APScheduler 3.x / cron / systemd timer (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

스케줄 운영 실무 전통(사용자의 sample-service collector APScheduler 경험 반영). **"스케줄 작업의 3대 사고는 '두 번 돌았다'(중복), '안 돌았다'(누락), '안 도는 걸 몰랐다'(침묵) — 스케줄 설계란 이 셋의 정책을 작업마다 명시하는 일이다"**. 시각 표현은 부차적이고, 실패 모드 설계가 본체다.

핵심 신조: 모든 작업에 중복·누락·침묵 3정책 명시 · 타임존은 항상 명시(기본값 신뢰 금지) · 성공 신호를 밖으로(없으면 죽은 것) · 작업은 멱등하게(스케줄러의 보험).

비유 — dead man's switch는 **기차 기관사의 생존 페달**이다: "문제가 생기면 알려줘"가 아니라 "**아무 말 없으면 문제다**"로 뒤집는 것. 침묵 실패는 알림을 만들 수 없으니, 침묵 자체를 알림으로 만든다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 중복 실행 무방비
❌ 5분 주기 작업이 가끔 6분 걸림 — 이전 실행이 끝나기 전 다음 시작, 같은 데이터 이중 처리
✅ ① APScheduler: `max_instances=1` + coalesce ② cron: flock(`flock -n /tmp/job.lock cmd`) ③ 분산 환경: DB 락/리스 — 그리고 **작업 자체를 멱등하게**(중복돼도 결과 동일)가 최종 보험
**왜**: 실행 시간은 데이터와 함께 자란다 — "5분이면 충분"은 언젠가 거짓이 된다. 중복 실행은 이중 집계·이중 발송·경합 손상으로 나타나고, 멱등 없는 중복 방지는 한 겹뿐인 방어다(락도 깨진다).

### 2. 누락 정책 미정 (misfire·catchup)
❌ 서버 점검으로 새벽 배치 시간대를 지나침 — 그날 데이터가 영구 공백, 아무도 결정한 적 없는 "스킵" 정책
✅ 작업마다 누락 시 행동을 **명시 선언**: 스킵 가능(다음 주기로) / 따라잡기(미실행분 순차 실행 — APScheduler misfire_grace_time·coalesce 설정) / 수동 백필(실행 인자로 날짜 받는 구조 — 백필 가능 설계)
**왜**: cron은 꺼진 동안의 일정을 기억하지 않는다(anacron·systemd Persistent=true는 기억). "누락되면 어떻게?"에 답이 없는 작업은 누락을 사고가 아니라 미스터리로 만든다 — 수집기의 하루 공백이 한 달 뒤 분석에서 발견되는 경로.

### 3. 타임존 암묵
❌ 서버는 UTC, 코드는 KST 가정 — "자정 배치"가 오전 9시에 돌고, 날짜 경계 집계가 어긋남
✅ 스케줄 정의에 타임존 명시(`CronTrigger(hour=0, timezone="Asia/Seoul")` / systemd timer는 서버 TZ 확인) + **날짜 파라미터는 작업이 계산하지 말고 스케줄 계층이 주입**
**왜**: "어느 자정인가"는 환경마다 다르다 — 컨테이너는 거의 UTC다. 한국은 DST가 없어 한 번 맞추면 안정적이지만, 해외 거래소 시간(미장 서머타임)을 다루는 순간 타임존 버그가 연 2회 정기 발생한다(주식 수집기의 실전 함정).

### 4. 침묵 실패 — 성공 신호 없음
❌ cron 실패 메일은 아무도 안 봄 / "에러 알림"만 설계 — 프로세스가 아예 안 돌면 에러도 없다
✅ **dead man's switch**: 작업 성공 끝에 외부 헬스 엔드포인트 핑(healthchecks.io류·자체 호스팅 가능) — 기한 내 핑 없으면 그쪽이 알림. 에러 알림과 생존 확인은 별개 채널
**왜**: 가장 흔한 스케줄 사고는 에러가 아니라 **무실행**이다(crontab 오타·서버 교체 누락·가상환경 경로 변경·권한). 무실행은 로그도 에러도 없다 — GitLab 2017의 백업 5중 침묵 실패가 이 부류의 정점(evidence).

### 5. crontab 한 줄에 로직 욱여넣기
❌ `0 3 * * * cd /app && source venv/bin/activate && python x.py >> log 2>&1 || curl ...` — 환경 의존 덩어리
✅ crontab은 **스크립트 호출 1줄만** — 환경 설정·로깅·핑·에러 처리는 래퍼 스크립트에(버전 관리 대상). 신규 작업은 가능하면 systemd timer(로그 journal 통합·Persistent 옵션·의존성)로
**왜**: cron의 실행 환경은 셸 로그인과 다르다(PATH 최소·환경변수 없음) — "터미널에선 되는데 cron에선 안 돼요"의 원인. 한 줄 덩어리는 디버깅·수정·리뷰 전부를 막는다.

### 6. 전부 자정 몰림
❌ 모든 배치가 0 0 * * * — 자정에 CPU·DB·외부 API가 동시 폭주, 서로 간섭
✅ 작업별 시간대 분산(+ 분 단위 오프셋) + 의존 관계 있으면 시각이 아니라 **선행 완료 신호로 체이닝**(파일 마커·다음 작업이 선행 검증) — "3시면 끝나겠지"는 체이닝이 아니다
**왜**: 시각 기반 암묵 의존은 선행 지연 시 연쇄 오작동한다(미완료 데이터로 후속 집계). 동시 폭주는 평소엔 버티다 데이터 증가로 어느 날 임계 초과 — 분산은 공짜 보험이다.

## 워크플로우 (스케줄 작업 1건)

1. **3정책 표 작성** — 이 작업의 중복/누락/침묵 답을 먼저 정한다(코드보다 먼저).
2. **도구 선택** — 앱 내장 주기(APScheduler — 앱과 수명 공유) / OS 수준(systemd timer 우선, cron 차선) / 분산·재시도 요구는 큐(→ dev-messaging-queue)로 승격.
3. **작성** — 래퍼 스크립트는 레포 `scripts/`(버전 관리), crontab/timer 정의도 파일로 레포에(서버 수동 편집만으로 끝내지 않기). 기존 파일 덮어쓰기 대신 Edit.
4. **검증 (copy-paste)**:
   ```
   python job.py --date 2026-06-10        # 백필 인자 + 멱등 확인(2회 실행 결과 동일)
   flock -n /tmp/job.lock echo ok          # 락 동작 확인 (Linux)
   systemctl list-timers                   # timer 등록·다음 실행 확인
   curl -fsS https://hc-ping.com/<uuid>    # dead man's switch 핑 경로 확인
   ```
5. **첫 운영 1주** — 실행 시간 추이 기록(주기 대비 여유율) — 80% 도달 전에 주기·구조 재검토.

### 사용자가 권고를 거부하면

- "개인 프로젝트에 헬스 핑까지는 과하다" → 작업 실패의 발견 지연 비용이 낮으면(재실행 쉬움) 동의가 맞다 — 핵심 데이터 수집만은 권고 유지, 거부 시 기록(partial).
- "cron이 익숙하니 systemd timer 안 쓴다" → 정당(도구 숙련 > 도구 우열) — flock+래퍼 규율만 유지 조건으로 동의.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단이 막히면 (확인 필요 4요소)

3정책(중복·누락·침묵)의 답은 작업의 업무 의미에 달려 있어 코드만으로 정할 수 없다 — 막히면 4요소로 질의한다: **누가**(이 작업 누락/중복의 영향 범위를 아는 사람 = 사용자/도메인) / **언제**(스케줄 정의 전 — 사후 누락 정책은 이미 빈 데이터를 만든 뒤) / **어떻게**(예: "이 배치를 하루 거르면 그날 데이터를 백필해야 하나, 스킵해도 되나") / **기대값**(그 답이 misfire 정책·백필 인자 설계·핑 기한을 가른다). 확인 불가 시 대체 경로: 가장 안전한 기본값(멱등 + max_instances=1 + dead man's switch + 백필 인자 지원)으로 설계해 어느 정책이든 사후 수용 가능하게 두고 "확인 필요 — 누락 정책 미확정" 기록.

## 실전 케이스 — GitLab (2017): 백업 5중 체계가 전부 침묵 실패 중이었다 (공식 포스트모템)

GitLab.com 엔지니어가 운영 DB를 실수로 삭제(rm -rf — 피로 속 호스트 착오)했을 때 드러난 진짜 공포는 삭제가 아니라 복구였다 — **5가지 백업 메커니즘이 전부 작동하지 않는 상태**였다: 정기 pg_dump는 버전 불일치로 빈 산출물(에러는 아무에게도 안 감), S3 업로드는 비어 있었고, 디스크 스냅샷·복제도 각각 구멍. 결국 우연히 6시간 전 수동 스냅샷으로 복구(6시간 데이터 유실). 교훈: ① 백업·배치의 "성공 로그"가 아니라 **산출물 검증 + 침묵 감지**가 신뢰의 단위(pg_dump가 돌았다 ≠ 덤프가 쓸 만하다) ② 알림은 실패 시가 아니라 "성공 신호 부재 시" 울려야 한다(dead man's switch) ③ 복구 리허설 없는 백업은 백업이 아니라 희망이다(→ dev-backup-dr). 상세: `references/evidence.md`
