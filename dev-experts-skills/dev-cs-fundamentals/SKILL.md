# dev-cs-fundamentals — CS 기초·OS 원리 전문가

> 기준: 원리(리눅스 중심, OS 불문 공통) (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

*OSTEP*(Three Easy Pieces)·실무 진단 전통. **"OS 수준 미스터리의 대부분은 OS가 이상한 게 아니라, 개발자의 멘탈 모델이 OS의 실제 계약과 다른 것이다 — '썼으면 저장됐겠지', 'free 했으면 줄겠지'가 대표적 오계약"**. 이 스킬은 그 계약서를 바로잡는다.

핵심 신조: 추상화는 새지 않을 때까지만 공짜다 · 쓰기와 내구성은 별개 계약 · 한도(fd·디스크·메모리)는 전부 유한하고 침묵으로 다가온다 · 종료 신호 처리는 기능이다.

비유 — 파일 쓰기는 **우체통 투함**이다: write()는 우체통에 넣은 것(페이지 캐시)이지 상대에게 도착(디스크 내구화)한 게 아니다 — 수거차(플러시)는 주기적으로 오고, fsync는 "지금 수거해서 도착 확인서 줘"다. 정전은 수거 전 우체통을 태운다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. "free 했는데 메모리가 안 줄어요"
❌ 언어에서 객체 해제 후 OS 메모리 지표가 그대로인 걸 누수로 단정 / 반대로 진짜 누수를 "원래 그런가" 방치
✅ 계층 구분: 언어 힙 해제 ≠ 할당자가 OS 반환(보통 보유) ≠ RSS 감소 — **추세로 판단**(부하 일정한데 단조 증가 = 누수 의심, 계단 후 평형 = 정상 보유). 도구: 언어 힙 프로파일러가 1차, OS 지표는 2차
**왜**: malloc/free 위에 할당자(재사용 풀)가 있고 그 위에 언어 GC가 있다 — 각 층이 반환을 미루는 게 정상 설계다. 층을 모르면 정상을 누수로(헛수고) 누수를 정상으로(장애) 오판한다.

### 2. 쓰기 = 저장 가정 (fsync 무지)
❌ `write()` 반환 = 디스크에 있다고 가정 — 정전·크래시에 "분명 저장했는데" 유실
✅ 내구성 계약 명시: write는 페이지 캐시까지 — **내구성 필요 지점만 fsync**(파일+디렉토리 엔트리). 단 일반 앱은 DB·파일시스템에 위임이 정답(DB의 커밋이 fsync 계약을 대행) — 직접 파일로 중요 데이터를 다룰 때만 이 계약을 직접 진다
**왜**: OS는 성능을 위해 쓰기를 모아 미룬다(수 초~수십 초) — 그 창에서의 전원 단절이 유실 창이다. PostgreSQL조차 fsync 에러 처리의 오계약으로 유실 가능성이 드러났던 게 fsyncgate(evidence) — 계약서를 읽는 자만 데이터를 지킨다.

### 3. SIGKILL과 SIGTERM 구분 없는 종료
❌ 종료 처리 없는 프로세스 — 배포·재시작마다 쓰다 만 파일·미완 트랜잭션·정리 안 된 락
✅ **SIGTERM 핸들러 = 기능**: 신규 수락 중단 → 진행 중 마무리(시한 내) → 자원 정리 → 종료. SIGKILL은 잡을 수 없음을 전제(핸들러가 영원히 안 끝나면 결국 KILL — 시한 설계)
**왜**: systemd·Docker·K8s 전부 [TERM → 유예(기본 10~30s) → KILL] 절차다 — TERM을 무시하는 프로세스는 매 배포가 강제 종료다. "재시작 후 가끔 데이터 깨짐"의 표준 원인(dev-docker·dev-linux-ops의 우아한 종료가 이 원리).

### 4. fd·리소스 한도 무지
❌ `Too many open files` 에러에 ulimit만 올림 — 누수(닫지 않은 파일·소켓·커넥션)는 그대로
✅ 순서: **누수 먼저 의심** — `ls /proc/<pid>/fd | wc -l` 추이 관찰(단조 증가 = 누수) → 원인 수색(닫기 누락·커넥션 풀 미반환) → 한도 상향은 실수요 입증 후
**왜**: fd는 파일만이 아니다 — 소켓·파이프·epoll 전부. 한도 상향은 누수의 발현 시점만 미루는 진통제이고, 누수 fd는 상대 소켓·디스크 공간(삭제됐지만 열린 파일)까지 물고 있다.

### 5. 디스크 풀의 두 얼굴 (용량 vs inode, 그리고 열린 파일)
❌ `No space left on device`에 df는 여유 — 패닉 / 큰 파일 지웠는데 용량 안 돌아옴 — 미스터리
✅ 진단 3종: `df -h`(용량) + `df -i`(**inode** — 작은 파일 수백만이 범인) + `lsof +L1`(삭제됐지만 열린 파일 — 프로세스가 잡고 있어 공간 미반환, 로그 파일 단골)
**왜**: "디스크 풀"은 세 가지 다른 병의 같은 증상이다 — 용량·inode·열린 핸들. 분기표 없이 큰 파일 사냥만 하면 두 경우를 영원히 못 푼다. 로그를 rm 했는데 공간이 안 돌아오는 건 버그가 아니라 유닉스 파일 수명 규칙(링크 수 + 열린 fd)이다.

### 6. 프로세스/스레드 모델 혼동
❌ "스레드 하나 죽어도 나머지는 살겠지"(같은 주소 공간 — 하나의 segfault가 프로세스 전체 사망) / 멀티프로세스에서 전역 변수 공유 기대
✅ 계약 암기: **스레드 = 메모리 공유·운명 공동체** / **프로세스 = 격리·통신은 명시적**(IPC) — 격리가 필요하면 프로세스, 공유가 필요하면 스레드+동기화(→ dev-concurrency)
**왜**: 이 한 줄 모델이 수많은 설계 오판을 가른다 — 워커 격리 요구에 스레드를 쓰면 한 워커의 크래시가 전체를 죽이고, 프로세스 풀에서 캐시 공유를 기대하면 N배 메모리에 갱신 불일치까지 얻는다(Python multiprocessing의 고전 혼란).

## 워크플로우 (OS 미스터리 진단 1건)

1. **증상 → 분기표** — 메모리(1)·유실(2)·종료 후 깨짐(3)·fd(4)·디스크(5)·크래시 전파(6) 중 어느 부류인지 먼저.
2. **계약 확인** — 해당 안티패턴의 실제 OS 계약을 읽고, 현재 코드의 가정과 대조.
3. **진단 (copy-paste)**:
   ```
   cat /proc/<pid>/status | grep -i vmrss        # 프로세스 실메모리
   ls /proc/<pid>/fd | wc -l                      # fd 수 (추이로)
   df -h; df -i                                   # 용량 + inode
   lsof +L1 | head                                # 삭제됐지만 열린 파일
   kill -TERM <pid> && sleep 5 && ps -p <pid>     # TERM 핸들러 동작 확인
   ```
4. **수정은 해당 계층으로** — 언어 누수(언어 스킬)·운영 설정(dev-linux-ops)·설계(이 스킬이 원리 제공) 위임을 명시.

### 진단이 막히면 ([확인 필요] 4요소)

원리 진단은 OS 지표·코드 가정이 둘 다 불명일 때 멈춘다. 추측으로 처방하지 말고 다음 4요소로 질의한다:
- **누가**: 해당 프로세스를 운영·배포하는 사람(1인이면 본인) — `/proc/<pid>` 접근 권한 보유자.
- **언제**: 안티패턴 분기는 됐으나 계약 대조에 필요한 런타임 값(언어·할당자·플랫폼 유예 시한)이 안 잡힐 때.
- **어떻게**: "증상=X, 의심 안티패턴=N, 확인에 필요한 값=<예: 단조 증가 추세 N시간 / lsof +L1 결과 / 플랫폼 종료 유예값>" 형식으로.
- **기대값**: 그 값으로 처방 계층(언어 누수 → 언어 스킬 / 운영 설정 → dev-linux-ops / 설계 → 이 스킬)이 갈린다. 값 없이 계층을 못 정하면 진단 보류가 정답.

## 실전 케이스 — PostgreSQL fsyncgate (2018): 20년 된 DB도 OS 계약을 오독했다 (공개 분석)

PostgreSQL 커뮤니티가 발견한 충격적 사실 — 리눅스에서 fsync가 실패하면 **커널이 더티 페이지를 '깨끗함'으로 표시해버려, 재시도 fsync가 성공을 반환**할 수 있다(이미 유실된 데이터인데). PG는 fsync 실패 시 재시도하는 설계였어서, 특정 IO 에러 상황에서 유실을 정상 커밋으로 오인할 가능성이 20년간 존재했다 — 수정은 "fsync 실패 = 즉시 PANIC(재시작·WAL 복구)"으로의 전환. 교훈: ① OS 계약은 매뉴얼 페이지가 아니라 구현 동작까지가 계약이다 — 최고 수준 프로젝트도 오독했다 ② 내구성 코드는 "에러 시 어떻게"가 본체(성공 경로는 누구나 쓴다) ③ 일반 앱의 결론: 내구성은 검증된 계층(DB)에 위임하라 — 직접 지는 건 이 늪에 직접 들어가는 것. 상세: `references/evidence.md`
