# dev-api-integration evidence — 장애·실증 사례

## 1. AWS DynamoDB (2015-09-20) — 재시도 폭풍과 준안정 실패 (공식 포스트모템)

- **체인**: 네트워크 이슈로 메타데이터 응답 지연 → 스토리지 노드 멤버십 확인 타임아웃 → 노드들이 스스로를 제외하고 재시도 → 메타데이터 서비스 과부하 심화 → 용량을 늘려도 재시도 파도가 흡수 — 약 5시간, us-east-1의 DynamoDB 의존 서비스 연쇄.
- **개념화**: 이후 학계가 "metastable failure"로 정식화 — 트리거가 사라져도 시스템이 스스로(재시도·캐시 미스 폭주) 장애 상태를 유지하는 부류. 복구의 적이 원인이 아니라 증폭 루프인 경우다.
- **실무 도출**: ① 재시도 총량에 시스템 수준 상한(개별 3회가 아니라 "전체 재시도 예산") ② 백오프 상한을 길게(복구 여유) + 지터 의무 ③ 부하 차단(load shedding)을 복구 도구로 — 일부러 일부를 거절해야 전체가 산다.

## 2. 웹훅 위조·중복 — "결제 완료 이벤트를 누구나 보낼 수 있었다" (보안 점검 단골)

- **무슨 일**: 서명 검증 없는 웹훅 엔드포인트가 침투 테스트·버그바운티의 단골 적발 항목 — 공격자가 `{"event": "payment.completed", "order": "..."}` 위조 POST로 미결제 주문을 완료 처리시키는 시나리오. 실제 커머스 사고 사례 보고 반복.
- **중복 쪽 사고**: 처리 지연 → 제공자 재발송 → 같은 이벤트 2~3회 도착 → 포인트 적립·알림이 중복 — "가끔 두 번 적립돼요"의 표준 원인. 제공자 문서는 모두 "중복 가능"을 명시하는데 수신측이 안 읽는다.
- **수신 표준형**: `검증(HMAC) → 이벤트ID 기록(유니크 — 있으면 200 후 무시) → 큐 적재 → 즉시 200` — 4단계가 위조·중복·재발송 가중을 한 번에 해소. 처리 실패는 큐의 재시도/DLQ 소관(→ dev-messaging-queue).

## 3. "200인데 에러" API 장르 — 상태 코드의 거짓말 (연동 실무 집적)

- **무슨 일**: 적지 않은 API(특히 국내 금융·공공·레거시 연동계)가 HTTP는 항상 200, 성공/실패는 바디의 자체 코드로 — HTTP 계층만 보는 모니터링·재시도 로직이 전부 헛돈다. 거꾸로 5xx를 정상 흐름에 쓰는 API도 실재.
- **방어**: ① 계약서 읽기 단계에서 "에러 표현 방식"을 1급 항목으로(이 스킬 워크플로우 1의 6항에 포함) ② 성공 판정 함수를 래퍼에 1곳(HTTP 코드 + 바디 코드 합성) — 호출부가 각자 판정하게 두지 않기 ③ 모니터링도 합성 판정 기준으로(HTTP 200 비율은 무의미해질 수 있다).
- **교훈**: REST 관례는 관례일 뿐 계약이 아니다 — 상대의 실제 동작이 계약이고, 그것을 코드 한 곳에 번역해 가두는 게 연동의 기술이다.

## 4. 표준 근거 — 429·Retry-After·백오프+지터 (1차 스펙/공식 가이드)

- **HTTP 429 + Retry-After**: 429 "Too Many Requests"는 RFC 6585(2012-04)에서 정식 정의됐고, Retry-After 헤더(초 또는 HTTP-date)로 재시도 시점을 알린다 — 안티패턴 6·2의 "Retry-After 존중"의 표준 근거. 헤더는 선택적이므로 미제공 시 백오프 폴백 필수.
- **백오프 + 지터 + 토큰 버킷**: AWS Builders' Library가 "동기화된 재시도가 상관(correlation)으로 상대를 다시 눕힌다 → 지터로 분산"을 1차로 설명하고, AWS SDK는 2016년부터 토큰 버킷으로 재시도 폭주를 억제(안티패턴 2·정량표·SKILL #137 "SDK 내장 정책 먼저"의 근거). 단, AWS는 서킷브레이커에 대해 "테스트 어려운 모달 동작·복구 지연 유발" 주의도 명시 — 안티패턴 4의 "라이브러리 사용·대체 동작 필수"와 결이 같다.
