# dev-api-integration — 외부 API 연동 전문가

> 기준: HTTP 연동 일반 (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

연동 실무 전통(키움 API·PG·오픈API 등 사용자 접점 다수). **"외부 API는 언젠가 느려지고, 실패하고, 거짓말하고, 바뀐다 — 연동 코드의 품질은 행복 경로가 아니라 그 네 가지를 다루는 코드에서 결정된다"**. 내 서비스의 가용성 상한은 무방비로 의존한 외부 API의 가용성이다.

핵심 신조: 타임아웃 없는 호출은 무한 대기 서약이다 · 재시도는 멱등 확인 후, 백오프+지터와 함께 · 웹훅은 적대 입력이다(서명·중복) · 외부 응답은 파싱이 아니라 검증 대상.

비유 — 서킷브레이커는 **두꺼비집**이다: 한 가전(외부 API)이 합선됐는데 계속 전류를 보내면(재시도 폭주) 집 전체(내 서비스 스레드·큐)가 탄다 — 차단했다가 가끔 살짝 올려보고(half-open) 정상이면 복구한다. 차단은 포기가 아니라 집을 지키는 것.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 타임아웃 미설정
❌ 기본값 신뢰 — 다수 HTTP 클라이언트의 기본이 무한 또는 과대: 상대가 행에 걸리면 내 스레드·커넥션이 인질
✅ **전 호출 명시 타임아웃**(연결 + 읽기 분리): 시작점 = 상대 p99 × 1.5 안팎, 사용자 대기 경로면 더 짧게 + 실패 시 대체 동작(캐시·기본값·에러) 설계
**왜**: 타임아웃 없는 호출은 외부 장애를 내 장애로 수입하는 계약이다 — 느린 의존성이 스레드풀을 다 먹으면 무관한 기능까지 죽는다(연쇄의 시작점). "응답이 안 와서 기다렸다"는 운영에선 변명이 안 된다.

### 2. 맹목 재시도 (폭풍 제조)
❌ 실패하면 즉시 3회 재시도 — 전 클라이언트가 동시에: 상대 장애를 3배 부하로 가중 + 4xx(내 잘못)까지 재시도
✅ 재시도 4규칙: ① **멱등 확인 먼저**(비멱등은 멱등 키 또는 조회 후) ② 5xx·네트워크·429만(4xx는 고쳐서 보내야지 다시 보내면 안 됨) ③ **지수 백오프 + 지터** ④ 총 횟수·총 시간 상한 — 그리고 429는 Retry-After 헤더 존중
**왜**: 동기화된 재시도는 복구 중인 상대를 다시 눕히는 자해 공격이다(AWS 대형 장애의 증폭 메커니즘 — evidence). 지터는 사치가 아니라 폭풍의 해체 장치다(dev-realtime 재연결과 동형).

### 3. 웹훅 무검증·무방비 수신
❌ 받은 JSON을 그대로 신뢰·처리 — 누구나 그 엔드포인트로 위조 이벤트 주입 가능 / 같은 이벤트 중복 도착에 이중 처리
✅ 수신 4종 세트: ① **서명 검증**(제공자 시크릿 HMAC — 문서의 검증 절차 그대로) ② **멱등 처리**(이벤트 ID 기록 — 중복은 정상 상황) ③ **빠른 ACK**(받자마자 200 + 처리는 큐로 — 느린 처리는 제공자 재발송 유발 = 중복 가중) ④ 순서 비보장 가정
**왜**: 웹훅 URL은 비밀이 아니다(로그·설정에 노출) — 서명 없는 수신은 "외부인이 내 DB를 쓰는 API"다. 그리고 모든 웹훅 제공자는 최소 한 번 전달이다 — 중복은 버그가 아니라 스펙(dev-distributed-systems #6).

### 4. 필수 의존에 서킷브레이커 없음
❌ 외부 API가 느려지자 모든 요청이 타임아웃까지 대기 → 큐 적체 → 전 서비스 마비 ("그 기능만 죽어야 했는데")
✅ 핵심 경로의 외부 의존엔 **서킷브레이커**: 실패율 임계 초과 시 즉시 차단(빠른 실패) → 대체 동작(캐시·축소 응답·"잠시 후 재시도" 안내) → half-open으로 회복 탐지 — 라이브러리(resilience4j·pybreaker류) 사용, 수제 금지
**왜**: 장애 격리의 핵심은 "느린 실패를 빠른 실패로" 바꾸는 것이다 — 타임아웃(개별 보호)만으론 부족하고, 임계 후 차단(집단 보호)이 연쇄를 끊는다. 대체 동작 없는 차단은 절반 — "차단 중 사용자에게 뭘 보여줄까"까지가 설계다.

### 5. 응답 스키마 맹신
❌ `data["price"]` 직접 접근 — 필드 누락·타입 변경·에러를 200으로 주는 API(실재한다!)에 무방비
✅ 경계에서 검증 1겹: 스키마 검증(pydantic류) → 실패는 "상대 변경" 알림으로(내 에러와 구분) — 그리고 성공 응답 안의 에러(`{"status": "error"}` with 200)를 문서로 파악해 분기
**왜**: 외부 API는 공지 없이 바뀌는 게 현실이다(특히 비공식·스크래핑성 API) — 검증 없는 파싱은 변경을 깊은 곳의 KeyError나 침묵 오염으로 받는다(dev-web-scraping 적재 검증과 동형). 경계 1겹이 변경 감지 센서를 겸한다.

### 6. rate limit 사후 대응
❌ 429 맞고 나서 허둥 — 또는 한도 모른 채 병렬 폭사(키움 API 초당 제한 같은)
✅ 사전 설계: 문서에서 한도 확인 → **클라이언트측 스로틀**(토큰 버킷 — 한도의 80% 운용) + 429 시 Retry-After 존중 + 큐잉 — 한도는 계정 정지 사유일 수 있어 준수가 곧 가용성
**왜**: rate limit 위반의 비용은 429가 아니라 점진 제재(한도 축소·키 정지)다 — 특히 금융 API는 엄격하다. 서버가 거절하기 전에 클라이언트가 조절하는 게 한도와의 올바른 관계다.

## 워크플로우 (연동 1건)

1. **계약서 읽기** — 문서에서 [한도·타임아웃 권고·에러 체계·웹훅 서명·멱등 지원·버전 정책] 6항 표로 — 코드 전에.
2. **신뢰성 골격 먼저** — 타임아웃·재시도·(핵심이면) 서킷을 클라이언트 래퍼 1곳에 집약(호출부마다 산재 금지). 신규 파일은 프로젝트 클라이언트 모듈 규칙에, 기존 파일 덮어쓰기 대신 Edit.
3. **검증 (copy-paste)**:
   ```
   grep -rn "requests.get\|httpx.get\|fetch(" src/ | grep -v timeout    # 무타임아웃 호출 검출
   # 실패 주입: 상대를 못 가는 주소로 바꿔 타임아웃·재시도·차단 동작 관찰
   python -c "import time; t=time.time(); call_with_bad_host(); print(time.time()-t)"   # 실제 차단 시간 확인
   # 웹훅: 서명 틀린 요청 → 401 확인 / 같은 이벤트 2회 → 1회 처리 단언
   ```
4. **장애 시나리오 표** — [상대 다운/느림/429/스키마 변경] 4행에 각각 내 서비스의 동작을 적는다 — 빈 칸이 설계 구멍.

### 판단이 막히면 (확인 필요 4요소)

연동은 외부 API의 계약이 문서에 안 적혀 막히는 일이 잦다(한도·에러 체계·멱등 지원). 추측으로 메우지 말고 **누가·언제·어떻게·기대값** 4요소를 갖춘 `[확인 필요]`로 질의한다.

- **누가**: API 제공자 문서·지원 채널, 또는 그 계약을 아는 연동 담당자 — 응답 샘플만으로는 단정 불가한 항목의 출처.
- **언제**: ① 멱등 키 지원/재시도 안전성 미상(재시도해도 되나?) ② 한도·Retry-After 정책 불명 ③ "200 + 에러 바디"의 코드 목록 미파악 ④ 웹훅 서명 알고리즘·재발송 정책 불명.
- **어떻게**: `[확인 필요] <항목> — 현재 가정: <A>, 근거: <문서 줄/응답 샘플>, 다른 답이면 <재시도 정책/서킷 임계>가 바뀜. 확정 답?` (가정/근거/영향/택일 명시).
- **기대값**: "멱등 지원 O/X", "초당 N건", "에러 코드 목록" 같은 **확정 사실**. 답이 오면 계약 표·장애 시나리오 표의 해당 행을 확정한다. 끝내 확인 불가면 가장 보수적 가정(비멱등 취급·재시도 금지·서킷 보수 임계)으로 잠그고 운영 수집으로 보강할 것을 기록.

## 실전 케이스 — AWS DynamoDB 장애 (2015-09): 재시도 폭풍이 복구를 막다 (공식 포스트모템)

DynamoDB 메타데이터 서비스가 일시 과부하 → 스토리지 노드들의 멤버십 갱신 요청이 타임아웃 → 노드들이 **일제히 재시도** → 복구 시도마다 재시도 파도가 다시 눕힘 — 5시간 장애로 EC2·SQS 등 연쇄. AWS의 사후 조치가 교과서: 타임아웃·재시도 정책 재설계 + 용량 증설 + **백오프 강화**. 교훈: ① 재시도는 개별로는 합리, 집단으로는 흉기 — 시스템 설계는 집단 행동을 설계하는 것 ② 복구를 막는 건 원인이 아니라 증폭 구조일 때가 많다(metastable failure) ③ 세계 최고 인프라 팀도 이 함정을 밟았다 — "우리는 괜찮겠지"의 반례로 충분하다. 상세: `references/evidence.md`
