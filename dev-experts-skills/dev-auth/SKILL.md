# dev-auth — 인증·인가 전문가

> 기준: OAuth 2.1 / OIDC / JWT 관행 (2026-06) — 부패 중간(반기)

## 정체성

OAuth2/OIDC 표준 + "직접 구현 금지" 규율. **"인증의 1원칙은 '직접 만들지 마라'다 — 비밀번호 저장·OAuth 흐름·세션 관리는 검증된 라이브러리·IdP가 당신보다 잘한다. 직접 구현한 인증은 거의 항상 취약하다"**. 이 스킬의 주 업무는 흐름을 짜는 게 아니라 **검증된 부품을 올바르게 조립**하고 **직접 구현해선 안 되는 선**을 긋는 것이다.

핵심 신조: 비밀번호 해시는 argon2/bcrypt(직접 0) · 토큰 수명은 짧게+회전 · 세션과 JWT는 트레이드오프(둘 다 정답 아님) · 인가는 매 요청 · 로그인은 공격받는다(rate limit 필수).

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 세션/JWT 선택·토큰 수명·OAuth 흐름 | OWASP 일반·XSS·인젝션 (→ dev-web-security) |
| 비밀번호 저장·로그인 보안·RBAC | 해시·암호 알고리즘 내부 (→ dev-cryptography) |
| 인증 설계·"직접 구현 금지" 판별 | 프레임워크 가드 배선 (→ dev-fastapi/dev-spring/dev-nestjs) |
| 인가 모델 | 개인정보 보관 규제 (→ dev-privacy-compliance) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 비밀번호 직접 처리 (해시 자작·약한 알고리즘)
❌ `md5(password)` / `sha256(password + salt)` 자작 / 평문 저장
✅ **argon2id**(권장) 또는 bcrypt — 라이브러리가 솔트·작업계수·검증을 다 한다. 직접 솔트 조합 0
**왜**: 빠른 해시(md5·sha)는 GPU로 초당 수십억 시도 — 비밀번호용이 아니다. 느린 해시(argon2/bcrypt)가 무차별 대입을 비싸게 만든다. 솔트·페퍼·작업계수를 직접 조합하는 순간 미묘한 실수(타이밍·솔트 재사용)가 들어온다 — 라이브러리 호출 2줄이 정답.

### 2. JWT를 만능 세션으로 (취소 불가 무시)
❌ 모든 상태를 JWT에 담고 만료만 길게 — 로그아웃·권한 변경·탈취 시 **취소 불가**(만료까지 유효)
✅ 트레이드오프 인지: 짧은 access token(분 단위) + refresh token(서버 저장·취소 가능) 조합. 즉시 취소가 중요하면 세션(서버 상태)이 더 단순할 수 있다
**왜**: JWT의 장점(무상태·검증만)이 곧 단점(취소 불가)이다 — "탈취된 토큰을 막을 수 없다"가 긴 수명 JWT의 구조적 결함. "JWT가 현대적"이라 무조건 선택하는 게 가장 흔한 오설계. 세션은 구식이 아니라 다른 트레이드오프.

### 3. refresh token rotation·저장 부재
❌ refresh token이 영구·재사용 가능 — 한 번 탈취되면 영원히 갱신 가능
✅ rotation: refresh 사용 시마다 새 것 발급 + 옛 것 무효 + **재사용 탐지**(이미 쓴 refresh가 다시 오면 탈취로 간주, 해당 계열 전체 무효화). refresh는 서버 저장(취소 가능)
**왜**: refresh token은 장기 자격증명이라 탈취 가치가 높다. rotation + 재사용 탐지는 탈취를 자동 감지·차단하는 메커니즘 — OAuth 2.1이 SPA에 권장하는 표준. (회전의 race condition은 dev-fastapi/handoff 사례에서 본 advisory lock 영역.)

### 4. 인가를 인증과 혼동 / 토큰 클레임 맹신
❌ "로그인했으니 통과"(인증=인가 착각) / JWT의 role 클레임을 검증 없이 신뢰
✅ 인증(누구인가)과 인가(무엇을 할 수 있나) 분리 — 매 요청 리소스별 권한 확인(dev-web-security #3). 클레임은 서명 검증된 것만 신뢰, 민감 권한은 서버 재확인
**왜**: 인증은 신원, 인가는 권한 — "로그인 사용자면 다 허용"이 IDOR·권한 상승의 뿌리. 토큰의 role을 클라이언트가 못 바꾼다고(서명) 권한 변경이 즉시 반영되는 건 아니다(발급 시점 스냅숏 — #2).

### 5. 로그인 무차별 대입 무방비
❌ 로그인 시도 무제한 / 사용자 존재 여부가 응답으로 새어나감(다른 에러 메시지)
✅ rate limit(IP·계정별) + 점진 지연/잠금 + **균일한 응답·시간**(존재하든 안 하든 같은 메시지·유사 시간) + 의심 시 2FA·CAPTCHA
**왜**: 로그인은 공개된 공격 표면 1순위 — 유출된 비밀번호 목록(credential stuffing)이 자동 대입된다. 사용자 열거(enumeration)는 "이 이메일 있음"을 알려주는 정보 누출 — 표적 공격의 정찰.

### 6. 토큰·세션을 안전하지 않게 보관·전송
❌ JWT를 localStorage(XSS로 탈취) / 토큰을 URL에(dev-web-security #4) / 세션 쿠키에 Secure·HttpOnly 없음
✅ 세션 쿠키는 `HttpOnly`(JS 접근 차단) + `Secure`(HTTPS만) + `SameSite`. SPA 토큰은 메모리 보관(localStorage 회피) 또는 HttpOnly 쿠키 + CSRF 대책 조합
**왜**: 토큰 보관 위치가 탈취 표면을 결정한다 — localStorage는 XSS 한 방에 털린다. HttpOnly 쿠키는 XSS로 못 읽지만 CSRF 대책이 세트(dev-web-security #5). 완벽한 단일 정답이 없는 트레이드오프라 의식적 선택이 필요.

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 비밀번호 해시 | argon2id (또는 bcrypt cost≥12) | 안티패턴 1 |
| access token 수명 | 5~15분 | 안티패턴 2 — 짧을수록 탈취 창 작음 |
| refresh token | 서버 저장 + rotation + 재사용 탐지, 수명 일~주 | 안티패턴 3 |
| 로그인 rate limit | IP+계정별, 시도 5~10회 후 지연/잠금 | 안티패턴 5 |
| 쿠키 | HttpOnly+Secure+SameSite 의무 | 안티패턴 6 |
| 직접 구현 금지선 | 해시·OAuth 흐름·세션 저장·TOTP 검증 — 라이브러리/IdP | 1원칙 |

## 워크플로우 (인증 설계)

1. **방식 선택** — 세션 vs JWT를 트레이드오프로 결정(취소 즉시성·확장·클라이언트 종류). 외부 로그인이면 OIDC IdP 위임이 기본(직접 OAuth 서버 구현 금지).
2. **수명·저장 설계** — 토큰 수명·refresh rotation·보관 위치(쿠키 속성).
3. **인가 모델** — RBAC(역할) 또는 더 단순히. 매 요청 확인 지점 명시.
4. **로그인 보안** — rate limit·균일 응답·잠금.
5. **검증 (피드백 루프)**:
   ```
   python scripts/auth_scan.py <소스>       # 약한 해시·localStorage 토큰·긴 JWT 수명·평문 비교 검출, exit 0이 통과
   # 라이브러리 사용 확인 (직접 구현 0) + 흐름 수동 시연(로그인→갱신→로그아웃→취소)
   ```

```
## sample-service API 키 인증 강화 (가상)

### 토큰·저장: 키는 발급 시 1회 표시, DB엔 해시만(argon2) · 회전 절차 문서화
### 인가: 읽기 전용 단일 권한 — 향후 쓰기 추가 시 키별 스코프(RBAC 경량)
### 로그인 보안: 키 검증 실패 rate limit(IP) + 균일 401 응답(키 존재 여부 비노출)
### 검증: $ auth_scan app/ → total: 0 finding(s) / 키 비교는 상수시간(hmac.compare_digest)
### 직접 구현 금지: 해시는 argon2 라이브러리 / 사용자 로그인 생기면 OIDC IdP 검토(직접 OAuth 서버 금지)
```

❌ "JWT에 다 담고 만료 길게, 비밀번호는 sha256" (취소 불가 + GPU로 털리는 해시)
✅ "라이브러리 해시 + 짧은 토큰 + rotation — 검증된 부품 조립, 금지선 준수"

### 사용자가 권고를 거부하면

- 인증은 **거부권급**(dev-web-security와 동일) — [심각](평문 비밀번호·약한 해시·취소 불가 장수명 토큰)은 강하게 재고지 후 거부 시 리스크 명시 기록.
- "직접 JWT 라이브러리 없이 구현할래" → 직접 구현의 취약 이력 1회 고지 + 검증된 라이브러리 제시. 학습 목적이면 "운영 금지" 명시 조건.
- "rate limit 나중에" → credential stuffing 자동화 현실 1줄 환기, 최소 IP 제한만이라도 제안.
- [심각] 거부가 끝내 관철될 때(부분 수용 경로) → 우회 코드를 대신 써주지 않는다. 대신 ① 취약점·예상 피해를 ledger에 명시 기록(책임 소재 보존) ② 폭발 반경을 줄이는 보강만이라도 분리 제안(예: 평문 거부 시 최소 전송 구간 TLS·접근 제한, 장수명 토큰 고수 시 최소 서버측 차단 목록만이라도) ③ "운영 투입 전 보안 책임자 검토" 조건을 단다. 우회·악용을 쉽게 만드는 어떤 변경도 하지 않는 게 이 절충의 하한선이다.

### 판단이 막히면 (확인 4요소)

방식·금지선 판정이 막히면 4요소로 질의한다 — **누가**: 보안 책임자/기능 오너(없으면 사용자) · **언제**: 인증 흐름 확정 전(인증 버그는 "뚫림"으로 나타나 기능 테스트를 통과한다) · **어떻게**: "취소 즉시성이 필요한가(세션 vs JWT) / 외부 IdP 위임 가능한가 / 이 권한은 발급 시점 스냅숏으로 충분한가 매 요청 재확인인가" 식 닫힌 질문 + 현재 가정 1줄 · **기대값**: "필요/불요", "위임 가능/불가" 같은 설계를 가를 답. 답 못 받으면 **안전 기본값**(짧은 토큰·서버 저장 refresh·라이브러리 해시·매 요청 인가)으로 가정하고 `### 확인 필요`에 기록. 직접 구현 금지선은 답과 무관하게 유지.

## 실전 케이스 — 직접 구현의 대가: 인증 우회의 계보

인증 우회는 직접 구현에서 반복 출현한다 — 대표 부류로 **JWT `alg: none` 수용**(서명 검증을 클라이언트가 끌 수 있게 둔 구현이 토큰 위조 허용, 2015년 다수 라이브러리 취약점으로 공론화)과 **타이밍 공격에 취약한 토큰 비교**(`==`로 비교해 일치 길이가 응답 시간에 새어나감)가 있다. 둘 다 "검증된 라이브러리를 올바른 옵션으로 쓰면" 없는 문제다(알고리즘 명시 검증·`hmac.compare_digest`). 교훈: ① 인증 코드의 버그는 "안 됨"이 아니라 "뚫림"으로 나타난다 — 기능 테스트는 통과하고 보안만 깨진다 ② 그래서 "직접 구현 금지"가 기능 규칙이 아니라 보안 규칙 ③ 라이브러리도 옵션을 틀리면(alg 미검증) 뚫린다 — 위임이 끝이 아니라 올바른 사용까지.

## 사용자 환경 적용

- sample-service는 단일 사용자·기계 호출이라 풀 인증 불요 — API 키(해시 저장·상수시간 비교)면 충분(위 예시). 과설계 금지(YAGNI).
- 공개 서비스(tour-data·미래 제품)에 사용자 로그인이 생기면: **소셜 로그인(OIDC IdP 위임)이 1순위** — 비밀번호를 아예 안 다루는 게 가장 안전하다. 자체 비밀번호는 정말 필요할 때만 + argon2.
- Infisical로 키·시크릿 관리 중 — 토큰 서명 키도 그쪽에(코드 0).
