# evidence + 출고 전 체크리스트

> 사고 메커니즘 본문은 `evidence.md`. 이 파일은 출처 요약 + 출고 체크 + 점검 주기(gold-standard 3절 형식).

## 실증·출처

- **Proxmox VE 9.2** (proxmox.com 공식, 2026-05 — Debian 13 "Trixie" 기반, 커널 6.17 계열, SDN/WireGuard·BGP-EVPN·LXC qcow2 등) — SKILL.md 버전 라벨의 1차 출처. 9.x 계열이 현재 production-ready 라인(확인 필요: 사용 시점 패치 버전).
- **OpenZFS ARC 문서** — ARC(읽기 캐시)가 명시 상한 없으면 물리 메모리의 상당분까지 자란다는 동작의 출처. `zfs_arc_max`(`/etc/modprobe.d/zfs.conf`) 명시가 메모리 회계의 항수라는 안티패턴 2의 근거.
- **LVM-thin / ZFS thin provisioning** — "쓸 때 할당(allocate on write)" 모델로 약속 합계 > 실물이 기본 가능. 약속 동시 청구가 임계를 넘는 날이 장애일이라는 안티패턴 4·실전 케이스의 메커니즘 출처. 풀 100% 도달 시 스냅샷 삭제조차 메타데이터 쓰기 공간이 없어 거부되는 잠금 상태는 Proxmox 포럼 반복 보고.
- **IOMMU 그룹 / PCI 패스스루** — Proxmox 공식 PCI(e) Passthrough 문서 + ACS(같은 그룹은 통째로만 분리) 제약. 순서(보드 지원→BIOS→커널 파라미터→그룹 확인→드라이버 블랙리스트)와 "그룹 확인 전 시도는 복권"이라는 안티패턴 5의 근거.
- **스냅샷 ≠ 백업** — 스냅샷은 같은 풀 위의 차분이라 풀/디스크 사망 시 원본과 함께 소멸. 백업의 정의는 "다른 스토리지"가 절반이라는 안티패턴 3의 위협 모델 구분 근거.
- 출처 종합: Proxmox 공식 문서·포럼 사고 집적 · OpenZFS 문서 · 홈랩 커뮤니티 패스스루 가이드 검증분. 2026-06, PVE 9.2 기준.

## 출고 전 체크리스트 (가상화 구성 출고 시)

- [ ] 게스트별 VM/LXC 판정에 근거(격리 요구·OS·커널 의존)가 적혀 있다
- [ ] 메모리 회계: 게스트 합계 + 호스트 예약(2GB+) + **ZFS ARC 상한** ≤ 물리 (오버커밋 시 명시)
- [ ] `zfs_arc_max`가 기본값 방치가 아니라 명시 설정됨 (NAS 겸용이면 상향 근거)
- [ ] 스냅샷은 작업용(일 단위 내 삭제), 백업은 **노드 외부** 스토리지 1+
- [ ] 백업 복구 리허설을 실제로 1회 수행했다 (vzdump → 외부에서 복원 확인)
- [ ] thin 풀 실사용 80% 경보가 **호스트 pvesm/zpool 기준**으로 걸려 있다 (게스트 내부 df 아님)
- [ ] 패스스루는 `pvesh get .../hardware/pci`로 IOMMU 그룹 단독 분리를 확인한 뒤 시도
- [ ] 단일 노드 복구 동선: 게스트 전체 중지 상태에서 호스트 접근(SSH/콘솔)이 DNS·VPN 게스트에 의존하지 않음을 1회 확인
- [ ] 2노드 클러스터면 QDevice(쿼럼 장치) 구성 — 아니면 1노드(정직한 단일)
- [ ] 게스트 생성이 qm/pct CLI 기록으로 남아 재구축 가능
