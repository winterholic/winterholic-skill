# dev-virtualization evidence — 실증 사례

## 1. thin 풀 100% — "스냅샷 지울 공간도 없다" (포럼 반복 사고)

- **무슨 일**: LVM-thin/ZFS thin 게스트들이 "보이는 용량" 기준으로 데이터를 쌓다 실제 풀 100% 도달 → 전 게스트 동시 IO 에러/프리즈. 복구 시도에서 발견: 스냅샷 삭제·파일 삭제조차 메타데이터 쓰기 공간이 필요해 거부되는 잠금 상태 — Proxmox 포럼의 반복 구조 사고.
- **메커니즘**: thin은 "쓸 때 할당" — 게스트 N개에 각 100GB를 약속하고 실물은 300GB뿐인 구조가 기본 가능하다. 약속의 동시 청구가 임계를 넘는 날이 온다(오버커밋 일반 원리).
- **방어**: ① 풀 실사용 80% 경보(게스트 내부 df가 아니라 **호스트 pvesm/zpool 기준**) ② 게스트 fstrim 주기 실행(삭제 공간 반환 — discard 옵션 활성 전제) ③ 잠금 대비 비상 여유(예약 공간 또는 즉시 제거 가능한 더미 볼륨) 1개.

## 2. ZFS ARC 회계 누락 — "32GB인데 메모리가 모자라요" (홈랩 표준 미스터리)

- **무슨 일**: Proxmox에 ZFS를 쓰면 ARC(읽기 캐시)가 기본적으로 물리 메모리의 상당분(역사적으로 절반 수준)까지 자란다 — VM 합계만 계산한 운영자가 호스트 OOM·게스트 사망을 겪고서야 발견하는 반복 패턴. ARC는 압박 시 줄어들지만 반환이 OOM보다 느린 경합 창이 존재.
- **방어**: ① `/etc/modprobe.d/zfs.conf`에 `zfs_arc_max` 명시(워크로드 따라 물리의 1/4~1/3 시작점 — NAS 캐시 겸용이면 상향, 확인 필요) ② 회계식에 ARC 상한을 항수로 포함 ③ 실측: `arcstats`의 size 추이를 부하 시간대에 확인.
- **교훈**: "쓸 수 있는 메모리"의 정의가 계층마다 다르다(free의 available·ARC·발룬) — 회계는 가장 보수적인 정의로.

## 3. 패스스루 전제 체크리스트 — 반나절 삽질의 예방주사 (커뮤니티 집적)

- **무슨 일**: GPU/디스크 컨트롤러 패스스루 시도의 표준 실패 경로 — ① BIOS에서 IOMMU(VT-d/AMD-Vi) 비활성 ② 같은 IOMMU 그룹에 다른 장치가 묶여 분리 불가(보드 차이 — ACS 지원 여부) ③ 호스트 드라이버가 장치를 선점(블랙리스트 누락) ④ NAS용 디스크를 개별 패스(RDM류)했다가 SMART·시리얼 미노출로 ZFS 운용 반쪽 — 각각이 포럼 단골.
- **순서 고정**: CPU/보드 지원 확인 → BIOS 활성 → 커널 파라미터 → **그룹 확인**(`find /sys/kernel/iommu_groups/ -type l` 또는 PVE UI) → 드라이버 블랙리스트 → 게스트 매핑 — 그룹 확인 전의 모든 시도는 복권이다.
- **NAS VM 정석**: 디스크 개별이 아니라 **HBA/컨트롤러 통째 패스스루** — 게스트(TrueNAS류)가 SMART·시리얼·캐시 제어까지 직접 보게(→ dev-storage-nas의 ZFS 전제와 접속).

> 출처: Proxmox 공식 문서·포럼 사고 집적 · OpenZFS 문서(ARC) · 홈랩 커뮤니티 패스스루 가이드 검증분. 2026-06, PVE 9.2 기준.
