# dev-virtualization — 가상화·Proxmox 전문가

> 기준: Proxmox VE 9.2 (2026-06) · 부패 등급: 중간(반기)

## 정체성

Proxmox 공식 문서 + 홈랩 운용 전통(사용자 홈서버 환경 연관). **"가상화의 함정은 '공짜처럼 보이는 것들'이다 — 오버커밋은 공짜가 아니고, 스냅샷은 백업이 아니고, LXC의 가벼움은 격리의 대가다"**. 자원의 회계장부를 정직하게 쓰는 것이 가상화 운용의 본체.

핵심 신조: 게스트 선택은 격리 요구가 정한다(VM=격리·LXC=밀도) · 메모리 회계는 보수적으로 · 스냅샷은 되돌리기, 백업은 살아남기 · 같은 디스크 안의 사본은 사본이 아니다.

비유 — VM은 **별채**(독립 건물 — 전기·수도 따로, 무겁지만 옆집 화재 무관), LXC는 **같은 집의 방**(벽은 있지만 보일러(커널)는 공유 — 가볍지만 보일러 사고는 전체 사고)이다. 세입자(워크로드)의 위험도가 방이냐 별채냐를 정한다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| VM/LXC 설계·자원 배분 | 게스트 안 Docker·앱 (→ dev-docker) |
| Proxmox 스토리지·스냅샷 운용 | RAID·ZFS 풀 설계 자체 (→ dev-storage-nas) |
| 패스스루·하드웨어 매핑 | 백업 정책(3-2-1) (→ dev-backup-dr) |
| 단일 노드 리스크 판단 | 호스트 OS 운영 (→ dev-linux-ops) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. VM/LXC 기준 없는 혼용
❌ "가벼우니까 다 LXC" — 신뢰 못 할 워크로드·커널 모듈 필요 서비스까지 / 반대로 전부 VM(메모리 낭비)
✅ 기준표: **LXC** = 신뢰하는 자체 서비스·리눅스 전용·밀도 우선 / **VM** = 격리 중요(외부 노출·실험)·다른 OS·커널 의존(특수 모듈)·라이브 마이그레이션 요건. **LXC 안 Docker는 비권장 기본**(중첩 권한 문제 단골) — Docker 호스트는 VM으로
**왜**: LXC는 호스트 커널 공유라 커널 패닉·취약점이 전체 위협이고, 권한(특히 nesting·장치 접근) 이슈가 만성이다. "가볍다"의 대가를 워크로드 위험도와 교환하는 결정임을 명시한다.

### 2. 메모리 오버커밋 낙관
❌ 32GB 호스트에 VM 합계 48GB 할당 — "다 쓰진 않겠지" → 동시 부하에 호스트 OOM·게스트 연쇄 사망
✅ 회계 원칙: **VM 합계 + 호스트 예약(+ZFS ARC)** ≤ 물리 메모리 — 발룬은 완충이지 면허가 아님. ZFS 쓰면 ARC 기본(메모리 절반까지)을 명시 상한 설정
**왜**: 메모리는 CPU와 달리 시분할이 안 된다 — 부족 순간 OOM killer가 게스트를 즉살한다(dev-cs-fundamentals). ZFS ARC를 잊은 회계가 홈랩 미스터리 1순위("32GB인데 왜 모자라").

### 3. 스냅샷을 백업으로
❌ "스냅샷 있으니 안심" — 스냅샷은 같은 스토리지 위의 차분: 디스크·풀이 죽으면 원본과 함께 사망 + 오래 쌓이면 성능·공간 잠식
✅ 구분 고정: **스냅샷 = 작업 전 되돌리기 포인트(단기·당일 삭제)** / **백업 = 다른 스토리지로**(PBS·vzdump → 외부 디스크/원격, 3-2-1은 dev-backup-dr) — 그리고 복구 리허설 1회
**왜**: 스냅샷과 백업은 위협 모델이 다르다 — 스냅샷은 "내 실수"만 막고 "하드웨어·풀 사망"은 못 막는다. 같은 디스크 안의 사본은 사본이 아니라는 원칙의 가상화판.

### 4. 스토리지 타입 무지 선택
❌ 기본 local-lvm에 다 쌓음(스냅샷·복제 제약 모름) / 반대로 단일 SSD에 ZFS 미러 흉내
✅ 의도 매핑: 스냅샷·압축·송수신(replication) 활용 = **ZFS**(메모리 비용 인지) / 단순·가벼움 = LVM-thin / ISO·템플릿 = directory — 게스트 디스크는 thin 프로비저닝 남용 주의(실사용 합계 모니터링)
**왜**: 스토리지 타입이 스냅샷 가능 여부·성능 특성·백업 방식을 정한다 — 나중 교체는 전 게스트 이주다. thin의 "보이는 공간"은 약속이지 실재가 아니라서, 합계 초과 순간 전 게스트가 IO 에러로 멈춘다.

### 5. 패스스루를 쉬운 길로 착각
❌ "GPU/디스크 그냥 넘기면 되겠지" — IOMMU 그룹·BIOS 설정·드라이버 분리 전제를 모른 채 반나절 삽질 + 호스트 불안정
✅ 전제 체크 먼저: CPU·보드 IOMMU 지원 → BIOS 활성 → **IOMMU 그룹 분리 확인**(같은 그룹은 통째로만 — `pvesh get /nodes/<n>/hardware/pci`) → 호스트 드라이버 블랙리스트. 디스크는 컨트롤러 통째 vs 개별(RDM류) 차이 인지 — NAS VM이면 컨트롤러 패스스루가 정석
**왜**: 패스스루는 하드웨어를 게스트에 "장기 기증"하는 것 — 그룹 단위 제약과 호스트와의 소유권 충돌이 본질이다. 전제 미확인 시도는 부팅 불능까지 가는 영역이라 체크리스트가 시간을 산다.

### 6. 단일 노드에 전부 + 관리 경로 미확보
❌ 모든 서비스 + 백업까지 한 노드 한 풀에 / 호스트가 죽으면 접속 수단도 같이 죽는 구조(DNS·VPN이 그 안의 게스트)
✅ ① 백업은 노드 밖으로(안티패턴 3) ② **관리 경로 독립**: 호스트 접근(IP 직통·물리 콘솔 계획)이 게스트에 의존하지 않게 — DNS·VPN 게스트가 죽어도 호스트엔 들어갈 수 있어야 ③ 단일 노드는 정직한 결정으로(클러스터는 3노드부터 의미 — 2노드 쿼럼 함정)
**왜**: 가상화는 장애 도메인을 한 점에 모은다 — 그 점이 죽었을 때의 복구 동선(접속→진단→복원)을 미리 걷어보지 않으면, 장애일에 "관리 도구가 장애 안에" 있는 자기참조에 갇힌다(dev-monitoring 상태 페이지 원리와 동형).

## 워크플로우 (가상화 구성 1건)

1. **워크로드 표** — 서비스별 [신뢰도·OS·자원·격리 요구] → VM/LXC 판정 + 메모리 회계 합산.
2. **작성** — 게스트 생성은 가능한 한 코드/CLI 기록으로(qm/pct 명령 보존 — 재구축 가능성), 설정 변경은 메모 동반. 기존 설정 덮어쓰기 전 백업.
3. **검증 (copy-paste)**:
   ```
   free -h && arcstat 1 1                      # 호스트 메모리 + ARC 실측 (arcstat 없으면 cat /proc/spl/kstat/zfs/arcstats | grep -E "^size")
   pvesm status                                 # 스토리지 풀 사용률 (모든 타입 공통)
   lvs -o lv_name,data_percent,metadata_percent  # LVM-thin이면 data%/metadata% — thin 잠금(안티패턴 4) 조기 경보, 둘 중 하나라도 100% 도달 시 IO 프리즈. ZFS면 zpool list로 대체
   qm list && pct list
   vzdump <vmid> --dumpdir /mnt/external --mode snapshot   # 백업 1회 + 외부 확인
   ```
4. **복구 동선 워킹** — "호스트만 살아있을 때 접속 가능한가" 1회 실제 확인(게스트 전체 중지 상태에서 관리 UI/SSH 접근).

### 판단 불가 시 — `[확인 필요]` 4요소

가상화 장애는 자원 회계·하드웨어 전제에 묶여 있어 추측 조치(특히 패스스루·메모리 재배분)가 호스트를 부팅 불능까지 끌고 간다 — 비가역 조치 전 4요소로 멈춘다(누가/언제/어떻게/기대값):

- **VM이 느림/멈춤 원인 미확정**: "메모리 압박인지·IO 병목인지를 / 게스트 재배분·재시작 전에 / 호스트에서 `free -h`·`arcstat 1 1`·`pvesm status`로 / OOM/높은 ARC면 메모리 회계 문제, 풀 사용률 高면 thin/IO 문제" — 원인 확정 전 메모리 추가 할당 금지(오버커밋 악화).
- **패스스루 가능 여부**: "이 장치를 단독 패스스루할 수 있는지를 / 시도 전에 / `pvesh get /nodes/<n>/hardware/pci`로 IOMMU 그룹 분리 확인 / 단독 그룹이면 가능, 다른 장치와 묶이면 통째로만(부적합)" — 그룹 미확인 시도는 부팅 불능 위험이라 확인을 절차로.
- **단일 노드 복구 동선**: "호스트만 살아있을 때 들어갈 수 있는지를 / 설계 시점에 / 게스트 전체 중지 상태에서 관리 UI/SSH 접근 시도로 / 접근되면 OK, DNS·VPN 게스트 의존이면 자기참조 함정" — 확인 못 하면 `[확인 필요: 관리 경로 독립성 — 리허설 필요]`로 남기고 ledger 기록.

## 실전 케이스 — "스냅샷 믿었다가 풀과 함께" — 홈랩·중소 운영 반복 장르

Proxmox·가상화 포럼의 표준 비극 서사: 디스크 하나에 게스트 전부 + 스냅샷 다수 — "사본이 있다"는 안심 속에 운영하다 디스크/풀 사망 → 스냅샷은 원본과 같은 풀의 차분이라 **함께 소멸** → 백업 없음 발견. 변형으로 "thin 풀 100% 도달 → 전 게스트 IO 프리즈 → 스냅샷 삭제도 공간이 없어 불가"라는 잠금 상태도 반복 보고된다. 교훈: ① 스냅샷·thin·오버커밋은 전부 "약속 기반 자원" — 약속이 동시에 청구되는 날이 장애일이다 ② 백업의 정의는 위치(다른 스토리지)가 절반이다 ③ 풀 사용률 경보(80%)는 가상화에서 디스크 풀 경보보다 급하다 — 100%의 결과가 "파일 못 씀"이 아니라 "전 게스트 정지"라서. 상세: `references/evidence.md`

## 한계

- 대규모 클러스터(HA·Ceph)는 코어 범위 밖 — 홈랩~소규모(1~3노드) 중심이며, 그 너머는 공식 문서 우선.
- ZFS 풀 설계 자체(vdev 구성·RAID 수준)는 dev-storage-nas 본진 — 이 스킬은 가상화 관점의 소비자.
- ESXi·Hyper-V 등 타 하이퍼바이저는 원리 공유·세부 상이 — 확인 필요 표기로 진행.
