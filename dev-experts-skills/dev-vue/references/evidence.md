# dev-vue evidence — 실증 사례

## 1. index key 데이터 밀림 — 편집 가능 목록의 정합성 사고 (반복 실증)

- **무슨 일**: 행 추가·삭제가 있는 폼 목록에서 `:key="index"` 사용 시, 중간 행 삭제 후 DOM에 살던 상태(입력 중 텍스트·체크박스·포커스)가 아래 데이터와 어긋나게 짝지어지는 패턴. Vue/React 공통으로 이슈 트래커·포럼에 수년간 반복 보고.
- **메커니즘**: key가 index면 "3번 행"이라는 정체성만 있고 "어떤 데이터의 행"인지가 없다. 삭제 시 Vue는 마지막 행을 제거하고 나머지 행의 **내용만 패치** — v-model 바인딩은 따라가지만 비제어 상태(raw input·서드파티 위젯)는 남는다.
- **검출**: 단건 테스트로 안 잡힘 — "행 2개 입력 → 1번 삭제 → 남은 행 값 단언" 시나리오 테스트가 필요. 정적 검출은 `eslint-plugin-vue`의 `require-v-for-key` + index key 수동 리뷰.

## 2. composable이 reactive를 반환 — 호출부 전원이 함정 진입 (API 설계 실증)

- **무슨 일**: `useX()`가 `return reactive({ data, loading })`을 반환하면 호출부의 자연스러운 사용법이 `const { data, loading } = useX()` — 그 순간 반응성 절단. 라이브러리 이슈로 "loading이 영원히 true"류 리포트가 반복되는 표준 원인.
- **표준 계약**: composable은 **refs 묶음을 평평하게 반환**(`return { data, loading }` — 각각 ref). 구조분해해도 ref 자체가 넘어가므로 안전. VueUse 전체가 이 계약을 따른다 — 생태계 표준.
- **이 스킬과의 연결**: 안티패턴 1·6. API를 함정 없는 형태로 설계하면 호출부 실수가 원천 차단된다 — "문서로 경고"보다 "구조로 불가능하게".

## 3. stale 응답 경합 — "한 글자 전 검색 결과" (네트워크 순서 실증)

- **무슨 일**: 자동완성·필터 UI에서 요청 A(느림)·B(빠름) 순서로 발사 → B 응답 후 A 응답이 도착해 최신 결과를 덮음. 재현이 네트워크 타이밍 의존이라 "가끔 이상해요"로 보고되는 부류.
- **방어 사다리**: ① watch의 `onCleanup`으로 stale 플래그(본 스킬 안티패턴 5) ② AbortController로 이전 요청 취소(자원도 절약) ③ 디바운스는 빈도만 줄일 뿐 경합을 **막지 못한다** — 디바운스만 믿는 게 흔한 오답.
- **이 스킬과의 연결**: 안티패턴 5. 테스트: 응답 지연을 모킹해 "A 늦게, B 먼저" 순서를 강제한 단언 1개를 두면 회귀 방지.
