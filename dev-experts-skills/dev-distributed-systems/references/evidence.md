# dev-distributed-systems evidence — 장애·실증 사례

## 1. GitHub (2018-10-21) — 43초가 만든 24시간 (공식 포스트모템)

- **체인**: 광케이블 장비 교체 → 동부↔서부 43초 단절 → Orchestrator가 서부 레플리카를 프라이머리 승격(자동 페일오버 정상 동작!) → 단절 직전 동부 쓰기 일부가 서부 미복제 상태 → 복구 후 두 갈래 이력(스플릿 브레인) → 자동 병합 불가, 수동 재동기화 24시간+ (그동안 웹훅·빌드 지연 누적).
- **교훈 분해**:
  1. **자동 페일오버의 전제 점검**: 승격 조건에 "복제 완결" 확인이 없으면 페일오버가 분기 제조기 — 펜싱(구 프라이머리 쓰기 차단)·세미싱크 복제가 그 비용이다.
  2. **지리적 분산의 양면**: 지연 때문에 비동기 복제 → 비동기라서 파티션 때 분기 — 멀리 둘수록 CAP 청구서가 커진다.
  3. **복구 우선순위 선언**: GitHub은 "데이터 정합 > 가용성"을 명시 선택하고 시간을 지불했다 — 이 우선순위를 장애 전에 정해둔 것이 대응의 침착함을 만들었다.
- **공식 출처**: GitHub 공식 포스트모템 "October 21 post-incident analysis"(Jason Warner, 2018-10-30) — https://github.blog/news-insights/company-news/oct21-post-incident-analysis/ (1차 출처. 43초 단절·24h11m 저하·Orchestrator는 Raft 기반·국경 간 승격 금지로 재구성·미복제 쓰기는 한 클러스터 954건 수준 등 본문 수치 전부 이 글에서 확인. 2026-06 재확인, 본문과 일치).

## 2. 두 장군 문제 — "정확히 한 번"이 불가능한 이유 (이론 기반)

- **명제**: 신뢰할 수 없는 채널로 두 노드가 "둘 다 확실히 합의했음을 둘 다 아는" 상태에 도달하는 유한한 프로토콜은 없다 — 마지막 확인 메시지가 항상 유실될 수 있으므로(확인의 확인의 확인…).
- **실전 번역**: ① "보냈고 받았음이 확실한" 전달은 못 만든다 — 만들 수 있는 건 [최소 한 번 + 수신측 멱등]뿐 ② 브로커의 exactly-once는 그 브로커 트랜잭션 경계 안의 기교 — DB 쓰기·외부 API 호출이 끼는 순간 끝 ③ 따라서 모든 소비자는 중복 내성이 기본 스펙이다(설계 검토 질문: "이 핸들러에 같은 메시지가 두 번 오면?").
- **연결**: dev-event-driven(멱등 소비)·dev-payments(멱등 키)·dev-realtime(중복 제거)이 전부 이 정리의 응용이다.

## 3. 복제 지연 실사고 — "방금 결제했는데 주문 내역에 없어요" (운영 반복 패턴)

- **무슨 일**: 읽기 부하 분산을 위해 레플리카로 읽기를 돌린 서비스의 표준 사고 — 쓰기 직후 리다이렉트된 페이지(주문 완료 → 주문 목록)가 레플리카에서 읽어 방금 쓴 행이 없음. 사용자는 "결제 실패"로 인지하고 재결제 시도(이중 결제 위험으로 비화). 평시 지연 ms라 테스트 통과, 부하·배치·VACUUM으로 지연이 초 단위로 늘어난 날 대량 발생.
- **방어 사다리**: ① 자기 쓰기 읽기(read-your-writes)가 필요한 경로 분류 → 프라이머리/세션 고정 ② 쓰기 직후 페이지는 쓴 데이터를 응답에 동봉(재조회 자체를 제거) ③ 지연 모니터링 + 임계 초과 시 레플리카 읽기 일시 차단(자동 강등).
- **교훈**: "이중화·부하분산"이라는 인프라 작업이 애플리케이션 일관성 계약을 조용히 바꾼다 — 인프라 변경 시 일관성 표(본 스킬 워크플로우 3)를 재검토하는 근거.
