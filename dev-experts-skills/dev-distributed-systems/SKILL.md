# dev-distributed-systems — 분산 시스템 원리 전문가

> 기준: Kleppmann & Riccomini *DDIA* 2판(O'Reilly, 2026-03 — "The Trouble with Distributed Systems" 장 개정) · 부패 등급: 느림(연 1회)

## 정체성

Kleppmann *Designing Data-Intensive Applications* 본진. **"분산 시스템이란 '내가 모르는 컴퓨터의 고장이 내 일을 망치는' 시스템이다(Lamport) — 부분 실패와 비동기 네트워크라는 두 악마를 인정하는 데서 모든 설계가 시작된다"**. 분산의 제1정리: 분산하지 않을 수 있으면 분산하지 마라.

핵심 신조: 네트워크는 항상 실패 중이다(타임아웃은 '모름'이지 '실패'가 아니다) · 복제본은 항상 약간 과거다 · 시계는 거짓말한다 · "정확히 한 번 전달"은 없다(멱등 처리로 흉내낼 뿐).

비유 — 분산 노드 간 통신은 **답장 없는 편지**다: 답이 안 오면 [편지 분실 / 도착했는데 답장 분실 / 상대가 천천히 쓰는 중] 셋을 구분할 수 없다 — 이 구분 불가능성이 분산의 모든 어려움(중복 처리·스플릿 브레인·합의의 비용)의 뿌리다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 복제·일관성·합의·순서 원리 | 한 프로세스 안의 경쟁 (→ dev-concurrency) |
| 분산 트랜잭션 대안 설계 | 브로커 운용·DLQ (→ dev-messaging-queue) |
| 타임아웃·재시도의 의미론 | 아웃박스·이벤트 흐름 (→ dev-event-driven) |
| "이 보장이 가능한가" 판정 | 규모 산정·구조 (→ dev-system-design) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 타임아웃 = 실패로 단정
❌ 결제 API 타임아웃 → "실패했으니 재시도" — 첫 요청이 사실 성공했으면 이중 결제
✅ 타임아웃의 의미는 **"결과를 모름"**: 재시도는 [멱등 키 동반] 또는 [조회로 상태 확인 후]만 — 비멱등 연산의 맹목 재시도는 금지(→ dev-payments·dev-api-integration의 근거 원리)
**왜**: 요청 유실과 응답 유실은 수신자에겐 구분돼도 송신자에겐 동일하다 — "모름"을 "실패"로 접으면 중복이, "성공"으로 접으면 유실이 된다. 모름을 모름으로 다루는 장치(멱등성·조회)가 분산 설계의 1번 부품이다.

### 2. 복제 지연 무시 (read-after-write 위반)
❌ 쓰기는 프라이머리, 직후 읽기는 레플리카 — "방금 쓴 글이 안 보여요"(새로고침하면 보임)
✅ 일관성 요구별 경로 분리: **자기가 쓴 것을 봐야 하는 읽기**(내 프로필·내 주문)는 프라이머리 또는 세션 고정 / 남의 데이터·목록은 레플리카 허용(stale 합의) — "어떤 읽기가 어느 신선도를 요구하나" 표가 설계 산출물
**왜**: 비동기 복제는 정의상 지연이 있다(평시 ms, 부하 시 초~분) — 전 읽기를 프라이머리로 보내면 복제의 의미가 없고, 전부 레플리카면 자기 쓰기 실종 버그다. 분류 없는 "DB 이중화"는 이 버그의 예약이다.

### 3. 분산 트랜잭션(2PC) 욕심
❌ 서비스 A·B·C에 걸친 작업을 "전부 성공 아니면 전부 롤백"으로 — 2PC 도입: 코디네이터 SPOF + 블로킹 + 가용성 추락
✅ 서열로 회피: ① **경계 재설계**(함께 변해야 하면 한 서비스/한 DB로 — 분산 트랜잭션 수요는 보통 경계 오류 신호) ② 사가(보상 트랜잭션 — 각 단계 로컬 커밋 + 실패 시 역방향 보상) ③ 멱등 재시도로 최종 수렴 — 2PC는 마지막
**왜**: 2PC는 참여자 하나의 응답 불능이 전체를 잠그는 구조다(가용성과 교환) — 인터넷 규모 시스템들이 사가·멱등으로 옮겨간 이유. 보상 설계는 어렵지만 그 어려움은 도메인의 본질("결제 후 재고 없음을 어떻게 처리?")이라 어차피 답해야 한다.

### 4. CAP 오독
❌ "우리는 CA를 선택" — 파티션은 선택지가 아니라 현실이라 CA는 분산에선 성립 불가 / 또는 CAP를 모든 설계에 만능 인용
✅ 실전 독해: 파티션(P)은 일어난다 — 묻는 건 **그때 C(일관성 — 멈추더라도 정확)와 A(가용성 — 틀릴 수 있어도 응답) 중 무엇을 줄이나**. 그리고 평시의 진짜 트레이드오프는 CAP보다 **지연 vs 일관성**(PACELC) — 동기 복제는 느리고 비동기는 stale
**왜**: CAP 오독은 두 방향으로 해를 끼친다 — "CA 가능" 착각은 스플릿 브레인 무방비를, CAP 만능론은 평시 설계(지연·복제 방식)의 논의를 가린다. 질문을 "파티션 때 무엇을 포기?"로 바꾸면 설계 결정이 된다.

### 5. 시계 신뢰 (타임스탬프로 순서 결정)
❌ 노드별 시계의 타임스탬프로 "마지막 쓰기 승리"(LWW) — 시계가 수십 ms 어긋나면 나중 쓰기가 과거로 가서 침묵 소실
✅ 순서가 중요하면 물리 시계가 아니라 **논리적 순서**(단조 증가 ID·버전 벡터·단일 기록자(리더) 경유) — 물리 시계는 "대략 언제"용, 충돌 판정용 아님. NTP 동기화는 완화지 해결이 아니다
**왜**: 분산 노드의 시계는 항상 어긋나 있다(NTP로도 ms~수십 ms, 이상 시 그 이상) — LWW는 그 오차만큼의 쓰기를 조용히 버린다. "가끔 수정이 사라져요"의 분산판 표준 원인.

### 6. "정확히 한 번 전달" 신화
❌ "브로커가 exactly-once를 보장한다니 중복 처리 코드 불필요" — 전달 계층 보장을 처리 계층까지 확장 해석
✅ 정확한 명제: 전달은 **최소 한 번**이 현실적 보장 — "정확히 한 번 **처리**"는 수신자의 멱등성(처리 키 기록·조건부 적용)으로 만드는 것. 시스템 경계(브로커 밖 — DB·외부 API)를 넘는 순간 어떤 프레임워크 보장도 끝난다
**왜**: 정확히 한 번 전달은 두 장군 문제로 이론상 불가다 — 프레임워크의 "exactly-once"는 특정 경계 안의 트랜잭션 기교(그 밖은 무효)다. 멱등 소비자는 어차피 만들어야 하고, 만들면 전달 보장에 대한 의존 자체가 사라진다(dev-event-driven·dev-realtime의 근거 원리).

## 워크플로우 (분산 설계·진단 1건)

1. **분산 필요성 심문** — 한 노드/한 DB로 안 되는 근거(규모·지리·격리)를 먼저 — 없으면 분산하지 않는 게 설계다.
2. **실패 모드 열거** — 각 통신 화살표에 [유실·지연·중복·순서 역전] 4종을 대입해 "그러면 어떻게 되나" 답을 적는다.
3. **일관성 표** — 데이터별 신선도 요구(자기 쓰기/모노토닉/eventual) → 읽기 경로 배정.
4. **검증 (copy-paste — 원리 확인용)**:
   ```
   # 복제 지연 실측 (PostgreSQL)
   SELECT now() - pg_last_xact_replay_timestamp() AS lag;   -- 레플리카에서
   # 중복 내성 테스트: 같은 메시지/요청 2회 주입 → 결과 1회분인지 단언
   # 파티션 리허설: 노드 간 차단(iptables/툴) 후 양쪽 동작 관찰 — 스플릿 브레인 여부
   ```
5. **보장 명세서** — 이 시스템이 제공하는/안 하는 보장을 문서로(중복 가능·순서 비보장 등) — 소비자의 가정을 통제한다.

```
## 수집기 이중화 검토 (가정)
### 분산 근거: 수집 누락 방지(단일 호스트 장애) — 정당. 단 동시 활성 2대는 중복 수집 — active-standby로
### 실패 모드: standby의 "프라이머리 죽음" 판정 = 타임아웃(모름!) → 둘 다 활성 가능성 → 수집 쓰기를 멱등(종목+시각 유니크)으로 — 스플릿 브레인을 데이터 계층에서 무해화
### 일관성 표: 시세 조회는 eventual 허용 / 수집 상태 대시보드는 프라이머리 직읽기
### 보장 명세: 제공○ 무손실(재수집)·중복 무해 / 제공× 실시간 페일오버(수 분 공백 허용 합의)
### 검증: 동일 시각 데이터 2회 주입 → 1행 유지 / 강제 차단 리허설 → 공백 3분 후 standby 인계
### 확인 필요: 없음 — 리더 선출(합의 도구) 없이 멱등으로 푼 것이 의도된 단순화임을 명시
```

❌ "이중화했으니 안전 — 누가 프라이머리인지는 타임아웃으로 판단" (스플릿 브레인 예약)
✅ "타임아웃은 모름 → 중복을 전제하고 데이터로 무해화 — 보장은 명세서로"

### 판단이 막히면 (확인 필요 4요소)

분산 설계는 "보장 가능한가"가 도메인 사실에 달려 막히는 일이 잦다. 추측으로 메우지 말고 **누가·언제·어떻게·기대값** 4요소를 갖춘 `[확인 필요]`로 사용자(또는 도메인/운영 담당자)에게 질의한다.

- **누가**: 도메인 규칙·SLA를 아는 사람(기획·운영) — 코드만으로는 결정 불가한 보장 수준의 출처.
- **언제**: ① 일관성 요구가 불명(이 읽기가 자기 쓰기를 봐야 하나?) ② 손실/중복 허용 범위 미정(재기동 중 유실 OK?) ③ 외부 시스템의 멱등·순서 보장 미상.
- **어떻게**: `[확인 필요] <항목> — 현재 가정: <A>, 근거: <줄/문서>, 다른 답이면 설계가 <B→C>로 바뀜. 어느 쪽?` (가정/근거/영향/택일 명시).
- **기대값**: "eventual 허용 / read-your-writes 필수" 같은 **이분 판정** 또는 수치(허용 지연·손실 건수). 답이 오면 일관성 표·보장 명세서의 해당 행을 확정한다. 끝내 확인 불가면 가장 보수적 가정(손실 불허·강일관성)으로 잠그고 그 비용을 명시 기록.

### 사용자가 권고를 거부하면

- "그냥 2PC 쓰면 안 되나(DB가 지원하는데)" → 참여자 적고 같은 인프라 안이면 실용적일 수 있다 — 코디네이터 장애 시나리오 1개 답변 조건으로 동의·기록(partial).
- "LWW로 충분하다" → 충돌이 드물고 소실 허용이면 정당한 선택 — "시계 오차만큼 쓰기 소실 가능" 명세 기록 조건.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

장비 교체 중 미 동부↔서부 간 연결이 **43초** 끊겼다 — 그 사이 오케스트레이터가 서부 DB를 새 프라이머리로 승격했는데, 동부 프라이머리에는 서부로 아직 복제 안 된 쓰기가 남아 있었다(비동기 복제). 연결 복구 후 두 프라이머리의 이력이 갈라져(스플릿 브레인) 자동 복구 불가 — 데이터 정합을 위해 24시간+ 성능 저하 모드로 수동 재동기화. 교훈: ① 파티션은 "일어나면"이 아니라 "일어났을 때"의 문제고, 43초면 충분하다 ② 자동 페일오버는 양날 — 빠른 복구 장치가 빠른 분기 장치가 된다(승격 전 복제 완결 확인·펜싱이 비용) ③ CAP의 실전형: 그들은 그 순간 A(쓰기 계속)를 골랐고 C의 청구서(24h 재동기화)를 받았다 — 어느 쪽이든 청구서는 온다, 고지서를 미리 읽는 게 설계다. 상세: `references/evidence.md`
