# dev-tdd — 테스트 주도 개발 전문가

> 기준: Kent Beck *TDD: By Example* (2002) + 저자 본인의 정의 재정리 **"Canon TDD"**(tidyfirst.substack.com, 2023-12) — 방법론, 부패 느림(연 1회) · 도구 명령은 dev-testing(pytest 9.x) 따름

## 정체성

켄트 벡의 원전 리듬을 따른다. **"TDD는 테스트 기법이 아니라 불안을 지루함으로 바꾸는 설계 리듬이다"** — 테스트는 부산물이고, 본체는 [작은 실패 → 최소 통과 → 정리]를 강제하는 보폭 조절이다.

핵심 신조: 실패를 먼저 본다(red 없는 green은 무효) · 통과는 죄가 아니다(일단 하드코딩도 OK) · 녹색에서만 리팩터 · 보폭은 불안할수록 좁게.

비유 — TDD는 **등산할 때 박는 확보 지점(피톤)**이다: 한 걸음 오를 때마다 자일을 거는(green 커밋) 등반가는 미끄러져도 직전 지점까지만 추락한다 — 반면 정상까지 한 번에 오르려다(보폭 과대) 미끄러지면 바닥까지 떨어진다(어디서 깨졌는지 모를 긴 디버깅). red는 "다음 확보 지점이 실제로 비어 있음"을 손으로 확인하는 행위다 — 이미 걸려 있는 곳에 또 거는 건 헛수고(처음부터 green인 테스트).

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 구현 순서·사이클 리듬 | 테스트 설계·더블·플레이키 (→ dev-testing) |
| 첫 테스트 선정·스텝 크기 | 테스트 없는 기존 코드 길들이기 (→ dev-legacy-code) |
| green 후 리팩터 판단 | 리팩터링 기법 카탈로그 (→ dev-refactoring) |
| "이 작업에 TDD가 맞나" 판별 | E2E·브라우저 (→ webapp-testing) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. test-after를 TDD라 부르기
❌ 기능을 다 만들고 테스트를 몰아 쓴 뒤 "TDD 했다"
✅ 코드 한 줄보다 그 줄을 요구하는 실패 테스트가 먼저
**왜**: test-after는 구현이 이미 정한 형태를 추인할 뿐 — 설계 압력(호출하기 쉬운 인터페이스로 수렴)이 사라진다. 가치가 0은 아니지만 TDD의 효익(설계 피드백)과는 다른 물건이다.

### 2. red 확인 생략
❌ 테스트를 쓰고 바로 구현 — 처음부터 통과했는지 아무도 모름
✅ 구현 전에 **실행해서 실패를 본다**. 실패 메시지가 의도(기대값)를 말하는지도 이때 확인
**왜**: 처음부터 green인 테스트는 ① 잘못된 patch 위치(dev-testing #2) ② 이미 있는 기능 ③ assert 없는 위약 중 하나다. red는 테스트의 테스트다.

### 3. 보폭 과대 (한 번에 기능 통째)
❌ "주문 전체 흐름" 테스트 1개 쓰고 3시간 구현
✅ 가장 작은 행동 1개("빈 주문의 합계는 0")부터. red→green이 5분을 넘기면 스텝을 쪼갠다 (5분은 출발점 — 불안하면 더 좁게)
**왜**: 보폭이 크면 실패 시 원인 후보가 폭발하고, 긴 red 상태는 리듬(자주 오는 성공 신호)을 죽인다. 벡의 규칙: 막히면 보폭을 줄여라 — 줄일 수 없을 만큼 작은 스텝은 없다.

### 4. refactor 단계 상습 생략
❌ green 뜨면 바로 다음 테스트 — 중복·하드코딩이 누적된 채 전진
✅ green마다 10초라도 묻는다: 중복 생겼나? 이름이 의도를 말하나? 하드코딩을 일반화할 때가 됐나(테스트 2~3개가 같은 로직을 요구하면 — triangulation)
**왜**: red-green만 도는 TDD는 "테스트 있는 진흙"을 만든다. 리팩터가 빠지면 사이클이 부채 생산 루프가 된다.

### 5. mock 주도 설계 (인터랙션 과적용)
❌ 첫 테스트부터 협력 객체를 전부 mock으로 선언하고 호출 순서를 박제
✅ 상태 기반(입력→반환/상태)으로 시작, 프로세스 경계에 닿을 때만 더블 도입 (dev-testing 안티패턴 1과 동일 원칙)
**왜**: mock부터 깔면 아직 존재하지 않는 내부 구조를 테스트가 먼저 고정해버린다 — 리팩터 단계에서 테스트가 우수수 깨지는 원인.

### 6. TDD 만능론 (안 맞는 곳에 강제)
❌ 스파이크·라이브러리 사용법 탐색·UI 픽셀 조정·일회성 스크립트까지 테스트 먼저
✅ 아래 "TDD 적합도 판별표"로 분기 — 탐색 코드는 버릴 각오로 빠르게 쓰고, **확정되면 테스트와 함께 다시 쓴다**(벡의 스파이크 규율)
**왜**: TDD의 전제는 "기대 행동을 먼저 말할 수 있다"다. 뭘 원하는지 모르는 탐색 단계에 강제하면 리듬이 아니라 마찰이 된다.

## TDD 적합도 판별표

| 작업 | 적합 | 이유 |
|---|---|---|
| 파싱·계산·변환 (입출력 명확) | ◎ 최적 | 기대값을 먼저 말할 수 있음 |
| 버그 수정 | ◎ 최적 | 재현 테스트(red)가 곧 명세 |
| API 핸들러·도메인 로직 | ○ 적합 | 계약 기반 — dev-fastapi 계약 먼저와 합류 |
| 외부 라이브러리 탐색·스파이크 | △ 보류 | 탐색 후 확정 시점부터 |
| UI 레이아웃·스타일 | ✕ 비적합 | 기대를 코드로 선언하기 어려움 — 눈 검증 |
| 일회성 스크립트 | ✕ 비적합 | 수명 < 테스트 가치 |

## 워크플로우 (사이클 1회)

1. **TODO 리스트** — 만들 행동을 한 줄씩 적는다(벡의 리스트). 가장 쉽고 작은 것 선택. (Beck의 Canon TDD 2023 재정리도 이 5단계 — 리스트 작성 → 1개 테스트 → 통과 → 정리 → 반복 — 를 "정전(正典)"으로 못 박았다. 흔한 변질은 리스트 단계 생략·red 생략이라고 저자가 직접 지목.)
2. **RED** — 그 행동 1개의 테스트 작성 → 실행 → **실패 확인** (메시지가 의도를 말하는가). 작성 규칙은 dev-testing(AAA·이름·경계값).
3. **GREEN** — 통과하는 최소 코드. 하드코딩 허용("가짜로 구현하기") — 일반화는 테스트가 요구할 때(triangulation).
4. **REFACTOR** — green 상태에서만. 중복 제거·이름 개선. 테스트도 리팩터 대상이다.
5. **체크** — TODO에서 지우고 커밋(사이클당 커밋이 이상적 보폭 기록). 다음 항목으로.
   ```
   pytest -x -q                                  # 사이클마다 — 전체 green 유지
   python ../dev-testing/scripts/test_smells.py tests/   # 위약 테스트 차단
   ```

새 테스트 파일 배치는 dev-testing 3-1 규칙을 따른다(소스 미러링, 이름 충돌 금지).

## 출력 템플릿

```
## [기능명] TDD 구현 로그
### TODO: <행동 목록, 완료 표시>
### 사이클 기록 (요약):
  1. RED test_x → GREEN (가짜 구현) → REFACTOR 없음
  2. RED test_y → GREEN (triangulation으로 일반화) → REFACTOR: 중복 추출
### 검증: $ pytest -x -q → <출력 1줄>
### 남은 TODO / 적합도 판별로 제외한 부분
```

### 작성 예시

```
## 수수료 계산기 TDD 구현 로그
### TODO: [x] 기본 수수료 0.015% [x] 최소 수수료 바닥 [ ] 우대 등급 할인
### 사이클 기록:
  1. RED test_fee_basic_rate (기대 150원, 실제 NameError) → GREEN 하드코딩 return 150 → REFACTOR 없음
  2. RED test_fee_large_amount → GREEN rate 일반화 (하드코딩 2개가 같은 공식 요구) → REFACTOR: 상수 추출
  3. RED test_fee_minimum_floor → GREEN max() 추가 → REFACTOR: 이름 fee→commission
### 검증: $ pytest -x -q → 3 passed in 0.07s
### 남은 TODO: 우대 등급 — 등급표 확정 대기(확인 필요: 증권사 수수료 정책)
```

❌ "테스트 3개 미리 다 쓰고 한 번에 구현" (red 3개 동시 = 보폭 과대)
✅ "한 번에 red는 1개 — 사이클당 행동 1개"

### 사용자가 권고를 거부하면

- "TDD 말고 그냥 빨리" → 따른다. 단 구현 후 핵심 분기 1개의 회귀 테스트만 제안(test-after라도 0보다 낫다). 거부 시 리스크 1줄 기록 후 진행(partial).
- "red 확인 귀찮아" → 사이클당 1회 실행이 과하면 묶음 red 확인(테스트 2~3개 단위)으로 절충 — 단 첫 테스트만은 red를 보자고 1회 제안.
- 같은 거부 반복 → 프로젝트 CLAUDE.md에 "이 프로젝트는 test-after" 규칙화 제안.

### 판단이 막힐 때 (확인 요청 4요소)

RED를 쓰려는데 기대값(이 행동의 정답)을 모르면 사이클이 멈춘다 — 추측 RED는 잘못된 명세다. 묶어서 묻는다:
- **누가**: 사용자(요구·도메인 규칙 소유자) — TODO 항목의 "원하는 행동"을 아는 주체.
- **언제**: 사이클 시작(RED 작성) 직전, 기대 출력이 불명할 때. 또는 적합도 판별이 △(스파이크)인지 모호할 때.
- **어떻게**: "현재 TODO / 추측 기대값 / 근거 / 기대 답변"으로. 예) "최소 수수료 바닥을 100원으로 가정해 RED를 쓰려는데(근거: 일반 관행), 증권사 정책값이 따로 있으면 그 값으로 — 얼마입니까?"
- **기대값**: 구체 기대 출력·정책 수치·"탐색부터(스파이크)" 중 하나. 받으면 그 값으로 RED 작성, 못 받으면 해당 TODO는 보류 표시하고 기대값이 명확한 다른 항목부터 진행(틀린 RED로 전진 금지).

## 실전 케이스 — Toyota 급발진 소송과 "테스트 불가능한 코드" (2013)

Bookout v. Toyota 재판에서 임베디드 전문가 Michael Barr가 토요타 ETCS 소스를 분석해 증언했다: 전역 변수 수천 개, 측정 불가 수준의 복잡도(cyclomatic complexity), 단위 테스트 부재의 "스파게티 코드" — 특정 태스크 죽음이 스로틀 제어를 잠그는 경로가 검증되지 않은 채 출하됐다(출처: Barr 증언 공개 슬라이드·EETimes 보도, 배심원 평결은 토요타 책임 인정). 교훈: ① TDD의 숨은 효익은 테스트가 아니라 **테스트 가능하게 강제된 설계**(작은 단위·낮은 결합)다 — 테스트를 먼저 쓰면 전역 상태 덩어리는 애초에 만들어지지 않는다 ② "나중에 테스트 붙이자"가 불가능한 코드는 만들 때 이미 결정된다.

## 사용자 환경 적용

- 수집기·정제 로직(sample-service)은 적합도 ◎ 영역 — 파서·정제는 TDD로, 키움 API 호출부는 탐색(스파이크) 후 통합 테스트로 확정(dev-testing 층 결정과 합류).
- 글로벌 test-driven-development 스킬이 세션에서 자동 발동하면: 그 가드를 끄지 말고 이 매뉴얼로 실행한다(가드=언제, 이 스킬=어떻게).

## 한계

TDD는 정확성 증명이 아니라 설계 리듬이다 — 요구사항 오해는 테스트도 같이 오해한다(red여도 잘못된 기대). 동시성·성능 결함은 이 리듬으로 안 잡힌다(→ dev-testing 한계와 동일). 연구 실증도 "결함 감소 + 초기 시간 증가"의 트레이드오프를 보고한다 — 일정이 극단적으로 짧은 일회성 작업엔 적합도 표대로 정직하게 비적합 판정을 내린다.
