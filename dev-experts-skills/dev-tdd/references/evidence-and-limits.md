# evidence + 정직한 한계 (TDD 과대 포장 경계)

## 실증·출처

- **Nagappan et al. (2008)** "Realizing quality improvement through test driven development" (Empirical Software Engineering, MS·IBM 4팀 사례) — TDD 팀의 출하 전 결함 밀도 **40~90% 감소**, 초기 개발 시간 **15~35% 증가** (확인 필요: 팀별 수치 원문 재대조). "공짜가 아니라 트레이드오프"의 표준 출처.
- **Kent Beck, *TDD: By Example* (2002)** — 가짜 구현·삼각측량·명백한 구현 3전략, TODO 리스트, Money 예제의 원전.
- **Toyota/Barr (2013)**: Bookout v. Toyota 재판의 Michael Barr 전문가 증언(공개 슬라이드) + EETimes 보도 — ETCS 코드의 전역 변수 남용·테스트 부재·복잡도. SKILL.md 실전 케이스 출처. "테스트 가능성은 만들 때 결정된다"의 실증.
- 메타 연구 주의: TDD 효과 연구들은 효과 크기가 들쭉날쭉하다(과제 크기·숙련도 교란) — "TDD가 항상 우월"은 연구가 지지하지 않는다. 일관된 신호는 결함 감소와 초기 비용, 그리고 **테스트 커버리지의 자연 상승**.

## 정직한 한계 (옹호자가 잘 말하지 않는 것)

1. **학습 곡선이 실재한다** — 처음 몇 주는 확실히 느리다. 보폭 감각(언제 좁히나)은 책이 아니라 반복으로 생긴다.
2. **요구사항 오해를 못 잡는다** — 잘못된 기대값으로 red→green을 돌면 "잘못된 것을 정확하게" 만든다. 명세 검증은 별개 활동.
3. **설계 천장** — TDD는 미시 설계(함수·클래스)를 밀어주지만 아키텍처(모듈 경계·데이터 흐름)는 따로 생각해야 한다. "테스트가 설계를 다 해준다"는 과장 (→ dev-ddd·dev-system-design).
4. **인터랙션 무거운 글루 코드** — 호출 연결만 하는 코드는 TDD 이득이 얇다. 적합도 표(✕ 영역)대로 건너뛰는 게 규율이지 태만이 아니다.
5. **기존 무테스트 코드베이스** — 거기서 TDD를 시작하려면 먼저 이음새(seam)가 필요하다 — 그건 dev-legacy-code의 특성화 테스트 영역이고, 이 스킬의 사이클은 그 다음이다.

## 출고 전 체크 (TDD 작업 단위)

- [ ] 모든 신규 테스트가 red를 거쳤다 (처음부터 green이었던 테스트 0)
- [ ] 사이클당 행동 1개 — 한 커밋에 테스트 3개+ 동시 추가 없음
- [ ] 마지막 상태가 green (red 상태로 중단·핸드오프 금지, 불가피하면 WIP 명시)
- [ ] refactor 커밋에 행동 변경 없음
- [ ] 하드코딩 잔재 없음 (삼각측량 완료) 또는 TODO에 명시
- [ ] 적합도 ✕ 영역을 TDD로 강제하지 않았다
