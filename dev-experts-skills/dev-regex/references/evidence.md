# dev-regex evidence — 장애·실증 사례

## 1. Cloudflare 글로벌 502 (2019-07-02) — WAF 정규식 백트래킹 (공식 포스트모템)

- **무슨 일**: WAF 신규 규칙의 정규식에 `.*.*=.*` 패턴 — `.*` 두 개의 겹침이 입력에 따라 백트래킹 폭주. 전 세계 엣지 서버 CPU 100% → 27분 글로벌 502. 매출·신뢰 손실 외에 "보안 장치가 장애 원인"이라는 구조적 충격.
- **증폭 요인**: WAF 규칙은 긴급 대응용 빠른 배포 경로 사용 — 점진 배포·카나리를 우회했다. 정규식 성능 테스트도 부재.
- **사후 조치(답안지)**: ① 비백트래킹 엔진 전환 검토(RE2 계열 — 입력 길이에 선형 보장) ② WAF 과부하 시 글로벌 킬 스위치 ③ 규칙 배포도 점진 배포로. 교훈: 정규식을 "설정"이 아니라 "코드"로 취급 — 테스트·배포 규율 동일 적용.

## 2. Stack Overflow 다운 (2016-07-20) — 트림 정규식과 2만 공백 (공식 포스트모템)

- **무슨 일**: 게시글 렌더링의 공백 트림 정규식 `^[\s‌]+|[\s‌]+$` 가 약 2만 개 연속 공백+비공백 문자로 끝나는 게시글에서 O(n²) 백트래킹 — 렌더링 스레드 점유로 34분 전면 다운. 악의 입력도 아니고 우연한 게시글 하나였다.
- **메커니즘**: `[\s]+$`가 끝 아님이 판명될 때마다 시작 위치를 한 칸씩 옮겨 재시도 — 20,000 공백이면 ~2억 문자 비교.
- **수정**: 정규식 제거, 단순 substring 트림으로 — "정규식이 가장 짧은 코드지만 가장 빠른 코드는 아니다"의 표본. 트림·고정 접두/접미 검사 같은 단순 연산은 문자열 함수가 항상 우위.

## 3. 백트래킹 산식 — 왜 "실패하는 입력"이 무기인가

- **원리**: `(a+)+$`에 `"a"×n + "b"` 입력 — 끝의 b 때문에 전체 매치는 불가능하지만, 엔진은 a들을 그룹에 배분하는 모든 방법(2ⁿ⁻¹)을 시도한 후에야 실패를 선언한다. **n=30이면 5억 경로** — 입력 31바이트로 CPU 수 분.
- **검출 휴리스틱**: ① 수량자 안에 수량자(`(X+)*`) ② 선택지 겹침(`(a|ab)+`) ③ 인접 토큰이 같은 문자를 먹을 수 있음(`.*.*`) — 셋 중 하나면 정밀 점검. 도구: 각 언어용 ReDoS 정적 검사기(regexploit 등) + "긴 비매치 입력 시간 측정" 스모크 1줄.
- **구조적 해법 서열**: 비백트래킹 엔진(RE2 — 선형 보장, 단 역참조 불가) > 패턴 재설계(상호배타 클래스) > 매치 타임아웃(.NET·Java 내장) > 입력 길이 제한(최후).
