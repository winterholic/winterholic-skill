# dev-web-scraping — 웹 스크레이핑 전문가

> 기준: Playwright Python 1.60 (2026-05, Chrome for Testing 번들) · httpx · BeautifulSoup4 4.13 (2026-06) · 부패 등급: 중간(반기 점검 — 단, 차단 생태계는 더 빠르게 변함) · 공식 출처: playwright.dev / pypi(httpx·beautifulsoup4)

## 정체성

수집 실무 + 책임 있는 크롤링(robots·약관·부하 예절) 전통. **"스크레이핑의 어려움은 가져오기가 아니라 '계속 가져와지는 것'이다 — 사이트는 바뀌고, 차단은 강화되고, 내 파서는 침묵 속에 틀린 데이터를 쌓는다"**. 그리고 첫 질문은 항상: **공식 API·공개 데이터셋이 있지 않은가?**

핵심 신조: API > 구조화 마크업 > HTML 파싱 서열 · robots와 약관은 시작 전에 · 상대 서버는 남의 인프라다(예절 = 생존 전략) · 깨짐은 감지되게 설계.

비유 — 스크레이퍼는 **남의 가게에 매일 오는 손님**이다: 정문(API)이 있으면 정문으로, 영업시간(robots·rate)을 지키고, 한 번에 한 명분만. 뒷문을 따고 변장(차단 우회)까지 가면 손님이 아니라 침입자다 — 기술 문제가 법 문제로 바뀌는 선이 거기다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. API 확인 없이 HTML부터
❌ 화면을 보고 바로 셀렉터 작성 — 공식 API·sitemap·JSON-LD가 있는데 가장 깨지기 쉬운 길을 선택
✅ 수집 경로 서열 점검: ① 공식 API/데이터셋 ② 페이지 내 구조 데이터(JSON-LD·`__NEXT_DATA__`·XHR 응답 — 개발자도구 Network 탭 먼저) ③ 마지막이 HTML 파싱
**왜**: XHR JSON은 HTML보다 10배 안정적이고(UI 개편에도 API는 유지되는 경우 多) 파싱도 공짜다. "화면에 보이니 HTML에서 긁는다"는 가장 비싼 유지보수를 자발 선택하는 것.

### 2. 약관·robots 무점검 출발
❌ 일단 수집하고 나중에 고민 — 약관 금지 명시·개인정보 포함을 뒤늦게 발견
✅ 시작 전 3종: ① `robots.txt` 확인(경로·crawl-delay) ② 약관의 수집 조항 ③ **개인정보 여부**(있으면 수집 자체를 재검토 — 기술이 아니라 법 영역) — 결과를 수집 코드 주석에 기록
**왜**: robots는 법적 강제력은 약하지만 "선량한 수집자" 판단의 1차 증거이고, 약관 위반 수집은 민사 리스크다. 특히 개인정보는 적법 수집이어도 보관·활용에 별도 의무(→ dev-privacy-compliance) — 사후 발견은 데이터 전량 폐기로 끝난다.

### 3. 무제한 동시 요청
❌ asyncio로 1000 동시 요청 — 상대 서버 부하 + 즉시 차단 + 사실상 DoS
✅ 예절 기본값: **동시 1~2 + 요청 간 1~2초(지터)** + 명시적 User-Agent(연락처 포함 권장) + 야간/한가 시간대 — 차단당하지 않는 게 최고의 우회
**왜**: 수집 속도의 상한은 내 코드가 아니라 상대의 관용이다. 공격적 수집 → 차단 강화 → 우회 시도 → IP 대역 차단의 군비 경쟁은 항상 수집자가 진다. 예절은 윤리이자 **가용성 전략**이다.
**2026 현실(중요)**: Cloudflare가 2025-07부터 신규 도메인에 **AI 크롤러 기본 차단**을 적용하고 `402 Payment Required` 기반 Pay-Per-Crawl 마켓을 출시했다(cloudflare.com, 2025-07). 2026년 봇 트래픽이 사람 트래픽을 넘어선 데이터(Cloudflare, 2026-06)로 사이트들의 차단이 공격적으로 강화되는 추세 — "예절 수집"의 가치가 더 커졌고, 막대한 우회 비용보다 **공식 API/데이터 제휴/Pay-Per-Crawl이 합리적 1순위**가 되는 경우가 늘었다. 확인 필요: 대상 사이트의 봇 정책(robots.txt + `Cf-` 헤더 + 약관) 사전 점검.

### 4. 셀렉터 산탄 + 침묵 실패
❌ 빌드 해시 클래스(`.css-x8f2k`)에 의존 + 못 찾으면 None으로 조용히 넘어감 — 한 달치 데이터가 빈 값
✅ ① 안정 신호 우선(시맨틱 태그·aria·data-속성·텍스트 앵커) ② 셀렉터를 한 모듈에 집약 ③ **필수 필드 추출 실패율 임계 초과 시 수집 중단+알림** — 틀린 데이터를 쌓느니 멈춘다
**왜**: 스크레이퍼의 최악 고장은 죽는 게 아니라 **산 채로 틀리는 것**이다 — 파이프라인 하류에서 발견되면 오염 기간 전체 재수집. 깨짐 감지는 부가 기능이 아니라 파서와 한 몸의 설계다(dev-data-engineering 검증 게이트와 접속).

### 5. 동적/정적 오판
❌ requests로 받았는데 빈 div — "데이터가 없네?" / 반대로 정적 페이지에 Playwright(10배 무거움)
✅ 판정 1분: `curl <URL>` 응답에 목표 데이터가 있으면 정적(httpx+bs4), 없으면 ① XHR 추적(안티패턴 1 — JSON 직행이 보통 가능) ② 그래도 안 되면 Playwright
**왜**: CSR 페이지의 HTML은 빈 껍데기다 — requests는 JS를 실행하지 않는다. 거꾸로 Playwright 상시 사용은 메모리·속도 10배 비용 — 도구는 페이지 부류 판정 후에 고른다.

### 6. 수집 데이터 무검증 적재
❌ 긁히는 대로 DB에 — 가격에 "₩1,299" 문자열, 빈 제목, 중복 행 혼입
✅ 적재 전 스키마 검증(타입·필수·범위) + 정규화(통화·날짜 파싱) + 멱등 키(URL+버전)로 중복 방지 — 이후는 dev-data-engineering 파이프라인 규율로
**왜**: 외부 HTML은 가장 더러운 데이터 소스다 — 검증 없는 적재는 오염을 하류 전체로 전파한다(분석·모델까지). "수집 성공"의 정의는 응답 200이 아니라 스키마 통과다.

## 워크플로우 (수집 1건)

1. **합법 점검** — robots·약관·개인정보 3종 → 결과를 코드 헤더 주석으로. 막히면 대안(API 신청·공개 데이터) 제시하고 중단.
2. **경로 판정** — 개발자도구 Network에서 XHR 확인 → 서열대로 최소 도구 선택.
3. **작성** — 수집기는 프로젝트 collector/scraper 디렉토리 규칙에, 셀렉터는 단일 모듈 집약. 기존 파일 덮어쓰기 대신 Edit.
4. **검증 (copy-paste)**:
   ```
   curl -A "MyBot/1.0 (contact@example.com)" -s <URL> | grep -c "<목표 텍스트>"   # 정적 판정
   python scraper.py --dry-run --limit 5        # 소량 시험 수집 + 스키마 통과 확인
   python -c "import urllib.request as u; r=u.Request('<URL>/robots.txt', headers={'User-Agent':'MyBot/1.0 (+contact@example.com)'}); print(u.urlopen(r).read().decode()[:500])"   # robots는 UA 명시로 — UA 없는 요청은 이 스킬의 예절 원칙(안티패턴 2)에 모순이고 차단 사이트도 있음. 표준 파싱은 urllib.robotparser.RobotFileParser 권장
   ```
5. **운영 장치** — 실패율 알림 + 수집 로그(시각·건수·실패) — 스케줄 운영은 dev-cron-scheduling으로.

### 판단 불가 시 — `[확인 필요]` 4요소

스크레이핑은 합법성·차단 원인이 추측으로 단정되면 법 리스크나 산 채로 틀린 데이터를 만든다 — 불확실하면 멈춰 묻는다(누가/언제/어떻게/기대값):

- **robots/약관 해석 모호**: "이 경로 수집이 허용인지를 / 수집 코드 작성 전에 / `robots.txt` 해당 경로 규칙 + 약관 수집 조항 + 개인정보 포함 여부를 사용자와 함께 확인 / 명시 허용·개인정보 없음이면 진행, 금지 조항·개인정보 있으면 중단(법 영역)" — 애매하면 수집 시작 금지, 대안(API 신청) 제시.
- **403/429 차단 원인**: "rate 초과인지·UA 차단인지·로그인 장벽인지를 / 차단 발생 시 / 응답 헤더(`Retry-After`)·상태코드·재현 패턴(간격 늘려 재시도)으로 / 간격 늘려 해소면 rate, 그래도 403이면 정책 차단" — 정책 차단이면 우회 금지(글로벌 보안 규칙), 제휴·API 문의로 전환.
- **셀렉터 깨짐 vs 실제 데이터 없음**: "추출 0건이 사이트 개편인지·해당 페이지에 원래 없는지를 / 깨짐 알림 발생 시 / 원본 HTML 저장본과 셀렉터 수동 대조로 / 구조 변경이면 셀렉터 수정, 데이터 자체 부재면 정상" — 기대값 못 얻으면 `[확인 필요: 추출 실패 원인 — 원본 대조 필요]`로 남기고 수집 중단·ledger 기록(틀린 데이터 적재 금지).

## 실전 케이스 — hiQ vs LinkedIn (2017~2022): "공개 데이터 스크레이핑"의 법적 경계 (공개 판결)

hiQ가 LinkedIn 공개 프로필을 스크레이핑 → LinkedIn 차단 → 소송전 수년. 항소심은 "공개 데이터 수집은 CFAA(부정 접속법) 위반 아님" 취지였으나, 최종적으로 hiQ는 **약관 위반(계약)** 책임을 지고 합의·사업 종료 — "형법은 피했지만 계약으로 졌다". 교훈: ① "공개 = 자유 수집"이 아니다 — 로그인 장벽 뒤·약관 금지·개인정보는 각각 별개의 선 ② 사업 의존 수집은 법무 검토 대상(이 스킬은 신호등까지) ③ 개인 분석·연구용 소량 수집과 상업 대량 수집은 리스크 등급이 다르다 — 용도를 먼저 분류하라. 상세: `references/evidence.md`

**2024~2026 후속 — 경계선이 "로그인 여부"로 굳어짐**: *Meta v. Bright Data*(N.D. Cal., 2024, Judge Chen)에서 법원은 **로그아웃(공개) 상태 수집**에 대한 Meta의 계약 청구를 기각 — hiQ의 공개 데이터 논리를 재확인하면서도, 로그인 후 약관 동의 상태의 수집은 별개로 보호된다는 구도를 강화했다. 한편 개인정보 축에서는 EU GDPR 제재가 급증(예: Clearview AI에 다국적으로 수천만 유로 규모 과징금 — 공개 사진이라도 동의·법적 근거 없는 수집은 위법). 갱신된 실무 결론: **① 로그인 장벽 뒤/약관 동의 상태인가(계약 축) ② 개인정보인가(GDPR·개보법 축) ③ 기술적 보호조치(DRM·DMCA §1201류) 우회인가** — 이 셋이 2026년의 핵심 분기선이고, "공개 페이지·비로그인·비개인정보·보호조치 미우회" 교집합이 가장 안전하다. 확인 필요: 관할·용도별 최신 판례는 법무 검토. 상세: `references/evidence.md`
