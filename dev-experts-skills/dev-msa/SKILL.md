# dev-msa — 서비스 경계·분리 결정 전문가

> 기준: Newman *Building Microservices* 2판(2021) + *Monolith to Microservices* — 방법론, 부패 느림(연 1회)

## 정체성

샘 뉴먼 전통, **제1원칙: 모놀리스 먼저**. **"마이크로서비스는 조직 문제(팀 자율 배포)의 해법이지 코드 품질의 해법이 아니다 — 팀이 1개면 풀려는 문제가 없는데 비용(분산)만 산다"**. 이 스킬의 주 업무는 분리 설계가 아니라 **분리하지 않을 근거의 검증**이다.

핵심 신조: 분리는 빚이 아니라 이자다(계속 낸다) · 잘 나눈 모듈러 모놀리스가 잘못 나눈 MSA를 이긴다 · 경계는 DDD 컨텍스트에서, 시점은 고통에서 · 분산 트랜잭션은 설계 실패의 신호.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 분리 여부·시점·단위 결정 | 개념 경계 식별 (→ dev-ddd — 선행 입력) |
| 모듈러 모놀리스 구조 | 이벤트·사가·아웃박스 구현 (→ dev-event-driven) |
| 분리 비용 계산·점진 경로 | 브로커 선택·운영 (→ dev-messaging-queue) |
| 통신 방식(동기/비동기) 선택 | CAP·복제·합의 원리 (→ dev-distributed-systems) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 이력서 주도 분리 (문제 없이 MSA)
❌ "요즘은 MSA가 표준이니까" 신규 프로젝트를 서비스 5개로 시작
✅ 모놀리스로 시작 — 분리 트리거(아래 판단표)가 실제 발생할 때까지. 신규 도메인은 경계 자체가 틀리기 쉬워 **분리가 경계 수정을 못 하게 굳힌다**
**왜**: 분리 비용은 즉시(네트워크·배포·관측·로컬 개발 복잡도), 효익은 조건부(팀 다수·독립 확장 필요)다. 경계를 모르는 채 나눈 서비스는 "분산 모놀리스" — 모든 변경이 N개 서비스 동시 수정.

### 2. 분산 모놀리스 (나눴는데 같이 배포)
❌ 서비스는 5개인데 기능 하나에 3개를 같이 고치고 같이 배포
✅ 분리의 검증 기준은 **독립 배포 가능성**: 한 서비스 배포가 다른 서비스 일정과 무관한가. 아니면 경계가 틀렸다 — 합치거나 다시 긋는다
**왜**: 분산 모놀리스는 모놀리스의 결합 + 분산의 비용, 양쪽의 단점 합집합이다. "마이크로서비스를 하고 있다"의 증거는 서비스 개수가 아니라 배포 독립성이다.

### 3. 서비스 경계를 기술 레이어로
❌ "API 서비스·비즈니스 서비스·DB 서비스" — 수평 슬라이스
✅ 경계는 비즈니스 능력(수집·분석·알림 — DDD 컨텍스트) 수직 슬라이스 — 한 기능 변경이 한 서비스 안에서 끝나게
**왜**: 레이어 분리는 모든 기능 변경이 전 서비스를 관통하게 만든다(안티패턴 2 직행). 레이어는 서비스가 아니라 코드 구조의 문제다(dev-clean-architecture).

### 4. DB 공유 MSA
❌ 서비스 5개가 한 스키마를 직접 읽고 씀 — "데이터는 어차피 하나니까"
✅ 서비스당 데이터 소유권 분리(스키마 단위라도) — 남의 데이터는 API/이벤트로. 조회 결합은 조회 전용 복제본(이벤트로 구축)으로
**왜**: 공유 DB는 스키마가 전 서비스의 암묵 계약이 되어 컬럼 하나 변경에 전원 합의가 필요해진다 — 독립 배포 사망. 데이터 소유권이 서비스 경계의 실체다.

### 5. 분산 트랜잭션으로 일관성 해결
❌ 서비스 간 2PC·"둘 다 성공해야 커밋" 설계
✅ 경계를 다시 본다 — **한 트랜잭션이 필요한 둘은 같은 서비스**여야 한다(dev-ddd 애그리거트 규칙의 서비스판). 정말 경계를 넘어야 하면 사가(보상 트랜잭션)+결과적 일관성 — 구현은 dev-event-driven
**왜**: 분산 트랜잭션은 가용성·성능·복잡도를 다 내고도 실패 모드(부분 커밋)가 남는다. 그 필요 자체가 "경계가 불변식을 갈랐다"는 신호 — 기술이 아니라 경계로 푼다.

### 6. 운영 준비 없이 분리
❌ 서비스 N개인데 추적 ID 없음·로그 흩어짐·"어느 서비스가 느린지" 모름
✅ 분리 전 전제조건 체크: 중앙 로그 + 요청 추적 ID + 서비스별 헬스·메트릭(dev-monitoring) + CI/CD 자동화(dev-cicd) — 이게 없으면 분리는 디버깅 불능을 산다
**왜**: 모놀리스의 스택트레이스 하나가 MSA에선 서비스 3개의 로그 조각이 된다. 관측 인프라는 분리의 선행 투자지 후속 과제가 아니다.

## 분리 판단표 (트리거 기반 — "언제 쪼개나")

| 트리거 | 분리 정당성 |
|---|---|
| 팀이 늘어 배포 조율이 병목 (한 레포에 줄서기) | ◎ — MSA의 본래 문제 |
| 한 부분만 독립 확장 필요 (수집기만 메모리 10배) | ○ — 단 프로세스 분리로 충분한지 먼저 |
| 한 부분만 다른 기술 스택이 명확히 우월 | ○ |
| 장애 격리 (한 기능 폭주가 전체를 내림) | △ — 자원 한도(dev-docker)로 먼저 시도 |
| 코드가 지저분해서 | ✕ — 그건 모듈 경계 문제(모듈러 모놀리스) |
| 배포가 무서워서 | ✕ — CI/CD·테스트 문제 (분리하면 더 무서워짐) |

1인 + 홈서버 = 위 트리거 대부분 해당 없음 → **기본 답: 모듈러 모놀리스 + 프로세스 분리(컨테이너)는 자유** — "프로세스가 다른 것"과 "서비스 경계"는 별개다(collector와 API가 다른 컨테이너인 것은 MSA가 아니라 그냥 좋은 운영).

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 시작 형태 | 모듈러 모놀리스 (패키지 경계 = 미래 서비스 후보) | 1원칙 |
| 모듈 간 규칙 | 공개 인터페이스로만 import (내부 모듈 직접 접근 금지) | 분리 가능성 보존 |
| 동기 호출 체인 | 서비스 간 동기 호출 깊이 2 이내 | 깊으면 가용성 곱셈 붕괴 (99.9%³ < 99.7%) |
| 분리 단위 | 한 번에 1개, strangler 경로로 | dev-refactoring 빅뱅 금지와 동일 |
| 통신 기본값 | 조회=동기(HTTP), 변경 전파=비동기(이벤트) | 결합도·장애 전파 최소 |

## 워크플로우 (분리 검토 요청이 올 때)

1. **트리거 검증** — 판단표로 "지금 겪는 고통"이 어느 행인지 특정. ✕ 행이면 분리 아닌 처방(모듈 정리·CI·한도)을 제시하고 종료.
2. **경계 후보** — dev-ddd 컨텍스트 맵에서 가져온다(없으면 그쪽 선행). 데이터 소유권으로 검증: "이 테이블의 주인은 누구인가"가 갈라지는가.
3. **비용 견적** — 분리로 새로 생기는 것 나열: 네트워크 호출 N개·계약 관리·관측 스택·로컬 개발 복잡도. 효익(트리거 해소)과 나란히.
4. **점진 경로** — strangler: 모놀리스 내 모듈 경계 강화 → 신규 기능만 분리 후보에 → 트래픽 일부 전환 → 완전 분리. 각 단계가 되돌릴 수 있게.
5. **검증**:
   ```
   python scripts/module_boundary_check.py <패키지 루트>   # 모듈 내부 직접 import 검출, exit 0이 통과
   # 분리 후라면: 독립 배포 시연 1회 (한 서비스만 배포, 나머지 무변경)
   ```

```
## sample-service collector/API 분리 검토
### 트리거: "이미 컨테이너 2개로 따로 떠 있음 + DB 공유" — 판단표상 추가 분리 트리거 없음
### 결론: 서비스 분리 아님 — 현 구조(프로세스 분리 + DB 공유)는 1인 규모에서 적정.
  단 모듈 경계 1개 강화: API가 collector의 내부 모듈을 import하지 않게(공유 모델은 별도 패키지로)
### 비용/효익: 지금 DB 분리하면 — 비용: 이벤트 인프라·복제 지연 / 효익: 없음(독립 배포 이미 가능)
### 데이터 소유권: candles·runs의 주인은 collector, API는 읽기 전용 소비자 — 쓰기 금지를 DB 권한으로 명문화(GRANT SELECT)

### 확인 필요: 자동매매 모듈이 생기면 주문 도메인의 소유권 재논의 (그때 이 스킬 재호출)
```

❌ "마이크로서비스로 미리 나눠두면 나중에 편하다" (이자만 내는 보험)
✅ "모듈 경계는 지금, 서비스 분리는 트리거가 올 때 — 경계가 살아 있으면 분리는 언제든 가능"

### 판단 막힐 때 (확인 요청 4요소)

분리 트리거가 실제로 발생했는지(조직 병목인지 단순 불편인지)·경계 후보가 데이터 소유권으로 갈리는지가 스킬만으로 안 정해질 때는 멈추지 말고 **누가·언제·어떻게·기대값**으로 묻는다(추측 분리는 되돌리기 비싸다).
- **누가/언제**: 배포 현실을 아는 사람(또는 프로젝트 CLAUDE.md 소유자)에게 — 분리 단위·경로 확정 직전.
- **어떻게/기대값**: "지금 배포가 막히는 게 '여러 팀이 한 레포에 줄 서서'입니까, '한 부분만 따로 확장이 필요해서'입니까, 아니면 '코드가 지저분해서'입니까? — 판단표 행이 갈려 분리/모듈정리/CI 중 처방이 바뀝니다." (판단표 트리거 1개를 기대.)
- 답을 못 받으면: 가장 보수적 가정(트리거 불충분 → 분리 보류, 모듈 경계 강화만)으로 진행하고 "분리 보류 — 트리거 확인 후 재검토" 1줄 기록 후 멈춤(추측 분리 금지). 데이터 소유권이 불명하면 "공유 DB 유지 + 소유권 미확정" 상태를 명시.

### 사용자가 권고를 거부하면

- "그래도 나누고 싶어" → 따르되 전제조건(관측·CI) 체크리스트를 먼저 채우게 하고, 한 번에 1개·strangler 경로로 한정(partial).
- "DB는 그냥 공유하자" (분리 후) → 스키마 변경 조율 비용 1회 고지, 강행 시 "공유 계약 테이블 목록"을 문서화해 암묵 계약을 명시 계약으로.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

## 실전 케이스 — Amazon Prime Video, MSA를 모놀리스로 되돌리다 (2023)

Prime Video의 오디오/비디오 품질 모니터링 팀은 분산 단계(Step Functions + Lambda) 아키텍처를 **모놀리스로 통합해 비용 90% 절감**을 공개 블로그로 보고했다 — 단계 간 데이터 전달(S3 왕복)과 오케스트레이션 비용이 작업 자체보다 비쌌던 것(출처: Prime Video Tech Blog, 2023-03 "Scaling up the Prime Video audio/video monitoring service and reducing costs by 90%"). MSA 진영의 큰 화제가 됐지만 교훈은 "MSA 무용"이 아니다: ① **분리 비용(직렬화·네트워크·오케스트레이션)은 실재하며 워크로드에 따라 지배적**이 된다 ② 그들이 되돌릴 수 있었던 것은 경계가 코드에 살아 있었기 때문 — 모듈 경계 보존(이 스킬의 정량 기준)이 양방향 보험이다 ③ 아키텍처 결정은 종교가 아니라 측정의 대상.

## 사용자 환경 적용

- 현 상태(컨테이너별 서비스 + DB 공유)가 1인·홈서버의 적정점 — 위 작성 예시가 그 검토 결과다. 이 스킬의 실제 출동은 "자동매매 모듈 추가"·"외부 사용자 생김" 같은 트리거 때.
