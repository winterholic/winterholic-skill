# dev-messaging-queue — 브로커·작업 큐 운영 전문가

> 기준: 브로커 중립 원리 + Kafka/RabbitMQ/Redis Streams 어휘 (2026-06) · 부패 등급: 중간(반기)

## 정체성

브로커 운영 실무 전통. **"큐는 부하를 없애주지 않는다 — 시간축으로 옮겨줄 뿐이다. 소비가 생산을 영구히 못 따라가면 큐는 해법이 아니라 지연 저장소다"**. 이 스킬의 절반은 브로커 선택이 아니라 **브로커가 필요 없는 경우의 판별**이다(DB 큐로 충분한 규모가 길다).

핵심 신조: 가장 작은 브로커부터(DB 큐 → Streams → 전용 브로커) · 모든 큐에 DLQ와 알림 · lag은 1급 지표 · poison 하나가 파티션을 막는다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 브로커 선택·컨슈머·DLQ·lag | 이벤트 스키마·멱등·아웃박스 (→ dev-event-driven — 선행) |
| 작업 큐(지연 작업·재시도) 운영 | 큐를 쓸지 자체 (→ dev-msa 통신 기본값) |
| poison·백프레셔 대응 | Redis 캐시 용법 (→ dev-redis) |
| 적체 모니터링 연결 | 경보 설계 (→ dev-monitoring) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 규모 없이 Kafka부터
❌ 일 수천 건 작업에 Kafka 클러스터 — 운영 비용(브로커·ZK/KRaft·파티션 설계)이 일보다 큼
✅ 선택 사다리: **① DB 큐**(테이블 + SELECT FOR UPDATE SKIP LOCKED — 일 수만 건까지 충분) → **② Redis Streams**(이미 Redis 있고 초당 수백) → **③ RabbitMQ**(라우팅·작업 큐 본격) → **④ Kafka**(리플레이·대용량 스트림·다중 구독이 본질 요구일 때)
**왜**: 브로커는 인프라다 — 운영(업그레이드·모니터링·장애 대응)을 평생 산다. DB 큐는 기존 백업·트랜잭션·운영을 공짜로 상속(아웃박스와 한 몸이 되는 보너스 — dev-event-driven). "Kafka 경험 쌓기"는 이력서 주도(dev-msa #1)다.

### 2. DLQ 없는 재시도 무한 루프
❌ 실패 메시지를 무조건 재큐잉 — poison message(영원히 실패할 메시지)가 무한 회전하며 로그 폭주·처리량 잠식
✅ 재시도 N회(지수 백오프) → **DLQ로 격리 + 알림** → DLQ는 사람이 본다(수리 후 재투입 절차 문서화). 재시도 가능/불가 에러 분류는 dev-data-engineering 재시도 규칙 동일
**왜**: 파싱 불가 메시지는 백 번 재시도해도 파싱 불가다 — 재시도는 일시 장애용이지 결함용이 아니다. DLQ 없는 큐는 poison 하나에 전체가 인질로 잡힌다(순서 보장 큐면 뒤 메시지 전부 블록).

### 3. ack 시점 오류 (받자마자 ack / 처리 후 ack 혼동)
❌ 수신 즉시 ack 후 처리 — 처리 중 죽으면 메시지 유실 (at-most-once를 모르고 선택)
✅ **처리 완료 후 ack**(at-least-once — 기본값) + 소비 멱등(dev-event-driven #2)이 세트. 유실 허용 작업만 선-ack를 의식적으로
**왜**: ack 시점이 전달 보장을 결정한다 — 프레임워크 기본값(auto-ack 여부)을 모른 채 쓰면 보장을 모른 채 운영하는 것. "가끔 작업이 사라져요"의 1순위 원인.

### 4. lag 무관측 (적체를 사용자 신고로 알기)
❌ 컨슈머가 며칠 죽어 있었는데 아무도 모름 — 큐가 조용히 수백만 건
✅ lag(미처리 깊이)을 1급 지표로: 임계+증가 추세 경보(dev-monitoring) — "lag > N **그리고** 30분째 증가"가 좋은 경보(절대값만은 배치 직후 오탐)
**왜**: 큐는 장애를 숨기는 장치이기도 하다 — 생산자는 정상이므로 아무 에러가 없다. lag만이 소비 측 사망을 말해준다. dev-data-engineering의 "exit 0 ≠ 성공"과 동일 구조.

### 5. 순서 필요 작업을 경쟁 컨슈머에
❌ 같은 주문의 [생성→수정→취소]를 컨슈머 3개가 경쟁 소비 — 취소가 생성보다 먼저 처리
✅ 순서 단위(주문 ID)를 파티션 키/단일 큐로 직렬화 — dev-event-driven #3의 운영판. 키 안 순서 + 키 간 병렬이 표준 구도
**왜**: 경쟁 컨슈머(work queue)는 처리량을 사고 순서를 판다 — 그 거래를 모르고 하면 상태 기계가 깨진다. "가끔 순서가 바뀌어요"는 버그가 아니라 토폴로지 선택의 결과다.

### 6. 무한 큐 가정 (백프레셔 무설계)
❌ 생산 속도 무제한 — 브로커 디스크/메모리 풀 때까지
✅ 한도를 명시: 큐 길이/보존 기간 상한 + 도달 시 정책(생산 차단 vs 오래된 것 폐기 vs 샘플링)을 **도메인이 결정** — 시세 틱이면 "최신 우선·옛 틱 폐기"가 보통 옳고, 주문이면 차단이 옳다
**왜**: 큐가 차는 날은 반드시 온다(소비자 장애 + 생산 피크). 정책 없이 차면 브로커 OOM·디스크 풀로 **생산자까지** 죽는다 — 부하 이전 장치가 부하 증폭 장치로.

## 실전 케이스 — poison message가 멈춘 파이프라인들 (공식 문서가 패턴이 된 이유)

AWS SQS가 DLQ를 1급 기능으로, Kafka 생태계가 "poison pill" 처리를 표준 문서로 다루는 것은 이 실패가 보편이라서다 — 대표 공개 사례로 **역직렬화 불가 메시지 1건이 컨슈머를 크래시 루프에 빠뜨려 파티션 전체가 멈추는** 구조가 Confluent 공식 블로그("Spring for Apache Kafka — poison pill" 등)에 재현 코드와 함께 정리돼 있다. 컨슈머는 재시작 → 같은 오프셋 → 같은 크래시 — lag만 자라고 에러 로그는 같은 줄 반복. 교훈: ① 큐의 실패 모드는 "안 돎"이 아니라 "한 건에 막힘"이다 — DLQ는 선택이 아니라 가동 조건 ② 역직렬화·검증 실패는 재시도 불가 분류의 대표 — 즉시 격리 ③ 크래시 루프 + lag 증가 조합 경보(안티패턴 4)가 이 모양의 검출기다.

## 사용자 환경 적용

- 현 규모의 정답은 거의 항상 **DB 큐**(위 작성 예시) — 이미 PostgreSQL·백업·모니터링이 있다. Redis Streams 승격은 Redis가 다른 이유로 이미 떠 있고 처리량이 DB 큐를 넘어설 때. Celery류 프레임워크는 워커 1~2개 규모에선 자체 루프(SKIP LOCKED 폴링)보다 운영 무게가 크다.

## 한계

브로커 중립 원리 중심 — 특정 브로커의 운영 세부(Kafka 파티션 재배치·RabbitMQ 미러링)는 그 선택 후 공식 문서가 1차. 스트림 처리(윈도우 집계·조인 — Kafka Streams/Flink)는 별개 영역(그 요구면 도구 선정부터 재검토). 정확히-한-번 마케팅은 여기서도 의심 대상(dev-event-driven 신조).
