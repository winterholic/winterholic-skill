# 상황→패턴 결정 표 + 패턴별 함정 체크리스트 (SKILL.md 비중복)

## 상황(증상) → 구조 결정 표

| 증상 | 1차 처방 | 패턴 이름(필요 시) |
|---|---|---|
| 같은 알고리즘의 변형이 늘어남 | 함수 전달 → 3개째에 레지스트리 | Strategy |
| 객체 생성이 여러 곳에서 복잡하게 반복 | 생성 함수 1개 → 의존 조립이면 조립 지점(main)으로 | Factory / DI |
| "X가 변하면 Y도 알아야" 결합 | 콜백 등록 → 많아지면 이벤트 이미터 | Observer |
| 외부 라이브러리 API가 우리 코드 전체에 침투 | 얇은 래퍼 모듈 1개로 격리 | Adapter/Facade |
| 요청을 기록·취소·재실행해야 | 요청을 데이터로(dataclass) + 핸들러 | Command |
| 단계 고정·일부만 교체 | 교체 부분을 함수 인자로 | Template Method의 번역 |
| 상태별로 가능한 행동이 다름 | 구별된 유니언 + 전이 함수 | State |
| 기존 객체에 횡단 기능(로깅·캐시) | 데코레이터/고차함수 | Decorator |
| 무거운 객체 접근 제어·지연 | 지연 속성·캐시 함수 | Proxy의 번역 |
| 복잡한 객체 단계 조립 | 키워드 인자 + dataclass가 보통 충분 | Builder (파이썬에선 드묾) |

읽는 법: 증상 없이 이 표를 위에서부터 적용하는 것이 바로 패턴 강박이다 — 증상 칸이 먼저 채워져야 한다.

## 패턴별 알려진 함정 (이름의 색인 가치 — 직접 구현 시 점검)

### Observer / 이벤트
- [ ] 콜백 안 예외가 다른 구독자를 죽이는가 (격리 try + 로깅)
- [ ] 해지(unsubscribe) 경로가 있는가 — 누수의 단골
- [ ] 알림 순서에 의존하는 구독자가 있는가 (있으면 설계 재고)
- [ ] 콜백에서 다시 발행(재진입) 시 무한 루프 가드

### Strategy / 레지스트리
- [ ] 미등록 키 처리 (KeyError를 의미 있는 에러로)
- [ ] 전략 간 공유 상태 없음 (있으면 전략이 아니라 모드 플래그)

### Factory / DI
- [ ] 조립이 한 곳(main/lifespan)에 모여 있는가 — 흩어진 new가 DI를 무효화
- [ ] 순환 의존 생성 시도 없는가

### Decorator (런타임 조합)
- [ ] 순서 의존성 문서화 (압축→암호화 ≠ 암호화→압축)
- [ ] 파이썬 @데코레이터면 functools.wraps (dev-python 데코레이터 규칙)

### Command / undo
- [ ] undo가 진짜 역연산인가(부수효과 복원 포함) — 단순 반대 호출이 아닐 수 있음
- [ ] 스택 크기 상한

### Adapter/Facade (경계 격리)
- [ ] 래퍼가 외부 타입을 그대로 노출하지 않는가 (노출하면 격리 실패 — 우리 타입으로 변환)
- [ ] 외부 예외를 우리 예외로 번역하는가

## "패턴인 척" 식별 (읽기용)

- 클래스 이름에 ~Manager/~Helper/~Util — 패턴 아님, 책임 미정의 신호.
- Factory라는 이름인데 분기 없이 한 가지만 생성 — 그냥 생성자.
- Visitor라 부르는데 이중 디스패치 없음 — 그냥 순회.
- 이름과 구조가 어긋난 코드는 이름부터 고치는 게(dev-refactoring rename) 패턴 적용보다 먼저다.
