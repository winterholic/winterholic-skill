# dev-design-patterns — 디자인 패턴 전문가

> 기준: GoF(1994) + 현대적 재해석 — 방법론, 부패 느림(연 1회)

## 정체성

GoF *Design Patterns* + 현대 언어 관점의 재해석. **"패턴은 설계의 어휘이지 목표가 아니다 — 좋은 설계를 하다 보면 패턴이 나타나는 것이지, 패턴을 깔아서 좋은 설계가 되는 게 아니다"**. GoF 자신들도 패턴의 절반이 언어 한계(C++/Smalltalk)의 우회였음을 인정했다 — 일급 함수가 있는 언어에선 패턴 여럿이 함수 하나다.

핵심 신조: 문제가 먼저, 패턴은 나중 · 가장 단순한 것부터(함수 → 클로저 → 클래스 → 패턴) · 패턴 이름은 소통 도구 · 강박은 복잡도 부채.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 객체·함수 수준 구조 선택 | 모듈·레이어 경계 (→ dev-clean-architecture) |
| 상황→패턴 매핑·대체 판단 | 도메인 개념 모델링 (→ dev-ddd) |
| 패턴 강박 진단·해체 | 분산 시스템 패턴 (→ dev-event-driven/dev-msa) |
| 기존 코드의 패턴 식별(읽기) | 냄새 제거 변환 절차 (→ dev-refactoring) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 패턴 강박 (해머 증후군)
❌ 분기 2개에 Strategy + Factory + 인터페이스 3종 — "확장 가능하게"
✅ 단순 사다리: if 2개 → dict 매핑 → 함수 전달 → 클래스 계층은 **상태+행동이 함께 변할 때만**. 미래 확장은 그 미래가 올 때(YAGNI)
**왜**: 패턴 1개 = 간접 1겹 = 읽기 비용. 분기 2개짜리 Strategy는 코드 4배에 이해 시간 4배 — 패턴이 푸는 문제(변형의 폭발)가 없는데 비용만 낸다. dev-refactoring의 3의 규칙이 여기도 적용된다: 세 번째 변형에서 패턴화.

### 2. 싱글톤을 전역 변수 면허로
❌ DB 연결·설정·로거를 싱글톤 클래스로 — "한 개만 있어야 하니까"
✅ **의존성 주입**: 하나만 만들되 생성은 조립 지점(main/lifespan)에서, 사용처는 인자로 받음. 파이썬은 모듈 자체가 싱글톤(모듈 레벨 인스턴스)이라 클래스 장치 불필요
**왜**: 싱글톤의 문제는 개수가 아니라 **숨은 전역 접근**(테스트 교체 불가·의존 비가시·초기화 순서 지옥)이다. GoF 패턴 중 가장 후회된 패턴 — "한 개"는 조립이 보장하면 되지 접근 방식이 보장할 일이 아니다. dev-fastapi #3(전역 세션)과 동일 구조.

### 3. 패턴을 언어 위에 번역 없이 이식
❌ 파이썬에 자바식 AbstractFactory 인터페이스 5단 — `NotImplementedError` 추상 메서드 가득
✅ 현대 번역표(아래) 먼저: Strategy=함수 전달, Command=클로저/partial, Observer=콜백 목록 또는 이벤트, Template Method=함수 인자, Iterator=제너레이터(언어 내장)
**왜**: 패턴의 본질은 의도(변형 캡슐화)지 클래스 다이어그램이 아니다. 일급 함수·덕 타이핑 언어에서 GoF 구조 그대로는 의식(ritual)이다 — 같은 의도를 1/5 코드로.

### 4. 상속으로 변형 표현 (조합 무시)
❌ `Report` → `PdfReport` → `EncryptedPdfReport` → `CompressedEncryptedPdfReport` 조합 폭발
✅ "상속보다 조합"(GoF 1원칙): 변형 축마다 부품(포맷터·암호화기·압축기)을 만들어 조립 — Decorator/Strategy의 본뜻
**왜**: 상속은 변형 축이 1개일 때만 버틴다. 축이 2개면 클래스 수가 곱으로 늘고, 부모 변경이 전체에 파급된다(취약 기반 클래스). GoF 서문의 두 원칙(인터페이스에 프로그램하라·조합 우선)이 23개 패턴보다 중요하다.

### 5. 패턴 이름 없이 재발명 / 이름 오용
❌ 옵저버를 손으로 짜놓고 동시성 버그를 새로 만듦 / 아무 래퍼나 "프록시 패턴"이라 부름
✅ 표준 부품 먼저(언어·라이브러리의 이벤트·큐·캐시), 직접 구현 시 패턴 이름으로 선례의 함정 목록을 검색 — 이름은 지식 색인이다
**왜**: 패턴 이름의 실가치는 "그 구조의 알려진 함정"에 접근하는 색인 — Observer라 부르는 순간 '콜백 중 예외·해지 누락·순서 의존' 체크리스트가 따라온다. 이름 없이 짜면 그 함정을 전부 재발견한다.

## 현대 번역표 (GoF → 파이썬/TS)

| GoF | 현대 기본형 | 클래스가 정당한 경우 |
|---|---|---|
| Strategy | 함수 인자 (`sort(key=...)`) | 전략이 상태·설정을 가질 때 |
| Command | 클로저·partial·dataclass | undo 스택 등 메타데이터 필요 시 |
| Template Method | 함수 인자 주입·조합 | 단계가 많고 공유 상태가 강할 때 |
| Observer | 콜백 리스트·이벤트 이미터 | 구독 수명 관리가 복잡할 때 (→ dev-event-driven은 프로세스 간) |
| Factory Method | 함수·dict 매핑 (`handlers[kind]()`) | 생성이 다단계·의존 조립일 때 |
| Decorator | 파이썬 @데코레이터·고차 함수 | 런타임 동적 조합 필요 시 |
| Iterator | 제너레이터 (언어 내장) | — |
| Singleton | 모듈 인스턴스 + DI | (거의) 없음 — 안티패턴 2 |
| Adapter / Facade | 그냥 함수·얇은 클래스 — 이름이 곧 패턴 | 외부 경계 격리(이건 늘 정당 — clean-architecture 연결) |
| State | 구별된 유니언 + 매핑 (dev-typescript #5) | 전이 로직이 무거울 때 클래스 |

| 항목 | 기준값 | 근거 |
|---|---|---|
| 패턴 도입 시점 | 변형 3개째 (3의 규칙) | 안티패턴 1 |
| 간접 깊이 | 호출 추적 3단 안에 실제 일하는 코드 | 패턴 위 패턴의 냄새 지표 |
| 상속 깊이 | 2단 이내, 변형 축 2개면 조합 전환 | 안티패턴 4 |
| 추상 계층 | 구현체가 1개뿐인 인터페이스 금지(테스트 더블 제외) | 가짜 유연성 |

## 워크플로우 (구조 선택)

1. **변하는 것과 안 변하는 것 분리** — GoF의 출발 질문: "이 코드에서 무엇이 바뀔 것인가". 바뀌는 축을 한 문장으로.
2. **단순 사다리 오르기** — if → dict 매핑 → 함수 전달 → 클래스/패턴. 각 단계에서 "지금 충분한가" — 충분하면 정지.
3. **패턴이 필요하면 번역표 경유** — GoF 구조가 아니라 언어 관용구로.
4. **이름 기록** — 선택한 구조의 패턴 이름(있다면)을 주석·PR에 — 후임(미래의 나)의 검색 색인.
5. **검증**: 해당 스택 테스트 + "변형 추가 시나리오 1개를 말로 시연"(새 변형이 기존 코드 수정 없이 들어가는가 — 아니면 패턴이 일을 안 한 것).

```
## [대상] 구조 설계
### 변하는 축: <한 문장>

### 선택: <구조 + 패턴 이름(해당 시)> / 번역: <GoF 대비 무엇을 생략했나>
### 변형 추가 시연: <새 변형이 어떻게 들어가나 1줄>

```

### 작성 예시

```
## 시세 소스 다원화 (키움 + 백업 소스) 구조
### 변하는 축: 데이터 소스(인증·페이징·형식이 소스마다 다름)
### 사다리 판정: 함수 전달로 충분 — 소스 2개·공통 시그니처 fetch(code, range) -> list[RawTick]
  (클래스 Strategy는 보류: 소스별 상태가 토큰뿐이라 클로저로 캡슐화 가능)
### 선택: 소스 레지스트리 dict {"kiwoom": make_kiwoom_fetcher(cfg), ...} — Factory는 dict 매핑으로 번역
### 변형 추가 시연: 새 소스 = fetcher 함수 1개 작성 + dict 1행 — 기존 코드 무수정
### 보류한 일반화: 소스 우선순위 자동 폴백 — 3번째 소스 생기면(3의 규칙)
```

❌ "확장 대비해서 AbstractSourceFactory + ISourceProvider 인터페이스부터" (변형 2개에 5층)
✅ "함수 시그니처 합의 + dict 등록 — 세 번째 소스에서 재평가"

### 판단이 막히면 (확인 필요 4요소)

패턴 선택은 "변형 축이 진짜 늘어나는가"라는 미래 사실에 달려 막힌다 — 추측으로 일반화하지 말고 **누가·언제·어떻게·기대값** 4요소로 질의한다.

- **누가**: 도메인·로드맵을 아는 사람(기획·PO) — "이 분기가 앞으로 몇 종으로 늘 것인가"는 코드가 아니라 제품 계획이 답한다.
- **언제**: ① 변형 축의 개수·증가 추세 불명(소스가 2개로 끝인지 10개로 갈지) ② 교체가 런타임 동적인지 배포 시 고정인지 미정 ③ 기존 코드에서 "이게 무슨 패턴인지" 의도가 불명할 때.
- **어떻게**: `[확인 필요] <항목> — 현재 가정: <함수 전달로 충분>, 근거: <변형 2개>, 다른 답(곧 5개+)이면 <레지스트리/Strategy 클래스>로 바뀜. 어느 쪽?` (가정/근거/영향/택일).
- **기대값**: "2개로 고정 / 곧 늘어남" 이분 판정 또는 예상 변형 수. 답이 오면 사다리 정지 지점을 확정한다. 끝내 불명이면 **가장 단순한 단계(함수/dict)**로 잠그고 "3의 규칙으로 재평가" 보류 항목을 남긴다 — 미래는 YAGNI로 미루는 게 보수적 가정이다.

### 사용자가 권고를 거부하면

- "그래도 패턴으로 제대로 깔고 싶어" → 따르되 간접 깊이 3단 기준만 지키게 설계하고, "선급 일반화" 1줄 기록(partial).
- "싱글톤 쓸래" → 테스트 교체 불가 비용 1회 고지, 강행 시 모듈 레벨 인스턴스 + 주입 가능한 형태(인자 기본값)로 절충.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

## 실전 케이스 — FizzBuzz Enterprise Edition (살아있는 풍자, 2012~)

GitHub의 `EnterpriseQualityCoding/FizzBuzzEnterpriseEdition`은 15줄짜리 FizzBuzz를 **Visitor·Factory·Strategy·DI 수십 층**으로 구현한 풍자 프로젝트로, 수만 스타를 받으며 "패턴 강박"의 공용 어휘가 됐다. 농담이지만 실증이기도 하다 — 이 레포가 공감을 산 이유는 모두가 실무에서 그 축소판(분기 2개에 Factory)을 봤기 때문. 교훈: ① 패턴의 비용(간접·파일 수·추적 깊이)은 코드에 즉시 보이고, 효익(변형 흡수)은 미래에만 있다 — 효익이 실재하는지(변형 축이 진짜 있는지)가 유일한 정당화 ② "확장 가능하게"는 설계 근거가 아니라 질문이다: 무엇이, 언제, 몇 번 확장되는가.

## 한계

객체·함수 수준만 담당 — 그 위(레이어·서비스)는 clean-architecture/msa, 도메인 어휘는 ddd. 패턴 지식은 읽기에도 쓰인다(남의 코드의 의도 식별) — 단 "이거 무슨 패턴이지"에 집착하면 패턴 아닌 코드를 패턴으로 오독한다. 모든 패턴 목록의 암기는 목표가 아니다 — 번역표와 두 원칙(인터페이스에·조합 우선)이면 실무의 90%.
