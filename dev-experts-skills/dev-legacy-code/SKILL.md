# dev-legacy-code — 레거시 코드 전문가

> 기준: Feathers *Working Effectively with Legacy Code* (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

Michael Feathers 전통. **"레거시 코드란 오래된 코드가 아니라 '테스트 없는 코드'다 — 테스트가 없으면 변경의 안전망이 없고, 안전망이 없으면 코드는 나이와 무관하게 레거시다"**. 그리고 레거시의 역설: 테스트를 넣으려면 코드를 바꿔야 하고, 코드를 안전하게 바꾸려면 테스트가 필요하다 — 이 매듭을 푸는 최소 기술(심·특성화 테스트)이 이 스킬의 본체다.

핵심 신조: 동작 보존이 1순위(지금 동작이 명세다 — 버그처럼 보여도) · 바꾸기 전에 현재를 박제(특성화 테스트) · 재작성 충동은 이해 부족의 신호일 때가 많다 · 울타리는 치워진 이유를 알기 전까지 그대로.

비유 — 레거시 변경은 **오래된 건물의 배관 공사**다: 도면(테스트)이 없으니 벽을 함부로 못 깬다 — 먼저 물을 틀어보고 어디로 나오는지 기록(특성화 테스트)하고, 작은 점검구(심)를 내서 그 부분만 격리한 뒤 작업한다. "다 부수고 새로 짓자"는 견적이 항상 두 배로 끝나는 그 공사다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 테스트 없는 코드의 안전 변경 | 테스트 확보 후 구조 개선 (→ dev-refactoring) |
| 특성화 테스트·심 기법 | 신규 설계 원칙 (→ dev-clean-architecture) |
| 재작성 vs 점진 판단 | 버그 원인 추적 (→ systematic-debugging) |
| 죽은 코드 판정 절차 | 테스트 작성 기법 일반 (→ dev-testing, dev-tdd) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 테스트 없이 "조심해서" 수정
❌ "작은 변경이니까 눈으로 확인하면 돼" — 회귀는 변경 지점이 아니라 그 코드를 쓰는 먼 곳에서 터진다
✅ **특성화 테스트 먼저**: 현재 동작을(옳든 그르든) 그대로 단언하는 테스트를 변경 대상 주변에 — "입력 X면 지금 Y가 나온다"를 박제 → 그 다음 수정 → 의도한 차이만 테스트 갱신
**왜**: 레거시에서 명세는 문서가 아니라 현재 동작이다 — 누군가 그 '버그 같은 동작'에 의존하고 있을 수 있다(하이럼의 법칙). 특성화 테스트는 명세 발굴이자 안전망 설치를 한 동작으로 끝낸다.

### 2. 빅뱅 재작성
❌ "이 코드는 답이 없다, 갈아엎자" — 2배 기간·기능 동결·구버그의 재발견·신버그의 추가를 한 세트로
✅ **교살자(strangler fig) 점진**: 새 구현을 경계 뒤에 세우고 트래픽/기능을 한 조각씩 이관 — 옛 코드는 호출이 0이 된 조각부터 제거. 항상 출시 가능 상태 유지
**왜**: 재작성 견적은 "보이는 기능"만 세지만 레거시의 본체는 **보이지 않는 엣지케이스의 퇴적층**이다(수년치 핫픽스가 곧 명세). Netscape의 재작성이 회사를 잃게 한 고전(evidence) — 그 코드가 더러운 이유의 절반은 현실이 더러워서다.

### 3. 이해 전 삭제 (체스터튼의 울타리)
❌ "이 분기 안 쓰는 것 같은데" 삭제 — 분기·플래그·이상한 보정값이 연 1회(정산·윤년·특정 거래처)의 이유였음
✅ 울타리 절차: 치우기 전에 **세워진 이유를 찾는다** — git blame·커밋 메시지·관련 이슈 → 못 찾으면 로깅 심어 실사용 관측(한 주기 이상 — 연 단위 로직은 1년) → 그 후 제거. 제거도 플래그 뒤에서(즉시 복구 가능)
**왜**: 레거시의 이상한 코드는 높은 확률로 누군가의 피로 쓴 핫픽스다 — 이유 모를 코드의 삭제는 그 사고의 재구매다. "안 쓰는 것 같다"는 관측이 아니라 추측이고, 관측은 로그가 한다.

### 4. 의존성 직결 상태로 테스트 시도
❌ "이 함수는 DB·외부 API·전역 상태에 엉켜서 테스트 불가" → 포기
✅ **심(seam)을 찾는다**: 동작을 코드 수정 최소로 갈아끼울 수 있는 지점 — 함수 인자로 의존 끌어올리기(extract & override)·생성자 주입 한 줄·래퍼 한 겹. 심을 만드는 최소 변경만은 테스트 없이 허용(기계적·동작 불변 변환만)
**왜**: 레거시의 매듭(테스트하려면 변경, 변경하려면 테스트)은 "동작을 안 바꾸는 기계적 변환"이라는 좁은 문으로 푼다 — Feathers 기법 카탈로그의 존재 이유. 전역 싱글톤 호출을 인자로 바꾸는 5줄이 테스트 가능성의 전부를 바꾼다.

### 5. 변경 범위 폭주 (보이스카웃 과욕)
❌ 버그 하나 고치러 들어가 "이왕 온 김에" 네이밍·구조·포맷까지 — diff 800줄, 리뷰 불능, 회귀 추적 불능
✅ **변경 분리**: 이번 임무(버그/기능)의 최소 diff + 발견한 개선거리는 목록으로(ledger·이슈) — 정리는 별도 커밋/PR로(동작 변경과 구조 변경을 한 diff에 섞지 않기 — dev-refactoring 동일 규율)
**왜**: 거대 diff에서 회귀가 나면 원인 후보가 800줄이다 — 작은 diff는 리뷰·bisect·롤백 전부를 살린다. 레거시에서 "이왕 온 김에"는 특히 위험하다(주변 코드의 의도를 모르는 상태이므로).

### 6. 전수 테스트 욕심에 착수 마비
❌ "커버리지 80% 만들고 나서 고치자" — 수개월짜리 선행 과제 앞에서 아무것도 못 함
✅ **변경 지점 중심 동심원**: 이번에 바꿀 코드의 입출력만 특성화 → 변경 → 다음 변경 때 그 주변 — 테스트는 변경을 따라 자란다(전수 선행이 아니라). 자주 바뀌는 곳부터 두꺼워지는 게 올바른 분포다
**왜**: 레거시 전수 테스트화는 ROI가 균일하지 않다 — 안 바뀌는 코드의 테스트는 비용만 있다. "변경이 테스트를 끌고 온다" 모델은 착수 장벽을 없애면서 정확히 위험한 곳(변경 빈발 지점)에 안전망을 집적시킨다.

## 워크플로우 (레거시 변경 1건)

1. **읽기 먼저** — 변경 지점의 호출자/피호출자 한 겹씩 + git log로 이력(왜 이렇게 됐나 단서).
2. **특성화** — 현재 동작 박제 (대표 입력 3~5개 → 현재 출력을 그대로 단언, 틀려 보여도 그대로):
   ```python
   # tests/characterization/test_target.py
   import pytest
   from legacy import calc_fee  # 변경 대상

   @pytest.mark.parametrize("amount,expected", [
       (10_000, 30),    # 현재 출력을 "관측해서" 채운다 — 옳다고 믿는 값이 아니라 실제 반환값
       (0, 0),          # 경계
       (999_999, 2999), # "버그 같은" 반올림도 그대로 박제 (의존자 미상)
   ])
   def test_calc_fee_current_behavior(amount, expected):
       assert calc_fee(amount) == expected
   ```
   ```
   pytest tests/characterization/test_target.py -v   # 전부 green = 현재 동작 박제 완료
   ```
3. **심 확보(필요시)** — 의존 끊는 최소 기계 변환 → 특성화 재실행(동작 불변 확인).
4. **수정** — 의도한 차이만 — 특성화 중 그 차이만 갱신, 나머지 green 유지.
5. **기록** — 발견한 지뢰·이유 불명 코드를 ledger에(다음 사람을 위한 지도) — 특성화 테스트는 프로젝트 테스트 규칙 위치(예: `tests/characterization/test_<대상>.py`)에 일반 테스트와 분리해 두고(나중에 폐기·승격 추적용), 기존 파일 덮어쓰기 대신 Edit.

### 작성 예시

```
## 수수료 계산 레거시 수정 (가정)
### 이력 단서: 0.3% 하드코딩에 주석 없음 — 2019 커밋 "거래처 A 특례" 발견 (살아있는 특례!)
### 특성화: 대표 입력 5건 박제 — 그중 1건이 "버그 같은" 반올림인데 그대로 박제(의존자 미상)
### 심: 환율 조회가 전역 호출 → 인자 주입으로 5줄 변환(동작 불변 확인)
### 변경: 신규 구간 수수료만 추가 — 특례·반올림 동작 보존
### 검증: 특성화 5/5 green (의도 차이 0 — 추가만) / 신규 케이스 3 green
### 지뢰 기록: "반올림 방식 의존자 조사 필요" ledger 등재
```

❌ "이 코드 답 없네, 갈아엎고 테스트도 그때 짜자" (안전망 없이 절벽 공사)
✅ "박제 → 심 → 최소 변경 — 지금 동작이 명세다, 명세를 적고 나서 고친다"

### 사용자가 권고를 거부하면

- "급하니 특성화 생략하고 고치자" → 핫픽스 현실 인정 — 수정 후 24시간 내 특성화 소급 조건으로 동의·기록(partial). 2번째 같은 코드 수정부터는 선행 권고 강화.
- "재작성하고 싶다(학습/사기 문제)" → 동기 존중 — 교살자 스케치(조각 분할·이관 순서) 1장을 먼저 만들어 점진 경로와 비교 후 결정, 과정 기록.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단 불가 시 — `[확인 필요]` 4요소

이유 불명 코드(체스터튼의 울타리)나 "버그 같은 동작"의 의존자 여부는 추측으로 삭제·수정하지 않고 4요소로:
- **누가**: 사용자·원작자(git blame 대상자) 또는 이력(커밋 메시지·관련 이슈/티켓)
- **언제**: 이유 모를 분기·보정값을 제거하기 전 / "버그 같은 동작"을 정상화하기 전(의존자 미상이면 멈춤)
- **어떻게**: `git log -S<코드>`·blame으로 도입 맥락 발굴 → 못 찾으면 로깅 심어 한 주기(연 단위 로직은 1년) 실사용 관측
- **기대값**: "이 분기는 2019 거래처 A 특례, 현재도 유효" 같은 확정 — 못 얻으면 `[확인 필요: <항목> — 관측 필요]`로 남기고 동작 보존(삭제 보류·플래그 경유)으로 진행

## 실전 케이스 — Netscape 재작성 (1997~2000): "다시 쓰면 깨끗해질 것"의 대가 (Spolsky 분석)

Netscape는 Navigator 코드를 버리고 처음부터 재작성을 결정 — 3년간 신기능 출시가 멈췄고 그 사이 IE가 시장을 가져갔다. Joel Spolsky의 "Things You Should Never Do"가 이를 "단일 최악의 전략적 실수"로 부검한 고전: 오래된 코드의 "더러움"의 상당 부분은 **실전에서 얻은 버그 수정의 퇴적**(특정 프록시·특정 OS·특정 사이트 대응)이고, 재작성은 그 학습을 전부 버리고 같은 수업료를 다시 내는 것이다. 교훈: ① "읽기 어렵다"는 재작성의 근거가 아니다 — 읽기 어려움의 해법은 이해(특성화)와 점진(교살자)이다 ② 재작성 기간의 기능 동결은 경쟁 환경에선 자해다 ③ 정당한 재작성도 있다(플랫폼 소멸·규모 불일치) — 단 그때도 교살자 경로가 거의 항상 가능하다. 상세: `references/evidence.md`

## 한계

- **테스트 하네스 의존**: 특성화는 프로젝트의 기존 테스트 러너(pytest/jest/JUnit 등)에 얹는다 — 하네스가 아예 없으면 그 도입이 0단계(언어 표준 러너부터, 새 프레임워크 도입은 별건). 특성화 작성 기법 자체는 dev-testing.
- 동작 보존이 불가능한 변경(보안 패치로 동작 자체를 바꿔야 함)은 특성화의 대상을 "바뀌면 안 되는 주변"으로 옮긴다 — 원칙의 적용이 달라짐을 명시.
- 코드 고고학(이력 발굴)에는 한계가 있다 — 끝내 이유 불명인 코드의 위험 수용은 사용자 결정 사항으로 에스컬레이션.
- 테스트 기법 자체(목·픽스처 설계)는 dev-testing, 확보 후 구조 개선은 dev-refactoring이 본진.
