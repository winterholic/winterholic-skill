# dev-legacy-code evidence — 실증 사례

## 1. Netscape 재작성 (1997~2000) — 빅뱅의 정사(正史) (Spolsky "Things You Should Never Do")

- **무슨 일**: Navigator 4 이후 코드 전면 폐기·재작성(Mozilla 프로젝트 초기) — 출시까지 ~3년 공백, 그 사이 IE 점유율 역전, 회사는 AOL에 매각. Spolsky의 2000년 에세이가 표준 부검이 됐다.
- **핵심 논증**: "코드는 읽기보다 쓰기가 쉽다"는 착각이 재작성 충동의 뿌리 — 옛 코드의 이상한 두 줄은 누군가의 2주짜리 버그 수정이다. 재작성은 [기능 동결 + 학습 폐기 + 새 버그]의 3중 지불.
- **균형 각주**: Mozilla는 결국 Firefox로 부활했다(재작성 결정 1998 → Firefox 1.0 2004, 약 6년 뒤) — "재작성 산출물이 영원히 나쁘다"가 아니라 **사업 시간축에서의 공백**이 치명이라는 게 정확한 교훈. 같은 이유로, 경쟁 압력 없는 내부 도구의 재작성은 셈법이 다를 수 있다(그래도 교살자가 보통 더 싸다).

## 2. 하이럼의 법칙 — "관측 가능한 모든 동작에 누군가 의존한다" (구글 경험칙)

- **명제**: 사용자가 충분히 많으면 API의 **문서화 여부와 무관하게** 관측 가능한 모든 동작(에러 메시지 문자열·순서·타이밍·버그까지)에 의존자가 생긴다 — 구글 엔지니어 Hyrum Wright의 경험칙(hyrumslaw.com).
- **레거시 실무 번역**: ① "이건 명세에 없는 동작이니 바꿔도 됨"은 위험한 추론 — 특성화 테스트가 "지금 동작 전부"를 박제하는 이유 ② 버그 수정조차 호환성 변경이다 — 버그에 의존한 우회 코드가 어딘가에 있다(수정 공지·플래그 경유가 정중한 절차) ③ 거꾸로, 내가 만드는 코드의 관측면을 줄이는 것(에러 문자열 파싱 못 하게 코드化 등)이 미래 레거시 비용을 줄인다.

## 3. 교살자 무화과 성공 장르 — 점진 이관의 실재 증명 (공개 사례 다수)

- **사례들**: 거대 모놀리스→서비스 이관을 교살자로 완수한 공개 기록이 다수 — 프록시/라우터를 앞에 세우고 경로 단위로 신구 전환(언제든 비율 조절·롤백), 호출 0이 된 옛 모듈부터 삭제. 금융·커머스의 코어 시스템 이관 발표에 반복 등장하는 표준 패턴(Fowler가 2004년 명명).
- **성공 조건 추출**: ① **경계 지점 확보**가 전부다(HTTP 라우터·메시지 토픽·DB 뷰 — 신구를 같은 인터페이스 뒤에) ② 비교 검증 기간(같은 입력을 양쪽에 — 섀도 트래픽 — 출력 대조) ③ 조각 크기 = 한 번에 롤백 가능한 크기 ④ "옛 코드 삭제"를 마일스톤으로 명시(안 하면 이중 운영이 영구화 — 교살자의 실패 모드).
- **레거시 일반화**: 서비스 이관만이 아니라 함수·모듈 수준에서도 동일 — 새 구현을 옆에 세우고(플래그) 호출부를 하나씩 — "큰 교체"를 "작은 교체 N번"으로 바꾸는 보편 기법이다.

> 출처: Spolsky "Things You Should Never Do"(2000) · Hyrum's Law · Fowler "StranglerFigApplication" + 공개 이관 사례 집적. 2026-06 기준.
