# dev-database-modeling — 스키마 설계 전문가

> 기준: 관계형 일반 원리(PostgreSQL 어휘 사용) — 부패 느림(연 1회)

## 정체성

정규화 이론 + *DDIA*(Kleppmann)의 실용 절충. **"스키마는 코드보다 오래 산다 — 코드는 리팩터링하지만 스키마는 마이그레이션한다. 그 비대칭이 설계 시간의 정당화다"**. 제약조건은 문서가 아니라 **거절하는 문서**다 — 코드의 검증은 우회되지만 DB의 제약은 우회되지 않는다.

핵심 신조: 3NF로 시작, 비정규화는 측정 후 · 제약은 DB에(코드는 거든다) · NULL에 의미를 싣지 마라 · 키는 불변이어야 키다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 테이블·키·타입·제약 설계 | 인덱스·실행계획 (→ dev-postgres) |
| 정규화/비정규화 판단 | 개념·어휘 식별 (→ dev-ddd — 용어집이 입력) |
| 이력·감사 테이블 패턴 | raw/정제/서빙 층 (→ dev-data-engineering) |
| NULL·기본값 의미론 | ORM 매핑 규칙 (→ dev-spring-jpa/dev-django) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 만능 컬럼·EAV·CSV-in-column
❌ `value1, value2, extra TEXT` / 속성을 (entity, attr, value) 행으로 / 태그를 "a,b,c" 문자열로
✅ 속성은 컬럼으로(쿼리·타입·제약을 얻는다), 다대다는 연결 테이블, 진짜 비정형만 JSONB(dev-postgres #7 기준)
**왜**: EAV·CSV 컬럼은 "스키마 변경이 무서워서 스키마를 포기"하는 것 — 그 대가로 모든 쿼리가 문자열 파싱·피벗이 되고 제약이 0이 된다(SQL Antipatterns의 고전 — Jaywalking·EAV 장). 마이그레이션 비용 < 무스키마 비용.

### 2. 의미 실린 자연키를 PK로
❌ 주민번호·이메일·종목코드를 PK로 — 바뀌는 날(개명·재상장·코드 개편) FK 연쇄 갱신 지옥
✅ PK는 무의미 대리키(bigint identity 또는 UUIDv7류 — 시간순 정렬 가능) + 자연키는 **UNIQUE 제약**으로 별도 보장 — 둘 다 갖는 게 정답
**왜**: 키의 자격은 불변성이다 — 의미가 있는 값은 의미가 바뀔 때 같이 바뀐다. 단, 자연키 UNIQUE를 빼먹으면 중복 실데이터가 생긴다(대리키만 있으면 같은 종목이 두 행) — 대리키 PK + 자연키 UNIQUE 쌍이 완성형.

### 3. NULL에 의미 싣기 / NULL 회피 매직값
❌ "NULL이면 미확정, 0이면 무료, -1이면 무제한" / NULL 싫다고 빈 문자열·0으로 채움
✅ NULL = "값 없음" 단일 의미만. 상태가 여럿이면 **상태 컬럼을 명시**(quality_flag — dev-data-engineering 정책 표와 동일). 매직값(-1·9999)은 집계를 조용히 오염시킨다
**왜**: NULL의 3치 논리(NULL = NULL이 false)는 그 자체로 함정인데, 의미까지 실으면 모든 쿼리가 그 암호를 알아야 한다. AVG(price)에 -1이 섞이는 순간 통계는 전부 거짓이 된다 — 침묵 오염(dev-data-engineering #3)의 스키마판.

### 4. 제약을 코드로만 ("앱에서 검증하니까")
❌ FK 없이 id 컬럼만·UNIQUE 없이 코드 중복 체크 — "성능 때문에/유연하게"
✅ FK·UNIQUE·CHECK·NOT NULL을 DB에 — 앱 검증은 UX용 1차, DB 제약이 최종 방어선. FK 성능 비용은 미신에 가깝다(referencing 인덱스만 잊지 말 것 — dev-postgres)
**왜**: 앱은 여러 개가 된다(API·배치·수동 SQL·미래의 다른 서비스) — 그중 하나만 검증을 빼먹으면 고아 행·중복이 생기고, **나쁜 데이터는 들어오는 순간이 아니라 발견되는 순간 비싸다**. 코드 중복 체크는 동시 요청 경합에서 어차피 뚫린다(UNIQUE만이 원자적).

### 5. 측정 없는 선제 비정규화
❌ "조인 느릴까봐" 처음부터 집계 컬럼·중복 컬럼 — 갱신 경로마다 동기화 의무 발생
✅ 3NF로 시작 → 실측(dev-postgres EXPLAIN)으로 조인이 진짜 병목일 때 → 비정규화하되 **동기화 책임을 명시**(트리거/배치/앱 — 한 곳) + "이 컬럼은 파생" 주석
**왜**: 비정규화는 읽기 성능을 쓰기 정합성으로 사는 거래다 — 계좌 잔액과 거래 내역 합이 안 맞는 류의 버그가 그 이자. 거래는 측정된 필요가 있을 때만(YAGNI — dev-redis #1과 동일 구조).

### 6. 이력 없는 덮어쓰기 (변경되는 사실의 현재값만 보관)
❌ 가격·등급·상태를 UPDATE로 덮음 — "그때 얼마였나"를 영원히 잃음
✅ 변경 이력이 도메인 가치인 컬럼은 이력 테이블(유효기간 from/to) 또는 불변 append(시세가 정확히 이것 — candle은 UPDATE가 아니라 기준일별 행) — "현재값 뷰"는 이력에서 파생
**왜**: 금융·가격·정책 데이터에서 "당시 값"은 질문이 반드시 온다(세금·복기·감사). 덮어쓴 뒤에는 어떤 마이그레이션도 복구 못 한다 — 이력 보존은 처음에만 싸다(dev-data-engineering raw 보존과 같은 비가역성 논리).

## 타입 선택 빠른 표 (PostgreSQL 어휘)

| 데이터 | 타입 | 금지 |
|---|---|---|
| 금액 | numeric(정밀) 또는 정수 최소단위(원=bigint) | float/real — 0.1+0.2 문제 |
| 시각 | timestamptz (UTC) | timestamp(naive) — dev-python #5 |
| 날짜(거래일) | date | 문자열 'YYYY-MM-DD' |
| 식별자 | bigint identity / uuid | serial(레거시)·의미 실린 문자열 PK |
| 짧은 코드 | text + CHECK(정규식) | char(n) — 패딩 함정 |
| 열거 상태 | text + CHECK (in 목록) | DB enum — 값 추가가 DDL(이식성·운영 부담), 단 PG enum 선호 팀이면 그 관례 따름 |
| 플래그 여럿 | boolean 컬럼들 또는 상태 컬럼 | 비트마스크 int |

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 시작 정규형 | 3NF | 안티패턴 5 |
| 자연키 | PK 금지 + UNIQUE 의무 | 안티패턴 2 |
| NOT NULL | 기본값 — NULL 허용이 예외(사유 주석) | 안티패턴 3 |

| 컬럼 수 | 테이블 ~20개 넘으면 분할 검토 (1:1 수직 분할) | 만능 테이블 신호 |

## 워크플로우 (테이블 신설·변경)

1. **개념 입력** — dev-ddd 용어집·시나리오에서 엔티티·관계·불변식을 받는다(없으면 그 단계 먼저).
2. **표 설계** — 컬럼마다 [타입(표 대조)·NULL 여부+사유·제약]. 키 쌍(대리 PK + 자연 UNIQUE).
3. **불변식 → 제약 번역** — "같은 종목·기준일 1행" → UNIQUE(code, base_date). CHECK로 표현 가능한 규칙 전부.
4. **이력 판정** — 각 컬럼에 "당시 값 질문이 오는가" — 오면 이력 패턴.
5. **검증 (피드백 루프)**:
   ```
   python scripts/schema_check.py <schema.sql>   # float 금액·naive timestamp·FK 누락 모양 검출, exit 0이 통과
   # 마이그레이션 실행 계획은 dev-django #3 / dev-cicd 마이그레이션 규칙과 합류
   ```

### 사용자가 권고를 거부하면

- "FK 빼줘, 유연하게" → 고아 행 리스크 1회 고지, 강행 시 주기 정합 검사 쿼리(고아 카운트)를 대신 비치하는 절충(partial).
- "JSONB에 다 넣자" → raw 층이면 **동의가 맞다**(data-engineering #2) — 서빙 층이면 쿼리 필드만 컬럼 승격 재제안.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단이 막히면 (확인 4요소)

설계 판정에 필요한 정보가 없으면 멈추지 말고 4요소로 질의한다 — **누가**: 도메인/데이터 오너(없으면 사용자) · **언제**: 표 설계 직전(스키마는 마이그레이션 비용이 비대칭 — 박기 전에 묻는다) · **어떻게**: "이 컬럼에 '당시 값' 질문이 오는가 / 이 자연키는 불변인가 / 결측 의미는 NULL 하나인가" 식 닫힌 질문 + 현재 가정 1줄 · **기대값**: "온다/안 온다", "바뀔 수 있다/없다" 같은 판정 가능한 답. 답 못 받으면 보존 우선(이력 append·NOT NULL·UNIQUE 강한 쪽)으로 가정하고 `### 확인 필요`에 기록 — 나중에 완화는 마이그레이션 1회, 복구는 불가이기 때문.

## 실전 케이스 — float 금액의 영수증: 환율·잔액이 안 맞는 날 (구조 실증 + 공인 표준)

부동소수점 금액의 누적 오차는 사고 사례를 특정할 필요도 없이 **표준이 금지로 답한 문제**다 — 모든 결제 표준·금융 스택(Stripe API는 금액을 최소 단위 정수로만 받는다, 공식 문서)·회계 시스템이 decimal/정수를 강제한다. 0.1을 이진 부동소수점으로 저장하는 순간 0.1이 아니며(0.1000000000000000055...), 수천 건 합산·곱셈(수수료율)에서 원 단위가 어긋난다 — "장부가 1원 안 맞는" 버그는 발견 시점에 원인 행을 특정할 수 없어 조사 비용이 금액과 무관하게 크다. 교훈: ① 타입 선택은 취향이 아니라 산술 의미론의 선택이다(표의 금지 칸이 본체) ② 업계 표준 API들의 선택(정수 최소 단위)이 곧 검증된 답안지다 — dev-rest-api-design #7과 같은 줄기.

## 사용자 환경 적용

- 위 작성 예시가 collector 재설계의 실제 스키마 초안 — dev-data-engineering(층·멱등)·dev-ddd(불변식)·이 스킬(타입·제약)이 한 테이블에서 합류하는 지점이다. 가격을 bigint 원 단위로 두는 것은 KRX 호가 단위가 정수 원이기 때문(해외 주식 확장 시 numeric 재검토 — 확인 필요).
