# 골든 시그널·RED/USE·SLO·경보·대시보드 (SKILL.md 비중복)

## 세 가지 방법론 (무엇을 측정하나 — 상황별)

| 방법론 | 측정 | 맞는 곳 |
|---|---|---|
| **골든 시그널** (SRE) | 지연·트래픽·에러·포화 | 사용자 대면 서비스 전반(기본) |
| **RED** | Rate·Errors·Duration | 요청 기반 서비스(API)의 간결판 |
| **USE** | Utilization·Saturation·Errors | 자원(CPU·디스크·큐)의 진단축 |

실무 조합: 경보는 RED(요청 증상), 대시보드 진단은 USE(자원 원인) — 안티패턴 1의 분업이 이 두 방법론의 역할 분리.

## 관측 3축 분업 (카디널리티 폭발 방지)

| 축 | 용도 | 카디널리티 | 예 |
|---|---|---|---|
| 메트릭 | 집계·추세·경보 | 낮음(라벨 유한) | 초당 요청·p95 지연 |
| 로그 | 개별 사건·디버깅 | 높음 OK(저장만) | 요청별 상세(dev-error-logging) |
| 추적 | 요청의 서비스 간 흐름 | 샘플링 | 분산 호출 체인(dev-msa 이후) |

"메트릭에 user_id"가 틀린 이유: 그건 로그·추적의 일이다(안티패턴 5). 축을 섞으면 비용이 터진다.

## SLO·에러 예산 산정

```
SLI: 측정 가능한 사용자 경험 지표 (성공 요청 / 전체 요청, p95 지연)
SLO: SLI의 목표      예) "성공률 99.9%" / "p95 < 300ms를 99%의 시간"
에러 예산 = 100% - SLO   예) 99.9% -> 월 0.1% = ~43분 다운 허용
```

- 에러 예산의 용도: **배포 속도 조절기**. 예산 남으면 공격적 배포, 소진되면 안정화 모드(기능 동결·신뢰성 작업). SLO는 벌이 아니라 합의된 현실.
- 100% SLO는 함정 — 비용이 무한대로 가고, 의존 서비스(클라우드·DNS)가 이미 100%가 아니다. "충분히 좋은" 지점이 SLO.
- 사용자가 1명(본인)이어도 SLO는 유효: "수집이 영업일 아침까지 완료"가 SLI, 99%가 SLO(월 1회 실패 허용).

## 경보 규칙 작성 패턴

```yaml
# 좋은 경보: 증상 + 지속시간(순간 스파이크 무시) + 런북
- alert: HighErrorRate
  expr: rate(http_errors[5m]) / rate(http_requests[5m]) > 0.05
  for: 10m                      # 10분 지속 - 일시 스파이크 오탐 방지
  annotations:
    summary: "error rate > 5% for 10m"
    runbook: "check recent deploy, DB health, downstream APIs"   # 행동 가능성(안티패턴 2)
```

- `for:` 지속 시간이 알람 피로의 1차 방어 — 순간값 경보는 노이즈.
- 다중 윈도우(빠른 소진 + 느린 소진) 번 레이트 경보가 SRE 고급 패턴 — 소규모는 단순 임계+지속으로 충분(YAGNI).
- 경보 심각도 분리: page(즉시 깨움) vs ticket(업무시간 처리) — 모든 게 page면 알람 피로.

## 대시보드 구성 (원인 진단용)

- 상단: SLO 현황(에러 예산 잔량) — "지금 괜찮은가" 한눈에.
- 중단: 골든 시그널 4축 시계열.
- 하단: 원인 메트릭(USE — 자원 포화)·최근 배포 마커·최근 에러 로그 링크.
- 패널은 "이 그래프로 무슨 결정을 하나"가 있어야 — 장식 그래프는 인지 부하만.

## 헬스체크 계층

- liveness: "프로세스 살아있나"(죽으면 재시작) — 가벼움.
- readiness: "요청 받을 준비됐나"(의존성 연결 확인) — dev-docker depends_on·LB 라우팅 기준.
- 깊은 헬스체크(DB 쿼리까지)는 readiness에, liveness는 가볍게 — liveness가 무거우면 일시 부하에 불필요 재시작.
