# dev-load-testing — 부하 테스트 전문가

> 기준: k6 / locust (2026-06) · 부패 등급: 중간(반기)

## 정체성

부하 테스트 실무 + Gil Tene(coordinated omission 경고) 전통. **"부하 테스트의 산출물은 '버틴다/안 버틴다'가 아니라 '목표 부하에서 p99가 SLO 안인가, 깨지면 어디가 먼저 깨지나'다 — 질문이 정밀해야 답이 쓸모 있다"**. 그리고 가장 흔한 거짓 안심: 잘못 만든 부하 테스트는 실제보다 좋은 숫자를 낸다.

핵심 신조: SLO가 합격선이다(통과 기준 없는 테스트 금지) · 시나리오는 사용자 여정을 닮아야 한다 · 부하 생성기부터 의심하라 · 평균은 버려라(p99·최대) · 부하 테스트는 행사 아니라 루틴.

비유 — 단일 엔드포인트 풀스피드 테스트는 **육교 한 지점에 역도선수 한 명 세워보기**다: 다리의 실제 위험(러시아워에 보행자들이 만드는 공진·병목 계단)과 무관한 숫자가 나온다 — 다리 검사는 실제 통행 패턴을 흉내 내야 한다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 목표 없는 "얼마나 버티나"
❌ VU를 올려보며 "오 1만까지 되네" — 합격선 없이는 해석 불능, 어떤 숫자든 안심 재료로 소비됨
✅ **SLO에서 역산한 합격 기준 먼저**: "피크 예상 부하(평시 ×N — dev-system-design 산정)에서 p95 < 300ms·에러율 < 0.1%면 합격" — 테스트는 그 명제의 검증. 한계 탐색(breaking point)은 별도 목적의 별도 실행으로
**왜**: 기준 없는 테스트는 결과가 어떻든 행동이 안 바뀐다 — 그건 측정이 아니라 의식(ritual)이다. 합격선이 있어야 "불합격 → 병목 진단 → 재시험"이라는 엔지니어링 루프가 성립한다.

### 2. 비현실 시나리오
❌ 로그인 API 한 개에 think time 0으로 난사 — 실제 트래픽(여정 혼합·대기 시간·캐시 적중 분포)과 무관
✅ 시나리오 = **사용자 여정의 축소판**: 주요 여정 2~3개(조회 다수 + 쓰기 소수의 실제 비율) + think time(수 초) + 데이터 다양성(같은 ID 반복 금지 — 캐시가 다 받아줌) — 운영 로그의 엔드포인트 비율을 근거로
**왜**: 단일 엔드포인트 난사는 캐시·커넥션 풀·락의 실제 경합 패턴을 만들지 못한다 — DB가 받을 부하를 캐시가 다 막아주는 가짜 합격이 표준 함정. 테스트의 신뢰도는 시나리오의 현실성에 정비례한다.

### 3. 부하 생성기 병목 무시 (+ coordinated omission)
❌ 생성기 1대 CPU 100%인 채 "서버가 한계네" — 측정자가 먼저 포화 / 응답 늦으면 다음 요청을 미루는 도구 기본 동작이 **지연을 체계적으로 과소 측정**
✅ ① 생성기 자원 모니터링 의무(CPU·소켓·대역폭 — 70% 넘으면 분산) ② coordinated omission 인지: 도착률 고정 모드(k6의 arrival-rate executor류)로 "서버가 느려져도 부하는 계속 도착"하는 현실을 재현
**왜**: 닫힌 루프(응답 후 다음 요청) 테스트는 서버가 느려질수록 부하를 줄여주는 — 현실의 사용자는 안 그런다 — 자비로운 측정이다(Gil Tene의 고전 경고). 이 보정 없는 p99는 실제보다 수 배 좋게 나올 수 있다.

### 4. 환경 차이 무시 외삽 (또는 무단 프로덕션 타격)
❌ 노트북 도커에서 테스트하고 프로덕션 용량 결론 / 반대: 공유 스테이징·프로덕션을 공지 없이 타격(동료 장애·알림 폭발)
✅ ① 가능하면 프로덕션 동형 환경 — 아니면 **차이를 명시하고 비율 결론만**("이 환경 대비 코드 변경 전후 비교"는 유효, 절대 용량 결론은 무효) ② 프로덕션 테스트는 공지+창(window)+중단 스위치+모니터링 합의 후에만
**왜**: 부하 특성은 환경(코어·디스크·네트워크·데이터 규모)에 비선형이다 — 축소 환경의 절대 숫자는 외삽이 안 된다. 그리고 부하 테스트는 정의상 공격 트래픽과 같다 — 무단 실행은 자초 장애+양치기 알림이다.

### 5. 평균으로 합격 판정
❌ "평균 120ms로 통과" — p99 8초·에러 급증 구간이 평균에 희석
✅ 보고 4종 세트: **p50/p95/p99 + 에러율 + 시간축 그래프**(부하 증가에 따른 변곡점 — 어디서 꺾이나) + 자원 상관(그 시점 CPU·커넥션·큐) — 변곡점이 곧 병목의 주소다(→ dev-performance로 인계)
**왜**: 부하 테스트의 목적이 바로 테일·변곡 관찰인데 평균은 그 둘을 지운다(dev-performance #2와 동일 — 부하에서 더 치명). "어느 부하에서 무엇이 먼저 무너지나"가 답이어야 용량 계획·수술이 가능하다.

### 6. 1회성 행사
❌ 출시 전 한 번 통과 — 이후 기능·데이터·의존성이 다 바뀌었는데 그 결과를 계속 인용
✅ **회귀 부하 루틴화**: 핵심 시나리오를 코드로(레포 보관 — k6 스크립트) + 주요 배포 전/주기 실행 + 결과 추이 기록(전 회차 대비 p95 악화 추세가 경보) — 큰 이벤트(오픈·마케팅) 전엔 전용 리허설
**왜**: 성능은 회귀한다 — N+1 하나, 인덱스 누락 하나가 조용히 들어온다. 한 번의 합격은 그 시점의 사실일 뿐 — 부하 테스트의 가치는 추이에서 나온다(테스트가 코드면 비용은 실행뿐이다).

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 합격선 | SLO 기반 명문화(p95·에러율) — 없으면 테스트 시작 금지 | 안티패턴 1 |
| 목표 부하 | 예상 피크 × 1.5~2 (여유 검증) | 용량 계획 관행 |
| think time | 여정당 수 초(실사용 근거) — 0은 의도 명시 시만 | 안티패턴 2 |
| 생성기 | CPU 70% 초과 시 분산·증설 | 안티패턴 3 |
| 보고 | p50/95/99+에러율+시간축 — 평균 단독 금지 | 안티패턴 5 |
| 지속 시간 | 워밍업 후 정상 상태 수 분+ (스파이크 테스트는 별도 설계) | 순간치 함정 |
| 이벤트성 부하 | 평시 ×N이 아니라 "0초에 전원" 스파이크 모델 + 핫스팟(같은 행·재고) 재현 | 실전 케이스 |

## 워크플로우 (부하 테스트 1건)

1. **명제 작성** — "부하 X에서 SLO Y를 만족한다"를 검증 명제로 + 목표 부하 산정 근거(dev-system-design).
2. **시나리오 코드화** — 운영 비율 기반 여정 + 데이터 다양화. 스크립트는 레포 `loadtest/`에(버전 관리). 기존 파일 덮어쓰기 대신 Edit.
3. **환경·안전 합의** — 대상 환경 명시 + (공유 환경이면) 공지·창·중단 스위치.
4. **실행 (copy-paste)**:
   ```
   k6 run --vus 50 --duration 5m loadtest/journey.js   # 기본형(closed-loop) — 빠른 스모크용
   k6 run loadtest/journey.js                           # CO 보정형(아래 options 내장 후) — 합격 판정용
   # 실행 중 생성기 자원: 다른 셸에서 모니터링 (Windows: 작업관리자 / Linux: top·ss -s)
   ```
   CO 보정 핵심 — 스크립트 `options`에 **도착률 고정** executor를 둔다(서버가 느려져도 부하는 계속 도착):
   ```js
   export const options = {
     scenarios: {
       journey: {
         executor: 'constant-arrival-rate',
         rate: 50, timeUnit: '1s',        // 초당 50요청을 "도착시킨다" (응답을 기다리지 않음)
         duration: '5m',
         preAllocatedVUs: 100, maxVUs: 500,  // VU가 모자라면 dropped — 그 자체가 생성기 한계 신호
       },
     },
     thresholds: { http_req_failed: ['rate<0.001'], http_req_duration: ['p(95)<300'] },  // SLO = 합격선
   };
   ```
5. **보고·인계** — 4종 세트 + 변곡점 → 불합격이면 dev-performance 진단 루프로 → 수술 후 **같은 시나리오 재시험**.

### 작성 예시

```
## API 서버 출시 전 부하 (가정)
### 명제: 50 RPS(예상 피크 25×2)에서 p95<300ms·에러<0.1% → 판정: 불합격
### 시나리오: 조회 여정 80%+등록 20%(운영 로그 비율), think 3s, 종목 ID 풀 3천 개 순환
### 결과: p50 85ms / p95 1.2s / 에러 0% — 35 RPS부터 p95 변곡, 그 시점 DB 커넥션 풀 소진 확인
### 생성기 건전성: CPU 31% / arrival-rate 모드
### 다음: 풀 크기·쿼리 진단 인계 → 수술 후 동일 시나리오 재시험 예약
### 확인 필요: 없음 — 변곡점·자원 상관까지 특정됨
```

❌ "1만 동접 버팀! (단일 GET·think 0·캐시 100% 적중)" (가짜 합격)
✅ "현실 여정 + 도착률 고정 + p99 — 불합격의 주소(변곡점)까지가 산출물"

### 사용자가 권고를 거부하면

- "그냥 한계치만 보고 싶다" → breaking point 테스트는 정당한 목적 — 합격선 테스트와 별개임을 명시하고 진행·기록.
- "스테이징 없으니 로컬에서" → 비교 결론(전후 상대 비교) 한정 조건으로 동의 — "절대 용량 결론 불가" 1줄 기록(partial).
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단이 막히면 (확인 필요 4요소)

진행 불가 지점에서는 추측으로 메우지 말고 4요소를 갖춰 사용자에게 질의한다 — **누가**(결정 주체: SLO 합격선·목표 피크 부하·대상 환경은 사용자/운영 결정 사항) / **언제**(시나리오 코드화 전 — 합격선 없는 실행은 거짓 안심을 제조하고, 공유 환경 무단 타격은 동료 장애를 부른다) / **어떻게**(예: "p95·에러율 합격선을 얼마로 둘까", "예상 피크 부하의 근거(DAU·이벤트성 여부)는", "스테이징이 프로덕션과 동형인가, 공지·창은 합의됐나") / **기대값**(그 답이 합격 판정 기준·도착률 모델·절대 vs 상대 결론 가능 여부를 가른다). 확인 불가 시 대체 경로: 절대 용량 결론을 보류하고 "코드 변경 전후 상대 비교"만 산출 + "확인 필요 — SLO·환경 미확정, 비교 결론 한정" 1줄 기록.

대학 수강신청·콘서트 티켓팅·게임 출시·공공 재난지원금 사이트 — 예고된 동시 접속 이벤트에서의 다운이 연례 장르로 반복된다. 사후 분석의 공통 패턴: 부하 테스트를 했지만 ① 평시 패턴으로(전원이 같은 1초에 몰리는 스파이크가 아니라) ② 단일 API로(실제론 로그인→조회→신청의 여정이 세션·락 경합을 만듦) ③ 캐시가 다 받아주는 데이터로(전원이 같은 인기 항목을 두드리는 핫스팟 미재현) 테스트했다 — 즉 **테스트가 거짓 안심을 제조**했다. 교훈: ① 이벤트성 부하는 평시 ×N이 아니라 "0초에 전원" 스파이크 모델로 별도 설계 ② 핫스팟(같은 행·같은 재고)이 진짜 시험 문제다 ③ 대기열(가상 대기실)은 부하 테스트의 실패를 인정하고 부하 자체를 설계하는 정답일 수 있다. 상세: `references/evidence.md`
