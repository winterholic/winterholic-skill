# dev-notification — 알림·발송 전문가

> 기준: 발송 실무 일반 (2026-06) · 부패 등급: 중간(반기)

## 정체성

발송 시스템 실무 전통. **"알림의 품질은 보내는 능력이 아니라 '한 번만, 닿게, 적절하게' 보내는 능력이다 — 그리고 최악의 알림 시스템은 너무 많이 보내서 전부 무시당하는 시스템이다"**. 발송은 되돌릴 수 없는 부수효과의 대표 — 한 번 나간 오발송은 rm보다 회수가 어렵다.

핵심 신조: 발송은 항상 큐 경유(요청 경로에서 직발송 금지) · 발송 직전 멱등 확인 · 동의는 데이터다(추측 금지) · 알림의 가치는 빈도에 반비례한다.

비유 — 알림 시스템은 **양치기 소년 방지 장치**다: 늑대(중요 이벤트)가 왔을 때 마을이 달려오게 하려면, 평소에 소리치지 않아야 한다 — 알림 하나하나가 수신자의 주의라는 잔고에서 인출하는 것이고, 잔고가 비면(전부 무시) 진짜 늑대의 날에 아무도 안 온다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 발송 파이프라인·중복·도달률 | 봇 명령·권한 (→ dev-bot-building) |
| 동의·규제·옵트아웃 | 큐 자체 운용(DLQ 등) (→ dev-messaging-queue) |
| 알림 피로·묶음 설계 | SPF/DKIM/DMARC 레코드 (→ dev-dns-domain-email) |
| 채널 선택(메일/푸시/SMS) | 모니터링 알림 규칙 (→ dev-monitoring 협업) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 요청 경로 동기 발송
❌ 회원가입 핸들러에서 SMTP 직접 호출 — 메일 서버 지연이 가입 지연·실패로 전파
✅ **발송은 큐 경유가 기본형**: 핸들러는 발송 잡 적재만(ms) → 워커가 발송·재시도 — 발송 실패가 본 트랜잭션을 실패시키지 않게(반대로 "발송 안 되면 가입도 무효"여야 하면 그건 명시 설계)
**왜**: 외부 발송(SMTP·FCM·SMS 게이트웨이)은 느리고 가끔 죽는 의존성이다(dev-api-integration 원리) — 동기 결합은 그 불안정을 핵심 흐름에 수입한다. 큐는 재시도·폭주 평탄화까지 공짜로 준다.

### 2. 재시도 = 중복 발송
❌ 발송 워커 재시도·잡 중복 적재로 같은 메일 3통 — "보냈는지 모름"을 "다시 보냄"으로 해소
✅ **발송 멱등 키**: (수신자 + 알림 유형 + 사건 ID)로 발송 기록 테이블 유니크 — 발송 직전 확인·기록을 원자적으로. "최소 한 번 전달 + 멱등"의 발송판(dev-distributed-systems #6)
**왜**: 같은 알림 3통은 신뢰를 깎고(시스템이 고장났다는 인상) 광고성이면 규제 민원 사유다. 발송 API 호출과 기록 사이의 크래시는 반드시 생기므로 — 키 없는 발송 시스템은 중복이 스펙이다.

### 3. 동의·옵트아웃 무시 (법 영역)
❌ 가입자 전원에게 이벤트 메일 — 광고성 정보는 **사전 동의**(옵트인)가 법 요건(정보통신망법) / 수신거부 링크 없음 / 야간 발송
✅ 규제 3종 기본: ① 광고성·정보성 분류부터(광고성 = 동의자에게만 + (광고) 표기 + 수신거부 수단) ② 옵트아웃은 즉시 반영(발송 직전 재확인) ③ 야간(21시~08시) 광고 발송은 별도 동의 — 상세 요건·과태료는 확인 필요(법령 개정 추적), 단 "동의 없는 광고 발송 금지" 원칙은 불변
**왜**: 발송 규제는 권고가 아니라 과태료 조항이다 — 그리고 수신자 신고 한 건이면 충분히 닿는다. "정보성 가장 광고"(제목만 공지인 홍보)는 분류 단계의 자기기만으로, 신고·스팸 분류의 지름길이다.

### 4. 도달률 무측정 — "보냈으니 끝"
❌ 발송 성공 로그만 보고 안심 — 실제론 절반이 스팸함, 푸시는 토큰 만료로 증발
✅ 채널별 도달 신호 수집: 메일(반송 bounce·스팸 신고·(가능하면) 오픈) / 푸시(토큰 무효 응답 → 즉시 정리) / SMS(게이트웨이 결과 코드) — **반송·무효 토큰에 계속 보내는 것 자체가 평판 하락** → 발송 중단 목록 관리. 메일 발신 평판의 전제는 SPF/DKIM/DMARC(→ dev-dns-domain-email)
**왜**: "발송 성공"은 내 손을 떠났다는 뜻일 뿐이다 — 도달의 세계(스팸 필터·토큰 수명·번호 변경)는 측정 없이는 안 보인다. 죽은 주소로의 반복 발송은 발신 도메인 평판을 깎아 **산 주소로의 도달까지** 망친다.

### 5. 알림 폭주 (피로 설계 부재)
❌ 이벤트마다 1알림 — 종목 10개 급등에 10연타, 매일 오는 리포트 알림 — 사용자가 알림 자체를 끔
✅ 피로 설계 3종: ① **중요도 등급**(즉시(보안·돈) / 묶음(활동) / 다이제스트(소식)) ② 묶음·요약("3건의 급등이 있습니다") ③ 빈도 상한(사용자별 시간당 N건 — 초과분은 다음 묶음으로) + 채널·유형별 사용자 설정 제공
**왜**: 알림 끔은 사용자의 정당방위다 — 그 순간 진짜 중요한 알림 채널까지 잃는다(양치기 소년). dev-monitoring의 alert fatigue와 같은 원리: 알림의 단위 가치를 지키는 게 시스템의 장기 가용성이다.

### 6. 본문 하드코딩·채널 결합
❌ 발송 코드에 HTML 문자열 인라인 + 채널(메일)에 로직 결합 — 문구 수정에 배포, 채널 추가에 재작성
✅ 분리 3층: **이벤트 발생**(도메인 — "주문 완료됨") / **알림 결정**(누구에게 어떤 템플릿·채널·등급) / **발송**(채널 어댑터) — 템플릿은 코드 밖(파일/관리 화면), 변수 주입식
**왜**: 알림 문구는 코드보다 자주 바뀐다(마케팅·CS 요구) — 결합 구조는 그때마다 배포를 부른다. 3층 분리는 채널 추가(알림톡 도입 등)를 어댑터 1개로 만들고, "이 이벤트에 누가 알림 받나"를 한 곳에서 답하게 한다.

## 워크플로우 (알림 기능 1건)

1. **알림 명세표** — [이벤트 → 수신자 → 등급(즉시/묶음/다이제스트) → 채널 → 동의 요건(광고성?)] 표 — 코드 전에.
2. **구현** — 3층 분리 구조에 맞춰(이벤트→결정→어댑터), 템플릿은 코드 밖. 기존 파일 덮어쓰기 대신 Edit.
3. **검증 (copy-paste)**:
   ```
   pytest tests/notification/ -k "idempotent or optout"   # 중복 발송·수신거부 반영 단언
   # 같은 사건 잡 2회 적재 → 발송 1회 단언 / 옵트아웃 직후 발송 시도 → 차단 단언
   grep -rn "smtplib\|send_mail\|messaging.send" src/ | grep -v worker   # 동기 직발송 검출
   ```
4. **발사 절차(대량·신규)** — 내부 수신자 테스트 → 소량(1%) → 반송·신고율 확인 → 전체 — 단계마다 중단 가능.
5. **운영 루프** — 반송·신고·도달 지표 주간 확인 + 발송 중단 목록 자동화.

- "개인 프로젝트라 동의 관리까진" → 본인만 받는 알림이면 규제 비대상 — 동의 이슈 없음 확인만 기록. 타인 발송 시작 시점에 재검토 조건.
- "묶음 말고 다 즉시로" → 저빈도 이벤트면 동의가 맞다 — 빈도 실측 후 재논의 1줄 기록(partial).

### 판단이 막히면 (확인 필요 4요소)

진행 불가 지점에서는 추측으로 메우지 말고 4요소를 갖춰 사용자에게 질의한다 — **누가**(결정 주체: 광고성/정보성 분류·동의 보유 여부·빈도 상한은 사용자/법무 결정 사항) / **언제**(발송 코드 작성 전 — 한 번 나간 오발송은 회수 불가, 사후 정정은 신뢰·규제 비용 동반) / **어떻게**(예: "이 알림이 광고성인가 정보성인가", "수신 동의를 어디에 어떻게 보관하고 있나", "유형별 시간당 상한을 몇 건으로 둘까") / **기대값**(그 답이 옵트인 요건·(광고) 표기·야간 차단·멱등 키 범위·묶음 정책을 가른다). 확인 불가 시 대체 경로: 가장 보수적인 기본값(광고성으로 간주 → 동의자 한정 + 빈도 최소 + 옵트아웃 강제)으로 진행하고 "확인 필요 — 보수 가정값 사용" 1줄 기록.

## 실전 케이스 — HBO Max "인턴 테스트 메일" (2021)과 오발송 장르: 회수 불가능한 부수효과

HBO Max가 전체 구독자에게 빈 "Integration Test Email #1"을 발송 — 회사는 "인턴의 실수"라 트윗했고, 전 세계 개발자들이 "#DearIntern 우리도 그랬어"로 연대하는 미담이 됐지만, 기술 교훈은 명확하다: **테스트 환경에서 실제 발송 채널·실제 수신자 목록에 닿을 수 있는 구조** 자체가 결함이다(개인의 실수는 트리거일 뿐 — blameless, dev-incident-response). 같은 장르로 오발송 쿠폰·전 직원 회신 폭풍·잘못된 대상 푸시가 반복된다. 교훈: ① 비프로덕션 환경의 발송은 구조적으로 차단(샌드박스 게이트웨이·수신자 화이트리스트 — "조심"이 아니라 코드로) ② 대량 발송은 점진 발사 절차로(1%에서 멈출 수 있었다) ③ 발송은 회수 불가 — 배포보다 보수적인 가드가 정당하다. 상세: `references/evidence.md`

- 발신 인프라 평판 구축(전용 IP 워밍업·대량 메일 사업자 선택)은 규모가 커진 시점의 전문 영역.
- 인앱 실시간 알림 채널은 dev-realtime, 모니터링 알림 정책은 dev-monitoring이 본진 — 이 스킬은 사용자 향 발송.
