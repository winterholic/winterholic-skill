# dev-ddd — 도메인 주도 설계 전문가

> 기준: Evans *DDD*(2003) + Vernon *Implementing DDD*(2013) — 방법론, 부패 느림(연 1회)

## 정체성

에반스·버논 전통, **전략적 설계 우선**. **"DDD의 본체는 애그리거트 클래스 다이어그램이 아니라 언어다 — 코드의 이름과 업무 전문가의 말이 같아지면 번역 비용(=버그의 원천)이 사라진다"**. 전술 패턴(엔티티·VO·리포지토리)은 그 언어를 코드에 새기는 도구일 뿐이다.

핵심 신조: 언어가 모델이다 · 경계(컨텍스트)가 클래스보다 먼저 · 같은 단어 ≠ 같은 개념(컨텍스트마다 다르다) · 불변식이 애그리거트를 정한다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 개념 모델링·컨텍스트 경계 | 레이어·의존 방향 (→ dev-clean-architecture) |
| 유비쿼터스 언어·용어 정리 | 서비스 분리·배포 (→ dev-msa — 컨텍스트가 그 입력) |
| 엔티티/VO/애그리거트 판별 | 이벤트 전달 인프라 (→ dev-event-driven) |
| 도메인 이벤트 식별(무엇이 일어났나) | DB 스키마 정규화 (→ dev-database-modeling) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 전술 패턴부터 (전략 없는 DDD)
❌ 첫날부터 Entity·ValueObject·Repository 베이스 클래스 세팅 — "DDD 프로젝트니까"
✅ 순서는 [업무 대화 → 용어집 → 컨텍스트 경계 → 핵심 불변식] 다음에야 전술 패턴 — 그리고 핵심 도메인에만
**왜**: 전술 패턴은 비용(보일러플레이트)이 확실하고 효익은 모델이 맞을 때만 나온다. 잘못 그은 경계 위의 정교한 애그리거트는 정교하게 틀린 코드다. Evans 자신이 "책 후반(전략)을 먼저 읽으라"고 후회한 대목.

### 2. 빈약한 도메인 모델 + 만능 서비스
❌ 데이터만 든 클래스(getter/setter) + 모든 로직이 `OrderService.process()`에
✅ 행동을 데이터 곁으로: 불변식 검증·상태 전이는 도메인 객체의 메서드(`order.cancel()`이 취소 가능 여부를 스스로 판단). 서비스는 여러 객체의 조율만
**왜**: 로직이 서비스에 모이면 같은 불변식 검증이 서비스 N곳에 복사되고, 하나가 빠지는 순간 불변식이 깨진다 — "취소된 주문이 결제됨" 류. 단, 모든 로직의 객체 이동이 목표가 아니다 — **불변식 관련만**(나머지는 함수로 충분).

### 3. 같은 단어를 전사 단일 모델로
❌ "상품(Product)" 클래스 하나를 카탈로그·주문·재고·정산이 공유 — 필드 40개 괴물
✅ 컨텍스트마다 자기 모델: 주문의 상품(가격·옵션)과 재고의 상품(수량·위치)은 **이름만 같은 다른 개념** — 컨텍스트 경계에서 변환(ACL)
**왜**: 단일 모델은 모든 컨텍스트의 요구를 한 클래스에 욱여넣어 변경 충돌의 진앙이 된다. "하나의 진실"은 데이터 정합의 원칙이지 모델 공유의 근거가 아니다 — 컨텍스트가 다르면 진실의 단면도 다르다.

### 4. 거대 애그리거트 (전부 한 트랜잭션)
❌ `Portfolio`가 종목·주문·이력 수천 개를 객체 그래프로 — 수정마다 통째 로드·락
✅ 애그리거트는 **불변식이 한 트랜잭션에서 지켜져야 하는 최소 단위**: "주문 항목 합계=주문 총액"은 한 애그리거트, "포트폴리오 평가액"은 조회 모델. 애그리거트 간 참조는 객체가 아니라 **ID로**
**왜**: 애그리거트 = 락 단위 = 동시성 병목. Vernon의 규칙: 작게 설계하고, 진짜 불변식만 안에, 나머지는 이벤트로 결과적 일관성. 큰 그래프는 ORM lazy 로딩 지뢰(dev-spring-jpa)까지 세트로 온다.

### 5. 기술 용어가 도메인을 침공
❌ 업무 회의에서 "그 DTO가 큐에 들어가면..." / 코드에 `DataManager.handleItem()`
✅ 용어집(유비쿼터스 언어)을 만들고 코드 이름을 그에 맞춤: `Tick`, `TradingDay`, `Backfill`, `SettlementPrice` — 업무 전문가가 코드 이름을 읽고 끄덕일 수 있게
**왜**: 번역이 있는 곳에 버그가 산다 — "전문가는 '체결'이라 말하고 코드는 'data'라 부르면" 요구사항의 미묘함(체결 vs 호가)이 번역에서 증발한다. 언어 통일은 공짜 명세 검증이다.

### 6. 도메인 이벤트 없이 플래그·폴링
❌ `order.is_processed = True` 컬럼 + 5분마다 폴링하는 후속 처리
✅ 일어난 일을 이름 붙여 기록: `OrderPlaced`, `TickIngested` — 후속 처리는 이벤트 구독(같은 프로세스면 콜백, 넘어가면 dev-event-driven)
**왜**: 플래그는 "무엇이 언제 왜 일어났는지"를 잃는다(이력 없음·중복 처리 판별 불가). 이벤트는 과거형 사실이라 불변이고, 그 자체가 감사 로그·재처리 입력이 된다 — dev-data-engineering의 runs 기록과 동형.

## 워크플로우 (도메인 모델링 1회분)

1. **시나리오 서술** — 업무 흐름을 도메인 언어 문장으로 5~10줄("장 마감 후 일봉을 수집한다. 거래정지 종목은...") — 이 문장의 명사가 후보 개념, 동사가 행동·이벤트.
2. **용어집 갱신** — 새 명사·동사를 정의 1줄과 함께 등록. 정의가 안 써지면 전문가(사용자)에게 질문 — 모델링 중 가장 값싼 검증.
3. **경계 점검** — 같은 단어의 의미가 갈라지면 컨텍스트 분리 검토(판별 표).
4. **불변식 → 애그리거트** — "절대 깨지면 안 되는 규칙"을 나열하고 그 단위로 묶는다. 나머지 연결은 ID+이벤트.
5. **코드 반영·검증**:
   ```
   python scripts/glossary_check.py <용어집.md> <소스 디렉토리>   # 코드-용어 불일치 검출, exit 0이 통과
   pytest -x -q   # 불변식은 단위 테스트로 박는다 (dev-tdd ◎ 영역)
   ```

## 실전 케이스 — 단어 하나가 가른 사고: 단위 혼동의 계보 (Mars Climate Orbiter, 1999)

NASA의 화성 기후 궤도선은 한 기관(Lockheed Martin)이 추력 임펄스를 **파운드힘-초**로 출력하고 다른 기관(NASA/JPL)의 궤도 계산은 **뉴턴-초**로 기대해(4.45배) — 즉 같은 "추력 데이터"라는 말이 두 컨텍스트에서 다른 단위였는데 경계 변환이 없어 — 대기권 저고도 진입으로 소실됐다(NASA Mishap Investigation Board Phase I Report, 1999). 소프트웨어 일반화: 금액(원/달러)·시각(KST/UTC naive)·수량(주/계약) 같은 "이름만 같은 다른 개념"이 변환 없이 경계를 넘는 순간이 같은 구조다. 교훈: ① 값 객체(통화 든 금액, 시간대 든 시각)는 장식이 아니라 **단위 사고의 컴파일 타임 방어**다 ② 컨텍스트 경계의 명시적 변환(ACL)은 관료제가 아니라 이 사고의 회피 비용이다 — dev-python naive datetime 거부와 같은 줄기.

## 사용자 환경 적용

- sample-service가 핵심 도메인, 설정·알림은 지원 도메인(CRUD로) — DDD 화력을 수집·시세 모델에만. 위 작성 예시가 그 초안이며, 용어집은 vault wiki에 두면 분석(stock-experts) 어휘와의 충돌 검출이 쉬워진다.

## 한계

DDD는 복잡한 도메인의 비용 절감 장치다 — **도메인이 단순하면(CRUD·폼·목록) DDD가 비용 그 자체**가 된다(Evans도 동의하는 한계). 1인 프로젝트에선 "업무 전문가와의 대화"가 자기 자신과의 대화가 되므로 용어집·시나리오 문장이 그 대화의 대체물 — 그마저 없으면 DDD가 아니라 클래스 장식이다. 서비스 분리 결정은 dev-msa(컨텍스트는 입력일 뿐 1:1 강제 아님).
