# 전략적 설계 — 컨텍스트 매핑·도메인 구분·이벤트 스토밍 경량판 (SKILL.md 비중복)

## 핵심/지원/일반 도메인 구분 (투자 배분 결정)

| 구분 | 정의 | 처방 |
|---|---|---|
| **핵심(Core)** | 이걸 잘해서 이기는 부분 — 경쟁력 그 자체 | DDD 풀화력(용어집·애그리거트·이벤트) + 최고 인력/시간 |
| **지원(Supporting)** | 핵심을 돕지만 차별점 아님 (알림·설정·관리 화면) | CRUD·단순 구조 — 빈약한 모델이 정답인 곳 |
| **일반(Generic)** | 어디나 같은 문제 (인증·결제·메일) | 사고 말고 도입 — 라이브러리·SaaS·기성 스킬(dev-auth 등) |

가장 흔한 전략 실패: 일반 도메인(직접 만든 인증)에 핵심급 투자, 핵심 도메인은 CRUD 방치 — 배분표를 먼저 그려라.

## 컨텍스트 매핑 관계 유형 (경계 간 계약)

| 관계 | 뜻 | 쓰는 순간 |
|---|---|---|
| **ACL (Anticorruption Layer)** | 상대 모델을 내 모델로 번역하는 방어층 | 외부 API·레거시와 접점 — **기본값** (키움 API ↔ 내 Tick 변환층이 정확히 이것) |
| Conformist (순응) | 상대 모델을 그대로 수용 | 번역 비용 > 모델 불만일 때 (대형 플랫폼 SDK) |
| Customer/Supplier | 하류가 상류에 요구 가능 | 두 팀이 협상 가능한 사내 관계 |
| Partnership | 함께 변경 조율 | 강결합 두 컨텍스트 — 가능하면 피함 |
| Shared Kernel | 모델 일부 공유 | 최후 수단 — 공유분 변경이 양쪽 동시 배포 강제 |
| Published Language | 공개 표준 스키마로 소통 | 다수 소비자 (rest-api-design의 계약이 이것) |

1인 프로젝트의 번역: 관계 유형은 "모듈 간 import 규칙"이 된다 — 분석 모듈이 수집 모듈의 내부 모델을 직접 import하면 Shared Kernel(최후 수단)을 기본값으로 쓰고 있는 것.

## 이벤트 스토밍 경량판 (1인용 30분)

1. **주황 포스트잇(이벤트)**: 도메인에서 일어나는 일을 과거형으로 나열 — "일봉이 적재됐다", "수집이 실패했다", "점검일이 도래했다". 시간순 정렬.
2. **파랑(커맨드)**: 각 이벤트를 일으키는 행위 — "수집을 실행한다".
3. **노랑(애그리거트)**: 커맨드를 받고 이벤트를 내는 단위 — 커맨드·이벤트가 모이는 곳이 애그리거트 후보.
4. **경계 긋기**: 이벤트 흐름이 한산해지는 지점·언어가 바뀌는 지점이 컨텍스트 경계 후보.
5. 산출물: 이벤트 목록(이름 그대로 도메인 이벤트 클래스/테이블 후보) + 경계 스케치 — 이것이 모델링 워크플로우 1(시나리오)의 시각판.

## 전술 패턴 최소 사전 (필요해졌을 때만)

- **리포지토리**: 애그리거트의 저장·복원 추상 — 컬렉션처럼 보이게. 쿼리 빌더 만능 객체로 비대해지면 조회는 별도 조회 모델(CQRS-lite)로.
- **팩토리**: 생성 불변식이 복잡한 애그리거트만 — 아니면 생성자/클래스메서드.
- **도메인 이벤트 구현**: 같은 트랜잭션 내 기록 + 커밋 후 발행(아웃박스 — dev-event-driven) — 발행 먼저 하면 롤백 시 유령 이벤트.
- **CQRS**: 쓰기 모델(애그리거트)과 읽기 모델(평면 뷰) 분리 — 조회 화면이 애그리거트를 비틀기 시작하면 도입 신호. 이벤트소싱과는 별개 결정(같이 갈 필요 없음).
