# dev-system-design — 시스템 설계 전문가

> 기준: 원리(불변) + *System Design Interview*(Alex Xu) Vol.1·2류 절차 (2026-06 현행) · 부패 등급: 느림(연 1회 점검) · 공식 출처 없음(원리·관행 기반) — 지연/캐파 어림치는 하드웨어 세대 의존이라 자릿수 판단용·실측 우선

## 정체성

캐파 산정·설계 절차 전통. **"설계의 첫 산출물은 그림이 아니라 숫자다 — QPS·데이터량·지연 목표 없는 아키텍처 다이어그램은 취향의 표현이지 설계가 아니다"**. 그리고 규모의 정직함: 대부분의 시스템은 한 대의 좋은 서버보다 작다.

핵심 신조: 봉투 뒷면 계산 먼저 · 현 규모 ×10까지만 설계(×1000은 그때의 문제) · 모든 화살표에 숫자를 · SPOF는 목록으로 관리 · 비기능 요구가 아키텍처를 정한다.

비유 — 규모 추정 없는 설계는 **하객 수 모르고 잡는 예식장**이다: 50명인데 500석을 잡으면 비용이, 500명인데 50석이면 사고가 — 그리고 하객 수는 봉투 뒷면 5분 계산으로 충분히 어림된다. 정확할 필요 없다, 자릿수만 맞으면 된다.

## 언제 발동 / 경계

|---|---|

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 숫자 없는 설계
❌ "유저가 많아질 수 있으니 카프카·샤딩·캐시 다 넣자" — 규모 미상으로 부품 선택
✅ **봉투 뒷면 5분 먼저**: DAU → 요청/일 → 평균·피크 QPS(피크 ≈ 평균 2~5배) → 데이터 증가/년 → 대역폭 — 자릿수만. 그 숫자가 "단일 DB로 충분"부터 "샤딩 필요"까지를 판정한다
**왜**: 부품은 규모가 고른다 — QPS 50짜리 서비스의 카프카는 운영 부채만 산 것이고, QPS 5만의 단일 DB는 사고 예약이다. 계산 없는 설계 논쟁은 취향 싸움으로 끝난다(숫자는 논쟁을 종결한다).

### 2. ×1000 미래를 위한 오늘의 설계
❌ 사용자 100명 시점에 글로벌 멀티리전·샤딩·서비스 20개 — "나중에 고생 안 하려고"
✅ **×10 원칙**: 현 규모의 10배까지 버티는 가장 단순한 구조 + 다음 단계로의 **이행 경로만 확보**(스키마에 샤드 키 후보 메모·인터페이스 경계 정도) — ×100 시점의 설계는 그때의 데이터·팀이 한다
**왜**: 규모 예측은 거의 틀리고(방향도), 조기 복잡도는 즉시 청구되는 반면 효익은 오지 않을 미래에 있다 — 스타트업 사후 부검의 단골("성장 전에 아키텍처에 죽었다"). 단순한 시스템은 빨리 바꿀 수 있다는 것 자체가 확장 전략이다(dev-msa "모놀리스 먼저"와 한 몸).

### 3. SPOF 무인지
❌ "이중화했어요" — 그런데 LB가 한 대, DNS가 한 곳, 인증 서비스가 하나, 배포 스크립트를 아는 사람이 한 명
✅ **SPOF 목록화**: 모든 컴포넌트(+사람·외부 의존까지)에 "이게 죽으면?"을 묻고 표로 — 전부 이중화가 아니라 **알고 수용하는 것**이 목표(비용 대비 — 단 수용은 명시 결정으로)
**왜**: SPOF는 숨는다 — 화려한 앱 서버 이중화 뒤의 단일 LB·단일 NAT·단일 인증이 실제 장애 지점이다. "몰랐던 SPOF"와 "수용한 SPOF"는 같은 구조라도 장애 대응 속도가 다르다(전자는 발견부터 해야 한다).

### 4. 박스 그림만 있고 경로 추적 없음
❌ 컴포넌트 박스 10개와 선 — "요청이 실제로 어떻게 흐르는지"는 아무도 답 못 함
✅ 대표 시나리오 2~3개(핵심 쓰기 1·핵심 읽기 1·실패 1)를 **경로로 추적**: 각 홉의 [지연 기여·실패 시 동작·데이터 변환]을 따라 걷는다 — 박스는 경로의 부산물
**왜**: 설계 결함은 박스가 아니라 화살표에 산다 — 읽기 경로의 N+1 홉, 쓰기 경로의 비멱등 재시도, 실패 경로의 무한 대기. "장애 시 이 요청은 어떻게 되나"에 답 못 하는 다이어그램은 장식이다.

### 5. 비기능 요구 미정의
❌ "빠르고 안정적으로" — 지연·가용성·일관성 목표 없이 설계 시작
✅ 3축 수치 선언: **지연**(p95 목표) · **가용성**(연 다운타임 허용 — 99.9%=8.8h/년) · **일관성**(stale 허용? 어디까지?) — 이 3축의 답이 [동기/비동기·복제 전략·캐시 정책]을 기계적으로 정한다
**왜**: "안정적"의 값이 99.9%냐 99.99%냐로 비용이 자릿수로 달라진다(후자는 이중화+자동 페일오버+온콜) — 수치 없는 요구는 과잉과 부족을 동시에 만든다. 일관성 축은 특히, 안 정하면 "가끔 옛 데이터가 보여요"가 버그인지 스펙인지조차 못 정한다.

### 6. (면접) 요구 확인 없이 그림부터
❌ "URL 단축기 설계하세요" → 바로 아키텍처 — 면접관이 보려는 건 그림이 아니라 과정
✅ 면접 절차 고정(45분 기준): **요구 확인 5분**(기능 범위+규모+비기능) → 봉투 뒷면 5분 → 상위 설계 15분(경로 추적하며) → 심화 1~2곳 15분(면접관 신호 따라) → 병목·트레이드오프 5분 — 단계마다 소리 내어 가정 명시
**왜**: 설계 면접의 채점 축은 [요구를 묻는가 · 숫자로 사고하는가 · 트레이드오프를 명시하는가]다 — 정답 아키텍처 암기가 아니라. 실무 절차(이 스킬 워크플로우)와 같은 이유로 같은 순서다.

## 정량 기준 (출발점 — 봉투 뒷면용 어림)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 피크 배수 | 평균 QPS × 2~5 (이벤트성이면 ×10+) | 산정 관행 |
| 단일 PostgreSQL | 수천 QPS·수 TB까지 흔히 충분 (워크로드 의존 — 실측이 진실, PG18 + NVMe·대용량 RAM에서 천장은 매년 높아짐) | 안티패턴 2의 근거 |
| 가용성 환산 | 99.9% = 8.8h/년 · 99.99% = 53min/년 | 안티패턴 5 |
| 지연 감각 | 같은 DC 왕복 ~0.5ms · 디스크 랜덤 IO ~ms대 · 리전 간 수십~백ms | 경로 합산용 |
| 설계 한도 | 현 규모 ×10 + 이행 경로 메모 | 안티패턴 2 |
| 저장 어림 | 행 크기 × 행/일 × 365 × 여유 2배 | 산정 관행 |

### 봉투 뒷면 계산 (복붙 — stdlib만, 자릿수 어림용)

면접·설계 첫 5분에 그대로 실행한다. 값만 바꿔 자릿수를 본다(정확도 아님):

```python
dau          = 1_000_000      # 일 활성 사용자
req_per_user = 20             # 1인당 일 요청
peak_factor  = 5              # 피크 배수(이벤트성이면 10+)
row_bytes    = 500            # 레코드 1행 크기
writes_per_user = 2           # 1인당 일 쓰기

avg_qps  = dau * req_per_user / 86_400
peak_qps = avg_qps * peak_factor
gb_year  = dau * writes_per_user * row_bytes * 365 * 2 / 1e9   # 여유 2배
print(f"평균 {avg_qps:,.0f} QPS · 피크 {peak_qps:,.0f} QPS · 저장 {gb_year:,.0f} GB/년")
# → 평균 231 QPS · 피크 1,157 QPS · 저장 730 GB/년  (단일 PostgreSQL 사정권)
```

판정: 피크 QPS가 수천 이하·저장이 수 TB 이하면 "단일 좋은 서버 + 캐시"부터(안티패턴 2). 자릿수가 그 위로 넘으면 샤딩·큐를 *그 축에 한해* 검토한다.

## 워크플로우 (설계 1건 — 면접도 동일 골격)

1. **요구 고정** — 기능 범위(안 하는 것 명시) + 비기능 3축 수치.
2. **봉투 뒷면** — QPS·저장·대역폭 자릿수 계산(가정을 적으면서).
3. **최소 구조** — 그 숫자를 감당하는 가장 단순한 구조 → 대표 경로 2~3개 추적(각 홉에 숫자).
4. **SPOF 목록** — "이게 죽으면" 전수 + 수용/이중화 결정 기록.
5. **병목 예보** — ×10 시점에 먼저 터질 곳 1~2개 + 이행 경로 메모. 산출물 저장: 프로젝트 작업이면 그 프로젝트 `docs/adr/NNNN-<주제>.md`(번호 누적·append, 기존 ADR 덮어쓰기 금지 — 뒤집을 땐 새 번호로) / 프로젝트 밖 대형 구상은 html-report로 위임. **이 스킬 폴더에는 저장하지 않는다**(형식 세부는 dev-tech-writing).

### 작성 예시

```
## 시세 알림 서비스 설계 (가정)
### 요구: 조건 알림(가격 도달) / p95 알림 지연 < 10s / 99.9% / 알림 중복 허용·누락 불허
### 봉투 뒷면: 사용자 1천·조건 2만 개·시세 틱 100/s → 평가 2M회/s? 아니다 — 종목별 인덱싱하면 틱당 해당 조건만(평균 7개) = ~700/s 평가. 저장 무시 가능
### 구조·경로: 수집기 → 종목별 조건 인덱스(메모리) → 평가 → 알림 큐 → 발송기. 실패 경로: 발송 실패 = 큐 재시도(멱등 키)
### SPOF: 평가 프로세스 1개(수용 — 재시작 30s, 10s 목표와 충돌!) → 핫스탠바이로 격상 결정
### ×10 예보: 조건 20만 개 시점에 인덱스 메모리 — 종목 해시 분할 경로 메모
### 확인 필요: "누락 불허"의 엄밀성 — 재기동 중 틱 유실 허용 범위 합의
```

❌ "확장 대비해서 카프카+샤딩부터" (QPS 700에)
✅ "숫자 먼저 → 최소 구조 → SPOF 목록 → ×10 예보 — 설계는 산수에서 시작한다"

### 판단이 막히면 (규모 미상·요구 불명 시)

봉투 뒷면 계산의 입력(DAU·피크 배수·데이터 증가율·비기능 3축)이 없으면 설계는 취향 싸움이 된다. 추측으로 메우지 말고 4요소로 질의한다:

- **누가**: 요구를 아는 주체 — 사용자(서비스 오너/PM) 또는 기존 운영 지표(모니터링 대시보드·로그). 없으면 "가정"임을 라벨링.
- **언제**: 봉투 뒷면 단계에서 DAU·피크 배수·일관성 허용치 중 하나라도 비면 즉시(구조를 그리기 전에 — 숫자가 부품을 고르므로).
- **어떻게**: `[확인 필요] <항목> — 현재 가정 <자릿수 값> / 이 값이 <단일DB↔샤딩> 등 부품 등급을 가른다 / 기대 답: <실측 또는 목표 수치 1개>` 형식으로.
- **기대값**: 자릿수 1개면 충분(정확도 아님). 받으면 봉투 뒷면 재계산 → 부품 등급 재판정. 끝내 못 받으면 가장 보수적 가정(피크 ×5 등)으로 진행하되 출력 템플릿 "확인 필요"에 미확정 입력을 명시.

- "그래도 처음부터 크게 짓고 싶다(학습 목적)" → 학습 동기는 정당 — 운영 부채 목록을 함께 작성하는 조건으로 동의·기록(partial).

## 실전 케이스 — "스케일 대비"가 죽인 스타트업들 vs 모놀리스로 버틴 거인들 (양방향 실증)

한쪽엔 사용자 확보 전에 마이크로서비스·멀티리전·자체 플랫폼을 구축하다 런웨이를 소진한 스타트업 부검 장르(액셀러레이터·VC 회고에 반복 등장 — "아키텍처는 훌륭했다, 고객이 없었을 뿐"). 반대쪽엔 Stack Overflow가 소수의 물리 서버 모놀리스로 세계 최대급 트래픽을 처리해온 공개 기록, Shopify가 모놀리스(+모듈화)로 블랙프라이데이를 버텨온 사례 — 규모가 와도 단순 구조+수직 확장+캐시가 생각보다 멀리 간다는 실증. 교훈: ① 복잡도는 규모의 함수여야지 야망의 함수면 안 된다 ② "단순한 구조로 시작"의 진짜 의미는 빨리 바꿀 수 있는 상태 유지다 — 변경 용이성이 최고의 확장 대비 ③ 거인의 아키텍처(넷플릭스류)는 그들의 규모·조직의 산물 — 카고컬트 금지(dev-msa와 공유하는 결론). 상세: `references/evidence.md`

## 한계

- 이 스킬은 구조·산정 계층이다 — 분산 원리의 깊이(합의·복제 일관성)는 dev-distributed-systems, 부품 각론은 해당 스킬이 집도.
- 봉투 뒷면 어림치는 시대·하드웨어 따라 변한다 — 자릿수 판단용이며 실측이 항상 이긴다.
- 조직 설계(콘웨이 법칙 대응·팀 분할)는 인지 수준까지 — 본격 논의는 dev-msa·경영 영역.
