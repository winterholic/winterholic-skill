# dev-system-design evidence — 실증 사례

## 1. Stack Overflow — "무어의 법칙 쪽에 베팅한" 모놀리스 (공개 아키텍처 기록)

- **무슨 일**: 세계 최대급 Q&A 트래픽을 소수의 물리 서버(웹 서버 단 자릿수 + SQL Server 소수 대)로 처리해온 공개 기록 — 마이크로서비스·클라우드 전환 압력 속에서도 "수직 확장 + 극단적 캐시 + 단순 구조"를 유지하며 p95 수 ms를 달성했다(아키텍처 블로그·발표로 상세 공개).
- **성립 조건도 정직하게**: 읽기 압도적 워크로드 · 최고 수준 팀의 성능 집착 · 캐시 친화적 도메인 — 모든 서비스가 복제할 모델은 아니다. 그러나 "그 정도 규모도 이렇게 된다"는 상한 실증으로서, ×1000 대비 설계의 반례 가치는 충분하다.
- **이식 교훈**: 단일 고성능 DB + 캐시 계층의 사정거리는 직관보다 길다 — 분산의 비용(dev-distributed-systems의 모든 함정)을 지불하기 전에 수직 확장의 잔여 거리를 계산하라.

## 2. 과잉 설계 부검 장르 — "아키텍처는 훌륭했다" (스타트업 회고 집적)

- **패턴**: 시드 단계에서 마이크로서비스 12개·K8s 클러스터·이벤트 소싱·멀티리전 — 기능 출시 속도가 인프라 운영에 잠식되고, 피벗(스타트업의 본질)마다 서비스 경계가 전부 틀린 경계가 됨 → 런웨이 소진. 창업자 회고·VC 포스트모템에 장르적으로 반복(특히 빅테크 출신 창업팀 — 전 직장 규모의 도구를 이식).
- **수치 감각**: 초기 스타트업 트래픽은 거의 항상 단일 서버 수준(QPS 수십 이하) — 그 규모에서 분산 시스템의 모든 비용(배포 복잡도·디버깅·정합성)은 순손실이다.
- **균형 각주**: 반대 실패(성장이 왔는데 못 버팀)도 실재하나 빈도가 훨씬 낮고, 그 경우조차 병목은 예측한 곳이 아닌 데서 왔다 — "그때 데이터로 그때 설계"가 양쪽 실패의 공통 처방.

## 3. 봉투 뒷면 숫자표 — 산정의 구구단 (실무 어림치)

- **시간 어림** (자릿수용 — 하드웨어 따라 변동, 확인 필요):
  - 메모리 참조 ~100ns · SSD 랜덤 읽기 ~수십µs · 디스크(HDD) 시크 ~ms대
  - 같은 DC 왕복 ~0.5ms · 서울↔도쿄급 ~30ms · 대륙 간 ~100ms+
  - 1MB 순차 읽기: 메모리 ≪ SSD < 네트워크(1Gbps ≈ 8ms)
- **환산 구구단**: 1일 ≈ 86,400초(≈10⁵로 어림) — "일 100만 요청" ≈ 평균 12 QPS(직관보다 훨씬 작다 — 과잉 설계 교정의 1번 숫자) · 1년 ≈ 3×10⁷초 · 99.9% = 8.8h/년.
- **사용법**: 정확도가 아니라 **자릿수 비교**가 목적 — "이 경로는 디스크 랜덤 IO 3번 = ~10ms대, p95 5ms 목표와 충돌" 같은 판정. 계산은 가정을 적으면서(가정이 틀리면 가정만 고치면 된다).
