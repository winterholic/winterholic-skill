# dev-rest-api-design — API 계약 설계 전문가

> 기준: HTTP 의미론(RFC 9110) + Stripe/GitHub API 관행 (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

RESTful 관행 + Stripe·GitHub API의 실전 규약. **"API는 한 번 공개하면 영원히 호환을 끄는 빚이다 — 설계 시간 1시간이 마이그레이션 한 달보다 싸다"**. REST 순수주의가 아니라 **예측 가능성**이 목표: 처음 보는 클라이언트가 문서 없이도 다음 엔드포인트를 추측할 수 있으면 잘 설계된 것.

핵심 신조: 리소스는 명사, 행위는 메서드 · 에러도 계약이다 · 페이지네이션 없는 목록은 시한폭탄 · 추가는 자유, 변경·삭제는 breaking.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| URL·메서드·상태코드·스키마 규약 | Pydantic 모델·라우터 구현 (→ dev-fastapi) |
| 페이지네이션·필터 규약 | keyset 쿼리 구현 (→ dev-postgres) |
| 버저닝·호환성 정책 | 인증 방식 (→ dev-auth) |
| 에러 응답 표준 | 에러 로깅·추적 (→ dev-error-logging) |
| 내 API의 계약 | 남의 API 호출·재시도 (→ dev-api-integration) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. URL에 동사
❌ `POST /getUserList`, `POST /candle/delete?id=3`
✅ `GET /users`, `DELETE /candles/3` — 행위는 메서드가, URL은 리소스(명사·복수형)가
**왜**: 동사 URL은 메서드 의미론(캐시·멱등·재시도 가능성)을 버린다 — 중간 장비·클라이언트 라이브러리가 GET은 재시도해도 되고 POST는 안 된다는 가정으로 동작한다. 예외: 리소스로 못 푸는 동작은 하위 액션(`POST /orders/3/cancel`)으로 — 단 남발하면 RPC다.

### 2. 전부 200 OK (에러를 본문으로만)
❌ `200 {"success": false, "msg": "not found"}`
✅ 상태코드가 1차 신호: 404 + 표준 에러 스키마. 클라이언트 잘못(4xx)과 서버 잘못(5xx)을 정직하게
**왜**: 200-always는 모니터링(5xx율)·재시도 로직·캐시 전부를 장님으로 만든다. "HTTP 위에 자체 프로토콜"은 HTTP의 생태계 이점을 전부 포기하는 선택이다.

### 3. 에러 응답 형식 중구난방
❌ 어떤 건 `{"error": "..."}`, 어떤 건 `{"detail": [...]}`, 어떤 건 문자열
✅ 단일 에러 스키마 고정: `{"error": {"code": "code_not_found", "message": "...", "details": {...}}}` — code는 기계용(불변 식별자), message는 사람용(바뀔 수 있음)
**왜**: 클라이언트는 에러를 **분기 처리**한다 — message 문자열 매칭으로 분기하게 만들면 메시지 수정이 breaking change가 된다. code 필드가 그 분기의 안정 계약.

### 4. 무제한 목록 응답
❌ `GET /candles` → 전 기간 400만 행
✅ limit 기본 50·최대 200 + 커서 페이지네이션: 응답에 `{"data": [...], "next_cursor": "..."}` — 커서는 불투명 문자열(base64 등)로, 내부 키 구조를 계약에서 숨긴다
**왜**: 무제한 목록은 데이터 증가에 따라 어느 날 터지는 시한폭탄(dev-fastapi 정량 기준과 동일). 커서를 불투명하게 하는 이유: 내부 정렬 키를 바꿔도(스키마 변경) 계약이 안 깨진다.

### 5. breaking change를 마이너 취급
❌ 응답 필드 이름 변경·제거, 필수 파라미터 추가, 에러 code 변경을 슬쩍 배포
✅ breaking 판별표(아래)로 분류 — breaking이면 새 버전(`/v2`) 또는 신규 필드 병행 + 폐기 예고(deprecation 기간). **추가는 안전, 변경·삭제·강화는 breaking**
**왜**: API 소비자는 내 배포 일정을 모른다. 단 하나의 클라이언트(자기 프론트)라도 배포 순서 문제(API 먼저 vs 클라 먼저)가 생긴다 — 병행 기간이 그 답.

### 6. 비멱등 재시도 무방비
❌ `POST /orders`가 타임아웃 → 클라이언트 재시도 → 주문 2건
✅ 부수효과 있는 POST엔 멱등키 헤더(`Idempotency-Key`) 수용 — 같은 키 재요청엔 첫 응답 재반환 (Stripe 패턴)
**왜**: 네트워크는 "보냈는데 응답을 못 받은" 상태를 반드시 만든다. 클라이언트는 성공인지 모르면 재시도할 수밖에 없고, 서버가 멱등키 없이는 구분 못 한다. 읽기(GET)·PUT·DELETE는 메서드 자체가 멱등 — POST만 이 장치가 필요.

### 7. 시간·통화·ID 표현 즉흥
❌ `"date": "06/11/26"`, 금액 float, ID로 DB auto-increment 노출
✅ 시각은 ISO 8601 UTC(`2026-06-11T07:10:00Z`), 금액은 최소 단위 정수(원 단위 int) 또는 문자열 decimal, 노출 ID는 의미 없는 식별자 검토(증분 ID는 규모·순서 정보 유출)
**왜**: 표현 규약은 나중에 못 바꾼다(전부 breaking). float 금액은 0.1+0.2 문제를 계약에 박는 것. 처음에 정하는 게 유일한 기회다.

## breaking change 판별표

| 변경 | 판정 |
|---|---|
| 응답에 필드 추가 / 새 엔드포인트 / 선택 파라미터 추가 | ✅ 안전 |
| enum에 새 값 추가 | ⚠️ 준-breaking — 클라이언트가 미지 값 허용하도록 문서에 명시했을 때만 안전 |
| 필드 이름·타입 변경, 필드 제거 | ❌ breaking |
| 필수 파라미터 추가, 검증 강화(되던 요청이 422) | ❌ breaking |
| 에러 code 변경, 상태코드 변경 | ❌ breaking |
| 기본 limit·정렬 순서 변경 | ❌ breaking (조용히 결과가 달라짐 — 가장 악질) |

버저닝 기본값: **URL 메이저(`/v1`) 1개만 유지 + 추가 위주로 진화** — 다중 버전 동시 운영은 1인 프로젝트에서 유지비가 효익을 넘는다(YAGNI). v2는 정말 갈아엎을 때.

## 워크플로우 (API 계약 신설·변경)

1. **리소스 목록 먼저** — 명사 목록과 관계(부모/자식)를 적는다. URL은 그 사상: `/stocks/{code}/candles`. 깊이는 2단까지 — 더 깊으면 최상위 리소스로 승격.
2. **엔드포인트 표 작성** — 메서드·경로·요청·응답·에러를 표로(출력 템플릿). 이 표가 곧 리뷰 대상이자 문서의 씨앗.
3. **변경이라면 판별표 통과** — breaking이면 병행 전략을 표에 함께.
4. **구현 위임** — 표를 dev-fastapi(모델 3종 세트)로 넘긴다. 계약 표 ↔ OpenAPI(/docs)가 일치하는지가 구현 검수 기준.
5. **검증 (피드백 루프)**:
   ```
   python scripts/api_lint.py <openapi.json 또는 라우트 표 .md>   # 규약 위반 기계 검출, exit 0이 통과
   # FastAPI면: 서버 띄우고 /openapi.json 저장 → 위 검사 입력으로
   ```

> **산출물 위치**: API 계약은 OpenAPI 스펙 파일이 정본 — 라우트/스키마 변경 시 그 파일을 **append/Edit**으로 갱신하고(엔드포인트 이력 보존, 통째 덮어쓰기 금지), 버저닝·deprecation 표기를 동반한다. 설계 결과(출력 템플릿)는 대화로 제시하거나 스펙의 description 필드에 남긴다.

❌ "일단 /getCandles로 만들고 형식은 나중에 정리" (나중 = breaking change)
✅ "엔드포인트 표 → 리뷰 → 구현 — 표현 규약은 첫날에"

### 사용자가 권고를 거부하면

- "내부용인데 규약 과해" → 핵심 3개(상태코드 정직·에러 code·limit)만 지키는 경량판 제안. 거부 시 기록(partial) — 내부 API가 외부가 되는 날이 breaking 청구일.
- "그냥 v2로 다 바꿔" → 병행 비용 없이 일괄 전환이 정말 가능한지(클라이언트 전부 동시 배포 가능?) 1회 확인 후 존중.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단이 막힐 때 (확인 요청 4요소)

소비자가 누구인지(내부 전용/외부 공개/미래 클라이언트)와 호환 정책은 사용자만 안다 — 모르면 과설계하거나 breaking을 슬쩍 내보낸다. 묶어서 묻는다:
- **누가**: 사용자(API 소비자 목록·공개 계획·배포 순서 통제권 소유자).
- **언제**: 리소스 설계 단계(워크플로우 1) 또는 변경이 breaking 판별표에서 ❌로 나올 때.
- **어떻게**: "현재 항목 / 추측값 / 근거 / 기대 답변"으로. 예) "이 API를 내부 전용으로 가정해 멱등키를 생략했는데(근거: GET 위주 읽기 전용), 외부/모바일 소비자가 생길 계획이면 지금 넣는 게 쌉니다 — 소비자 범위가 어디까지입니까?"
- **기대값**: 소비자 범위·breaking 승인(병행 vs 일괄)·버전 정책 중 하나. 받으면 확정 설계로, 못 받으면 가장 호환 안전한 가정(추가만·병행 기간 둠·표현 규약은 첫날 확정)으로 진행 + 미확정을 "확인 필요"로 명시.

## 실전 케이스 — Stripe, 10년 넘게 안 깨지는 API (지속 사례)

Stripe는 2011년 이후 멱등키·불투명 커서·code 기반 에러·버전 고정(계정별 API 버전 + 변환 레이어)으로 "클라이언트 코드를 한 번도 강제로 깨뜨리지 않는" 운영을 해왔다(출처: Stripe 엔지니어링 블로그 "APIs as infrastructure: future-proofing Stripe with versioning" 2017). 반면 흔한 반례는 임의 시점의 무예고 필드 제거로 통합 파트너 장애를 내는 사내 API들이다. 교훈: ① 이 스킬의 규약들(멱등키·불투명 커서·code)은 취향이 아니라 **십수년 검증된 호환성 기술** ② "추가만 한다"는 규율 하나가 버전 운영 비용 대부분을 대체한다 ③ 결제처럼 재시도가 위험한 도메인이 멱등키의 출생지다 — 주문·적재가 있는 모든 API에 이식 가능.

## 사용자 환경 적용

- sample-service API(읽기 전용)는 멱등키 불필요(GET뿐) — 커서 페이지네이션과 에러 code가 핵심. 위 작성 예시가 그 초안.
- 외부 공개 계획이 없어도 규약은 지킨다 — Discord 봇·프론트·미래의 자동매매 모듈이 전부 "클라이언트"다.

## 한계

계약 설계만 담당 — 구현·성능·보안은 경계 표의 전문가로. REST가 항상 답은 아니다: 내부 서비스 간 고빈도 호출은 gRPC, 프론트 주도 유연 조회는 GraphQL이 나을 수 있다 — 그 선택 비교는 라우터의 비교 프레임으로(이 스킬은 "HTTP API로 간다" 결정 이후를 맡는다).
