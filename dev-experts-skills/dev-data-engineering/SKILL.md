# dev-data-engineering — 수집·파이프라인 전문가

> 기준: 배치 중심 설계 원칙 (2026-06) · 부패 등급: 느림(연 1회) — 원칙 위주, 도구 종속 최소

## 정체성

*Designing Data-Intensive Applications*(Kleppmann)의 배치 원칙 + 실무 파이프라인 관행. **"파이프라인의 품질은 행복 경로가 아니라 '다시 돌렸을 때'로 측정된다"** — 같은 입력을 두 번 돌려도, 어제 것을 오늘 돌려도, 중간에 죽었다 살아나도 결과가 같아야 한다(멱등성).

핵심 신조: 원본은 버리지 않는다 · 단계는 분리하고 각 단계는 재실행 가능 · 결측은 정책이지 예외가 아니다 · 적재했으면 검증한다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 파이프라인 구조·멱등·백필 | 실행 시각·cron 설정 (→ dev-cron-scheduling) |
| 결측·이상치 정책 설계 | 테이블 설계·인덱스 (→ dev-database-modeling/dev-postgres) |

| 배치 파이프라인 | 실시간 스트림·브로커 (→ dev-messaging-queue) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 비멱등 적재 (재실행 = 중복)
❌ `INSERT INTO ticks VALUES (...)` — 같은 날짜를 두 번 돌리면 2배
✅ 자연키(종목+일자) 기준 `INSERT ... ON CONFLICT DO UPDATE`(upsert) 또는 [DELETE 파티션 → INSERT] 단위 교체
**왜**: 파이프라인은 **반드시** 재실행된다(장애·백필·코드 수정). 재실행이 무서운 파이프라인은 손대지 못하는 파이프라인이 되고, 결국 데이터가 썩는다.

### 2. 추출과 정제의 결합 (원본 미보존)
❌ API 응답을 받자마자 가공해 최종 테이블에만 적재 — 정제 버그 발견 시 원본이 없음
✅ raw 층(받은 그대로: JSON/원시 행 + 수집 시각) → 정제 층(파싱·검증) → 서빙 층. 정제 버그는 raw에서 재처리
**왜**: 정제 로직은 반드시 틀린다(소스 형식 변화·미처 본 적 없는 값). raw가 있으면 버그 수정 = 재처리 1회, 없으면 = 데이터 영구 손실. 저장은 싸고 재수집은 비싸거나 불가능하다(과거 시세는 다시 안 옴).

### 3. 결측을 침묵으로 때우기
❌ 값이 없으면 0/이전 값으로 조용히 채움 — 채운 티가 안 남
✅ 결측 정책을 명시 컬럼으로: NULL 유지 + `quality_flag`(missing/ffill/estimated) 또는 결측 행 별도 기록. 채움은 **서빙 층에서, 흔적 남기고**
**왜**: 0으로 채운 거래량과 진짜 0 거래량은 분석에서 구분 불가 — 침묵 보정은 하류의 모든 분석을 조용히 오염시킨다. "데이터가 없다"도 데이터다.

### 4. 전량 재수집 기본값 (증분 설계 부재)
❌ 매일 전체 종목 × 전체 기간을 다시 받음 — API 한도 소진·실행 시간 폭증
✅ 워터마크(마지막 성공 지점: 일자·커서) 기록 → 그 이후만 수집. 백필은 같은 코드에 기간 인자만 다르게
**왜**: 전량 재수집은 소스 API rate limit과 실행 창(새벽 배치 시간)을 모두 태운다. 단, 소량(수천 행 이하)이면 전량+교체가 오히려 단순 — 행수로 판단(YAGNI).

### 5. 적재 후 무검증 (믿음 기반 파이프라인)
❌ exit 0이면 성공으로 간주 — 0행 적재·반토막 적재도 "성공"
✅ 적재 직후 검증 쿼리: 기대 행수 범위·필수 컬럼 NULL 비율·키 중복·당일 데이터 존재. 위반 시 **시끄럽게 실패**(알림)
**왜**: 파이프라인의 최빈 장애는 "에러 없이 틀린 데이터" — 소스가 빈 응답을 주거나 파서가 조용히 0건을 반환하는 경우. exit code는 프로세스 생존만 증명한다.

### 6. 시간대·거래일 무정책
❌ `datetime.now()`로 "오늘" 판단 — 자정 직후 배치가 어제/오늘을 혼동, 휴장일에 빈 데이터를 결측으로 오인
✅ 거래일 캘린더를 명시 모듈로(휴장일 판단 분리) + 모든 타임스탬프 aware UTC 저장, "데이터 기준일"과 "수집 시각"을 별도 컬럼으로
**왜**: 금융 데이터의 "오늘"은 벽시계가 아니라 거래일이다. dev-python 안티패턴 5(naive datetime)의 파이프라인 버전 — 기준일 혼동은 하루치 데이터가 통째로 어긋나는 버그.

## 정량 기준 (출발점 — 소스·규모가 이긴다)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 재시도 | 3회, 지수 백오프(1s→2s→4s) + 지터 | 일시 장애 대부분 2회 내 해소, 무지터는 동시 재돌진 |
| rate limit 준수 | 소스 문서 한도의 80% 이하로 자율 제한 | 한도 칼치기는 차단 리스크 — "확인 필요: 키움 API 초당 한도" |
| 증분 전환 기준 | 1회 수집 > 1만 행 또는 실행 > 10분이면 증분 설계 | 그 이하는 전량+교체가 단순(안티패턴 4의 YAGNI) |
| 적재 검증 | 행수 하한 + NULL 비율 상한 + 키 중복 0 — 3종 최소 | 안티패턴 5 |
| raw 보존 | 무기한 기본(시세류는 작다) · 대용량만 보존 기간 정책 | 안티패턴 2 |

## 워크플로우 (파이프라인 신설·개편)

1. **소스 계약 파악** — API 한도·페이징·갱신 주기·과거 데이터 제공 범위를 문서로 확인(불명은 "확인 필요"). 이게 설계의 절반.
2. **3층 + 단계 분리 설계** — extract(소스→raw) / transform(raw→정제) / load(정제→서빙) 각각 독립 실행 가능한 함수·모듈로. 정제 로직은 순수 함수로 → dev-tdd ◎ 영역.
3. **멱등 키 결정** — 각 층의 자연키(종목+기준일 등)와 upsert/교체 전략. "이 단계만 다시 돌리면?"을 층마다 자문.
4. **결측·이상치 정책 표 작성** — 케이스(결측·0·음수·휴장일·상폐)별 처리·플래그를 표로 먼저 합의(출력 템플릿 참조).
5. **검증·관측 내장** — 적재 검증 3종 + 실행 결과 1행 로그(시작·끝·행수·결측수). 알림은 dev-bot-building/dev-monitoring 연계.
6. **검증 (피드백 루프)** — 멱등성은 테스트로 증명한다:
   ```
   python scripts/pipeline_check.py <파이프라인.py>   # 구조 냄새 기계 검출, exit 0이 통과
   pytest -x -q                                       # 정제 순수 함수 단위 테스트(dev-tdd)
   # 멱등성 스모크: 같은 기준일 2회 실행 → 행수 동일 확인 쿼리
   ```

### 판단이 막힐 때 (확인 요청 4요소)

소스 계약(한도·과거 범위·재수집 가능성)이나 결측 정책은 사용자만 아는 정보다 — 모르는 채 설계하면 멱등성·검증 임계가 허구가 된다. 묶어서 묻는다:
- **누가**: 사용자(소스 API 문서·운영 정책 소유자) 또는 dev-postgres(적재 스키마가 선행 미정일 때).
- **언제**: 소스 계약 파악 단계(워크플로우 1) — 특히 rate limit·과거 데이터 제공 범위·재수집 가능 여부가 불명일 때.
- **어떻게**: "현재 항목 / 추측값 / 근거 / 기대 답변"으로. 예) "키움 초당 한도를 5건으로 가정해 백오프를 잡았는데(근거: 일반 REST 관행), 문서값이 다르면 그대로 — 실제 한도는 얼마입니까?"
- **기대값**: 한도 숫자·과거 범위·결측 처리 승인 중 하나. 받으면 확정값으로, 못 받으면 가장 보수적 가정(한도 낮게·raw 무조건 보존·결측은 NULL+flag)으로 진행 + 가정과 "확인 필요"를 출력 템플릿에 명시.

## 실전 케이스 — Knight Capital의 데이터 판박이, 그리고 "조용한 0건" (2012/일반)

Knight Capital(라우터 실전 케이스)의 본질은 "배포 검증 부재"였지만, 데이터 파이프라인의 등가 사고는 **조용한 부분 적재**다. 공개 포스트모템이 흔한 영역은 아니라(사내 사고로 묻힘) 대신 구조를 박는다: 소스 API가 200 OK + 빈 배열을 주는 날(점검·형식 변경), 무검증 파이프라인은 "성공"하고, 하류 분석은 며칠 뒤 "왜 이 구간 데이터가 없지"로 발견한다 — 그때는 워터마크가 이미 전진해 자동 재수집도 안 된다. 이 스킬의 적재 검증 3종 + 워터마크는 성공 시에만 전진 규칙이 정확히 이 시나리오의 방어선이다. (실명 사례 확보 시 교체 — 확인 필요)

## 사용자 환경 적용 (sample-service 직결)

- 기존 collector(APScheduler+키움)의 불만이 이 재설계의 출발점 — 위 작성 예시가 그 골격이다. 기존 DB 스키마와의 호환은 raw 층 신설 + 기존 테이블을 서빙 층으로 두는 점진 전환이 안전.
- 키움 API는 세션·토큰 만료가 있다 — 추출 층에서 재인증을 재시도와 분리 처리(401은 백오프가 아니라 토큰 갱신).
- 홈서버(ubuntu-01) 배치 실행: venv 절대경로(dev-python 규칙) + 실행 로그 1행을 Discord 봇 알림과 연계(기존 monitoring-discord-bot 활용).
