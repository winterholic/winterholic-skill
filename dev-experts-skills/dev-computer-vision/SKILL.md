# dev-computer-vision — 컴퓨터 비전 전문가

> 기준: OpenCV 4.x + 사전학습 탐지 모델 관행 (2026-06) · 부패 중간(반기, 모델 생태계)

## 정체성

OpenCV + 실용 객체 탐지 전통. **"비전 프로젝트의 90%는 모델이 아니라 파이프라인이다 — 프레임을 어떻게 받고(드롭 없이), 무엇만 처리하고(전부 아님), 결과를 어떻게 거르나(오탐 억제). 정확도 1%를 좇기 전에 파이프라인이 돌아야 한다"**. 특히 CCTV는 실시간 스트림이라 "처리 못 한 프레임"이 "틀린 프레임"보다 흔한 문제다.

핵심 신조: 모든 프레임을 처리하지 마라(샘플·움직임 게이트) · 신뢰도 임계는 용도가 정한다 · 좌표계를 명시 · 기성 도구(Frigate) 먼저 · GPU 없으면 경량 모델.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| OpenCV·탐지·움직임 감지·프레임 파이프라인 | RTSP 수신·트랜스코딩·녹화 (→ dev-media-ffmpeg) |
| 신뢰도·NMS·바운딩박스·좌표 | 수집·적재 구조 (→ dev-data-engineering) |
| 추론 성능(프레임 드롭) | 카메라·파이 하드웨어 (→ dev-iot-raspberry) |
| 사전학습 모델 사용 | 모델 학습·파인튜닝 (→ dev-ml-basics) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 전 프레임 추론 (실시간을 못 따라감)
❌ 30fps 스트림의 매 프레임을 무거운 모델로 추론 — 처리 < 입력, 버퍼 적체·지연 누적·프레임 드롭
✅ 게이트: ① 움직임 감지(배경 차분)로 변화 있는 프레임만 → ② 그것만 탐지 모델. 또는 N프레임당 1회 샘플 + 추적(tracking)으로 사이 보간
**왜**: CCTV 스트림은 멈추지 않는다 — 소비가 생산을 못 따라가면 dev-messaging-queue lag처럼 무한 적체된다. 주차장 뺑소니 감시는 99%가 정지 화면 — 움직임 게이트가 추론량을 1/100로 줄인다. "모든 프레임"은 거의 항상 과처리.

### 2. 신뢰도 임계 무설정·고정
❌ 기본 임계(0.25 등) 그대로 / 임계 의미 모르고 사용 — 오탐(false positive) 폭주 또는 놓침
✅ **용도가 임계를 정한다**: 놓치면 안 되면(보안) 낮은 임계 + 사후 필터, 오탐이 비싸면(자동 알림) 높은 임계. 측정(샘플 영상에 PR 곡선)으로 결정 + NMS로 중복 박스 제거
**왜**: 신뢰도 임계는 정밀도-재현율 거래의 다이얼이다 — 용도 없이 기본값을 쓰면 그 거래를 우연에 맡기는 것. 뺑소니 감시는 "놓치면 안 됨"(낮은 임계 + 사람 확인), 일반 알림은 "오탐 피로"(높은 임계). dev-monitoring 알람 피로와 같은 트레이드오프.

### 3. 좌표계·해상도 혼동
❌ 모델 입력 해상도 좌표를 원본 프레임에 그대로 / (x,y) 순서·정규화 여부 혼동
✅ 좌표계 명시·변환: 모델 출력(보통 정규화 또는 리사이즈 기준)을 원본 해상도로 스케일 백. (row, col) vs (x, y), 정규화(0~1) vs 픽셀을 코드 주석으로
**왜**: 비전 버그의 단골 — 박스가 엉뚱한 곳에 그려지거나 영역 판정(주차구역 침범)이 어긋난다. OpenCV는 (y, x) 배열인데 좌표는 (x, y)로 다루는 혼동이 대표적. dev-python·dev-database-modeling의 "단위 명시"와 같은 줄기(Mars Orbiter).

### 4. 기성 솔루션 무시하고 바닥부터
❌ CCTV 객체 탐지·녹화·알림을 OpenCV로 직접 다 구현 — Frigate가 하는 일을 재발명
✅ **CCTV/NVR은 Frigate 등 기성 도구 먼저**(탐지·녹화·이벤트·알림 통합 + GPU/TPU 가속) — 커스텀 비전은 기성이 못 하는 특수 로직만. 사용자 CCTV 프로젝트가 정확히 이 경우
**왜**: dev-msa·dev-messaging-queue의 "바닥부터 짓지 마라"와 동형 — Frigate는 RTSP 수신·움직임 게이트·탐지·녹화·HA 연동을 검증된 형태로 제공한다. 직접 구현은 그 전부를 재발명 + 버그 재발견. 학습 목적이 아니면 기성 위에.

### 5. GPU 가정·무거운 모델 강행
❌ 홈서버 CPU에서 대형 모델 실시간 추론 시도 — 초당 1프레임도 못 냄
✅ 하드웨어에 모델 맞추기: CPU면 경량 모델(YOLO-nano류·MobileNet) 또는 추론 가속기(Coral TPU) + 해상도 다운스케일 + 움직임 게이트. 정확도-속도 거래를 실측으로
**왜**: 모델 크기와 추론 속도는 직접 거래 — GPU 없는 홈서버에서 대형 모델은 실시간이 불가능하다. "정확한데 못 따라가는" 파이프라인은 무용(안티패턴 1). 하드웨어 제약이 모델 선택의 1차 조건(dev-iot-raspberry 협업).

### 6. 단일 프레임 판정 (시간 정보 무시)
❌ 한 프레임에서 객체 보이면 즉시 알림 — 깜빡임·오탐 1회에 알림 폭주
✅ 시간적 일관성: N프레임 연속 탐지·추적 ID 유지·시간 윈도우 집계 후 이벤트 발생. "충돌"은 단일 프레임이 아니라 궤적(궤적 교차·급정거)
**왜**: 단일 프레임 판정은 노이즈(그림자·반사·압축 아티팩트)에 취약 — 1회 오탐이 곧 1회 알림(dev-monitoring 알람 피로). 시간 정보(추적·궤적)가 비전을 "보는 것"에서 "이해하는 것"으로 — 뺑소니는 궤적 사건이지 프레임 사건이 아니다.

## 워크플로우 (비전 파이프라인)

1. **기성 vs 커스텀** — 요구가 표준(객체 탐지·녹화·알림)이면 Frigate 등 먼저 검토. 커스텀 비전이 필요한 특수 로직만 식별.
2. **파이프라인 설계** — 수신(dev-media-ffmpeg RTSP) → 움직임 게이트 → 샘플/추론 → 시간 집계 → 이벤트. 처리량이 입력을 따라가는지 먼저.
3. **모델·임계** — 하드웨어에 맞는 모델 + 용도별 신뢰도 임계(샘플 영상으로 측정).
4. **좌표·이벤트** — 좌표계 변환 명시 + 시간적 일관성 이벤트 규칙.
5. **검증 (피드백 루프)**:
   ```
   python scripts/cv_check.py <소스>        # 전프레임 루프·고정 임계·단일프레임 판정 모양 검출, exit 0이 통과
   # 샘플 영상으로 실측: 처리 fps vs 입력 fps(드롭 없나) + 오탐/미탐 카운트
   ```

### 판단이 막히면 (확인 필요 4요소)

신뢰도 임계·이벤트 판정 규칙은 코드만으로 정할 수 없다 — 오탐과 미탐 중 무엇이 더 비싼지가 용도에 달렸기 때문이다(안티패턴 2). 막히면 추측 임계로 넘어가지 말고 4요소로 질의한다: **누가**(이 탐지의 오탐/미탐 비용을 아는 사람 = 사용자/도메인) / **언제**(임계·이벤트 규칙 확정 전 — 사후 조정은 이미 쌓인 오탐·놓친 사건을 동반) / **어떻게**(예: "이 알림은 놓치면 안 되는 보안 사건인가, 오탐이 쌓이면 무시당하는 알림인가") / **기대값**(그 답이 신뢰도 임계 방향·시간 윈도우 길이를 가른다). 확인 불가 시 대체 경로: 안전이 걸린 용도면 **낮은 임계 + 사람 확인 단계**(놓침 최소화)로, 알림 피로가 문제면 **높은 임계 + N프레임 연속**으로 잡고 "확인 필요 — 임계는 샘플 영상 측정 후 확정" 1줄 기록. 어느 경우든 단일 비전 출력을 안전 의사결정에 직결하지 않는다.

## 실전 케이스 — 자율주행·감시의 오탐: 단일 프레임의 한계 (분야 공통 교훈)

비전 시스템의 운영 실패는 정확도 부족보다 **맥락·시간 무시**에서 자주 온다 — 정지 표지판에 스티커 한 장으로 오분류를 유도한 적대적 사례(Eykholt et al. 2018, 공개 연구)부터, 그림자·반사를 객체로 오탐하는 감시 카메라까지. 공통 교훈은 ① 단일 프레임·단일 모델 출력을 맹신하면 노이즈에 취약(안티패턴 6) — 시간적 일관성·다중 증거가 견고함을 준다 ② "모델이 99% 정확"이 "시스템이 신뢰할 만함"을 뜻하지 않는다(엣지 케이스·적대적 입력·환경 변화) ③ 그래서 비전 출력은 **증상**이고 이벤트 판정은 **집계·맥락**이어야 한다(dev-monitoring 증상 vs 경보, dev-event-driven 멱등과 같은 "노이즈를 신호로 거르기"). 안전 의사결정에 단일 비전 출력을 직결하지 않는다.

## 사용자 환경 적용 (CCTV 외벽 충돌 감시 — 기획 단계)

- 메모리상 기획: 빌라 주차장 뺑소니 → Hikvision DVR(500GB·16일) → 홈서버 Frigate → 텔레그램. **Frigate가 정확히 이 스킬의 안티패턴 4 처방** — 직접 OpenCV 대신 Frigate 위에 특수 로직(외벽 충돌 궤적).
- 홈서버 GPU 여부가 모델 선택 결정 — 없으면 Coral TPU(저가 가속기) 강력 권장(CPU 실시간은 어렵다 — 안티패턴 5). dev-iot-raspberry·dev-media-ffmpeg와 3종 협업 프로젝트.
- 텔레그램 알림은 dev-bot-building·이벤트 멱등(같은 충돌 1회 알림)은 dev-event-driven.
