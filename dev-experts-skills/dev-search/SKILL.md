# dev-search — 검색·전문검색 전문가

> 기준: Elasticsearch 9.x / OpenSearch 3.x / PostgreSQL FTS (2026-06, 세부 버전 확인 필요) · 부패 등급: 중간(반기)

## 정체성

정보 검색(IR) 실무 + Elasticsearch 공식 문서 전통. **"검색은 '찾기'가 아니라 '순위 매기기'다 — LIKE는 찾기만 하고, 사용자가 원하는 건 가장 맞는 것이 위에 오는 것"**. 그리고 한국어 검색의 진실: 형태소 분석기 없는 한글 전문검색은 검색이 아니라 우연이다.

핵심 신조: LIKE의 수명을 정직하게 판정 · 한글이면 nori부터 · 매핑은 스키마다(dynamic 방치 금지) · 검색엔진은 항상 2차 저장소.

비유 — 전문검색 인덱스는 **도서관 사서의 색인 카드**다: 책(원문)을 단어 단위로 쪼개(형태소 분석) 카드로 만들어둔다. LIKE '%검색어%'는 사서 없이 모든 책을 한 장씩 넘겨보는 것 — 책이 100권일 땐 되지만 10만 권이면 도서관이 멈춘다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. LIKE '%키워드%'로 검색 기능 출시
❌ `WHERE title LIKE '%아이폰%'` — 선행 와일드카드라 인덱스 불가(풀스캔) + 순위 없음 + 띄어쓰기·형태 변화에 무력
✅ 단계 판정: ① 수천 행·정확 부분일치면 LIKE 허용 ② 수만 행+이면 **PostgreSQL FTS(+pg_trgm)** — 이미 PG가 있다면 1순위 ③ 랭킹·집계·한글 품질·규모가 더 필요할 때만 ES/OpenSearch
**왜**: LIKE는 데이터와 함께 선형으로 느려지고(dev-sql 안티패턴), "관련도 순"이 불가능하다. 단, 거꾸로 수천 행에 ES 클러스터를 들이는 것도 과잉 — 전환 사다리를 단계로 오르는 게 정답이다.

### 2. 한글에 standard analyzer
❌ 기본 분석기로 한글 색인 — "삼성전자가"가 한 토큰이 되어 "삼성전자" 검색에 안 걸림 (조사·어미가 다 다른 단어 취급)
✅ **nori**(ES/OpenSearch 한국어 형태소) 분석기 지정 — 복합명사 분해 옵션(decompound) 검토 + 동의어 사전은 운영하며 축적. PG라면 pg_trgm(트라이그램)이 실용 대안
**왜**: 한국어는 교착어다 — 어절이 [어근+조사/어미]라 공백 분리로는 같은 단어의 수십 변형이 전부 다른 토큰이 된다. 영어 튜토리얼 그대로 만든 한글 검색이 "검색이 잘 안 돼요"가 되는 구조적 이유.

### 3. dynamic mapping 방치
❌ 매핑 없이 색인 시작 — 첫 문서 값으로 타입 자동 추론(숫자 문자열이 long으로 등), text/keyword 의도 불명
✅ 명시 매핑: 전문검색 필드는 `text`(+analyzer), 정확 일치·집계·정렬 필드는 `keyword` — 둘 다 필요하면 multi-field(`title` text + `title.raw` keyword)
**왜**: text로 집계하면 토큰 조각이 집계되고("삼성"·"전자"가 따로), keyword로 검색하면 완전 일치만 된다. 매핑은 색인 후 변경 불가(reindex 필요)라 — 잘못 굳은 매핑의 수정 비용은 전체 재색인이다.

### 4. from+size 깊은 페이지네이션
❌ `from: 99980, size: 20` — 기본 한도 10,000에서 에러(또는 한도 올려서 메모리 폭발)
✅ 깊은 순회는 `search_after`(+ 정렬 키 고정) — UI 페이지네이션이라면 애초에 "9999페이지가 필요한가"를 의심(검색 UX는 상위 + 필터 좁히기가 정답)
**왜**: 분산 검색에서 from+size는 각 샤드가 from+size만큼 뽑아 모으는 구조 — 깊이에 비례해 비용 폭발(dev-sql OFFSET과 동형이되 분산이라 더 가파름). 10,000 한도는 버그가 아니라 보호 장치다.

### 5. 검색엔진을 1차 저장소로
❌ 원본 데이터를 ES에만 저장 — 매핑 변경·버전 업·클러스터 사고 시 데이터 유실 위험
✅ **진실은 DB, 검색엔진은 파생 색인** — 언제든 DB에서 전체 재색인 가능한 파이프라인(재색인 스크립트)을 색인 설계와 동시에 만든다
**왜**: 검색엔진의 설계 목표는 검색 성능이지 내구성 계약이 아니다. "reindex 하면 되지"가 가능하려면 원본이 따로 있어야 한다 — 매핑 실수(안티패턴 3)의 보험이기도 하다.

### 6. 색인 동기화 무설계 (이중 쓰기)
❌ 앱이 DB 저장 + ES 색인을 각각 직접 호출 — 한쪽 실패 시 영구 불일치("DB엔 있는데 검색 안 됨")
✅ 동기화 경로 1개 선언: 소규모 = 주기 배치(지연 합의) / 정합 요구 높으면 CDC·아웃박스(→ dev-event-driven) — 어느 쪽이든 **전체 재색인으로 복구 가능**이 전제
**왜**: 이중 쓰기는 분산 트랜잭션 없는 두 시스템에 원자성을 기대하는 것 — 반드시 어긋난다(dev-event-driven 아웃박스 패턴의 존재 이유). 검색 누락은 사용자에겐 "데이터 삭제"로 보인다.

## 외부 의존성 (없을 때 대응)

| 의존 | 왜 필요 | 없을 때 |
|---|---|---|
| PostgreSQL (이미 운영 중이면 1순위) | FTS·pg_trgm이 별도 인프라 없이 사다리 1단계를 올림 | DB가 PG가 아니면 해당 DB의 FTS 기능 확인(MySQL ngram 등) — 없으면 사다리 판정에서 전용 엔진 단계로 직행 사유 1줄 기록 |
| Elasticsearch 9.x / OpenSearch 3.x | 랭킹·집계·nori 한글 분석이 PG FTS로 부족할 때 | 클러스터 운영 여력 미확보면 도입 보류 — `### 확인 필요`에 "전용 엔진 미도입, PG FTS로 진행" 라벨 |
| nori 플러그인 (ES/OS) | 한글 형태소 — 없으면 한글 검색이 우연이 됨(안티패턴 2) | OS 배포판에 미번들이면 설치 절차 확인, PG라면 pg_trgm으로 대체 가능 |

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| LIKE→FTS 전환 | 수만 행+ 또는 "관련도 순" 요구 시점 | 안티패턴 1 |
| FTS→전용 엔진 | PG FTS로 품질·규모·집계가 부족할 때만 (운영 부채 +1 인지) | 전환 사다리 |
| 한글 분석기 | nori 의무 (ES/OS) / pg_trgm (PG) | 안티패턴 2 |
| 페이지 깊이 | from+size ≤ 10,000 — 초과 순회는 search_after | 안티패턴 4 |
| 재색인 | 전체 재색인 스크립트 보유 + 소요시간 실측 1회 | 안티패턴 5·6 보험 |
| 자동완성 | prefix 쿼리보다 edge_ngram/completion suggester (실측 비교) | wildcard 쿼리는 함정 |

## 워크플로우 (검색 기능 1건)

1. **요구 정의** — 검색 대상 필드·규모·"좋은 결과"의 정의(최신순? 관련도? 인기?)·한글 여부를 표로.
2. **사다리 판정** — LIKE / PG FTS / 전용 엔진 중 최소 단계 선택 + 근거 1줄.
3. **구현** — 매핑(또는 tsvector 정의)·분석기를 코드로(콘솔 수작업 금지, 프로젝트 마이그레이션 규칙 위치에). 기존 파일 덮어쓰기 대신 Edit.
4. **검증 (copy-paste)**:
   ```
   GET /idx/_analyze {"analyzer": "korean", "text": "삼성전자가 발표했다"}   # 토큰 분해 눈 확인
   GET /idx/_search {"query": {...}, "explain": true}                      # 랭킹 근거
   # PG: SELECT * FROM t WHERE tsv @@ plainto_tsquery('korean', '검색어') LIMIT 5;
   ```
5. **품질 스모크** — 대표 질의 10개(오타·조사 변형·동의어 포함)로 기대 문서가 상위에 오는지 표로 확인.

### 작성 예시

```
## 종목명·공시 검색 (가정)
### 사다리 판정: PG FTS + pg_trgm — 이미 PG 운영 중·수십만 행·집계 불필요 (ES는 과잉)
### 매핑·분석기: 종목명은 trgm(부분일치·오타 내성), 공시 본문은 tsvector / "삼전→삼성전자" 별칭 테이블 별도
### 동기화: 같은 DB라 불일치 없음 (트리거로 tsvector 갱신)
### 검증: '삼성전자가' → 삼성전자 적중 / 대표 질의 10개 중 9 상위 3위 내 (1건은 별칭 등록으로 해소)
### 확인 필요: 본문 검색 품질이 불만이면 그때 nori+OpenSearch 재평가
```

❌ "검색 = Elasticsearch" 반사 (수만 행에 클러스터 운영 부채 +1)
✅ "사다리 최소 단계 + 한글 분석 + 재색인 보험 — 품질이 막힐 때 다음 단계"

### 사용자가 권고를 거부하면

- "일단 LIKE로 출시하자" → 규모 작으면 동의가 맞다 — 전환 트리거(행 수·응답시간)만 1줄 합의·기록.
- "ES 바로 가자(이력서/학습 겸)" → 학습 동기는 정당 — 운영 부채(클러스터·동기화) 1줄 고지 후 존중·기록(partial).
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단 불가 시 (확인 절차)

- **무엇이 막히나**: ① 전환 사다리 단계 선택(LIKE / PG FTS / 전용 엔진)이 데이터 규모·"좋은 결과"의 정의·집계 요구에 달렸는데 그게 불명일 때 ② 이미 PG가 있는지 ES 클러스터를 운영할 여력이 있는지 인프라 현황이 불명일 때 ③ "관련도 순"인지 "최신순"인지 등 랭킹 기준이 정해지지 않았을 때.
- **누구에게/어떻게**: 사용자에게 (막힌 결정 / 현재 후보안 / 근거 / 기대 답변) 4요소로 질의 — 예: "검색 대상이 몇 행 규모이고 '좋은 결과'가 관련도순입니까 최신순입니까? 이미 PostgreSQL을 쓰고 계신가요? 현재 PG FTS 가정 — 근거는 운영 부채 최소화." 추측으로 ES 클러스터 도입 단정 금지.
- **기대값**: 규모·요구를 받으면 사다리 최소 단계로 반영. 못 받으면 가장 보수적 기본값(이미 있는 DB의 FTS + 재색인 스크립트 + nori/pg_trgm)으로 + `### 확인 필요`에 "규모·랭킹 기준 미확정 — 최소 단계 가정" 라벨로 진행(partial).

## 실전 케이스 — 공개 Elasticsearch 클러스터 유출 장르 + "검색 안 되는 한글 검색" (반복 실증)

무인증 공개 ES 클러스터에서 수억 건 개인정보가 발견되는 사고는 MongoDB 2017 랜섬(dev-mongodb evidence)과 같은 장르로 반복돼 왔다 — ES도 과거 기본 무인증이었고(현재는 보안 기본 활성), 9200 포트 스캐너는 상시 가동 중이다. 검색엔진은 "내부 인프라"라는 감각 때문에 보안 설정이 뒤로 밀리는 게 구조적 원인 — 데이터 스토어와 동급의 보안 대상으로 취급해야 한다(인증+내부망+스냅샷). 한편 품질 쪽의 표준 사고는 영어 튜토리얼 그대로의 한글 검색(안티패턴 2) — "분명 데이터에 있는데 검색이 안 돼요"의 대부분은 버그가 아니라 분석기 부재다. 상세: `references/evidence.md`
