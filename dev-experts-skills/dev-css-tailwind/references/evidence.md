# dev-css-tailwind evidence — 실증 사례

## 1. 프로덕션 purge 증발 — "로컬은 되는데 배포만 깨져요" (생태계 반복 실증)

- **무슨 일**: Tailwind GitHub 이슈·Discussions·스택오버플로에 수년간 최다 반복되는 사고 유형. dev에서 보이던 스타일이 prod 빌드에서 사라짐. 진단 끝에 `text-${color}-500` 식 동적 조립 또는 스캔 범위 밖 소스(모노레포 패키지·DB 저장 클래스)로 귀결.
- **메커니즘**: Tailwind 빌드는 소스 파일을 **정규식 수준 텍스트 스캔**해 발견된 완전한 클래스 문자열만 CSS로 생성. 런타임 평가가 없으므로 조립식 클래스는 존재를 알 수 없다.
- **방어 3종**: ① 완전 문자열 매핑 테이블 ② 외부 유래 클래스는 `@source inline(...)` (v4) / safelist로 명시 ③ CI에서 prod 빌드 스모크 테스트(핵심 화면 스크린샷 비교).
- **이 스킬과의 연결**: 안티패턴 1·2. v4 자동 감지는 "파일 누락"만 해결 — 동적 조립은 구조적으로 영구 함정.

## 2. @apply — 제작자의 공개 후회 (설계 의도 실증)

- **무슨 일**: Tailwind 창시자 Adam Wathan이 공개적으로 "@apply는 존재하지 않았어야 할 기능 / 유틸리티 회의론자를 달래려 넣었고 후회한다"고 반복 발언(트위터·팟캐스트). 공식 문서도 "컴포넌트 추출이 우선, @apply는 최후"로 안내.
- **남용의 결말**: 유틸리티로 시작한 코드베이스가 `.card`, `.btn-primary` 시맨틱 클래스 층을 다시 쌓아 — 클래스 명명 고민 부활 + 스타일 출처 이원화 + Tailwind 업그레이드 시 @apply 블록이 추가 마이그레이션 비용.
- **이 스킬과의 연결**: 안티패턴 3. 반복의 올바른 해소 단위는 CSS 클래스가 아니라 **컴포넌트**(React/Vue) — 마크업과 스타일이 함께 재사용된다.

## 3. 다크모드 반쪽 적용 — "다크모드에서 안 보이는 버튼" (반복 실증)

- **무슨 일**: `dark:` variant를 일부 요소에만 적용하고 출시 → 다크 배경 위 다크 텍스트, 흰 카드 위 흰 아이콘 등 **조합 사각지대**에서 콘텐츠 비가시. 사용자 제보로만 발견되는 부류(개발자는 라이트 모드로 작업하니까).
- **방어**: ① 색을 직접 쓰지 않고 **시맨틱 토큰 쌍**으로(`--color-surface`/`--color-on-surface`를 @theme에서 라이트·다크 정의 — 요소는 토큰만 참조) ② 출시 전 다크모드 강제 순회(`document.documentElement.classList.add('dark')` 콘솔 1줄) ③ 스크린샷 테스트를 두 모드로.
- **이 스킬과의 연결**: 정량 기준 "절반 다크모드는 안 한 것보다 나쁨" — 모드가 늘면 검증 매트릭스도 2배라는 비용 인식이 도입 결정의 일부다.

> 출처: Tailwind 공식 문서·GitHub Discussions · Adam Wathan 공개 발언 · WCAG 2.x. 2026-06, Tailwind 4.3 기준.
