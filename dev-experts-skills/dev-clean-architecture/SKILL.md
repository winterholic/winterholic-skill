# dev-clean-architecture — 레이어·의존 방향 전문가

> 기준: Martin *Clean Architecture*(2017) + 헥사고날(Cockburn) + **비판 동비중** — 방법론, 부패 느림(연 1회)

## 정체성

밥 마틴의 의존성 규칙 + 그 비용에 대한 정직한 회계. **"이 아키텍처의 본체는 동심원 그림이 아니라 한 문장이다: 의존성은 안쪽(정책)으로만 향한다 — 나머지(레이어 4개·이름들)는 그 문장의 한 가지 구현일 뿐이고, 종종 과한 구현이다"**. 이 스킬은 규칙의 적용만큼 **어디까지만 적용할지**를 판단한다.

핵심 신조: 지킬 것은 방향이지 층수가 아니다 · 추상화는 변할 것 앞에만 · 프레임워크 독립은 정도 문제(0/1 아님) · 레이어보다 테스트 가능성이 목적.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 의존 방향·레이어 수·포트 설계 | 도메인 개념·불변식 (→ dev-ddd) |
| 프레임워크 결합도 판단 | 배포 단위 분리 (→ dev-msa) |
| 추상화 비용·생략 판단 | 인터페이스·패턴 수준 (→ dev-design-patterns) |
| 테스트 가능 구조 만들기 | 테스트 작성 자체 (→ dev-testing) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 교과서 4층 의무 복제 (의식으로서의 클린)
❌ CRUD 앱에 Entities/UseCases/InterfaceAdapters/Frameworks + 요청 하나에 DTO 변환 4회
✅ 층수는 변형 압력에 비례: 소규모 기본형은 **2층(도메인 / 그 외)** — "계산·정책은 프레임워크 import 없는 모듈에, 나머지는 자유". 층은 고통이 증명할 때 추가
**왜**: 레이어 1층 = 변환·보일러플레이트 1겹. 동심원 그림은 처방전이 아니라 의존 규칙의 삽화다 — 마틴 본인도 "네 개여야 한다는 법은 없다"고 썼다(원전). 비용을 내는데 지키는 정책이 없으면 의식이다.

### 2. 의존 방향 역행 (도메인이 프레임워크를 안다)
❌ 도메인 계산 함수가 `from fastapi import ...`·ORM 모델·HTTP 상태코드를 참조
✅ 안쪽(정책·계산)은 표준 라이브러리만 — 웹·DB·외부 API는 바깥에서 호출하며 도메인 타입으로 변환해 전달
**왜**: 이것이 지켜야 할 유일한 규칙이다. 도메인이 프레임워크를 알면 ① 테스트가 프레임워크 기동을 요구하고 ② 프레임워크 업그레이드가 정책 코드를 건드리며 ③ 로직 재사용(CLI·배치에서 같은 계산)이 막힌다. dev-fastapi "엔드포인트는 얇게"와 같은 줄기.

### 3. 모든 것에 포트·인터페이스 (DIP 만능)
❌ 구현체 1개뿐인 인터페이스 전부(`IUserRepository`+`UserRepository` 쌍 양산)
✅ 포트(추상)는 **교체가 실재하는 경계**만: 외부 시스템(DB·API·시계·랜덤 — 테스트 더블이 곧 두 번째 구현), 그리고 변형이 이미 2개+인 곳. 내부 호출은 그냥 함수
**왜**: dev-design-patterns의 "구현체 1개 인터페이스 = 가짜 유연성"과 동일 — DIP의 목적(안정 정책이 불안정 상세에 의존 않기)이 없는 곳의 인터페이스는 점프 한 번 늘린 간접일 뿐이다. 파이썬은 덕 타이핑이라 형식 인터페이스 없이도 더블 주입이 된다 — Protocol은 타입 검사가 필요할 때만.

### 4. 추상화가 새는 줄 모르기 (leaky abstraction)
❌ "DB 독립" 리포지토리인데 시그니처에 SQLAlchemy 세션·쿼리 객체가 노출 / "스토리지 독립"인데 S3 예외가 도메인까지 전파
✅ 포트의 시그니처·예외·반환 타입은 **도메인 어휘로만** — 어댑터가 외부 타입·예외를 번역(dev-ddd ACL과 동일). 번역 안 할 거면 추상화를 걷어내고 정직하게 결합
**왜**: 새는 추상화는 최악의 조합 — 독립의 비용(간접)은 내는데 효익(교체 가능)은 없다. "이 포트의 구현을 바꾸면 호출자가 한 줄이라도 변하는가"가 검사 질문.

### 5. "언젠가 DB를 바꿀지 모르니까" (가상 요구사항)
❌ 일어나지 않을 교체(PostgreSQL→?)를 위해 ORM 위에 자체 추상층
✅ 교체 시나리오를 실명으로: 시계·랜덤(테스트마다 교체 — 실재), 외부 API(장애 폴백 — 가능), DB 엔진(거의 안 일어남 — 보류). 실재하는 것만 포트로
**왜**: DB 교체 대비 추상층은 비용이 확정이고 효익이 가상이다 — 게다가 진짜 교체 때는 그 추상층이 막상 안 맞는다(쿼리 의미론 차이는 인터페이스로 안 가려진다). 추상화할 가치가 있는 경계의 1순위는 화려한 DB가 아니라 **시계**다(테스트가 매일 증명).

## 소규모 기본형 (2층 + 어댑터)

```
src/
├── domain/            # 안쪽: 계산·정책·불변식 - 표준 라이브러리만 import
│   ├── models.py      #   Tick, TradingDay (dev-ddd 어휘)
│   └── rules.py       #   normalize, validate - 순수 함수 (dev-tdd 최적 영역)
├── adapters/          # 바깥: 세상과의 접점 - 도메인을 import한다 (역방향 금지)
│   ├── kiwoom.py      #   외부 API → 도메인 타입 변환 (ACL)
│   ├── repo.py        #   DB 접근
│   └── api.py         #   FastAPI 라우터 (얇게)
└── main.py            # 조립 지점 - 여기서만 전부를 안다 (DI)
```

검증 가능한 한 줄 규칙: **domain/은 adapters/를 import하지 않는다** — 이것만 기계로 지키면(아래 스크립트) 핵심은 산 것이다.

## 워크플로우 (구조 설계·재배치)

1. **정책 식별** — "프레임워크가 다 사라져도 남아야 하는 코드"를 나열(계산·검증·전이 규칙). 그것이 domain/ 입주자.
2. **경계 표 작성** — 외부 접점(DB·API·시계...)마다 [포트로 추상 / 정직하게 결합] 판정 + 이유(교체 시나리오 실명).
3. **배치·조립** — 기본형 구조로. 조립(누가 무엇을 받나)은 main/lifespan 한 곳에(dev-design-patterns DI와 합류).
4. **검증 (피드백 루프)**:
   ```
   python scripts/dependency_direction.py src/ --domain domain   # 역행 import 검출, exit 0이 통과
   pytest tests/domain -x -q     # domain 테스트가 프레임워크 없이 도는가 - 구조의 산 증거
   ```

## 실전 케이스 — 의존 방향이 만든 차이: SQLite의 테스트 자산 (지속 사례)

SQLite는 코어(정책)가 OS·환경 접점(VFS — 가상 파일시스템 포트) 뒤에 격리된 구조 덕에, VFS를 더블로 교체해 **크래시 시뮬레이션·I/O 장애 주입을 포함한 수억 건 테스트**를 돌린다(출처: sqlite.org "How SQLite Is Tested" — 100% 분기 커버리지, 장애 주입 테스트 공식 문서). 교훈: ① 포트(VFS)는 "OS를 바꿀지 몰라서"가 아니라 **테스트가 매일 쓰는 두 번째 구현**이라서 존재한다 — 안티패턴 5의 검사 질문("교체가 실재하는가")의 모범 답안 ② 의존 역전의 실효익은 그림이 아니라 "프레임워크 없이 도는 테스트"라는 측정 가능한 형태로 온다 — 워크플로우 4의 검증이 그것.

## 사용자 환경 적용

- collector 재설계(dev-data-engineering 골격)에 이 구조를 입히면: extract/transform/load 중 **transform만 domain**이고 나머지는 어댑터 — 위 작성 예시가 그 판이다. 기존 코드에서 순수 함수 추출(dev-refactoring)이 이행 경로.

## 한계

구조는 수단이다 — 도메인이 단순하면(스크립트·글루) 이 스킬 전체가 과하다(파일 하나가 정답인 코드가 있다). "프레임워크 독립"은 Next.js 같은 프레임워크-동형 앱에선 환상에 가깝다 — 그 경우 독립시킬 가치가 있는 것(핵심 계산)만 떼어내는 부분 적용이 정직하다. 레이어가 성능 비용(변환·간접)이 되는 극단(핫패스)은 dev-performance 측정과 함께 예외 결정.
