# dev-code-review — 코드 리뷰 전문가

> 기준: Google Engineering Practices(eng-practices 공개 문서) — 방법론, 부패 느림(연 1회)

## 정체성

구글 엔지니어링 가이드 전통. **"리뷰의 승인 기준은 완벽이 아니다 — '이 변경이 코드베이스의 건강을 확실히 개선하는가'다"**. 완벽을 기준으로 삼는 순간 리뷰는 병목이 되고, 기준이 없으면 리뷰는 의식이 된다. 리뷰는 결함 검출이자 **지식 전파 장치**이며, 후자가 종종 더 큰 가치다.

핵심 신조: 코드를 비판하지 사람을 비판하지 않는다 · 모든 코멘트에 근거(원칙·문서·결과) · 취향은 취향이라 표시한다 · 빠른 리뷰가 좋은 리뷰의 전제다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 리뷰 관점·코멘트 작법·승인 판단 | diff 자동 리뷰 실행 (→ 글로벌 code-review/review) |
| 리뷰 문화·규모 기준 | 보안 집중 검토 (→ security-review) |
| 리뷰 받는 자세·반박 | 지적된 냄새의 수리 (→ dev-refactoring) |
| 셀프 리뷰 절차 | 검증 명령 실행 (→ 각 스택 스킬) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 거대 PR을 통째로
❌ 2,000줄 PR에 "LGTM 👍" — 읽지 않았다는 자백
✅ 400줄 안팎까지만 정밀 리뷰 가능(그 이상은 분할 요청이 1번 코멘트) — 리팩터/기능 분리(dev-refactoring #3)·커밋 단위 리뷰로 쪼갠다
**왜**: 리뷰 결함 검출률은 변경 규모에 반비례한다(SmartBear 연구: 400줄 초과 시 검출률 급락). 거대 PR 승인은 검토가 아니라 책임 이전 — "분할해 주세요"가 가장 가치 있는 코멘트인 경우가 많다.

### 2. 취향을 결함처럼
❌ "저라면 이렇게 짤 것 같아요" 를 변경 요구로 — 핑퐁 10회
✅ 라벨링 규약: **[블로커]**(정확성·보안 — 머지 불가), **[제안]**(개선 — 선택), **[nit]**(취향 — 무시 가능), **[질문]**(이해 — 답이 코멘트). 스타일은 포매터·린터에 위임하고 리뷰에서 다루지 않는다
**왜**: 등급 없는 코멘트 20개는 전부 블로커처럼 읽혀 작성자를 마비시킨다. 스타일 논쟁은 도구(ruff·prettier)가 끝낸 문제 — 사람이 다시 하면 양쪽 시간만 탄다.

### 3. "이거 이상해요" (행동 불가능 코멘트)
❌ 무엇이 왜 어떻게 바뀌어야 하는지 없는 감상
✅ 코멘트 3요소: **무엇이**(줄·코드) + **왜**(깨지는 시나리오·원칙·문서 링크) + **대안**(코드 또는 방향). 예: "42행 == 비교: null==undefined가 true라 권한 우회 가능 → ===로"
**왜**: 행동 불가능 코멘트는 작성자에게 해독 비용을 떠넘긴다 — 리뷰어가 1분 더 써서 작성자의 30분을 아끼는 것이 리뷰의 경제학이다. (이 스킬군의 ❌/✅ 형식이 바로 이 작법이다.)

### 4. 줄 단위만 보고 설계를 놓침
❌ 변수명·오타 코멘트 15개, "이 기능이 왜 이 모듈에 있는가"는 무언급
✅ 2-pass: **1차 — 전체**(이 변경이 필요한가·맞는 위치인가·계약 변경인가·테스트가 행동을 검증하나), **2차 — 줄**(로직·에러 처리·경계값). 1차에서 막히면 2차는 하지 않는다(구조가 바뀌면 줄 코멘트는 증발)
**왜**: 줄 코멘트는 쉽고 설계 질문은 어려워서, 방치하면 리뷰가 오타 검사로 퇴화한다. 잘못된 위치의 완벽한 코드가 더 비싸다.

### 5. 느린 리뷰 (이틀째 방치)
❌ PR이 이틀 묵음 — 작성자는 컨텍스트를 잃고, 머지 충돌이 쌓이고, 다음 작업이 막힘
✅ 1영업일 내 첫 응답을 규약으로 — 전체 리뷰가 어려우면 "내일 봅니다 + 1차 인상 한 줄"이라도. 작은 PR 우선 처리(이게 분할 인센티브가 된다)
**왜**: 리뷰 지연은 PR 거대화를 유발하는 악순환의 시작이다(기다리는 동안 더 얹게 됨). 구글 가이드가 속도를 별도 장으로 둔 이유 — 리뷰 속도가 곧 팀의 배포 주기다.

### 6. 리뷰 받을 때 방어전
❌ 코멘트마다 반사 반박 / 반대로 전부 무비판 수용
✅ 코멘트는 코드에 대한 것(나에 대한 것 아님) — 각 코멘트를 [수용/근거 있는 반론/질문] 중 하나로 응답하고, 반론은 코드·문서 근거로(CLAUDE.md의 "검증 먼저" 규칙과 동일). 합의 불가 시 제3자 또는 기존 컨벤션이 타이브레이커
**왜**: 방어전은 리뷰어가 코멘트를 줄이게 만들고(좋은 지적도 같이 사라짐), 무비판 수용은 틀린 지적도 코드에 들어가게 한다 — 둘 다 리뷰의 학습 가치를 죽인다.

## 리뷰 관점 우선순위 (1차 pass의 체크 순서)

1. **정확성** — 의도대로 동작하나, 경계·동시성·에러 경로는 (블로커 후보)
2. **보안·데이터** — 입력 검증·비밀·파괴적 변경(마이그레이션) (블로커 후보)
3. **설계** — 맞는 위치·계약 변경 여부(breaking 판별표)·과설계(YAGNI)
4. **테스트** — 행동을 검증하나(구현 결합 아닌가)·실패 경로 케이스 존재
5. **가독성** — 이름·흐름·주석의 why (제안 등급)
6. ~~스타일~~ — 도구 소관, 리뷰 제외

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| PR 크기 | ~400줄 (초과 시 분할 요청 정당) | SmartBear 검출률 연구 |
| 첫 응답 | 1영업일 내 | 안티패턴 5 |
| 코멘트 등급 | 블로커/제안/nit/질문 4종 표기 의무 | 안티패턴 2 |
| 승인 기준 | "확실한 개선 + 블로커 0" — 완벽 아님 | 구글 기준 |
| 셀프 리뷰 | PR 올리기 전 자기 diff 통독 1회 | 가장 싼 리뷰어는 5분 뒤의 자신 |

## 워크플로우 (리뷰 수행 1회)

1. **맥락 파악** — PR 설명·이슈·테스트 결과 먼저(코드보다 먼저). 설명이 없으면 그게 1번 코멘트.
2. **1차 pass (전체)** — 관점 우선순위 1~4. 구조 문제면 여기서 멈추고 대화.
3. **2차 pass (줄)** — 로직·에러 경로·경계값. 자동 검출 가능한 것(린트·이 스킬군의 검출기들)은 도구를 돌리고 결과만 첨부.
4. **코멘트 작성** — 3요소 + 등급 라벨. 좋은 부분 1개 이상 언급(학습 강화는 지적만으로 안 된다).
5. **판정** — 승인(개선 확실) / 코멘트 후 승인(nit만) / 변경 요청(블로커) — 어느 것인지 명시.

## 출력 템플릿

```
## [PR/변경] 리뷰
### 한 줄 판정: <승인 / 코멘트 후 승인 / 변경 요청> — <근거 1줄>
### 1차(전체): <필요성·위치·계약·테스트 소견>
### 코멘트: (등급 라벨 + 3요소 형식, 심각순)
  - [블로커] <무엇> — <왜> → <대안>
  - [제안] ...  - [nit] ...
### 잘한 점: <1개+>
### 도구 결과: <린트·검출기 실행 출력 1줄>
```

### 작성 예시

```
## collector 결측 처리 PR 리뷰
### 한 줄 판정: 변경 요청 — 블로커 1 (침묵 결측 채움)
### 1차(전체): 필요성 OK(정책 표 구현) · 위치 OK(domain/rules) · 계약 변경 없음
  · 테스트: 정상 경로만 — 결측 경로 케이스 부재(제안 아님, 이 PR의 본질이라 블로커에 준함)
### 코멘트:
  - [블로커] rules.py:31 fillna(0) — 진짜 0 거래량과 구분 불가(data-engineering #3, 합의된 정책 표 위반)
    → NULL 유지 + quality_flag='missing'
  - [제안] clean.py:58 가격 파싱 3중 중복 — 3의 규칙 충족, parse_price 추출
  - [질문] 휴장일 행이 들어오는 경우가 실제 있나? (있다면 케이스 추가, 없다면 주석으로 전제 명시)
  - [nit] tickdata → tick_data
### 잘한 점: rejected 테이블에 사유 남기는 구현 — 정책 표 의도 정확히 반영
### 도구 결과: $ pipeline_check.py → fillna 1건 (위 블로커와 동일)
```

❌ "전체적으로 좀 그래요. 다시 봐주세요" (행동 불가 + 등급 없음)
✅ "블로커 1개(근거+대안), 나머지는 제안·nit로 분리 — 작성자가 5분에 우선순위 파악"

### 사용자가 권고를 거부하면

- (작성자로서) "nit까지 다 고치라는 거야?" → 아니다 — nit는 무시 가능이 정의. 등급 체계 자체를 재안내.
- (리뷰어 역할 요청에서) "그냥 통과시켜줘" → 블로커가 있으면 1회만 구체 리스크 고지 후, 강행 시 "검토 의견 무시하고 머지" 기록(partial — 몰래 승인하지 않는다).
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단이 막히면 (확인 필요 4요소)

코멘트의 등급(블로커/제안)이 코드만으로 안 갈리는 경우가 있다 — 이 분기가 의도된 동작인지, 깨지는 시나리오가 실제로 발생하는지가 도메인 지식에 달렸을 때다. 막히면 추측으로 블로커를 달지 말고 4요소로 질의한다: **누가**(이 변경의 의도·계약을 아는 사람 = 작성자/도메인) / **언제**(승인 판정 전 — 잘못 단 블로커는 핑퐁을, 놓친 블로커는 사고를 부른다) / **어떻게**(예: "42행 분기가 휴장일에 실제로 진입하나 — 그렇다면 블로커, 불가능하면 [질문]으로 강등") / **기대값**(그 답이 등급과 승인 여부를 가른다). 확인 불가 시 대체 경로: 정확성·보안 의심은 보수적으로 **[질문]으로 보류**하고 "확인 전까지 머지 보류" 1줄 명시 — 추측으로 블로커를 확정해 작성자를 마비시키지 않되, 의심을 침묵시키지도 않는다.

## 실전 케이스 — Apple goto fail (2014)

```c
if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
    goto fail;
    goto fail;          // <- 중복 줄: 항상 실행, 이하 서명 검증 도달 불가
```

iOS/macOS의 TLS 서명 검증이 **중복된 `goto fail;` 한 줄** 때문에 통째로 우회되는 채로 출하됐다(CVE-2014-1266, 공개 소스로 전 세계가 검증). 교훈: ① 이것은 2차 pass(줄 리뷰)가 잡으라고 존재하는 정확히 그 부류다 — diff에서 중복 줄은 눈에 띄지만, **400줄 넘는 변경 속에서는 띄지 않는다**(안티패턴 1과 직결) ② 도구 병행의 근거: 도달 불가 코드 경고(컴파일러 플래그)가 켜져 있었다면 리뷰 전에 잡혔다 — 사람 리뷰는 도구가 못 잡는 것(설계·의도)에 화력을 집중해야 한다는 역설적 증명.

## 사용자 환경 적용

- 1인 개발의 리뷰는 ① 셀프 리뷰(올리기 전 diff 통독 — 정량 기준) ② Claude 리뷰(글로벌 code-review 스킬 — 그 실행 시 이 스킬의 관점 우선순위·등급 라벨을 출력 형식으로) ③ 협업 프로젝트(tour-data)에서는 친구와 이 등급 규약 합의가 첫 단추.

## 한계

리뷰는 결함의 일부만 잡는다(설계 오해·동시성은 통과 잦음) — 테스트·타입·검출기와 합쳐야 안전망이다. 1인 셀프 리뷰는 자기 맹점을 공유한다 — 시차(다음날 읽기)와 도구가 부분 보완일 뿐. 리뷰 문화 규약은 팀 합의가 본체라 이 스킬은 그 합의의 초안 공급자다.
