# OWASP Top 10 플레이북 + 보안 헤더·입력 검증 (SKILL.md 비중복)

> 기준: OWASP Top 10:2025 (2025-11 공개 → 2026-01 최종 확정, owasp.org/Top10/2025). 항목별 [증상 → 점검 → 처방]. 아래는 2025판 순위·통합 반영본 — 2021판 번호와 다르니 코드 주석/리포트에 항목번호 인용 시 2025 기준임을 명시.

## 항목별 점검표 (2025판)

| OWASP:2025 | 증상·점검 | 처방 |
|---|---|---|
| A01 접근 제어 깨짐 (#1 유지, **SSRF 통합**) | id 바꿔 남의 리소스? 권한 우회 경로? 서버가 사용자 URL을 fetch? | 매 요청 서버 인가(소유권+역할) — 안티패턴 3. SSRF는 URL allowlist·내부망/클라우드 메타데이터 차단(2025에 A01로 흡수) |
| A02 보안 설정 오류 (#5→#2 급상승) | 디버그 on·기본 비밀번호·과다 권한·클라우드 버킷 공개? | 최소 노출·보안 헤더·디버그 off — 안티패턴 6 |
| A03 소프트웨어 공급망 실패 (**신설**, 구 "취약 컴포넌트" 확장) | 오래된 의존성? 빌드/배포 파이프라인·아티팩트 신뢰? | 의존성 스캔·패치(→ dev-dependency-security) + 빌드 무결성·SBOM·아티팩트 서명(→ dev-cicd) — Equifax·Log4Shell·SolarWinds |
| A04 안전하지 않은 설계 | 위협 모델 없이 만듦? | 기능 설계 시 악용 시나리오 1개 — "이걸 어떻게 깰까" |
| A05 암호 실패 (#2→#5 하락) | 평문 저장? 약한 해시? TLS 없음? | 비밀번호 argon2/bcrypt(→ dev-cryptography), 전송 TLS, 저장 암호화 |
| A06 취약·구식 컴포넌트 (잔존 — 공급망과 일부 중첩) | 알려진 CVE 보유 컴포넌트? | A03과 함께 점검 — 스캔·패치(→ dev-dependency-security) (확인 필요: 정확한 잔존 항목명·순위는 owasp.org/Top10/2025 표) |
| A07 인증 실패 | 약한 세션·무차별 대입 허용? | dev-auth 위임 + rate limit·잠금 |
| A08 무결성 실패 | 검증 없는 역직렬화·업데이트? | 서명 검증·신뢰 소스 — 공급망(A03)과 연계 |
| A09 로깅·모니터링 실패 | 침해를 모름? | 보안 이벤트 로깅·탐지(→ dev-monitoring) — Equifax 탐지 지연 |
| A10 예외 조건 부실 처리 (**신설**) | 에러 핸들링 누락·fail-open·논리 오류로 부하 시 보안 우회? | 명시적 에러 처리·fail-closed·예외 경로도 인가 유지 (24개 CWE — 스캔으로 잘 안 잡힘, 부하/이상조건 테스트 필요) |

> 주의: 위 표의 **#1·#2·#5·A03·A10·SSRF 통합은 2025판으로 검증된 사실**. 중간 순위(A06~A09)의 정확한 항목명·번호는 변동 가능 — 인용 전 owasp.org/Top10/2025 원문 대조(확인 필요).

## 보안 헤더 세트 (기본 적용)

```
Content-Security-Policy: default-src 'self'; ...   # XSS 영향 최소화 (가장 효과적, 설정 까다로움)
Strict-Transport-Security: max-age=31536000; includeSubDomains   # HTTPS 강제
X-Content-Type-Options: nosniff                    # MIME 스니핑 차단
X-Frame-Options: DENY                              # 클릭재킹 (또는 CSP frame-ancestors)
Referrer-Policy: strict-origin-when-cross-origin
```

- CSP는 가장 강력하지만 가장 어렵다 — `report-only` 모드로 시작해 위반 수집 후 조인다. 인라인 스크립트 금지가 핵심(nonce/hash).
- 헤더는 리버스 프록시(nginx — dev-nginx)나 앱 미들웨어 한 곳에서 일괄. 프레임워크 보안 헤더 라이브러리(helmet 등) 활용.

## 입력 검증 전략 (allowlist 우선)

- **허용 목록 > 차단 목록**: "위험한 것 제거"(blocklist)는 항상 새 우회가 나온다 — "허용된 형태만 통과"(allowlist)가 견고. 종목코드는 `^\d{6}$`만 허용이지 "위험문자 제거"가 아니다.
- 검증 위치: 경계(진입) 1회 + 위험 맥락 진입 시 인코딩. 검증과 인코딩은 다른 것 — 검증은 "받을지", 인코딩은 "안전하게 출력".
- 파일 업로드: 확장자·MIME 신뢰 금지(위조 가능), 내용 검사 + 실행 권한 없는 경로 + 별도 도메인 서빙.
- 정규화 후 검증: 경로(`../` 트래버설)·유니코드는 정규화 먼저 — 검증 우회의 단골.

## 위협 모델링 경량판 (A04 — 1인용 10분)

1. 이 기능의 자산(보호 대상): 무엇이 유출·변조되면 아픈가.
2. 진입점: 누가 어디로 입력을 넣나(인증 전/후).
3. "내가 공격자라면": 각 입력으로 무엇을 시도할까 3개.
4. 그 3개에 대한 방어가 있는가 → 없으면 작업 항목.

STRIDE 같은 정식 기법은 규모가 정당화할 때 — 소규모는 이 4질문이 90%.
