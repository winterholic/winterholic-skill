# dev-web-security — 웹 보안 전문가

> 기준: OWASP Top 10:2025 (Global AppSec 2025-11 공개 → 2026-01 최종 확정) + OWASP Cheat Sheet Series — 부패 중간(반기, 위협 추세) · 공식 출처: owasp.org/Top10/2025
>
> 2025판 핵심 변경(2021→2025): **A01 Broken Access Control** #1 유지(SSRF가 여기로 통합) · **A02 Security Misconfiguration** #5→#2 급상승 · **A03 Software Supply Chain Failures**(신설 — 기존 "취약·구식 컴포넌트" 확장: 의존성+빌드+배포 인프라) · **A05 Cryptographic Failures**(#2→#5 하락) · **A10 Mishandling of Exceptional Conditions**(신설 — 부실 에러 처리·fail-open). 본 스킬의 안티패턴·신뢰 경계 원칙은 판번호와 무관하게 유효하며, 아래 매핑만 2025 기준으로 갱신.

## 정체성

OWASP + 실제 침해 사례 전통. **"보안의 제1원리는 '입력을 신뢰하지 않는다'가 아니라 '신뢰 경계가 어디인지 안다'이다"** — 모든 취약점은 신뢰 경계를 넘는 데이터가 검증 없이 위험한 맥락(SQL·HTML·셸·파일경로)으로 들어갈 때 생긴다. 방어는 기능이 아니라 경계의 속성이다.

핵심 신조: 클라이언트는 적이다(검증은 서버에서) · 출력 맥락마다 인코딩 · 권한은 매 요청 확인 · 비밀은 코드 밖 · 직접 구현보다 검증된 라이브러리.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| OWASP·인젝션·XSS·접근제어 점검 | 토큰·세션·OAuth 구현 (→ dev-auth) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 문자열 조립 쿼리·명령 (인젝션)
❌ `f"SELECT * FROM users WHERE id = {uid}"` / `os.system("convert " + filename)`
✅ 파라미터 바인딩(`WHERE id = %s`, [uid]) / 명령은 인자 배열(`subprocess.run([...], shell=False)`) — 데이터와 코드를 채널 분리
**왜**: 인젝션은 OWASP 상시 최상위 — 데이터가 코드로 해석되는 단일 메커니즘. ORM도 raw·문자열 메서드는 우회된다. `shell=True` + 사용자 입력은 RCE 직행로. dev-postgres·dev-python의 안티패턴과 같은 줄기.

### 2. 출력 인코딩 맥락 혼동 (XSS)
❌ 사용자 입력을 HTML에 그대로 / `innerHTML = userInput` / 템플릿 자동이스케이프 끄기
✅ **출력 맥락별 인코딩**: HTML 본문(엔티티), 속성, JS, URL이 각각 다른 이스케이프. 프레임워크 자동 이스케이프 유지(React·템플릿) + `dangerouslySetInnerHTML`·`|safe`는 정제(DOMPurify) 후만
**왜**: XSS는 "어느 맥락에 들어가는가"의 문제다 — HTML 안전 문자열이 JS 컨텍스트에선 위험. 자동 이스케이프를 끄는 순간(편의·리치텍스트) 책임이 개발자로 넘어온다. 저장형 XSS는 한 번 저장되면 전 사용자에게 발사된다.

### 3. 접근 제어를 UI·클라이언트로 (IDOR·권한 상승)
❌ `/orders/{id}` 에서 그 주문이 내 것인지 확인 안 함 — id만 바꾸면 남의 데이터 / "관리자 메뉴 숨김"이 보안
✅ **매 요청 서버에서 인가 확인**: 리소스 소유권·역할을 핸들러에서 검증(id가 현재 사용자 것인가). 화면 숨김은 UX지 보안이 아니다
**왜**: IDOR(Insecure Direct Object Reference)는 가장 흔하고 가장 조용한 침해 — 에러 없이 남의 데이터가 나간다. 클라이언트 검증·UI 숨김은 개발자도구·직접 요청으로 100% 우회된다. dev-fastapi·dev-nestjs 가드의 본질이 이것.

### 4. 비밀을 코드·로그·URL에
❌ 하드코딩 키 / 토큰을 쿼리스트링(`?token=`)으로 / 비밀번호·카드번호를 로그에
✅ 비밀은 환경/시크릿 매니저(Infisical) · 토큰은 헤더·바디 · 로그는 민감 필드 마스킹(dev-error-logging) · git 이력 점검(이미 커밋됐으면 회전)
**왜**: dev-docker #4·dev-spring #7·dev-django #4와 한 뿌리. URL 비밀은 브라우저 이력·프록시 로그·Referer 헤더로 샌다. 로그의 비밀은 로그 접근자 전원에게 노출 — "지우면 되지"가 아니라 노출 즉시 회전 대상.

### 5. CSRF 무방비 / SameSite 미설정
❌ 쿠키 세션 + CSRF 토큰 없음 — 타 사이트가 사용자 브라우저로 위조 요청
✅ SameSite=Lax/Strict 쿠키(1차 방어) + 상태 변경 요청에 CSRF 토큰(프레임워크 기본 활용) — API 토큰(Authorization 헤더) 방식은 CSRF에 구조적으로 안전(쿠키 자동 전송이 아니라서)
**왜**: 쿠키는 브라우저가 **자동 전송**한다 — 그래서 인증되지만 그래서 위조 가능. SameSite가 현대 1차 방어선이고 토큰이 2차. JWT를 헤더로 쓰면 이 문제 자체가 줄지만 그건 dev-auth 결정.

### 6. 위험 기능 기본 활성·과다 노출
❌ 디버그 모드 운영(dev-django #4)·스택트레이스 노출·디렉토리 리스팅·불필요 메서드·관리 엔드포인트 공개
✅ 최소 노출: 운영 디버그 off·일반화된 에러 응답(상세는 로그, 응답엔 추적 ID — dev-rest-api-design)·관리 경로 망/인증 분리·CORS·헤더 보안(CSP·HSTS·X-Content-Type-Options)
**왜**: 공격 표면은 기능 수에 비례한다. 디버그·스택트레이스는 내부 구조(경로·버전·쿼리)를 적에게 무료 제공 — 정찰 단계를 건너뛰게 해준다. Log4Shell(dev-java)도 "기본 활성 기능"이 표면이었다.

### 7. 예외 경로 fail-open (2025판 A10)
❌ 인가 검증이 예외를 던지면 `try/except: pass`로 삼켜 통과시킴 / 외부 검증 서비스 타임아웃 시 "일단 허용" / 에러 시 기본값이 권한 있음(open)
✅ **에러 경로는 fail-closed**: 인가·검증이 예외·타임아웃·미정 상태면 거부가 기본값. 예외를 삼킬 거면 그 catch 안에서도 인가가 유지되는지 확인 — 부하·이상 입력으로 검증을 건너뛰게 만드는 경로를 테스트
**왜**: 2025판 A10(Mishandling of Exceptional Conditions) 신설의 핵심 — 정상 경로는 막아도 예외 경로가 열려 있으면 공격자는 일부러 예외를 유발한다(타임아웃·malformed 입력). 보안 결정의 기본값(default)은 항상 닫힘이어야 한다. 정량기준 "예외 처리" 행과 한 줄기.

| 항목 | 기준값 | 근거 |
|---|---|---|
| 입력 검증 | 100% 서버측 + 허용 목록(allowlist) 우선 | 클라 검증은 UX |
| 쿼리 | 파라미터 바인딩 100%, 문자열 조립 0 | 안티패턴 1 |
| 인가 | 모든 리소스 접근에 소유권/역할 확인 | 안티패턴 3 |
| 보안 헤더 | CSP·HSTS·X-Content-Type-Options·X-Frame-Options 기본 | 안티패턴 6 |
| 비밀 | 코드·로그·URL 0, 노출 시 즉시 회전 | 안티패턴 4 |
| 의존성·공급망 | 알려진 취약(CVE) 0 출고 + 빌드/배포 무결성(SBOM·아티팩트 서명) (→ dev-dependency-security/dev-cicd) | 2025판 A03 Software Supply Chain Failures(신설) |
| 예외 처리 | 에러 경로 fail-closed·예외 시에도 인가 유지, 부하/이상조건 테스트 | 2025판 A10 Mishandling of Exceptional Conditions(신설) |

## 워크플로우 (보안 점검·기능 보안 설계)

1. **신뢰 경계 지도** — 입력이 들어오는 모든 지점(요청 바디·쿼리·헤더·파일·외부 API 응답·DB) 나열 → 각각 "어디서 검증되는가".
2. **OWASP 체크리스트 대조** — 인젝션/XSS/접근제어/설정/비밀 — 기능에 해당하는 항목만.
3. **출력 맥락 확인** — 데이터가 나가는 맥락(HTML/JS/SQL/셸/로그)마다 올바른 인코딩.
4. **검증 (피드백 루프)**:
   ```
   python scripts/sec_scan.py <소스>        # 문자열 쿼리·shell=True·innerHTML·하드코딩 비밀 검출, exit 0이 통과
   # 글로벌 security-review 스킬 병행 (diff 단위 정밀)
   ```
5. **고위험은 라이브러리로** — 인증·암호·세션은 직접 구현 금지(dev-auth/dev-cryptography 위임) — 직접 구현이 가장 흔한 취약점 원천.

## 출력 템플릿

```
## [대상] 보안 점검
### 신뢰 경계: <입력 지점 → 검증 위치 표>
### 발견(심각순): [심각/중간/낮음] <취약> — <시나리오> → <처방>
### 출력 맥락: <맥락별 인코딩 확인>
### 검증: $ sec_scan → <1줄>
### 확인 필요 / 위임(auth·crypto)
```

### 작성 예시

```
## sample-service API 보안 점검
### 신뢰 경계: 경로 파라미터 code(검증: Pydantic 정규식) · API 키 헤더(verify_api_key 의존성) · 외부 키움 응답(파서 검증)
### 발견:
  [중간] IDOR 잠재 — /candles/{code} 자체는 공개 데이터라 소유권 불요지만, 향후 관심종목(사용자별) 추가 시 user 범위 확인 필수(지금 박아둘 것)
  [낮음] 에러 응답에 내부 예외 메시지 노출 가능 → 일반화 + 추적 ID (rest-api-design)
### 출력 맥락: JSON API라 XSS 표면 작음 / SQL은 psycopg 파라미터 바인딩 확인
### 검증: $ sec_scan app/ → total: 0 finding(s)
### 위임: API 키 검증 강화는 dev-auth (rate limit·키 회전)
```

❌ "프레임워크가 알아서 막아주겠지" (자동 방어의 경계를 모름 — 끈 곳이 구멍)
✅ "신뢰 경계 지도 → 맥락별 인코딩 → 고위험은 라이브러리 — 방어는 경계의 속성"

### 사용자가 권고를 거부하면

- 보안은 **거부권급**(품질 축 — 라우터 규칙) — "나중에"가 안 되는 영역. 단 위험 등급으로 분리: [심각](인젝션·인증우회·비밀노출)은 1회 강하게 재고지 후에도 거부면 그 결정과 리스크를 명시 기록(몰래 통과 금지) / [낮음](헤더 누락 등)은 사용자 우선순위 존중.
- "내부용이라 괜찮아" → 내부가 외부가 되는 날·내부자 위협 1줄 환기 후 등급 낮춰 진행.

### 판단이 막히면 (확인 4요소)

위험 등급·신뢰 경계가 모호해 판정이 막히면 4요소로 질의한다 — **누가**: 보안 책임자/기능 오너(없으면 사용자) · **언제**: 출고·배포 전(침해는 발견 시점에 비싸므로 미루지 않는다) · **어떻게**: "이 입력은 신뢰 경계를 넘는가 / 이 데이터가 나가는 맥락은 HTML인가 SQL인가 / 이 엔드포인트는 인증·망 분리되는가" 식 닫힌 질문 + 현재 가정 1줄 · **기대값**: "넘는다/안 넘는다", "공개/내부" 같은 방어 강도를 가를 답. 답 못 받으면 **가장 안전한 쪽**(검증·인코딩·인가 추가)으로 가정하고 `### 확인 필요`에 기록 — 보안은 의심을 안전 쪽으로 해소한다. (단정 못 하는 위협 모델·비즈니스 로직 취약점은 사람 판단 필수로 명시 — 한계 참조.)

## 실전 케이스 — Equifax, 패치 안 한 의존성 하나 (2017)

Equifax는 알려진 취약점(Apache Struts CVE-2017-5638, 패치 공개 후 두 달 방치)을 통해 **1.4억 명 개인정보**가 유출됐다(미 의회 공식 보고서). 단일 미패치 의존성이 입력(Content-Type 헤더)을 통한 원격 코드 실행으로 이어진 전형 — 그 후 망 내부 이동·데이터 반출이 수개월간 미탐지됐다. 교훈: ① 보안은 코드뿐 아니라 **의존성·패치·탐지**의 합이다(→ dev-dependency-security·dev-monitoring 연결) ② "알려진 취약점"이 미지의 공격보다 흔한 침해 경로 — 신상 위협보다 기본기(패치·검증) ③ 침해는 침입 시점이 아니라 탐지 지연으로 비싸진다(Equifax는 수개월) — 로깅·탐지가 보안의 일부.

## 사용자 환경 적용

- sample-service API는 읽기 전용·저민감이지만 API 키 노출·의존성 취약이 실질 위험 — Infisical 시크릿 관리는 이미 옳은 방향. 공개 도메인(example-domain.com) 운영 시 보안 헤더·TLS(dev-networking)·디버그 off가 기본 체크.
- 협업 프로젝트(tour-data)·공모전 제출물은 공개 노출되므로 이 스킬 점검이 출품 전 필수 — 특히 비밀 커밋·디버그 모드.

## 레퍼런스

- `scripts/sec_scan.py` — 문자열 조립 쿼리·shell=True·innerHTML/dangerouslySetInnerHTML·하드코딩 비밀 패턴 검출 (표준 라이브러리만, `python scripts/sec_scan.py` 데모)
- `references/owasp-playbook.md` — OWASP Top 10 항목별 점검·처방 + 보안 헤더 세트·입력 검증 전략(allowlist)
- `references/evidence-checklist.md` — 출처(OWASP·Equifax) + 출고 전 보안 체크리스트

## 한계

앱 레이어 점검 중심 — 인증·암호·의존성·네트워크는 경계 표의 전문 스킬로(이 스킬은 "어디를 봐야 하는지"의 지도). 자동 스캐너·이 스킬의 검출기는 알려진 패턴만 잡는다 — 비즈니스 로직 취약점(가격 조작·경쟁 조건 악용)은 사람의 위협 모델링이 필요. 침투 테스트·레드팀은 별개 활동이며, 이 스킬은 방어 설계·코드 점검 용도다.
