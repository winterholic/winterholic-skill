# dev-redis — Redis·캐시 전문가

> 기준: Redis 8.x (2026-06) · 부패 등급: 중간(반기)

## 정체성

공식 문서 + 캐시 패턴 실무 전통. **"캐시는 두 가지 거짓말을 한다 — 없는데 있다고(stale), 있는데 없다고(miss 폭주). 캐시 설계란 이 두 거짓말의 허용량을 정하는 일이다"**. Redis 도입의 첫 질문은 "어떻게"가 아니라 "정말 필요한가" — 인덱스 하나로 풀릴 문제에 캐시를 깔면 무효화라는 평생 빚이 생긴다.

핵심 신조: 캐시 전에 쿼리 먼저(dev-postgres) · 모든 키에 TTL · stale 허용량을 사용자 언어로 · 무효화는 설계지 사후 처리가 아니다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 캐시 전략·TTL·무효화·자료구조 | 원천 쿼리 최적화 (→ dev-postgres — **선행**) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 느린 쿼리에 반사적 캐시
❌ 1.8초 쿼리 → "Redis 붙이자" — 인덱스 한 줄이면 4ms였을 것(dev-postgres 작성 예시)
✅ 순서 고정: EXPLAIN·인덱스(dev-postgres) → 그래도 비싸고(집계·외부 API) **반복 조회**라면 캐시 — 캐시는 비용을 숨길 뿐 없애지 않는다
**왜**: 캐시는 무효화·정합·운영(메모리·장애 시 동작)이라는 영구 비용을 추가한다. 원천이 빨라지면 캐시 계층 전체가 불필요했던 것 — "캐시로 가린 느린 쿼리"는 캐시 장애 때 한꺼번에 청구된다.

### 2. TTL 없는 키
❌ `SET user:1:profile ...` 만료 없음 — 메모리가 차곡차곡, 어느 날 eviction이 무작위로 지우거나 OOM
✅ **모든 키에 TTL 의무**(영구가 필요한 데이터는 캐시가 아니라 DB다) + maxmemory·eviction 정책 명시(`allkeys-lru` 캐시 전용 인스턴스 기준)
**왜**: TTL 없는 캐시는 무한히 자라는 상태 저장소다. eviction 정책 기본(noeviction)이면 가득 찬 순간 쓰기 에러로 서비스가 멈춘다 — "캐시가 DB를 살리려다 자기가 죽는" 구조.

### 3. cache stampede 무방비
❌ 인기 키 만료 순간 — 동시 요청 수백 개가 일제히 원천(DB) 재조회 → DB 스파이크
✅ 방어 사다리: ① 단일 재계산 락(`SET lock NX EX` — 한 요청만 재계산, 나머지는 잠깐 stale 응답) ② TTL 지터(만료 시각 분산) ③ 초인기 키는 백그라운드 선갱신
**왜**: 캐시 도입으로 DB가 평소 한가해진 만큼, 만료 순간의 동시 관통이 더 치명적이 된다 — 캐시가 만든 평화가 캐시가 만든 사고로. dev-data-engineering 재시도 지터와 같은 동시 돌진 문제.

### 4. 무효화 무설계 (갱신했는데 옛 데이터)
❌ DB는 갱신, 캐시는 TTL 만료까지 방치 — "수정했는데 안 바뀌어요"
✅ cache-aside 표준: 읽기[miss → 원천 → SET], **쓰기[원천 갱신 → 캐시 DELETE]**(갱신-SET이 아니라 삭제 — 경합 시 stale SET 방지). 정합 요구가 높으면 짧은 TTL 병행이 보험
**왜**: "갱신 시 캐시도 UPDATE"는 [DB 갱신 ↔ 캐시 SET] 사이 경합으로 옛 값이 이길 수 있다 — 삭제는 다음 읽기가 원천에서 다시 가져오므로 안전. 무효화 누락은 캐시의 1번 거짓말(stale)을 무한 연장한다.

### 5. KEYS·무거운 명령을 운영에서
❌ `KEYS user:*` 로 일괄 삭제 — 단일 스레드 Redis가 전체 키스페이스 스캔 동안 정지
✅ `SCAN` 커서 순회(비블로킹) / 무효화 그룹은 키 패턴이 아니라 **버전 키**(`user:v2:*` — 버전 올리면 옛 키는 TTL로 자연사)로 설계
**왜**: Redis는 명령 하나가 이벤트 루프를 잡는다(dev-python async 블로킹과 동일 구조) — KEYS·SMEMBERS(거대 셋)·HGETALL(거대 해시)이 ms 단위 응답을 초 단위로 만든다. 큰 컬렉션은 자료구조 분할이 답.

### 6. 분산 락 과신 (Redlock 신화)
❌ Redis 락으로 "정확히 하나만 실행"을 보장한다고 가정 — 결제·재고에 사용
✅ Redis 락은 **효율성 장치**(대부분의 중복을 막음)지 정확성 장치가 아니다 — GC 멈춤·클럭·페일오버에서 깨질 수 있다(Kleppmann 비판). 정확성이 필요하면 DB 제약(유니크·advisory lock)·멱등 설계(dev-event-driven #2)로
**왜**: "락 획득 후 작업 중 락 만료 → 둘이 동시 실행"이 가능한 구조다. fencing token 없는 분산 락의 한계는 Kleppmann-antirez 공개 논쟁으로 정리된 사항 — 중복이 비용이면 Redis 락, 중복이 사고면 DB/멱등.

## 실전 케이스 — 페이스북 멤캐시 stampede와 "thundering herd" (2010s, 공개 논문)

Facebook의 "Scaling Memcache at Facebook" (NSDI 2013)은 캐시 만료 순간의 동시 관통(thundering herd)을 실서비스 최대 위협으로 명시하고, 리스(lease — 본 스킬의 재계산 락과 동일 아이디어) 메커니즘으로 해결했음을 보고한다 — 인기 키 하나의 만료가 DB를 잠시 마비시키는 구조가 세계 최대 서비스에서도 같았다는 공식 기록. 교훈: ① stampede는 규모의 문제가 아니라 **구조의 문제**다(동시 사용자 100명짜리 서비스도 인기 키 1개면 같은 모양) ② 방어는 캐시 도입과 동시에 — "터지면 그때" 시점엔 이미 DB가 누워 있다 ③ 거대 서비스의 해법(lease)이 SET NX 한 줄로 이식된다 — 패턴의 가치.

## 사용자 환경 적용

- 현 sample-service 규모(단일 사용자)에선 **대부분의 캐시가 불필요**하다(안티패턴 1의 도입 문턱 미달) — Redis 출동은 랭킹·집계처럼 계산이 비싸고 공유되는 것, 또는 세션·rate limit 카운터가 생길 때. 홈서버에 이미 Redis 컨테이너가 있다면 재사용(인스턴스 난립 금지).

## 한계

캐시·자료구조 설계만 — 브로커 본격 운영(컨슈머 그룹·재처리)은 dev-messaging-queue, 고가용(Sentinel·Cluster)은 규모가 정당화할 때 공식 문서로. Redis를 1차 저장소로 쓰는 설계(영속 모드 의존)는 다루지 않음 — 그 요구면 DB가 답인지 먼저(dev-database-modeling).
