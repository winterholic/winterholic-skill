# dev-concurrency — 동시성 원리 전문가

> 기준: 원리(언어 불문) (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

동시성 이론·실무 전통(*The Art of Multiprocessor Programming*·각 언어 메모리 모델 공통 원리). **"동시성 버그의 본질은 '내 코드 두 줄 사이에 남이 끼어들 수 있다'는 사실의 망각이다 — 그리고 그 버그는 테스트가 아니라 트래픽이 찾아낸다"**. 간헐 재현은 미스터리가 아니라 동시성의 서명이다.

핵심 신조: 원자성은 가정이 아니라 확보하는 것 · 락 순서는 전역 규칙 · 공유 가변 상태가 적이다(공유 않기 > 불변 > 락) · "동시에 두 요청" 시나리오를 설계 단계에서 묻는다.

비유 — 경쟁 조건은 **공용 화장실 문**이다: "노크(check) → 들어감(act)" 사이에 남이 먼저 들어갈 수 있다 — 해법은 더 빠른 노크가 아니라 **잠금장치**(원자 연산)다. 데드락은 좁은 복도에서 마주 본 둘이 서로 비켜주길 기다리는 것 — 해법은 "항상 같은 방향 우선"(전역 락 순서)이라는 교통 규칙이다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. check-then-act 비원자
❌ `if (balance >= amount) { balance -= amount; }` — 검사와 행동 사이에 다른 스레드의 같은 검사가 통과 (이중 출금)
✅ 검사+행동을 **하나의 원자 단위로**: 락으로 묶기 / 원자 연산(CAS) / DB라면 조건부 UPDATE(`UPDATE ... WHERE balance >= ?`) — "그 사이에 누가 끼면?"을 모든 검사-행동 쌍에 묻는다
**왜**: 이 패턴은 동시성 버그의 절반이다 — 파일 존재 확인 후 생성, 캐시 미스 확인 후 빌드(dev-javascript #6), 재고 확인 후 차감, 전부 같은 골격. 단일 스레드에선 100% 안전해 보이는 코드라 리뷰로도 놓친다.

### 2. 락 순서 무규칙 — 데드락
❌ 스레드 A: lock(계좌1)→lock(계좌2), 스레드 B: lock(계좌2)→lock(계좌1) — 서로 기다리며 영원 정지
✅ **전역 락 순서 규칙**(항상 ID 작은 쪽 먼저 등) — 문서화하고 전 코드가 따른다. 또는 타임아웃 있는 락 + 실패 시 전체 해제 후 재시도
**왜**: 데드락은 4조건(상호배제·점유대기·비선점·순환대기)이 모두 성립할 때만 발생 — 순서 규칙은 순환대기를 구조적으로 제거하는 가장 싼 방법이다. 데드락은 부하가 높은 최악의 순간에만 발현하는 게 잔인한 특성.

### 3. 락 범위 양극단
❌ 함수 전체를 거대 락(병렬성 소멸 — 락이 곧 병목) / 반대로 필드 일부만 보호(불변식이 여러 필드에 걸치는데)
✅ 락의 단위는 코드 줄 수가 아니라 **불변식(invariant)**: 함께 일관돼야 하는 데이터 묶음 = 한 락. 락 안에서는 최소 작업만(IO·외부 호출을 락 안에서 금지)
**왜**: 과대 락은 동시성을 산 의미를 없애고(Amdahl — 직렬 구간이 상한을 정함), 과소 락은 보호를 안 한 것과 같다. "이 락이 지키는 불변식이 뭔가"에 한 문장으로 답 못 하면 설계가 안 된 것.

### 4. 동시성·병렬성 혼동 (도구 미스매치)
❌ CPU 계산을 async/스레드(GIL)로 — 빨라지지 않음 / IO 대기를 프로세스 풀로 — 자원 낭비
✅ 부류 판정 먼저: **IO 바운드 = 동시성**(async·스레드 — 기다림을 겹침) / **CPU 바운드 = 병렬성**(프로세스·네이티브 스레드 — 코어를 더 씀). 측정으로 부류 확인(→ dev-performance USE)
**왜**: 동시성은 "여럿을 다루는 구조", 병렬성은 "여럿을 동시에 실행"이다 — 다른 문제다. Python GIL에서 스레드로 CPU 작업은 오히려 느려지고(컨텍스트 스위칭만 추가), async에 CPU 작업은 루프 전체를 멈춘다(dev-python·dev-rust의 블로킹 함정이 이 원리의 각론).

### 5. 공유 가변 상태 기본값
❌ 일단 전역 dict·공유 객체로 설계하고 나중에 락을 "추가"
✅ 회피 서열로 설계: ① **공유하지 않기**(작업별 분할·메시지 패싱 — 소유권 이전) ② **불변 데이터**(공유해도 읽기뿐이면 안전) ③ 그래도 필요한 곳만 락 — 락은 1순위가 아니라 3순위 도구
**왜**: 락은 깜빡한 한 곳에서 무너지는 규율이다(컴파일러가 강제 안 하는 언어에선 특히). 공유 자체를 없애면 버그의 존재 가능성이 사라진다 — Go의 "communicate by sharing 금지" 격언과 Rust 소유권이 이 서열을 언어로 만든 것.

### 6. sleep으로 동기화
❌ `start_worker(); sleep(2); assert ready` — "2초면 되겠지" (느린 CI에서 간헐 실패, 빠른 머신에선 2초 낭비)
✅ 명시적 동기화 신호: 이벤트/조건 변수·채널·폴링+타임아웃(`wait_until(ready, timeout=10)`) — "준비됨"을 기다리지 "시간"을 기다리지 않는다
**왜**: sleep 동기화는 타이밍 가정이고, 타이밍은 환경마다 다르다 — 플레이키 테스트의 최대 원인이자, 프로덕션에선 "더 느린 날"에 터지는 시한 장치다. 신호 기반은 빠른 환경에선 즉시, 느린 환경에선 정확히 기다린다.

## 워크플로우 (동시성 설계·버그 1건)

1. **공유 지도** — 여러 실행 흐름이 닿는 가변 상태를 전부 나열 → 각각 회피 서열(분할/불변/락) 적용.
2. **버그면 분류** — "간헐 재현 + 부하 의존"이면 동시성 가설 1순위 → 검사-행동 쌍과 공유 쓰기 지점부터 수색.
3. **작성** — 동기화 코드는 한 모듈에 집약(락·큐 래퍼), 산재 금지. 기존 파일 덮어쓰기 대신 Edit. 언어별 구현은 해당 스킬(dev-go 채널·dev-python asyncio 등)로.
4. **검증 (copy-paste)**:
   ```
   go test -race ./...                       # Go: race detector
   python -X dev -m pytest tests/ -k concurrent   # Python: 동시 시나리오 테스트
   # 부하 재현: 같은 자원에 동시 N발 (간헐 버그를 확률에서 필연으로)
   seq 1 50 | xargs -P 50 -I{} curl -s -X POST localhost:8000/withdraw
   ```
5. **재현 후 수정** — 동시성 버그는 재현 장치를 먼저 만들고 고친다(재현 없는 수정은 "안 터지길 빌기").

### 판단이 막히면 (확인 필요 4요소)

동시성 버그는 "코드만 봐선 안전/위험 판정 불가"한 경우가 잦다 — 막히면 4요소로 질의한다: **누가**(이 자원에 동시 접근하는 실행 흐름이 실제로 몇 개인지 = 사용자/배포 구조가 답) / **언제**(설계 단계 — 출고 후 발견되는 간헐 버그는 재현이 가장 비쌈) / **어떻게**(예: "이 함수가 워커 N개에서 동시 호출되나, 단일 writer인가") / **기대값**(그 답이 락 필요 여부·회피 서열을 가른다). 확인 불가 시 대체 경로: 가장 보수적 가정(동시 접근 있음)으로 검사-행동 쌍을 원자화하고 "확인 필요 — 동시성 보수 가정" 기록. 보수 가정은 정확성을 희생하지 않는다(과보호는 성능 손실뿐, 과소 보호는 데이터 손상).

## 실전 케이스 — Therac-25 (1985~87): 경쟁 조건이 사람을 죽였다 (공식 조사 보고)

방사선 치료기 Therac-25가 과조사 사고 6건(사망 포함)을 냈다 — 핵심 원인 중 하나가 **숙련 조작자의 빠른 입력이 만든 경쟁 조건**: 설정 변경 입력과 장비 셋업 루틴이 동기화 없이 병행되어, 화면은 안전 모드인데 장비는 고출력 모드인 불일치 창이 열렸다. 이전 모델의 하드웨어 인터락을 소프트웨어로 대체하며 방어가 한 겹이 된 것도 치명적이었다. 교훈: ① 경쟁 조건은 "특정 속도·순서의 입력"이라는 재현 조건 때문에 테스트를 통과하고 숙련 사용자에게서 터진다 ② 안전이 걸린 불변식은 소프트웨어 동기화 + 독립 검증 층(이중)으로 ③ "간헐 보고를 재현 불가로 종결"한 제조사의 대응이 사고를 6건으로 만들었다 — 간헐은 종결 사유가 아니라 동시성 수사의 개시 사유다. 상세: `references/evidence.md`
