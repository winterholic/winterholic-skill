# dev-storage-nas — 스토리지·NAS 전문가

> 기준: OpenZFS 2.3.x(2025-01 GA, RAIDZ 확장·fast dedup·Direct I/O) · RAID 일반 (2026-06 현행) · 부패 등급: 느림(연 1회 점검) · 공식 출처: openzfs.github.io · Backblaze Drive Stats 2025(연간/Q4)

## 정체성

스토리지 실무 + Backblaze 통계 전통. **"RAID는 가용성 장치지 백업이 아니다 — 디스크가 죽어도 서비스가 계속되게 할 뿐, 삭제·랜섬웨어·풀 손상·화재 앞에선 모든 RAID가 평등하게 무력하다"**. 그리고 디스크는 죽는 게 정상이다(연 1~2% — 통계가 있다). 설계란 그 죽음을 일정에 넣는 것.

핵심 신조: RAID≠백업(주문처럼) · 대용량 패리티는 리빌드가 고비 · ZFS는 scrub과 함께만 완성 · 디스크는 흩어 산다(로트 분산) · 감시 없는 스토리지는 시한폭탄.

비유 — RAID는 **자동차 스페어타이어**다: 펑크(디스크 1개 사망)에도 달릴 수 있게 하는 장치 — 그러나 차가 통째로 침수(풀 손상·랜섬웨어)되면 스페어도 같이 잠긴다. 침수 대비는 다른 차고의 다른 차(백업 — dev-backup-dr)다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. "RAID 있으니 백업 됐다"
❌ 미러/RAIDZ 구성 후 백업 생략 — 실수 삭제·랜섬웨어·컨트롤러 고장·풀 손상이 **모든 복제본에 동시 적용**
✅ 역할 분리 선언: RAID = 디스크 사망 시 무중단(가용성) / 백업 = 데이터의 과거 시점 사본을 **다른 시스템에**(생존성 — dev-backup-dr 3-2-1) — NAS 설계서에 두 줄로 박는다
**왜**: RAID는 쓰기를 전 복제본에 충실히 전파한다 — rm도 암호화(랜섬)도 똑같이 전파된다. "복제"와 "백업"의 차이는 시점 분리다. 이 혼동이 데이터 유실 사연의 부동의 1위.

### 2. 대용량 단일 패리티 (RAID5/RAIDZ1)
❌ 12TB+ 디스크 4장 RAIDZ1 — 1장 사망 후 리빌드 수일간 나머지 전체를 혹사: 그때 2번째가 죽으면 전멸 (확률이 직관보다 높다)
✅ 대용량은 **미러 또는 이중 패리티(RAIDZ2)** 기본 — 리빌드 창의 추가 사망·읽기 에러를 견딘다. 소용량·백업 충실 환경만 Z1 허용(정직한 결정으로)
**왜**: 리빌드는 전 디스크 풀 읽기 — 같은 로트·같은 나이 디스크들이 가장 약한 순간에 최대 부하를 받는다(동반 사망의 무대). 디스크가 커질수록 리빌드 창이 길어져 Z1의 안전 마진은 해마다 줄어왔다.

### 3. scrub 없는 ZFS (침묵 부패 방치)
❌ 풀 만들고 끝 — 비트 부패·잠복 불량 섹터가 **읽는 날**(=리빌드하는 최악의 날) 발견됨
✅ **월 1회 scrub** 스케줄(전 데이터 검증·자가 치유) + 결과 알림(dev-cron-scheduling dead man's switch) — scrub 에러 증가 추세는 디스크 교체 신호
**왜**: ZFS 체크섬의 가치는 읽을 때만 발휘된다 — 안 읽는 데이터(아카이브)의 부패는 scrub만이 찾는다. 잠복 에러를 평시에 청소해두는 것이 리빌드 성공률의 실질 보험이다(안티패턴 2와 한 쌍).

### 4. SMR 디스크를 NAS에
❌ 싸다고 산 디스크가 SMR(겹쳐쓰기 방식) — 지속 쓰기·리빌드에서 성능 절벽, ZFS 리빌드가 며칠~실패까지
✅ NAS·RAID용은 **CMR 확인 후 구매**(제조사 스펙시트 — NAS 라인업도 과거 침묵 혼입 전력) + 용도별: 아카이브 단독 디스크는 SMR 허용
**왜**: SMR은 임의 쓰기를 내부 재정리로 흡수하다 지속 부하에서 무너진다 — RAID 리빌드가 정확히 그 부하다. 2020년 제조사들의 SMR 침묵 혼입 사태(evidence)가 "스펙시트 확인"을 의무로 만들었다.

### 5. 같은 날 같은 로트 디스크로 풀 구성
❌ 동일 모델·동일 구매 디스크 4장 — 같은 결함·같은 마모 곡선: 1장 죽을 때가 나머지의 임박 신호인데 리빌드로 혹사
✅ 분산 전략: 구매 시점/판매처/(가능하면) 모델 분산 + Backblaze 통계로 모델별 고장률 참고 — 그리고 어차피 죽는다는 전제로 핫스페어 또는 신속 조달 계획
**왜**: 디스크 고장은 독립 사건이 아니다 — 같은 로트는 고장 상관이 있다. RAID 수학(독립 가정)이 현실에서 깨지는 지점이며, 분산은 공짜에 가까운 상관 절단이다.

### 6. 무감시 운용 (SMART·용량·온도)
❌ "조용하니 정상" — 디스크는 보통 예고(재할당 섹터 증가)를 먼저 보내는데 아무도 안 들음
✅ 감시 3종 상시: **SMART 주기 점검**(재할당/펜딩 섹터 추세 — smartd 알림) + 풀 사용률(80% 경보 — ZFS는 만석 근처에서 성능 급락) + 온도. "신호 없으면 정상"이 아니라 "신호 수집이 정상"
**왜**: 재할당 섹터 증가 추세는 가장 신뢰도 높은 사망 예고다(Backblaze 통계) — 예고 단계 교체는 계획 작업, 사망 후 교체는 리빌드 도박이다. 감시의 ROI가 가장 높은 영역.

## 워크플로우 (스토리지 설계 1건)

1. **요구 표** — 용량(3년 성장 포함)·가용성(중단 허용?)·성능(순차/임의)·예산 — 이 표가 RAID 수준을 정한다.
2. **역할 분리 선언** — 이 풀의 가용성 설계(RAID)와 별개로 백업 경로(dev-backup-dr)를 같은 문서에 — 백업 없는 설계는 미완성.
3. **구매·구성** — CMR 확인·로트 분산 → 풀 구성은 명령 기록 보존(재구축 가능성).
4. **검증 (copy-paste)**:
   ```
   zpool status -v && zpool list               # 풀 상태·사용률
   zpool scrub tank && zpool status            # 첫 scrub
   smartctl -a /dev/sdX | grep -E "Reallocated|Pending|Power_On"
   systemctl list-timers | grep -E "scrub|smart"   # 감시 스케줄 등록 확인
   ```
5. **사망 리허설** — 디스크 1개 분리 후 교체·리실버 절차를 **평시에 1회**(처음이 실전이면 안 된다).
6. **산출물 저장** — 설계서·풀 구성 명령·디스크 시리얼/슬롯 매핑은 프로젝트 작업이면 그 프로젝트 `docs/`(설계 결정은 `docs/adr/NNNN-*.md` 번호 누적·append, 기존 파일 덮어쓰기 대신 Edit) / 프로젝트 밖이면 운영 위키(vault 규칙). **이 스킬 폴더에는 저장하지 않는다.** 풀 구성·시리얼 매핑은 재구축의 생명줄이라 휘발 금지(형식 세부는 dev-tech-writing).

### 판단 불가 시 — `[확인 필요]` 4요소

스토리지는 비가역 조작(풀 파괴·디스크 분리·교체)이 데이터 전체를 걸기 때문에, 디스크 정체·풀 상태가 불확실하면 추측 조치를 금지하고 4요소로 멈춘다(누가/언제/어떻게/기대값):

- **디스크 사망 의심**: "재할당/펜딩 섹터 추세인지·일시 오류인지를 / 디스크 교체·풀 조작 전에 / `smartctl -a /dev/sdX`의 Reallocated/Pending 추세 + `zpool status -v`로 / 추세 증가면 교체 대상, 0 유지면 케이블·컨트롤러 의심" — 단발 에러로 디스크 분리 단정 금지.
- **교체 대상 디스크 식별**: "물리적으로 어느 디스크를 뽑을지를 / 분리 전에 / 시리얼 대조(`smartctl -i`·디스크 LED 점멸)로 / 시리얼 일치 확인 후에만 분리" — GitLab류 "엉뚱한 대상 조작"의 스토리지판, 잘못 뽑으면 정상 디스크 탈락으로 리빌드 도박 진입.
- **SMR 여부 불명**: "이 모델이 CMR인지를 / 구매·풀 투입 전에 / 제조사 스펙시트 + 커뮤니티 DB(서브레딧 SMR 목록) 대조로 / CMR 확정이면 투입, 불명/SMR이면 RAID 풀 배제" — 확인 못 하면 `[확인 필요: 기록 방식 — 스펙시트 미확인]`로 남기고 아카이브 단독 용도로만 한정.

## 실전 케이스 — WD Red SMR 침묵 혼입 (2020): "NAS용"이라는 라벨의 배신 (공개 사태·집단소송)

WD가 NAS 라인업(Red)에 SMR 방식을 **표기 없이** 혼입 — 사용자들이 ZFS 리실버 실패·RAID 리빌드 탈락(타임아웃으로 어레이에서 축출)을 겪고 커뮤니티 조사로 발각. 집단소송·합의, 이후 제조사들이 CMR/SMR 표기를 명시하게 됐다. 교훈: ① "NAS용 라벨"이 아니라 **기록 방식 스펙**이 진실이다 — 구매 전 스펙시트 확인이 의무가 된 역사적 근거 ② 평시 벤치마크로는 안 보였다 — SMR의 절벽은 리빌드급 지속 쓰기에서만 드러난다(최악의 순간에만 보이는 결함) ③ 커뮤니티 집단 검증(Backblaze 통계·서브레딧 조사)이 제조사 마케팅보다 신뢰할 만한 데이터 소스다. 상세: `references/evidence.md`

## 한계

- 백업 전략(일정·세대·오프사이트·리허설)은 dev-backup-dr 본진 — 이 스킬은 "백업이 별도 필수"라는 선언까지.
- 분산 스토리지(Ceph·GlusterFS)·엔터프라이즈 SAN은 코어 범위 밖.
- 시놀로지 등 어플라이언스는 원리 동일·UI 상이 — 세부는 해당 공식 문서로.
- **확장 경로 갱신(OpenZFS 2.3, 2025-01)**: 이제 기존 RAIDZ vdev에 디스크 1개씩 추가하는 **RAIDZ 확장**이 정식 지원 — 과거 "RAIDZ는 vdev 통째 추가만"이라는 제약이 풀렸다. 단 ① 확장 후 기존 데이터의 패리티 비율은 즉시 최적화되지 않음(재기록 필요) ② 확장이 미러의 단순성·리빌드 속도 이점을 없애지는 않음 — 작성 예시의 "미러 vdev 추가 vs 디스크 교체 증설" 선택지에 "RAIDZ 단일 디스크 확장"이 3번째로 추가됨(확인 필요: 풀이 2.3+ 기능플래그인지). fast dedup(2.3)도 과거 dedup의 메모리 폭발 문제를 완화하나, 여전히 명확한 중복 패턴이 없으면 비권장 — 라벨만 갱신.
