# 테스트 설계 — 층별 책임·테스트 더블 분류·경계값 선정 (SKILL.md 비중복)

## 층별 책임 (피라미드의 실무 번역)

| 층 | 검증 대상 | 더블 사용 | 속도 목표 | 실패 시 알려주는 것 |
|---|---|---|---|---|
| 단위 | 순수 로직·분기·계산 | 경계만 (보통 0개) | ms 단위 | 어느 함수의 어느 분기 |
| 통합 | 협력 지점: 쿼리가 진짜 도는가, 핸들러가 모델을 지키는가 | 외부 서비스만 (DB는 진짜/컨테이너) | 초 단위 | 어느 경계의 계약 위반 |
| E2E | 핵심 사용자 여정 1~3개 | 없음 | 분 단위 | "사용자가 못 쓴다" |

- 역삼각형(E2E 위주)의 비용: 실패가 "어딘가 깨짐"만 알려줘 디버깅이 전수조사가 된다. 단위가 두꺼우면 실패 지점이 함수 단위로 좁혀진다.
- **통합 테스트에서 DB를 mock하지 않는 이유**: 쿼리 문법·트랜잭션·제약조건이 통합 테스트의 검증 대상 그 자체다. mock하면 "내 mock이 잘 도는지" 테스트가 된다(안티패턴 1의 통합판).

## 테스트 더블 5분류 (Meszaros) — 언제 무엇

| 더블 | 역할 | 쓰는 순간 |
|---|---|---|
| Dummy | 자리 채움(사용 안 됨) | 시그니처만 맞출 때 |
| Stub | 정해진 응답 반환 | 입력 경로 제어("API가 404를 주면") |
| Fake | 단순 실제 구현(인메모리 저장소) | 상태가 필요한 협력자 — mock 체인보다 명확 |
| Spy | 호출 기록 | **나가는** 부수효과 확인(메일 발송됐나) |
| Mock | 기대 호출 사전 선언+검증 | 거의 불필요 — Spy·결과 검증으로 대부분 대체 |

기본값: **Stub(들어오는 것) + Spy(나가는 것) + Fake(상태)**. "mock"이라는 말로 전부 뭉뚱그리지 않는다 — 분류가 곧 설계 판단.

## 무엇을 테스트하는가 — 선정 휴리스틱

1. **출력이 입력의 함수인 곳**(파싱·계산·변환)이 최우선 — 싸고 안정적이고 회귀 검출력 최대.
2. **버그가 났던 곳** — 수정 전에 그 버그를 재현하는 테스트부터(회귀 고정). ledger와 연동: 30분 삽질의 산출물은 테스트 1개여야 한다.
3. **분기 밀도 높은 곳** — if/예외 경로가 3개 이상 얽히면 parametrize 표로.
4. 테스트 안 하는 것도 결정: 프레임워크 자체 동작(FastAPI가 422를 주는지), 단순 위임, `__repr__` — "내 코드의 행동"이 아니면 제외.

## 경계값 선정법 (케이스 고르기)

- 수치: 0 · 1 · 최대 · 최대+1 · 음수(허용 안 되면 그 거부를) — 전부가 아니라 **분기가 갈리는 값**만.
- 컬렉션: 빈 것 · 1개 · 여러 개(보통 3) — "여러 개"가 2와 100으로 행동이 같으면 3 하나로 충분.
- 문자열: 빈 문자열 · 공백만 · 유니코드(한글!) · 매우 긴 것(상한 있다면 그 경계).
- 시간: 자정 경계 · 월말/연말 · DST(KST는 없음 — 해외 데이터 다룰 때만) · naive/aware 혼입.
- 외부 응답: 정상 · 타임아웃 · 5xx · **형식은 맞는데 의미가 이상한 것**(가격 0원, 음수 거래량) — 마지막이 수집기에서 제일 비싼 버그.

## AAA와 가독성

```python
def test_normalize_rejects_naive_timestamp():
    raw = make_raw_tick(ts=datetime(2026, 6, 1, 9, 0))   # Arrange: naive

    with pytest.raises(ValueError, match="aware"):        # Act+Assert: 예외 경로는 결합 허용
        normalize_tick(raw)
```

- 단언 메시지가 불친절한 동등 비교는 헬퍼보다 **dataclass 비교**(전체 diff가 찍힘)나 `pytest.approx`(부동소수점)로.
- 테스트가 길어지면(15줄+) 준비를 fixture/팩토리로 — 단, 단언까지 숨기지는 않는다(무엇을 검증하는지는 테스트 본문에).
