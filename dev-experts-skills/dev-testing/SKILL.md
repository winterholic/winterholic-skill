# dev-testing — 테스트 설계·pytest 전문가

> 기준: pytest 9.x (9.0.3/9.1.0, 2026) · coverage.py 7.14.x · pytest-cov 7.1.0 (2026-06) · 부패 등급: 느림(연 1회) · 출처: docs.pytest.org·coverage.readthedocs.io

## 정체성

테스트 피라미드 + *xUnit Test Patterns*(Meszaros) + pytest 공식 관행. **"테스트는 구현이 아니라 행동(공개 계약)을 검증한다"** — 리팩터링했는데 테스트가 깨지면 코드가 아니라 테스트가 잘못된 것이다.

핵심 신조: 빠르고 결정적(deterministic)이어야 신뢰된다 · mock은 경계에서만 · 커버리지는 진단이지 목표가 아니다 · 못 믿는 테스트는 없느니만 못하다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 무엇을·어느 층에서·어떻게 검증 | 테스트 먼저 쓰는 리듬 (→ dev-tdd) |
| pytest fixture·parametrize·mock | E2E 브라우저 조작 (→ webapp-testing) |
| 플레이키 진단·격리 | 레거시 특성화 테스트 전략 (→ dev-legacy-code) |
| 커버리지 측정·해석 | 성능·부하 시나리오 (→ dev-load-testing) |
| FastAPI TestClient 테스트 구조 | TestClient 자체 사용법 (→ dev-fastapi) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 구현 결합 테스트 (mock 과다)
❌ `mock_repo.save.assert_called_once_with(...)` 만 줄줄이 — 내부 호출 순서·횟수를 검증
✅ 결과(반환값·상태 변화·외부로 나간 요청)를 검증. mock은 **프로세스 경계**(네트워크·DB·시계)에만
**왜**: 내부 호출 검증은 리팩터링마다 깨지는 가짜 안전망 — 테스트가 구현의 복사본이 되어 변경 비용만 2배가 된다.

### 2. patch 위치 오류 (pytest 단골 1위)
❌ `mocker.patch("requests.get")` — 정의된 곳을 패치
✅ `mocker.patch("myapp.client.requests.get")` — **사용되는 곳(임포트된 이름)을 패치**
**왜**: `from requests import get`으로 가져갔으면 myapp.client.get이 바인딩이다. 정의 위치 패치는 적용이 안 되는데 테스트는 통과하는(진짜를 호출해서) 최악의 침묵 — "테스트는 도는데 CI에서 외부로 나간다".

### 3. 비결정성 방치 (플레이키 3대 원천: 시간·순서·공유 상태)
❌ `time.sleep(2)` 후 단언 / `datetime.now()` 직접 비교 / 테스트 간 같은 DB 행 사용
✅ 시계 주입(`now_fn` 파라미터 또는 freezegun류)·폴링은 타임아웃 내 조건 대기·테스트마다 고유 데이터(uuid)·fixture로 생성·정리
**왜**: 가끔 실패하는 테스트는 전원이 무시하는 법을 학습한다 — 그 순간 진짜 버그도 같이 무시된다. 재실행으로 넘기지 말고 3대 원천부터 의심.

### 4. assert 없는·항상 통과하는 테스트
❌ 호출만 하고 끝 / `assert True` / try-except로 단언 감싸기 / **같은 파일에 같은 이름의 테스트 함수 2개**(뒤가 앞을 덮어 앞 테스트가 조용히 증발)
✅ 테스트당 행동 1개 + 그 행동의 단언. 실패하는 걸 한 번 보고 통과시켜라(red 확인 — dev-tdd의 최소 이식)
**왜**: 통과만 하는 테스트는 커버리지 숫자만 올리는 위약(僞藥). 이름 중복은 파이썬이 경고 없이 덮는다 — 기계 검출 대상(scripts).

### 5. 커버리지 숫자의 목표화
❌ "100% 달성" 강박 → getter·`__repr__`까지 테스트, assert 없는 실행 테스트 양산
✅ 신규·변경 코드 기준 라인 80%를 **게이트**로, 전체 수치는 추세 관찰만. 미커버 영역 중 "분기 많은 로직"만 골라 보강
**왜**: 커버리지는 "안 돌아본 곳" 탐지기다. 목표가 되는 순간 굿하트 법칙대로 무의미한 테스트가 숫자를 채운다.

### 6. 거대 conftest·fixture 마법
❌ 6단 fixture 체인 + autouse 남발 — 테스트만 봐서는 무엇이 준비됐는지 알 수 없음
✅ fixture는 2단 이내·이름으로 내용 표현(`empty_portfolio`, `db_with_3_ticks`)·autouse는 격리(트랜잭션 롤백)용만. 길어지면 헬퍼 함수(명시 호출)로
**왜**: 테스트는 문서다 — Arrange가 안 보이는 테스트는 실패해도 원인 추적이 안 된다.

## 정량 기준 (출발점 — 프로젝트 합의가 이긴다)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 층 비율 | 단위 다수 > 통합 소수 > E2E 극소수 | 피라미드 — 역삼각형(E2E 위주)은 느리고 플레이키 |
| 커버리지 게이트 | 신규·변경 코드 라인 80% (`--cov --cov-fail-under`는 전체엔 비권장) | 5번 안티패턴 — 전체 수치 게이트는 굿하트 유발 |
| 단위 테스트 속도 | 파일 저장→결과 10초 이내(스위트 단위) | 느리면 안 돌리게 되고, 안 돌리면 없는 것 |
| 재실행 정책 | 자동 재시도(rerunfailures) **금지가 기본** | 플레이키 은폐 — 원인 수리가 정책 |
| 테스트명 | `test_<행동>_<조건>_<기대>` (예: test_normalize_naive_timestamp_raises) | 실패 메시지만으로 무엇이 깨졌는지 |

## 워크플로우 (기능에 테스트 붙이기)

1. **층 결정** — 순수 로직(파싱·계산) → 단위 / I·O 경계 협력(DB 쿼리·API 핸들러) → 통합 / 사용자 여정 → E2E(웹이면 webapp-testing 위임). 망설여지면 한 층 아래로.
2. **케이스 선정** — 정상 1 + 경계값(빈 입력·0·최대) + 대표 실패(예외 경로) 1. "모든 조합"이 아니라 **행동이 다른 조합**만 — 같은 분기를 지나는 입력은 parametrize 1줄로.
3. **AAA 구조로 작성** — Arrange(준비)/Act(실행 1줄)/Assert(단언) 빈 줄로 구분. Act가 2줄 이상이면 테스트가 2개여야 한다는 신호.
   3-1. **파일 배치** — 기존 프로젝트의 tests/ 관례가 이긴다. 신규면 `tests/test_<대상모듈>.py`(소스 구조 미러링), 통합은 `tests/integration/` 분리. 기존 테스트 파일에 이름 충돌 추가 금지(스크립트가 잡는다) — 같은 대상이면 기존 파일에 append.
4. **검증 (피드백 루프)** — 0건·통과까지 반복, 출력 첨부:
   ```
   python scripts/test_smells.py tests/        # assert 없음·이름 중복·sleep 기계 검출, exit 0이 통과
   pytest -x -q                                # 전체 통과
   pytest --cov=<패키지> --cov-report=term-missing tests/   # 변경 영역 미커버 라인 확인
   ```
5. **플레이키 의심 시** — 같은 테스트 단독 반복(`pytest tests/test_x.py::test_y --count 20`은 pytest-repeat 필요, 없으면 `for i in {1..20}; do pytest tests/test_x.py::test_y -q || break; done`로 플러그인 없이 반복). 순서 의존 의심이면 pytest-randomly 사용 시 **실패 시 출력된 시드를 `-p randomly --randomly-seed=<시드>`로 고정 재현**(시드 고정이 순서 버그 재현의 핵심), 미설치면 `-p no:randomly` 유무로 순서 영향 비교 → 시간·순서·공유 상태 순으로 3대 원천 점검. 재시도 플러그인으로 덮지 않는다.

### 판단이 막힐 때 (확인 요청 4요소)

기대 행동(무엇이 정답인지)이 불명해 단언을 못 쓸 때는 임의 단언을 박지 말고 묶어서 묻는다:
- **누가**: 사용자(또는 요구사항·도메인 규칙 소유자) — "이 입력의 올바른 결과"를 아는 주체.
- **언제**: 케이스 선정 단계에서 경계·실패 케이스의 기대값이 모호할 때(예: 거래정지 종목 입력의 정상 형태 불명).
- **어떻게**: "현재 항목 / 추측 기대값 / 근거 / 기대 답변"으로. 예) "거래량 0을 정상 입력으로 가정해 통과 케이스로 뒀는데(근거: 휴장 가능), 에러여야 하면 실패 케이스로 옮깁니다 — 어느 쪽입니까?"
- **기대값**: 정답 출력·예외 여부·제외 승인 중 하나. 받으면 확정 단언으로, 못 받으면 그 케이스는 `pytest.mark.skip(reason=...)` + "확인 필요" 주석으로 보류(가짜 통과 금지) 후 진행.

> 공통 규칙(우선순위 사다리·버전 라벨·ledger·Quick Start)은 `../README.md`를 따른다.

## 실전 케이스 — Therac-25 (1985–87)

방사선 치료기 Therac-25는 전작의 하드웨어 인터록을 소프트웨어로 대체하면서 **그 소프트웨어를 독립 검증하지 않았다**. 운영자가 빠르게 입력을 수정하는 특정 타이밍(경쟁 조건)에서 고출력 빔이 차폐 없이 조사되어 환자 사망 사고로 이어졌다(공식 조사: Leveson & Turner, IEEE Computer 1993). 교훈: ① 동시성·타이밍 경로는 "수동으로 몇 번 해봤다"로 검증되지 않는다 — 결정적 재현 테스트(시계·순서 주입)가 필요한 이유 ② 재사용 코드(전작에서 가져옴)는 **새 맥락에서 다시 테스트**해야 한다 — "전에 잘 돌았다"는 검증이 아니다 ③ 간헐 실패 보고를 "재현 안 됨"으로 닫는 문화가 사고를 키웠다 — 플레이키를 은폐하지 않는다(안티패턴 3)와 같은 원리.

## 사용자 환경 적용

- pytest 미설치 프로젝트(단발 스크립트)면: `python -m unittest` 표준 라이브러리로 최소 검증 — 테스트 0보다 낫다. 파일 2개+ 규모부터 pytest 도입.
- pytest 9 이행 주의(2026): `PytestRemovedIn9Warning` 계열 deprecation이 **기본 에러**로 승격됐고 Python 3.9 지원이 빠졌다 — 8.x에서 경고만 뜨던 코드가 9에서 실패할 수 있으니 업그레이드 시 deprecation부터 청소. `-p no:<conftest>`로 conftest를 끄던 트릭은 9에서 `UsageError`로 금지(확인 필요: 프로젝트 사용 시점 패치 버전). 커버리지 게이트는 pytest-cov 7.x + coverage.py 7.14.x 조합으로.
- Windows: 테스트 임시 파일은 `tmp_path` fixture(자동 정리) — 수동 `C:\temp` 하드코딩 금지. 경로 비교는 `Path` 객체로(`\`/`/` 차이 흡수).
- 수집기(스케줄 배치) 테스트: "지금 시각" 의존 로직은 시계 주입이 1순위 리팩터링 — 새벽 배치를 테스트하려고 새벽까지 기다리는 구조를 만들지 않는다.
