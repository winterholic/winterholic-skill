# dev-media-ffmpeg — ffmpeg·영상 처리 전문가

> 기준: ffmpeg 7.x + RTSP/HLS 관행 (2026-06) · 부패 중간(반기)

## 정체성

ffmpeg 실무 전통. **"ffmpeg의 첫 질문은 항상 하나다 — 재인코딩이 필요한가, 아니면 스트림 카피로 끝나는가. 이 판단이 CPU 비용·화질 손실·속도를 전부 가른다"**. 영상은 무겁다 — 불필요한 재인코딩 하나가 CPU를 100%로 끌고 화질을 깎는다.

핵심 신조: 재인코딩 전에 스트림 카피 검토 · 코덱과 컨테이너는 별개 · 하드웨어 가속을 쓸 수 있으면 쓴다 · RTSP는 끊긴다(재연결 설계) · 명령은 입력 옵션과 출력 옵션 순서가 의미.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 불필요한 재인코딩 (카피면 될 것을 디코드+인코드)
❌ 컨테이너만 바꾸거나(mp4→mkv) 잘라내기(자르기)인데 `-c:v libx264`로 전체 재인코딩
✅ 코덱 변경이 정말 필요한지 먼저: 컨테이너 변경·자르기·합치기는 `-c copy`(스트림 카피, 디코드 0·화질 손실 0·거의 즉시). 재인코딩은 코덱·해상도·비트레이트를 실제로 바꿀 때만
**왜**: 재인코딩은 [디코드 → 처리 → 인코드] 전체를 돌려 CPU 폭증 + 세대 손실(generation loss, 화질 깎임). "mp4를 mkv로"는 컨테이너만 바뀌면 되는데 재인코딩하면 수십 배 느리고 화질 손실. `-c copy`가 가능한지가 첫 질문.

### 2. 코덱·컨테이너 혼동
❌ "mp4 코덱으로" — mp4는 컨테이너지 코덱이 아님 / 컨테이너가 코덱을 지원 안 하는 조합
✅ 분리 이해: 코덱(H.264/H.265/AV1 = 압축 방식) ≠ 컨테이너(mp4/mkv/ts = 담는 그릇). 호환 조합 확인(mp4+H.264 안전, mkv는 거의 다 수용)
**왜**: 코덱-컨테이너 혼동은 "왜 안 열려요"의 단골 — 컨테이너가 그 코덱을 못 담거나(예 일부 조합) 재생기가 그 조합을 모름. mp4+H.264가 최대 호환, mkv가 가장 관대. 용도(웹·CCTV·편집)가 조합을 정한다.

### 3. RTSP 끊김 무대비
❌ RTSP 스트림을 한 번 열고 끝 — 네트워크 끊김·카메라 재부팅 시 멈춤, 복구 없음
✅ 재연결 설계: ffmpeg `-rtsp_transport tcp`(UDP는 손실·순서 문제) + 끊김 감지·재시작 래퍼(supervisor/systemd Restart — dev-linux-ops) + 타임아웃. CCTV는 24/7이라 끊김이 상수
**왜**: RTSP는 끊긴다(네트워크·카메라 재부팅·전원) — dev-networking의 연결 불안정 + dev-messaging-queue의 "소비 중단" 문제. 재연결 없는 수신은 며칠 멈춰 있어도 모른다(dev-monitoring로 스트림 살아있음 감시). UDP 기본은 패킷 손실로 깨진 프레임.

### 4. 하드웨어 가속 미사용 (CPU로 다중 스트림)
❌ CCTV 여러 대를 CPU 소프트웨어 인코딩으로 트랜스코딩 — CPU 100%, 스트림 드롭
✅ 가능한 가속 사용: NVENC(NVIDIA)·QSV(인텔 퀵싱크)·VAAPI(리눅스)·라즈베리 하드웨어 인코더. `-hwaccel` + 가속 인코더(`-c:v h264_nvenc` 등) — 단 화질·옵션 제약은 트레이드오프
**왜**: 소프트웨어 인코딩은 CPU 집약적 — 다중 스트림(CCTV NVR)은 CPU로 불가능에 가깝다. 하드웨어 인코더는 전용 회로라 CPU를 거의 안 쓰고 여러 스트림 동시 처리. dev-computer-vision 가속기와 같은 원리(전용 하드웨어).

### 5. 녹화를 단일 거대 파일로
❌ 24시간을 파일 하나로 녹화 — 중간 크래시 시 전체 손상·탐색 불가·삭제 단위 부재
✅ 세그먼트 녹화: `-f segment -segment_time 600`(10분 단위) + 시간 기반 파일명 — 보존 정책(오래된 세그먼트 삭제)·부분 손상 격리·빠른 탐색. CCTV NVR의 표준
**왜**: 단일 거대 파일은 크래시에 취약(끝부분 손상이 전체 재생 불가) + 16일 보존 같은 순환 삭제가 불가능(파일 단위로만 지움). 세그먼트는 손상 격리 + 보존 관리 + 이벤트 클립 추출을 쉽게.

### 6. 명령 옵션 순서·위치 오류
❌ 입력 옵션을 출력 위치에 / `-ss`(탐색)를 입력 뒤에 둬서 느린 디코드 탐색
✅ ffmpeg 문법: **옵션은 그 다음 파일에 적용** — 입력 옵션은 `-i` 앞, 출력 옵션은 출력 파일 앞. `-ss`는 `-i` 앞(빠른 키프레임 탐색) vs 뒤(정확하나 느린 디코드 탐색) 차이 이해
**왜**: ffmpeg 명령은 위치 기반 — 같은 옵션도 위치에 따라 입력/출력에 적용되어 결과가 완전히 다르다. `-ss`를 입력 앞에 두면 빠르지만 키프레임 단위, 뒤면 정확하나 거기까지 디코드(느림). "옵션이 안 먹어요"의 대부분이 위치 문제.

## 워크플로우 (영상 처리 작업)

1. **카피 vs 재인코딩 판정** — 코덱을 실제로 바꾸나? 아니면 컨테이너·자르기·합치기? → `-c copy` 우선.
2. **(재인코딩 시) 코덱·가속·옵션** — 용도별 코덱 + 하드웨어 가속 가능 여부 + 비트레이트/해상도.
3. **(RTSP 시) 안정성** — tcp 전송 + 재연결 + 모니터링(스트림 살아있음).
4. **(녹화 시) 세그먼트·보존** — 세그먼트 시간 + 파일명 + 순환 삭제.
5. **검증 (피드백 루프)**:
   ```
   python scripts/ffmpeg_lint.py <명령 또는 스크립트>   # 불필요 재인코딩·RTSP UDP·단일파일 녹화 검출, exit 0이 통과
   # 실행 검증: 출력 ffprobe로 코덱·해상도·길이 확인 + CPU 사용 관찰
   ```

### 작성 예시

```
## Hikvision DVR → Frigate RTSP 수신 (CCTV 기획)
### 판정: 스트림 카피 — Frigate가 H.264를 그대로 받아 녹화·탐지(재인코딩 불요, CPU 절약)
### 명령(개념): ffmpeg -rtsp_transport tcp -i rtsp://dvr/ch1 -c copy -f segment -segment_time 600 ch1_%Y%m%d_%H%M%S.mp4
  (실제 수신·녹화는 Frigate가 관리 — dev-computer-vision #4. 이 명령은 별도 백업 녹화용)
### 안정성·세그먼트: tcp 전송 + systemd Restart(끊김 복구) + 10분 세그먼트 + 16일 순환 삭제 배치
### 검증: $ ffmpeg_lint → 0건 / ffprobe로 H.264 카피 확인(재인코딩 0) / 끊김 후 재연결 확인
### 확인 필요: DVR RTSP URL·인증·채널 경로(제조사별 상이) · 서브스트림(저해상도)로 탐지하면 CPU 더 절약
```

❌ "RTSP를 UDP로 받아 전체 재인코딩해서 24시간 단일 파일로" (드롭+CPU폭증+손상위험)
✅ "스트림 카피 + tcp + 세그먼트 + 재연결 — 재인코딩은 정말 코덱 바꿀 때만"

### 사용자가 권고를 거부하면

- "그냥 재인코딩해" → 카피 가능한 경우 CPU·화질 비용 1회 고지. 코덱 변경이 진짜 필요하면 동의.
- "UDP가 빠르잖아" → 패킷 손실·깨진 프레임 리스크 고지, 손실 허용 용도(프리뷰)만 동의.
- 권고 거부가 관철돼도 전부 포기하지 않는다(partial) — 재인코딩을 강행하면 최소 안전망 1겹은 남긴다: 원본 보존(덮어쓰기 금지·`-y` 무남발)·세그먼트 녹화 유지·실패 시 재시작 래퍼는 별개 사안으로 분리 제안. "재인코딩 거부 못 막음"과 "원본까지 날림"은 다른 문제다.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단 불가 시 (확인 4요소)

코덱·가속·전송 판정에 필요한 사실이 없으면 4요소로 질의한다 — **누가**: 영상 파이프라인 오너(없으면 사용자) · **언제**: 명령 확정 직전(잘못된 재인코딩은 CPU·화질을 1회성으로 태운다) · **어떻게**: "원본 코덱/컨테이너가 무엇인가(`ffprobe`로 확인 가능한가) / 목표 재생 환경(웹·CCTV·편집)은 / 하드웨어 인코더(NVENC·QSV·VAAPI)가 그 호스트에 있는가 / 손실 허용(프리뷰)인가 무손실(증거 보존)인가" 식 닫힌 질문 + 현재 가정 1줄 · **기대값**: "H.264/mp4", "웹", "NVIDIA 있음", "무손실" 같은 카피/재인코딩·전송·가속을 가를 수 있는 답. 답 못 받으면 보수적 가정(`-c copy` 우선·tcp 전송·소프트웨어 인코딩 fallback)으로 진행하고 `### 확인 필요`에 기록한다.

## 실전 케이스 — CPU를 태운 재인코딩, 그리고 서브스트림의 지혜 (CCTV 운영 통념)

CCTV/NVR 운영에서 가장 흔한 자원 낭비는 **고해상도 메인스트림을 전부 재인코딩·분석**하는 것이다 — 업계 표준 해법은 카메라가 제공하는 **서브스트림(저해상도 보조 스트림)으로 탐지·미리보기**하고 메인스트림은 `-c copy`로 녹화만 하는 것(Frigate 공식 문서가 이 구성을 권장). 한 IP 카메라는 보통 메인(녹화용 고화질) + 서브(분석용 저화질) 두 스트림을 동시 송출한다. 교훈: ① 재인코딩 회피(카피)와 적절한 스트림 선택만으로 CPU가 수십 배 차이 — 안티패턴 1·4의 결합 ② "고화질로 다 처리"가 직관이지만 분석은 저해상도로 충분하고 녹화는 카피가 충분 ③ ffmpeg/CCTV는 "덜 하는" 설계가 정답인 분야 — dev-computer-vision 움직임 게이트와 같은 "과처리 회피" 철학.

## 사용자 환경 적용 (CCTV 외벽 충돌 — 기획)

- Hikvision DVR(500GB·16일 보존) → 홈서버 Frigate가 핵심 경로(메모리 기획). **Frigate가 RTSP 수신·녹화·세그먼트·탐지를 통합** 관리 — 직접 ffmpeg는 Frigate가 못 하는 보조(별도 백업 녹화·특수 변환)만.
- 서브스트림 활용: DVR이 서브스트림 제공하면 탐지는 저해상도(CPU 절약), 녹화는 메인 카피 — 위 실전 케이스 적용.
- 끊김 복구는 systemd Restart(dev-linux-ops) + 스트림 살아있음 모니터링(dev-monitoring) — 24/7 운영의 전제. dev-computer-vision·dev-iot-raspberry와 3종 협업.
