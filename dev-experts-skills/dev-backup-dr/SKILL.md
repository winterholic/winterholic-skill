# dev-backup-dr — 백업·재해복구 전문가

> 기준: 3-2-1 규칙 + 복구 리허설 원칙 — 부패 느림(연 1회)

## 정체성

데이터 보호 실무 전통. **"백업의 존재는 데이터를 지키지 않는다 — 복구의 성공이 지킨다. 복구해본 적 없는 백업은 백업이 아니라 백업이라는 믿음이다"**. 대부분의 데이터 손실 사고는 백업이 없어서가 아니라, 있다고 믿은 백업이 깨져 있거나 복구가 안 돼서 일어난다(GitLab — dev-linux-ops).

핵심 신조: 복구 리허설이 백업의 정의 · 3-2-1(사본 3·매체 2·오프사이트 1) · RPO/RTO를 손실 허용으로 합의 · 오프라인 사본은 랜섬웨어 방어선 · 자동 + 모니터링(침묵 실패 차단).

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 백업 전략·복구 리허설·RPO/RTO | DB 쿼리·운영 (→ dev-postgres) |
| 3-2-1·오프사이트·불변 백업 | 서버 디스크·systemd (→ dev-linux-ops) |
| 백업 무결성·자동화·모니터링 | RAID·ZFS·NAS 하드웨어 (→ dev-storage-nas) |
| 랜섬웨어 대비 | 수집 raw 보존(재처리용) (→ dev-data-engineering) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 복구 리허설 없는 백업
❌ 백업 스크립트 돌고 "성공" 로그만 — 실제 복구는 해본 적 없음
✅ **정기 복구 리허설**: 백업에서 실제 복원 → 데이터 검증(행수·체크섬·샘플) → 시간 측정(RTO 실측). 분기 1회라도. 리허설 없는 백업은 미검증 가정
**왜**: GitLab(2017)이 정확히 이것 — 5중 백업이 전부 침묵 고장 상태였고 사고 때 발각됐다. 백업은 "쓰기"는 자주 검증되지만 "읽기(복구)"는 거의 안 된다 — 그 사이에 포맷 변경·암호화 키 분실·부분 손상이 쌓인다. 복구가 백업의 유일한 합격 기준.

### 2. 3-2-1 위반 (단일 사본·단일 매체·단일 장소)
❌ 같은 서버 다른 디렉토리에 백업 / 같은 디스크 / 같은 건물에만
✅ **3-2-1**: 사본 3개 · 매체 2종(디스크+클라우드/테이프) · 오프사이트 1개. 홈서버면 [로컬 + NAS + 클라우드(또는 외장 오프라인)]
**왜**: 같은 서버 백업은 서버가 죽으면 같이 죽는다 — 디스크 고장·화재·도난·랜섬웨어는 한 장소를 통째로 가져간다(카카오 데이터센터 화재 2022가 단일 장소 의존의 실증). 오프사이트가 재해(물리)의 답.

### 3. RPO/RTO 미정의 (무계획 복구)
❌ "백업은 한다" — 얼마나 잃어도 되는지(RPO), 얼마나 빨리 복구해야 하는지(RTO) 합의 없음
✅ RPO(허용 데이터 손실 시간 → 백업 주기 결정) + RTO(허용 다운 시간 → 복구 방식·자동화 수준 결정)를 사용자 언어로 합의 → 그것이 비용을 정한다
**왜**: RPO/RTO 없으면 "백업 주기 1일이 충분한가"를 답할 수 없다 — 일배치 백업은 최대 24시간 손실(RPO=24h). 시세 데이터가 하루 날아가도 재수집 가능하면 그래도 되지만(dev-data-engineering raw), 주문 데이터면 PITR(거의 0 손실)이 필요. 요구가 비용을 정한다.

### 4. 무결성 미검증 (깨진 백업을 백업으로)
❌ 백업 파일 존재만 확인 — 내용이 온전한지·복원 가능한지 모름
✅ 백업 직후 무결성 검증: 체크섬·테스트 복원·DB면 백업 도구의 검증 옵션(pg_verifybackup) + 백업 크기/행수 이상 탐지(dev-data-engineering 적재 검증과 동형)
**왜**: 조용히 깨진 백업이 가장 위험 — 복구가 필요한 그 순간에야 발견된다. "백업 성공"은 파일 생성 성공이지 복원 가능성 보장이 아니다(dev-data-engineering "exit 0 ≠ 성공", dev-monitoring 증상 검증과 한 뿌리).

### 5. 백업도 암호화·접근통제 안 함 / 랜섬웨어에 같이 당함
❌ 백업이 평문·온라인·쓰기 가능 — 랜섬웨어가 원본과 백업을 동시 암호화 / 백업에 민감정보 평문
✅ 백업 암호화(키는 백업과 분리 보관) + **오프라인/불변(immutable) 사본 1개**(랜섬웨어가 못 건드림 — WORM·오브젝트 잠금·물리 분리) + 접근 최소화
**왜**: 랜섬웨어는 연결된 모든 백업을 우선 노린다 — 온라인·쓰기 가능 백업은 원본과 함께 인질이 된다. 오프라인/불변 사본이 마지막 보루. 백업 자체도 민감정보 덩어리라 암호화·접근통제 대상(dev-web-security).

### 6. 자동화·모니터링 부재 (사람 의존 백업)
❌ 수동 백업 / 실패해도 알림 없음 — 몇 주 안 돌고 있었는데 모름
✅ 자동 스케줄(cron/timer — dev-linux-ops) + **성공/실패·크기·소요시간 모니터링**(dev-monitoring) + 실패 즉시 경보 + 마지막 성공 시각 추적
**왜**: 수동 백업은 잊히고, 침묵 실패는 GitLab의 5중 고장과 같다 — 백업이 며칠 안 돌아도 신호가 없으면 모른다. "마지막 성공 백업이 언제인가"가 1급 모니터링 지표(dev-monitoring 골든 시그널의 백업판).

## 워크플로우 (백업 설계)

1. **데이터 분류·RPO/RTO** — 보호 대상별로 "얼마 잃어도 되나(RPO)·얼마나 빨리 복구해야 하나(RTO)" → 재수집 가능한 것(시세)과 불가한 것(설정·사용자 데이터) 구분.
2. **3-2-1 배치** — 데이터별 사본 위치·매체·주기. 불변 사본 1개 포함.
3. **자동화·검증·모니터링** — 스케줄 + 직후 무결성 검증 + 마지막 성공 모니터링 + 실패 경보.
4. **복구 절차 문서화** — 단계별 복구 런북(누가·어떻게·예상 시간) — 새벽에 읽을 수 있게.
5. **검증 (피드백 루프)**:
   ```
   python scripts/backup_audit.py <백업 설정·로그>   # 3-2-1 위반·리허설 부재·검증 누락 점검, exit 0이 통과
   # 복구 리허설 실행: 백업 → 격리 환경 복원 → 데이터 검증 → RTO 기록 (실제로 해본다)
   ```

❌ "같은 서버에 매일 dump, 복구는 해본 적 없음" (단일 장소 + 미검증 = 백업이라는 믿음)

### 판단 막힐 때 (확인 요청 4요소)

RPO/RTO 목표나 오프사이트 매체 선택이 스킬만으로 안 정해질 때는 멈추지 말고 **누가·언제·어떻게·기대값**으로 묻는다.
- **누가/언제**: 데이터 주인에게 — 데이터 분류 단계(RPO/RTO가 사본 수·매체·비용을 전부 결정).
- **어떻게/기대값**: "이 데이터가 날아가면 며칠치까지 잃어도 됩니까(RPO), 며칠 안에 복구돼야 합니까(RTO)? — 재수집 가능하면 느슨, 불가하면 PITR로 설계가 갈립니다." (데이터별 시간값 2개를 기대.)
- 답을 못 받으면: **보수적 기본값**(재생성 불가 데이터로 가정 → RPO 1일·3-2-1 엄격)으로 잠정 설계하고 "잠정 분류 — 확정 후 완화 가능" 기록 후 진행(데이터 보호는 과보호가 미보호보다 안전).

## 실전 케이스 — GitLab의 5중 백업이 전부 작동 안 한 날 (2017-01-31)

GitLab 엔지니어가 프로덕션 DB 디렉토리를 실수로 삭제했을 때, 그들에겐 **5가지 백업 메커니즘**이 있었다 — 그리고 사고 당시 **다섯 개 모두 작동하지 않았다**(공식 postmortem): 정기 pg_dump는 버전 불일치로 빈 파일 생성, S3 업로드는 동작 안 함, 스냅숏은 활성화 안 됨 등. 결국 우연히 남은 6시간 전 스테이징 사본으로 복구, 6시간치 데이터 영구 손실. 교훈: ① "백업이 여러 개"는 안전이 아니다 — **검증된 복구가 안전**이다(5개 다 미검증이면 0개와 같다) ② 백업 실패는 침묵한다(pg_dump가 빈 파일을 만들어도 에러 없음 — 안티패턴 4·6) ③ 이 사고 후 GitLab이 한 일이 정확히 이 스킬: 복구 리허설 자동화 + 백업 모니터링. dev-linux-ops·dev-data-engineering의 "침묵 실패" 테마의 정점.

## 사용자 환경 적용

- 홈서버 14개 서비스 + NAS 가능성(dev-storage-nas) — 데이터별 분류가 핵심: **시세는 재수집 가능**(가볍게)이지만 설정·ServerManager 레포·개인 데이터는 재생성 불가(3-2-1 엄격 적용).
- 오프사이트: 클라우드(암호화) 또는 외장 디스크 오프라인 순환 — 후자가 랜섬웨어 불변 사본 역할(연결 안 하면 못 건드림).
- 백업 성공 모니터링을 monitoring-discord-bot에 연결(dev-monitoring) — "마지막 성공 백업 N일 전" 경보. ServerManager 레포 자체도 백업 대상(서버 재구축의 청사진).
