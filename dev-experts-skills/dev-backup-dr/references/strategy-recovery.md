# 전략·복구 — RPO/RTO·DB 백업 3형·리허설·불변·런북 (SKILL.md 비중복)

## RPO/RTO 산정

```
RPO (Recovery Point Objective): 허용 데이터 손실 = "언제로 돌아가도 되나" -> 백업 주기 결정
  일배치 백업 -> RPO 최대 24h / 시간당 -> 1h / PITR(WAL) -> 초~분
RTO (Recovery Time Objective): 허용 다운 시간 = "얼마나 빨리 복구" -> 복구 방식·자동화 결정
  수동 복원 -> 시간 단위 / 대기 복제본 -> 분 단위 / 핫 스탠바이 -> 초
```

- 비용은 RPO·RTO에 반비례 — 0에 가까울수록 비싸다. 데이터별로 다르게: 시세(재수집 가능)는 느슨, 주문·사용자 데이터는 빡빡.
- "RPO 0"(무손실)은 동기 복제 비용 — 대부분 "몇 분 손실 허용"이 현실적. 합의가 핵심.

## DB 백업 3형 (PostgreSQL 어휘)

| 형 | 방식 | RPO | 복구 속도 | 용도 |
|---|---|---|---|---|
| 논리(pg_dump) | SQL/아카이브 덤프 | 백업 시점 | 느림(재실행) | 소규모·이식·버전 이동 |
| 물리(pg_basebackup) | 데이터 디렉토리 사본 | 백업 시점 | 빠름 | 대용량·전체 복원 |
| PITR | 물리 베이스 + WAL 아카이브 | 초~분(임의 시점) | 중간 | 손실 최소화 필요(주문류) |

- 검증: pg_dump는 **테스트 복원**이 유일한 검증(파일 존재≠유효 — GitLab의 빈 dump), 물리는 `pg_verifybackup`.
- 소규모 기본: 논리 백업(pg_dump)로 시작, 손실 민감 데이터만 PITR(WAL 아카이빙 — dev-postgres 협업).
- 백업 중 일관성: pg_dump는 단일 트랜잭션 스냅숏(일관성 보장), 파일 직접 복사는 멈추거나 스냅숏 도구 필요.

## 복구 리허설 절차 (백업의 합격 시험)

```
1. 최신 백업을 격리 환경(별도 컨테이너/서버 — dev-docker)에 복원
2. 데이터 검증: 행수·체크섬·핵심 테이블 샘플 쿼리 (dev-data-engineering 적재 검증 재사용)
3. 애플리케이션 기동 시도(복원 데이터로 서비스가 뜨나)
4. RTO 측정: 시작~서비스 가능까지 실제 시간 기록
5. 발견한 문제(누락 의존·키·순서)를 런북에 반영
```

- 분기 1회 최소 — "성공한 적 있는 복구"만 신뢰. 자동화하면(CI에서 정기 복원 테스트) 침묵 고장이 즉시 드러난다.
- 리허설이 드러내는 것: 백업에 빠진 것(파일·시크릿·스키마), 복구 순서 의존, 예상보다 긴 RTO.

## 불변(immutable) 백업 — 랜섬웨어 방어

| 방식 | 구현 |
|---|---|
| 오프라인 순환 | 외장 디스크에 백업 후 **분리**(연결 안 하면 못 건드림) — 가장 단순·확실 |
| 오브젝트 잠금 | S3 Object Lock·WORM(보존 기간 내 삭제·변경 불가) |
| append-only 자격증명 | 백업 대상 저장소에 삭제 권한 없는 키 사용(백업은 쓰기만) |

- 랜섬웨어는 연결된 백업을 우선 암호화 — 온라인·쓰기 가능 백업은 원본과 함께 인질. 불변 사본 1개가 마지막 보루.
- 백업 키와 백업을 같은 곳에 두지 않기(키 분실=복구 불가, 키 노출=백업 노출).

## 복구 런북 템플릿 (새벽에 읽을 수 있게)

```markdown
# 복구 런북: <시스템>
## 전제: 어디에 무엇이 (백업 위치·복호화 키 위치·접근 방법)
## 단계
1. [백업 받기] <명령>
2. [복호화] <명령>
3. [복원] <명령> — 예상 N분
4. [검증] <쿼리/체크>
5. [서비스 재개] <명령>
## 예상 RTO: <리허설 측정값>
## 연락/에스컬레이션: <막히면>
```

- 런북은 리허설로 검증된 것만 — "될 것"이 아니라 "해봤고 N분 걸림". GitLab 후속 조치의 핵심이 런북 + 자동화.
- ServerManager 레포 자체가 인프라 복구의 청사진(서버 재구축) — 데이터 백업과 별개로 "구성"도 백업 대상(dev-iac).
