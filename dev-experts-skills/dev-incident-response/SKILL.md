# dev-incident-response — 장애 대응·포스트모템 전문가

> 기준: Google SRE Book(장애 관리·포스트모템 장) (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

구글 SRE 전통. **"장애 중의 최우선 질문은 '왜 터졌나'가 아니라 '어떻게 멈추나'다 — 원인 규명은 서비스가 살아난 다음의 일이다"**. 그리고 포스트모템의 공리: **사람을 원인으로 지목하는 순간 학습은 끝난다** — 그 사람을 치워도 같은 구조가 다음 사람을 기다린다.

핵심 신조: 완화 먼저 원인 나중 · 기록하며 대응(타임라인은 그때만 쓸 수 있다) · 비난 없는 사후 분석(blameless) · 액션 아이템 없는 포스트모템은 일기다.

비유 — 장애 대응은 **응급실**이다: 지혈(완화)이 먼저고 병명(근본 원인)은 안정된 뒤다 — 출혈 환자 앞에서 발병 경위를 묻는 의사는 없다. 포스트모템은 사망사고 조사위원회 — "간호사 탓"으로 끝나는 조사는 다음 사고의 예약이다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 장애 중 대응 절차·의사결정 | 버그의 기술적 추적 (→ systematic-debugging) |
| 포스트모템 작성·재발 방지 | 감지·알림 체계 구축 (→ dev-monitoring) |

| 액션 아이템 체계 | 보고서 문서 산출 (→ html-report) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 원인 규명이 복구를 막음
❌ 장애 30분째 "근본 원인을 찾아야 고치지" — 로그 정주행 동안 사용자는 계속 단절
✅ **완화 사다리 먼저**: 롤백(직전 배포가 의심 1순위) → 재시작 → 트래픽 차단/축소 → 기능 플래그 off — 원인 몰라도 멈출 수 있는 수단부터. 단 **증거 보존**(로그·덤프 스냅샷) 후에
**왜**: 장애 비용은 시간에 비례하고, 완화와 규명은 분리 가능하다 — "최근에 뭐 바꿨나"의 답을 되돌리는 게 통계적으로 최速 복구다(장애의 다수는 변경 유발). 단 증거를 지우는 완화(재시작)는 보존 한 장 뜨고 나서.

### 2. 전원이 다 같이 디버깅 (역할 무분리)
❌ 5명이 전부 터미널에 — 누구도 전체 그림·기록·소통을 안 함, 같은 명령을 서로 모르게 중복 실행
✅ 1인 운영이라도 역할을 **모자로 분리**: 지휘(상황 판단·결정 기록) / 조치(손 움직임) / 소통(이해관계자 공지) — 사람이 부족하면 한 사람이 모자를 바꿔 쓰되 **지금 어느 모자인지 의식**. 조치는 한 번에 하나(동시 변경은 인과 추적 파괴)
**왜**: 무질서 대응의 2차 사고(서로 모르는 동시 조치·기록 부재로 같은 시도 반복)가 장애를 연장한다. GitLab 2017의 치명타도 피로 속 단독 작업이었다 — 구조가 사람을 보호한다.

### 3. 타임라인 사후 재구성
❌ 끝나고 기억으로 "아마 3시쯤..." — 시각·순서가 틀려 포스트모템의 인과 분석이 모래성
✅ **대응하며 기록**: 전용 채널/메모에 [시각 + 관찰 + 조치 + 결과] 실시간 1줄씩 — 명령·출력 복붙 포함. 이게 포스트모템의 원료다
**왜**: 장애 중 기억은 압축·왜곡된다(스트레스) — "조치 A가 효과였는지 우연이었는지"는 시각 순서만이 답한다. 기록 비용은 대응 중 1줄, 미기록 비용은 사후 진실 소실.

### 4. 비난형 포스트모템 ("누가" 로 종결)
❌ "원인: ○○가 명령을 잘못 침. 조치: 주의 환기" — 끝
✅ blameless 심문: 그 사람이 **그렇게 행동한 게 합리적이었던 맥락**(피로? 비슷한 호스트명? 확인 단계 부재? 도구가 위험을 안 알림?)을 파고든다 — 수정 대상은 사람이 아니라 그 맥락(확인 장치·네이밍·권한·자동화)
**왜**: "주의하겠습니다"는 재발 방지가 아니다 — 같은 조건이면 다음 사람도 같은 실수를 한다. 사람을 벌하는 문화의 진짜 비용은 다음 장애 때 정보 은폐(보고 지연)로 청구된다. 정직한 보고가 가장 빠른 감지 체계다.

### 5. 액션 아이템 증발
❌ 포스트모템에 "모니터링 강화하자" 5개 합의 — 담당·기한 없이 회의록 속으로
✅ 액션 아이템 규격: **[구체 작업 + 담당 + 기한 + 추적 위치(이슈)]** — 모호어("강화"·"개선") 금지, 다음 분기 점검에서 잔존 확인. 우선순위는 "같은 장애 재발 차단 > 감지 단축 > 영향 축소"
**왜**: 포스트모템의 산출물은 문서가 아니라 변경이다 — 추적 없는 합의는 다음 같은 장애에서 "그때 하기로 했는데"가 된다. 같은 원인의 2회차 장애는 1회차의 액션 아이템 부검부터.

### 6. 침묵 대응 (소통 부재)
❌ 고치는 데 집중하느라 2시간 무소식 — 사용자·동료가 각자 추측, 신뢰 손실이 장애 자체보다 큼
✅ 주기 공지 고정: 시작 시 인지 공지 → **30분 간격**(또는 합의 주기) 상태 갱신("조사 중"도 갱신이다) → 복구 공지 + 사후 분석 예고 — 템플릿화해 소통 비용 최소화
**왜**: 무소식의 공백은 최악의 상상으로 채워진다 — 사용자 신뢰는 장애 빈도보다 장애 중 투명성에 좌우된다는 게 반복 실증(GitLab의 생중계 복구가 신뢰를 오히려 올린 사례 — evidence).

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 완화 착수 | 인지 후 첫 완화 시도 ~15분 내(롤백 가능 여부 판단 포함) | 안티패턴 1 |
| 상태 공지 | 30분 간격 기본 | 안티패턴 6 |
| 포스트모템 트리거 | 사용자 영향 장애 전건 + 아차사고(near miss)도 약식으로 | 학습 면적 |
| 작성 시한 | 복구 후 ~5영업일 내(기억 부패 전) | 안티패턴 3 |
| 액션 아이템 | 전 항목 담당+기한, 분기 잔존 점검 | 안티패턴 5 |
| 동시 조치 | 1개씩 (변경→관찰→다음) | 안티패턴 2 |

## 워크플로우 A — 장애 중 (이 순서 그대로)

1. **선언·기록 개시** — "장애 대응 시작" + 타임라인 채널/메모 열기 + 첫 공지.
2. **증거 한 장** — 로그·상태 스냅샷(재시작·롤백이 지울 것들).
3. **완화 사다리** — 최근 변경 롤백 → 재시작 → 차단/축소 → 플래그 — 한 번에 하나, 각 결과 기록.
4. **안정 확인** — 핵심 지표 복귀 확인 후 복구 공지.
5. **원인 규명은 이제** — systematic-debugging으로 전환(증거 한 장이 출발점).

## 워크플로우 B — 포스트모템 (복구 후)

1. 타임라인 정리(기록 원료 → 시각 순) → 2. 영향 정량화(기간·사용자·데이터) → 3. 원인 분석(blameless — "왜"를 시스템에 5번) → 4. 액션 아이템 규격화 → 5. 공유(html-report 활용 가능). 산출물은 프로젝트 문서 규칙 위치에(기존 문서 덮어쓰기 금지, 날짜별 신규).

```
# 포스트모템 골격 (copy-paste)
## 요약 (영향: 기간/범위) / ## 타임라인 (시각+관찰+조치) / ## 원인 분석 (트리거→증폭→감지 지연 각각)
## 잘 된 것 / ## 운이 좋았던 것 / ## 액션 아이템 (작업+담당+기한+링크)
```

## 출력 템플릿 (장애 중 보고)

```
## 장애 대응 [시각]
### 상태: <조사 중/완화 중/복구>
### 영향: <무엇이 누구에게>
### 타임라인 최근: <마지막 3줄>
### 다음 조치: <1개>
```

### 작성 예시

```
## 장애 대응 [14:32]
### 상태: 완화 중 — 13:40 배포 롤백 실행
### 영향: API 5xx 약 40% (13:55 인지~), 수집기는 정상
### 타임라인 최근: 14:10 에러 급증 그래프 확인 / 14:18 직전 배포 의심 / 14:30 롤백 개시
### 다음 조치: 롤백 후 5분 지표 관찰 — 미복구 시 커넥션 풀 재시작
```

❌ "원인 찾을 때까지 손대지 말자" (규명이 인질극이 됨)
✅ "증거 한 장 → 롤백 → 기록 — 살리고 나서 부검한다"

### 사용자가 권고를 거부하면

- "포스트모템까진 오버다(혼자 쓰는 서비스)" → 규모 비례는 정당 — 3줄 약식(원인/조치/재발 방지 1개)을 ledger에 남기는 절충 제안, 거부 시 기록.
- "범인은 명백히 그 작업자다" → blameless의 실리(보고 문화 보존)를 1회 설명 — 문서 표현만이라도 시스템 중심으로 절충·기록(partial).
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

### 판단 불가 시 — `[확인 필요]` 4요소

장애 중 추측 조치는 2차 사고를 부르고(GitLab 교훈), 비가역 완화(재시작·롤백)는 증거를 지운다 — 불확실하면 4요소로 멈춘다(누가/언제/어떻게/기대값):

- **롤백 대상·영향 범위 불명**: "무엇을 되돌릴지·영향이 어디까지인지를 / 완화 실행 전에 / '최근 변경(배포·설정·인프라) 목록' + 영향 지표(어느 엔드포인트·사용자군)를 지휘 모자가 확인 / 직전 변경이 시점상 일치하면 1순위 롤백 대상, 변경 없으면 의존 서비스 의심" — 대상 미확정 채로 여러 조치 동시 실행 금지(인과 추적 파괴).
- **근본 원인 추측 단계**: "관찰된 증상이 원인인지·증상인지를 / 포스트모템 원인 분석 시 / 타임라인(시각+조치+결과)으로 '왜'를 시스템에 5번 + 우연/효과 구분으로 / 조치 직후 회복이면 그 조치가 효과, 무관하게 회복이면 다른 요인" — 단일 관찰로 근본 원인 단정 금지(blameless: 사람 아닌 맥락).
- **비가역 완화 전 증거**: "재시작/롤백이 지울 증거가 있는지를 / 완화 직전에 / 로그·상태·덤프 스냅샷 1장 확보 여부 확인 / 스냅샷 떴으면 완화 진행, 안 떴으면 먼저 보존" — 기대값 못 얻으면 `[확인 필요: 변경 이력·증거 보존 — 미확인]`로 남기고 타임라인·ledger 기록.

## 실전 케이스 — GitLab (2017): 최악의 사고, 모범의 대응 (공식 기록)

DB 삭제 + 백업 5중 실패(dev-cron-scheduling evidence)라는 내용은 최악이었지만, **대응은 업계 교본**이 됐다: 사고 문서를 실시간 공개로 작성하고 복구 과정을 유튜브로 생중계 — 추측성 보도가 사라지고 커뮤니티가 복구 아이디어까지 보탰으며, 사후 신뢰도는 오히려 상승했다는 평가가 지배적이다. 포스트모템은 작업자 개인을 비난하지 않고(피로·유사 호스트명·확인 장치 부재라는 맥락) 시스템 개선 목록으로 종결 — 해당 엔지니어는 실명 공개에 동의했고 커뮤니티의 격려를 받았다(이후 고용 결과는 공식 기록에 없음). 교훈: ① 투명성은 장애 비용을 줄이는 실전 도구다(신뢰는 무결점이 아니라 정직에서) ② blameless는 윤리가 아니라 정보 흐름 보존 전략 ③ "운이 좋았던 것"(우연한 수동 스냅샷)을 명시한 것이 백업 체계 전면 재구축의 동력이 됐다 — 운을 기록해야 운에 안 기댄다. 상세: `references/evidence.md`
