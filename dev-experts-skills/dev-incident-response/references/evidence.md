# dev-incident-response evidence — 실증 사례

## 1. GitLab (2017) — 투명 대응의 교과서 (공식 기록·생중계)

- **대응의 재구성**: 데이터 유실 인지 → 사고 문서(구글 닥스)를 **공개 상태로 실시간 작성** → 복구 과정 유튜브 생중계 → 트위터로 주기 갱신. 결과: 추측 보도 차단·커뮤니티 조력·사후 신뢰 상승. 포스트모템은 작업자 맥락(새벽 피로·db1/db2 호스트명 유사·위험 명령에 확인 장치 부재)을 분석하고 시스템 개선(백업 검증 자동화·명령 안전장치)으로 종결.
- **이식 가능한 교훈**: ① 공지 템플릿·채널을 평시에 준비(장애 중 작문은 비용) ② "운이 좋았던 것" 섹션 — 우연(6시간 전 수동 스냅샷)을 명시해야 그 운을 시스템으로 대체할 동기가 생긴다 ③ 1인 운영 번역: 공개 생중계 대신 "타임라인 메모 + 이해관계자(또는 미래의 나)용 기록"이 같은 기능.

## 2. Knight Capital (2012) — 45분, 4.6억 달러: 대응 부재의 가격 (SEC 보고서)

- **무슨 일**: 배포 누락으로 8대 중 1대 서버에 구형 코드 잔존 → 신규 플래그가 구형 코드의 테스트 로직(Power Peg)을 활성화 → 45분간 폭주 주문으로 $460M 손실, 회사는 사실상 소멸. SEC 보고서가 표준 부검.
- **대응 관점의 실패 해부**: ① **킬 스위치 부재** — "전부 멈추기" 수단이 없어 원인 추적과 출혈이 동시 진행 ② 이상 신호(개장 전 경고 메일 97통)가 묵살됨 — 감지는 있었으나 대응 절차에 연결 안 됨 ③ 첫 조치가 오히려 악화(정상 서버들의 신규 코드를 롤백 — 문제는 구형 코드였으므로 8대 전부가 폭주) — **가설 없는 조치**의 위험.
- **교훈**: 완화 사다리의 최상단엔 "전체 정지"가 있어야 한다(부끄러운 버튼이 회사를 살린다) · 경고가 절차에 연결되지 않으면 없는 것 · 조치 전 "이 조치가 틀렸다면 무엇이 보일까"를 1줄이라도 — 한 번에 하나, 관찰하며.

## 3. 5 Whys의 실전 사용법 — 그리고 그 한계 (방법론 실증)

- **올바른 사용**: "왜"를 사람이 아니라 시스템에 던진다 — "왜 잘못된 호스트에서 실행됐나" → "왜 호스트명이 혼동 가능했나" → "왜 위험 명령에 확인이 없었나" → 각 층이 액션 아이템 후보가 된다. 한 갈래가 아니라 **세 갈래(트리거/증폭/감지 지연)** 각각에 왜를 묻는 게 실전형 — 트리거만 파면 "오타 방지"로 끝나고 증폭 구조(백업 부재)를 놓친다.
- **한계 인지**: 5 Whys는 단선 인과를 가정한다 — 복잡 장애(여러 요인의 동시 성립)에선 "기여 요인 목록"이 더 정직한 틀이다. "근본 원인은 하나"라는 강박이 오히려 분석을 왜곡할 수 있다(현대 안전공학의 표준 비판).
- **품질 검사**: 완성된 포스트모템에 "사람 이름이 원인 자리에 있는가"·"액션 아이템 없이 끝나는 왜 갈래가 있는가" 2개 질문 — 둘 다 아니오면 합격.
