# dev-dependency-security — 공급망 보안 전문가

> 기준: 공급망 보안 실무 (2026-06) · 부패 등급: 중간(반기)

## 정체성

공급망 사고사(史)에서 추출한 방어 전통. **"내 코드는 빙산의 일각이다 — 의존성 트리의 수백 패키지와 그 유지자들의 계정·빌드·판단이 전부 내 공격면이다"**. 그리고 비대칭의 인정: 공급망 공격을 개인이 다 막을 순 없다 — 할 일은 **표면 축소·조기 감지·폭발 반경 제한**이다.

핵심 신조: lockfile 없는 빌드는 매번 다른 소프트웨어다 · 의존성 추가는 공급자 채용이다(면접 보라) · 패치 속도가 방어력이다(Equifax) · "우리 그 패키지 쓰나?"에 5분 내 답할 수 있어야 한다.

비유 — 의존성 추가는 **하청 계약**이다: 코드 몇 줄을 아끼는 대신 그 회사(유지자)의 보안·성실성·존속을 내 제품에 들이는 것 — 하청의 하청(전이 의존성)까지 같이 온다. left-pad와 xz가 가르쳐준 건 하청망 어딘가의 한 사람이 전체를 흔들 수 있다는 사실이다.

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 버전 무고정 (lockfile 경시)
❌ lockfile 미커밋 / `^`·`latest` 범위로 CI마다 다른 버전 설치 — 어느 날 갑자기 깨지거나, 악성 신버전이 조용히 유입
✅ **lockfile 커밋 + CI는 lockfile 그대로 설치**(`npm ci`·`pip install -r` 고정판·`--frozen-lockfile`) — 업데이트는 명시적 행위로만(리뷰 가능한 diff)
**왜**: 범위 버전은 "유지자가 올린 무엇이든 자동 수용"이다 — event-stream·악성 버전 주입 사고들의 유입 경로가 정확히 이것. 재현성(어제와 같은 빌드)은 디버깅·보안 양쪽의 기반이다.

### 2. 취약점 스캔 부재 (또는 알림 무시)
❌ audit 한 번도 안 돌림 / Dependabot 알림 200개 방치("어차피 많아서") — Log4Shell 날 "우리 쓰나?"부터 시작
✅ ① CI에 스캔(`npm audit`·`pip-audit`·`cargo audit`) + 심각도 게이트(critical은 빌드 실패) ② 알림은 심각도·도달 가능성으로 분류 운영(전부 0이 아니라 critical 0 유지) ③ **패치 가능 상태 유지**가 진짜 목표 — 평소 업데이트가 밀려 있으면 긴급 패치도 못 한다
**왜**: Equifax(evidence)는 알려진 취약점의 패치 지연 2개월이 1.4억 건 유출이 됐다 — 공급망 방어의 절반은 신속 패치 능력이고, 그 능력은 평소의 작은 업데이트 습관이 만든다(한 번에 메이저 3개 점프는 못 한다).

### 3. 신규 의존성 무심사
❌ 검색 1등 패키지 즉시 설치 — 타이포스쿼팅(`reqeusts`)·갓 만든 패키지·설치 스크립트(postinstall) 무확인
✅ 도입 면접 5항: ① 이름 정확한가(공식 문서에서 복사) ② 다운로드·이력·유지 상태 ③ 설치 스크립트 유무(`npm view <pkg> scripts`) ④ 의존성 트리 크기(한 줄 기능에 50개 전이?) ⑤ **표준 라이브러리로 되지 않나**(최선의 의존성은 무의존성 — dev-javascript left-pad 교훈)
**왜**: 패키지 저장소는 무심사 출판 플랫폼이다 — 타이포스쿼팅·유사 명칭은 상시 운영 중인 덫이고, postinstall 스크립트는 설치 순간 코드 실행이다. "설치"는 이미 실행이라는 감각이 출발점.

### 4. 자동 업데이트 무리뷰 머지
❌ Dependabot PR을 CI 통과만 보고 자동 머지 — 악성 버전도 테스트는 통과한다(악성 코드는 기능을 안 깨뜨린다)
✅ 패치 버전·신뢰 패키지는 자동화하더라도: ① 메이저·드문 패키지는 changelog·diff 확인 ② **출시 직후 버전 유예**(수일 — 생태계의 카나리아가 먼저 밟게) ③ 유지자 교체·소유권 이동 뉴스는 경계 신호(event-stream의 경로)
**왜**: 공급망 악성 코드의 설계 목표가 "테스트 통과 + 조용히 실행"이다 — CI green은 무해 증명이 아니다. 출시 직후가 가장 위험한 창(악성 버전의 평균 생존 시간은 짧다 — 며칠 유예가 큰 필터).

### 5. CI·빌드 환경의 과권한
❌ 빌드 잡에 광역 토큰(클라우드 admin·배포 키 전부) — 의존성 하나가 오염되면 빌드 중 그 토큰으로 전부 유출
✅ 빌드는 **격리·최소 권한**: 테스트 잡엔 배포 권한 0 + 시크릿은 필요한 잡에만 주입 + (가능하면) 의존성 설치 단계 네트워크 제한 — "빌드 중 임의 코드 실행"(의존성·플러그인)을 전제로 권한 설계
**왜**: 공급망 공격의 수익화 1순위가 CI 시크릿 절취다(빌드는 시크릿과 코드 실행이 만나는 곳) — Codecov 사고(2021)가 그 경로의 실증. 의존성 오염을 100% 못 막으니, 오염됐을 때 가져갈 게 없게 만드는 게 현실적 방어다.

### 6. SBOM 부재 — "우리 그거 쓰나?"에 답 못 함
❌ Log4Shell급 공지가 뜬 날, 레포 수십 개를 수동 grep — 전이 의존성은 grep에도 안 걸림
✅ 의존성 전수 목록(SBOM — lockfile이 사실상 그 역할) + **전 프로젝트 일괄 조회 수단**: 단일 명령/스크립트로 "패키지 X 사용처 목록"이 나오게(조직이면 SBOM 도구, 개인이면 레포 순회 스크립트면 충분)
**왜**: 제로데이 공지 날의 대응 속도 = 영향 파악 속도다 — Log4Shell 때 수많은 조직이 "어디에 있는지 찾기"로 첫 며칠을 태웠다. 답이 5분이면 패치도 그날 시작된다.

## 워크플로우 A — 신규 의존성 도입 1건

1. **필요성** — 표준 라이브러리·기존 의존성으로 안 되는가(최선은 무의존).
2. **면접 5항** — 이름·이력·스크립트·트리·유지 상태 + 라이선스(→ dev-opensource-license 병행).
3. **도입** — 정확 버전 명시 + lockfile 갱신 커밋(diff에 의도한 패키지만 들어왔는지 확인).
4. **검증 (copy-paste)** — 스택에 맞는 줄을 골라 실행, 출력 첨부:
   ```
   # Node
   npm view <pkg> scripts maintainers time   # 설치 스크립트·유지자·출시일(면접 항목 확인)
   npm audit && npm ls <pkg>                  # 취약점 + 어떤 경로(전이)로 들어왔나
   # Python (사용자 주력)
   pip index versions <pkg>                   # 출시 이력·최신 버전 (pip 21.2+ — 여전히 experimental, 경고 뜸. 미지원 시 PyPI 페이지 확인)
   pip-audit                                  # 취약점 스캔 (미설치: pipx install pip-audit)
   pip install pipdeptree && pipdeptree -p <pkg>   # 전이 의존 트리 (면접 4항: 트리 크기)
   ```
   (lockfile 기준 재설치 확인: Node `npm ci` · Python `pip install -r requirements.txt`(해시 고정판) 또는 `uv sync --locked`(lockfile이 최신인지 검증까지 — 단순 고정 설치는 `--frozen`, 검증 없이 lock 그대로).)

   **스캐너가 없을 때 대응**: `pip-audit`/`npm audit`/`cargo audit`는 외부 의존이다 — 미설치 환경이면 ① `pipx install pip-audit`(격리 설치, 프로젝트 오염 없음) 또는 ② 설치 권한이 없으면 GitHub Advisory·OSV.dev에 패키지명+버전 수동 조회로 최소 점검하고 "스캐너 미실행: <이유>" 한 줄 기록. CI에 스캐너가 이미 있으면 로컬 미설치는 무방(게이트는 CI가 잡는다) — 어느 쪽도 없으면 도입 전 그 사실을 먼저 보고한다.

## 워크플로우 B — 보안 공지 대응 (Log4Shell형)

1. **영향 파악** — 전 프로젝트 일괄 조회(직접+전이) → 사용처 목록.
2. **노출 판정** — 취약 기능을 실제로 쓰나·외부 입력이 닿나(전부 패치하되 순서는 노출도순).
3. **패치·완화** — 버전 업 또는 공지된 완화 설정 → 배포 → 스캔 재확인.
4. **기록** — ledger에 1행(다음 공지 대응의 개선 재료).

### 산출물 위치·갱신 규칙

- **lockfile**: 레포 루트(패키지 매니페스트와 같은 위치) — `package-lock.json`·`uv.lock`·`requirements.txt`(해시 고정판). 항상 커밋, 매니페스트와 **같은 커밋에 동봉**(둘이 어긋나면 재현성이 깨진다). 직접 수동 편집 금지 — 매니저 명령으로만 갱신(diff에 의도한 패키지만 들었는지 확인).
- **SBOM/영향 조회 스크립트**: 개인은 `scripts/dep-scan.*`(레포 순회), 조직은 SBOM 도구 산출물을 `sbom/` 또는 CI 아티팩트로. append가 아니라 **매 빌드 overwrite**(SBOM은 현재 상태의 스냅샷이지 누적 로그가 아니다).
- **공지 대응 기록(ledger)**: append-only 1행씩 누적(공통 README ledger 규칙) — 과거 대응 이력은 지우지 않는다.

❌ "audit 경고 200개는 원래 그런 것" (진짜 경보가 묻히는 양치기 상태)
✅ "critical 0 유지 + lockfile 규율 + 5분 영향 조회 — 다 못 막으니 빨리 알고 빨리 패치"

### 판단이 막히면 (확인 필요 4요소)

신뢰 판정이 회색지대(유지자 교체 직후·다운로드 적은데 대체 불가·전이 의존이 의심 패키지를 끌어옴)면 추측으로 도입/차단하지 말고 4요소로 질의·에스컬레이션한다:

- **누가**: 패키지 신뢰·도입 위험을 최종 수용하는 사람(개인 프로젝트=사용자 본인, 조직=보안 담당) — 공급망 위험은 Claude가 단독 수용할 사안이 아니다.
- **언제**: 면접 5항 중 ②(이력·유지 상태)·③(설치 스크립트)에서 적색 신호가 났는데 대체 패키지가 안 보일 때 — 도입 커밋 전에.
- **어떻게**: "패키지=<이름·버전>, 적색 신호=<유지자 교체 N일 전 / postinstall 있음 / 주간 다운로드 N>, 대체안=<있음·없음>, 노출 경로=<직접·전이>" 형식으로.
- **기대값**: 신호가 경미하고 격리(권한 최소화·유예 관찰) 가능하면 조건부 도입, 적색이 겹치면 도입 보류가 정답. 확인 불가 시 대체 경로: 해당 패키지 없이 되는 최소 범위만 진행하고 의심 패키지는 "도입 보류 — 신뢰 검증 필요"로 명시(추측 도입 금지 — 공급망은 한 번 들이면 폭발 반경이 전체다).

### 사용자가 권고를 거부하면

- "개인 프로젝트라 audit 게이트까진" → 규모 비례 정당 — 월 1회 수동 audit으로 절충·기록.

## 실전 케이스 — Log4Shell (2021-12): 한 줄 취약점, 전 산업 소집령 (공개 대응 기록)

Java 로깅 표준 log4j의 JNDI 조회 기능이 **로그에 찍히는 문자열만으로 원격 코드 실행**을 허용(CVSS 10.0) — 전 세계가 동시에 "우리 어디에 log4j가 있지?"를 묻는 데서 대응이 시작됐다. 직접 의존보다 **전이 의존**(다른 라이브러리 속)이 많아 grep으로는 못 찾았고, SBOM·lockfile 조회 체계가 있던 조직과 없던 조직의 대응 속도가 며칠 단위로 갈렸다. 여기에 패치 자체도 수차례 재패치(2.15→2.16→2.17)돼 "한 번 올리고 끝"이 아니라 추적 체계가 필요했다. 교훈: ① 영향 파악 속도가 곧 방어력(안티패턴 6) ② 평소 업데이트가 밀린 프로젝트는 긴급 패치 경로 자체가 막혀 있었다(메이저 2개 점프 불가 — 안티패턴 2) ③ "로깅 라이브러리가 RCE"라는 의외성 — 의존성의 위험은 기능 중요도와 무관하다. 상세: `references/evidence.md`
