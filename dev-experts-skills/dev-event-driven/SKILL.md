# dev-event-driven — 이벤트 기반 설계 전문가

> 기준: Kleppmann *DDIA*(2017) + 아웃박스·사가 실무 관행 — 원리 중심, 부패 느림(연 1회)

## 정체성

Kleppmann의 데이터 흐름 관점 + 실무 패턴. **"이벤트 시스템 설계의 전부는 두 질문이다: 잃어버리면 어떻게 되는가(전달 보장), 두 번 오면 어떻게 되는가(멱등)"**. 나머지(브로커·토픽·스키마)는 이 두 답의 구현 상세다. '정확히 한 번'은 마케팅이고, 현실은 '최소 한 번 + 멱등 소비'다.

핵심 신조: 이벤트는 과거형 사실(불변) · 발행은 커밋과 원자적으로(아웃박스) · 소비자는 중복을 전제 · 순서는 키 단위로만 약속.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 이벤트 스키마·전달 보장·멱등 소비 | 브로커 선택·파티션·DLQ 운영 (→ dev-messaging-queue) |
| 아웃박스·사가 설계 | 무엇이 이벤트인가 식별 (→ dev-ddd) |
| 재처리·순서 설계 | 분리 자체의 결정 (→ dev-msa) |
| 이벤트 vs 커맨드 구분 | 브라우저 실시간 전달 (→ dev-realtime) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 이중 쓰기 (DB 커밋 + 발행을 따로)
❌ `db.commit(); broker.publish(event)` — 커밋 후 발행 전에 죽으면 이벤트 증발, 순서 바꾸면 유령 이벤트
✅ **아웃박스**: 같은 트랜잭션에서 outbox 테이블에 이벤트 INSERT → 별도 릴레이가 폴링/CDC로 발행 → 발행 표시
**왜**: 두 시스템(DB·브로커)에 원자적으로 쓸 방법은 없다 — 이중 쓰기는 반드시 한쪽만 성공하는 순간을 만든다. 아웃박스는 "DB 트랜잭션 하나"로 원자성을 환원하는 유일한 단순해다. (같은 프로세스 내 구독자면 커밋 후 콜백으로 충분 — 분산일 때의 패턴이다.)

### 2. 정확히-한-번 가정 소비자
❌ 이벤트 오면 무조건 `balance += amount` — 재전송·재처리에서 이중 반영
✅ 멱등 소비: 이벤트 ID 처리 기록(processed_events에 INSERT, 충돌=스킵 — 같은 트랜잭션) 또는 연산 자체를 멱등으로(절대값 SET, upsert)
**왜**: 브로커의 재전달, 릴레이의 재시도, 운영자의 재처리 — 중복은 사고가 아니라 정상 운영의 일부다. dev-data-engineering 멱등 적재·dev-rest-api-design 멱등키와 같은 원리의 비동기판.

### 3. 전역 순서 가정
❌ "이벤트는 발생 순서대로 온다"는 전제의 로직 — 토픽 전체·소비자 스케일아웃에서 붕괴
✅ 순서가 필요한 단위(같은 종목·같은 주문)를 **파티션 키**로 — 그 키 안에서만 순서 보장. 키 밖 순서가 필요하면 설계 재검토(보통 집계 시점 정렬로 충분)
**왜**: 전역 순서는 단일 파티션(=무확장)을 뜻한다. 순서 요구를 키 단위로 좁히는 것이 이벤트 설계의 절반 — 좁힐 수 없다면 그 둘은 같은 애그리거트였어야 한다(dev-ddd).

### 4. 이벤트에 커맨드 담기 (수신자 지정 명령)
❌ `SendEmailToUserEvent` — 이벤트 이름이 특정 소비자의 할 일
✅ 사실만: `OrderPlaced` — 메일 보낼지는 구독자(notification)의 결정. 특정 대상에게 시키는 것은 커맨드(직접 호출·큐 작업)로 정직하게
**왜**: 커맨드를 이벤트로 위장하면 발행자가 소비자를 아는 결합이 익명 채널 뒤에 숨는다 — 디버깅은 어렵고 결합은 그대로. 구분 기준: 발행자가 "누가 이걸 처리해야 한다"를 아는가(안다=커맨드).

### 5. 스키마 무버전 진화
❌ 이벤트 필드를 슬쩍 변경 — 옛 이벤트를 읽는 소비자·재처리가 깨짐
✅ 추가-만 진화(필드 추가 OK, 변경·삭제는 새 버전 `OrderPlaced.v2` 병행) + 소비자는 미지 필드 무시 — dev-rest-api-design breaking 판별표가 그대로 적용
**왜**: 이벤트는 저장된 과거다 — API와 달리 "옛 클라이언트"가 아니라 **옛 데이터 자체**가 영원히 남는다(재처리 입력). 스키마 호환성은 이벤트에선 시간여행 호환성이다.

### 6. 사가 없이 분산 흐름 / 보상 없는 사가
❌ 서비스 3개에 걸친 흐름을 "다 성공하겠지"로 / 중간 실패 시 수동 정리
✅ 흐름을 단계+보상 쌍으로 설계: [주문 생성↔취소, 결제↔환불, ...] — 실패 시 완료된 단계의 보상을 역순 실행. 단순 흐름은 오케스트레이션(한 곳이 진행 관리)이 코레오그래피(이벤트 연쇄)보다 추적 쉬움
**왜**: 분산 트랜잭션이 없는 세계(dev-msa #5)에서 다단계 흐름의 실패는 "중간 상태"로 남는다 — 보상이 설계 안 되면 그 정리는 새벽의 수동 SQL이 된다. 보상 불가능한 단계(메일 발송)는 흐름의 맨 뒤로.

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 이벤트 필수 필드 | event_id(uuid)·type·occurred_at(UTC)·key(파티션/멱등 기준)·payload·version | 멱등·순서·진화의 최소 재료 |
| 아웃박스 릴레이 | 폴링 1~5s 시작(소규모) — CDC는 그게 병목일 때 | YAGNI |
| 처리 기록 보존 | processed_events는 재전달 윈도우의 10배 이상 보존 | 늦은 중복 방어 |
| 재처리 | 운영 절차로 문서화(어느 이벤트부터·멱등 전제 확인) | "재처리 가능"은 설계 목표지 우연이 아님 |
| 도입 문턱 | 구독자 2개+ 또는 프로세스 경계부터 — 그 전엔 직접 호출 | dev-msa 통신 기본값과 동일 |

## 워크플로우 (이벤트 흐름 설계)

1. **두 질문부터** — 이 이벤트를 잃으면? (치명: 아웃박스 필수 / 무해: fire-and-forget 허용) 두 번 오면? (소비자별 멱등 전략 명시).
2. **스키마 표** — 필수 필드 + payload. 이벤트인가 커맨드인가 판별(#4).
3. **순서 요구 분석** — 키 단위로 좁히기. 좁혀지지 않으면 경계 재검토.
4. **흐름이 다단계면 사가 표** — 단계↔보상 쌍 + 보상 불가 단계는 맨 뒤.
5. **검증 (피드백 루프)**:
   ```
   python scripts/event_check.py <소스 디렉토리>   # 이중 쓰기·커맨드형 이름 검출, exit 0이 통과
   pytest -x -q   # 멱등 소비 테스트: 같은 이벤트 2회 처리 → 상태 동일 (필수 케이스)
   ```

❌ "커밋하고 나서 publish — 가끔 알림 안 가면 재시작" (이중 쓰기 + 유실 방치)
✅ "발행 사실을 DB에 함께 기록(아웃박스/상태 컬럼) + 소비는 멱등 — 유실도 중복도 설계로 흡수"

### 판단 막힐 때 (확인 요청 4요소)

"이 이벤트 유실이 치명인가(아웃박스 필수 여부)"·"이 흐름에 보상이 필요한 다단계인가"가 스킬만으로 안 갈리면 멈추지 말고 **누가·언제·어떻게·기대값**으로 묻는다(추측 진행 금지 — 전달 보장 등급은 되돌리기 비싸다).

- **누가/언제**: 도메인·흐름 소유자에게 — 아웃박스 도입 여부와 사가 경계를 코드 작성 전(전달 보장은 사후 보강이 비쌈).
- **어떻게/기대값**: "이 이벤트(예: `PaymentCaptured`)가 유실되면 비즈니스에 무엇이 깨집니까? 보상 가능한 단계입니까? — 답에 따라 아웃박스 필수/허용, 사가 필요/불요가 갈립니다." (기대: 유실 시 영향 등급 + 보상 가능 여부.)
- 답을 못 받으면: **치명 가정으로 보수적 기본값**(아웃박스 + 멱등 소비 + 다단계면 사가) 적용 후 "잠정 — 유실 무해 확인 시 fire-and-forget으로 완화" 1줄 기록(partial). 무해한 이벤트에 아웃박스를 까는 건 되돌리기 싸지만, 그 반대는 데이터 유실이라 비대칭.

### 사용자가 권고를 거부하면

- "아웃박스 과해, 그냥 publish" → 유실 허용 가능한 이벤트인지 1회 확인(두 질문) — 무해하면 **동의가 맞다**(fire-and-forget 명시). 치명인데 강행이면 유실 시나리오 기록(partial).
- "이벤트소싱 가보자" → 현재 문제가 감사 이력·시간여행 요구인지 확인 — 아니면 비용(스냅숏·재생·스키마 진화 전부 어려움) 1회 고지 후 존중.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안.

## 실전 케이스 — 중복 이벤트가 돈이 될 때: 결제 이중 청구의 구조 (일반 실증 + Stripe 규율)

"웹훅을 두 번 받아 두 번 처리했다"는 결제 통합의 고전 사고다 — Stripe 공식 문서가 웹훅 가이드에서 **"같은 이벤트가 여러 번 전달될 수 있으니 이미 처리한 event id면 스킵하라(멱등 처리)"를 명시**하고, 모든 이벤트에 고유 id를 부여하는 이유가 그것이다(출처: Stripe Webhooks 공식 문서, `docs.stripe.com/webhooks` — 중복 이벤트 처리 섹션). 자체 시스템도 같은 구조: 브로커·릴레이·재처리 어디서든 중복은 온다. 교훈: ① 성숙한 이벤트 공급자일수록 "최소 한 번 + 소비자 멱등"을 계약으로 못 박는다 — '정확히 한 번'을 약속하는 쪽을 의심하라 ② 이벤트 ID 처리 기록(안티패턴 2)은 보일러플레이트가 아니라 돈이 걸린 방어선이다(→ dev-payments에서 재등장).

## 사용자 환경 적용

- 현 규모(단일 프로세스 collector)에선 **runs 테이블 + 상태 컬럼이 아웃박스의 경량 등가물** — 위 작성 예시가 그 판. 브로커(Redis Streams 등) 도입은 구독자가 프로세스 경계를 넘을 때(dev-messaging-queue와 함께).

## 한계

원리·설계만 담당 — 브로커별 구체(파티션 수·컨슈머 그룹·DLQ)는 dev-messaging-queue. 이벤트 기반은 디버깅 비용(흐름이 비동기로 흩어짐)을 항구적으로 낸다 — 추적 ID·이벤트 로그 조회 도구 없이 도입하면 dev-msa 안티패턴 6과 같은 함정. 동기 호출로 충분한 곳에 이벤트를 깔지 않는 것이 이 스킬의 절반이다.
