# 상태 패턴 — 위치 결정·리듀서·컨텍스트·폼 (SKILL.md 비중복)

## 상태 위치 결정 절차

```
1. 그 상태를 읽는 컴포넌트를 전부 나열
2. 그들의 가장 낮은 공통 조상이 기본 위치
3. 한 컴포넌트만 읽는다 → 그 안에 (지역)
4. 공통 조상이 너무 멀다(3단+ 드릴링)
   ├─ 읽기만 깊다 → children/composition으로 중간 단계 제거 먼저
   ├─ 저빈도 갱신(테마·로그인 사용자) → Context
   └─ 고빈도 갱신(시세 틱·폼 전체) → 상태 라이브러리 (Context는 소비자 전원 리렌더)
```

- Context 분리 규칙: 값과 setter를 한 Context에 넣으면 setter만 쓰는 컴포넌트도 값 변경에 리렌더 — 둘을 쪼개거나 라이브러리로.

## useState → useReducer 전환 기준

신호 3개 중 2개면 전환:
1. setState 여러 개가 항상 같이 불린다 (한 이벤트에 set 3연발)
2. 다음 상태가 이전 상태에 복잡하게 의존
3. 같은 전이 로직이 여러 핸들러에 중복

```jsx
type Action = { type: "select"; code: string } | { type: "clear" } | { type: "loaded"; data: Candle[] };
function reducer(s: PanelState, a: Action): PanelState { /* 전이가 한 곳에 - 테스트 가능한 순수 함수 */ }
```

- 리듀서는 dev-tdd ◎ 영역(순수 함수) — 복잡 전이는 리듀서 추출 후 테스트가 정석.
- 구별된 유니언 Action(dev-typescript #5)과 세트로 — 불가능 액션이 컴파일 에러.

## 폼 패턴

| 규모 | 선택 |
|---|---|
| 필드 1~3개 | 제어 컴포넌트(useState) 그대로 |
| 필드 많음·검증 복잡 | react-hook-form 등 (비제어 기반 — 타이핑 리렌더 0) + zod 스키마(dev-typescript 경계와 같은 스키마 재사용) |
| 제출만 필요(검색창 등) | 비제어 + FormData — 상태 자체가 불필요한 경우가 의외로 많다 |

- "타이핑마다 느려요"는 폼 상태가 너무 높이 있다는 신호(안티패턴 6) — 라이브러리 전에 위치부터.

## 서버 상태 vs 클라이언트 상태 (혼동이 버그의 뿌리)

- **서버 상태**(시세·목록·상세): 소유자는 서버, 클라이언트엔 캐시 사본 — TanStack Query류가 관리(staleTime·무효화). useState에 복사하지 않는다(복사본 동기화 지옥).
- **클라이언트 상태**(선택·열림·입력 중): 소유자는 UI — useState/리듀서.
- 경계 사례 "서버에서 받아 수정 중인 폼": 초기값만 서버에서, 편집 본은 클라이언트 상태 — `key={data.id}`로 대상 변경 시 리셋(안티패턴 5의 역활용).

## 리스트 가상화 판단

- 행 수백 개까지는 그냥 렌더 — 가상화(react-window류)는 수천 행+에서, Profiler로 렌더 비용 확인 후(안티패턴 4와 같은 측정 우선 규율).
