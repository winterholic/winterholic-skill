# dev-payments evidence — 실증 사례

## 1. 이중 결제 해부 — "두 번 결제됐어요"의 기술 경로 (실무 집적)

- **발생 경로 3종**: ① 승인 API 타임아웃 → 클라이언트/서버 재시도(첫 요청은 사실 성공) ② 사용자 더블클릭·뒤로가기 후 재시도(프론트 비활성화는 UX 보조일 뿐 방어가 아님) ③ 웹뷰·네트워크 전환 중 중복 제출 — 전부 "정상 동작의 조합"이라는 게 핵심: 버그가 아니라 설계 부재가 원인.
- **방어 계층**: [PG 멱등/주문번호 체계(같은 주문번호 재승인 거부)] + [내 DB 유니크 제약(경합의 최종 심판 — dev-concurrency #1)] + [타임아웃 시 조회 우선] — 3겹 중 DB 유니크가 마지막 보루다(앱 로직은 경합에서 진다).
- **사후 처리도 설계**: 그래도 발생한 이중 건의 탐지(대사)와 자동 환불 절차 — "발생 0"이 아니라 "발생 시 당일 해소"가 현실적 목표.

## 2. 가격 변조 — 파라미터 조작의 영원한 현역 (보안 커뮤니티 반복 보고)

- **무슨 일**: 결제 요청의 amount를 개발자도구/프록시로 수정 — 서버가 클라이언트 금액으로 결제를 생성하면 1원 결제가 성립한다. 국내외 버그바운티·보안 점검에서 끊이지 않는 적발 항목이며, 실제 상품 수령까지 간 사례들이 보도돼 왔다.
- **이중 검증 절차**(PG 가이드 공통 요구): ① 결제 생성은 서버 저장 금액으로만 ② **승인 후** PG 응답의 금액·주문번호를 서버 주문과 대조 — 불일치 시 즉시 취소 API + 보안 알림. ②가 있는 이유: 결제창 호출 파라미터 자체가 조작되는 경로까지 막는 최종 관문.
- **연결**: 입력 불신 원칙(dev-web-security)의 돈 버전 — "금액·수량·할인율"은 항상 서버 재계산 대상이다.

## 3. 대사가 잡는 것들 — 일일 대조의 실전 수확 목록 (운영 집적)

- **불일치 3분류와 원인**:
  1. **PG에 있는데 나에게 없음**: 웹훅 유실+폴링 구멍·승인 후 서버 에러 — 고객은 돈만 나간 상태(최우선 처리)
  2. **나에게 있는데 PG에 없음**: 위조 신호 처리·테스트 데이터 오염·취소 미반영 — 무료 상품 발송 경로
  3. **금액 불일치**: 부분 환불 미반영·끝전 처리 차이·수수료 해석 차이 — 누적되면 정산 분쟁
- **운영 형태**: PG 정산/거래내역 API(또는 일 파일)를 받아 건별 키 매칭 배치 — 불일치는 분류별 큐로, "불일치 0"을 일일 정상 상태로 정의(dead man's switch 핑 포함 — dev-cron-scheduling).
- **교훈**: 대사는 사고를 막지 않는다 — **사고의 발견 시점을 "고객 항의"에서 "다음날 아침"으로** 당긴다. 결제 시스템의 신뢰는 무사고가 아니라 발견·해소 속도에서 나온다.

## 4. 1차 출처 — 공식 문서가 직접 명세하는 절차 (2026-06 웹 확인)

아래 세 항목은 본 스킬의 안티패턴 1·2·3·4가 "관행"이 아니라 **PG 공식 문서가 명문화한 절차**임을 보이는 1차 출처다.

- **멱등 키(안티패턴 1)** — Stripe 공식: `Idempotency-Key` 헤더로 모든 POST에 전달, 연결 오류 시 안전 재시도(중복 객체 생성 방지). PaymentIntents 문서는 "장바구니/세션 ID 기반 멱등 키로 중복 PaymentIntent 생성을 막으라"고 명시. 키는 24시간 후 만료(이후 재사용은 새 요청 취급). 출처: https://docs.stripe.com/api/idempotent_requests (Stripe 공식 API 레퍼런스 — 멱등성 정의·헤더·만료 규칙의 1차 출처)
- **서버측 금액 검증(안티패턴 2)** — 포트원 공식: "결제 요청은 클라이언트 환경에서 이뤄지므로 스크립트 조작으로 amount 위변조 가능 → 클라이언트 조작은 원천 차단 불가 → 결제 후 서버에서 위변조 여부 반드시 검증". merchant_uid(주문번호)는 가맹점 서버가 고유 채번해 DB 저장, 대사 시 검증 키로 사용. 출처: https://portone.gitbook.io/docs/auth/guide/5/post (포트원 공식 "결제정보 사후 검증" — 금액 대조 절차의 1차 출처)
- **웹훅 기준 확정 + 중복 흡수(안티패턴 3·4)** — 포트원 공식: "Wi-Fi 끊김·브라우저 자동 리로드로 클라이언트 응답 유실 가능 → DB 처리는 웹훅 수신 데이터 기준으로 해야 누락 없음". Stripe 공식: 웹훅은 동일 이벤트 다중 수신·순서 비보장·최대 3일 재시도 → 핸들러는 멱등해야 함(이벤트 ID 추적 + DB 유니크 제약). 출처: https://portone.gitbook.io/docs/result/webhook (포트원 공식 웹훅 가이드) · https://docs.stripe.com/webhooks (Stripe 공식 웹훅 — 재시도·중복·순서 비보장의 1차 출처)
- **토스페이먼츠 확정 흐름** — 결제창 성공 리다이렉트 후 서버가 `/v1/payments/confirm`(V1) 또는 V2 결제 흐름으로 **승인 API 재호출**해야 확정(리다이렉트만으로는 미확정). 출처: https://docs.tosspayments.com/guides/v2/get-started/payment-flow (토스페이먼츠 공식 결제 흐름 — 승인 단계 명세). 세부 confirm 윈도우(리다이렉트 후 승인 제한 시간)는 작업 시점 문서 확인 필요.

> 출처: 위 PG 공식 연동 가이드(토스페이먼츠·포트원·Stripe — 2026-06 웹 확인) · 보안 점검·버그바운티 보고 집적 · 커머스 운영 관행. PG별 파라미터·필드 세부는 부패가 빠르므로 작업 시점 공식 문서가 진실.
