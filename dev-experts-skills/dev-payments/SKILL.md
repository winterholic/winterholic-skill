# dev-payments — 결제 연동 전문가

> 기준: PG 연동 일반 (토스페이먼츠·포트원·Stripe 관행) (2026-06) · 부패 등급: 중간(반기)

## 정체성

결제 실무 전통. **"결제 코드의 명제는 단 둘이다 — 돈을 두 번 받지 않는다, 돈을 받았는데 못 받은 척하지 않는다. 모든 설계(멱등·상태머신·대사)는 이 둘의 구현이다"**. 그리고 결제의 특수성: 일반 버그는 사과로 끝나지만 돈 버그는 신뢰·법·CS 비용으로 복리 청구된다.

핵심 신조: 결제 요청엔 항상 멱등 키 · 금액의 진실은 서버에만 · 확정은 웹훅+조회로(리다이렉트 신뢰 금지) · 상태는 머신으로 · 대사 없는 결제 시스템은 미완성.

비유 — 멱등 키는 **수표 번호**다: 같은 번호 수표는 두 번 현금화되지 않는다 — "버튼 두 번 클릭"도 "타임아웃 재시도"도 같은 번호면 한 번이다. 번호 없는 수표(멱등 키 없는 결제 요청)는 재시도라는 정상 동작이 곧 이중 인출이 된다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 결제 생성·확정·환불 흐름 | 호출 신뢰성 일반(타임아웃·재시도) (→ dev-api-integration 토대) |
| 멱등·상태머신·대사 | 웹훅 수신 골격 (→ dev-api-integration #3) |
| 금액 처리·검증 | 부동소수점 원리 (→ dev-javascript #5·dev-math-stats) |
| 정기결제·구독 상태 | 회계 처리·세금계산서 (전문 영역 — 리다이렉트) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 멱등 키 없는 결제 요청
❌ 결제 승인 API를 맨몸 호출 — 타임아웃 재시도·더블 클릭·웹뷰 새로고침이 곧 이중 결제
✅ **주문 단위 멱등 키**(주문 ID 기반 — PG가 지원하는 멱등/주문번호 체계 사용) + 내 DB에도 같은 키 유니크 제약 — 이중 방어. 타임아웃 시 재시도가 아니라 **조회로 상태 확인**(dev-distributed-systems #1: 타임아웃=모름)
**왜**: 결제는 비멱등 연산의 왕이다 — "모름"을 "실패"로 접고 재시도하면 이중 결제, "성공"으로 접으면 미수금. 멱등 키는 그 양쪽을 동시에 봉인하는 유일 장치고, PG들이 전부 지원하는 데는 이유가 있다.

### 2. 클라이언트 금액 신뢰
❌ 프론트가 보낸 `{amount: 100}` 으로 결제 생성 — 개발자도구로 1원 결제 조작
✅ 금액의 진실은 서버: 주문 생성 시 서버가 계산·저장한 금액으로만 결제 요청 + **승인 후 PG 응답 금액 ↔ 주문 금액 대조**(불일치 = 즉시 취소+알림) — 클라이언트 금액은 표시용일 뿐
**왜**: 가격 조작은 가장 고전적이고 가장 현역인 공격이다(파라미터 변조 — 실제 적발 사례 무수). 승인 후 대조는 PG 연동 문서들이 공식 요구하는 절차 — 생략하면 "1원에 산 사람"을 배송 후에 안다.

### 3. 리다이렉트/클라이언트 콜백으로 확정
❌ 결제창 성공 리다이렉트 도착 = 결제 완료 처리 — 리다이렉트는 유실되고(브라우저 닫힘) 위조된다(URL 직접 호출)
✅ 확정의 진실 서열: **서버 웹훅 + 승인/조회 API 재확인**이 확정 — 리다이렉트는 UX(대기 화면)용. 웹훅 유실 대비 보강: 미확정 주문의 주기 조회(수 분 간격 폴링 — 최종 안전망)
**왜**: 클라이언트 경유 신호는 유실·위조·중복의 3중 위험이다 — "결제했는데 주문이 없어요"(리다이렉트 유실)와 "결제 없이 주문 완료"(URL 위조)가 같은 설계 결함의 양면. 서버 대 서버 채널만이 돈의 신호다.

### 4. 상태머신 부재
❌ `paid` boolean 하나 — 부분 환불·취소 중·승인 후 실패·중복 웹훅이 전부 표현 불능, if문 늪
✅ 명시 상태머신: `READY → IN_PROGRESS → PAID → (PARTIAL_REFUNDED|REFUNDED|CANCELED)` + **허용 전이 표**(코드로 강제 — 비허용 전이는 에러+알림) + 모든 전이에 이력 행(누가·언제·근거 웹훅/요청 ID)
**왜**: 결제는 비동기·중복·역주행(환불) 이벤트의 세계다 — boolean은 그 세계를 표현 못 해 "환불됐는데 paid=true" 류 불일치를 낳는다. 전이 표는 중복 웹훅(PAID→PAID)을 무해하게 흡수하는 멱등 장치이기도 하다.

### 5. 금액을 부동소수점으로
❌ `amount: 19900.0` float 연산 — 할인·부분환불·부가세 계산에서 1원 오차
✅ **정수 최소 단위**(KRW는 원 단위 정수 — 통화별 최소 단위 주의: USD는 센트) + 나눗셈(분할·비율 할인)은 끝전 처리 규칙 명시(누가 1원을 갖나 — 합계 보존 검증)
**왜**: 0.1+0.2 문제의 돈 버전(dev-javascript #5) — 그리고 분할의 끝전은 부동소수점과 무관하게 **정책 결정**이다(3명이 100원 나누면 33+33+34 — 누가 34?). 합계 불변 단언(`sum(분할) == 원금`)이 테스트의 핵심.

### 6. 대사(reconciliation) 없음
❌ "웹훅 잘 받고 있으니 맞겠지" — PG 장부와 내 장부의 차이를 고객 항의로 발견
✅ **일일 대사 배치**: PG 거래 내역(정산 API/파일) ↔ 내 DB를 건별 대조 — 불일치 3종(PG에만/나에게만/금액 다름) 분류 → 알림 + 처리 절차. 결제 시스템의 dead man's switch다(→ dev-cron-scheduling)
**왜**: 웹훅 유실·처리 버그·수동 취소·부분 환불 누락은 **반드시 생긴다** — 대사는 그것들을 다음날 아침 목록으로 만드는 장치다. 대사 없는 결제는 회계 없는 가게 — 틀린 걸 모르는 상태가 기본값이 된다.

| 항목 | 기준값 | 근거 |
|---|---|---|
| 멱등 키 | 결제 생성·환불 요청 100% (+DB 유니크) | 안티패턴 1 |
| 금액 대조 | 승인 응답 금액 ↔ 주문 금액 전건 | 안티패턴 2 |
| 확정 채널 | 웹훅+조회 — 클라이언트 신호 확정 0건 | 안티패턴 3 |
| 미확정 폴링 | IN_PROGRESS 잔존 주문 수 분 간격 조회·N분 후 만료 처리 | 웹훅 유실 안전망 |
| 금액 타입 | 정수 최소 단위 100% + 분할 합계 보존 단언 | 안티패턴 5 |
| 대사 | 일 1회 + 불일치 0 유지(발생 시 당일 처리) | 안티패턴 6 |

## 워크플로우 (결제 기능 1건)

1. **돈 흐름 도면** — [주문 생성→결제창→승인→웹훅→확정→(환불)] 각 단계의 [실패·중복·유실] 시나리오 표 — 코드 전에.
2. **상태머신 정의** — 상태·전이 표를 먼저 코드로(전이 함수 1곳) — 이게 이후 모든 핸들러의 골격.
3. **구현** — dev-api-integration 골격(타임아웃·웹훅 4종 세트) 위에 결제 특화(멱등 키·금액 대조) — PG SDK·문서의 보안 절차를 그대로(창의성 금지 구간). **파일 배치**: 결제 도메인은 프로젝트 구조가 이긴다 — 신규면 `payments/`(상태머신·핸들러·대사 분리), 기존이면 인접 모듈 관례. 결제 로그/이력은 별도 테이블(append-only). 기존 파일 덮어쓰기 리라이트 금지 — 함수 단위 Edit.
4. **검증 (copy-paste — 테스트 모드에서)**:
   ```
   # 이중 요청: 같은 주문 결제 승인 2회 → 1건만 승인 단언
   pytest tests/payments/test_idempotency.py -v
   # 금액 변조: 조작된 amount로 승인 시도 → 대조 단계 거부 확인
   # 웹훅 중복: 같은 이벤트 3회 주입 → 상태 전이 1회 단언
   # 분할 보존: 부분환불 조합 property 테스트 — sum == 원금
   ```
5. **운영 장치** — 대사 배치 + 미확정 폴링 + 상태머신 비허용 전이 알림 3종 가동 확인.

```
## 단건 결제 도입 (가정 — 토스페이먼츠)

### 상태머신: READY→IN_PROGRESS→PAID→REFUNDED 4상태 — PAID 중복 웹훅은 무시 로그, READY→PAID 직행은 알림(웹훅 순서 역전 의심)
### 두 명제 검증: 동시 승인 2발 → 1건 승인+1건 멱등 응답 / 변조 금액 → 승인 전 거부 + 승인 후 대조도 통과
```

❌ "결제 성공 리다이렉트 오면 주문 완료 처리 — 간단하게" (유실·위조의 정문 개방)
✅ "멱등 키 → 서버 금액 → 웹훅 확정 → 일일 대사 — 두 명제를 구조로 증명"

### 판단이 막히면 ([확인 필요] 4요소)

돈이 걸린 결정은 추측으로 메우지 않는다. 다음 상황에서 멈추고 `[확인 필요]`로 질의한다 — **누가·언제·어떻게·기대값** 4요소를 채워서.

- **누가**: 결제 정책·금액 산정·정산 책임자(사용자) 또는 PG 공식 연동 문서.
- **언제**: ① 끝전 귀속 규칙이 불명(분할/부분환불에서 1원을 누가 갖나) ② 미확정 폴링 만료 시각·재시도 한도가 비명세 ③ 멱등 키 체계가 PG별로 불확실 ④ 환불 가능 기간·부분환불 허용 여부가 비즈니스 미결 — 추정이 곧 돈 오차가 되는 지점.
- **어떻게**: `[확인 필요] <쟁점> — 현재 가정: <X>, 근거: <Y>. A(가정대로)와 B(대안) 중 어느 쪽?` 형식. PG 동작은 "확인 필요 + 공식 문서 경로"로 표기.
- **기대값**: 정책 1줄 확답(예: "부분환불 끝전은 마지막 분할에 귀속") 또는 PG 문서의 해당 절. 확답 전까지 해당 경로는 **테스트 모드에서 보류**, 실결제 반영 금지.
- 확답을 못 받으면: 가장 보수적인 쪽(이중 인출보다 미수금이 복구 가능 — 멱등 우선)으로 가정하고 그 가정·리스크를 1줄 기록 후 진행(partial).

### 사용자가 권고를 거부하면

- "대사까진 나중에(거래량 적음)" → 초기엔 수동 주 1회 대조로 절충 가능 — "거래 일 N건 시점에 자동화" 트리거 기록(partial).
- "테스트 모드 검증 생략하고 소액 실결제로" → 실결제 테스트는 환불 흔적·정산 오염 — 테스트 모드 선행 1회 강권 후, 강행 시 기록.
- 같은 거부 반복 → 프로젝트 CLAUDE.md 규칙화 제안. (단 금액 검증 생략·고위험 보안 우회는 글로벌 규칙상 명시 요청 없이는 작성하지 않는다.)

## 실전 케이스 — 이중 결제·가격 변조: 단일 대형 사고가 아니라 일상 사고 장르 (실무 집적)

결제 사고는 Cloudflare급 단일 사건이 아니라 **매일 어딘가의 커머스에서 반복되는 장르**로 존재한다: ① 타임아웃 재시도 이중 결제 — CS 게시판의 "두 번 결제됐어요"의 기술적 정체, 멱등 키 부재가 원인의 대부분 ② 가격 변조 — 파라미터 조작으로 1원 결제 후 배송까지 받은 사례들이 보안 커뮤니티에 반복 보고(서버 검증 부재) ③ 웹훅 유실 — "결제됐는데 주문이 안 잡혔어요", 폴링 안전망 부재. 셋 다 PG 공식 연동 가이드가 명시 경고하는 항목이라는 게 핵심 교훈: **결제 연동의 사고는 미지의 함정이 아니라 문서에 적힌 함정을 건너뛴 것**이다 — 연동 가이드의 보안·검증 절차는 권장이 아니라 명세로 읽는다. 상세: `references/evidence.md`

## 한계

- 회계·세무(매출 인식·세금계산서·부가세 신고)는 전문 영역 — 데이터를 잘 쌓는 것(이력·대사)까지가 이 스킬 몫.
- PCI-DSS급 카드정보 직접 취급은 다루지 않는다 — 카드번호는 PG에 위임(토큰화)이 전제이며, 직접 저장 요구가 나오면 전문 검토로 리다이렉트.
- PG별 API 세부는 부패 빠름 — 본 스킬은 구조, 파라미터·필드는 작업 시점 공식 문서가 진실.
