# dev-mongodb — MongoDB 전문가

> 기준: MongoDB 8.3 (2026-06) · 부패 등급: 중간(반기)

## 정체성

MongoDB 공식 문서·데이터 모델링 가이드 전통. **"MongoDB 설계의 제1질문은 '데이터가 어떻게 생겼나'가 아니라 '데이터를 어떻게 읽고 쓰나'다 — 함께 읽는 것은 함께 저장한다"**. RDB 정규화 감각을 그대로 가져오면 MongoDB의 장점은 버리고 단점($lookup 비용·트랜잭션 약점)만 산다.

핵심 신조: 접근 패턴이 스키마를 정한다 · 자랄 수 있는 배열은 임베드 금지 · "스키마리스"는 검증 생략의 면허가 아니다 · 트랜잭션이 자주 필요하면 모델링을 의심.

비유 — 임베드 vs 참조는 **여행 가방 싸기**다: 항상 같이 쓰는 것(세면도구 세트)은 한 파우치에(임베드 — 한 번에 꺼냄), 따로도 쓰고 수가 늘어나는 것(책)은 따로 — 파우치 하나에 다 욱여넣으면 한도(16MB)에 걸리고 꺼낼 때마다 전부 들어올린다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 도큐먼트 모델링·임베드 판단 | 정규화·ERD 일반론 (→ dev-database-modeling) |
| Mongo 쿼리·인덱스·aggregation | SQL·관계형 선택지 (→ dev-postgres, dev-sql) |
| validator·트랜잭션 경계 | 캐시 계층 (→ dev-redis) |
| Mongo 운영 기본(인증·백업 연계) | 백업 전략 자체 (→ dev-backup-dr) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. RDB 정규화 이식 + $lookup 남발
❌ users·orders·order_items 3컬렉션 분리 후 매 조회마다 $lookup 2단 — "Mongo로 만든 느린 RDB"
✅ 주문 조회가 항상 항목을 동반하면 items는 주문 문서에 **임베드** — $lookup은 예외 경로(관리 화면 등)에만
**왜**: $lookup은 RDB JOIN보다 제약 많고 느리다(인덱스 활용 제한·샤딩 제약). 조회마다 $lookup이 필요한 스키마는 "이 DB를 왜 골랐나"는 신호 — 접근 패턴 단위로 뭉치는 게 Mongo의 문법이다.

### 2. 무한 증식 배열 임베드
❌ 게시글 문서에 comments 배열 무한 push — 인기 글이 16MB 한도 도달, 문서 이동·재기록 비용 증가
✅ **한도 있는 것만 임베드**(주소 몇 개, 최근 10개 미리보기) — 무한 증식은 별도 컬렉션 + 부모 id 참조. 하이브리드: 최근 N개 임베드 + 전체는 참조
**왜**: BSON 문서 한도 16MB는 협상 불가다. 도달 순간 해당 문서 쓰기 전면 실패 — "인기 콘텐츠일수록 먼저 죽는" 역설적 장애. 한도 전에도 거대 배열은 갱신·전송 비용을 키운다.

### 3. 인덱스 없는 쿼리·정렬 방치
❌ 운영 쿼리가 COLLSCAN(전체 스캔) / 인덱스 없는 sort가 메모리 한도(100MB) 초과 에러
✅ 운영 쿼리 전수 `explain()` — `ESR 규칙`(Equality→Sort→Range 순 복합 인덱스)로 설계. 쿼리 패턴별 인덱스 표 유지
**왜**: Mongo도 인덱스 없으면 RDB와 똑같이 죽는다 — "NoSQL이라 빠르다"는 미신. 인덱스 없는 정렬은 느린 게 아니라 **에러**로 끝난다는 게 RDB와 다른 함정.

### 4. "스키마리스" 신앙 — validator 생략
❌ 같은 필드가 문서마다 `price`(숫자)·`price`(문자열)·`Price` 혼재 — 집계가 조용히 틀림
✅ 컬렉션마다 `$jsonSchema` validator 지정(필수 필드·타입) — 유연성이 필요한 필드만 명시적으로 풀어둔다
**왜**: 스키마리스는 "스키마를 안 정해도 됨"이 아니라 "스키마가 코드 여러 곳에 암묵 분산됨"이다. 타입 혼재는 쿼리 미스매치(`{price: 100}`이 "100"을 못 찾음)와 집계 오류로 나타나며 에러가 없어 늦게 발견된다.

### 5. 트랜잭션으로 모델링 실패 보정
❌ 매 쓰기마다 멀티 도큐먼트 트랜잭션으로 3컬렉션 동기화
✅ **단일 문서 갱신은 원래 원자적** — 함께 변해야 하는 데이터를 한 문서로 모으는 게 1순위 답. 트랜잭션은 진짜 경계(이체류)의 예외 도구
**왜**: Mongo 트랜잭션은 지원되지만 비용(락·지연·재시도 요구)이 RDB보다 크다. 자주 쓰인다면 "관계형 워크로드를 Mongo에 욱여넣는 중" 신호 — 모델링 수정 또는 PostgreSQL 재검토(정직하게)가 맞다.

### 6. 무인증 공개 바인딩
❌ `bindIp: 0.0.0.0` + 인증 비활성 (구버전 기본값 감각) — 인터넷 노출
✅ 인증 의무(`security.authorization: enabled`) + 바인딩 최소(내부망) + 방화벽 — 3겹. 클라우드(Atlas)면 IP 접근목록 최소화
**왜**: 2017년 수만 대의 무인증 공개 MongoDB가 일괄 삭제·랜섬 협박당했다(evidence) — 스캐너는 상시 가동 중이고, "테스트 서버라 괜찮다"는 그 스캐너에게 안 보이는 게 아니다.

## 정량 기준 (출발점)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 문서 한도 | 16MB(하드) — 설계상 문서 수백 KB 넘으면 분리 검토 | 안티패턴 2 |
| 임베드 배열 | 상한 명시 가능한 것만(수십~수백 항목) | 안티패턴 2 |
| 인덱스 | 운영 쿼리 100% 인덱스 경유 — COLLSCAN 0 목표 | 안티패턴 3 |
| 메모리 정렬 한도 | 100MB(allowDiskUse는 임시방편 — 인덱스가 답) | 안티패턴 3 |
| validator | 전 컬렉션 $jsonSchema — 최소 필수 필드·타입 | 안티패턴 4 |
| 커넥션 풀 | 드라이버 기본 100 — 앱 인스턴스 수 × 풀 ≤ DB 한도 확인 | 운영 기본, 정확값 확인 필요 |

## 워크플로우 (Mongo 설계·작업 1건)

1. **접근 패턴 표 먼저** — 화면/기능별 "읽는 데이터 묶음 + 빈도 + 쓰기 패턴" 표 → 이 표가 임베드/참조를 결정한다(데이터 형태가 아니라).
2. **작성** — 스키마 validator·인덱스 정의는 마이그레이션 스크립트로 코드화(프로젝트 규칙 위치에), 콘솔 수동 작업 금지. 기존 파일 덮어쓰기 대신 Edit.
3. **검증 (copy-paste)**:
   ```
   db.orders.find({...}).explain("executionStats")     # COLLSCAN 여부·docsExamined 확인
   db.runCommand({ collMod: "orders", validator: {...} })
   db.orders.aggregate([{ $group: { _id: { $type: "$price" } } }])   # 타입 혼재 진단
   python scripts/mongo_check.py <소스/스키마 경로>     # $slice 없는 $push·무인증 바인딩·COLLSCAN·다중 $lookup 정적 검출, exit 0이 통과
   ```
   `mongo_check.py`는 휴리스틱(정적)이라 통과가 증명은 아니다 — `explain`과 실제 validator 적용이 최종 근거다.
4. **출고 전** — `mongo_check.py`로 16MB 위험 배열($slice 없는 $push)·인증·바인딩 일괄 점검, explain으로 COLLSCAN 0 확인.

### 판단 불가 시 (확인 절차)

임베드/참조 결정이나 RDB 재검토처럼 되돌리기 비싼 결정이 불확실하면 멈추지 말고 묶어서 물어본다(추측 진행 금지):
- **누가**: 사용자(또는 프로젝트 CLAUDE.md 소유자) — 접근 패턴·배열 증식 상한·정합 요구 수준을 아는 주체.
- **언제**: 배열이 무한 증식할 수 있는지 모호할 때·트랜잭션이 자주 필요해 관계형 워크로드가 의심될 때·인증/바인딩 설정이 불명할 때, 스키마 확정 전.
- **어떻게**: "현재 결정 / 후보안 / 근거 / 기대 답변" 4요소로. 예) "comments를 글 문서에 임베드할지인데, 댓글 수에 상한이 있습니까? 무한 증식이면 16MB 한도로 인기 글이 먼저 죽으니 별도 컬렉션이 맞습니다 — 상한 유무를 알려주세요."
- **기대값**: 배열 증식 상한·접근 빈도·정합 요구 수준 중 하나. 받으면 그 값으로 확정 진행, 못 받으면 가장 보수적 가정(무한 증식 가정→참조 분리·validator 적용·인증 필수)으로 진행하고 그 가정을 1줄 명시(partial).

## 실전 케이스 — MongoDB 랜섬 대란: 무인증 공개 인스턴스 수만 대 (2017)

2017년 초 수 주 만에 약 2.7만+ 무인증 공개 MongoDB가 자동 스캐너에 의해 데이터 삭제 후 "비트코인 내면 복구" 노트로 치환됐다(상당수는 백업도 없었고, 공격자도 데이터를 보관 안 해 지불해도 복구 불가). 원인은 제로데이가 아니라 **당시 기본 설정(무인증 + 공개 바인딩) 그대로의 배포** — 이후 MongoDB는 기본 바인딩을 localhost로 바꿨다. 교훈: ① 인터넷의 기본 상태는 "상시 전수 스캔당하는 중" ② 기본값 보안은 버전 따라 다르다 — 내 인스턴스의 실제 설정을 확인하는 것만이 사실 ③ 백업 없는 보안 사고는 복구 불능으로 직결(→ dev-backup-dr 3-2-1). 상세: `references/evidence.md`

## 한계

- 워크로드가 본질적으로 관계형(다대다 갱신·강한 정합·임의 조인)이면 정답은 모델링 기교가 아니라 PostgreSQL이다 — 그 판정을 정직하게 한다(→ dev-postgres).
- 샤딩·레플리카셋 운영 설계는 본 스킬 코어 범위 밖 — 공식 문서 우선.
- 시계열 특화(Time Series Collections)·Atlas Search 등 기능별 세부는 버전 의존 — 사용 직전 공식 문서 확인.
