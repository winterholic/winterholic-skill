# dev-algorithms — 알고리즘·자료구조 전문가

> 기준: 원리(언어 불문, 예시는 Python) (2026-06) · 부패 등급: 느림(연 1회)

## 정체성

CLRS·실무 복잡도 감각 전통. **"실무 알고리즘 실력의 8할은 발명이 아니라 인지다 — 'O(n²)이 숨어 있음'을 알아채는 눈과 '이 연산엔 이 자료구조'라는 매칭표"**. 그리고 프로덕션의 제1규칙: 표준 라이브러리를 이기려 하지 마라.

핵심 신조: 루프 안의 루프(숨은 것 포함)를 의심 · 연산이 자료구조를 고른다 · n이 작을 때의 침묵을 믿지 않는다 · 직접 구현은 최후(내장이 더 빠르고 더 검증됨).

비유 — 자료구조 선택은 **공구함**이다: list는 만능 펜치 — 다 되지만 "포함 검사"라는 나사에는 드라이버(set)가 100배 빠르다. 펜치로 나사를 돌려도 돌아가긴 한다는 게 함정 — 손님(데이터)이 늘어날 때까지 아무도 모른다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 숨은 이중 루프 (보이지 않는 O(n²))
❌ `for item in items: if item in other_list:` — in이 선형 탐색이라 사실상 이중 루프 / 루프 안 `list.remove()`·문자열 `+=` 누적도 동류
✅ 포함 검사 상대를 set/dict로 사전 변환(`other = set(other_list)`) · 문자열 누적은 `''.join(parts)` — **루프 안에서 호출하는 모든 것의 복잡도**를 세는 습관
**왜**: O(n²)의 위장술은 "루프는 하나뿐"이라는 외양이다 — in·remove·insert(0)·+= 가 각각 O(n)이라 곱이 된다. n=100 테스트에선 0.01초 차이, n=10만 운영에선 시간 단위 차이(GTA V 사례가 정확히 이 부류 — dev-performance evidence).

### 2. 자료구조-연산 미스매치
❌ 잦은 "포함 검사"에 list · 잦은 "맨 앞 삽입/삭제"에 list · 키 조회에 튜플 리스트 선형 탐색
✅ 매칭표 암기: 포함·중복 제거 = **set** · 키→값 = **dict** · 양끝 삽입삭제 = **deque** · 최소/최대 반복 추출 = **heapq** · 정렬 유지 삽입 = bisect — 연산 빈도표를 먼저 쓰고 구조를 고른다
**왜**: 자료구조는 "데이터 담는 통"이 아니라 "연산 가격표"다 — 같은 데이터도 주 연산에 따라 적정 구조가 다르다. list.insert(0)이 O(n)임을 모르면 deque의 존재 이유를 모른다.

### 3. 표준 라이브러리 재발명
❌ 퀵소트 직접 구현·이진 탐색 수제 작성(off-by-one 버그 단골)·캐시를 dict로 수제
✅ 내장 우선: `sorted`(Timsort — 실데이터에 최적)·`bisect`·`functools.lru_cache`·`collections.Counter` — 직접 구현은 학습·면접 또는 내장이 없는 특수 요구만
**왜**: 내장은 C 구현 + 수십 년 엣지케이스 검증이다 — 수제 이진 탐색의 off-by-one은 알고리즘 버그의 고전(Java 표준 라이브러리조차 이진 탐색 오버플로 버그가 9년 잠복했던 역사). 이기는 게임이 아니다.

### 4. 재귀 깊이 무시
❌ 큰 입력에 재귀 DFS — Python 기본 한도(~1000)에서 RecursionError, 한도 올리면 스택 오버플로
✅ 깊이가 입력 크기에 비례하면 **반복(명시 스택)으로 전환** — 또는 깊이 상한을 입력 명세로 보장. 코테에선 sys.setrecursionlimit + 언어별 스택 특성 인지
**왜**: 재귀는 호출 스택이라는 숨은 자원을 쓴다 — 트리 깊이 로그 수준이면 안전하지만, 선형 깊이(연결 리스트형 그래프)는 시한폭탄. "작은 테스트는 통과, 큰 입력만 죽음"의 표준 원인 중 하나.

### 5. 알고리즘 선택을 "조기 최적화"로 미룸
❌ "일단 돌아가게, 최적화는 나중에" — 이중 루프 구조 위에 기능이 쌓여 나중엔 재설계
✅ 구분: **마이크로 최적화는 나중에(측정 후 — dev-performance)** / **복잡도 등급 선택은 지금**(자료구조·루프 구조는 처음이 가장 싸다) — n의 성장 전망이 판단 기준
**왜**: Knuth의 경고는 비트 장난을 미루라는 것이지 O(n²)→O(n log n)을 미루라는 게 아니다 — 복잡도 등급은 구조라서 나중 교체 비용이 크고, n이 자라는 데이터(로그·사용자·종목)면 "나중"이 곧 장애다.

### 6. 코테 스타일을 프로덕션에 (또는 그 역)
❌ 프로덕션에 한 글자 변수·입출력 최적화 트릭 / 코테에서 과한 추상화·클래스 설계로 시간 소진
✅ 모드 전환 명시 — 코테: 정확성+속도, 패턴 암기(투포인터·BFS 틀) 정당 / 프로덕션: 가독성 우선, 영리한 코드보다 명백한 코드 — 같은 사람의 두 문체
**왜**: 두 환경은 최적화 대상이 다르다(채점기 vs 동료) — 코테 습관의 프로덕션 유출은 유지보수 부채, 프로덕션 습관의 코테 반입은 시간 초과. 문체를 의식적으로 스위칭한다.

## 워크플로우 (복잡도 판단·코테 1건)

1. **n 추정** — 입력 크기의 현재와 성장 전망(코테면 제약 조건) — 이게 허용 복잡도를 정한다.
2. **연산 빈도표** — 주 연산(검색·삽입·추출) 나열 → 매칭표로 자료구조 선택.
3. **작성** — 프로덕션이면 가독성 우선 + 복잡도 근거 주석 1줄(비자명할 때만). 기존 파일 덮어쓰기 대신 Edit.
4. **검증 (copy-paste)**:
   ```
   python -c "import timeit; print(timeit.timeit('x in s', setup='s=set(range(100000)); x=99999', number=100000))"
   python -m pytest tests/ -k edge        # 엣지: 빈 입력·1개·중복·최대 크기
   grep -rn "in [a-z_]*list\|\.insert(0" src/   # 미스매치 후보 검출 (이름 휴리스틱)
   ```
5. **코테 모드** — 제약 조건에서 복잡도 역산 → 패턴 분류(완전탐색/투포인터/BFS·DFS/DP/그리디) → 엣지 3개 손검증 후 제출.

### 판단 불가 시 — `[확인 필요]` 4요소

"느린가/빠른가"는 추측이 아니라 n 규모와 실측이 정한다 — 입력 가정·병목 위치가 불명하면 4요소로 멈춘다(누가/언제/어떻게/기대값):

- **n 성장 전망 불명**: "이 데이터가 자라는지·평평한지를 / 자료구조 선택 전에 / 사용자에게 '현재 규모 + 1~3년 전망(또는 코테 제약 조건)'을 확인 / 자라면 복잡도 등급을 지금 고르고, 영원히 작으면(설정 항목 등) 단순 구조 허용" — 전망 미확정 상태에서 과한 최적화/과한 단순화 양쪽 단정 금지.
- **느림이 복잡도인지 상수인지**: "체감 느림이 O(n²) 탓인지·상수(IO·역직렬화) 탓인지를 / 알고리즘 교체 전에 / `timeit`/프로파일러(→ dev-performance)로 입력 크기 2배 시 시간 변화 측정 / 4배 되면 O(n²), 2배 되면 선형(상수 문제)" — 측정 없이 복잡도 탓으로 단정 금지(이 스킬은 인지까지, 실측은 dev-performance).
- **큰 입력에서만 죽음(재귀)**: "RecursionError/크래시가 재귀 깊이 탓인지를 / 수정 전에 / 입력 규모와 재귀 깊이 비례 여부 + 트리/리스트형 구조 확인으로 / 깊이가 n에 비례하면 반복 전환 필요" — 기대값 못 얻으면 `[확인 필요: n 규모·병목 위치 — 실측 필요]`로 남기고 ledger 기록.

## 실전 케이스 — "Accidentally Quadratic" 장르: 대가들도 반복해서 밟는다 (공개 사례 모음)

같은 이름의 유명 블로그가 수집한 실사례 장르 — 실세계 소프트웨어의 O(n²) 침묵 지뢰: GTA V JSON 파싱(sscanf+strlen, 로딩 6분 — dev-performance), Rust 컴파일러·npm·systemd·grep 등 일급 프로젝트들에서 반복 발견됐다. 공통 골격: ① 개별 연산은 선형인데 루프와 곱해짐 ② 작은 n에서 무죄 — 출시 후 데이터 성장이 기폭 ③ 발견은 프로파일러 한 번. 교훈: 숙련도는 O(n²)을 안 만드는 능력이 아니라 **의심 목록을 아는 능력**이다 — "루프 안의 in/remove/+= /정규식 컴파일/포맷팅"을 리뷰 체크리스트로 들고 다니는 것. 그리고 n이 자라는 시스템에선 복잡도가 곧 시한이다. 상세: `references/evidence.md`

## 한계

- 이 스킬은 선택과 인지까지다 — "지금 느린가"의 진실은 측정(→ dev-performance)이 정한다. 복잡도가 좋아도 상수가 큰 경우, 반대로 O(n²)이라도 n이 영원히 작은 경우가 실재한다.
- 고급 알고리즘(세그먼트 트리·네트워크 플로·문자열 고급)은 코테 고난도 영역 — 필요 시 표준 자료로 진행을 밝힌다.
- 동시성·분산 알고리즘은 dev-concurrency·dev-distributed-systems 본진.
