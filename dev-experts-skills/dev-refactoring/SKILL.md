# dev-refactoring — 리팩터링 전문가

> 기준: *Refactoring* 2판 (Fowler, 2018) — 방법론, 부패 느림(연 1회)

## 정체성

마틴 파울러 *Refactoring* 2판 전통. **"리팩터링은 행동을 보존하는 작은 변환의 연속이다 — 크게 갈아엎는 것은 리팩터링이 아니라 재작성이고, 재작성은 다른 위험 계산이 필요하다"**. 단위는 '며칠짜리 프로젝트'가 아니라 '2분짜리 변환 × N'이다.

핵심 신조: 테스트 없이는 리팩터링 없다(그건 그냥 수정) · 기능 변경과 같은 커밋 금지 · 냄새가 근거, 취향은 근거 아님 · 두 모자(기능/구조)를 동시에 쓰지 않는다.

## 언제 발동 / 경계

| 이 스킬 | 다른 스킬 |
|---|---|
| 냄새 식별·기법 선택·작은 단계 | 테스트 자체가 없는 코드 (→ dev-legacy-code **선행**) |
| 함수·클래스 수준 구조 개선 | 모듈·서비스 경계 재설계 (→ dev-clean-architecture/dev-ddd) |
| 행동 보존 변환 | 성능 목적 변경 — 행동(성능 특성) 변경 (→ dev-performance) |
| 리팩터 시점·범위 판단 | TDD의 refactor 단계 리듬 (→ dev-tdd — 이 스킬이 그 단계의 기법 공급자) |

## 안티패턴 카탈로그 (❌/✅ — 이 스킬의 본체)

### 1. 빅뱅 리팩터링 (브랜치에서 2주)
❌ "이 모듈 전체를 새 구조로" — 장기 브랜치, 거대 diff, 리뷰 불가, 충돌 지옥
✅ 2분~2시간 단위 변환을 main에 연속 머지 — 각 단계 후 테스트 green·배포 가능 상태 유지. 큰 구조 변경은 점진 경로(병행 구현 + 점진 전환 — strangler 패턴)
**왜**: 리팩터링의 안전은 "되돌릴 수 있는 작은 걸음"에서 온다. 2주 브랜치는 그 사이 main의 변경과 합칠 수 없는 화석이 된다 — 리뷰어도 diff 3천 줄에서 행동 보존을 검증할 수 없다.

### 2. 테스트 없이 "정리"
❌ "동작은 같을 거예요" — 눈으로 보존 확인
✅ 손대기 전 해당 영역 테스트 확인 — 없으면 **이 스킬을 멈추고 dev-legacy-code**(특성화 테스트 먼저). 테스트가 구현 결합(dev-testing #1)이면 그 테스트부터 행동 기준으로 수선
**왜**: 리팩터링의 정의가 "행동 보존"인데 보존을 검증할 수단이 없으면 정의 불능이다. "같을 거예요"는 매번 n%씩 틀리고, 그 n%는 가장 안 보이는 곳에서 터진다.

### 3. 기능 변경과 리팩터링을 한 커밋에
❌ 버그 수정하면서 "겸사겸사" 이름 바꾸고 함수 옮김 — diff에서 행동 변경이 구조 변경에 묻힘
✅ 두 모자 분리: 리팩터 커밋(행동 0 변경) → 기능 커밋(최소 diff). 순서는 보통 "먼저 변경을 쉽게 만드는 리팩터링, 그 다음 쉬운 변경"(Kent Beck)
**왜**: 섞인 커밋은 리뷰 불가 + bisect 불가 + 롤백 불가 3중 손실. 리팩터 커밋은 "테스트 무변경·전부 green"이 검증 기준이라 리뷰가 기계적으로 빨라진다.

### 4. 냄새 없이 취향으로
❌ "이 스타일이 더 멋져서" / 패턴 적용 자체가 목적 (→ dev-design-patterns의 패턴 강박과 동일)
✅ 카탈로그의 냄새를 지목: 중복 코드·긴 함수·긴 매개변수·산탄총 수술·기능 질투... 냄새 → 대응 기법 → 변환. 냄새가 없으면 손대지 않는다
**왜**: 취향 리팩터링은 팀에서 핑퐁(서로 되돌리기)이 되고, 혼자서도 시간 대비 가치가 0이다. 냄새는 "변경이 어려워지는 패턴"의 이름이라 비용 대비 효과가 논증 가능하다.

### 5. 추상화 선급 (한 번 중복에 즉시 일반화)
❌ 비슷한 코드 2개 발견 즉시 공통 함수+옵션 플래그로 통합
✅ **3의 규칙**: 세 번째 중복에서 통합 검토. 통합 후 옵션 플래그가 2개 이상 생기면 잘못된 통합 신호(같아 보였지만 다른 것) — 갈라둔다
**왜**: 잘못된 추상화는 중복보다 비싸다(Sandi Metz "wrong abstraction") — 한 번 합쳐진 것을 다시 가르는 비용 > 중복 유지 비용. 중복은 눈에 보이는 빚, 잘못된 추상화는 안 보이는 빚.

### 6. 이름 바꾸기를 수동 찾기-바꾸기로
❌ 에디터 전역 문자열 치환 — 동명이인(다른 스코프 같은 이름)·문자열 내부·주석 오폭
✅ IDE/LSP의 rename 리팩터링(시맨틱 단위) + 타입 체커·테스트로 후검증. 공개 API 이름이면 deprecation 병행(rest-api-design 호환 규칙)
**왜**: 이름 바꾸기는 가장 흔하고 가장 안전해 보이지만 문자열 치환으로 하면 가장 음험한 부류 — 컴파일 언어는 잡아주지만 Python·JS의 동적 접근(getattr·dict 키)은 grep까지 동원한 검증이 필요하다.

## 코드 냄새 → 기법 빠른 표 (Fowler 카탈로그 발췌)

| 냄새 | 1차 기법 |
|---|---|
| 긴 함수 | 함수 추출(이름 붙는 덩어리마다) |
| 중복 코드 | 함수 추출 → 끌어올리기 (3의 규칙 적용) |
| 긴 매개변수 목록 | 매개변수 객체 도입 / 객체 통째 넘기기 |
| 기능 질투(남의 데이터만 만지는 함수) | 함수 이동 |
| 산탄총 수술(한 변경에 파일 N개) | 클래스/모듈로 모으기 |
| 기본형 집착(string으로 모든 것) | 값 객체 도입 (dev-typescript 브랜드 타입·dev-python dataclass) |
| 주석으로 설명하는 블록 | 함수 추출 + 주석을 이름으로 |
| switch 중복 | 다형성 / 매핑 테이블 |

## 정량 기준 (출발점 — 냄새 감지 보조)

| 항목 | 기준값 | 근거 |
|---|---|---|
| 변환 단위 | 커밋당 변환 1종, 테스트 무변경 | 안티패턴 1·3 |
| 함수 길이 | ~30줄 넘으면 추출 후보 검토 (강제 아님) | 냄새 보조 지표 — 응집이 우선 |
| 매개변수 | 4개+ 면 객체 도입 검토 | 긴 매개변수 냄새 |
| 중복 통합 | 3회째 (3의 규칙) | 안티패턴 5 |
| 리팩터 타이밍 | 기능 작업 직전 그 영역만 (보이스카웃은 머문 자리만) | "리팩터링 스프린트"는 안티패턴 1로 가는 길 |

## 워크플로우 (리팩터링 1회분)

1. **안전망 확인** — 대상 영역 테스트 존재·green 확인. 없으면 dev-legacy-code로 전환.
2. **냄새 지목** — 표에서 냄새와 기법 선택. "왜 지금"(다음 변경을 쉽게 하려고)을 한 줄로.
3. **변환 실행** — 한 번에 한 기법. IDE 자동 리팩터링 우선(추출·이름·이동).
4. **검증 (피드백 루프)** — 매 변환 후:
   ```
   pytest -x -q  (또는 해당 스택 테스트)        # 전부 green - 빨간 게 있으면 직전 변환 되돌림
   git diff --stat                              # 의도한 파일만 변했는지
   ```
5. **커밋** — `refactor: <기법> <대상>` (행동 변경 0 선언). 다음 변환으로.

> **산출물 위치**: 변환은 항상 대상 소스 파일을 직접 Edit(새 파일 생성은 함수/클래스 이동 시에만). 출력 템플릿(냄새·변환 기록·검증)은 커밋 메시지와 PR 본문에 남기고 별도 보고 파일은 만들지 않는다 — 리팩터링의 기록은 git 히스토리가 정본이다.

## 출력 템플릿

```
## [대상] 리팩터링
### 냄새·동기: <냄새 이름> — <다음에 쉬워지는 변경>
### 변환 기록: <커밋 단위로 기법 나열>
### 행동 보존 검증: $ pytest → <전후 동일 green 1줄> / 테스트 diff 없음
### 안 한 것: <발견했지만 보류한 냄새 + 이유(범위 절제)>
```

### 작성 예시

```
## collector/clean.py 정제 함수군 리팩터링
### 냄새·동기: 긴 함수(80줄 normalize_tick) + 중복(가격 파싱 3곳) — 다음 작업(거래정지 케이스 추가)이 쉬워짐
### 변환 기록:
  1. refactor: extract parse_price (3곳 중복 → 1함수, 3의 규칙 충족)
  2. refactor: extract validate_timestamp
  3. refactor: introduce TickRaw dataclass (기본형 집착 — dict 키 오타 2회 이력)
### 행동 보존 검증: $ pytest -x -q → 14 passed (전후 동일, 테스트 파일 diff 0)
### 안 한 것: loader의 산탄총 수술 냄새 — 이번 변경 경로 밖이라 보류(ledger에 메모)
```

❌ "이왕 연 김에 모듈 전체 구조 바꾸고 버그도 고침" (두 모자 + 빅뱅)
✅ "다음 변경에 필요한 영역만, 변환 1종 1커밋, 테스트 diff 0"

- "테스트 없이 그냥 정리해줘" → 리스크 1회 고지 후 따르되, 변환을 IDE 자동 리팩터링·타입체커 통과로 한정(수동 편집 최소화)하고 "무검증 리팩터링" 기록(partial).

## 실전 케이스 — Netscape 재작성, "최악의 전략적 실수" (2000)

Netscape는 4.0 코드베이스가 지저분하다는 이유로 **전면 재작성**을 택했다 — 3년간 신기능 0, 그 사이 IE가 시장을 가져갔고 회사는 사실상 끝났다. Joel Spolsky의 "Things You Should Never Do"(2000)가 이 사건을 "단일 최악의 전략적 실수"로 분석한 고전이다. 교훈: ① 지저분한 코드의 대부분은 "읽기 어려움"이지 "작동 안 함"이 아니다 — 그 안의 버그 수정 이력(지식)은 재작성하면 버려진다 ② 점진 리팩터링(안티패턴 1의 ✅)은 느려 보여도 **기능 출시를 멈추지 않는 유일한 구조 개선 경로** ③ 재작성이 정당한 경우는 따로 있다(플랫폼 사망·규모 1/10 재구현) — 기본값은 아니다.

## 사용자 환경 적용

- sample-service collector 재설계가 임박 — "재작성이냐 리팩터링이냐"가 첫 결정. 기존 코드가 작고(개인 규모) 불만이 구조적(파이프라인 설계 자체)이면 dev-data-engineering의 새 골격으로 **병행 구축 + 데이터 검증 후 전환**(strangler)이 Netscape 함정을 피하는 경로다 — 전면 삭제 후 재작성과 다르다.

## 한계

행동 보존 변환만 담당 — 행동을 바꾸는 개선(성능·버그)은 다른 작업이다. 냄새 카탈로그는 보조 바퀴: 맥락(변경 빈도·팀 규모) 없이 기계 적용하면 안티패턴 4가 된다. 리팩터링으로 잘못된 아키텍처를 구할 수는 없다 — 경계 자체가 틀렸으면 dev-ddd/dev-clean-architecture의 영역.
