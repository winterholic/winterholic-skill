# Code Walkthrough — 코드 한 줄 한 줄 독해 보고서

## 이 스킬이 푸는 문제

LLM이 코드를 작성하면서 **생산 속도가 인간의 이해 속도를 앞질렀다.** 클린코드 원칙대로 잘게 쪼개진 코드일수록, 한 줄을 이해하려면 그 변수가 정의된 다른 메서드로 올라가고, 그 결과값의 출처로 또 올라가다 보면 1줄 읽는 데도 막대한 시간이 걸린다. 내가 짠 코드도 아니기에 더 그렇다.

`pr-review`·`self-review`는 **"문제가 있나 없나"를 탐지해 보고서로 낸다.** 빠르지만, LLM이 놓친 부분은 그냥 넘어가고 코드를 전체적으로 훑지 못한다. 이 스킬은 정반대다 — **지정 범위의 코드를 빠짐없이 따라 읽으며 "이 줄은 왜 이렇게 썼고, 이 값은 어디를 타고 와서 어디로 가는가"를 풀어준다.** 그 과정에서 "이래서 문제다 / 이래서 잘 짜였다"가 자연히 드러난다.

따라서 이 스킬의 산출물은 **읽기 위한 문서**다. 파일을 하나하나 뜯어보기 편한 구조 — 좌측 파일트리로 이동하고, 코드청크 바로 아래 해설이 붙고, 변수·함수 참조는 정의로 점프하는 링크로 연결된다.

> **두 스킬의 관계** — `pr-review`/`self-review`는 *판정*("이 변경 통과시킬 만한가"), 본 스킬은 *독해*("이 코드를 끝까지 이해하기"). 사용자가 PR 전 점검이나 PR 리뷰를 요청하면, 해당 스킬을 돌린 뒤(또는 함께) 같은 범위로 이 스킬도 돌려 "판정 + 완전한 독해"를 둘 다 남긴다.

## 절대 규칙

- **읽기 전용**: 파일 Read, `git log/show/diff`, `gh pr view/diff`만. **코드 수정·commit·push 금지.** 사용자가 명시적으로 수정을 요청하면 그때만 별도로.
- **저장 위치**: `./artifacts/code-walkthrough/`
- **출력**: **단일 자기완결 HTML 파일**. CSS·JS는 전부 인라인 — 보고서를 누구에게 보내든 파일 하나로 열려야 하기 때문. 외부 의존은 한글 가독성용 **Pretendard CDN 1개뿐**이며, CDN이 차단된 망(폐쇄망 등)에서도 템플릿의 `font-family` 폴백(system-ui·Apple SD Gothic Neo·Noto Sans KR)으로 깨지지 않는다. 코드 하이라이팅은 외부 라이브러리 없이 인라인 `c-keyword`/`c-string` span으로 처리 — 의존을 늘리지 않으려는 의도다.
- **파일명**: `YYYY-MM-DD-{scope}-{slug}.html` (scope = `pr37` / `branch` / `manual`, slug은 케밥케이스 영문). 같은 범위를 다시 독해하면 **새 파일로 덮어쓴다**(독해는 그 시점 코드 스냅샷이라 라운드 누적이 무의미). 단 사용자가 "이어서/추가로"라고 하면 기존 파일에 `section.wt-file`을 덧붙인다.
- **템플릿**: `~/.claude/skills/code-walkthrough/template-modal.html`을 복사한 뒤 채운다. **디자인 토큰·컴포넌트 클래스는 변형하지 않는다** (html-report 디자인 시스템과 동일).
- **위치 표기는 프로젝트 루트 기준 풀 경로 + 라인번호** (예: `backend/app/users.py:14`). 동명 파일이 많으므로 파일명만 쓰지 않는다.
- 추측으로 채우지 않는다. 호출자·정의를 못 찾으면 "확인 필요"로 명시한다.

## 출력 형식

`template-modal.html` 하나로 뽑는다. **파일 전체 코드를 그대로(중간 발췌 없이) 표시**하고, 해설 달린 줄엔 색 마커(◧)+개수칩을 붙인다. 그 줄을 **클릭하면 모달**이 떠 해설을 보여주고 X·백드롭·Esc로 닫는다. 코드 원형이 안 끊겨 한눈에 들어오는 게 이 형식의 핵심 가치다.

> **트레이드오프**: 해설이 기본 숨김이라 "전부 펼쳐 읽기"엔 약하다 — 이를 보완하려 인쇄 시엔(`@media print`) 모달 대신 노트를 코드 뒤에 자동으로 펼쳐 출력한다. 모바일/터치는 클릭으로 동작.

## 실행 흐름

### 1단계 — 분석 범위 확정 (가장 중요)

범위가 어디서 오느냐에 따라 진입이 갈린다. **범위를 먼저 확정하지 않고 코드를 읽기 시작하지 않는다.**

| 상황 | 범위 | 확정 방법 |
|------|------|-----------|
| `self-review`와 함께 / "PR 전 내 코드" | **현재 브랜치 diff** | `git diff <base>...HEAD --stat` 의 변경 파일·라인 |
| `pr-review`와 함께 / "PR #N" | **그 PR의 변경분** | `gh pr diff <N> --name-only`, `gh pr view <N> --json files` |
| 그 외 (사용자가 직접 호출) | **명시적 입력 필요** | 아래 참조 |

**그 외의 경우** — 범위가 코드 전체일 수 있어 토큰·시간이 폭발한다. 다음 중 하나로 좁힌다:

1. 사용자가 이미 범위를 자세히 줬으면 (특정 파일/디렉토리/함수) 그대로 사용.
2. 안 줬으면 **한 번 물어본다**: "어디를 볼까요? (파일/디렉토리/함수 단위, 또는 진입점부터 N단계)". 막연히 "전체"면 진입점·핵심 모듈부터 제안하고 합의.
3. 범위가 커서 한 번에 무리면(파일 10개+ 또는 1000줄+) 파일 그룹으로 나눠 진행하고 중간 보고.

> **범위를 못 좁히거나 그래도 초과할 때** — 거부 이유에 따라 다르게 대응한다:
> - **"그냥 전체 다 봐"** (의도된 큰 범위) → 진입점·핵심 경로부터 partial 진행(아래).
> - **범위 판단 자체를 못 하겠다** (코드베이스 처음) → 먼저 진입점 후보(`main`/라우터/`__init__`/엔트리 스크립트)를 grep해 2~3개 제시하고 합의.
> - **시간·토큰만 부족** → 가장 위험해 보이는/자주 바뀐 파일 우선순위로 좁힐지 제안.
>
> **partial 모드** — 위 어느 경우든 빈 칸을 추측으로 채우지 말고 **진입점·핵심 경로부터 완성하고 나머지는 파일트리에 남기되 해당 섹션을 "미독해 — 후속" 한 줄로 표시**한다. 저장 후 "N개 파일 독해 완료 / M개 후속"을 명시 보고. 어설픈 전체보다 정확한 부분이 낫다.

> diff 범위(self/pr)라도, **이해에 필요한 주변 코드(호출자·정의·타입)는 범위 밖이라도 읽는다.** 단 해설 노트는 변경/지정 범위에 집중하고, 범위 밖 코드는 참조 흐름을 풀기 위한 맥락으로만 인용한다(`a.xref.ext`로 "범위 밖" 표시).

### 2단계 — 프로젝트 기준 문서 확인

코드를 읽기 전에 규칙·맥락을 잡는다. 있으면 읽는다: 루트와 하위 **CLAUDE.md**, README/docs, CONVENTIONS·CONTRIBUTING, `.claude/skills/` 프로젝트 스킬, 변경 모듈 로컬 문서. 여기서 파악한 컨벤션은 해설의 "의도/주의" 근거가 된다.

### 2.5단계 — 독자 눈높이 추론 (건너뛰지 말 것)

`html-report`·`pr-review`와 동일 원리. **이 워크스루를 누가 읽고 무엇을 모를지** 추론해 해설 깊이를 맞춘다. 작성자 본인 복습용인지, 신규 합류자 온보딩용인지, 인접 팀원용인지에 따라 같은 코드도 풀이량이 달라진다. 단서 없으면 "같은 코드베이스의 동료 개발자"를 기본값으로. 특수 도메인 용어·고급 개념만 골라서 풀고, 보편 개념까지 다 풀어 장황해지지 않는다. 추론한 수준은 헤더 메타 `대상` 필드에 반영.

**비유로 한 번에 잡아주기 (초보·인접 독자용)** — 신규 합류자나 도메인 밖 독자가 섞이면, 어려운 메커니즘을 익숙한 것에 빗대는 한 문장이 열 줄 설명보다 빠르다. 예: "이 큐는 식당 대기표 — 번호 받은 순서대로만 불린다", "이 락은 화장실 열쇠 하나 — 가진 사람이 나와야 다음 사람이 들어간다". 비유는 **본문이 아니라 `의도` 노트 첫 문장**에 짧게 얹고, 정확한 동작은 그 뒤에 잇는다. 전문가만 읽을 게 분명하면 생략(장황해짐).

> **초보 독자 walkthrough — 5초 안내**: 보고서를 처음 여는 사람은 ① 좌측 **파일트리**로 파일 이동 → ② 코드 아래(또는 모달)의 **색 막힌 노트**가 해설 → ③ 노트 안 **↳ 점프 링크**를 누르면 "그 변수가 정의된 곳"으로 바로 이동, 한 줄을 이해하려고 직접 거슬러 올라갈 필요가 없다. 이 사용법을 모르면 그냥 긴 코드로 보이므로, 온보딩 대상 보고서라면 `한눈에`(tldr) 끝에 이 3단계를 한 줄로 안내한다.

### 3단계 — 읽는 순서 정하기

파일을 알파벳 순이 아니라 **이해 순서**로 배치한다. 보통 **진입점/상위 흐름 → 거기서 호출되는 하위 헬퍼** 순. 데이터가 흐르는 방향을 따라가면 독자가 참조 링크를 거슬러 오를 필요가 줄어든다. 좌측 파일트리는 디렉토리 구조 그대로 두되, 본문 섹션 순서는 이 이해 순서를 따른다.

### 4단계 — 한 줄 한 줄 읽으며 해설 작성

**해설 밀도: 의미 단위 위주 + 함정만 줄단위.** (사용자 합의 사항)

- **대부분의 줄**은 함수·블록 단위로 묶어 "의도" 노트 하나로 설명한다. 자명한 줄(`import`, 단순 대입, getter, 보일러플레이트)에 노트를 달지 않는다.
- **다음에 해당하는 줄만** 따로 떼어 깊게 판다:
  - **"이 변수/값 어디서 옴?"** → `참조 흐름` 노트. 정의·호출자로 `a.xref` 점프 링크를 건다.
  - **"이거 왜 이렇게 썼지?"** (비직관적 선택, 우회, 숨은 제약) → `의도` 노트로 배경 설명.
  - **함정** (버그·엣지케이스·보안·NPE·경쟁조건 등) → `위험`(danger) 또는 `주의`(warn) 노트.
  - **잘 짜인 부분** (영리한 처리, 좋은 추상화) → `잘된 점`(good) 노트. 비판만 하지 않는다.

해설 노트(`.wt-note`)는 해당 라인에 묶여, 그 줄을 클릭하면 모달로 뜬다. 한 줄에 여러 노트가 달릴 수 있다.

**좋은 해설 vs 나쁜 해설** — 이 스킬의 가치는 "코드를 한국어로 번역"이 아니라 **코드만 봐선 모를 것을 채워주는 것**이다:

| | ❌ 나쁨 (코드 재진술) | ✅ 좋음 (모를 것을 채움) |
|---|---|---|
| 의도 | "rows를 순회하며 _norm을 적용해 리스트로 반환한다" (코드 그대로) | "조회 결과를 API 응답용으로 정규화. **변환 로직은 `_norm` 한 곳뿐**이라 응답 형태를 바꾸려면 거기만 보면 된다" |
| 참조 | "uids는 파라미터다" (자명) | "uids는 `batch_sync`가 `set()`으로 **중복 제거 후** 넘김 → 중복은 없지만 빈 입력은 통과 (→정의 점프)" |
| 위험 | "여기서 에러가 날 수 있다" (모호) | "행 0개 → 빈 리스트 → 호출부 `active[0]`에서 **IndexError**. 빈 배치일 때 실제 도달 (sync.py:31)" |

나쁜 쪽은 코드를 다시 읽는 비용만 늘린다. 자명하면 노트를 **달지 않는** 게 낫다.

#### 참조 흐름을 끊기지 않게 잇는 법 (이 스킬의 핵심 가치)

사용자가 가장 답답해하는 지점 — "이 변수가 다른 메서드 결과값이라 또 올라가야 함" — 을 문서가 대신 풀어준다.

1. **정의된 줄에 앵커를 단다**: `<div class="cl def" id="L-{file}-{line}">`. 함수·중요 변수 정의 라인.
2. **참조하는 노트에서 그 앵커로 링크**: `<a class="xref" href="#L-users-12">get_active (users.py:12)</a>`. 클릭하면 정의 라인으로 점프 + 깜빡임 강조.
3. **약어 풀이**: `r` → "ORM Row 약어", `ctx` → "context" 처럼 한 글자·축약 변수는 무엇의 약자인지 적는다.
4. **출처가 범위 밖**이면 `a.xref.ext`(↗ 표시)로 "범위 밖 파일:라인"임을 알리고, 그 코드의 요지만 한 줄 인용.
5. 한 가설(예: "빈 리스트면 터질 듯")이 **여러 파일에 걸쳐 확정**되면, 각 지점 노트를 링크로 연결해 추론 사슬을 보여준다 (템플릿의 users.py↔sync.py 예시 참조).

**출처를 끝내 못 찾았을 때 (추측 금지)** — 호출자·정의·타입을 못 찾으면 지어내지 말고, 해당 노트를 `주의`(warn)로 만들어 아래 4가지를 명시한다. 사용자가 그 줄만 보고 직접 확인을 끝낼 수 있어야 한다.

| 항목 | 적을 내용 | 예 |
|------|----------|-----|
| 무엇이 미확인인가 | 못 찾은 대상 | "`uids`의 최초 생성 지점" |
| 어느 해설이 영향받나 | 이 공백이 흔드는 결론 | "→ L14 빈 리스트 위험 판정이 잠정적" |
| 어떻게 확인하나 | 사람이 밟을 구체적 경로 | "`batch_sync` 호출자(라우터/스케줄러)를 grep" |
| 확인되면 어떻게 갱신 | 결과별 분기 | "빈 배치 가능하면 위험 확정, 아니면 노트 삭제" |

#### 파일 메타 카드 (`.wt-filecard`)

각 파일 섹션 머리에 채운다: **역할**(이 파일이 범위에서 하는 일), **의존**(import·호출하는 외부 심볼, 정의로 xref), **정의 심볼**(이 파일이 노출하는 함수·클래스), **사용처**(이 파일의 심볼을 누가 호출하는지). 이것만 읽어도 파일의 위치를 안다.

### 5단계 — 템플릿 채우기

```bash
SLUG=user-sync-flow
SCOPE=branch            # pr37 | branch | manual
OUT=./artifacts/code-walkthrough/$(date +%Y-%m-%d)-$SCOPE-$SLUG.html
mkdir -p ./artifacts/code-walkthrough
cp ~/.claude/skills/code-walkthrough/template-modal.html "$OUT"
```

범위·라인수 파악에 자주 쓰는 보조 명령 (언어 무관):

```bash
# 변경 파일 + 라인 통계 (self/pr 범위)
git diff <base>...HEAD --stat
gh pr diff <N> --name-only

# 특정 파일의 라인 수 / 함수 정의 위치 빠르게
wc -l backend/app/users.py
grep -nE '^\s*(def|class|function|const .*=>|func) ' backend/app/users.py   # py/js/ts/go 정의 줄

# 심볼 호출처(사용처) 추적 — "이 함수 누가 부르나"
grep -rn 'get_active(' --include='*.py' .

# 저장 후 확인
open "$OUT"
```

> `cp`가 실패하면(경로 오타·권한) 템플릿 경로부터 `ls ~/.claude/skills/code-walkthrough/`로 확인한다. `grep`/`gh`가 없거나 결과가 비면 추측하지 말고 해당 출처를 "확인 필요"로 남긴다(4단계 4요소 표).

> **점진 작성 원칙 (중간에 끊겨도 살아남게)**: 5단계 `cp`로 골격 파일이 이미 디스크에 있다. 이제 **파일(`section.wt-file`) 단위로 Edit를 나눠** 채운다 — 헤더·tldr·navTree를 먼저, 그다음 **한 파일씩** 코드+노트를 완성해 디스크에 반영한다. **전체를 한 번의 거대한 Edit/Write로 통째 작성하지 않는다.** 코드가 길수록 한 파일 안에서도 코드 블록 → 노트 store로 더 잘게 쪼갠다. 이렇게 하면 도중에 끊겨도 그때까지 독해한 파일이 보고서에 남고, "N개 완료 / M개 후속"(partial 모드)으로 이어서 진행할 수 있다.

먼저 Edit 도구로: ① 헤더 슬롯(`{{...}}`: 제목·부제·범위·파일수·라인수·날짜·대상) ② `한눈에`(tldr) ③ 좌측 `#navTree`(실제 디렉토리 구조, 위험/주의 파일엔 `dot risk`/`dot warn`).

그다음 각 `section.wt-file`을 하나씩, 그 안에서
1. `figure.wt-codefull` > `.code-body`에 **파일 전체 코드**를 라인 단위 `<div class="cl" id="L-{file}-{line}">`로. 정의 라인엔 `def`.
2. 해설 달 라인엔 `class="cl ann sev-{ref|good|warn|risk}"` + `data-notes="(자기 id)"` + 텍스트 끝에 `<span class="chip">{노트 개수}</span>`. (sev는 그 라인 노트 중 가장 심각한 종류로.)
3. 코드 바로 뒤 `<div class="notes-store" hidden>`에 라인별 `<div class="line-notes" data-for="(라인 id)" data-loc="users.py:14">…wt-note들…</div>`. **`data-for`는 라인의 `data-notes`와 정확히 일치해야** 모달이 연결된다 (불일치 = 클릭해도 안 뜸).
4. `a.xref` href는 다른 라인 id를 가리킴 — 모달 안에서 클릭하면 닫고 그 라인으로 이동 후 노트 있으면 모달 재오픈(JS 처리).

다이어그램은 미포함.

### 6단계 — 검증

완료 표시 전 확인. 링크·슬롯 정합은 번들 스크립트로 자동 검사한다 (수동 눈검사보다 확실):

```bash
python3 ~/.claude/skills/code-walkthrough/scripts/check_links.py "$OUT"
# [OK] … 정합  /  [FAIL] 깨진 xref·미치환 슬롯·모달 노트 불일치를 라인별로 출력
```

- 모든 `{{...}}` 슬롯이 제거됐는가? (스크립트가 잡음)
- 모든 `a.xref` 링크의 타깃 `id`가 실제 존재하는가? (깨진 점프 = 가치 상실, 스크립트가 잡음) **타깃을 못 만들겠으면(범위 밖·미발견) `xref` 링크로 두지 말고 평문 + "정의 위치 확인 필요"로 강등** — 클릭해도 안 가는 죽은 링크가 더 나쁘다.
- 자명한 줄에 노이즈 노트를 안 달았는가? 반대로, 비직관적 줄을 그냥 넘기지 않았는가?
- 위치 표기가 풀 경로 + 라인번호인가?
- 라이트/다크 토글, 파일 필터, 파일 점프가 동작하는가? (`open "$OUT"`로 확인)
- 추측을 사실처럼 쓰지 않았는가? 못 찾은 출처는 "확인 필요"로 남겼는가?

### 7단계 — 보고

파일 경로를 알리고 `open "$OUT"` 안내. 발견한 위험/주의가 있으면 1~2줄로 요약하고, 수정 여부는 사용자에게 확인(이 스킬은 독해가 목적이므로 자동 수정하지 않는다).

## 해설 노트 종류 (Quick Reference)

| 클래스 | 라벨 | 언제 |
|--------|------|------|
| `.wt-note.intent` | 의도 | 기본. 이 코드가 무슨 일을 왜 하는지 (대부분의 묶음 설명) |
| `.wt-note.ref` | 참조 흐름 | 변수·값·호출의 출처/행선지. `a.xref` 점프 링크 동반 |
| `.wt-note.good` | 잘된 점 | 영리한 처리·좋은 추상화. 비판 일변도 방지 |
| `.wt-note.warn` | 주의 | 실수 유발·이해 부채·엣지케이스 미처리 |
| `.wt-note.risk` | 위험 | 버그·보안·장애·데이터 손실 가능성 |

코드청크 라인 강조: 해설이 가리키는 줄에 `<div class="cl hl">`. 정의/점프 타깃 줄엔 `<div class="cl def" id="L-...">`.

## 무엇을 하지 않는가

- **문제만 찾는 판정 리뷰** → `pr-review`(타인 PR) / `self-review`(PR 전 자기 점검). 본 스킬은 그 보완재.
- **코드 수정·리팩터링** → 독해가 목적. 수정은 사용자 명시 요청 시 별도로.
- **한두 함수 즉답 설명** → 그냥 대화로 답한다. 보고서는 범위가 어느 정도 있을 때.
- **디자인 변경** → CSS 토큰·컴포넌트 클래스 변형 금지.
- **시크릿 노출** → 코드 내 API 키·접속정보·내부 URL이 보이면 보고서에 그대로 싣지 말고 마스킹.
