# Self Code Review

## 왜 이 리뷰가 중요한가

LLM이 코드를 작성하면서 코드 생산 속도가 인간의 이해 속도를 앞질렀다. 코드는 쌓이지만 팀의 이해는 따라가지 못하면 이해 부채가 쌓인다. 이해 부채가 누적되면 (1) 제품 방향성을 상실하고 (2) 장애에 취약해지며 (3) 교정 비용이 급증한다. Blackbox가 만든 Blackbox를 Blackbox가 디버깅하는 무한 토큰 지옥을 막는 것이 리뷰의 핵심 목적이다.

**작성자의 책임**: 버그가 없는 코드를 내는 것만으로는 부족하다. 타인과 미래의 자신이 코드의 의도와 맥락을 이해할 수 있도록 만드는 것이 작성자의 책임이다.

리뷰는 체크리스트를 기계적으로 따르는 과정이 아니다. 코드를 처음 보는 사람의 관점에서 "이건 왜 이렇게 했지?"라는 물음을 던지며 읽는다.

## 실행 흐름

### 1단계: 변경 범위 파악

```bash
git log --oneline <base-branch>..HEAD
git diff <base-branch>...HEAD --stat
```

- base branch가 불분명하면 사용자에게 확인한다. git 저장소가 아니면(또는 `git`/`gh` 미설치) diff를 못 뽑으므로, 리뷰 대상 파일·디렉토리 범위를 사용자에게 직접 받아 그 범위로 진행한다.
- 변경된 파일 목록과 diff 규모를 먼저 파악한 뒤, 전체 diff를 읽는다.
- 변경 파일뿐 아니라 관련된 주변 코드(호출부, 테스트, 타입 정의 등)도 함께 읽어 맥락을 이해한다.

### 2단계: 프로젝트 기준 문서 확인

코드를 읽기 전에, 이 프로젝트가 정의한 규칙과 맥락을 먼저 파악한다. 아래 문서가 존재하면 읽고, 리뷰 기준으로 삼는다.

1. **CLAUDE.md** — 프로젝트 루트 및 하위 디렉토리의 CLAUDE.md. 코딩 컨벤션, 아키텍처 원칙, 금지사항 등이 담겨 있다.
2. **README / docs/** — 프로젝트 구조, 설계 의도, 사용법. 변경이 문서와 어긋나지 않는지 확인.
3. **스킬/워크플로우 문서** — `.claude/skills/` 등에 정의된 프로젝트 스킬이 있으면 참고하여 해당 워크플로우와 충돌하는 변경이 없는지 확인.
4. **변경된 모듈의 로컬 문서** — 변경 파일이 속한 디렉토리에 README나 doc 주석이 있으면 함께 읽는다.

문서가 많을 경우 변경 범위와 직접 관련된 것만 우선 읽되, 프로젝트 루트 CLAUDE.md는 항상 읽는다.
이 단계에서 파악한 규칙은 3단계 리뷰 시 구체적 근거로 활용한다.

### 3단계: 코드 읽기 — 리뷰어의 시선으로

diff를 한 줄씩 읽으며 아래 관점으로 검토한다.

#### 표면이 아니라 추적으로 판단 (모든 관점의 상위 원칙)

지적의 근거는 **"코드 줄의 모양"이 아니라 "데이터·제어 흐름을 끝까지 추적한 맥락"**이어야 한다. 표면 패턴("이 줄 모양이 위험해 보임")으로 시작하되 거기서 멈추지 않는다. 추적은 **양방향**으로 작동한다 — 가짜 지적을 걷어내고, 표면에 안 보이는 진짜 결함을 드러낸다. 아래 모든 관점에 이 원칙을 먼저 적용한다.

**방향 1 — 표면상 위험해 보이는 것을 추적해 걷어낸다 (false positive 억제)**

"이런 입력이 오면 터질 수도"라고 적기 전에, 그 시나리오가 **실제 도달 가능한지** 추적한다.

- **입력 출처**: 이 값은 어디서 오는가? 외부(신뢰 불가)인가, 내부에서 이미 검증·생성된 값인가?
- **상위 방어**: 호출부·미들웨어·타입 시스템·DB 제약·assert·스키마 검증이 이미 막고 있지 않은가?
- **의도된 설계**: 의도적으로 그렇게 둔 것인가? (단, 그 의도가 **코드에 실제로 반영됐는지**까지 확인 — 의도만 있고 구현이 빠졌으면 그게 진짜 버그)
- 추적 결과 **도달 불가 / 이미 보장 / 의도된 것** → 적지 않거나 Suggestion 이하로만. 추적했는데도 **못 닫음**(맥락이 코드 밖) → "어디를 보면 확정되는지" 명시한 열린 질문으로. **추측만으로 Warning/Critical 금지.**

**방향 2 — 표면상 멀쩡해 보이는 것을 추적해 잡아낸다 (false negative 억제 — 더 값짐)**

개별 줄만 보면 정상인데 **흐름을 따라가야 드러나는** 결함이 더 위험하고 놓치기 쉽다. 내가 짠 코드라 더 표면만 보고 넘기기 쉬우니 의식적으로 추적한다.

- **호출부 신뢰 가정**: 이 함수는 그 자체론 안전한데, 호출부가 검증 없이 신뢰 불가 값을 넘기는가?
- **경계의 가정 불일치**: 두 모듈·함수가 각자는 정상인데 인터페이스에서 가정이 어긋나는가? (단위·널 가능성·정렬·인코딩·시간대·소유권)
- **불변식 붕괴-발현 분리**: 상태가 깨지는 곳과 터지는 곳이 멀어 표면 리뷰로는 안 보이는가?
- **의도-구현 괴리**: "의도대로 짰다"고 가정했는데 그 의도가 실제 코드엔 구현 안 됐는가?

> **요지**: 표면 가능성 나열도, 무지성 컷도 아니다. **데이터가 어디서 와서 어디로 가는지 끝까지 따라가 판단을 닫는 것**이 리뷰의 핵심이다. 추적이 안 닫히면 버리지 말고 열린 질문으로 남겨 진짜 치명적인 걸 놓치지 않는다.

예시로 감을 잡으면:

- ❌ **표면만**: "`parseConfig(raw)`에서 `raw`가 null이면 터진다 → Warning" — 줄 모양만 보고 가능성 나열.
- ✅ **방향1로 걷어냄**: "`raw`는 호출부(`loader.ts:30`)에서 `zod` 스키마 검증을 통과한 값만 들어옴 → null 도달 불가. 미기재. (다만 그 의존이 암묵적이라 검증을 우회하는 새 호출부가 생기면 깨짐 — 한 줄 메모만)"
- ✅ **방향2로 잡아냄**: "`parseConfig` 자체는 안전한데, 추적해보니 `cli.ts:88`이 검증 없이 사용자 인자를 직접 넘김 → 여기가 진짜 구멍. Critical." — 정작 바뀐 줄엔 안 보이고 호출부 추적으로만 드러남.

#### 의도·맥락 가시성 (이해 부채 직결)

이 항목이 핵심이다. 코드가 동작하는지보다 **왜 이렇게 동작하는지** 읽히는지를 먼저 본다.

- **PR description**: 이 PR이 무엇을 왜 바꾸는지 설명하는가? diff만 보고는 알 수 없는 배경·트레이드오프·결정 과정이 담겨 있는가?
- **커밋 메시지**: "fix bug", "update code" 같은 내용 없는 메시지가 아니라, 변경 의도가 담겨 있는가?
- **Why 주석**: 비직관적인 선택, 숨겨진 제약, 우회 이유 등 코드만으로는 알 수 없는 배경이 주석으로 남겨져 있는가?
- **네이밍**: 이름만 보고 동작·목적을 예측할 수 있는가? 축약어나 모호한 이름이 맥락을 가리지 않는가?
- **LLM 생성 코드 특유 패턴**: 불필요한 추상화·과잉 구현이 끼어들지 않았는가? 기존 유사 코드를 모르고 새로 만든 중복 구현은 없는가? 코드는 동작하지만 의도와 실제 행동이 미묘하게 다른 부분은 없는가?

#### 가독성

- **구조**: 파일 위치와 디렉토리 구조가 직관적인가? 새로 온 사람이 어디에 뭐가 있을지 예측할 수 있는가?
- **추상화 수준**: 역할을 빠르게 파악할 수 있는가? 과도하거나 부족하지 않은가?
- **함수 크기**: 단일 함수가 너무 크거나 작아서 흐름 파악이 어렵지 않은가?
- **복잡한 로직**: 이해가 어려운 부분이 있다면 더 단순하게 표현할 수 있는가?
- **주석**: 주석이 코드 이해를 실제로 돕는가? 코드와 불일치하지 않는가? 자명한 것에 불필요한 주석이 달려있지 않은가?

#### 안전성

- **수정 용이성**: 다른 개발자나 LLM이 이 코드를 수정·사용할 때 실수할 여지가 높은 구조인가?
- **예외 처리**: 과도한 예외 처리로 실제 문제 검출을 차단하고 있지 않은가?
- **Edge Case**: 현재 코드가 상정하지 않는 현실적인 엣지 케이스는 무엇인가?
- **권한과 자유도**: 과도한 권한이나 자유도가 부여되어 보안 문제의 소지가 있는가?
- **안전장치**: 문제 발생 시 복구 및 강제 중지 수단이 존재하는가?
- **관측 가능성**: 문제를 파악할 수 있는 로그와 모니터링 체계가 갖춰져 있는가?

#### 실수 점검

- **일관성**: 새 코드가 기존 코드베이스의 아키텍처와 컨벤션을 따르는가? (2단계에서 파악한 CLAUDE.md, README, docs 기준으로 판단)
- **중복/Dead Code**: 중복 코드나 사용되지 않는 코드가 남아있지 않은가?
- **API 사용**: 외부 API나 라이브러리를 공식 문서에 맞게 사용하고 있는가?
- **임시 코드**: 개발·디버깅용으로 넣었던 임시 코드(console.log, TODO hack, hardcoded 값 등)가 남아있지 않은가?

#### 문서 동기화 (코드 → 문서)

2단계가 "문서를 기준으로 코드를 보는" 방향(문서 → 코드)이라면, 여기서는 **반대 방향 — 이번 변경에 수반되어야 할 문서 갱신이 빠지지 않았는지**를 본다. 코드 자체엔 버그가 없어도, 변경이 기존 문서를 구식으로 만들면 미래의 독자(타인·미래의 자신)를 적극적으로 오도한다.

- **공개 계약 변경**: API 시그니처·CLI 옵션·설정 키·env 변수·응답 스키마가 바뀌었는데 README/docs/예시가 옛날 그대로인가?
- **프로젝트 규칙 문서**: 아키텍처·디렉토리 구조·컨벤션에 영향 주는 변경인데 CLAUDE.md / CONVENTIONS.md / 아키텍처 문서가 미갱신인가?
- **인접 주석·docstring**: 변경된 함수의 docstring·주석이 새 동작과 어긋나지 않는가? (구식 주석은 없느니만 못하다)
- **신규 기능 문서**: 새 기능·모듈인데 사용법·설정 문서·예시가 누락됐는가?
- **breaking change**: 호환성을 깨는 변경인데 마이그레이션 가이드·CHANGELOG·버전 노트가 빠졌는가?

문서 갱신이 필요한데 누락됐으면 기본 **Warning**으로 짚는다 (코드 동작과 무관해도). 단 오도 위험이 크면 격상 — breaking change인데 마이그레이션 가이드가 없거나 보안·과금에 영향 주는 설정 문서가 틀린 경우는 **Critical**. 문서를 후속 PR로 미루기로 명시된 경우만 **Suggestion**.

### 4단계: 리뷰 결과 보고

아래 형식으로 결과를 보고한다. 발견 사항이 없는 섹션은 생략한다.

```
## Self Review: <브랜치명>

### 변경 요약
- 변경 파일 N개, +X / -Y lines
- 핵심 변경: (한두 줄 요약)

### 이해 부채 위험 신호
(PR description, 커밋 메시지, Why 주석, 네이밍, LLM 특유 패턴에서 발견된 항목)

#### [Critical/Warning/Suggestion] 제목
- 파일: `path/to/file.ts:42`
- 내용: 구체적 문제 설명
- 제안: 개선 방향 또는 대안 (근거 포함)

### 기술적 발견 사항
(버그, 안전성, 실수 등 코드 동작 관련 항목)

#### [Critical/Warning/Suggestion] 제목
- 파일: `path/to/file.ts:87`
- 내용: 구체적 문제 설명
- 제안: 개선 방향 또는 대안 (근거 포함)

### 점검 결과
- [x] PR description이 변경 의도와 배경을 설명한다
- [x] 비직관적 선택에 Why 주석이 달려있다
- [x] 기존 코드베이스와 아키텍처/컨벤션 일관성
- [x] 중복 코드, Dead Code 없음
- [x] 표면이 아니라 흐름 추적으로 판단함 (가짜 지적 걷어냄 / 숨은 결함 발굴)
- [x] 코드 변경에 수반될 문서(README/docs/주석·docstring) 갱신 반영
- [ ] Edge case 미처리 → (위 발견 사항 참조)
- ...해당하는 항목만 표시
```

**심각도 기준:**

| 심각도 | 기준 | 예시 |
|--------|------|------|
| Critical | 버그, 데이터 손실, 보안 취약점, 장애 가능성 | 인증 우회, SQL injection, 무한 루프 |
| Warning | 잠재적 문제, 엣지 케이스 미처리, 이해 부채 고위험 | 에러 핸들링 누락, 의도 불명 복잡 로직 |
| Suggestion | 가독성, 구조 개선, 더 나은 접근법 | 네이밍 개선, 함수 분리, Why 주석 추가 |
| Nitpick | 사소한 스타일, 선호 차이 | 줄바꿈, import 순서 (lint로 잡히는 것은 제외) |

### 5단계: 수정 여부 확인

리뷰 결과를 보고한 뒤, Critical이나 Warning이 있으면 수정할지 사용자에게 확인한다.
사용자가 수정을 원하면 해당 부분을 고치고, 변경된 부분만 재검토한다.

사용자가 **지금 고치지 않기로** 한 경우, 그냥 덮지 말고 사유별로 처리한다:

| 거부 사유 | 처리 |
|----------|------|
| 이번 PR 범위 밖 | "Scope 외 참고사항" 섹션으로 이관 + 가능하면 후속 이슈로 등록할 항목 명시 |
| 나중에 처리 | 코드에 `TODO`/`FIXME`(사유·맥락 포함)로 남기거나 이슈/메모로 기록 — 추적되지 않게 사라지지 않도록 |
| 의도된 동작 | 왜 의도된 것인지 **근거를 코드 주석/PR description에 남기고** 닫는다 (다음 리뷰어가 같은 지적을 반복하지 않도록) |

Critical을 미해결로 닫는 경우, 보고서에 "미해결 Critical 잔존" 을 명시해 머지 전 의사결정이 누락되지 않게 한다.

리뷰가 통과됐고 사용자가 커밋·PR 준비로 넘어가려 하면 `/git-workflow`(브랜치·커밋 단위 정리)로 이어진다. 코드를 전체적으로 한 줄씩 훑어 흐름을 이해하고 싶으면 같은 범위로 `/code-walkthrough`를 함께 돌린다.

## 주의사항

- 수정 제안에는 반드시 **논리적 근거와 대안**을 함께 제시한다. "이게 더 낫다"는 식의 단편적 제안은 하지 않는다.
- 이번 PR 범위 밖이더라도, 수정이 필요해 보이는 부분이 있으면 별도 섹션(Scope 외 참고사항)으로 제안한다. 단, PR에 포함시키라는 것이 아니라 후속 작업으로 분리하도록 안내한다.
- 변경 규모가 큰 경우(파일 10개 이상 또는 500줄 이상), 파일 그룹별로 나눠서 리뷰하고 중간중간 진행 상황을 공유한다.
- lint, formatter, 타입 체커가 잡을 수 있는 문제는 별도로 지적하지 않는다. 인간 리뷰어가 봐야 할 것에 집중한다.
