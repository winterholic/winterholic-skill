# PR Review

## 왜 이 리뷰가 중요한가

LLM이 코드를 작성하면서 코드 생산 속도가 인간의 이해 속도를 앞질렀다. 코드는 쌓이지만 팀의 이해는 따라가지 못하면 **이해 부채**가 누적된다. 이해 부채가 쌓이면 (1) 제품 방향성을 상실하고 (2) 장애에 취약해지며 (3) 교정 비용이 급증한다. Blackbox가 만든 Blackbox를 Blackbox가 디버깅하는 무한 토큰 지옥을 막는 것이 리뷰의 핵심 목적이다.

**리뷰어의 역할**: 코드의 맥락·구성·의도를 끝까지 이해하려 노력한다. "동작하는가"보다 "왜 이렇게 동작하는가"를 묻는다. 이해되지 않는 코드는 통과시키지 않는다.

**리뷰 문서의 사용자**: 본인이 다시 읽거나, 작성자에게 전달하거나, 미래의 팀원이 PR 결정 맥락을 추적할 때 쓴다. 따라서 **추론한 독자 눈높이(1.5단계)에 맞춰** 친절히 작성한다 — 모를 독자에겐 진입장벽을 풀어주되, 전문가 독자에겐 장황하지 않게. "누구든 처음 읽어도"를 *항상 최대치로* 적용하면 전문가 독자에겐 유치해지므로, 무엇을 얼마나 풀지는 항상 독자 추론에서 출발한다.

## 절대 규칙

- **읽기 전용**: `gh pr view/diff`, `git log/show/diff`, 파일 Read만 허용. **commit/push 금지**.
- **저장 위치**: `./artifacts/code-review/`
- **출력 형식**: **단일 자기완결 HTML 파일**. 인라인 CSS/JS, 외부 의존성 없음.
- **파일명**: `PR-{번호}-{브랜치-슬러그}.html` (예: `PR-37-newhigh-improvements.html`)
- **템플릿**: `~/.claude/skills/pr-review/template.html`을 그대로 복사한 뒤 본문(헤더·요약·커밋·리뷰 포인트·테스트 가이드·요약 표·진행 추천)을 채워 저장. 디자인 시스템(컬러 토큰·뱃지·카드·심각도 클래스)은 절대 변형하지 않는다.
- **이미 같은 파일이 있으면 append** — `<!-- ROUND-INSERT-MARKER -->` 주석 **바로 위**에 새 라운드 `<section class="round-divider">` 삽입. 기존 내용·마커·닫는 태그는 절대 수정하지 않는다.
- **위치 표기는 풀 경로 + 라인 번호 의무**. 형식·예시는 아래 "위치 명시" 섹션 참조.

### 위치 명시 (절대 형식)

형식: `<프로젝트-루트-기준-경로>:<라인번호>`

| 표기 | 판정 | 이유 |
|------|------|------|
| `backend/app/api/users.py:478` | O | 루트 기준 풀 경로 |
| `frontend/modules/admin/components/users-table.tsx:155` | O | 루트 기준 풀 경로 |
| `users.py:478` | X | 경로 불명확. Python은 동명 파일 다수 |
| `app/api/users.py:478` | X | 프로젝트 루트(backend) 누락 |
| `backend/users.py:478` | X | 중간 경로 생략 |

- **단일 라인**: `backend/app/core/llm.py:32`
- **범위**: `backend/app/core/llm.py:22~26`
- **여러 위치 대조**: `llm.py:32` vs `llm.py:22~26` (vs로 연결)
- **코드 스니펫**: 첫 줄에 주석으로 풀 경로 + 라인범위 표시 (`# backend/app/core/llm.py 라인 22~26`)

## 실행 흐름

### 1단계: PR 전체 맥락 흡수

리뷰의 출발점은 코드가 아니라 **맥락**이다. 작성자가 무엇을 왜 바꾸려 했는지 모르는 상태에서 diff부터 보면 단순 lint 수준 지적만 나온다.

> **사전 점검 (gh 의존)**: 아래 명령은 `gh` CLI + 인증을 전제한다. `gh auth status`로 먼저 확인하고, **미설치/미인증이면 `gh auth login` 안내** 후 진행. 인증이 불가한 환경이면 PR 웹페이지 URL을 사용자에게 받아 본문·커밋·코멘트를 수동 수집한다(아래 수집 항목 목록은 동일하게 채운다). **GitHub가 아닌 호스트**(GitLab `glab`, Bitbucket 등)면 해당 CLI의 대응 명령으로 치환하거나, 안 되면 웹 URL 수동 수집으로 폴백 — 이후 단계의 리뷰 본질은 호스트와 무관하다.

아래를 **빠짐없이** 수집한다.

```bash
# PR 메타 (제목, body, 작성자, 라벨, 연결 이슈, CI 상태)
gh pr view <PR번호> --json title,body,author,headRefName,baseRefName,labels,state,additions,deletions,changedFiles,statusCheckRollup,reviewDecision,closingIssuesReferences

# 커밋 목록 (오래된 순)
gh pr view <PR번호> --json commits

# 변경 통계
gh pr diff <PR번호> --name-only
gh pr view <PR번호> --json files

# 모든 인라인/리뷰 코멘트와 답글
gh api repos/{owner}/{repo}/pulls/<PR번호>/comments --paginate
gh api repos/{owner}/{repo}/pulls/<PR번호>/reviews --paginate
gh api repos/{owner}/{repo}/issues/<PR번호>/comments --paginate

# 연결된 이슈 (closes #N 등)가 있으면 그 본문도
gh issue view <이슈번호>
```

수집 후 **다음 질문에 답할 수 있어야** 한다:
- 이 PR이 해결하려는 문제는 무엇인가? (PR body, 연결 이슈)
- 작성자가 명시한 트레이드오프·결정 근거는 무엇인가?
- 이전 라운드 코멘트가 있다면 어떤 지적이 있었고 어떻게 대응됐는가?
- CI는 통과했는가? 실패라면 어떤 검사인가?
- 작성자가 "여기 봐달라"고 콕 짚은 부분이 있는가?

### 1.5단계: 리뷰 문서 독자·눈높이 추론 (건너뛰지 말 것)

PR 맥락(1단계)을 흡수했으면, 코드를 파기 전에 **이 리뷰 문서를 누가 읽고, 그 독자에게 무엇이 진입장벽인지**를 먼저 추론한다. 같은 리뷰라도 독자에 따라 "좋은 문서"가 갈린다 — 도메인·코드베이스 맥락을 모르는 독자에겐 풀이 없는 지적이 벽이 되고, 반대로 작성자 본인·도메인 전문가에겐 비유·기초 풀이가 장황·유치해진다. 이 단계가 없으면 풀이 도구(`.plain-talk`·`.impact`·비유·용어풀이)를 **전 항목에 기계적으로 도배**하거나 반대로 **아무 데도 안 써서** 독자와 어긋난다.

**질문하지 않는다.** PR 맥락으로 추론해 기본값을 잡고 진행한다. 과하거나 부족하면 사용자가 명시적으로 수정 요청한다. 애매할 때는 **"덜 풀어 못 알아듣는 것"보다 "풀어서 보조 요소(plain-talk·impact)에 담는 것"** 쪽으로 약간 기운다 — 이 요소들은 본문 아래 보조 위치라 전문가 독자를 크게 방해하지 않으므로 비용이 낮다. 단 *약간*이다 (아래 과잉 경계 참조).

**추론 입력:**
- **리뷰 대상 도메인 난이도**: 금융 거래·분산 시스템·암호·저수준 동시성처럼 진입장벽 높은 영역인가, CRUD·UI 같은 보편 영역인가
- **코드베이스 특유 맥락**: 이 PR이 프로젝트 고유의 아키텍처·암묵지(2단계의 CLAUDE.md/컨벤션)에 의존하는가
- **추정 독자**: 작성자 전달용(맥락 공유) / 같은 팀 리뷰어 / 도메인 모르는 신규·인접 팀원 / 비개발 이해관계자 / 미래 추적자. 단서가 없으면 "같은 코드베이스의 동료 개발자"를 기본값으로.

**무엇을 얼마나 풀지 — 항목별 선별 휴리스틱** (전부 풀거나 전부 안 푸는 게 아니라, 지적마다 따로 판단):

| 축 | 풀이 최소 (본문만) | 풀이 적극 (plain-talk·용어풀이·비유·맥락 박스) |
|----|------------------|-----------------------------------------|
| 도메인 용어 | 팀 전원이 쓰는 보편 용어(REST·캐시·트랜잭션) | 특수 도메인 용어(매칭엔진·T+2·증거금·VaR·eventual consistency) |
| 기술 개념 | 그 스택 실무자면 다 아는 것(async/await·인덱스·JOIN) | 덜 보편·고급(분산 락 fencing·MVCC·백프레셔·메모리 배리어) |
| 영향 범위 | 국소적·자명한 영향 | 사용자/운영/법적 파장이 큰 항목 → `.impact` 박스 적극 |
| 코드베이스 맥락 | 변경이 자기완결적 | 프로젝트 고유 아키텍처에 의존 → "이 PR의 맥락" 박스·ASCII 도식 |

**과잉 경계** — 추정 독자가 분명한 전문가(작성자·시니어)면 `.plain-talk`를 모든 항목에 달지 말고 **정말 비직관적이거나 영향이 큰 곳에만** 선별 적용한다. 비유로 도배된 리뷰는 전문가에게 신뢰를 떨어뜨린다. 반대로 신규·인접·비개발 독자가 섞이면 도메인 용어를 적극 풀고 배경 박스를 깐다. **핵심은 한 리뷰가 추론된 독자에게 정확히 맞는 눈높이를 갖는 것** — 무조건 친절도 무조건 압축도 아니다.

### 2단계: 프로젝트 기준 문서 확인

코드를 읽기 전에, 이 프로젝트가 정의한 규칙·맥락을 먼저 파악한다. 아래 문서가 존재하면 읽고, 리뷰 기준으로 삼는다.

1. **CLAUDE.md** — 프로젝트 루트와 하위 디렉토리. 코딩 컨벤션·아키텍처 원칙·금지사항.
2. **README / docs/** — 프로젝트 구조, 설계 의도, 사용법.
3. **CONVENTIONS.md / CODESTYLE.md / CONTRIBUTING.md** — 컨벤션 명시 문서.
4. **.claude/skills/** — 프로젝트 스킬·워크플로우.
5. **변경 모듈의 로컬 문서** — 해당 디렉토리 README, doc 주석.

이 단계에서 파악한 규칙은 4단계 리뷰 시 **구체적 근거**로 사용한다. ("CONVENTIONS.md 6.4절: TypeScript 파일명은 kebab-case 규정. 현재 위반.")

### 3단계: 변경 범위·구조 파악

```bash
git fetch origin <PR번호>:pr/<PR번호>
git log --oneline <base>..pr/<PR번호>
git diff <base>...pr/<PR번호> --stat
```

- 커밋이 N개면 **반드시 오래된 순**으로 정렬해서 흐름을 이해한다.
- 한 파일이 여러 커밋에 걸쳐 바뀌면 **각 커밋 시점의 변경**을 분리해서 본다 (`git show <SHA> -- <file>`).
- 변경 파일뿐 아니라 **호출부·테스트·타입 정의** 등 주변 코드도 함께 읽는다.

### 4단계: 코드 리뷰 — 커밋 순서대로

각 커밋을 **독립된 단위**로 본다. 파일별로 묶지 않는다 (한 파일이 여러 커밋에 걸쳐 변하면 각 커밋 섹션에 나누어 기재).

각 라인을 읽으며 아래 관점으로 검토한다.

#### 표면이 아니라 추적으로 판단 (모든 관점의 상위 원칙)

지적의 근거는 **"코드 줄의 모양"이 아니라 "데이터·제어 흐름을 끝까지 추적한 맥락"**이어야 한다. 표면 패턴 매칭("이 줄 모양이 위험해 보임")으로 시작하되 거기서 멈추지 않는다. 추적은 **양방향**으로 작동한다 — 가짜 지적을 걷어내고, 표면에 안 보이는 진짜 결함을 드러낸다. 아래 모든 관점(의도·정확성·일관성·구조)에 이 원칙을 먼저 적용한다.

**방향 1 — 표면상 위험해 보이는 것을 추적해 걷어낸다 (false positive 억제)**

"이런 입력이 오면 터질 수도"라고 적기 전에, 그 시나리오가 **실제 도달 가능한지** 추적한다.

- **입력 출처**: 이 값은 어디서 오는가? 외부(신뢰 불가)인가, 내부에서 이미 검증·생성된 값인가?
- **상위 방어**: 호출부·미들웨어·타입 시스템·DB 제약·assert·스키마 검증이 이미 막고 있지 않은가?
- **의도된 설계**: 주석·PR·커밋·아키텍처상 의도적으로 그렇게 둔 것인가? (단, 그 의도가 **코드에 실제로 반영됐는지**까지 확인 — 의도만 있고 구현이 빠졌으면 그게 진짜 버그)
- 추적 결과 **도달 불가 / 이미 보장 / 의도된 것** → 적지 않거나 `[참고]`로만("이건 X에서 막혀 안전, 다만 의존이 암묵적"). 추적했는데도 **못 닫음**(맥락이 코드 밖) → `[확인 필요]`로 "어디를 보면 확정되는지" 명시. **추측만으로 `[중간]`/`[심각]` 금지.**

**방향 2 — 표면상 멀쩡해 보이는 것을 추적해 잡아낸다 (false negative 억제 — 더 값짐)**

개별 줄만 보면 정상인데 **흐름을 따라가야 드러나는** 결함이 더 위험하고 놓치기 쉽다. 표면 스캔으로 멈추지 않는다.

- **호출부 신뢰 가정**: 이 함수는 그 자체론 안전한데, 호출부가 검증 없이 신뢰 불가 값을 넘기는가?
- **경계의 가정 불일치**: 두 모듈·함수가 각자는 정상인데 인터페이스에서 가정이 어긋나는가? (단위·널 가능성·정렬·인코딩·시간대·소유권)
- **불변식 붕괴-발현 분리**: 상태가 깨지는 곳과 터지는 곳이 멀어 표면 리뷰로는 안 보이는가?
- **의도-구현 괴리**: "의도된 설계"라 가정했는데 그 의도가 실제 코드엔 구현 안 됐는가?

> **요지**: 표면 가능성 나열도, 무지성 컷도 아니다. **데이터가 어디서 와서 어디로 가는지 끝까지 따라가 판단을 닫는 것**이 리뷰의 핵심 노동이다. 그물은 넓게 — 추적이 안 닫히면 버리지 말고 `[확인 필요]`로 남겨 진짜 치명적인 걸 놓치지 않는다. (범위가 넓어 추적이 버거우면 `/code-walkthrough`로 흐름을 먼저 훑는다.)

#### 의도·맥락 가시성 (이해 부채 직결)

- **PR description / 커밋 메시지**: 이 변경이 무엇을 왜 하는지 diff 없이 알 수 있는가?
- **Why 주석**: 비직관적 선택, 숨은 제약, 우회 이유에 주석이 있는가?
- **네이밍**: 함수·변수명만으로 동작·목적을 예측할 수 있는가?
- **LLM 생성 코드 특유 패턴**: 불필요한 추상화·과잉 구현, 기존 유사 코드를 모르고 새로 만든 중복, 코드는 동작하지만 의도와 미묘하게 어긋나는 부분.

#### 정확성·안전성

- **버그**: 분기 누락, off-by-one, 비동기 경합, 타입 불일치.
- **Edge case**: 빈 입력, 매우 큰 입력, 권한 없는 호출자, 동시 요청, 부분 실패.
- **권한·보안**: 인증/인가 우회 가능성, secrets 노출, SQL/template injection.
- **에러 처리**: 과한 except가 진짜 문제를 덮지 않는가? 실패 시 복구·중지 수단이 있는가?
- **관측 가능성**: 문제 발생 시 추적 가능한 로그·메트릭이 있는가?

#### 일관성·구조

- 프로젝트 컨벤션과 일치하는가? (2단계 기준)
- 기존 패턴과 다른 방식이라면 합리적 이유가 있는가?
- 중복 코드, dead code, 임시 디버깅 코드(console.log, hardcoded 값 등)는 없는가?
- 외부 API·라이브러리를 공식 문서대로 사용하는가?

#### 문서 동기화 (코드 → 문서)

2단계가 "문서를 기준으로 코드를 보는" 방향(문서 → 코드)이라면, 여기서는 **반대 방향 — 이번 PR에 수반되어야 할 문서 갱신이 빠지지 않았는지**를 본다. 코드 자체엔 문제 없어도, 변경이 기존 문서를 구식으로 만들면 미래 독자를 적극적으로 오도한다. 리뷰가 흔히 놓치는 축이다.

- **공개 계약 변경**: API 시그니처·CLI 옵션·설정 키·env 변수·응답 스키마가 바뀌었는데 README/docs/OpenAPI·예시가 옛날 그대로인가?
- **프로젝트 규칙 문서**: 아키텍처·디렉토리 구조·컨벤션에 영향 주는 변경인데 CLAUDE.md / CONVENTIONS.md / 아키텍처 문서가 미갱신인가?
- **인접 주석·docstring**: 변경된 함수의 docstring·주석이 새 동작과 어긋나지 않는가? (구식 주석은 없느니만 못하다)
- **신규 기능 문서**: 새 기능·모듈인데 사용법·설정 문서·예시가 누락됐는가?
- **breaking change**: 호환성을 깨는 변경인데 마이그레이션 가이드·CHANGELOG·버전 노트가 빠졌는가?

문서 갱신 누락은 보통 `[중간]` (구식 문서의 오도 위험이 크면 `[심각]`). PR description에 "문서는 후속 PR에서"라 명시됐으면 `[참고]`로 완화.

#### 함수·모듈 구조 (가독성 직결)

- **함수 길이**: 한 함수가 한 화면(~50줄)을 넘는가? 넘는다면 의미상 분리 가능한 책임 단위가 있는가?
- **반대로 잘게 쪼개짐**: 의미 없는 1~2줄 헬퍼가 호출 흐름을 분산시켜 추적이 어렵게 만들지 않는가? (LLM이 흔히 만드는 패턴)
- **단일 책임**: 한 함수가 "조회 + 검증 + 변환 + 저장 + 알림"처럼 여러 책임을 떠안고 있지 않은가?
- **중첩 깊이**: `if/for/try`가 4중 이상으로 중첩되어 분기를 따라가기 힘든가? early return·guard clause로 평탄화 가능한가?
- **파일 위치·디렉토리 구조**: 새로 추가된 파일이 직관적인 위치에 있는가? 새로 온 사람이 "이 기능 코드는 어디 있을까?"라고 물었을 때 예측 가능한 경로인가?

#### 인라인 코멘트·답글 통합

1단계에서 수집한 인라인 코멘트·답글은 리뷰에 반드시 반영한다.
- 이전 라운드 지적이 **해결됐는지** 검증한다 (해결/미해결/부분 해결).
- 작성자가 답글로 "이건 의도된 동작"이라 답한 부분도 본인 판단으로 재검토한다 (작성자 답이 항상 맞지는 않다).
- 미해결 또는 새로 발견한 항목은 별도 표시.

> **리뷰봇 코멘트는 의심하고 검증**: CodeRabbit·Korbit·GitHub Copilot 등 자동 리뷰봇 코멘트는 false positive와 맥락 부재가 잦아 신뢰도 낮음. 그대로 인용·채택 금지. **반드시 본인이 코드를 직접 확인**해 사실이면 채택, 틀렸으면 무시. 봇 지적을 그대로 옮겨 적은 리뷰는 가치 없음.

##### 작성자 거부 답글 처리 분기

작성자가 "의도된 동작" / "취향 차이" / "별도 이슈로 처리" 등으로 거부한 경우, 다음 분기로 처리:

| 거부 근거 | 검증 가능성 | 처리 |
|----------|-----------|------|
| 코드·문서·실측 데이터로 검증 가능하고 합리적 | ✅ | 본인 판단 보류, `[참고]`로 기록 + "작성자 답글: ..." 인용 |
| 검증 불가하거나 모호 | ⚠️ | `[확인 필요]`로 격상. "어떻게 확인하면 OK인지" 4요소(누가/언제/어떻게/기대결과) 명시 |
| 명백히 틀렸거나 코드와 모순 | ❌ | 그대로 다시 지적. 동일 항목 N회 거부 시 **상위 리뷰어 중재 필요** 신호를 리뷰 문서에 명시 (스킬은 신호까지만, 실제 격상은 사람이 트리거) |

리뷰 문서에 작성자 답글을 인용할 때는 "**작성자 답변** ({SHA} 답글):" 헤더로 식별 가능하게 표시. 동일 항목이 라운드를 거치며 반복 거부되면 2차/3차 리뷰의 "이전 라운드 지적 해결 확인 표"에서 `🔁 반복 거부` 표시.

#### 커밋 히스토리 평가

코드 내용뿐 아니라 **커밋의 형태**도 평가 대상이다. 작성자가 의도와 흐름을 어떻게 분할했는지가 미래 디버깅·롤백 효율을 결정한다.

- **커밋 단위의 적절성**:
  - 너무 큰 커밋(파일 10개+ 또는 500줄+): 의미상 분리 가능하면 **split 권장** (예: "기능 추가 + 리팩터링 + 테스트"가 한 커밋에 섞임).
  - 너무 잘게 쪼개진 커밋(1~2줄 fix가 연속, "fix typo" → "fix typo 2"): **squash 권장**.
  - 같은 PR 안에서 **자기교정 패턴** (커밋 N에서 만든 버그를 커밋 N+1에서 잡음) → 일반적으로 squash 후보. 단, 리뷰 라운드 사이의 대응 커밋이면 보존이 맞음.
- **커밋 메시지 품질**:
  - `fix bug`, `update`, `wip`, `temp`, `.` 같은 빈 메시지 검출 시 → 작성자에게 의도 보강 요청 (`[확인 필요]` 또는 Comment).
  - 메시지가 "무엇을"만 담고 "왜"가 없으면 보강 권장.
- **커밋 순서의 논리**:
  - 리팩터링 → 새 기능 추가 → 테스트 추가 식으로 흐름이 보이는가?
  - 새 기능 추가 후 또 리팩터링이 들어와 reviewable 단위가 흐트러지지 않는가?
- **잔여물 검출**:
  - WIP·checkpoint·debug·`@temporary` 커밋이 머지 직전까지 남아있지 않은가?

발견 시 처리: 권장 조치를 `[이번 PR에서 수정 권장]` (squash/split 등 history rewrite은 작성자 권한)으로 표시하고, 메시지 품질 누락은 별도 체크박스로 정리.

### 4.5단계: PR 목적·설계 타당성 종합 고찰 (PR 전체 차원 — 건너뛰지 말 것)

**전제 — PR 리뷰는 "코드 기술 검토"가 아니라 "하나의 작업(업무)에 대한 리뷰"다.** 이 PR은 어떤 업무 요청·문제의식에서 출발했고, 작성자가 무슨 의도로 이렇게 접근했으며, 그 결과가 **작업의 본래 의의·맥락에 부합하는가**를 본다. 기술 스택·도메인과 무관한 렌즈다 — LLM이든 배치 잡이든 UI 리팩터든 결제 로직이든, "이 작업이 의도한 가치를 실제로 냈는가"는 똑같이 물어야 한다.

4단계까지가 "**코드가 의도대로 잘 짜였는가**"(라인·구조·정확성)라면, 여기서는 한 층 올라가 "**그 의도·접근·규모 자체가 타당했는가, 들인 비용이 목적에 값했는가**"를 묻는다. 코드는 전부 옳은데 **PR 자체가 (1) 잘못된 문제를 풀거나 (2) 과한 방법으로 풀거나 (3) 목적을 못 이룬** 경우를 잡는 축이다. 리뷰가 라인 지적에만 매몰되면 이 층위를 통째로 놓친다 — 그러면 작성자도 요청자도 "왜 아쉬운지" 언어화 못 한 채 PR이 머지된다.

> **이 고찰을 4단계 뒤에 두는 이유**: 접근의 실제 복잡도·비용을 코드로 확인해야 ROI를 판단할 수 있기 때문. 단 1단계 맥락 흡수 때 미리 "이 PR이 왜 이 규모인가"라는 가설을 세워두고, 코드를 본 뒤 여기서 확정한다.

**평가 축** (PR 성격에 맞는 것만 — 버그픽스·소규모 PR엔 과하게 적용하지 말 것. 새 모듈·아키텍처 전환·접근 방식 변경에서 특히 중요):

> **아래 "적신호 예"는 축을 이해시키기 위한 샘플일 뿐, 특정 기술·도메인(LLM·배치·UI·결제 등)에 한정되지 않는다.** 실제 PR이 무슨 작업이든 그 맥락에 맞는 적신호를 직접 찾아 적용하라. 예시 문구를 그대로 복붙하지 말 것.

| 축 | 묻는 것 | 적신호 예 (도메인 무관 샘플) |
|----|--------|----------|
| **문제 ↔ 해법 적합성** | 이 문제에 이 접근이 비례하나? | 주 1회 배치에 실시간 스트리밍 인프라 도입(과함) / 반복 장애의 근본 원인에 매번 임시 핫픽스(부족) |
| **변경 규모의 정당성** | 변경의 무게(패러다임 전환 수준)가 문제 대비 정당한가? 더 작은 변경으로 됐나? | 설정 한 줄로 될 일을 새 추상화 레이어로 / 결정적·단순하던 처리를 비결정·자동화로 바꿨는데 그 이유가 PR에 없음 |
| **비용 대비 효과 (ROI)** | 늘어난 복잡도·유지보수·비용·리스크 대비 **산출물(결과·지표) 개선**이 그만한가? | **결과·지표가 기존과 거의 같은데** 복잡도·운영비만 크게 늘었다 → 변경의 정당성에 의문 |
| **요청자·이해관계자 기대 정합** | 원 업무 요청의 본래 의도·기대를 충족하나? "동작은 하는데 그래서 뭐가 나아졌나"가 분명한가? | 기술적으론 인상적이나 요청자가 체감하는 가치가 미미 → "아쉬움"의 정체 |
| **더 단순한 대안** | 더 적은 비용·복잡도로 같은(또는 충분한) 가치를 얻는 길이 있었나? | 기존 라이브러리·규칙·수동 1회 처리로 충분한데 새 시스템을 구축 |
| **숨은 비용** | 표면에 안 드러나는 지속 비용은? | 비결정성·운영 복잡도·신규 의존성·재현 곤란·디버깅 난이도·지속 비용 변동 |

**판단 원칙:**

- **"동작한다"와 "가치 있다"를 분리한다.** 코드가 완벽히 돌아도 목적을 못 이루면 그 사실 자체를 리뷰가 명시한다. 이게 빠지는 게 가장 흔한 누락.
- **큰 변경일수록 입증 책임도 크다.** 아키텍처·접근 방식을 바꾸는 PR은 "되니까"가 아니라 "이 전환이 그만한 값을 한다"를 보여야 한다. **결과가 기존과 비슷하면 그 입증이 실패한 것** → `[확인 필요]` 또는 `[중간]`으로 "이 접근이 목적에 값하는지 재검토"를 제기.
- **요청자 기대와의 갭은 단정 말고 질문으로.** 리뷰어가 요청자 의도를 멋대로 정의하지 말고, "원 요청의 기대치가 X로 보이는데 이 결과가 그걸 충족하나?"를 `[확인 필요]`(누가=요청자/PM, 어떻게=결과 대조)로 남긴다.
- **탓하기가 아니라 의사결정 가시화.** 큰 전환이 정당할 수도 있다(미래 확장성·다른 입력에서의 우위·운영 단순화 등). 그 근거가 PR에 있으면 `[양호]`로 인정하고, **없으면 "근거 보강 요청"**(작성자가 왜 이 규모를 택했는지 설명). 목적을 의심하는 게 아니라, 의심을 닫을 근거를 요구하는 것.

**산출물 반영**: 이 고찰은 개별 라인 지적과 달리 PR 전체에 대한 판단이므로, HTML의 `#background` 섹션에 **"설계·목적 타당성 평가"** 블록으로 넣고(6단계 참조), `.summary` 결론과 `#action-plan`에도 반영한다.

### 5단계: 프론트엔드 테스트 가이드 작성 (해당 시)

변경에 **사용자에게 보이는 UI 변화**가 있으면 (`.tsx`/`.jsx`/`.css`/`.html`/페이지 라우트/컴포넌트), 리뷰 문서에 **수동 테스트 가이드 섹션을 반드시 포함**한다. 백엔드만 바뀐 PR이면 생략.

가이드는 **체크박스 형식**으로 작성하여 사용자가 그대로 따라가며 OK/NG를 표시할 수 있게 한다.

#### 필수 구성

1. **실행 방법**: `pnpm dev` / `npm run dev` 등 명령 + 포트 + 접속 URL
2. **접근 경로**: 어떤 페이지 → 어떤 메뉴/버튼 (예: "Admin → Users 탭 → 사용자 행의 '삭제' 버튼")
3. **시나리오별 체크박스**:
   - 정상 흐름
   - 엣지 케이스 (빈 입력·매우 긴 입력·잘못된 입력·동시 클릭·권한 없는 호출)
   - 반응형 (모바일 767px 이하 vs 데스크톱)
   - 권한별 차이 (로그인/비로그인, 어드민/일반)
4. **확인 포인트**: 화면에서 시각적으로 무엇을 봐야 OK인지 (텍스트·버튼 상태·스타일 등)
5. **회귀 확인**: 이번 변경이 영향줄 수 있는 기존 페이지·기능

#### 형식 예시

```markdown
## 프론트엔드 테스트 가이드

### 실행
`pnpm dev` → http://localhost:3000

### 1. 사용자 삭제 모달 (커밋 2)

**경로**: Admin → Users 탭 → 사용자 행의 "삭제" 버튼

**정상 흐름**:
- [ ] 모달 제목 "정말 삭제하시겠습니까?" 표시
- [ ] 경고 문구 "이 작업은 되돌릴 수 없습니다" 표시
- [ ] 취소·확인 버튼 모두 활성화

**엣지 케이스**:
- [ ] 어드민 권한 없는 사용자 삭제 시도 → 403 토스트
- [ ] 마지막 활성 어드민 삭제 시도 → "활성 어드민 1명 이상 필요" 에러

**반응형 (767px 이하)**:
- [ ] 모달 너비 화면의 90% 이하
- [ ] 버튼 텍스트 줄바꿈 없음

**회귀 확인**:
- [ ] 사용자 목록 조회 정상 (1000명 이상 데이터)
- [ ] 검색·필터 기능 영향 없음
```

### 6단계: HTML 리뷰 문서 작성

**위치**: `./artifacts/code-review/PR-{번호}-{브랜치-슬러그}.html`

#### 작업 절차

1. **`cp`로 템플릿을 출력 경로에 먼저 복사한다** — `OUT=./artifacts/code-review/PR-{번호}-{브랜치-슬러그}.html; mkdir -p "$(dirname "$OUT")"; cp ~/.claude/skills/pr-review/template.html "$OUT"`. 빈 골격을 디스크에 만들어 두는 것이 시작점이다. (템플릿 전체를 Read해서 채운 완성본을 한 번에 Write하지 **않는다** — 아래 점진 작성 원칙 참조.)
2. 본문 placeholder(`{NUMBER}`, `{PR_TITLE}`, `{REPO_URL}`, `{SHA}`, 예시 코드 등)를 실제 PR 정보로 채운다.
3. 디자인 시스템(컬러 토큰·CSS 클래스·레이아웃·심각도 매핑)은 절대 변경하지 않는다. **본문 콘텐츠와 반복 블록만** 채운다.
4. `<!-- ROUND-INSERT-MARKER -->` 주석은 반드시 보존(2차/3차 리뷰 삽입 기준점).

> **점진 작성 원칙 (중간에 끊겨도 살아남게)**: 복사한 파일을 **한 번의 거대한 Edit/Write로 통째 채우지 않는다.** ① 먼저 헤더·요약 슬롯 → ② 커밋 섹션 하나 → ③ 그 안의 리뷰 포인트를 **한 개씩** Edit로 추가하는 식으로, **단위마다 디스크에 반영**하며 진행한다. 리뷰 포인트가 많거나 코드가 길수록 더 잘게 쪼갠다. 이렇게 하면 도중에 오류로 끊겨도 그때까지 채운 내용이 파일에 남는다. 각 Edit는 디자인 클래스를 건드리지 않고 콘텐츠 슬롯만 치환한다.

#### 친절함의 원칙

- 어려운 코드는 비유·약어 풀이·숫자 현황으로 풀어쓴다 (자세한 패턴은 아래 "사용자 친화적 작성 가이드" 참조). **단 강도는 1.5단계에서 추론한 독자 수준에 맞춰 조절** — 전문가 대상이면 과잉 풀이를 자제하고, 신규·비개발 독자가 섞이면 적극 풀이.
- **모든 위치 참조는 풀 경로 + 라인 번호** (위 "위치 명시" 절대 형식 따름). 코드 박스 헤더의 `codebox-file` + 브레드크럼의 `.line`에 명시.
- 코드 스니펫은 관련 라인만 발췌하고 **라인 번호 gutter + 문제 라인 하이라이트**(`.ln.hl`)와 함께.
- 심각도만 태그하고 끝내지 말 것. **리뷰 포인트 작성 7요소**(아래)를 모두 채운다 (필수 5 + 권장 2).
- 처음 보는 사람이 PR 흐름을 따라갈 수 있도록 커밋별로 "**배경 (왜 이 커밋이 필요한가)**"을 한두 줄 덧붙인다.
- **HTML 안전성**: 코드 본문의 `<`, `>`, `&`는 반드시 `&lt;`, `&gt;`, `&amp;`로 이스케이프. JSX·제네릭·shell heredoc에서 자주 깨짐.
- **블록 요소(`.codebox`·`.notice`·`table` 등 `div` 계열)를 `<p>` 안에 넣지 않는다** — 브라우저가 `<p>`를 자동 종료시켜 stray `</p>`가 생기고 DOM이 틀어진다. 권장 조치에 코드 예시를 붙일 땐 `<p>설명</p>`을 닫은 **뒤에** `.codebox`를 형제 요소로 둔다.
- **코드 한 줄이 아주 길어도 임의로 쪼개지 말 것** — 가로 스크롤은 `.codebox-body`가 처리한다(템플릿 `.main > .content { min-width: 0 }` 전제).

#### 리뷰 포인트 작성 7요소 (5필수 + 2권장)

각 리뷰 포인트는 **반드시 `<details class="review-point {severity}">`** 카드 한 개로 구성. 안에 다음 순서로 채운다.

**필수 5요소:**

1. **summary**: 심각도 태그 + 번호·요약 (위치는 본문 브레드크럼에서 표기)
   ```html
   <summary>
     <span class="severity-tag critical">심각</span>
     <span class="rp-title">1-1. 비밀번호 하드코딩</span>
   </summary>
   ```
2. **브레드크럼** (`.breadcrumb`): 커밋 › 파일 › 라인 + GitHub 라인 직링크. **위치 인지의 핵심 — 반드시 작성**.
3. **코드/맥락** (`<h4>코드</h4>` + `.codebox`): Mac 헤더(점·파일명·언어 뱃지·GitHub·복사) + 라인 번호 gutter + 문제 라인 `.ln.hl` 하이라이트.
4. **문제 분석** (`<h4>문제</h4>`): 무엇이·왜 문제인가, 동작상 영향, 컨벤션과의 관계.
5. **권장 조치** (`<h4>권장 조치 <span class="action-tag ...">...</span></h4>`): 다음 중 **하나는 반드시** 명시
   - `action-tag required` → **이번 PR 수정 필수** (보통 심각)
   - `action-tag recommended` → **이번 PR 수정 권장** (보통 중간)
   - `action-tag optional` → **선택사항** (보통 경미)
   - `action-tag out-of-scope` → **이번 PR 범위 밖** (후속 이슈, `gh issue create` 명령 첨부)
   - 가능하면 **방법 A / 방법 B** 식으로 두 가지 대안 제시

**권장 2요소** (비전공자 친화 — 어렵거나 영향이 큰 항목에서 적극 활용). **1.5단계 독자 추론에 따라 선별**: 독자가 전문가로 추정되면 비직관적이거나 고영향인 항목에만 달고 **전 항목 도배 금지**. 신규·비개발 독자가 섞이면 적극 활용:

6. **쉽게 말하면** (`.plain-talk`): 비전공자가 이해할 수 있는 비유·풀이. 도메인 지식 없는 사람도 2초 안에 "뭐가 문제인지" 알도록.
7. **왜 중요한가** (`.impact`): 사용자 영향 / 운영 영향 / 비즈니스·법적 영향을 bullet로. "왜 빨간 불인가"를 즉시 이해.

**도움말**은 필요 시 본문 끝에 `<h4>도움말</h4>` + `<p>`로 추가 (검증 명령·테스트 방법·관련 자료).

> **단편적 리팩토링 제안 자제 규칙**:
> 단일 위치의 스타일·구조 제안을 적기 전에 다음을 검증한다.
> - **동일 패턴이 코드베이스 다수 위치(3곳 이상)에 있는가?** → 다수면 별도 후속 이슈로 일괄. 이번 PR에서는 대표 1건만 언급 + "Scope 외 참고".
> - **단발 + 코드베이스 일관 위반 아님** → `optional`로 다운그레이드하거나 아예 적지 않는다.
> - **컨벤션 문서로 명문화된 규칙 위반인 경우만** `recommended` 이상.

#### 심각도 → CSS 클래스 매핑 (필수)

template.html은 단축된 클래스명을 쓴다. `severity-` 접두사는 `severity-tag`에만 붙고, 좌측 컬러 보더와 카운트에는 단축 클래스만 사용.

| 태그 | `<details>` / `.count` 클래스 | `severity-tag` 클래스 | `.priority` 클래스 |
|------|------|------|------|
| `[심각]` | `critical` | `critical` | `required` |
| `[중간]` | `medium`   | `medium`   | `recommended` |
| `[경미]` | `minor`    | `minor`    | `optional` |
| `[참고]` | `info`     | `info`     | `fyi` |
| `[양호]` | `good`     | `good`     | — |
| `[확인 필요]` | `check` | `check` | — |

[심각]인 경우 `<details>`에 `open` 속성 — 기본 펼침. 그 외는 닫힌 채로 두어 한눈에 스캔 가능.

#### 핵심 컴포넌트 사용법

**1. 브레드크럼 (`.breadcrumb`)** — 어디 커밋·파일·라인인지 즉시 인지
```html
<div class="breadcrumb">
  <a href="#commit-1">커밋 1</a>
  <span class="sep">›</span>
  <span class="file">src/foreign_flow/db.py</span>
  <span class="sep">›</span>
  <span class="line">L22~28</span>
  <span class="sep">·</span>
  <a href="{REPO_URL}/blob/{SHA}/src/foreign_flow/db.py#L22-L28" target="_blank">GitHub ↗</a>
</div>
```

**2. 코드 박스 (`.codebox`)** — Mac 헤더 + 라인 번호 + 하이라이트
- 헤더: `mac-dots` 3개 점 + `codebox-file`(풀 경로) + `codebox-lang`(언어 뱃지) + `codebox-gh`(GitHub 라인 링크) + `codebox-copy`(복사 버튼)
- 본문: `.codebox-gutter` 라인 번호 (실제 파일 라인 번호와 일치) + `.codebox-code` 안에 `<span class="ln">...</span>` 한 줄씩
- 문제 라인은 `<span class="ln hl">`로 노란 배경 강조
- diff: `<span class="ln add">` 녹색 / `<span class="ln del">` 빨강
- 구문 강조: `.kw`(키워드) `.fn`(함수) `.str`(문자열) `.var`(변수) `.cm`(주석) `.nm`(숫자) — 수동 wrapping

```html
<div class="codebox">
  <div class="codebox-head">
    <div class="mac-dots"><span></span><span></span><span></span></div>
    <span class="codebox-file">src/foreign_flow/db.py</span>
    <span class="codebox-lang">python</span>
    <a class="codebox-gh" href="{REPO_URL}/blob/{SHA}/...#L22-L28" target="_blank">L22-28 ↗</a>
    <button class="codebox-copy" onclick="copyCode(this)">복사</button>
  </div>
  <div class="codebox-body">
    <div class="codebox-gutter">22
23
24</div>
    <div class="codebox-code"><span class="ln"><span class="kw">def</span> <span class="fn">load</span>():</span><span class="ln hl">    <span class="str">"비밀번호 노출 라인"</span></span></div>
  </div>
</div>
```

**3. Before/After 2열 비교** (`.code-compare`)
```html
<div class="code-compare">
  <div>
    <div class="code-compare-label before">Before · 현재</div>
    <div class="codebox before">...</div>
  </div>
  <div>
    <div class="code-compare-label after">After · 권장</div>
    <div class="codebox after">...</div>
  </div>
</div>
```

**4. 쉽게 말하면 (`.plain-talk`)** — 비전공자용 한 줄 요약
```html
<div class="plain-talk">
  <span class="label"><span class="icon">💡</span>쉽게 말하면</span>
  <p>DB 비밀번호가 코드 파일에 그대로 적혀있어 GitHub에서 누구나 볼 수 있는 상태입니다.</p>
</div>
```

**5. 왜 중요한가 (`.impact`)** — 영향도 박스
```html
<div class="impact critical-bg">
  <span class="label"><span class="icon">🎯</span>왜 이게 중요한가</span>
  <ul>
    <li><strong>사용자 영향</strong>: 데이터 유출 가능</li>
    <li><strong>운영 영향</strong>: Secret rotation 필요</li>
  </ul>
</div>
```
- 심각도가 [중간]인 경우 `.impact.medium`으로 변경.

**6. 작성자 답글 (`.author-reply`)** — `<blockquote>` 아님, 전용 컴포넌트
```html
<div class="author-reply">
  <span class="by">작성자 답변 · abc1234</span>
  이건 의도된 동작입니다. 별도 이슈로 처리하겠습니다.
</div>
```

**7. 일반 notice 박스** — 보조 정보·경고·성공
```html
<div class="notice info"><span class="label">참고</span>...</div>
<div class="notice warn"><span class="label">주의</span>...</div>
<div class="notice success"><span class="label">완료</span>...</div>
<div class="notice critical"><span class="label">경고</span>...</div>
```

**8. 용어 풀이 (`abbr` / `.term`)** — hover 시 풀네임 표시
```html
<abbr title="Loan-To-Value ratio (담보인정비율)">LTV</abbr>
<span class="term" title="Cross-Site Scripting (악성 스크립트 주입)">XSS</span>
```

#### 문서 구조 (template.html이 강제하는 순서)

template.html은 다음 순서를 강제한다. **순서·섹션 ID·번호는 변경 금지** (TOC 링크가 깨짐).

| 위치 | 섹션 ID | 내용 |
|------|--------|------|
| Header (full-width) | `pr-header` | PR 메타 + GitHub 링크 |
| Header (full-width) | `.summary` | 한눈 요약 카운트 + 결론 1~3문장 |
| 좌측 Sticky | `#toc` | 목차 (active 자동 하이라이트, 커밋별 하위 트리) |
| 본문 | `#background` | PR 배경 + PR description 4가지 검증 + 설계·목적 타당성 평가(4.5단계) |
| 본문 | `#commits` | 커밋 순서 표 (오래된 순) |
| 본문 | `#review` | 커밋별 리뷰 — `.commit-block` 반복 |
| 본문 | `#frontend-test` | 프론트엔드 테스트 가이드 (UI 변경 있으면) |
| 본문 | `#summary-table` | 전체 요약 표 |
| 본문 | `#action-plan` | 리뷰 진행 순서 추천 + 합계 시간 |
| 본문 끝 | `<!-- ROUND-INSERT-MARKER -->` | 2차/3차 리뷰 삽입 기준점 |

각 커밋 블록은 `id="commit-N"`, 각 리뷰 포인트는 `id="rp-N-M"`로 고유 ID 부여 — TOC·브레드크럼이 anchor 링크로 사용.

#### PR description 4가지 검증 (배경 섹션에 포함)

작성자의 PR description이 다음 4가지를 담고 있는지 평가하고, 누락은 리뷰 문서에 명시:

| 검증 항목 | 의미 | 누락 시 처리 |
|-----------|------|--------------|
| **개발 의도** | 왜 이 PR이 필요한가 | 보강 요청 (Comment, Blocking 아님) |
| **핵심 흐름** | 무엇이 어떻게 동작하는지 | 보강 요청 (큰 PR일수록 강하게) |
| **트레이드오프·결정** | 대안 검토와 선택 근거 | 보강 요청 (특히 새 모듈·아키텍처 변경) |
| **코드 밖 맥락** | 외부 시스템·정책·이전 결정 | 치명적이면 [확인 필요] |

**단순 상세 ≠ 좋은 메시지**. 긴 설명이라도 4가지가 빠지면 "diff 옆 캡션" 수준. 짧아도 4가지 다 담기면 좋은 메시지.

#### 설계·목적 타당성 평가 (배경 섹션 — 4.5단계 산출)

4.5단계 고찰을 `#background` 섹션 안에 블록으로 싣는다. **새 CSS 클래스 금지** — `.table-wrap > table` + `.notice.*` + `severity-tag`만 재사용. 변경 규모가 작은 PR(버그픽스·소규모 개선)이면 이 블록은 생략하거나 한 줄로 압축한다. **새 모듈·아키텍처 전환·접근 방식 변경 PR에서 필수.**

- **평가 축별 한 줄 판정 표** (축 / 판정 / 근거). 판정엔 `severity-tag` 재사용(`good`=정당성 섰음, `check`=요청자·작성자 확인 필요, `medium`=ROI/규모 의문).
- 표 아래 **종합 한 줄**: "이 변경이 목적·비용 대비 정당한가" 결론. ROI 의문·요청자 기대 갭이 있으면 `.notice.warn`, 정당성이 잘 선 경우 `.notice.success`.
- 이 판정은 개별 코드 지적과 **별개 항목**으로 `.summary` 결론과 `#action-plan`에도 반영한다.

HTML 예 — **아래는 한 사례(여기서는 "주 1회 배치 집계를 실시간 스트리밍으로 전환했으나 지표는 비슷"한 케이스)의 구조만 보여주는 샘플이다. 어느 도메인이든 무방하며, 평가축은 모든 작업에 적용된다. 표 내용·근거는 실제 PR 맥락에 맞게 새로 쓴다(이 예시 문구를 그대로 복붙하지 말 것).**
```html
<h3>설계·목적 타당성 평가</h3>
<div class="table-wrap">
  <table>
    <thead><tr><th>축</th><th>판정</th><th>근거</th></tr></thead>
    <tbody>
      <tr>
        <td>변경 규모의 정당성</td>
        <td><span class="severity-tag check">확인 필요</span></td>
        <td>주 1회로 충분하던 집계를 실시간 스트리밍 파이프라인으로 전환. 운영 복잡도를 크게 키우는 큰 폭인데 PR에 그 근거(실시간성이 실제로 필요한 사유)가 없음</td>
      </tr>
      <tr>
        <td>비용 대비 효과(ROI)</td>
        <td><span class="severity-tag medium">중간</span></td>
        <td>대시보드 지표가 기존 일배치 결과와 유의미한 차이 없음 → 늘어난 인프라·운영비 대비 산출물 개선이 불분명</td>
      </tr>
      <tr>
        <td>요청자 기대 정합</td>
        <td><span class="severity-tag check">확인 필요</span></td>
        <td>요청자 체감 가치가 미미("아쉬움"). 원 요청의 기대치(실시간성이 정말 필요했나)를 요청자/PM과 대조 필요</td>
      </tr>
    </tbody>
  </table>
</div>
<div class="notice warn">
  <span class="label">종합</span>
  코드 구현 자체는 견고하나 <strong>"동작한다"가 "목적에 값한다"로 이어지지 못했다.</strong>
  큰 아키텍처 전환의 입증 책임(결과 개선)이 충족되지 않음 — 머지 전 작성자에게 "이 접근을 택한 근거"와
  "기존 대비 무엇이 나아지는가"의 보강을 요청하고, 요청자와 기대치를 대조할 것.
</div>
```

#### "이 PR의 맥락" 박스 (선택, 핫픽스·큰 구조 변경)

배경 카드 바로 아래에 `<div class="notice critical">` 또는 `<div class="notice warn">`로 5요소(증상·원인·수정 핵심·영향·결과) 박스 추가.

#### 빠르게 Approve 가능한 항목 / GitHub 코멘트 분류

- **Blocking (Request Changes)**: 머지 전 반드시 (`critical`)
- **Nit (코멘트만)**: 의견 전달, 머지 가능 (`minor`)
- **Future work**: 후속 이슈 링크 (`info`)
- **Positive feedback**: 잘된 부분 (`good` — 균형 유지)

#### 심각도 태그

| 태그 | 의미 |
|------|------|
| `[심각]` | 버그·데이터 손실·보안 취약점·장애 가능성. 머지 전 필수 해결 |
| `[중간]` | 잠재 버그·엣지 케이스 미처리·이해 부채 고위험. 가급적 해결 권장 |
| `[경미]` | 가독성·구조·소소한 개선. 후속 가능 |
| `[참고]` | 정보 공유 · 향후 고려 사항 |
| `[양호]` | 잘 작성된 부분 (Positive feedback) |
| `[확인 필요]` | 리뷰어가 판단 못 한 부분 — 작성자에게 질문 필요 |

#### 심각도 판정 트리 (헷갈릴 때)

**선결 조건**: 아래 트리를 타기 전에 4단계 "표면이 아니라 추적으로 판단"의 **방향 1**을 통과해야 한다. "가능성"은 *추적으로 도달 가능성을 확인한 뒤*의 가능성이다 — 줄 모양만 보고 상정한 가능성은 트리에 넣지 않는다(도달 불가면 미기재 또는 `[참고]`, 못 닫으면 `[확인 필요]`).

| 질문 | YES → 심각도 |
|------|--------------|
| 지금 상태로 버그·장애·보안 취약? (실제 트리거 경로 확인됨) | `[심각]` |
| 미래에 버그로 발전할 가능성 큼 (도달 경로 + 재현율 높음)? | `[중간]` |
| 엣지 케이스·성능 저하 (도달 가능성 추적으로 확인)? | `[중간]` |
| 가독성·코드 스타일 개선만 필요? | `[경미]` |
| 정보 공유·향후 고려 / 추적상 안전하나 의존이 암묵적? | `[참고]` |
| 추적했으나 코드 밖 맥락이라 못 닫음, 작성자 답이 필요? | `[확인 필요]` |

#### 심각도 처리 매핑

| 심각도 | 이번 PR 처리 | GitHub 코멘트 분류 | 후속 |
|--------|-----------|---------------------|------|
| `[심각]` | 필수 수정 | **Blocking** (Request Changes) | — |
| `[중간]` | 가급적 수정 | Comment(강한 권유). 큰 작업이면 이슈 링크 | 이슈 등록 가능 |
| `[경미]` | 시간 되면 | **Nit** (코멘트만) | future-work 이슈 |
| `[참고]` | — | 정보성 코멘트 | — |

#### `[확인 필요]` 항목 구체화

`[확인 필요]` 태그만 달고 끝내지 말고 다음 4가지를 모두 명시:

- **누가**: 작성자 / 리뷰어 / 테스터 / PM
- **언제**: 머지 전 / 배포 후 / 1주일 내 / 다음 스프린트
- **어떻게**: 로컬 테스트 / staging 모니터링 / 이슈 검색 / 데이터 검증
- **기대 결과**: 무엇을 확인하면 OK인지

예시:
> **작성자가 머지 전**: DB 50GB 시뮬레이션으로 백업 소요시간이 TTL 600초를 넘는지 측정. 600초 이내면 OK, 넘으면 TTL 증가 필요.

### 7단계: 추가 리뷰·보강 — HTML append 전략

> **먼저: 라운드 골격은 복사한다.** `template.html`(=이 보고서) 맨 아래 `<!-- ROUND-INSERT-MARKER -->` **바로 위**에 `라운드 골격 · COPY-PASTE TEMPLATE` 주석이 박혀 있다. S1/S3 정식 라운드는 그 안의 `<section class="round-divider" id="round-【N】"> … </section>`을 **통째로 복사**해 마커 위에 붙이고 `【…】`만 채운다. 아래 HTML 예시는 그 골격의 설명용 사본이다 — 기억으로 새로 짜지 말 것(append 라운드가 디자인 시스템에서 이탈하는 전형적 원인).

기존 `.html` 파일에 추가 작성할 때는 **(a) 시나리오를 먼저 분류**하고, **(b) 디자인 시스템(template.html 클래스) 외에 새 컴포넌트를 정의하지 않으며**, **(c) 종결 섹션에 끼워 넣지 않는다**.

#### 추가 작성 시나리오 (3종) — 어디에 어떻게 넣을지

| 시나리오 | 트리거 | 위치 | 형식 |
|---------|--------|------|------|
| **S1. 정식 라운드** | 작성자가 신규 커밋 푸시 → 대응 검증 | `ROUND-INSERT-MARKER` 바로 위 | `<section class="round-divider" id="round-2">` 신설 |
| **S2. 기존 섹션 보강** | 사용자 피드백으로 기존 내용 보완 ("배경이 이해 안 됨" 등) | 보강 대상 섹션 **내부 끝** | `<div class="notice info">` 보강 마커 + 본문 추가 |
| **S3. 후속 분석/보완** | 신규 커밋 없이 놓친 부분 추가 분석 | `ROUND-INSERT-MARKER` 바로 위 | `<section class="round-divider" id="addendum-1">` — 클래스 재사용, ID만 다름 |

#### 절대 추가하지 말 것 (금지선)

다음 위치에는 **새 내용을 끼워 넣지 않는다**. 별도 라운드 또는 보강 마커로 분리한다.

- `#action-plan` (진행 추천) — 1차 리뷰 종결 섹션
- 본문 끝 요약 표 (`#summary-table` 등) — 1차 리뷰 합계
- `<div class="notice success">` (전체 평가) — 1차 결론
- 닫는 `</body>` · `</html>` 태그 뒤

이 금지선을 어기면 라운드 구분이 모호해져 리뷰어·작성자 모두 어디까지가 1차이고 어디부터가 추가인지 인지 불가.

#### 디자인 시스템 재사용 (절대 규칙)

**새 CSS 클래스·인라인 스타일·신규 색상 토큰 추가 금지.** template.html의 기존 컴포넌트만 사용:

- 카드: `.review-point.{severity}`, `.card`
- 뱃지: `.severity-tag.{critical|medium|minor|check}`
- 박스: `.notice.{critical|warn|info|success}`
- 표: `.table-wrap > table`
- 상태: `.status.{resolved|unresolved|partial|pending}`
- 구분: `.round-divider`, `.section-head`

새 컴포넌트가 필요하다고 느끼면 → **기존 조합으로 표현 가능한지 먼저 검토**. 정말 없으면 사용자에게 디자인 시스템 확장 여부 확인.

#### S1 — 정식 라운드 (신규 커밋 케이스)

#### 삽입 방법 (Edit 도구 사용, 2단계 필수)

**1단계: 본문 섹션 삽입** — `ROUND-INSERT-MARKER` 바로 위에 round 섹션 추가

```
Edit:
  old_string: <!-- ROUND-INSERT-MARKER -->
  new_string: <section class="round-divider" id="round-2"> ... </section>

  <!-- ROUND-INSERT-MARKER -->
```

마커는 절대 제거하지 말 것 — 다음 라운드(3차·4차)의 기준점이다.

**2단계: TOC 업데이트 (필수)** — 사이드바 목차에 새 라운드 항목 추가. 반드시 기존 마지막 `<li>` 뒤에 삽입.

```
Edit:
  old_string: <li><a href="#action-plan">5. 진행 추천</a></li>
    </ul>
  </nav>
  new_string: <li><a href="#action-plan">5. 진행 추천</a></li>
      <li><a href="#round-2">6. 2차 리뷰</a>
        <ul>
          <li class="sub"><a href="#rp-r2-1">R2-1. 항목 요약</a></li>
          <!-- 신규 rp 항목 수만큼 반복 -->
        </ul>
      </li>
    </ul>
  </nav>
```

> TOC를 업데이트하지 않으면 사이드바에 "5. 진행 추천" 아래 묻혀 보인다. **2단계는 선택이 아니다.**

#### 삽입 후 자체검증 (append/갱신 완료 확인 — 생략 금지)

HTML 문서를 append·갱신했으면, 완료로 보고하기 전에 **실제로 제대로 갱신됐는지** 아래를 직접 확인한다. "Edit가 성공했으니 됐겠지"로 넘기지 않는다 — 마커 위치·anchor 누락은 Edit 성공과 무관하게 발생한다.

- [ ] `<!-- ROUND-INSERT-MARKER -->` 가 **여전히 존재**하고, 새 섹션이 그 **바로 위**에 들어갔는가? (마커가 삭제·이동되지 않았는가)
- [ ] 새 라운드/항목이 **TOC(`#toc`)에 추가**됐고, TOC 링크의 `href="#..."`가 본문의 실제 `id`와 **정확히 일치**하는가? (깨진 anchor 없음)
- [ ] 종결 섹션(`#action-plan`·`#summary-table`·1차 `notice success`)과 닫는 `</body>`·`</html>`를 **건드리지 않았는가**?
- [ ] 새로 쓴 컴포넌트가 template.html에 **정의된 클래스만** 쓰는가? (신규 클래스·인라인 색 추가 0)
- [ ] 새 코드 박스/표의 placeholder(`{SHA}`·`{REPO_URL}` 등)와 빈 슬롯이 **모두 실제 값으로** 치환됐는가?
- [ ] 코드 본문의 `<`·`>`·`&`가 `&lt;`·`&gt;`·`&amp;`로 이스케이프됐는가?

확인 수단: 위 항목 중 마커 카운트·anchor 정합·문서 종료에 더해 **디자인 시스템 정합**(정의 안 된 `var(--x)`·`.review-point`의 `.rp-content` 래퍼 누락·`priority`/`action-tag`/`severity-tag`의 모디파이어 누락)까지 번들 스크립트가 FAIL로 자동 판정한다 — append 라운드가 template에서 이탈하는 전형이다. 미치환 슬롯은 코드박스의 합법적 `{CAPS}` 리터럴과 구분이 안 되므로 **WARN(목록만)으로 띄우고 종료코드엔 반영 안 함** — 목록을 보고 진짜 미치환인지 육안 판단한다.

```bash
bash ~/.claude/skills/pr-review/scripts/verify.sh <리뷰_HTML_경로>
# 종료코드 0=FAIL 없음, 1=FAIL 있음. WARN(placeholder 목록)은 종료코드와 무관 — 직접 확인.
# CSS 변수·클래스·컴포넌트 래퍼 정합까지 자동 검사. 남는 육안 확인은 HTML 이스케이프·미세 간격뿐.
```

스크립트가 여전히 못 잡는 것(`<`·`>`·`&` 미이스케이프, 색·간격의 미세한 어긋남)과 WARN으로 뜬 placeholder는 위 체크리스트로 직접 확인한다.

#### 정형화된 2차/3차 체크리스트

신규 커밋이 들어왔을 때:

1. **변경 파일 확인**: `git diff <이전라운드 마지막 SHA> <신규 SHA> --stat`
2. **이전 지적 해결 여부 표** (필수 — 모든 1·2차 항목을 빠짐없이 매핑)
3. **신규 발견 항목** (1차와 동일한 5요소 `<details>` 카드 형식)
4. **N차 리뷰 요약** + **전체 평가** (Approve 가능 여부 한 줄 결론)

#### 해결 표시 기호 (status 클래스 매핑)

template.html의 `.status` 클래스는 `::before`로 기호를 자동 표시한다. 텍스트만 적으면 됨.

| 표시 | 클래스 | HTML |
|------|------|------|
| ✓ 해결 | `status resolved` | `<span class="status resolved">해결</span>` |
| ✗ 미해결 | `status unresolved` | `<span class="status unresolved">미해결</span>` |
| ◐ 부분 해결 | `status partial` | `<span class="status partial">부분 해결</span>` |
| ? 확인 필요 | `status pending` | `<span class="status pending">확인 필요</span>` |
| 추후 해결 (취소선) | `status resolved` + 별도 noting | `<del>확인 필요</del> <span class="status resolved">해결</span>` |

#### S2 — 기존 섹션 보강 (사용자 피드백 케이스)

신규 커밋 없이 기존 1차 리뷰 내용을 보완 요청받은 경우 (예: "배경이 이해 안 됨", "이 부분 더 자세히"). **별도 라운드를 만들지 않고 보강 대상 섹션 내부에서 끝낸다.**

##### 삽입 위치

보강 대상 섹션의 **내부 끝** (해당 `<section>` 닫는 태그 직전). 다른 섹션으로 넘어가지 말 것.

##### 보강 마커 (필수)

해당 섹션 내부 끝에 다음 박스를 먼저 삽입한 뒤 본문을 잇는다. 사용자가 "여기 보강됐구나"를 즉시 인지할 수 있어야 한다.

```html
<div class="notice info" style="margin-top:14px">
  <span class="label">보강 (2026-05-15)</span>
  <strong>사유</strong>: 사용자 피드백 — 배경 섹션이 이해하기 어렵다는 지적<br>
  <strong>추가 내용</strong>: ASCII 다이어그램, 핵심 용어 표, 안전장치 비교표
</div>

<!-- 이어서 동일 섹션 내에 표·카드·문단으로 본문 추가 -->
```

##### 금지 사항

- 보강 본문에 새 CSS 클래스·인라인 색상 추가 금지 (기존 `.table-wrap > table`, `.notice.*`, `<details class="review-point">` 등만 사용)
- 보강 내용을 `#action-plan`·`#summary-table`·`<div class="notice success">` 등 종결 섹션에 끼워 넣지 말 것 — 항상 보강 대상 섹션 안에 머무른다
- 보강이 많아 섹션이 너무 길어지면 → 시나리오를 **S3(후속 분석 라운드)**로 승격해서 분리 검토

#### S3 — 후속 분석 라운드 (신규 커밋 없음)

신규 커밋은 없지만 추가 분석·보완 리뷰가 필요한 경우 (예: 1차에서 다루지 못한 영역, 검증 깊이 부족 영역의 재검토). **`round-divider` 클래스를 재사용하고 ID만 다르게** 한다.

##### 삽입 위치 (2단계 필수)

`<!-- ROUND-INSERT-MARKER -->` 바로 위 (S1과 동일). **TOC 업데이트도 S1과 동일하게 필수.** `id="addendum-1"` 기준으로 TOC 항목 추가.

```html

    <span class="label">분석 범위</span> <code>backend/foo.py</code> 외 N개

    <summary>
      <span class="severity-tag medium">중간</span>
```

##### S1과의 차이

| 구분 | S1 (정식 라운드) | S3 (후속 분석) |
|------|-----------------|----------------|
| 트리거 | 신규 커밋 푸시 | 신규 커밋 없음, 분석 보완 |

| "이전 지적 해결 표" | 필수 | 선택 (해결 검증 목적 아니면 생략) |
| `round-meta` 사유 | "대응 검증" | "보완 분석", "놓친 영역 재검토" |

S3는 R2/R3보다 가벼운 라운드로 운영. 본문 항목 수도 보통 적음 (1~3개).

## 사용자 친화적 작성 가이드

### 풀어쓰기 패턴 (3종)

도메인 지식 없는 팀원이 섞여 있다고 1.5단계에서 추론한 경우, 그가 2초 안에 "뭐가 문제인지" 알 수 있게 한다. 다음 패턴을 조합하되, **전문가만 읽는 문서라면 비직관·고영향 항목에 선별 적용**(전 항목 강제 아님).

#### 패턴 1: 약어·전문 용어 풀이

```markdown
틀림: "ReplacingMergeTree 버전 컬럼 미지정"
맞음: "ReplacingMergeTree(버전컬럼명) — ClickHouse가 중복 행 제거 시 어느 행을 최신으로 볼지
     결정하는 기준 컬럼이 미설정. 미설정 시 비결정적 행이 남음."
```

#### 패턴 2: 일상 비유 (기술 설명 뒤에 추가)

```markdown
**기술 설명**: queryKey가 `["stocks", query]`로 query마다 달라져 두 컴포넌트가 서로 다른 캐시 엔트리를 만든다. 의도는 단일 호출이지만 실제로는 N번 호출.

**쉽게 말하면**: 같은 빵집(API)을 두 사람이 동시에 가는데, 손에 든 주문서가 미세하게 달라서 빵집은 "아, 다른 주문이네" 하고 빵을 두 번 굽는 상황. 주문서를 통일해야 한 번만 굽는다.

**권장 조치**: queryKey를 `["stocks"]`로 고정, query는 select 옵션으로 분리.
```

비유는 **추가**다. 정확한 기술 설명을 빼고 비유만 쓰지 않는다. 도메인 지식이 필요하거나 비직관적인 항목에만.

#### 패턴 3: 숫자로 현황 제시

```markdown
틀림: "메모리 사용량이 높다"
맞음: "메모리 RSS +1,397MB → +3.4MB (97.5% 개선), 백업 소요시간 104.8초"

틀림: "TTL이 부족할 수 있다"
맞음: "TTL 600초, 실측 소요시간 104.8초 (현재 5.7배 마진). DB 5GB 도달 시 ~520초 예상 → 마진 1.15배로 축소"
```

### 코드 스니펫 표시

- 관련 라인만 발췌. 100줄 통째 붙이지 않는다.
- 첫 줄에 풀 경로 + 라인범위 주석 (`<span class="comment">`로 감싸 회색 처리).
- 변경 전후 비교는 `# Before` / `# After` (또는 `# 현재` / `# 권장`).
- **HTML 안전성**: 코드 본문의 `<`, `>`, `&`는 반드시 `&lt;`, `&gt;`, `&amp;`로 이스케이프. JSX·제네릭·heredoc에서 자주 깨진다.

HTML 표현 예:

```html
<pre><code><span class="comment"># backend/app/core/llm.py 라인 22~26</span>
MODEL_PRICING: dict[str, dict[str, float]] = {
    "gemini-2.5-flash": {"input": 0.30, "output": 2.50},
    ...
}

<span class="comment"># 라인 32 — 가격 미등록 모델이 STRUCTURED_SEARCH_MODELS에 포함됨</span>
STRUCTURED_SEARCH_MODELS: set[str] = {"gemini-3.1-pro-preview", "gemini-3-flash-preview"}</code></pre>
```

**Before/After 분할 권장**: 한 `<pre>`에 둘 다 넣지 말고 두 블록으로 나눠 시각적 구분 (각 블록의 첫 줄에 `# Before` / `# After` 주석).

### 좋은 변형 패턴 (필요 시 사용)

기본 형식을 따르되, 아래 변형은 특정 상황에서 가독성을 크게 높이므로 적극 사용한다.

#### A. "이 PR의 맥락" 박스 — 핫픽스·큰 구조 변경에서

배경 요약과 별개로, 헤더 직후에 "증상 → 원인 → 수정 핵심 → 영향 범위 → 결과" 5요소를 박스화. 미래에 이 결정을 재검토할 때 즉시 이해 가능.

**HTML**: `#background` 섹션 안에 `<div class="notice info">` 박스 (또는 핫픽스의 경우 `notice critical`).

```html
<div class="notice critical">
  <strong>증상</strong>: 매일 03:00 KST에 Python 프로세스가 OOM Kill로 종료<br>
  <strong>원인</strong>: <code>backup_service.py:140</code>이 <code>cursor.fetchall()</code>로 전체 행을 메모리에 올림 (테이블당 ~1GB)<br>
  <strong>수정 핵심</strong>: (1) <code>DECLARE CURSOR</code> + <code>FETCH 2000</code> 청크 스트리밍, (2) Redis 분산 락<br>
  <strong>영향 범위</strong>: 백업 생성/복원 경로, 스케줄러 구조<br>
  <strong>결과</strong>: RSS 증가량 +1,397MB → +3.4MB (97.5%↓), 104.8초 만에 정상 완료
</div>
```

#### B. 공통 이슈 섹션화 — 여러 파일에 같은 패턴이 반복될 때

5개 SQL 파일 모두에 동일한 컨벤션 위반이 있는 상황에서 파일별 5번 반복하지 말고 별도 카드로 묶기.

**HTML**: `<details class="review-point medium">` 한 개로 묶고 `<h4>대상</h4>`에 파일 목록 명시. `rp-loc`은 `migrations/003~007_*.sql (5개)`처럼 표시.

#### C. 도식 + 비유 — 새로운 모듈·아키텍처 변경에서

ASCII 다이어그램으로 흐름을 그리고, 일상 비유 한 줄을 덧붙여 비개발자도 이해 가능하게.

**HTML**: 다이어그램은 `<pre><code>` 그대로, 비유는 `<div class="notice info">` (또는 `<p>` + `<strong>비유</strong>:`).

```html
<h4>구조 변화</h4>
```

## 리뷰 작업 시 주의사항

- **읽기 전용**. PR 브랜치 fetch는 OK, **commit/push 절대 금지**.
- 변경 규모가 크면(파일 10개 이상 또는 500줄 이상) **파일 그룹별로 나눠 작성**하고 중간 진행 상황을 사용자에게 공유한다.
- lint·formatter·타입 체커가 잡을 수 있는 문제는 별도로 지적하지 않는다. **인간 리뷰어가 봐야 할 것**에 집중.
- 이번 PR 범위 밖이지만 발견한 이슈는 **별도 섹션(Scope 외 참고)** 또는 **`[이번 PR 범위 밖]` 태그**로 분리. 가능하면 `gh issue create` 명령 함께.
- 수정 제안에는 반드시 **논리적 근거와 대안**을 함께. 가능하면 **방법 A / 방법 B**로 두 가지 제시.
- 작성자의 답글이 "이건 의도된 동작"이라 해도 본인 판단으로 재검토. 작성자가 항상 맞지는 않다.
- Submodule 변경이 포함되면 **별도 리포 확인 필요**임을 문서에 명시.
- CI 실패가 있으면 어떤 검사가 왜 실패했는지 헤더에 함께 적는다.
- 리뷰 문서는 본인이 미래에 다시 읽을 수도, 작성자에게 그대로 전달할 수도 있다. **항상 자기완결적**으로 작성.
